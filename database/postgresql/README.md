# PostgreSQL scripts (T4)

The `contosocare` database on T4, the Azure Database for PostgreSQL flexible server `pgflex01-<deploymentId>` (Phase 24, [ADR 0019](../../docs/adr/0019-t4-postgresql-flexible-server.md)). They're the PostgreSQL counterpart of [`database/common`](../common/README.md): the same synthetic clinic business, the same demo control model, and bounded scenario steps.

| Script | What it creates |
|---|---|
| `010-schema.sql` | Schemas `care` and `demo`, the business tables, their indexes, `demo.seed_state`, and `demo.fn_rand` (deterministic MD5-based values) |
| `020-seed.sql` | `demo.usp_seed_contosocare(scale, force)`: a deterministic, set-based seed (scale 1: 100 providers, 10,000 patients, 40,000 appointments, 20,000 encounters and claims, 2,000 work items) |
| `110-demo-control.sql` | Run bookkeeping (`demo.scenario_runs`, `demo.scenario_run_events`, `demo.scenario_control`), `demo.fn_scenario_catalog()` (the database layer of the bounds), stop requests, the session tools, cleanup, `demo.io_scratch`, and `demo.replica_lag_marks` (2026-11-13, `replica-lag`'s marks) |
| `120-scenario-functions.sql` | One short, bounded step per scenario: `healthy-baseline`, `cpu-pressure`, `locking-blocking`, `io-pressure`, `connection-surge`, `idle-in-transaction`, `missing-index` (2026-11-04: its step only checks the run; the runner sends the lookups as top-level statements, so Query Store captures them for autonomous tuning), and `replica-lag` (2026-11-13: one mark a call, and once a cycle an `ACCESS EXCLUSIVE` lock on `demo.replica_lag_marks` first) |

- **How they're applied:** `ContosoCare.Workload setup --target T4 --include-base-schema --seed-scale <n>` runs them on T4 from T1 with T1's managed identity, signed in as the P6 group's PostgreSQL role (an administrator). `Enable-DemoT4Workload` does that through action Run Command, then creates the runner's own role, `contosocare_runner`, mapped to T1's identity with `pgaadauth_create_principal_with_oid`, and grants it only what the scenarios need ([Microsoft Entra roles](https://learn.microsoft.com/azure/postgresql/security/security-manage-entra-users)). No password exists anywhere.
- **Batches:** each script is split on lines that hold only `-- @batch`, and each batch runs as one command.
- **Bounds (ADR 0010):** every step calls `demo.usp_run_assert_running` first, which raises SQLSTATE `CC001` once the run is stopped or past its deadline. The runner calls the steps in a loop, sets `statement_timeout`, `lock_timeout`, and `idle_in_transaction_session_timeout` on every session it opens, and its watchdog ends a run's sessions with `pg_terminate_backend` through `demo.usp_kill_demo_sessions`, which only ever touches this database's `ContosoCare.Demo/` sessions. The server's `idle_in_transaction_session_timeout` (15 minutes, set in Bicep) is the backstop.
- **Changes roll back:** locking, deadlock, and idle-in-transaction steps run in transactions the runner always rolls back. The baseline's audit rows and work-item touches carry the run ID; reset and the auto-cleanup remove them. `io-pressure` grows `demo.io_scratch` up to `scratchMb` (never past 8 GiB of database size) and the auto-cleanup truncates it. `replica-lag`'s marks carry the run ID too, and the auto-cleanup and reset delete them, never `TRUNCATE`, whose `ACCESS EXCLUSIVE` lock T4's read replica would have to replay as well.
- **T4's read replica (ADR 0025):** it has the same objects and roles, because it replays T4's WAL, but nothing can be written there. `replica-lag`'s report runs on it, and the runner reads its state and ends its `ContosoCare.Demo/` sessions (`pg_cancel_backend`, then `pg_terminate_backend`, never a control session) with direct statements rather than a function that writes ([hot standby](https://www.postgresql.org/docs/current/hot-standby.html), [signaling functions](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-SIGNAL)). `demo.usp_scenario_replica_lag` takes its `ACCESS EXCLUSIVE` lock as the runner's role, which `LOCK TABLE` allows because the role has `UPDATE`, `DELETE`, and `TRUNCATE` on the demo tables ([LOCK](https://www.postgresql.org/docs/current/sql-lock.html)); every setup grants them again, so the new table is covered.
- **Statistics snapshots:** functions that read `pg_stat_activity` call `pg_stat_clear_snapshot()` first, because a statistics view otherwise returns the same snapshot for the rest of the transaction.
- **Query Store stays off:** Microsoft Learn says not to enable it on the Burstable tier ([query store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)). The runner's `status --target T4` reads live sessions, waits, and blockers from `pg_stat_activity` and `pg_blocking_pids()` instead.
- **Changing a function's result:** `CREATE OR REPLACE FUNCTION` can't change a function's result columns or their names ("cannot change return type of existing function"), so a change to a `RETURNS TABLE` needs `DROP FUNCTION IF EXISTS demo.<name>(<argument types>);` in a batch before it. Result column names mustn't be SQL keywords either: `overlaps` is one, which the local test run found (`cpu-pressure` returns `overlap_pairs`).
- **Testing locally:** `PostgresTests.SetupRunAndResetAgainstALocalServer` runs the setup, a short baseline, and a reset against a disposable PostgreSQL 18 server when `CONTOSOCARE_TEST_PG_SERVER`, `CONTOSOCARE_PG_USER`, and `CONTOSOCARE_PG_PASSWORD` are set (for example a container from `config/versions.json` `workloadRunner.localTestPostgresImage`, or the PostgreSQL binaries with `initdb`, listening on localhost only); CI doesn't set them. `ContosoCare.Workload run --target T4 --server localhost:<port> --pg-password-from-environment --scenario <id> --duration 60s` runs any scenario the same way.
