# Azure Automation runbooks

The session control's runbooks ([ADR 0026](../docs/adr/0026-one-run-all-session.md), [ADR 0020](../docs/adr/0020-on-demand-activity-control.md) before it), which every deployment has, and the nightly safety stop's ([ADR 0024](../docs/adr/0024-nightly-safety-stop.md)). `scripts/deploy.ps1` publishes the control's to `aa-<prefix>-control` in `rg-<prefix>-control` (`scripts/setup-activity-control.ps1` does it on its own), and `DbHub-Stop` again, with its own settings, to `aa-<prefix>-<environment>-safetystop` in the demo resource group. Nothing here runs on your machine. `scripts/destroy.ps1` deletes the control's account with its runbooks when they serve the environment it destroys, and the safety stop's goes with the demo resource group.

| File | What it is |
|---|---|
| `runbooks/DbHub-Control.ps1` | Started by its webhook, from the notebook `NB_DatabaseHub_Control`: validates the request against the allow-lists, then runs one of six actions: a session (Run all: the showcase on every target, with T4's read replica and T5's container, a backup auto-stop, and the session's status for the notebook, which says when a dispatch Run Command that hadn't ended at the start, T2's after a cold start, sets its targets' activity), a run (the chosen activities), a capture of T4's and T5's metrics for the session's history, a stop (Stop now, which first exports the session's Incident RCA evidence, [below](#the-incident-rcas-evidence), and a session's end, which stops nothing when a `start-demo.ps1` session took over from it, but still exports its evidence), a reset, or, since 2026-11-23, `pending`: a read-only read of the session's status copy for `capture-t2-golden.ps1`, which starts it as a job with the same `WebhookData` when Azure Resource Manager can't give it the copy's value ([below](#the-incident-rcas-evidence)) |
| `runbooks/DbHub-Monitor.ps1` | Started by the schedules a run that uses `sqlvm01` creates, a session included: every 30 minutes, it checks T1's monitoring plugin and restarts T1's SQL IaaS Agent service when the plugin doesn't run, adds a session's host that stopped, or whose start or Run Command failed, to the session's status as a **Warning** with the fix ([ADR 0026](../docs/adr/0026-one-run-all-session.md#2026-11-16-amendment-a-host-that-stops-during-a-session)), and exports the session's Incident RCA evidence captured so far |
| `runbooks/DbHub-Stop.ps1` | Started by schedules ([below](#schedules)), and by `./scripts/stop-demo.ps1` during a Run all session (since 2026-11-22: `-Scope All -RequestedBy stop-demo.ps1`, through [Job - Create](https://learn.microsoft.com/rest/api/automation/job/create), which a Contributor may start). It never starts anything, never connects to a database, and uses Run Command only for a session's Incident RCA export, which only reads (`-Scope All`, [below](#the-incident-rcas-evidence)). In the control's account: `-Scope All`, a run's auto-stop, does what Stop now does: it exports a session's Incident RCA evidence, saves its T4 and T5 metrics to the control vault, deletes T4's read replica (or stops it where the control's role can't delete it), stops T4, deallocates both VMs, and deletes T5's container. One stop does a session's own part, its export, its metrics, and its status (since the review of 2026-11-22): a second stop of a session that has stopped already, or whose stop another job began and still runs, which it waits for, until that mark's life ends, stops only what's left. That includes a later run's auto-stop that reads the last session's ID from the group's tag. `-Scope T4`, the control's daily T4 safety stop, stops T4 when it runs, then a read replica that a session left behind, and deletes T5's container while `sqlvm01` doesn't run. In the safety stop's account: `-Scope Nightly`, the nightly safety stop, deallocates both VMs unless they're deallocated or deallocating, stops T4 when it's running (waiting up to 10 minutes for one that's starting), then a left-over read replica, and deletes T5's container. `-Scope T3Check` reads T3's status through Azure Resource Manager only, then stops T4 when it runs, and a left-over read replica, as `-Scope Nightly` does, for a T4 that Azure's 7-day restart started just after the stop. `Nightly`, `T3Check`, and `T4` change nothing while the demo resource group's busy marker says a `deploy.ps1` run or a session is still going |
| `runbooks/DbHubControl.Common.ps1` | The code the three runbooks share; setup puts it, and the settings, in place of each runbook's markers (`__DBHUB_SETTINGS__` and `# __DBHUB_COMMON__`), so a published runbook is self-contained |

- **T5's container** goes only while the demo resource group's `DbHubT5Container` tag is `Session`: then it exists only during a session, and the session's start creates it again. Otherwise every scope keeps it, and its result says why: with `AlwaysOn`, the session control holds a role that can't create it again yet, until an Owner runs `./scripts/deploy.ps1`, or `./scripts/grant-safety-stop.ps1` once ([ADR 0027](../docs/adr/0027-t5-cosmos-db.md#the-container-only-during-a-session-2026-11-19)).
- **Windows PowerShell 5.1,** which Learn recommends for webhooks, because a PowerShell 7 runbook receives the webhook's input as invalid JSON ([webhooks](https://learn.microsoft.com/azure/automation/automation-webhooks)). The static checks use the Windows PowerShell 5.1 rules for this folder, and a test runs the request validation in Windows PowerShell 5.1 too.
- **Azure Resource Manager REST only,** with a user-assigned identity's token from the sandbox's identity endpoint ([user-assigned identity](https://learn.microsoft.com/azure/automation/add-user-assigned-identity)); no Az module, no secret, and every request stays in the configured subscription. The control's identity `id-<prefix>-automation` has two custom roles: "DbHub Demo Activity Operator" at the demo resource group (A1) and at the control account (A2), which includes reading, creating, and deleting T5's session container, and "DbHub Demo Session Writer" at the control vault's two session secrets only (A4). The safety stop's identity `id-<prefix>-<environment>-safetystop` has "DbHub Demo Safety Stop" at the demo resource group only, with 9 actions: read the group, the VMs and their instance view, T3's database, T4, and T5's container; deallocate the VMs; stop T4; and delete T5's container. It can't start anything, use Run Command, or read data. `deploy.ps1` assigns these roles when you may (an Owner or User Access Administrator); otherwise an Owner runs `./scripts/grant-safety-stop.ps1` once ([the session control's permissions](../docs/permissions.md#the-on-demand-activity-control), [the nightly safety stop's](../docs/permissions.md#the-nightly-safety-stop)). The one exception: the control's runbooks keep the session's last status in their own account's variable `DbHubSessionStatus` with the sandbox's internal `Set-AutomationVariable` and `Get-AutomationVariable`, which need no role ([variables](https://learn.microsoft.com/azure/automation/shared-resources/variables)), so `DbHub-Monitor` can add a host's failure to it ([ADR 0026](../docs/adr/0026-one-run-all-session.md#2026-11-16-amendment-a-host-that-stops-during-a-session)).
- **The settings** baked in at publish hold the names, the bounds, the scenario catalog's allow-lists, the pinned API versions, and the VM-side workload-control template (`Get-DemoWorkloadControlTemplate`), so a run sets each profile with the same request as `demo-control.ps1`. `./scripts/deploy.ps1` republishes the runbooks on every run (`CONTROL.RUNBOOKS`), so a changed scenario reaches them with its next run. The safety stop's settings (`purpose` `safety-stop`) name its own account and the demo resource group, and add how long to wait for T4 and when to judge T3.
- **Nothing secret** is in the job output: the runbooks never see the webhook URL, and a token lives only in one job's memory. Each job prints its log, then one result line: `DBHUB-CONTROL <json>` or `DBHUB-STOP <json>`. A `Nightly` or `T3Check` job that couldn't do its work (`Partial`, or `NotGranted` while its role isn't assigned) fails after that line, so the job history shows it; `status.ps1` reads the line (`STATUS.SAFETYSTOP`). A `T3Check` line has `t4` and `failed` too, for what it did to T4.
- **Its Run Commands** (`DbHubControl-*`) carry no `parameters` or `protectedParameters`; the script holds only the validated request. A run or reset deletes the earlier ones on each VM it uses, and the finished ones on the other running VM. `DbHub-Stop` never touches them, so the last run's stay until the next run or reset, or until `start-demo.ps1` deletes the finished ones (`START.CONTROL.RUNCOMMANDS`: a terminal execution state, or an empty or Unknown one more than an hour after the time in its name); `status.ps1` reports any that are left (`STATUS.RUNCOMMANDS`). A VM allows 25 managed Run Commands ([Run Command overview](https://learn.microsoft.com/azure/virtual-machines/run-command-overview)). The Incident RCA's export deletes each of its own (`DbHubControl-rca-*`) once it's read.

## The Incident RCA's evidence

Since 2026-11-20 ([ADR 0031](../docs/adr/0031-incident-rca.md), [rca/README.md](../rca/README.md#transport)), the control's runbooks move the evidence that the workload runner's observer captures on the VMs into the control vault, for `NB_DatabaseHub_Control` to stage for the session's history ([the history](../fabric/README.md#the-incident-rcas-evidence-in-the-history-2026-11-20)).

- **When:** a session's stop (Stop now, or its auto-stop's `DbHub-Stop -Scope All`) exports it first, while the VMs still run, bounded by `rca.stopMinutes` (6); `DbHub-Monitor`'s 30-minute re-check exports what's been captured so far (`rca.recheckMinutes`, 8); and a session's start exports, on each VM right before its activity goes out there, what an earlier session captured there that no export took, with that session's ID, then fetches one earlier session's documents (`rca.startMinutes`, 6), for the next Run all to save under that session's ID. The nightly safety stop's account can't use Run Command, so what its stop ends stays on the VMs for a later start, and so does what the VMs' auto-shutdown ends.
- **The capture's end at a stop** (2026-11-23, Final tests' observation O1): the stop sends no Run Command to stop the activity, which runs on until the VMs deallocate, so its export asks each runner to end the capture first (the request's `endCapture`, in the export's own Run Command): the observer ends it within a second, as at a profile's end, and the export's 60-second wait sees it end, so the session's last minutes go into its history too, and the stop is no longer held up by that wait. A re-check's export, or a start's, never asks for it. A VM where the capture didn't end goes into the session's `leftVms`, so `RCA.PENDING` names it, and `RCA.EXPORT` is a **Warning** that says why ([the capture's end](../rca/README.md#the-captures-end-at-a-sessions-stop)).
- **What a start doesn't finish** (2026-11-20, re-reviews of 3b1348a and 93243d6): the session's status carries every earlier session whose evidence is still on the VMs as `rcaEarlierPending`. Each entry holds the documents an export listed but didn't fetch whole, with their VM, until the runner deletes them 7 days after that export (`expiresUtc`); the VMs where it holds capture that no export took, until 30 days after it began (`heldUntilUtc`); and, while no saved index lists them, its bundles. A start writes it before its first status write, so a refused or failed start keeps it, and a stop keeps it whichever status it replaces.
  - **One session per VM, exported first:** the runner gives capture that no export took to the session of the first export that takes it, so a VM's capture has to be exported with its own session's ID before any other session's export runs there. A start sends that export to each VM right before its activity goes out there, whichever session's documents it fetches, waits up to 3 minutes for it to end before the activity goes out (managed Run Commands run in parallel on a VM, so one that ran beside the activity would take the new session's first capture too), and reads it even when the VM stopped again meanwhile (a start that failed, or Stop now during a start), because the runner lists a document only once. A session's re-checks and its stop skip a VM that an earlier session holds, and documents of another session that any export finds go to that session's entry, never into the wrong history.
  - **When that can't happen:** the new session's activity reached a held VM before that export ran there (no room for another managed Run Command, Azure refused it, it failed, as it does into T2's guest while the guest still starts, or it didn't end). When an export of the earlier session's own had already taken from that capture, as its first re-check does half an hour into a session, the runner keeps the rest bound to that session (re-check of d2067d69): the new session's next export there lists it with that session's ID, it goes to that session's entry, a later start saves it with that session's history, and `RCA.EARLIER` is **Info** and says so. Each status records where that's so (its RCA state's `boundVms`: the VMs where a document carried the session's own ID; one of no session doesn't count). Otherwise the runner gives the earlier capture to the new session's export, which keeps only what the new session captured, so the earlier capture isn't in any history: `RCA.EARLIER` is a **Warning** that says so, and it's never exported later under the wrong ID. It's a **Warning** too, saying the capture may not be in any history, when the start's export there may have listed it without being read (it didn't end, or its runner ran and failed): the runner lists a document only once. Two sessions holding one VM end the same way: the later one keeps the VM, and its export there takes nothing captured before that session began.
  - **Capture from outside a Run all session** (2026-11-21, re-review of 02d398a): a run from the control notebook's activities mode, `./scripts/start-demo.ps1` or `deploy.ps1`'s activity profile, or a VM that sets its profile at boot captures with no session to hold it, and none of it goes into a session's history. The runbook tells it apart by time: a document's ID starts with when its window starts, and each status says when its session began (`acceptedUtc`), when it ended (`stoppedUtc`, or its planned `runEndUtc`), and when the session before it ended (`rcaPreviousEndUtc`). A session's exports don't fetch a document whose window starts between the session before it and its own start, and don't save one fetched from before its own start that's its own or of no session; an earlier session's documents at a start come only from within its activity (the carries' `startUtc` and `endUtc`). On a VM that ran before a session's start, the start sends an export with no session first, before that VM's activity, so what ran there outside a session goes with no session and no history takes it (an `RCA.EXPORT` **Info** line says how many documents). What that export lists from within the activity of an earlier session that holds the VM still goes with that session, as its own export's would: a Run all in the 10 minutes between a session's run end and its auto-stop (`autoStopBufferMinutes`) finds that session's VMs still running, its stop's export never ran, and its capture since its last re-check is there. Only when that export isn't read, or that session's status doesn't say when its activity ended, is its capture there lost, which `RCA.EARLIER` says. `RCA.EXPORT` counts the documents it didn't save.
  - **One session's documents per start:** the one whose bundles no saved index lists yet (the nightly stop or the VMs' auto-shutdown ended it), otherwise the one whose documents the runner deletes first; a VM that only holds documents gets no export Run Command, only their parts. At most 4 sessions and 6,000 bytes are kept, and the one whose evidence the runner deletes first goes first. Run all prints one `RCA.EARLIER` line for each part that's still on the VMs, which start takes it, and until when, and a **Warning** for one that isn't asked for any more.
  - **Limits:** Stop now during a start, before the status's copy records a VM's dispatch, can leave the session's first seconds of capture on that VM with no claim, so no history gets them. The operator's scripts export with no session (`--session none`): a history save between sessions takes a held VM's capture with no session, and the notebook writes it with that save's session. With `activityProfileOnBoot` true, a VM that an earlier session holds captures from its boot, before that session's export at a start can run there, so the export takes the new session's capture there under the earlier session's ID; neither history gets it, and `RCA.EXPORT` is a **Warning** that says so. Telling these apart at capture (the observer tagging each span with its session when a profile starts) would close all three. `./scripts/stop-demo.ps1` during a Run all session hands the session's stop to the session control (since 2026-11-22): its `DbHub-Stop` job (`-RequestedBy stop-demo.ps1`) stops the session as Stop now does, so a re-check and the stop's export are kept apart there too, and `STOP.CONTROL.SESSION` says what it did. When the control can't take it, `stop-demo.ps1` stops the demo itself, as before, with a **Warning** that says so: then the scripts' own `DbHubDemo-Rca-` Run Commands export without a stop marked begun, so a re-check that's exporting goes on, and the two can run side by side on the T2 host. Before a handoff, `stop-demo.ps1` still rotates the T2 host's one-time password when a Bastion sign-in set one, through a Run Command of its own that isn't kept apart from a re-check; then it waits up to 12 minutes for the T2 host to delete that Run Command before the control's job, and a delete that outlasts the wait is a **Warning** (`STOP.CONTROL.HOSTPASSWORD`), since the stop's export may then run beside it. An earlier session's rest that `RCA.EARLIER` **Info** says goes with the new session's next export there needs that export: when none of the new session's exports runs there (no re-check reached the VM, and its stop's export didn't run there), the next start's export there, with the new session's ID, takes nothing captured before the new session began, so that rest isn't saved.
- **How:** managed Run Commands that only read, `DbHubControl-rca-<vm>-...`, each the VM-side control's `Rca` action with one runner command, `rca export` or `rca part` ([the runner's commands](../rca/README.md#the-runners-commands)), whose one line the instance view's last 4 KB of output keeps ([managed Run Command](https://learn.microsoft.com/azure/virtual-machines/windows/run-command-managed)). On `sqlvm01`, up to `rca.maxParallel` (10) parts at a time, within the VM's 25 Run Commands; an export's own Run Commands that nothing deleted go once the time in their name is more than an hour old, finished or not, because another job may still have to read one (re-review of 93243d6). On the T2 host, one at a time, each gone before the next goes (R871: there, parallel Run Commands' deletes failed, and the host's next start didn't get its goal state); a delete Azure doesn't finish in `rca.hostDeleteSeconds` (300) is asked for once more, and after a second one the host gets no more parts in that export. That holds across the control's jobs too (live, 2026-11-21: a stop's export ran there beside its session's re-check's last two parts): an export sends its first Run Command there only once Azure lists no other `DbHubControl-rca-` Run Command there, checking at each poll without holding up `sqlvm01`; one still there at the export's deadline leaves the host to the next export, and `RCA.EXPORT` is a **Warning** that says so, or that the host's Run Commands couldn't be listed. One whose time is more than an hour old, which the export deletes, holds it up only for its delete: the export waits up to 90 s from its start for Azure to finish that delete, which takes seconds for a finished leftover, so it never runs beside it, and then goes beside one Azure still lists, as stuck in Deleting; no export runs an hour (review of 242a3ef7, and its re-review). A session's stop checks the host only from 60 seconds after it marks the session stopping (`stopBegunUtc`), so a re-check that read the mark just before it, with its three requests and two waits for a conflict, has sent what it will (review of 242a3ef7). What isn't read in time stays on the VMs (the runner keeps it), and the next export takes it.
- **Where:** each document is checked (every part, its SHA-256, its version, and that it's the session's, or of no session, which the operator's scripts export) and its parts are written as earlier versions of `dbhub-session-metrics`, bundles of at most 6 parts and 24,000 bytes; the `rca` member of the secret's final version, which the runbook writes last, lists them (at most 16 bundles and 32 documents). The session's status has the export's `RCA.EXPORT` and `RCA.CAPTURE.<target>` lines, which Run all prints with their fixes. Its stop adds `RCA.PENDING` **Info** when it leaves evidence on the VMs (step 1.8's finding 4): what (documents not fetched whole, from when; capture no export took, on which VMs, including one whose observer still captured when the stop's export ended), which start takes it (the next, or a later one behind earlier sessions' evidence, one session's per start), and until when the runner keeps it, as that start's own backlog of the stopped status gives them. A re-check that hands the stopped session more documents writes the line again. The identity writes the same secret it writes today, through Azure Resource Manager ([Secrets - Create Or Update](https://learn.microsoft.com/rest/api/keyvault/keyvault/secrets/create-or-update)), and the deployer's Key Vault Secrets User on it reads every version: nothing new is granted.
- **The final version, by its ID:** the stop's status names the version its metrics went into (`metrics.version`, from the write's `secretUriWithVersion`), and Run all reads that version, not the latest, because a re-check that was still exporting can write a bundle after it. A stop first marks itself begun in the status's copy (`stopBegunUtc`, the Automation variable `DbHubSessionStatus`), and a re-check checks that before each Run Command it would send and each bundle it would write, so once the stop has begun it sends and writes none: what it's already running ends and is read, and what it found goes into the stopped status as documents still to export (or into the copy's `rcaHandoff`, which the stop takes, while the stop runs), and a later session's start exports them from every VM that holds one. The mark lasts 15 minutes, or `rca.stopMinutes` and 9 more when that's longer, so a stop that failed doesn't block the session's re-checks. A status from a runbook before then names no version, and Run all reads the latest, as before.
- **Not disabled:** the bundles stay enabled versions of the secret after the history is saved. Disabling a version is Key Vault's data-plane Update Secret, which needs `secrets/set` on the secret ([Update Secret](https://learn.microsoft.com/rest/api/keyvault/secrets/update-secret/update-secret)); the identity reaches the vault through Azure Resource Manager only, whose secrets API has no versions, and the deployer reads only. No new grant is the rule, so they stay: readable only by those who can already read the session's metrics, and gone with the vault, which `./scripts/destroy.ps1` deletes and purges.
- **Older pieces:** settings published before the export have no `rcaScriptTemplate`, so a stop exports nothing and says so (`RCA.EXPORT`, a **Warning**: `./scripts/deploy.ps1` publishes them again); a VM whose runner or bootstrap bundle is older says so the same way, and its stop goes on. One from before the capture's end (2026-11-23) exports at a stop without it, as before, and `RCA.EXPORT` names it, with `./scripts/deploy.ps1`.

## Schedules

Daily times are in `autoShutdownTimeZone`; the examples in parentheses use the default `autoShutdownTime`, 19:00. What each one stops, in a user's words: [what stops or pauses on its own](../README.md#what-stops-or-pauses-on-its-own).

| Schedule | Account | When | Runs |
|---|---|---|---|
| `dbhub-autostop` | `aa-<prefix>-control` | Once, 10 minutes after a run's or a session's end | `DbHub-Stop -Scope All` |
| `dbhub-autostop-backup` | `aa-<prefix>-control` | Once, 30 minutes after `dbhub-autostop`, for a session only; the first auto-stop removes it, so it runs only when that one's job failed | `DbHub-Stop -Scope All` |
| `dbhub-monitor-1`, `-2`, ... | `aa-<prefix>-control` | Once each, every 30 minutes of a run that uses `sqlvm01`; they go with the run's auto-stop | `DbHub-Monitor` |
| `dbhub-t4-safety-stop` | `aa-<prefix>-control` | Daily, 15 minutes after `autoShutdownTime` (19:15), or at `control.t4SafetyStopTime` | `DbHub-Stop -Scope T4` |
| `dbhub-safety-stop` | `aa-<prefix>-<environment>-safetystop` | Daily at `autoShutdownTime` (19:00), with the VMs' own auto-shutdown | `DbHub-Stop -Scope Nightly` |
| `dbhub-safety-t3check` | `aa-<prefix>-<environment>-safetystop` | Daily, 30 minutes later (19:30), or T3's auto-pause delay plus 15 minutes when that's longer | `DbHub-Stop -Scope T3Check` |
| `dbhub-safety-deferred` | `aa-<prefix>-<environment>-safetystop` | Only after a `deploy.ps1` run that the nightly stop waited for: hourly from the end of the run's busy marker until the next morning | `DbHub-Stop -Scope Nightly` |
