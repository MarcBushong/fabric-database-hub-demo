# Azure Automation runbooks

The optional on-demand activity control's runbooks ([ADR 0020](../docs/adr/0020-on-demand-activity-control.md)), and the nightly safety stop's, which every deployment has ([ADR 0024](../docs/adr/0024-nightly-safety-stop.md)). `scripts/setup-activity-control.ps1` publishes the control's to `aa-<prefix>-control` in `rg-<prefix>-control`; `scripts/deploy.ps1` publishes `DbHub-Stop` again, with its own settings, to `aa-<prefix>-<environment>-safetystop` in the demo resource group. Nothing here runs on your machine.

| File | What it is |
|---|---|
| `runbooks/DbHub-Control.ps1` | Started only by its webhook, from the notebook `NB_DatabaseHub_Control`: validates the request, then runs, stops (Stop now), or resets the activity |
| `runbooks/DbHub-Stop.ps1` | Started only by schedules. In the control's account: `-Scope All`, the per-run auto-stop, and `-Scope T4`, the daily T4 safety stop. In the safety stop's account: `-Scope Nightly`, the nightly safety stop at the VMs' auto-shutdown time (both VMs deallocated unless they're deallocated or deallocating, and T4 stopped when it's running, waiting up to 10 minutes for one that's starting), and `-Scope T3Check`, which reads T3's status through Azure Resource Manager only, then stops T4 when it runs, as `-Scope Nightly` does (2026-11-09: a T4 that Azure's 7-day restart started just after the stop). It never starts anything, never connects to a database, and never uses Run Command |
| `runbooks/DbHubControl.Common.ps1` | The code both share; setup puts it, and the settings, in place of each runbook's markers (`__DBHUB_SETTINGS__` and `# __DBHUB_COMMON__`), so a published runbook is self-contained |

- **Windows PowerShell 5.1,** which Learn recommends for webhooks, because a PowerShell 7 runbook receives the webhook's input as invalid JSON ([webhooks](https://learn.microsoft.com/azure/automation/automation-webhooks)). The static checks use the Windows PowerShell 5.1 rules for this folder, and a test runs the request validation in Windows PowerShell 5.1 too.
- **Azure Resource Manager REST only,** with a user-assigned identity's token from the sandbox's identity endpoint ([user-assigned identity](https://learn.microsoft.com/azure/automation/add-user-assigned-identity)); no Az module, no secret, and every request stays in the configured subscription. The control's identity `id-<prefix>-automation` has its one custom role at the demo resource group (A1) and at the control account (A2); the safety stop's identity `id-<prefix>-<environment>-safetystop` has the stop-only role "DbHub Demo Safety Stop" at the demo resource group only.
- **The settings** baked in at publish hold the names, the bounds, the scenario catalog's allow-lists, the pinned API versions, and the VM-side workload-control template (`Get-DemoWorkloadControlTemplate`), so a run sets each profile with the same request as `demo-control.ps1`. Run setup again after a scenario changes. The safety stop's settings (`purpose` `safety-stop`) name its own account and the demo resource group, and add how long to wait for T4 and when to judge T3.
- **Nothing secret** is in the job output: the runbooks never see the webhook URL, and a token lives only in one job's memory. Each job prints its log, then one result line: `DBHUB-CONTROL <json>` or `DBHUB-STOP <json>`. A `Nightly` or `T3Check` job that couldn't do its work (`Partial`, or `NotGranted` while its role isn't assigned) fails after that line, so the job history shows it; `status.ps1` reads the line (`STATUS.SAFETYSTOP`). A `T3Check` line has `t4` and `failed` too, for what it did to T4.
- **Its Run Commands** (`DbHubControl-*`) carry no `parameters` or `protectedParameters`; the script holds only the validated request. A run or reset deletes the earlier ones on each VM it uses, and the finished ones on the other running VM (Phase 28 follow-up). `DbHub-Stop` never touches them, so the last run's stay until the next run or reset, or until `start-demo.ps1` deletes the finished ones (`START.CONTROL.RUNCOMMANDS`: a terminal execution state, or an empty or Unknown one more than an hour after the time in its name); `status.ps1` reports any that are left (`STATUS.RUNCOMMANDS`). A VM allows 25 managed Run Commands ([Run Command overview](https://learn.microsoft.com/azure/virtual-machines/run-command-overview)).

Tests: `tests/unit/Automation.Runbooks.Tests.ps1` (with Azure Resource Manager mocked, the `Nightly` and `T3Check` scopes included), `tests/unit/DbHubDemo.ActivityControl.Tests.ps1` (the published content), and `tests/unit/DbHubDemo.SafetyStop.Tests.ps1` (the safety stop's setup, settings, and status).
