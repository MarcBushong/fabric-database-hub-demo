# Azure Automation runbooks

The session control's runbooks ([ADR 0026](../docs/adr/0026-one-run-all-session.md), [ADR 0020](../docs/adr/0020-on-demand-activity-control.md) before it), which every deployment has, and the nightly safety stop's ([ADR 0024](../docs/adr/0024-nightly-safety-stop.md)). `scripts/deploy.ps1` publishes the control's to `aa-<prefix>-control` in `rg-<prefix>-control` (`scripts/setup-activity-control.ps1` does it on its own), and `DbHub-Stop` again, with its own settings, to `aa-<prefix>-<environment>-safetystop` in the demo resource group. Nothing here runs on your machine. `scripts/destroy.ps1` deletes the control's account with its runbooks when they serve the environment it destroys, and the safety stop's goes with the demo resource group.

| File | What it is |
|---|---|
| `runbooks/DbHub-Control.ps1` | Started only by its webhook, from the notebook `NB_DatabaseHub_Control`: validates the request against the allow-lists, then runs one of five actions: a session (Run all: the showcase on every target, with T4's read replica and T5's container, a backup auto-stop, and the session's status for the notebook), a run (the chosen activities), a capture of T4's and T5's metrics for the session's history, a stop (Stop now, which first exports the session's Incident RCA evidence, [below](#the-incident-rcas-evidence)), or a reset |
| `runbooks/DbHub-Monitor.ps1` | Started by the schedules a run that uses `sqlvm01` creates, a session included: every 30 minutes, it checks T1's monitoring plugin and restarts T1's SQL IaaS Agent service when the plugin doesn't run, adds a session's host that stopped, or whose start or Run Command failed, to the session's status as a **Warning** with the fix ([ADR 0026](../docs/adr/0026-one-run-all-session.md#2026-11-16-amendment-a-host-that-stops-during-a-session)), and exports the session's Incident RCA evidence captured so far |
| `runbooks/DbHub-Stop.ps1` | Started only by schedules ([below](#schedules)). It never starts anything, never connects to a database, and uses Run Command only for a session's Incident RCA export, which only reads (`-Scope All`, [below](#the-incident-rcas-evidence)). In the control's account: `-Scope All`, a run's auto-stop, does what Stop now does: it exports a session's Incident RCA evidence, saves its T4 and T5 metrics to the control vault, deletes T4's read replica (or stops it where the control's role can't delete it), stops T4, deallocates both VMs, and deletes T5's container. `-Scope T4`, the control's daily T4 safety stop, stops T4 when it runs, then a read replica that a session left behind, and deletes T5's container while `sqlvm01` doesn't run. In the safety stop's account: `-Scope Nightly`, the nightly safety stop, deallocates both VMs unless they're deallocated or deallocating, stops T4 when it's running (waiting up to 10 minutes for one that's starting), then a left-over read replica, and deletes T5's container. `-Scope T3Check` reads T3's status through Azure Resource Manager only, then stops T4 when it runs, and a left-over read replica, as `-Scope Nightly` does, for a T4 that Azure's 7-day restart started just after the stop. `Nightly`, `T3Check`, and `T4` change nothing while the demo resource group's busy marker says a `deploy.ps1` run or a session is still going |
| `runbooks/DbHubControl.Common.ps1` | The code the three runbooks share; setup puts it, and the settings, in place of each runbook's markers (`__DBHUB_SETTINGS__` and `# __DBHUB_COMMON__`), so a published runbook is self-contained |

- **T5's container** goes only while the demo resource group's `DbHubT5Container` tag is `Session`: then it exists only during a session, and the session's start creates it again. Otherwise every scope keeps it, and its result says why: with `AlwaysOn`, the session control holds a role that can't create it again yet, until an Owner runs `./scripts/deploy.ps1`, or `./scripts/grant-safety-stop.ps1` once ([ADR 0027](../docs/adr/0027-t5-cosmos-db.md#the-container-only-during-a-session-2026-11-19)).
- **Windows PowerShell 5.1,** which Learn recommends for webhooks, because a PowerShell 7 runbook receives the webhook's input as invalid JSON ([webhooks](https://learn.microsoft.com/azure/automation/automation-webhooks)). The static checks use the Windows PowerShell 5.1 rules for this folder, and a test runs the request validation in Windows PowerShell 5.1 too.
- **Azure Resource Manager REST only,** with a user-assigned identity's token from the sandbox's identity endpoint ([user-assigned identity](https://learn.microsoft.com/azure/automation/add-user-assigned-identity)); no Az module, no secret, and every request stays in the configured subscription. The control's identity `id-<prefix>-automation` has two custom roles: "DbHub Demo Activity Operator" at the demo resource group (A1) and at the control account (A2), which includes reading, creating, and deleting T5's session container, and "DbHub Demo Session Writer" at the control vault's two session secrets only (A4). The safety stop's identity `id-<prefix>-<environment>-safetystop` has "DbHub Demo Safety Stop" at the demo resource group only, with 9 actions: read the group, the VMs and their instance view, T3's database, T4, and T5's container; deallocate the VMs; stop T4; and delete T5's container. It can't start anything, use Run Command, or read data. `deploy.ps1` assigns these roles when you may (an Owner or User Access Administrator); otherwise an Owner runs `./scripts/grant-safety-stop.ps1` once ([the session control's permissions](../docs/permissions.md#the-on-demand-activity-control), [the nightly safety stop's](../docs/permissions.md#the-nightly-safety-stop)). The one exception: the control's runbooks keep the session's last status in their own account's variable `DbHubSessionStatus` with the sandbox's internal `Set-AutomationVariable` and `Get-AutomationVariable`, which need no role ([variables](https://learn.microsoft.com/azure/automation/shared-resources/variables)), so `DbHub-Monitor` can add a host's failure to it ([ADR 0026](../docs/adr/0026-one-run-all-session.md#2026-11-16-amendment-a-host-that-stops-during-a-session)).
- **The settings** baked in at publish hold the names, the bounds, the scenario catalog's allow-lists, the pinned API versions, and the VM-side workload-control template (`Get-DemoWorkloadControlTemplate`), so a run sets each profile with the same request as `demo-control.ps1`. `./scripts/deploy.ps1` republishes the runbooks on every run (`CONTROL.RUNBOOKS`), so a changed scenario reaches them with its next run. The safety stop's settings (`purpose` `safety-stop`) name its own account and the demo resource group, and add how long to wait for T4 and when to judge T3.
- **Nothing secret** is in the job output: the runbooks never see the webhook URL, and a token lives only in one job's memory. Each job prints its log, then one result line: `DBHUB-CONTROL <json>` or `DBHUB-STOP <json>`. A `Nightly` or `T3Check` job that couldn't do its work (`Partial`, or `NotGranted` while its role isn't assigned) fails after that line, so the job history shows it; `status.ps1` reads the line (`STATUS.SAFETYSTOP`). A `T3Check` line has `t4` and `failed` too, for what it did to T4.
- **Its Run Commands** (`DbHubControl-*`) carry no `parameters` or `protectedParameters`; the script holds only the validated request. A run or reset deletes the earlier ones on each VM it uses, and the finished ones on the other running VM. `DbHub-Stop` never touches them, so the last run's stay until the next run or reset, or until `start-demo.ps1` deletes the finished ones (`START.CONTROL.RUNCOMMANDS`: a terminal execution state, or an empty or Unknown one more than an hour after the time in its name); `status.ps1` reports any that are left (`STATUS.RUNCOMMANDS`). A VM allows 25 managed Run Commands ([Run Command overview](https://learn.microsoft.com/azure/virtual-machines/run-command-overview)). The Incident RCA's export deletes each of its own (`DbHubControl-rca-*`) once it's read.

## The Incident RCA's evidence

Since 2026-11-20 ([ADR 0031](../docs/adr/0031-incident-rca.md), [rca/README.md](../rca/README.md#transport)), the control's runbooks move the evidence that the workload runner's observer captures on the VMs into the control vault, for `NB_DatabaseHub_Control` to stage for the session's history ([the history](../fabric/README.md#the-incident-rcas-evidence-in-the-history-2026-11-20)).

- **When:** a session's stop (Stop now, or its auto-stop's `DbHub-Stop -Scope All`) exports it first, while the VMs still run, bounded by `rca.stopMinutes` (6); `DbHub-Monitor`'s 30-minute re-check exports what's been captured so far (`rca.recheckMinutes`, 8); and a session's start exports what an earlier session's stop didn't, because the nightly stop or the VMs' auto-shutdown ended it, right before each VM's activity goes out (`rca.startMinutes`, 6), for the next Run all to save under that session's ID. The nightly safety stop's account can't use Run Command, so what its stop ends stays on the VMs for that start.
- **How:** managed Run Commands that only read, `DbHubControl-rca-<vm>-...`, each the VM-side control's `Rca` action with one runner command, `rca export` or `rca part` ([the runner's commands](../rca/README.md#the-runners-commands)), whose one line the instance view's last 4 KB of output keeps ([managed Run Command](https://learn.microsoft.com/azure/virtual-machines/windows/run-command-managed)). On `sqlvm01`, up to `rca.maxParallel` (10) parts at a time, within the VM's 25 Run Commands, an earlier export's finished ones deleted first. On the T2 host, one at a time, each gone before the next goes (R871: there, parallel Run Commands' deletes failed, and the host's next start didn't get its goal state); a delete Azure doesn't finish in `rca.hostDeleteSeconds` (300) is asked for once more, and after a second one the host gets no more parts in that export. What isn't read in time stays on the VMs (the runner keeps it), and the next export takes it.
- **Where:** each document is checked (every part, its SHA-256, its version, and that it's the session's, or of no session, which the operator's scripts export) and its parts are written as earlier versions of `dbhub-session-metrics`, bundles of at most 6 parts and 24,000 bytes; the `rca` member of the secret's final version, which the runbook writes last, lists them (at most 16 bundles and 32 documents). The session's status has the export's `RCA.EXPORT` and `RCA.CAPTURE.<target>` lines, which Run all prints with their fixes. The identity writes the same secret it writes today, through Azure Resource Manager ([Secrets - Create Or Update](https://learn.microsoft.com/rest/api/keyvault/keyvault/secrets/create-or-update)), and the deployer's Key Vault Secrets User on it reads every version: nothing new is granted.
- **Not disabled:** the bundles stay enabled versions of the secret after the history is saved. Disabling a version is Key Vault's data-plane Update Secret, which needs `secrets/set` on the secret ([Update Secret](https://learn.microsoft.com/rest/api/keyvault/secrets/update-secret/update-secret)); the identity reaches the vault through Azure Resource Manager only, whose secrets API has no versions, and the deployer reads only. No new grant is the rule, so they stay: readable only by those who can already read the session's metrics, and gone with the vault, which `./scripts/destroy.ps1` deletes and purges.
- **Older pieces:** settings published before the export have no `rcaScriptTemplate`, so a stop exports nothing and says so (`RCA.EXPORT`, a **Warning**: `./scripts/deploy.ps1` publishes them again); a VM whose runner or bootstrap bundle is older says so the same way, and its stop goes on.

## Schedules

Daily times are in `autoShutdownTimeZone`; the examples in parentheses use the default `autoShutdownTime`, 19:00. What each one stops, in a user's words: [what stops or pauses on its own](../README.md#what-stops-or-pauses-on-its-own).

| Schedule | Account | When | Runs |
|---|---|---|---|
| `dbhub-autostop` | `aa-<prefix>-control` | Once, 10 minutes after a run's or a session's end | `DbHub-Stop -Scope All` |
| `dbhub-autostop-backup` | `aa-<prefix>-control` | Once, 30 minutes after `dbhub-autostop`, for a session only; the first auto-stop removes it, so it runs only when that one's job failed | `DbHub-Stop -Scope All` |
| `dbhub-monitor-1`, `-2`, ... | `aa-<prefix>-control` | Once each, every 30 minutes of a run that uses `sqlvm01`; they go with the run's auto-stop | `DbHub-Monitor` |
| `dbhub-t4-safety-stop` | `aa-<prefix>-control` | Daily, 15 minutes after `autoShutdownTime` (19:15), or at `control.t4SafetyStopTime` | `DbHub-Stop -Scope T4` |
| `dbhub-safety-stop` | `aa-<prefix>-<environment>-safetystop` | Daily at `autoShutdownTime` (19:00), with the VMs' own auto-shutdown | `DbHub-Stop -Scope Nightly` |
| `dbhub-safety-t3check` | `aa-<prefix>-<environment>-safetystop` | Daily, 30 minutes later (19:30), or T3's auto-pause delay plus 15 minutes when that's longer | `DbHub-Stop -Scope T3Check` |
| `dbhub-safety-deferred` | `aa-<prefix>-<environment>-safetystop` | Only after a `deploy.ps1` run that the nightly stop waited for: hourly from the end of the run's busy marker until the next morning | `DbHub-Stop -Scope Nightly` |
