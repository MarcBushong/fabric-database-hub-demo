# Plan regression (automatic plan correction)

A T3 incident (Azure SQL Database) for the showcase: one query's plan regresses, and automatic tuning corrects it. It's the one optimization that can be recommended and applied within a single session. In the showcase's second cycle it's also the **Database Agent loop** (2026-11-18): automatic tuning is held off, so Database Agents raises an issue for the regression, and the run itself makes the issue's manual response.

- **Definition:** [`scenario.json`](scenario.json) (10 minutes by default, 30 at most, for the agent beat's 30-minute slot; 2 sessions by default, 8 at most). T3 only: SQL Server 2022 Standard on T1 and T2 has no automatic tuning ([editions](https://learn.microsoft.com/sql/sql-server/editions-and-components-of-sql-server-2022)), and the procedure refuses to run there.
- **The query:** `demo.usp_visit_summary_lookup`, a front-desk summary of a few patients' visits by patient ID range. Its plan follows the first range it's compiled for: a few patients seek `ix_appointments_patient` and look their rows up (plan A); every patient scans `care.appointments` (plan B). A range predicate keeps it out of parameter-sensitive plan optimization, which handles equality predicates only.
- **The run:**
  1. Session 1 unforces a plan that an earlier run left forced for the lookup, and marks the lookup for recompilation (`sp_recompile`).
  2. For the first `goodPercent` of the run (35% by default), every session runs the lookup for one to three patients at a time: plan A, fast.
  3. At the switch, session 1 marks the lookup for recompilation again and runs it once for every patient, so the cached plan scans (plan B). The other sessions stay out of those 5 seconds.
  4. Every session goes on with narrow ranges on plan B: each lookup now scans the table. Query Store records one query whose plan regressed.
  5. With `FORCE_LAST_GOOD_PLAN` on, Azure SQL Database's default, the engine forces plan A once the estimated CPU gain is over 10 seconds, and then verifies that the forced plan is better ([automatic tuning](https://learn.microsoft.com/sql/relational-databases/automatic-tuning/automatic-tuning), [Azure SQL automatic tuning](https://learn.microsoft.com/azure/azure-sql/database/automatic-tuning-overview)).
- **The Database Agent beat** (the showcase's second cycle on T3, minutes 30 to 60: `goodPercent` 10, `respondPercent` 85, `holdAutoCorrection` true, 6 sessions with `pauseMs` 5, so the regression loads T3's two vCores):
  1. At its start, session 1 records `FORCE_LAST_GOOD_PLAN`'s desired state in `demo.auto_tuning_hold` and turns it off (`ALTER DATABASE CURRENT SET AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = OFF)`; event `auto-tuning-held`), so automatic tuning doesn't correct the regression before Database Agents raises its issue, about 15 minutes after the condition starts ([Database Agents](https://learn.microsoft.com/fabric/database/hub/database-agents)).
  2. The regression starts 3 minutes in. Database Agents investigates it without an LLM, and contextual Copilot explains the issue (**Explain why**) and its captured query (**Analyze slow query**) ([review a performance issue](https://learn.microsoft.com/fabric/database/hub/review-performance-issue)).
  3. **The response**, at 85% of the run (about 25.5 minutes in): Database Agents applies no change ("All scenarios require a manual response"), so session 1 makes the documented one: it forces the last good plan through Query Store (`sys.sp_query_store_force_plan`), the plan `sys.dm_db_tuning_recommendations` recommends for the lookup, or else the lookup's plan with the lowest average CPU; then it puts `FORCE_LAST_GOOD_PLAN` back as it was (event `agent-response`, then `auto-tuning-restored`). T3's CPU falls, and the issue closes when Database Agents sees the condition cleared, or when you close it.
  4. **Every way the beat ends puts `FORCE_LAST_GOOD_PLAN` back**, each logged as an `auto-tuning-restored` event of the run that held it (`demo.usp_release_auto_tuning_hold`, idempotent): the response; the run's end or its stop request (a cancel, a newer Run all, Stop now, `stop-demo.ps1`'s profile off); auto-cleanup after the run; the next run's start on T3 or the profile host's restart (a run that stopped with the VMs: the nightly safety stop, an auto-stop); reset; and setup (`deploy.ps1`). `stop-demo.ps1` also releases the hold through T3 itself before it stops T1, which leaves an off set outside the demo as it is, and reports the option (`STOP.T3.AUTOTUNING`); `status.ps1` shows it (`STATUS.T3.AUTOTUNING`). The safety stop itself changes nothing in T3 (ADR 0024).
  5. Results: `held_auto_correction`, `responded`, `responded_after_seconds`, `forced_plan_id`, `regressed_plan_id`, `already_forced`, `restored_auto_correction`, `lookups_after_response`, and `force_last_good_plan` at the end.
- **Bounds:** sessions tagged `ContosoCare.Demo/plan-regression/<run>`; the lookups only read; the run touches only `demo.usp_visit_summary_lookup`'s own plans (recompile, unforce, and in the agent beat force) and, in the agent beat, the one database option `FORCE_LAST_GOOD_PLAN`; its maximum is 30 minutes. The runner can do this on T3 because it signs in as a member of the P6 group, T3's Microsoft Entra administrator.
- **Where to look:**
  - `sys.dm_db_tuning_recommendations`: a `FORCE_LAST_GOOD_PLAN` recommendation for the lookup's query, with the regressed and recommended plan IDs, its estimated gain, and its state (Verifying, then Success). The DMV shows the regression whether or not the option is on.
  - The Azure portal: the database's **Automatic tuning** page and its history.
  - Query Store in SSMS: **Regressed Queries** and **Queries With Forced Plans**; `sys.query_store_plan.is_forced_plan`.
  - Database Hub: CPU steps up at the switch and back down once plan A is forced. Database Hub's telemetry describes resources, not queries, so the plans themselves are in the places above.
- **Timing (not documented):** the engine's detection follows the regressed executions; with 2 sessions at intensity 6, several hundred regressed lookups run within the first minutes after the switch. Whether and when the plan is forced within a 10-minute slot is unproven live until the owner's check ([limitations](../../docs/limitations.md)).
- **Reset:** a forced plan stays after the run, so it can be shown. The next run of this scenario, or `reset`, unforces it (`sp_query_store_unforce_plan`, for the lookup's queries only; the reset's check `forced-plan-unforced` says when it did). Reset also puts back a `FORCE_LAST_GOOD_PLAN` an agent beat still holds (check `auto-tuning-restored`).

```powershell
ContosoCare.Workload run --target T3 --server <server> --scenario plan-regression --duration 10m
```
