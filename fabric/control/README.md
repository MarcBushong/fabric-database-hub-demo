# The on-demand activity control notebook

`NB_DatabaseHub_Control.ipynb` starts the demo's activity when you run it and shows it live ([ADR 0020](../../docs/adr/0020-on-demand-activity-control.md)). It's optional: `control.enabled` turns it on, and `./scripts/setup-activity-control.ps1` imports it with its environment values filled in.

- **Where it goes:** in the folder **DBHub Control** of the demo's existing workspace where new Key Vaults can be public, so its Spark sessions start fast on the workspace's starter pool; or in a separate workspace, **DBHub Control**, on the same capacity, where a policy makes new vaults private. That workspace has a managed private endpoint to the vault, which creates a managed virtual network for the whole workspace and turns off starter pools, so its sessions start in 3 to 5 minutes ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)). A folder can't do that: network isolation in Fabric is per workspace.
- **What it does:** section 3 posts the activity (one scenario per target, `baseline` or a catalog scenario, and a duration) to the Azure Automation webhook, whose URL it reads from Key Vault for that one request; section 4 sends **Stop now** or **Reset**; section 5 refreshes a live view of each target's CPU, top wait categories, and blocked processes from the Database Hub telemetry endpoint.
- **Safety:** **Run all** sends nothing unless `CONFIRM = True`; Stop now and Reset also need their own switch, and with one of them set, section 3 sends no run request, so **Run all** sends only the stop or the reset. The webhook URL is never printed: a failed request prints only the error's type. The runbook validates every request again against the same allow-lists (`CATALOG_JSON`, filled at import from `scenarios/*/scenario.json`).
- **From a pipeline or the job API:** the notebook also runs through the Fabric job API ([Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job), [notebook public API](https://learn.microsoft.com/fabric/data-engineering/notebook-public-api)) or a pipeline's notebook activity, as its owner. A notebook parameter there is a string, a number, or a bool, so pass `ACTIVITIES` and `RESET_TARGETS` as JSON text, for example `[{"target": "T1", "scenario": "cpu-pressure"}]`, and set `WATCH_MINUTES` to `0` for one look at the live view. The job's status says only whether the notebook finished, not what its cells printed: the runbook's own job in the Automation account shows what it did with the request.
- **No lakehouse:** unlike the deployment and live-activity notebooks in [`fabric/notebooks`](../notebooks), it reads and writes no table, so it has no default lakehouse.
- **Its KQL** is the same as `scripts/modules/DbHubDemo/Kql/Live.CpuSummary.kql`, `Live.WaitDeltas.kql`, and `Live.CounterGauges.kql`; `tests/unit/Fabric.ControlNotebook.Tests.ps1` fails if they drift.

Without the control, `./scripts/demo-control.ps1` sets an activity profile from your machine (Contributor only), and `./scripts/stop-demo.ps1` stops the demo. A local `./scripts/start-demo.ps1` takes over from a notebook run: it cancels the run's pending auto-stop, with a Warning that says until when the VMs now run, and first waits for a stop job that's already running ([ADR 0020](../../docs/adr/0020-on-demand-activity-control.md#stop-layers)).
