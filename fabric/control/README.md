# The session control notebook

`NB_DatabaseHub_Control.ipynb` runs a whole demo session with one **Run all**, and ends it ([ADR 0026](../../docs/adr/0026-one-run-all-session.md); [ADR 0020](../../docs/adr/0020-on-demand-activity-control.md) before it). `deploy.ps1` imports it in every deployment, with its environment values filled in, and adopts a control set up before 2026-11-14. **There's nothing to edit before Run all,** and a session needs no GitHub Actions and no script on a PC.

## What one Run all does

1. **Pre-check (section 3, read-only):** the plan, with when the session ends and why: always before the VMs' nightly auto-shutdown, and, when that cuts it short, after its last whole 30-minute showcase cycle, so no beat is cut off; a session with less than 30 minutes left isn't started, and the fix is to Run all earlier or move `autoShutdownTime` (then `./scripts/deploy.ps1`). It reports the demo workspace's capacity (a paused one stops Run all with that message: you resume it, the notebook never does) and checks that the control vault answers. A session that already runs is followed instead of starting another. An earlier session's T4 metrics still in the vault are saved to the history first, by a job in the demo workspace.
2. **Start:** one request to the runbook through the webhook, whose URL the notebook reads from Key Vault for that one request and never prints. The runbook refuses it while another run is active, marks the demo busy so the nightly stop waits, creates the session's auto-stop and its backup, starts the VMs and T4, creates T4's read replica once T4 is Ready (at T4's size or the next one Azure accepts), and sets the showcase on T1 to T4.
3. **Follow:** the runbook writes its progress to the vault's status secret at each step, and the notebook prints each step with its fix: the VMs, T4, the read replica, each target's activity, and the replica-lag beat, or why it doesn't run this session.
4. **The presenter's guide:** links to Database Hub (Overview, Estate, Performance), the history report, the Real-Time Dashboard, and the Insights app; every beat in the demo's clock, what it fills, and when it shows (SQL telemetry 3 to 15 minutes after it starts, T4's Azure Monitor metrics 1 to 3); and the Database Agent prompts with this session's names and times.
5. **Live view:** each target's CPU, top wait categories, and blocked processes from the Database Hub telemetry endpoint every `REFRESH_SECONDS`, and each beat as it begins, until the session's end.
6. **The end:** Stop now through the runbook, which saves T4's and its replica's Azure Monitor metrics into the vault, deletes the replica, stops T4, deallocates the VMs, and removes the busy marker and the auto-stops. Once the telemetry has arrived (about 15 minutes, with the VMs already stopped), `NB_DatabaseHub_LiveActivity` runs as a job in the demo workspace with the session's ID, beats, window, and T4's metrics, and saves its history for the report and the Insights app. A session already in the history isn't saved twice.

Run all keeps this notebook's Spark session for the whole session, about two hours for the default 90 minutes. In the private path's control workspace, its session starts in 3 to 5 minutes.

## The switches

- `MODE = "session"` (the default) runs the session; `"check"` shows the plan and the checks and sends nothing; `"activities"` sends `ACTIVITIES` only, one per target (`showcase`, `baseline`, `off`, or a catalog scenario), as before 2026-11-14, with no replica and no history.
- `WAIT_FOR_END = False` ends Run all after the guide and `WATCH_MINUTES` of live view. The session's auto-stop, 10 minutes after its end, then does step 6's Azure part, and the next Run all saves its history.
- **Stop now** (section 4) needs `STOP_NOW = True`, so Run all never stops a session by accident; it ends the session as step 6 does. **Reset** needs `RESET_NOW = True`.

## Where it goes

In the folder **DBHub Control** of the demo's workspace where new Key Vaults can be public, so its Spark sessions start fast on the workspace's starter pool; or in a separate workspace named after the demo's ("Database Hub Demo Control" by default; **DBHub Control** for a control set up before 2026-11-14), on the same capacity, where a policy makes new vaults private. That workspace has a managed private endpoint to the vault, which creates a managed virtual network for the whole workspace and turns off starter pools, so its sessions start in 3 to 5 minutes ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)). A folder can't do that: network isolation in Fabric is per workspace. The activity notebook's job runs in the demo workspace, so it keeps its fast start.

## Details

- **What a start brings back (since 2026-11-03):** the runbook sends each VM its activity as soon as that VM runs, and T4's once T4 is Ready, so a slow target never holds back the others. On each VM the activity starts only once its target accepts connections (a cold SQL Server, a resuming serverless database, or a starting flexible server is waited for, up to 10 minutes, 20 for T2). T2's host first releases a guest that a golden capture left air-gapped, or starts an off guest, and never starts a restored copy that hasn't been reset. T1's monitoring plugin is checked once `sqlvm01` runs, and `DbHub-Monitor` checks it again every 30 minutes of the run, so the 90-minute showcase gets two checks. `./scripts/status.ps1` reports the same states (`T2.GUEST.STATE`, `T2.ARC.CONNECTED`, `T1.SQLVM.MONITORING`).
- **Without the Owner's grant:** the session runs without the replica and says so with the fix (`./scripts/grant-safety-stop.ps1`, once, by an Owner). When the runbook can't write the status, the notebook says that its steps can't be followed, with the same fix; the runbook's own output is in the control's Automation account, **Jobs**.
- **Safety:** the webhook URL and the secrets' values are never printed: a failed read prints only the error's type. The runbook validates every request again against the same allow-lists (`CATALOG_JSON`, filled at import from `scenarios/*/scenario.json` and `scenarios/activity-profiles.json`, with the session's rules). The notebook calls only the webhook, the control vault, the Fabric REST API with your `pbi` token, and the telemetry endpoint with your `kusto` token.
- **From a pipeline or the job API:** the notebook also runs through the Fabric job API ([Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job), [notebook public API](https://learn.microsoft.com/fabric/data-engineering/notebook-public-api)) or a pipeline's notebook activity, as its owner. A notebook parameter there is a string, a number, or a bool, so pass `ACTIVITIES` and `RESET_TARGETS` as JSON text.
- **No lakehouse:** it reads and writes no table, so it has no default lakehouse; the history is written by the activity notebook's job.
- **Its KQL** is the same as `scripts/modules/DbHubDemo/Kql/Live.CpuSummary.kql`, `Live.WaitDeltas.kql`, and `Live.CounterGauges.kql`; `tests/unit/Fabric.ControlNotebook.Tests.ps1` fails if they drift, and runs a whole Run all offline against stand-ins for the vault, the runbook, and Fabric.

From a PC instead: `./scripts/start-demo.ps1` starts a session with T4's read replica, `./scripts/demo-control.ps1` sets one activity, and `./scripts/stop-demo.ps1 -SaveHistory` stops the demo and saves its history (Contributor only). A local `./scripts/start-demo.ps1` takes over from a notebook session: it cancels the session's pending auto-stops, with a Warning that says until when the VMs now run, and first waits for a stop job that's already running ([ADR 0020](../../docs/adr/0020-on-demand-activity-control.md#stop-layers)).
