# The session control notebook

`NB_DatabaseHub_Control.ipynb` runs a whole demo session with one **Run all**, and ends it ([ADR 0026](../../docs/adr/0026-one-run-all-session.md); [ADR 0020](../../docs/adr/0020-on-demand-activity-control.md) before it). `deploy.ps1` imports it in every deployment, with its environment values filled in, and adopts a control set up before 2026-11-14. **There's nothing to edit before Run all,** and a session needs no GitHub Actions and no script on a PC.

## What one Run all does

1. **Pre-check (section 3, read-only):** the plan, with when the session ends and why: always before the VMs' nightly auto-shutdown, and, when that cuts it short, after its last whole 30-minute showcase cycle, so no beat is cut off; a session with less than 30 minutes left isn't started, and the fix is to Run all earlier or move `autoShutdownTime` (then `./scripts/deploy.ps1`). It checks that the control vault answers. It doesn't check the capacity, which runs this notebook: you resume and pause it, and the notebook never does. A session that already runs is followed instead of starting another. An earlier session whose T4 or T5 metrics are still in the vault has its history saved right after the start is sent, in this notebook's Spark session.
2. **Start:** one request to the runbook through the webhook, whose URL the notebook reads from Key Vault for that one request and never prints. The runbook refuses it while another run is active, marks the demo busy so the nightly stop waits, creates the session's auto-stop and its backup, starts the VMs and T4, creates T4's read replica once T4 is Ready (at T4's size or the next one Azure accepts), and sets the showcase on T1 to T5. T5, the Azure Cosmos DB account (since 2026-11-18), has no start or stop, but its container, whose provisioned throughput bills every hour it exists, exists only during a session (since 2026-11-19): the runbook creates it while the VMs start, before T5's activity goes out, and its T5 step says so, or why T5 sits the session out. T5's showcase goes to `sqlvm01`'s workload runner with T1's and T3's, and runs the whole session: the baseline plus two ru-storm waves every 30 minutes (at minutes 3 and 18 of each cycle), each only when it and 2 minutes of recovery end before the session does (`recoveryMinutes`), so T5's baseline runs on after its last one, with no throttled requests (429s), until the session ends, and every Run all repeats its storms from the first.
3. **Follow:** the runbook writes its progress to the vault's status secret at each step, and the notebook prints each step with its fix: the VMs, T4, the read replica, each target's activity, the replica-lag beat, and T5's steps: its container, and when T5 is back at its baseline after its last ru-storm, or why it doesn't run this session. A session that couldn't send any activity stops what it started, and only that (since 2026-11-17): its `Stop` step, a **Warning**, names what it left running, which the nightly safety stop still stops, and how to stop everything now (`STOP_NOW = True` and Run all, or `./scripts/stop-demo.ps1`).
4. **The presenter's guide:** links to Database Hub (Overview with **What needs attention** and **Recent signal changes**, Estate, Performance with its real-time dashboards for Microsoft SQL and PostgreSQL, and Optimization: its card in **What needs attention**, and T2 in Estate, ready to migrate), the history report, the Real-Time Dashboard, and the Insights app; every beat in the demo's clock, what it fills, and when it shows (SQL telemetry 3 to 15 minutes after it starts, T4's and T5's Azure Monitor metrics 1 to 3); T5's account, with where to see it (Estate, **View: Azure Cosmos DB**, and Performance: Peak Norm RU % at 100% and Throttled Requests (429s) during each ru-storm, then back to the baseline's level) and when its last storm ends ([Monitor a Cosmos DB account in the Database Hub](https://learn.microsoft.com/fabric/database/hub/monitor-cosmos-db)); **the Database Agent loop on T3** (2026-11-18): the one-time selection in **Manage agents** with T3's exact database, when T3's plan regresses, when the agent's issue shows, when this Run all responds, and when T3's CPU falls ([walkthrough](../../docs/demo-walkthrough.md#the-database-agent-loop-on-t3)); and the Copilot prompts with this session's names and times, starting with Copilot's three starting questions.
5. **Live view:** each target's CPU, top wait categories, and blocked processes from the Database Hub telemetry endpoint every `REFRESH_SECONDS`, and each beat as it begins, until the session's end. At the Database Agent beat's response it prints "Now: T3 Respond", and once T3's telemetry from after it has arrived it compares T3's CPU before and after (**Pass**, or a **Warning** that says why); the session's end repeats that line before the stop (2026-11-18). Every 5 minutes it reads the session's status again and prints anything new: a **Warning** when a host stops, or its start or Run Command fails, which the runbook's 30-minute re-checks add, with the fix ([2026-11-16](../../docs/adr/0026-one-run-all-session.md#2026-11-16-amendment-a-host-that-stops-during-a-session)). Since 2026-11-17, a target whose activity wasn't set on its VM gets one too, at the end of the session's start or at a re-check: its profile set failed, with the command that shows why, or the VM's workload runner is older than the control, which `./scripts/deploy.ps1` updates ([ADR 0020](../../docs/adr/0020-on-demand-activity-control.md#amendment-2026-11-17-a-failed-profile-set-is-said-and-a-run-that-sent-nothing-stops-only-its-own)).
6. **The end:** Stop now through the runbook, which saves T4's, its replica's, and T5's Azure Monitor metrics into the vault, deletes the replica, stops T4, deallocates the VMs, and removes the busy marker and the auto-stops. T5's account has no stop, so the runbook deletes its container, and its provisioned throughput doesn't bill until the next session creates it again; where the session control's role can't create it again yet (the demo resource group's `DbHubT5Container` tag isn't `Session`), the container stays and keeps billing (nothing on the free tier), which the stop's result says. Once the telemetry has arrived (about 15 minutes, with the VMs already stopped), `NB_DatabaseHub_LiveActivity` from the demo workspace runs in this notebook's own Spark session (a reference run) with the session's ID, beats, window, T4's metrics (`POSTGRES_METRICS`), and T5's (`COSMOS_METRICS`), and saves its history for the report and the Insights app. A session already in the history isn't saved twice. No second Spark job starts, so the capacity has nothing to refuse, even an F2 or F4 ([the Spark capacity](../../docs/adr/0026-one-run-all-session.md#the-historys-spark-session-2026-11-14)). When the history can't run there, the notebook prints why and starts it as a job in the demo workspace, which Run all never waits for: a small capacity queues the job until this notebook's Spark session ends, so Run all says so and where its result shows, and, run from the notebook editor, ends its own session as its last step ([2026-11-16](../../docs/adr/0026-one-run-all-session.md#2026-11-16-amendment-the-historys-reference-run-and-its-job)). A job the capacity refuses (HTTP 430) leaves the history for the next Run all, which saves it first.

Run all keeps this notebook's Spark session for the whole session, about two hours for the default 90 minutes, and the history runs in it too. In the private path's control workspace, its session starts in 3 to 5 minutes.

## The switches

- `MODE = "session"` (the default) runs the session; `"check"` shows the plan and the checks and sends nothing; `"activities"` sends `ACTIVITIES` only, one per target (`showcase`, `baseline`, `off`, or a catalog scenario), as before 2026-11-14, with no replica and no history. T5's entry is left out when T5 isn't one of the demo's targets (`t5Enabled` false).
- `WAIT_FOR_END = False` ends Run all after the guide and `WATCH_MINUTES` of live view. The session's auto-stop, 10 minutes after its end, then does step 6's Azure part, and the next Run all saves its history.
- **Stop now** (section 4) needs `STOP_NOW = True`, so Run all never stops a session by accident; it ends the session as step 6 does. **Reset** needs `RESET_NOW = True`.

## Where it goes

In the folder **DBHub Control** of the demo's workspace where new Key Vaults can be public, so its Spark sessions start fast on the workspace's starter pool; or in a separate workspace named after the demo's ("Database Hub Demo Control" by default; **DBHub Control** for a control set up before 2026-11-14), on the same capacity, where a policy makes new vaults private. That workspace has a managed private endpoint to the vault, which creates a managed virtual network for the whole workspace and turns off starter pools, so its sessions start in 3 to 5 minutes ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)). A folder can't do that: network isolation in Fabric is per workspace. The history runs in the control notebook's own session, so it needs no second session to start.

`./scripts/deploy.ps1` puts the notebook there on every run. `./scripts/destroy.ps1` deletes the separate workspace with the rest of the environment when the notebook in it serves this environment and no other environment uses the workspace, and a folder with the demo's workspace ([delete everything](../../README.md#delete-everything)).

## How it works

- **What starts:** the VMs (T2's guest with its host), T4, and T4's read replica; T3 wakes with its first query, and T5's Azure Cosmos DB container is created when it isn't there (it exists only during a session). The showcase runs for `DURATION_MINUTES` (90).
- **The webhook and the runbook:** the notebook sends each request to an Azure Automation webhook, because a Fabric notebook gets no Azure Resource Manager token. Its runbook checks the request against the scenario catalog's allow-lists, refuses it while another run is active, marks the demo busy so the nightly stop waits for it, creates the session's own **auto-stop** first, starts what's stopped, creates T4's read replica, sets each target's activity profile, and writes the session's progress and T4's and T5's metrics to two secrets of the control vault (T5's as the `cosmos` member of the metrics secret), which the notebook reads. **Stop now** in the notebook, the auto-stop, the VMs' nightly shutdown, the [nightly safety stop](../../docs/cost-management.md#what-stops-or-pauses-on-its-own) that every deployment has, and the control's own daily T4 safety stop each stop it by themselves, through Azure Resource Manager only. There's no recurring schedule.
- **A local session takes over:** `stop-demo.ps1` removes a run's pending auto-stop (and a session's backup auto-stop), and so does `start-demo.ps1`, with a **Warning** that the VMs now run until `stop-demo.ps1` or the nightly auto-shutdown at its time (`START.CONTROL.AUTOSTOP`). If a run's stop job is already queued or running, `start-demo.ps1` first waits up to 10 minutes for it to finish (`START.CONTROL.STOPJOB`).
- **Its roles need an Owner once:** `deploy.ps1` creates and assigns them when you may. Otherwise DONE says so, as a **Warning**, and an Owner runs `./scripts/grant-safety-stop.ps1` once, signed in with multifactor authentication, for the nightly safety stop's role and the control's together ([permissions](../../docs/permissions.md#the-on-demand-activity-control)). Until then, `./scripts/start-demo.ps1` runs a session from your machine with Contributor. An older configuration's `"enabled": false` under `control` no longer turns it off.
- **The webhook URL is the credential.** It's kept only as a secret in a Key Vault in `rg-<prefix>-control`, which only the users you name can read; the notebook reads it for each request and never prints it.

## Why it may need a second workspace

The notebook reads the webhook URL from that vault, and a Fabric notebook reaches a vault without public access only through a **managed private endpoint**. Network isolation in Fabric is per workspace, not per folder: a managed private endpoint creates a **managed virtual network for the whole workspace**, which turns off starter pools, so **every** Spark notebook in that workspace then starts in 3 to 5 minutes instead of seconds ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)); the control notebook's runs started in 107 to 166 seconds (2026-10-27). A folder can't have a network of its own. Putting the endpoint on the demo's workspace would slow its other notebooks too, so where one is needed, the control notebook gets its own workspace.

So the control adapts to your tenant (`control.vaultNetworkMode`, default `auto`):

| Your tenant | The vault | The notebook |
|---|---|---|
| New Key Vaults can keep public access | Public, with access granted per user through Microsoft Entra roles | In a folder, "DBHub Control", of the demo's existing workspace: it starts fast |
| An Azure Policy makes new vaults private (for example a Modify that sets `publicNetworkAccess` to `Disabled`) | Private | In a separate workspace on the same capacity, named after the demo's ("Database Hub Demo Control" by default; "DBHub Control" for a control set up before 2026-11-14), with a managed private endpoint to the vault that `deploy.ps1` creates and approves. Its sessions take 3 to 5 minutes to start |

`public` and `private` force a path. `public` in a tenant whose policy would make the vault private is refused before anything is created: the setup names the policy and never adds its exclusion tag, because opting out of a network control is your governance team's decision. `destroy.ps1` deletes the control with the rest of the environment, and `setup-activity-control.ps1 -Remove` deletes the control alone ([cleanup](../../docs/cleanup.md#the-on-demand-activity-control)).

## Details

- **What a start brings back (since 2026-11-03):** the runbook sends each VM its activity as soon as that VM runs, and T4's once T4 is Ready, so a slow target never holds back the others. On each VM the activity starts only once its target accepts connections (a cold SQL Server, a resuming serverless database, or a starting flexible server is waited for, up to 10 minutes, 20 for T2). T2's host first releases a guest that a golden capture left air-gapped, or starts an off guest, and never starts a restored copy that hasn't been reset. T1's monitoring plugin is checked once `sqlvm01` runs, and `DbHub-Monitor` checks it again every 30 minutes of the run, so the 90-minute showcase gets two checks. `./scripts/status.ps1` reports the same states (`T2.GUEST.STATE`, `T2.ARC.CONNECTED`, `T1.SQLVM.MONITORING`).
- **Without the Owner's grant:** the session runs without the replica and says so with the fix (`./scripts/grant-safety-stop.ps1`, once, by an Owner). When the runbook can't write the status, the notebook says that its steps can't be followed, with the same fix; the runbook's own output is in the control's Automation account, **Jobs**.
- **Safety:** the webhook URL and the secrets' values are never printed: a failed read prints only the error's type. The runbook validates every request again against the same allow-lists (`CATALOG_JSON`, filled at import from `scenarios/*/scenario.json` and `scenarios/activity-profiles.json`, with the session's rules). The notebook calls only the webhook, the control vault, the Fabric REST API with your `pbi` token, and the telemetry endpoint with your `kusto` token, and runs the activity notebook through `notebookutils.notebook.run`.
- **From a pipeline or the job API:** the notebook also runs through the Fabric job API ([Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job), [notebook public API](https://learn.microsoft.com/fabric/data-engineering/notebook-public-api)) or a pipeline's notebook activity, as its owner. A notebook parameter there is a string, a number, or a bool, so pass `ACTIVITIES` and `RESET_TARGETS` as JSON text.
- **The demo's lakehouse:** the notebook reads and writes no table itself, but `deploy.ps1` attaches the demo's `LH_DatabaseHub` as its default lakehouse, because Fabric runs a referenced notebook only when it uses the caller's lakehouse ([notebook run](https://learn.microsoft.com/fabric/data-engineering/notebookutils/notebookutils-notebook-run)); the repository's copy names none. When it isn't attached (`CONTROL.FABRIC.LAKEHOUSE`, a **Warning**), the history runs as a job in the demo workspace, which a capacity whose Spark cores are all in use refuses with HTTP 430; the notebook then says so, with the fix.
- **Its KQL** is the same as `scripts/modules/DbHubDemo/Kql/Live.CpuSummary.kql`, `Live.WaitDeltas.kql`, and `Live.CounterGauges.kql`; `tests/unit/Fabric.ControlNotebook.Tests.ps1` fails if they drift, and runs a whole Run all offline against stand-ins for the vault, the runbook, and Fabric.

From a PC instead: `./scripts/start-demo.ps1` starts a session with T4's read replica, `./scripts/demo-control.ps1` sets one activity, and `./scripts/stop-demo.ps1 -SaveHistory` stops the demo and saves its history (Contributor only). A local `./scripts/start-demo.ps1` takes over from a notebook session: it cancels the session's pending auto-stops, with a Warning that says until when the VMs now run, and first waits for a stop job that's already running ([ADR 0020](../../docs/adr/0020-on-demand-activity-control.md#stop-layers)).
