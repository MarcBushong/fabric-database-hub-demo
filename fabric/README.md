## The notebooks

Both notebooks keep the supplied notebook's PySpark kernel (`synapse_pyspark`), its default lakehouse's name (`LH_DatabaseHub`), and its session and compute settings. They hold no Fabric IDs ([ADR 0021](../docs/adr/0021-fabric-resources-by-name.md)): `WORKSPACE_ID` and `LAKEHOUSE_ID` are empty in the parameters cell, the import binds the uploaded copy to the workspace and lakehouse that the scripts resolve by name, and every scripted run passes their IDs. An empty ID means the session's own workspace or default lakehouse, so a notebook you import by hand works once you attach `LH_DatabaseHub`. The supplied notebook held only Fabric's `1+1` template cell; its content was replaced, and nothing else of it was kept or invented.

**Run all runs both,** with no dry-run defaults:

- **`NB_DatabaseHub_Deployment`** runs every check and changes no Azure or Fabric resource; its cleanup also needs `PURGE_DEMO_TABLES = True`, which stays `False`, so **Run all** never drops a table.
- **`NB_DatabaseHub_LiveActivity`** analyzes and saves, and changes no activity: `NB_DatabaseHub_Control`'s Run all runs it at each session's end in its own Spark session (a reference run; as a job in the demo workspace when it can't), with the session's ID (`SESSION_ID`), its beats (`SESSION_PLAN`), its window, T4's and T5's metrics, and the environment's resource group (`RESOURCE_GROUP`) ([ADR 0026](../docs/adr/0026-one-run-all-session.md)). A session already in `scenario_runs` isn't saved twice, and all of a session's runs save under its run ID, `session-<id>`, so when a cancel cuts a save off (the Insights app's **Stop now** can), the next run completes it, table by table. It has no `CONFIRM`, no stop cell, and no GitHub path (P9 is retired).
- **The scripts' own runs** of the live-activity notebook (`stop-demo.ps1 -SaveHistory`, `configure-fabric.ps1`'s first capture, and `deploy.ps1`'s snapshot at its end) pass the demo's resource group as `RESOURCE_GROUP`, which scopes the notebook's queries, and `CONFIRM` and `STOP_ACTIVITY` as `false` for a notebook imported before 2026-11-14, whose Run all sent an activity request. `stop-demo.ps1 -SaveHistory` and `deploy.ps1`'s snapshot also pass T4's and T5's metrics, and `configure-fabric.ps1 -RunLiveActivity` passes both ([below](#t4s-and-t5s-azure-monitor-metrics-in-the-history)); since 2026-11-20 the three stage the Incident RCA's evidence for it too, as `RCA_EVIDENCE_FILE` ([below](#the-incident-rcas-evidence-in-the-history-2026-11-20)).

### Tokens and the telemetry fallback

- Tokens come from `notebookutils.credentials.getToken`, which supports only the audience keys `storage`, `pbi`, `keyvault`, and `kusto` ([NotebookUtils credentials](https://learn.microsoft.com/fabric/data-engineering/notebookutils/notebookutils-credentials)). The notebooks request only `pbi` (Fabric REST) and `kusto` (telemetry), use each token in one HTTP header, and never print or save it.
- The telemetry endpoint documents a Microsoft Entra token for `https://kusto.kusto.windows.net` ([query performance monitoring telemetry](https://learn.microsoft.com/fabric/database/hub/microsoft-sql-query-performance-monitoring-telemetry)). **Whether it accepts a notebook `kusto` token isn't documented.** The notebooks check it once per run (`HUB.TELEMETRY.TOKEN`); if it isn't accepted, every query prints its KQL with the documented Azure Data Explorer web UI steps instead, and `scripts/validate.ps1` runs the same checks with an Azure CLI token. The maintainers' tenant accepted it (**Pass**), but because the behavior is undocumented, the check and the fallback stay.
- The KQL follows the article's rules: filter on `SampleTimeUTC` first, take per-series deltas of cumulative counters and skip resets, branch on `CounterType`, and group by `ResourceID` and `SqlServerInstanceName`.

Every table also has `report_date_utc` (`date`): the UTC calendar date of the row's primary time, the first that isn't null of `timestamp_utc` (validation results), `window_start_utc` then `requested_at_utc` (scenario runs), `bucket_utc` then `window_end_utc` then `captured_at_utc` (snapshots), `window_start_utc` then `captured_at_utc` (findings), and `window_start_utc` (incident windows). The Power BI history report relates every table to its date table through it. Each write is one Parquet file, which keeps every table far below Direct Lake's limit of 1,000 files per table on F16.

The live-activity notebook's persist cell (section 11) also readies the tables for the report, lakehouse data only: `CREATE TABLE IF NOT EXISTS` for all thirteen, the Incident RCA's eight included (Direct Lake can't frame a missing table), `report_date_utc` added and backfilled once on tables written before it existed, the incident windows merged on `incident_key`, and `OPTIMIZE` for any table with more than 200 files. An incident window is a **recorded request** (an `incident:*` request in `scenario_runs` that wasn't a Fail, with section 8's expected-signal verdict) or a **detected signal** that no request explains: consecutive bins with a blocked process, CPU at or above `EPISODE_CPU_PERCENT` (80) or `PAGEIOLATCH` waits at or above `EPISODE_PAGEIOLATCH_SECONDS` (1 s) per bin for `EPISODE_MIN_BINS` (2) bins, or any Log Rate Governor wait. A re-run unions overlapping detected episodes and keeps the earliest key. The thresholds are presenter heuristics, not product behavior (ADR 0014).

Re-running a cell in the same session replaces that run's rows, so nothing is duplicated. The tables keep demo history beyond the telemetry's 7-day retention. `LH_DatabaseHub` has lakehouse schemas, so the tables are in the `dbo` schema (`Tables/dbo/<table>` in OneLake).

### T4's and T5's Azure Monitor metrics in the history

The live-activity notebook can't read T4, the PostgreSQL flexible server, its read replica, or T5, the Azure Cosmos DB account: `notebookutils` has no Azure Resource Manager token audience, and Database Hub charts their Azure Monitor metrics, which aren't in the telemetry endpoint ([ADR 0025](../docs/adr/0025-t4-read-replica.md), [ADR 0027](../docs/adr/0027-t5-cosmos-db.md)). So they're read outside it and passed in; the notebook's section 7 documents each metric, unit, finding, and threshold.

1. **Capture:** `Get-DemoPostgresHistoryParameter` and `Get-DemoCosmosHistoryParameter` (`PostgresHistoryHelpers.ps1` and `CosmosHistoryHelpers.ps1` in `scripts/modules/DbHubDemo/Private/`) read them with the Azure CLI over the run's window, read-only ([Metrics - List](https://learn.microsoft.com/rest/api/monitor/metrics/list)): on T4 (`pgflex01-<deploymentId>`) and its read replica (`pgreplica01-<deploymentId>`), every 5 minutes, CPU, memory, connections, failed connections, and the replication lag that Database Hub's **Read replica lag** chart shows; on T5, the signals Database Hub's Cosmos DB views chart (normalized RU, total request units, throttled requests, provisioned throughput, and availability), the requests the 429 rate divides by, and the gateway's server-side latency. A server that doesn't exist, such as the replica between sessions, or that had no data is left out, with a note; T5's account stays between sessions, so its metrics can be read any time within Azure Monitor's retention.
2. **Pass:** at Run all's session end, the control's runbook saves them to the control vault's session metrics before it deletes the replica, whose metrics go with it, and `NB_DatabaseHub_Control` passes them to the notebook. `./scripts/stop-demo.ps1 -SaveHistory` captures them before it deletes the replica, and so do `./scripts/deploy.ps1`'s history snapshot at its end and `./scripts/configure-fabric.ps1 -RunLiveActivity`. They're the notebook's string parameters `POSTGRES_METRICS` and `COSMOS_METRICS`: compact JSON, version 1, with the window, the servers, and their series of points; names, sizes, times, and numbers, never an ID or a credential. Only points with a value are kept, and a document stays under about 24 KB: when it's larger, the intervals are combined into 15, 30, 60, or more minutes. Empty means none were passed: a run by hand says so in one line and adds nothing.
3. **Save:** section 7's T4 and T5 cells keep only valid servers, series, and points, and add them to the run's results, which the persist cell saves with the rest (a re-run replaces them): `telemetry_snapshots` rows, one per point, with the analysis `postgresql` and the target `T4` or `T4-replica`, or `cosmosdb` and `T5`; and the findings `postgresql.T4.capture`, `postgresql.T4-replica.lag`, `postgresql.T4.cpu`, `postgresql.T4.connections_failed`, `cosmosdb.T5.capture`, `cosmosdb.T5.throttling`, one `cosmosdb.T5.throttle.<yyyymmddThhmm>` per throttling episode, and, with 429s, `cosmosdb.T5.recovery`. A T4 document the cell can't use is one **Fail** finding, `postgresql.T4.capture`, and adds no rows. The thresholds are presenter heuristics, not product behavior.
4. **Show:** the Insights app's **Estate** page charts the latest capture on T4's and T5's target pages ([the app](app/README.md#whats-in-it)). The history model names `T4` and `T4-replica` in its Target dimension and `postgresql` in its Analysis dimension, and has T5's in its **Cosmos DB** measures; the Power BI report's pages stay on the SQL targets ([the report](powerbi/README.md)).

### The Incident RCA's evidence in the history (2026-11-20)

The Incident RCA ([ADR 0031](../docs/adr/0031-incident-rca.md)) explains blocking, waits, errors, and the replica's lag from what a DBA's own tools would show. The runner's observer captures it on the VMs, blind to what the workload runs, and the evidence reaches the lakehouse this way; [rca/README.md](../rca/README.md#transport) is the contract.

1. **Export:** the runner reduces what it captured into evidence documents and prints them as part lines, one per managed Run Command, which keeps the last 4 KB of output ([managed Run Command](https://learn.microsoft.com/azure/virtual-machines/windows/run-command-managed)). Run all's session: the control's runbook, at its stop, at each 30-minute re-check, and at a later session's start for what an earlier session's stop didn't export, with that session's ID, because the nightly stop or the VMs' auto-shutdown ended it ([the runbooks](../automation/README.md#the-incident-rcas-evidence)). The scripts: `./scripts/stop-demo.ps1 -SaveHistory`, `deploy.ps1`'s history snapshot, and `./scripts/configure-fabric.ps1 -RunLiveActivity`, with your sign-in (`RcaExportHelpers.ps1` in `scripts/modules/DbHubDemo/Private/`).
2. **Stage:** the parts travel as one `RCA_EVIDENCE` document in a file in the lakehouse, `Files/rca/inbox/<time>-<session or script>-<random>.json`, passed as `RCA_EVIDENCE_FILE`: neither a notebook run's parameters nor a job's document a size limit, and a full session's 64 parts come to about 218 KB. `NB_DatabaseHub_Control` reads the parts from the control vault (earlier versions of `dbhub-session-metrics`, listed by the `rca` member of its final version) and writes the file with `notebookutils.fs.put` ([file system utilities](https://learn.microsoft.com/fabric/data-engineering/notebookutils/notebookutils-file-system)); the scripts write it through OneLake's ADLS Gen2 API with the workspace role deploy gave you ([OneLake access with APIs](https://learn.microsoft.com/fabric/onelake/onelake-access-api), [workspace roles write OneLake](https://learn.microsoft.com/fabric/onelake/security/best-practices-secure-data-in-onelake)). Nothing new is granted for either.
3. **Save:** the persist cell (section 11) reads the file first, with `notebookutils.fs.head(path, 262144)` (its default is 100 KB), and the inline `RCA_EVIDENCE` too when both are passed, merging their parts; it checks every part and document against the contract (a missing part, a SHA-256 that doesn't match, a newer version, or another session's document is skipped and named, never written in part, and so is a parameter that can't be used, while the other's documents are still written), applies `redact()` to every string, and writes each document once by its ID: the seven detection tables, then `rca_answer_key` apart from them, then `rca_coverage` last, which marks the document saved. Its finding `rca_evidence` is `RCA.EVIDENCE`: **Pass**, **Warning** with why, or **Not selected** when none was passed. A run with `RCA_ONLY` true (Run all's save of an earlier session's evidence) writes only that, from its session cell.
4. **Clean up:** the notebook deletes the file once it's written, and one it can't use; one it couldn't read or write stays, and its run a day later deletes it at the latest. The scripts delete theirs once the job ends, then the empty folders, and the deployment notebook's purge removes `Files/rca/inbox` with the eight tables. A file the scripts find still there when they delete it (Path - Delete answers 200, not 404) means the notebook didn't write the evidence, even if its job completed, so its documents stay pending. Run all prints the notebook's own `RCA.EVIDENCE` from a reference run's exit value; for a history that runs as a job, whose exit value it doesn't get, it says what the file tells at its one look (re-check of d2067d69): **Pass** when the job deleted it, a **Warning** with the fix when the job ended without deleting it (Run all deletes it then), failed, or never started, and a **Warning** that it can't tell yet while the job is queued or running, since Run all doesn't wait for it, with where the job's own line is.
5. **Pending:** documents a scripts' save didn't take (a paused capacity, a failed run, a run that completed without writing them, a notebook from before the Incident RCA) stay listed by ID in `out/history-pending/rca-pending-<resource group>.json`, and the runner keeps them 7 days, so the next save fetches them again (`STOP.RCA.PENDING`). Nothing of the evidence is kept on your machine. Run all's sessions keep theirs in the session's status instead, for a later session's start ([the runbooks](../automation/README.md#the-incident-rcas-evidence)).
6. **Older pieces:** a notebook from before the Incident RCA ignores both parameters, so the scripts don't stage the file for it, with a **Warning** whose fix updates it; a runner or bootstrap bundle from before it is a **Warning** whose fix is `./scripts/deploy.ps1`; a session saved before it has no RCA rows, and the Insights app says no RCA capture is recorded for its windows ([troubleshooting](../docs/troubleshooting.md#the-incident-rcas-capture)).

## Import or update the notebooks

`deploy.ps1` imports them (`scripts/configure-fabric.ps1`): a notebook that isn't in the workspace yet without asking, and one that is only when `fabric.importNotebooks` is `true` (`-NewNotebooksOnly`); running the script yourself is the explicit request to create or update both. When the live-activity notebook was just created, or bound to a lakehouse that was just created, it runs once, so the history tables exist; that run comes before the targets send telemetry, so `deploy.ps1` runs the notebook once more at its end, analyze-only, once its telemetry checks pass, and refreshes the history model, so the report has the run's data ([deployment](../docs/deployment.md#the-history-reports-snapshot-at-the-end-2026-11-06)).

```powershell
./scripts/configure-fabric.ps1 -SkipHubChecks -WhatIf   # validates the files and shows the plan; no token, no network call
./scripts/configure-fabric.ps1             # signed-in Azure CLI user's Fabric token
./scripts/configure-fabric.ps1 -FabricToken $token -WorkspaceId <workspace-id>   # a token you already have, as a SecureString
```

- **How:** it validates each `.ipynb` locally (nbformat 4, no outputs or execution counts), finds the notebook by display name ([Items - List Items](https://learn.microsoft.com/rest/api/fabric/core/items/list-items)), then creates it ([Items - Create Item](https://learn.microsoft.com/rest/api/fabric/core/items/create-item), type `Notebook`) or updates its definition ([Items - Update Item Definition](https://learn.microsoft.com/rest/api/fabric/core/items/update-item-definition)) with the [ipynb notebook definition](https://learn.microsoft.com/rest/api/fabric/articles/item-management/definitions/notebook-definition) (format `ipynb`, one part `notebook-content.ipynb`, `InlineBase64`), and follows the [long-running operation](https://learn.microsoft.com/rest/api/fabric/articles/long-running-operation) pattern (on HTTP 202 it waits `Retry-After`, polls Get Operation State, and reads a created item from Get Operation Result).
- **Token:** without `-FabricToken`, the script runs the subscription guard and then `az account get-access-token --resource https://api.fabric.microsoft.com` through `Invoke-DemoAz` ([user-delegated Fabric calls from the command line](https://learn.microsoft.com/fabric/graph/gql-query-api)). The token stays a SecureString, is registered for redaction, and is sent only to `https://api.fabric.microsoft.com/v1`.
- **Idempotent, by name:** re-runs update the same notebooks; if two share a name, it stops with **Fail** instead of guessing. It first finds `fabric.workspaceName` and `fabric.lakehouseName`, and creates them when they're missing and `fabric.createIfMissing` is true ([configuration](../docs/configuration.md#fabric)). Only the uploaded copy of each notebook is bound to them; the files in Git don't change.
- **Results:** one **Pass**, **Warning**, **Fail**, or **Not selected** record per notebook, in `out/configure-fabric.jsonl`. In GitHub Actions it would run only where the Fabric tenant lets service principals use Fabric APIs and the identity has a workspace role; the local path is the default.

## The Real-Time Dashboard

## Rules for notebooks

- Keep the PySpark kernel and the `LH_DatabaseHub` lakehouse name. Never commit a workspace or lakehouse ID: export the notebook, then remove them (a test fails on any GUID-shaped value in a notebook).
- Keep `"language_info": {"name": "python"}` in the notebook metadata. Fabric's [Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job) rejects a notebook without it ("Not supported language"), and Fabric's own `.ipynb` export includes it.
- Commit notebooks **without outputs**. CI fails if a cell has outputs or an execution count, and the pre-commit `nbstripout` hook strips them. The committed files already use the sequential cell IDs that `nbstripout` writes, so the hook leaves them unchanged.
- No credentials, ever. Tokens come from `notebookutils.credentials` at run time and are never printed.
- In `notebooks/`, cells that change resources start with `# RESOURCE-CHANGING CELL:`, follow a markdown cell that flags them, and do nothing unless `CONFIRM = True`, the default. A cell that drops data needs its own switch too (`PURGE_DEMO_TABLES`), which stays `False`; the live-activity notebook has none. The control notebook marks its own with `# Resource-changing:`: its Run all starts and ends a session by design, and **Stop now** and **Reset** each need their own switch (`STOP_NOW`, `RESET_NOW`).
- Use only documented interfaces: never call Database Hub private routes (the one exception is the Insights app's estate function, under [ADR 0013's amendment](../docs/adr/0013-agent-experience.md#amendment-2026-11-18-the-ga-skill-and-one-narrow-exception)), and describe expected **signals** for Database Agent prompts, never expected answers.
- To edit a notebook, change it in Fabric, export it as `.ipynb`, run `nbstripout` (or let the pre-commit hook do it), and commit; or edit the JSON directly and run the Pester tests.
- Three notebook tests run the live-activity notebook's own code, its episode detection on fixture rows and its T4 cell on what `Get-DemoPostgresHistoryParameter` writes, and need Python 3 with pandas: set `DBHUB_TEST_PYTHON` to such an interpreter (a virtual environment's `python`), or they're skipped. One of them replays a recorded session's CPU samples (T1 and T2 at 99 and 97 in `SQLProcessCPUPercent`, 0 in `AvgCPUPercent`) and checks that T1 and T2 get their CPU windows.

The notebooks' first live imports and runs, and the Real-Time Dashboard's, are in the [implementation report](../docs/implementation-report.md).
