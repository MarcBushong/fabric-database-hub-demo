# Database Hub Insights: the Fabric App (preview)

`APP_DatabaseHub_Insights` is the demo's own operations product, a [Fabric app](https://learn.microsoft.com/fabric/apps/overview). It opens on Mission Control, where the session's plan meets what happened: the "Did we catch it?" scoreboard, a replay, and a postmortem ([ADR 0030](../../docs/adr/0030-insights-app-mission-control.md)). It's also a DBA console, where a DBA sees what needs attention across the estate, drills from the estate to a target and an incident, asks Copilot about what's on screen, and acts through the demo's own session control ([ADR 0029](../../docs/adr/0029-insights-app-dba-console.md)). Fabric Apps is a **preview**. Every visual says which of two sources it shows:

- **History:** the lakehouse history (`LH_DatabaseHub`), which `NB_DatabaseHub_LiveActivity` saves at each session's end, read as you through the semantic model `SM_DatabaseHub_History` and the read-only `history` connector. It keeps what Database Hub's 7 days of telemetry don't.
- **Live:** Database Hub's own view of the estate (its resources, their health in the last 24 hours, and security warnings), which the app's functions item reads as the app item's owner, scoped to the demo's resource group and cached for a minute, with the 8 read-only routes the GA Database Hub CLI skill (`databasehub-cli`) uses. Those routes aren't a public contract, so they're the repo's one exception to documented interfaces only ([ADR 0013](../../docs/adr/0013-agent-experience.md#amendment-2026-11-18-the-ga-skill-and-one-narrow-exception)). Without the function, each page says why in one line and shows the history.
- **Not live yet (2026-11-19, R924):** Database Hub refuses the sign-in that Fabric gives the app's functions, so the app shows the history, and T2's migration readiness as Azure had it at the last deploy; Database Hub shows the live estate. While Database Hub refuses the app as a whole (every view), the pages show no live parts, and **Live views** says in one line that Database Hub's live data isn't available to Fabric apps yet. A view that doesn't answer while another does shows as partial, and a live view that didn't answer just now says so, never with an error code. The function still asks Database Hub on every read, so the live views come back by themselves once it accepts that sign-in; `FABRIC.APP.ESTATE` (**Not supported**) says the same.

## At a glance

- **What it is:** the item `APP_DatabaseHub_Insights` in the demo's Fabric workspace, with two user data functions beside it: its functions (the live estate and Manage) and its connector to the history model. Anyone with access opens it; operators also use **Manage** to start or stop a session, which bills like any session.
- **What deploys it:** `./scripts/deploy.ps1`, on every run, with Ask's chat relay: nothing to set up in the app, no image to build, and no GitHub Actions workflow to run ([deploy](#deploy), [the relay](../../ask-relay/README.md)).
- **What it costs:** the app runs on your Fabric capacity; Ask's chat relay bills per second only while someone asks ([cost management](../../docs/cost-management.md#dated-example-asks-chat-relay-2026-11-18)). The Fabric capacity, Fabric and Power BI licenses, and each viewer's GitHub Copilot plan, which the chat runs on, are outside every estimate.
- **How a viewer signs in:** from the app's item in the workspace, with their Fabric account ([open the app](#open-the-app)); for Ask, with GitHub, once per browser, on the account that has their Copilot plan ([the chat](#ask-copilot-the-chat-in-the-app)).
- **How to remove it:** `./scripts/destroy.ps1` deletes the workspace with the app's three items, and the chat relay with the resource group; each viewer's GitHub authorization stays until they revoke it ([update and delete](#update-and-delete)).

## Demo it yourself

Anyone who deploys the demo demos it, with nothing to set up in the app:

1. **Deploy:** `./scripts/deploy.ps1` deploys the app with everything else, and updates it in place on every run.
2. **Open it:** in the Fabric portal, open the demo's workspace and select `APP_DatabaseHub_Insights`. It signs you in with your Fabric account and opens on **Mission Control**.
3. **Before any session,** Mission Control says **No session in this period** and Overview **No history yet**; both name the one action that fills them: **Run all** in `NB_DatabaseHub_Control`. Overview shows **Live now** when the app reads Database Hub live; today it doesn't (R924), so **Live views** says so, and Database Hub itself has the live view.
4. **After a session,** every page shows it: the incidents, T3's Database Agent loop, T4's read replica lag, T5's throttling and recovery, the findings, and **Readiness**, which every Run all fills by running `NB_DatabaseHub_Deployment`'s read-only checks. Each session adds to the history; a reset (in Manage, or `RESET_NOW` in the control notebook) and the next Run all work the same way every time.
5. **Copilot:** select **Copilot** in the top bar, or **Ask Copilot** on any visual. The first time, the dock signs in to GitHub; its chip in the top bar then shows your GitHub login and Copilot plan, next to your Fabric account.

Your Fabric account opens the app and runs its queries (it needs Read and Build on `SM_DatabaseHub_History`); your GitHub account, with a Copilot plan, runs the chat. They're separate, and neither is stored in the app.

## Open the app

**Open it from its item in the Fabric workspace.** The app runs embedded in the item page and signs you in by itself with `initEmbeddedAuth` ([Fabric authentication](https://learn.microsoft.com/fabric/apps/fabric-authentication)). **Live views** shows **"✓ Connector check passed"** with the counts of validation checks, telemetry rows, and incident windows, which proves sign-in, the connector, and your access to the model in one step. Don't open the hosted URL directly: it's a known preview limitation ([the hosted URL](#known-limitation-the-hosted-url)).

Viewers need access to the app item (a workspace role, or the item shared with them); **Read** and **Build** on `SM_DatabaseHub_History`, because the connector runs DAX as the signed-in user (delegated); and the tenant settings **Fabric Apps (preview)** and **Dataset Execute Queries REST API** for them ([prerequisites](../../docs/prerequisites.md)).

When a refresh of its history fails, it keeps showing what it had and asks again every 30 seconds; once the history loads again, it refreshes every 5 minutes, as before.

**The postmortem** (**Write the postmortem** on Mission Control, the scoreboard, and the replay): **Download Markdown** writes it from the data alone (summary, timeline, impact, cause, response, times to signal and recover, follow-ups, and the queries), with no GitHub sign-in. With the Incident RCA's tables, its cause is a blind investigation of the session's minutes, as the **Root cause** page makes it: up to six incidents, the capture's first, each with its root cause, confidence, and the rows it cites, or why it has none; what was injected follows, in a section labeled as the answer key ([ADR 0031, section 9](../../docs/adr/0031-incident-rca.md#9-the-postmortems-cause)). **Draft with Copilot** hands the viewer's own Copilot the session's minutes, T4's and T5's measured episodes, and the measured queries, never what was injected, and it investigates the rest ([ADR 0031](../../docs/adr/0031-incident-rca.md)). A lone incident request's postmortem has no draft, because its minutes are its fault's own; it points to the Root cause view when the app has it. While the telemetry hasn't loaded, nothing is measured, so the button says why and waits for **Retry**.

**The session these pages show** is the one picked in their **Session** list, or **Link to this moment**'s; without a pick, each shows the latest, and the next visit does too.

**T4's and T5's history:** the notebook can't read Azure Monitor, so Run all's session end, `./scripts/stop-demo.ps1 -SaveHistory`, and `./scripts/deploy.ps1` at its end pass their metrics to `NB_DatabaseHub_LiveActivity` (analyses `postgresql` and `cosmosdb`). Their pages read the latest capture, whatever the filters, and say how a capture gets there when there's none. A deployment without Cosmos DB (`t5Enabled` off) shows no T5.

**Look and feel:** Fluent 2 in Microsoft's colors, as the owner chose ([ADR 0030](../../docs/adr/0030-insights-app-mission-control.md)): Fluent 2's Microsoft blue, the Microsoft logo's four colors marking the targets and the charts' categories, and Fluent's layered neutrals and shadows. **Light**, **dark**, or **high contrast**, following the system until you pick one in the top bar; Mission Control, the scoreboard, the replay, and the kiosk are dark until you pick, and their pulses and shockwaves stop with reduced motion. Every control, tile, row, and chart works with the keyboard and screen readers (charts read their values with the arrow keys), status is never shown by color alone, and it fits Fabric's frame on a laptop screen.

### Ask Copilot, and take the data out

Every visual and table has:

- **Ask Copilot:** opens the Copilot dock with the visual's title, its rows (at most 200), and the DAX behind them, or, for a live visual, its time; an anomaly has **Ask why**, which adds what's unusual about it. The chat never sees the demo's answer key, what it injected and how it was graded ([ADR 0031](../../docs/adr/0031-incident-rca.md)): a visual that shows it hands over only its measured part. Where nothing measured is left, the visual has no Ask, or, with the RCA tables, hands the chat a window to investigate itself: the history's newest 90 minutes for the incidents, a whole session's minutes for the sessions, the replay, and the scoreboard.
- **The data as a table**, with sort, filter, **Download CSV**, and **Copy as CSV** (spreadsheet formulas are neutralized).
- **Show the DAX** and **Copy the DAX**, or for a live visual **Show the Database Hub API calls**.
- **Focus mode** (the visual alone; Esc closes it) and **Run the query again**.

The view (page, filter, drill-down, replay position) is kept in the frame's address and remembered per browser, since the portal's frame has no address bar of its own.

### Copilot in the app

The Copilot chat sits in a dock on the right: it resizes, goes full screen, and keeps its width. **Copilot** in the top bar opens it, and so does every **Ask Copilot** and **Ask why**. It answers from what's on screen and the tools it has, and draws its charts with the app's own charts ([Ask Copilot: the chat in the app](#ask-copilot-the-chat-in-the-app)).

### Ask the Database Agent

Database Hub's Database Agent (preview) works only in Database Hub's UI and has no API, so the app writes ready-made prompts from the data on screen: copy one, select **Open Database Hub**, and paste it into the agent, or select **Ask Copilot** to ask the in-app Copilot instead. Incidents has each window's prompts (what caused it, what moved with it, against the baseline, the evidence), with the target, its resource name, the UTC window, and the window's own numbers; Estate and Readiness have a prompt library. Every prompt ends with the [prompt pack's](../agent/prompts/README.md) safety sentence ("Don't apply anything; propose only."), and the panels say **Preview** and **Investigation only: this app never runs anything**. The **Copilot CLI · VS Code** switch rewrites the prompts for the documented fallback, GitHub Copilot CLI or VS Code with the GA Database Hub skill (`databasehub-cli`, in the `fabric-skills` plugin) and the `microsoft-sql` plugin ([agent guide](../agent/README.md)). Database Hub keeps 7 days of telemetry or less; for an older window the panel says the agent may not see it any more.

## Manage: bounded, confirmed actions

Run all in `NB_DatabaseHub_Control` stays the demo's one action ([ADR 0026](../../docs/adr/0026-one-run-all-session.md)); Manage's actions come in addition to it and do the same things:

| Action | What it does | The control's parameters |
|---|---|---|
| **Start a session** | What Run all does: starts every target, runs the showcase's incidents and T3's Database Agent beat, and stops everything at its end (30 to 120 minutes, 90 by default) | `MODE = "session"`, `DURATION_MINUTES`, `WAIT_FOR_END = True` |
| **Run an incident** | One scenario from the catalog on one target it applies to, within the scenario's maximum minutes, with the baseline beside it | `MODE = "activities"`, `ACTIVITIES`, `DURATION_MINUTES` |
| **Stop now** | Ends the session as its end would: saves the history, deletes T4's read replica, deallocates the VMs, stops T4, and deletes T5's container when T5's lifecycle is Session (with AlwaysOn, it stays). With no session running, it stops whatever runs and saves the last session's history, in case its end was cut off | `STOP_NOW = True` |
| **Reset** | Returns ContosoCare to its seed state on the running targets, and removes what a cut-off RU storm left on T5 | `RESET_NOW = True`, `RESET_TARGETS` |

Every action says what it does and what bounds it, shows the control request, and asks for confirmation; a value outside the control's allow-lists and caps can't be confirmed. No secret reaches the browser: the control's webhook URL stays in Key Vault, read by the control notebook. Manage works one of two ways, which the app finds out by itself (`FABRIC.APP.ACTIONS` says which):

- **Sending from the app,** when the app's Manage function (`rayfin/functions/src/manage.ts`) is deployed and set up:
  - **Who may send:** operators only, the deployer and the members of the demo's admin group, which `deploy.ps1` writes into the app's settings at every deploy (the deployer only, with a **Warning**, when it can't read the group's members). The function knows you by your Microsoft Entra object ID from your Fabric sign-in, never from what the browser sends, or, when Fabric's token has none, by your Fabric sign-in email ([ADR 0029](../../docs/adr/0029-insights-app-dba-console.md)). Everyone else sees Manage read-only, with the reason.
  - **How it runs:** the function runs `NB_DatabaseHub_Control` through the Fabric job API with the request's parameters, the control records who sent it (`REQUESTED_BY`, `app/<you>`), and the page follows the run's real state, a failure included. The control takes one request at a time and follows a session that's running instead of starting another, so while one of its runs is queued or in progress, the function refuses every action but **Stop now**.
  - **Stop now** cancels that run first (on an F2 or F4 capacity, the stop couldn't start until it ended), then asks again while the capacity refuses, for up to 150 seconds. If the stop still doesn't start, it says it cancelled the run and that nothing is stopping the session now, and copies the request. If the run it cancelled was ending a session, the stop saves that session's history.
  - **When it can't send** (it isn't set up, it can't confirm who you are, or Fabric refuses the run), it copies the request for Run all instead, with the reason.
- **Copying for Run all** (otherwise): each action copies its request as lines for a new cell under the control notebook's parameters cell and opens the notebook, where Run all sends it with the same checks.

**What the control ran** lists every session plan and activity request the notebooks recorded, newest first.

## Ask Copilot: the chat in the app

**Ask Copilot** opens a chat docked on the right, on the viewer's own GitHub Copilot ([ADR 0028](../../docs/adr/0028-ask-copilot-in-the-insights-app.md)): conversational analytics on the demo's history and its live estate, with the app's own charts.

- **What it can do:** run read-only DAX on `SM_DatabaseHub_History` through the app's delegated connector, as the viewer (`run_dax`; `EVALUATE` only, bounded rows); draw the result with the app's own charts (`show_chart`); read the live estate from Database Hub through the app's function (`estate_overview`); and suggest follow-ups. Every tool runs in the page; the model gets a guide to the history model's names, never data.
- **The first-line investigator** ([ADR 0031](../../docs/adr/0031-incident-rca.md)): once the history has the Incident RCA's tables, six more tools (`triage_window`, `find_incidents`, `explain_incident`, `explain_locking`, `explain_errors`, `explain_replica_lag`) and four starters ("What caused the latest incident?", "Who blocked whom?", "Why did the replica fall behind?", "What errors did the app hit?"). It answers with the root cause, its evidence and times, the recommendations with who approves each, the next steps, and what wasn't captured.
- **Blind, like a DBA's tools:** `run_dax` refuses the demo's answer key (`Scenario Runs`, `Incident Windows`, `Analysis Findings`, `RCA Answer Key`, and every measure that reads them) and the functions that read the whole model without naming a table (`COLUMNSTATISTICS`, the `INFO` functions, `CALENDARAUTO`, and `EXTERNALMEASURE`). It compares names as leniently as the engine might, so lookalike or invisible characters don't hide one, refuses a whole-model function's name even in a string or comment, and takes only plain ASCII outside strings and comments. It sends each query with a line feed for every carriage return and form feed, exactly the text it checked. The model guide leaves them out, so the chat finds what happened from the telemetry and the capture. The scoreboard is where the demo grades itself.
- **Every answer** shows its source (**Show the source**: the DAX, or the Database Hub routes), and can be copied; **Export** saves the conversation as Markdown with every query, and **New chat** starts over. The conversation stays for the browser session.
- **Sign-in:** **Sign in with GitHub**, once per browser: GitHub's device flow through the shared OAuth App **Database Hub Insights Ask**, which the relay runs because GitHub's endpoints don't allow browser calls ([the steps](../../README.md#the-copilot-chat-in-the-insights-app)). The account line shows `GitHub: <login> · Copilot <plan>`, with **Switch GitHub account** and **Sign out of GitHub**.
- **What it needs and costs:** each viewer's own GitHub Copilot plan, outside every estimate. The relay bills per second only while someone asks and scales to zero about 10 minutes after the last question ([cost management](../../docs/cost-management.md#dated-example-asks-chat-relay-2026-11-18)). Its image is public and pinned by digest in `config/versions.json` (`askRelay.image`); you never build it ([the relay](../../ask-relay/README.md)).
- **When it can't answer,** the dock says why: Ask isn't deployed, the relay is waking from zero (about 15 seconds), GitHub sign-in isn't set up, the account has no Copilot plan, an organization blocks the app, or the sign-in expired; a turn that ended without an answer says "Copilot didn't write an answer", with **Retry** (R925). The rest of the app works as before ([the dock's messages](../../docs/troubleshooting.md#ask-the-copilot-chat-in-the-insights-app-2026-11-18)).

## Update and delete

- **Update:** run `./scripts/deploy.ps1` again (or `./scripts/configure-fabric-app.ps1` for the app alone). It updates the item `APP_DatabaseHub_Insights` in place, keeps its history and its links, and refreshes Manage's operators list; the new version shows the next time the app opens. Upgrading an older demo is the same command ([deployment](../../docs/deployment.md#update-an-existing-environment)).
- **Delete:** `./scripts/destroy.ps1` deletes the demo's Fabric workspace, with the app's three items in it, when every item in it is one the demo creates (`-KeepFabric` keeps it), and Ask's chat relay with the demo resource group. The three items are the app, `AppBackend APP_DatabaseHub_Insights`, and the two user data functions its backend makes beside it: `APP_DatabaseHub_Insights_connector`, the connector's, and `APP_DatabaseHub_Insights`, the functions'. To remove only the app, delete those three items in the workspace, and `out/fabric-app/rayfin/.deployments.json` on the PC that deploys it, because the CLI would otherwise reuse the deleted app's ID in the same workspace; the next deploy creates them again. What stays: the stage and the CLI's sign-in on your PC, and each viewer's GitHub authorization of **Database Hub Insights Ask**, which they revoke at <https://github.com/settings/applications> (**Authorized OAuth Apps**); **Sign out of GitHub** in the chat's account menu clears a browser's sign-in ([what stays](../../docs/cleanup.md#what-stays-and-how-to-remove-it)).
- **What you control:** who can open it (the workspace's roles, or the item shared), who reads the history (Read and Build on `SM_DatabaseHub_History`), and who sends Manage's actions (the demo's admin group). In the configuration: whether Ask runs (`ask.enabled`, on by default), and, rarely, your own GitHub OAuth App or relay image (`ask.githubClientId`, `ask.image`, pinned by digest).

## Known limitation: the hosted URL

Opening the hosted app's URL directly in a browser tab fails in this preview: the Fabric Apps host shows its own **Sign in required** page, and its **Sign in** opens a Fabric portal page in a pop-up that stops at **"Page not accessible directly. This page must be opened from an application."** It happened in an InPrivate window signed in to Fabric as the demo's admin too, so the account and tenant aren't the cause. **Open the app from its workspace item**, the supported entry point. The app keeps `assetAccess: protected`: making the assets public wouldn't fix the hand-off, and would expose the bundle without sign-in.

The evidence, from anonymous requests: the hosted URL is on the Fabric Apps host (`https://<name>-<region>.webapp.fabricapps.net`), not the `<app>-app.rayfin.windows.net` form [hosting](https://learn.microsoft.com/fabric/apps/hosting) shows, and without a session it returns HTTP 401 `{"error":"Authentication required."}` to `Accept: application/json`, and the **Sign in required** page to a browser. That page sends `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, and `Content-Security-Policy: frame-ancestors 'none'`; its **Sign in** opens `https://app.fabric.microsoft.com/secureItemEmbed?...&extensionPath=/brokeredauth&ctid=<tenant>` in a pop-up, which hands the result back through the opener window ([Fabric authentication](https://learn.microsoft.com/fabric/apps/fabric-authentication)). No `Cross-Origin-Opener-Policy` header showed up on `secureItemEmbed`, the portal, or the sign-in pages, so what drops the opener is unconfirmed: a preview behavior outside the app's code. To report it, use **Help & support** in the Fabric portal (or [Fabric Ideas](https://ideas.fabric.microsoft.com/)) with these steps.

## Troubleshooting

The `FABRIC.APP.*` and `ASK.*` results of a deployment, the hosted URL's "Page not accessible directly", and the Copilot dock's messages are in [troubleshooting](../../docs/troubleshooting.md#the-insights-app-fabric-app), by check ID ([Ask's](../../docs/troubleshooting.md#ask-the-copilot-chat-in-the-insights-app-2026-11-18)). In the app:

| Symptom | Fix |
|---|---|
| A visual says Fabric refused the query | The viewer needs Read and Build on `SM_DatabaseHub_History`, and the Execute Queries tenant setting |
| T4's or T5's page says there's no history yet | A session's end (Run all), `./scripts/stop-demo.ps1 -SaveHistory`, or `./scripts/deploy.ps1` captures their Azure Monitor metrics and passes them to the notebook. A notebook you run by hand has none to pass; a deployment without Cosmos DB has no T5 |
| T4's page has no Read replica lag | The latest capture had no read replica: it exists only during a session, so capture before `stop-demo.ps1` deletes it (its `-SaveHistory` does) |
| Overview has no **Live now**, and Findings no live checks | Database Hub refuses the app's sign-in on every view (R924, 2026-11-19): it answers HTTP 401 to the sign-in Fabric gives the app's functions, and nothing in the demo fixes that (`FABRIC.APP.ESTATE` is **Not supported**); **Live views** says so in one line. The pages show the history, **Ready to migrate** shows T2's assessment as Azure had it at the last deploy, and Database Hub has the live view. They come back by themselves once Database Hub accepts that sign-in |
| A page says **Live · unavailable** | The line beside it says why: the app's live estate function isn't deployed, or Database Hub didn't answer just now. The page shows the history, and Database Hub has the live view. A tile that says "Not available to the app" or "Didn't answer just now", or a **Partial** note, means one part of Database Hub didn't answer while the rest did |
| **Ready to migrate** links the Azure portal instead of showing T2's readiness | Azure had no assessment result for `arcsql01` when the app was last deployed (its first run uploads about 6 minutes after `deploy.ps1` starts it): `./scripts/deploy.ps1` again, after `T2.ARC.MIGRATIONASSESSMENT` is **Pass** |
| Manage says each action copies its request | The app's Manage function isn't deployed or set up (`FABRIC.APP.ACTIONS` says why, for example when the session control's notebook wasn't found): paste the copied lines into a new cell under the control notebook's parameters cell, then Run all. Before 2026-11-19, a new environment's first `deploy.ps1` always left it so ("missing NB_DatabaseHub_Control"): `./scripts/deploy.ps1` again deploys the app once more once the notebook is in Fabric (R926) |
| Manage is read-only for you | You aren't one of the demo's operators: the deployer and the members of its admin group. Ask an operator, or one of them redeploys after adding you to the group (`./scripts/deploy.ps1` refreshes the list) |
| Manage says "Stop now cancelled the control's run, but the stop didn't start" | The capacity (an F2 or F4 runs one Spark session at a time) still refused the stop after 150 seconds, and nothing is stopping the session now. Paste the copied request into the control notebook and Run all, or run `./scripts/stop-demo.ps1 -SaveHistory` from a PC. The session's auto-stop still stops everything at its end, and the next Run all saves its history |
| Manage refuses an action: "... is in progress, and the control takes one request at a time" | One of `NB_DatabaseHub_Control`'s runs is queued or in progress: a session's Run all, or an earlier request. Wait for it to end (the page follows it), or use Stop now, which ends the session as its end would |
| A Real-Time Dashboard link opens the wrong page | The portal path for dashboards isn't documented; use the workspace link and open `RTD_DatabaseHub_LiveView` |

|---|---|

No database or storage |

From any visual, `useCopilot().ask` (`src/copilot/contract.ts`) passes the visual's title, rows, and DAX |

Every package is pinned to an exact version in `package.json` and `package-lock.json`, resolved from the public npm registry (`registry.npmjs.org`) with SHA-512 integrity: install new packages with `--registry=https://registry.npmjs.org/`, or fix the lock file's URLs after an install through a mirror. `npm run check:licenses` fails on a production dependency that isn't MIT, ISC, Apache-2.0, BSD, 0BSD, OFL-1.1, BlueOak-1.0.0, Unlicense, or CC0-1.0, and the build writes `dist/THIRD_PARTY_NOTICES.txt`; pages load lazily. `rayfin/rayfin.yml` holds placeholders only (`${DBHUB_FABRIC_WORKSPACE_ID}`, `${DBHUB_SEMANTIC_MODEL_ID}`), and `rayfin/connectors/history/` the connector's generated schema, with no IDs. `scripts/export-queries.ts` writes the query catalog as connector payloads for the deploy-time check, and `src/preview/`'s sample data is never built into the app. `src/mission/` holds the parts of Mission Control, the scoreboard, and the replay (the service map, the session ribbon, the replay, the postmortem dialog, and the kiosk), and `src/theme/` the themes, with ContosoCare's tokens (`identity.ts`, `stage.ts`).

### Overrides and known advisories

`package.json` overrides four packages that the pinned Rayfin packages and ESLint bring in, `@azure/msal-node`, `glob`, `minimatch`, and `zod`, each for a security advisory whose fix no release of its parents declares yet; `glob` and `minimatch` only in the advisory's vulnerable range, so a parent that declares a range outside it keeps its version. `config/versions.json` (`fabricApp.overrides`) records each override, its advisory, the version that fixes it, its parents' declared ranges, and why; a Pester test keeps that record, `package.json`, and the lock file in sync, and `src/test/overrides.test.ts` runs the code that uses each, offline. The overrides reach everything installed from the lock file, the stage's Rayfin CLI included, so every Rayfin command the scripts run comes from the stage, never `npx`, which would install the CLI without them. With them, `npm audit` reports no vulnerabilities. Remove an override once a pinned release of each parent depends on a fixed version.

### Deploy

`./scripts/configure-fabric-app.ps1` deploys the app; `./scripts/deploy.ps1` runs it in its Fabric track, after the history report, on every run, and ends **DONE** even when the app can't be created, with the app's step **Failed** on the status page, the actual error, and the fix ([deployment](../../docs/deployment.md#the-insights-app-part-of-every-deployment-2026-11-05)). The script is unattended and idempotent: it deploys to the item named `APP_DatabaseHub_Insights`, updates it in place on every run, and never deletes anything. It needs:

1. `SM_DatabaseHub_History` deployed (`./scripts/configure-powerbi.ps1`), and the workspace on an **Active** Fabric capacity: `rayfin up` can start a trial or assign a capacity when a workspace has none, so the script deploys only on an Active one.
2. Node.js 20, 22, or 24, the Rayfin CLI's supported versions.
3. **The sign-in the Rayfin CLI uses:** by default your Azure CLI sign-in, so no browser opens. After its subscription guard, the script gives each command a token for its audience as `RAYFIN_TOKEN` (the Fabric API for `rayfin up` and `rayfin up status`, the Power BI API for `rayfin connector invoke`), which the pinned CLI reads instead of its own sign-in; the [CLI reference](https://learn.microsoft.com/fabric/apps/cli-reference) doesn't document it. When Fabric refuses that token for `rayfin up` (`FABRIC.APP.TOKEN`, a **Warning** with the reason), the CLI's own one-time sign-in, as the demo's Fabric user, deploys instead: `./scripts/configure-fabric-app.ps1 -SignIn` makes it in your console, checks it, and deploys (interactive sessions only; **Not supported** in CI), and the next `deploy.ps1` starts it at its beginning, in a session that can take keyboard input, where only the app's step waits for it, at most 15 minutes from the start. Or, once the stage exists, run `./out/fabric-app/node_modules/.bin/rayfin login --tenant <tenantId>` from the repository root, never through `npx`, which installs the CLI without this project's npm overrides. The CLI renews its token cache silently; without `-SignIn`, the script only reads it (`rayfin login status --json`). Service principal sign-in is listed in the CLI reference but isn't supported yet. A browser that doesn't open: [troubleshooting](../../docs/troubleshooting.md#the-insights-app-fabric-app) (the terminal's `BROWSER`).

What it does, as ADR 0012 results in `out/configure-fabric-app.jsonl`:

| Step | Check IDs |
|---|---|
| Validate `fabric/app`: placeholders only, protected assets, the connector, and the pinned CLI | `FABRIC.APP.SOURCE` |
| The subscription guard, then the workspace role and an Active capacity | `PREFLIGHT.GUARD.CONTEXT`, `FABRIC.P5.WORKSPACE`, `FABRIC.P5.CAPACITY` |
| Find the model, the dashboard, and the report by name; build the new-tab links from their IDs | `FABRIC.APP.ITEMS` |
| Mirror `fabric/app` into the Git-ignored stage `out/fabric-app`, write `rayfin/.env` (connector IDs) and `public/dbhub-app.json` (links, the expected account, and the resource group name for the agent prompts), drop the CLI's records of other workspaces, and run `npm ci` when the lock file changed | `FABRIC.APP.STAGE`, `FABRIC.APP.DEPENDENCIES` |
| Node.js, the sign-in the CLI uses (the Azure CLI's tokens, or its own sign-in to the demo's tenant), and the two tenant settings | `FABRIC.APP.NODE`, `FABRIC.APP.SIGNIN`, `FABRIC.APP.TENANTSETTING`, `FABRIC.APP.EXECUTEQUERIES` |
| `rayfin up --workspace-id <id> --item-name APP_DatabaseHub_Insights --tenant <id> --yes --json`, then `rayfin up status --json`; when Fabric refuses the Azure CLI's token, the CLI's own sign-in deploys instead | `FABRIC.APP.DEPLOY`, `FABRIC.APP.STATUS`, `FABRIC.APP.TOKEN` (only after a refusal) |
| Every query in the app's catalog, anchored to the newest telemetry day, under your identity: through the connector's direct route (`rayfin connector invoke`), or, when that route refuses the Azure CLI's token (HTTP 401 from Power BI's `executeDaxQueries`), through Power BI's [Execute Queries](https://learn.microsoft.com/rest/api/power-bi/datasets/execute-queries-in-group) with the same token (one query per request, with the app's row bound compared here, since that API has none), so the checks need no Rayfin sign-in either; `-RayfinSignIn` runs them through the connector with the CLI's own sign-in. Then the hosted app must refuse anonymous requests | `FABRIC.APP.CONNECTOR`, `FABRIC.APP.QUERIES` (evidence `route`, `auth`, `connectorRefusal`), `FABRIC.APP.HOSTING` |
| Manage's function settings: the app's API and IDs, the control notebook's IDs, the operators, and the control's catalog, never a secret; an app's first deploy deploys once more, about a minute, because only then does it know the app's API. On a new environment, `deploy.ps1` puts the control notebook in Fabric only after its tracks, so it then runs the app's step once more, a few minutes, with the notebook's IDs and the API both (since 2026-11-19; before, every new environment's Manage copied its requests) | `FABRIC.APP.ACTIONS`, `FABRIC.APP.OPERATORS` |
| Ask: before the stage, deploy its chat relay (`infra/ask/ask-relay.bicep`, registering `Microsoft.App` when it isn't) and write its address into `dbhub-app.json`; after `rayfin up`, set the relay's origin to the app's, wake and check it, and read the strict-CSP tenant setting. Never a Fail: Pass, Warning, or Not selected | `ASK.RELAY`, `ASK.RELAY.HEALTH`, `ASK.SIGNIN`, `ASK.CSP` |
| The browser check: a note when the app is deployed and every query it runs returned its data. The note says exactly that, and that the app's own route in the browser (its sign-in, then its backend, User Data Functions, and a delegated on-behalf-of call) can't be checked from a script, since neither route above crosses it. Otherwise only a person can do it | `FABRIC.APP.BROWSER` (**Not selected**, "Not needed"; otherwise **Manual action required**) |

Without `-FabricAdmin`, the tenant settings can't be read; a passing deploy proves **Fabric Apps (preview)** and a passing connector check proves **Dataset Execute Queries REST API** (the connector's runtime calls the Execute Queries API, and the check's other route is that API), so both become a **Pass**. With `-FabricAdmin`, they're read through the [admin API](https://learn.microsoft.com/rest/api/fabric/admin/tenants/list-tenant-settings).

Options: `-WhatIf` validates the source and lists the plan with no token, network call, or write. `-DryRun` runs everything up to `rayfin up --dry-run`. `-CheckOnly` checks the deployed app without deploying. `-Queries Probe` runs only the connection check. `-TreatManualAsError` exits with code 2 while the browser check is pending. `-RayfinSignIn` uses only the Rayfin CLI's own sign-in, not the Azure CLI's tokens. With `-FabricToken`, the script runs no subscription guard, so it has no Power BI token, and the app's queries are checked only with `-RayfinSignIn` (otherwise `FABRIC.APP.CONNECTOR` is a **Warning** that says so). The CLI's `connector invoke --transport deployed` needs an app session the CLI can't create, so the in-app path is the browser check.

The CLI writes its deployment record (`rayfin/.deployments.json`, `rayfin/.env`, `.env.local`) in the stage. Those files hold the item ID, the hosting URL, and the app's publishable key, so they stay under `out/`, Git-ignored; the key is public by design (the browser bundle carries it), but the script redacts it from every result and log anyway. The CLI finds its record by the workspace's name and reuses the item it names, whatever workspace that was, so the stage drops the records of every other workspace before `rayfin up` (`FABRIC.APP.STAGE` names them): after `destroy.ps1`, a new workspace with the same name would otherwise get the deleted app's ID, and the deploy would fail.

### Develop and test

```powershell
cd fabric/app
npm ci
npm run verify       # typecheck, lint, Vitest (unit, page, chart, theme-contrast, and override tests), license check, build
npm run dev:sample   # the local preview with sample data: no Fabric, no sign-in
```

`./tests/Invoke-StaticValidation.ps1 -Check FabricApp` runs the same in the repository's static validation, and the `Fabric App` CI job runs it on Node.js 24. The tests use fixture rows shaped like the connector's results; no test reaches Fabric.

**The preview** (`npm run dev:sample`, then `/preview.html`) runs the whole app on made-up history and live answers, labeled **Sample data**, for design work and screenshots. Its addresses include `#/mission`, `#/scoreboard`, `#/replay?r=36` (a moment), `#/kiosk`, and `#/rca`: the Root cause view on the RCA contract's T1 fixture (`rca/fixtures/`) and a real capture from a local PostgreSQL primary and standby (`src/preview/data/pg-local.evidence.json`). The chat needs a deployed relay, so the preview's dock can't answer. Its query parameters: `theme=light|dark|contrast`, `copilot=open`, `manage=operator|viewer|running` (without it, Manage's copy mode), `empty=1` (no history: the first run), and `live=off` (no live source). Vite builds only `index.html`, so none of it ships.

To run the app locally against the deployed backend, work in the stage (`out/fabric-app`, after a deploy): `npm run dev` writes `.env.local` from the deployment record and serves on `http://localhost:5173`, which `rayfin.yml` allows as a redirect URI. Local sign-in isn't verified.
