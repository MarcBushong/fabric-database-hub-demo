# What fills Database Hub's visuals, and when

What each Database Hub visual shows during a demo session, which scenario fills it and when, and the history some of them need, which the baseline run gives. Database Hub is generally available; its labels, thresholds, and timings can still change, and its Copilot, Database Agents, and alerts are previews ([what's generally available, and what's a preview](limitations.md#preview-disclosures)). The [demo walkthrough](demo-walkthrough.md) has the presenter scripts, and the [control notebook's guide](../fabric/control/README.md) has what one **Run all** does.

## What fills each Database Hub visual, and when

**Run all** in the Fabric notebook `NB_DatabaseHub_Control` starts the **showcase** on all five targets for 90 minutes (120 at most):

- the steady Contoso Care baseline, plus a 30-minute rotation of bounded incidents, at most two at a time per target ([`activity-profiles.json`](../scenarios/activity-profiles.json));
- it repeats every 30 minutes, and each target's clock starts when its activity starts;
- at its end, Run all stops it and saves its history; if Run all stopped early, the session's auto-stop 10 minutes later deletes the replica, deallocates the VMs, stops T4, and deletes T5's container.

One run at a time: a Run all during a session follows it, and a session is refused while a run started another way is active. `DbHub-Monitor` checks T1's monitoring plugin every 30 minutes while at least 5 minutes of the run remain, so a run shorter than about 35 minutes gets no re-check and the 90-minute showcase gets two ([the notebook's guide](../fabric/control/README.md)).

**When data arrives:** the first data reaches Database Hub about **10-15 minutes after Run all** when the VMs already run, and **15-35 minutes** from a cold start (the VMs, T2's guest, T4): the notebook, the runbook, the start, and Database Hub's own lag, "Most performance data is available within 3 to 5 minutes ... Some inventory-based data can take up to 15 minutes" ([enable performance monitoring](https://learn.microsoft.com/fabric/database/hub/add-sql)). After that, each visual follows its slot by 3-15 minutes. "No data" means neither healthy nor down ([FAQ](https://learn.microsoft.com/fabric/database/hub/faq)). So start Run all about 30 minutes before the audience.

**Labels** come from the Learn pages cited. *Observed* means seen in the Database Hub UI, or in its telemetry, and not documented on Learn, so its label, threshold, or timing can change.

## The baseline run: why it matters, and when it doesn't

**What it runs.** The `baseline` activity profile runs the `healthy-baseline` scenario as back-to-back 30-minute runs ([`activity-profiles.json`](../scenarios/activity-profiles.json)): the steady Contoso Care mix of front-desk, billing, and scheduling lookups and small updates that stay within the seeded values.

| Target | Sessions | Intensity | What it does there |
|---|---|---|---|
| T1 `sqlvm01`, T2 `arcsql01` | 2 | 3 | Low, flat CPU; steady `Batch Requests/sec` and `Transactions/sec`; `Processes blocked` at 0 |
| T3 `ContosoCare` | 1 | 2 | The same, lighter. It also keeps the serverless database awake, which bills vCore-seconds, inside the free monthly allowance first when T3 has the free offer |
| T4 `contosocare` | 1 | 2 | The same lookups, a work-item update, and an audit row; low CPU and connections |
| T5 `contosocare`/`patient-events` | 1 | 2 | Point reads and small upserts over a fixed set of patient documents, so normalized RU stays low and the data stays the same size |

- **The quiet profile:** `"activityProfile": "baseline"` gives a demo without incidents; the default, `business-day`, runs the baseline under bounded incidents every hour, and the showcase runs it under its own.
- **On its own:** in the control notebook, `MODE = "activities"` with each `ACTIVITIES` entry's `"scenario"` set to `"baseline"`, then Run all, runs it alone for `DURATION_MINUTES` (5 to 120), with no read replica and no history; `./scripts/start-demo.ps1 -ActivityProfile baseline` runs it until `./scripts/stop-demo.ps1` or the nightly auto-shutdown.

**The history Database Hub's and Azure's own baselines need** is in the tables above: CPU spikes' 48 hours, the alert templates' 10 minutes, the advisors' day to a week, automatic tuning's check of "30 minutes to 72 hours", the drop-index recommendation's 90 days, the telemetry's 7-day retention, and quiet periods for the utilization suggestions.

**Why it matters:**

- **CPU spikes stays empty without history.** A target that sent no telemetry in the previous 48 hours has nothing to spike against, and demo VMs are deallocated most of the time.
- **Recommendations need days, not minutes.** Azure SQL Database's advisor needs at least a day of the same pattern, and PostgreSQL's Advisor up to a week. A single session never produces them; T3's automatic plan correction is the one exception ([above](#recommendations-and-optimizations)).
- **Incidents stand out against normal load.** **Recent signal changes**, a before-and-after chart, and an agent's "is this sustained or a spike?" all compare the incident with what came before; without a baseline, the first minutes of an incident are also the first minutes of data.
- **T3 stays awake.** Without activity, the serverless database pauses after `t3AutoPauseMinutes` (15 by default), and its charts show gaps. "No data" means neither healthy nor down ([FAQ](https://learn.microsoft.com/fabric/database/hub/faq)).

**Why it doesn't:**

- **Most visuals fill on absolute thresholds within one session:** High CPU (over 80%, *observed*; on T1 and T2 intermittent), waits by category, blocking, deadlocks, log, databases limited by service tier, and T4's CPU, connections, failed connections, IOPS, and storage.
- **The showcase brings its own baseline:** it runs the baseline under its incidents, so Run all 30 minutes before the audience is enough for those visuals.

**How long to run it** (`./scripts/estimate-cost.ps1` prices a session and a month at today's list prices; [cost management](cost-management.md#at-a-glance) has dated examples):

| You want | Do this | What it bills |
|---|---|---|
| A demo of the absolute-threshold visuals | **Run all** (the showcase) 30 minutes before the audience | A 90-minute session bills about 2 hours of the running costs |
| **CPU spikes** too | The day before, within 48 hours, run `baseline` on every target for 60 minutes, then Run all on the day: in the control notebook, `MODE = "activities"`, each `ACTIVITIES` entry's `"scenario"` set to `"baseline"`, and `DURATION_MINUTES = 60`, then Run all, which saves no history; or `start-demo.ps1 -ActivityProfile baseline` and `stop-demo.ps1` an hour later. The panel's minimum isn't documented. Prefer `baseline` to `business-day` here: hourly incidents raise the baseline that the next day's spikes are compared with (an inference, since the computation isn't documented) | About 1.4 billed hours more |
| T3's own index recommendation | Run the showcase, or `business-day`, on two or more days; then open the database's **Performance recommendation** page in the Azure portal (viewing it resumes a paused T3) | One session a day |
| PostgreSQL Advisor's history-based recommendations | Seven days on one configuration; not practical for this demo | n/a |

**Against the ceilings** ([ADR 0016](adr/0016-cost-profiles.md)): $20 a session (`sessionCeilingUsd`, a **Warning** above it) and $415 or more a month for a new configuration, from its region's worst case (`monthlyCeilingUsd`, a hard ceiling: preflight fails above it; a configuration keeps its own value); [cost management](cost-management.md#at-a-glance). The month's check also counts T4's 7-day automatic restart: about a day per restart with the nightly safety stop in place, which every deployment sets up (its role needs an Owner once), or T4 running for the rest of the month without it. The budget alerts at 50%, 80%, and 100% of the monthly ceiling. **Not in these figures:** your Fabric capacity, which runs the control notebook for about 2 hours a session (Run all keeps its Spark session for the whole session), Fabric and Power BI licenses, and each viewer's GitHub Copilot plan ([Fabric capacity](cost-management.md#microsoft-fabric-capacity)).

**What you lose by skipping it:** CPU spikes; Azure's own recommendations; a clean "before" picture in the Performance charts and in Query Store; an agent that can tell the incident from normal load; and, for the first minutes of a cold start, T3's charts, while it resumes.
