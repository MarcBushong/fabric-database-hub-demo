# Prerequisites

The core deployment needs **Contributor on an existing Azure subscription** and nothing more; an Owner, once, is recommended (P15, P16). README's [what you need](../README.md#what-you-need) is the short list. This page has every item, who provides it, and how `./scripts/preflight.ps1` and the Fabric scripts check it, in the six statuses; every role and its exact actions are in [permissions](permissions.md).

## Before you start

- **Sign in yourself** with `az login` to the demo's tenant (`--use-device-code` in a codespace or a container), and press Enter at the subscription selector for no changes. The scripts never sign in and never change your default subscription ([the subscription guard](#target-subscription-configuration-the-subscription-guard)); `./scripts/init.ps1`, or `deploy.ps1`'s first run, then writes your configuration.
- **The tools:** PowerShell 7.4, the Azure CLI with Bicep, Node.js 24 (20 and 22 also work), and Git, or the repository's dev container, locally or in GitHub Codespaces ([tools](#tools)). On Windows, `deploy.ps1` installs the .NET SDK it needs.
- **What it costs:** `./scripts/estimate-cost.ps1` estimates it before you deploy, with no sign-in: $20 a session (`sessionCeilingUsd`, a **Warning** above it) and $415 a month for a new configuration (`monthlyCeilingUsd`, a hard ceiling: preflight fails above it, `PREFLIGHT.COST.MONTHLY`; a configuration keeps its own value). The Fabric capacity, Fabric and Power BI licenses, and each viewer's GitHub Copilot plan are outside every estimate ([cost management](cost-management.md#at-a-glance)).
- **T5 (Azure Cosmos DB)** needs nothing more: no Owner, key, or sign-in ([tenant policies](#tenant-policies-checked-by-preflight)).

### How the Fabric checks work

`preflight.ps1`, `configure-fabric.ps1`, and `configure-fabric-app.ps1` run after the subscription guard and use documented interfaces only; Database Hub has no public API ([ADR 0012](adr/0012-validation-model.md#phase-9-database-hub-checks-2026-10-20)). In `deploy.ps1`, none of the Insights app's results keeps the run from **DONE**.

- **Tenant settings (P4, P12, P13):** the Fabric admin API [Tenants - List Tenant Settings](https://learn.microsoft.com/rest/api/fabric/admin/tenants/list-tenant-settings), matched by each setting's title, at most 25 calls a minute.
  - P4 is read on every run (`-FabricAdmin` is accepted and changes nothing): **Pass** when on for the organization, a **Warning** when on only for security groups, and **Manual action required** ("is disabled") when off. Only a Fabric administrator can read it; for anyone else it's **Manual action required**, "Couldn't check ... please confirm it's enabled", listed once under **Please confirm**, which never keeps `deploy.ps1` from **DONE**; only a setting read as off does. Its steps mention the Fabric Free licenses, for which Learn documents no check.
  - P12 and P13: preflight's `PREFLIGHT.FABRIC.APPSETTINGS` is a **Pass** when both are on for the organization, otherwise a **Warning**, also when only a Fabric administrator can read them; never a **Fail**. `configure-fabric-app.ps1` reads them with `-FabricAdmin`; without it, they're **Manual action required** with the portal steps, which turns into **Pass** in the same run when the step each one gates passes: the deploy for P12, the connector check for P13.
- **The workspace (P5):** found by name with [List Workspaces](https://learn.microsoft.com/rest/api/fabric/core/workspaces/list-workspaces), [List Capacities](https://learn.microsoft.com/rest/api/fabric/core/capacities/list-capacities), and [List Lakehouses](https://learn.microsoft.com/rest/api/fabric/lakehouse/items/list-lakehouses), and, when it's missing, made with [Create Workspace](https://learn.microsoft.com/rest/api/fabric/core/workspaces/create-workspace) on `fabric.capacityName` and [Create Lakehouse](https://learn.microsoft.com/rest/api/fabric/lakehouse/items/create-lakehouse) (`FABRIC.RESOLVE.*`); then your role, with [Get Workspace](https://learn.microsoft.com/rest/api/fabric/core/workspaces/get-workspace) and your Fabric token (`-FabricToken`, or one from the Azure CLI). Missing rights, a capacity that isn't running, or no role on an existing workspace are **Manual action required** with the steps; a capacity you can't see is a **Warning**, and a non-F SKU (for example a Trial) is **Manual action required** until a live run confirms its SKU name. `preflight.ps1` only reads: a workspace that doesn't exist yet is a **Warning** that names the capacity `deploy.ps1` creates it on. `configure-fabric-app.ps1` deploys only on an **Active** capacity, because `rayfin up` can start a trial or assign a capacity to a workspace without one.
- **Presenters (P8):** only when `assignRoles` is true: your right to create role assignments, then each role resolved by name and assigned to the presenters in `presenterObjectIds`; otherwise **Manual action required**, with one `az role assignment create` command per presenter and role.
- **The Rayfin CLI's sign-in (P14):** `DEPLOY.FABRIC.APPSIGNIN` is **Not selected** ("Not needed") by default; after a refusal, **Pass** when the CLI is signed in, a **Warning** when the sign-in was closed, failed, or timed out, and **Not supported** in CI or in a session that can't take keyboard input; never a **Fail**. `FABRIC.APP.SIGNIN` is a **Pass** with the Azure CLI's token; after Fabric refused it (`FABRIC.APP.TOKEN`, a **Warning**), or with `-RayfinSignIn`, it reads `rayfin login status --json` from the stage's pinned CLI, which never opens a browser, and is **Manual action required** with the exact command until it passes; nothing is deployed until then. With `-SignIn`, a missing sign-in runs in your console first. A refusal of the connector's direct route needs no sign-in: the app's queries run through Execute Queries with the same token. `FABRIC.APP.NODE` (`node --version`) is a **Warning** for a newer Node.js.

## Tenant policies (checked by preflight)

Preflight reads the Azure Policy assignments that apply to the subscription, including those inherited from management groups, and reports every conflict in one run (`PREFLIGHT.POLICY.*`, [ADR 0012](adr/0012-validation-model.md)). It only reads; it never changes or exempts a policy.

- **Read access:** Contributor can read the subscription's policy assignments. Definitions stored at a management group may need read access there (for example Reader); without it, preflight reports a **Warning** that names what it couldn't read, and `networkMode` `auto` resolves to private.
- **Adaptive defaults:** with `networkMode` `auto`, the default, a policy that turns off or denies public network access on SQL servers makes T3 private ([ADR 0007](adr/0007-networking-modes-and-egress.md)).
- **T5:** a policy that denies Azure Cosmos DB's resource types is a **Fail** (`PREFLIGHT.POLICY.RESOURCETYPES`) that names the fix: `"t5Enabled": false` leaves T5 out, and everything else deploys ([configuration](configuration.md#t5-azure-cosmos-db)). Where Azure refuses T5's account or its private endpoint during the run, `deploy.ps1` finishes everything else without T5 and says why (`DEPLOY.T5`, a **Warning**). The free tier's limits are in [limitations](limitations.md#targets-and-licensing).
- **Defender for Cloud:** policies that turn on Defender plans add cost; preflight reads the plans, and the cost estimate includes them ([cost management](cost-management.md#microsoft-defender-for-cloud)).
- **MFA:** where Azure enforces multifactor authentication for resource writes and deletes, sign in as a user with MFA. Workload identities, such as managed identities and service principals, including the GitHub OIDC identity (P7), aren't affected ([mandatory Microsoft Entra MFA](https://learn.microsoft.com/entra/identity/authentication/concept-mandatory-multifactor-authentication)).
- **Time:** reading large policy sets takes a few minutes. `preflight.ps1 -SkipPolicyInventory` skips it; `auto` then resolves to private.

## Target subscription configuration (the subscription guard)

`./scripts/init.ps1` writes `config/demo.config.json` (Git ignores it) from your sign-in: `subscriptionId`, `tenantId`, `azureAccount`, and the rest ([deployment](deployment.md#first-run-initps1)). Before the guard, its one Azure CLI call is `az account list`, a local, read-only read of the subscriptions your sign-in cached; it never runs `az account set` ([ADR 0023](adr/0023-first-run-automation.md)). Or copy `config/demo.config.example.json` to `config/demo.config.json` and set `subscriptionId` and `tenantId` yourself. Set `azureAccount` to the account you sign in with (your user principal name), or remove it: the guard then reports the account it finds with a **Warning** instead of failing on a different one.

**You don't need to change your default subscription, and the scripts never do.** The Azure CLI's default subscription belongs to the whole CLI profile, and other tools or sessions on the same machine can change it at any time, to another tenant included. So every script:

- passes `--subscription <subscriptionId>` on every Azure CLI call, and refuses `az account set`, `az login`, and anything else that would change the CLI context;
- never starts an interactive sign-in: sign in once yourself with `az login --tenant <tenantId>` as the account that runs the demo, and press Enter at the subscription selector for no changes ([sign in at a command line](https://learn.microsoft.com/cli/azure/authenticate-azure-cli-interactively));
- runs the subscription guard (`Assert-DemoAzContext`, check `PREFLIGHT.GUARD.CONTEXT`) before anything is written, and stops with **Fail**, naming the failed check, unless:
  - `az account show --subscription <subscriptionId>` returns that subscription in `tenantId`, as `azureAccount` when it's set;
  - read-only canaries reach the subscription through every authentication path the scripts use: an Azure Resource Manager read, `az rest` on the subscription's fully qualified URL, and tokens for Azure Resource Manager, Microsoft Fabric, Kusto (Hub telemetry), and Microsoft Graph, each checked locally for the right tenant and caller (tokens are never printed).

The guard runs once per script run and takes about half a minute. Sources: [az account](https://learn.microsoft.com/cli/azure/account), [az rest](https://learn.microsoft.com/cli/azure/reference-index#az-rest), [ADR 0011](adr/0011-control-surface-priority.md#guard-update-2026-10-21).

### Optional: a separate Azure CLI profile

On a machine whose Azure CLI profile is shared with other work, you can give the demo its own profile. This is a user action, and the scripts work without it.

```powershell
$env:AZURE_CONFIG_DIR = "$HOME/.azure-dbhub-demo"   # this PowerShell session only
az login --tenant <tenantId>                         # once, as the account that runs the demo
./scripts/status.ps1                                 # every script in this session uses that profile
```

- The Azure CLI keeps its configuration and token cache in `AZURE_CONFIG_DIR` (by default `%USERPROFILE%\.azure` on Windows and `$HOME/.azure` on Linux and macOS), so nothing else on the machine sees or changes this profile. Set the variable again in each new session. Sources: [Azure CLI configuration](https://learn.microsoft.com/cli/azure/azure-cli-configuration), [Concurrent execution](https://learn.microsoft.com/cli/azure/use-azure-cli-successfully-tips#concurrent-execution).
- It doesn't apply to Azure Cloud Shell, which signs you in for you and has its own profile.
- GitHub Actions doesn't need it: every job signs in on a fresh runner with OpenID Connect, and the workflows set `azureAccount` to the identity's client ID (`AZURE_CLIENT_ID`).

## Outbound access

The VMs have no public IPs, and their network security groups allow outbound HTTPS (TCP 443), which they need for Azure Arc, Database Hub's telemetry, and their downloads ([ADR 0007](adr/0007-networking-modes-and-egress.md), [ADR 0017](adr/0017-outbound-access.md)). In the default T2 mode, `JumpstartImage`, the T2 host also downloads its guest's disk from Arc Jumpstart's public storage, `jumpstartprodsg.blob.core.windows.net`, and Jumpstart's pinned script from GitHub, `raw.githubusercontent.com`. The demo's own rules already allow both; where a tenant firewall or proxy restricts outbound traffic, its administrator must allow them too.

Ask's chat relay, an Azure Container App, reaches GitHub (`github.com` and GitHub Copilot's API) over HTTPS from Azure's network, with Container Apps' default outbound access. Each viewer's browser reaches the relay at its `*.azurecontainerapps.io` address, and `github.com` once for the sign-in; a proxy that blocks either keeps the dock from connecting, and nothing else.

## Region

The default region is **West US 3**, which is in Database Hub's performance-monitoring list and the SQL VM unified-inventory list; Bastion Developer isn't offered there, so the scripts create Bastion Basic only on demand. Any region you choose must be in both lists: preflight passes West US 3 and East US 2 (checked 2026-10-19) and warns for any other region (`PREFLIGHT.P3.REGION`), which you then check against both lists yourself ([monitor SQL](https://learn.microsoft.com/fabric/database/hub/monitor-sql)). The Insights app also needs its Fabric capacity in a region that Fabric Apps supports ([region availability](https://learn.microsoft.com/fabric/apps/region-availability)).
