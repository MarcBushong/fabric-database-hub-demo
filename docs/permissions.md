# Permissions

Last reviewed 2026-11-19, against the code's three custom roles, Ask, and the Insights app's functions ([ADR 0008](adr/0008-identity-rbac-abac.md)). `validate.ps1 -Area Security` checks the footprint on a live environment ([verify it](#verify-the-footprint)).

## The model

- **Contributor on the subscription is the minimum** (P1): a Contributor deploys everything, and the deployment ends **DONE**.
- **Two owner-approved exceptions,** both with T5's container actions ([ADR 0027](adr/0027-t5-cosmos-db.md)): the [session control's](#the-on-demand-activity-control) Key Vault and its roles, A1 to A4 ([ADR 0020](adr/0020-on-demand-activity-control.md), [ADR 0026](adr/0026-one-run-all-session.md); P15), and the [nightly safety stop's](#the-nightly-safety-stop) read-and-stop custom role at the demo resource group ([ADR 0024](adr/0024-nightly-safety-stop.md); P16). Contributor deploys both; their role assignments need an Owner once per environment, and again after a destroy and redeploy. `deploy.ps1` assigns them when the deployer may (an Owner or a User Access Administrator); otherwise **DONE** names the one command an Owner runs once, `./scripts/grant-safety-stop.ps1`, which grants them all.
- **Everything else is optional,** gated by `assignRoles` or done once by an administrator: P7, P8, and P10 in [prerequisites](prerequisites.md). The opt-in Key Vault (`keyVault.enabled`) is the only feature that adds a Key Vault and data-plane roles in the demo resource group; it requires `assignRoles = true`, and `Initialize-DemoKeyVault` checks the permission before it deploys a vault, so none is left that nobody can use.

## What Contributor covers

- Creating the resource group and every resource, and registering resource providers (`Microsoft.Automation` and `Microsoft.App` when needed): the session control's resources in `rg-<prefix>-control`, the nightly safety stop's identity, Automation account, runbook, and schedules, and Ask's Container Apps environment `cae-<prefix>-<environment>-ask` and relay `ca-<prefix>-<environment>-ask`, which has no identity, role, or secret.
- Managed Run Command, VMAccess password resets, and SQL IaaS extension updates; Arc onboarding with the caller's own token, deleting stale Arc resources, and Arc SQL property updates; the Azure SQL Entra admin, Azure budgets, and on-demand Bastion.
- Reading the Hub telemetry endpoint and every target in Hub (Contributor includes Reader at subscription scope and `Microsoft.AzureArcData/sqlServerInstances/getTelemetry/action`), and everything `validate.ps1` and `status.ps1` read: role assignments, deployment history and operations, Run Command instance views, Resource Graph, budgets, auto-shutdown schedules, and the Automation jobs.
- Reading the Azure Policy assignments that apply to the subscription and the Defender for Cloud plans (preflight, read-only). Policy definitions stored at a management group may need read access there; preflight reports a Warning, not a Fail, when it can't read them.
- Reading your own permissions in the subscription and on the demo resource group (preflight, read-only: [Permissions - List For Resource Group](https://learn.microsoft.com/rest/api/authorization/permissions/list-for-resource-group)), so a first deployment's cost check counts the nightly safety stop that the run sets up when you can assign its role, and prices T5's container as the run will record it ([ADR 0016](adr/0016-cost-profiles.md#2026-11-19-a-first-deployments-worst-case-and-a-415-default-for-a-new-configuration)). It grants nothing.

## What needs more than Contributor

- **Role assignments and custom roles:** the session control's two custom roles and their assignments (P15) and the nightly safety stop's role (P16), both recommended, and the optional P7, P8, and `assignRoles = true`.
- **Key Vault data-plane roles:** the session control's A3, Key Vault Secrets User on its vault's three secrets in `rg-<prefix>-control` (P15), and, with `keyVault.enabled`, the opt-in vault's two roles.
- **Entra directory roles:** only for the hardened [T3 option](#t3-administration-options).
- **Fabric tenant settings,** which a Fabric administrator turns on: P4 (Database Hub), P12 and P13 (the Insights app), and **Create workspaces** when the scripts create the workspace ([prerequisites](prerequisites.md)).

## One-time administrator commands (optional)

The scripts print these with your values filled in. Shown here with placeholders:

```powershell
# P7: let the GitHub identity deploy (run by an Owner, User Access Administrator,
# or Role Based Access Control Administrator)
az role assignment create --subscription <subscriptionId> `
  --assignee-object-id <githubIdentityPrincipalId> --assignee-principal-type ServicePrincipal `
  --role Contributor --scope /subscriptions/<subscriptionId>

# P8: let a non-Contributor presenter use Hub
az role assignment create --subscription <subscriptionId> `
  --assignee-object-id <presenterObjectId> --assignee-principal-type User `
  --role Reader --scope /subscriptions/<subscriptionId>

# P8: let that presenter see T2 (Arc) performance data; the role is resolved by name
az role assignment create --subscription <subscriptionId> `
  --assignee-object-id <presenterObjectId> --assignee-principal-type User `
  --role "Azure Hybrid Database Administrator - Read Only Service Role" `
  --scope /subscriptions/<subscriptionId>/resourceGroups/rg-<prefix>-<env>

# Key Vault opt-in: give one more principal the one-time host password, on the vault only
# (<principalType>: User, Group, or ServicePrincipal, so the Azure CLI doesn't look the principal up)
az role assignment create --subscription <subscriptionId> `
  --assignee-object-id <objectId> --assignee-principal-type <principalType> `
  --role "Key Vault Secrets User" `
  --scope /subscriptions/<subscriptionId>/resourceGroups/rg-<prefix>-<env>/providers/Microsoft.KeyVault/vaults/kv-<prefix><env>-<deploymentId>
```

Administrators who delegate these assignments should prefer **Role Based Access Control Administrator with a condition** limited to the roles above, rather than Owner or User Access Administrator.

## The Key Vault opt-in

Off by default ([ADR 0008](adr/0008-identity-rbac-abac.md), [ADR 0009](adr/0009-secrets-handling.md); [how it's deployed](deployment.md#opt-in-the-password-in-key-vault-instead-of-the-clipboard)). With `keyVault.enabled`, which the configuration schema allows only with `assignRoles = true`:

- `deploy.ps1` deploys `kv-<prefix><environment>-<deploymentId>` in the demo resource group with Azure RBAC authorization and soft delete (`keyVault.softDeleteRetentionDays`, 7 by default; purge protection only with `keyVault.purgeProtection`), its firewall limited to `keyVault.allowedIpRanges` when that lists addresses. It holds only the one-time T2 host password: Bastion's documented RDP sign-in methods are Microsoft Entra ID (preview), username and password, and Kerberos ([connect with RDP](https://learn.microsoft.com/azure/bastion/bastion-connect-vm-rdp-windows)), so the operator copies the value from the vault's page in the portal instead of from a clipboard.
- Access is a role assignment on the vault only, resolved by role name: **Key Vault Secrets Officer** ("perform any action on the secrets of a key vault, except manage permissions") for the caller and `keyVault.operatorObjectIds` (for example the GitHub identity, so the scheduled stop can disable the secret), and **Key Vault Secrets User** ("read secret contents") for `keyVault.readerObjectIds` ([Key Vault RBAC](https://learn.microsoft.com/azure/key-vault/general/rbac-guide)). Assigning them needs `Microsoft.Authorization/roleAssignments/write` on the resource group (an Owner, User Access Administrator, or Role Based Access Control Administrator); without it, no vault is deployed. `validate.ps1 -Area Security` expects exactly that vault and those two roles on it ([verify the footprint](#verify-the-footprint)).

## The on-demand activity control

The session control (formerly the on-demand activity control) runs the control notebook's **Run all**, and it's part of every deployment ([ADR 0026](adr/0026-one-run-all-session.md); its first design is [ADR 0020](adr/0020-on-demand-activity-control.md)).

- **Contributor sets it up on every `deploy.ps1`:** it registers `Microsoft.Automation`, creates `rg-<prefix>-control`, deploys the identity, the Automation account, and the vault, publishes the runbooks, schedules the daily T4 safety stop, creates the webhook, and writes its URL and the session's two secrets into the vault, all through Azure Resource Manager (`Microsoft.KeyVault/vaults/secrets/write` is a control-plane action, so it needs no data-plane role). After the Fabric track it puts the notebook in Fabric, with your Fabric rights; `setup-activity-control.ps1` does the same on its own. `start-demo.ps1` and `stop-demo.ps1` remove a run's pending auto-stop (the schedules `dbhub-autostop` and `dbhub-autostop-backup`, with their job schedules), and `start-demo.ps1` reads the control account's jobs to wait for a stop in flight; your Contributor covers both, and neither ever stops a job. During a Run all session, `stop-demo.ps1` hands the session's stop to the control (2026-11-22): it starts a `DbHub-Stop` job ([Job - Create](https://learn.microsoft.com/rest/api/automation/job/create), `Microsoft.Automation/automationAccounts/jobs/write`), reads that job and its output, reads `DbHub-Stop`'s published content to see whether it knows `-RequestedBy`, and, right before the job, removes the session's auto-stop and lists the T2 host's Run Commands ([Virtual Machine Run Commands - List By Virtual Machine](https://learn.microsoft.com/rest/api/compute/virtual-machine-run-commands/list-by-virtual-machine)); your Contributor covers these too, and no role is assigned for them. The control's identity reads its own account's jobs, as its runbooks already do, to tell whether another stop of the session still runs. `capture-t2-golden.ps1` starts a `DbHub-Control` job the same way (2026-11-23), only when Azure Resource Manager can't give it the session's status copy, as once a tenant's policy has encrypted the variable `DbHubSessionStatus`: the job's `pending` action reads the copy with the sandbox's `Get-AutomationVariable`, which needs no role, and writes nothing; your Contributor covers starting it and reading its output.
- **The roles, granted once:** `deploy.ps1` creates and assigns them when you may (an Owner or a User Access Administrator); otherwise each missing one is a **Warning**, never a **Fail**, with `./scripts/grant-safety-stop.ps1`, which an Owner runs once, signed in with multifactor authentication, for these and the safety stop's role together:

  | # | Role | Principal | Scope |
  |---|---|---|---|
  | A1 | DbHub Demo Activity Operator | `id-<prefix>-automation` | `rg-<prefix>-<environment>` |
  | A2 | DbHub Demo Activity Operator | `id-<prefix>-automation` | `aa-<prefix>-control` |
  | A3 | Key Vault Secrets User | The Owner who grants, the environment's deployer, and `control.notebookUserObjectIds` | The secrets `dbhub-activity-webhook`, `dbhub-session-status`, and `dbhub-session-metrics` only |
  | A4 | DbHub Demo Session Writer | `id-<prefix>-automation` | The secrets `dbhub-session-status` and `dbhub-session-metrics` only |

  Both custom roles are assignable only in this subscription. The grant shows the identity's object ID before it assigns anything, `-WhatIf` lists each role's exact actions and each assignment without creating them, and a role that already has exactly its approved actions isn't written again.
- **Who can Run all (A3):** the environment's deployer is the person whose `deploy.ps1` last set up the control vault, as Azure records it on the vault (`systemData.lastModifiedBy`), resolved through Microsoft Graph, so a Contributor who deployed can Run all after an Owner's one grant, with nothing to edit. `CONTROL.ROLE.DEPLOYER` names them; when it can't tell, it's a **Warning** (**Not selected** when the vault's last change was an application's or a managed identity's), and the fix is to add the deployer's Microsoft Entra object ID to `control.notebookUserObjectIds` and run the grant again. Add each presenter who runs Run all there too. Nobody else gets the secrets: the webhook URL is a bearer secret.
- **DbHub Demo Activity Operator, 30 actions:** the 22 of [ADR 0020](adr/0020-on-demand-activity-control.md#the-role-dbhub-demo-activity-operator) (start and deallocate the demo's VMs, set their activity through managed Run Command, start and stop T4, and manage the control's own one-time schedules), and eight for a session:

  | Action | What a session uses it for | What it could also touch, at the demo resource group |
  |---|---|---|
  | `Microsoft.DBforPostgreSQL/flexibleServers/write` | Creates T4's read replica | Could change T4; the runbook never does |
  | `Microsoft.DBforPostgreSQL/flexibleServers/delete` | Deletes the replica after a session | Could delete T4; the runbook deletes only a server whose `replicationRole` says it's a read replica |
  | `Microsoft.DBforPostgreSQL/flexibleServers/configurations/write` | Sets the replica's `max_standby_streaming_delay` | Could change any server parameter of T4 or the replica |
  | `Microsoft.Insights/metrics/read` | Reads T4's, the replica's, and T5's metrics for the history | Read-only |
  | `Microsoft.Resources/tags/write` | Marks the demo busy for the nightly stop, and records the session | Could change any tag in the demo resource group, `deploymentId` included |
  | `Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/read` | Reads whether T5's container is there | Any Azure Cosmos DB container's settings there, where T5's account is the only account; never its documents |
  | `Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/write` | Creates T5's container at a session's start | Could change any container there; the runbook creates `contosocare/patient-events` only |
  | `Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/delete` | Deletes T5's container at a session's stop | Could delete any container there; the runbook deletes `contosocare/patient-events` only, and only while the demo resource group's `DbHubT5Container` tag is `Session` |

  No network join action: the replica's create names T4's delegated subnet and private DNS zone, and Azure creates it for a role without `Microsoft.Network/virtualNetworks/subnets/join/action` and `Microsoft.Network/privateDnsZones/join/action`. T5's three container actions touch nothing of its account, keys, network, or data plane; the owner approved them on 2026-11-19, because the container's throughput bills every hour it exists and an Azure Cosmos DB account has no stop ([ADR 0027](adr/0027-t5-cosmos-db.md); [Azure Cosmos DB's permissions](https://learn.microsoft.com/azure/role-based-access-control/permissions/databases#microsoftdocumentdb)).
- **Without the container actions** (an update by someone who isn't an Owner, until an Owner's `deploy.ps1` or grant), T5's container stays between sessions and bills, and `CONTROL.ROLE.DEFINITION` and `DEPLOY.T5.LIFECYCLE` say so. **With no role at all** (a Contributor's deployment), Run all can't start a session, `start-demo.ps1` creates the container with your own rights, and `stop-demo.ps1` deletes it; nothing automatic deletes it unless the nightly safety stop's role has its container actions, so `DEPLOY.T5.LIFECYCLE` is a **Warning** that says to run `stop-demo.ps1` after each session ([ADR 0027](adr/0027-t5-cosmos-db.md#2026-11-19-session-when-the-session-control-has-no-role-and-what-preflight-prices); [cost](cost-management.md#t5-azure-cosmos-db-2026-11-18)).
- **DbHub Demo Session Writer, 2 actions,** at the two session secrets only, never at the demo resource group, whose optional vault it never reaches: `Microsoft.KeyVault/vaults/secrets/read` reads their properties (Azure Resource Manager never returns a value), and `Microsoft.KeyVault/vaults/secrets/write` writes the session's status and metrics. It could overwrite those two values, which the notebook reads as status and metrics, never as credentials.
- **The Incident RCA's evidence needs nothing new (2026-11-20, [ADR 0031](adr/0031-incident-rca.md)):** the runbook's export uses A1's managed Run Command, which reads only, and writes the evidence as earlier versions of `dbhub-session-metrics` with A4; A3, Key Vault Secrets User on that secret, reads every version, so Run all's notebook reads them with its `keyvault` token ([Get Secret](https://learn.microsoft.com/rest/api/keyvault/secrets/get-secret/get-secret)). The versions aren't disabled after the save, because that needs `secrets/set` on the secret, which nobody here is granted ([the runbooks](../automation/README.md#the-incident-rcas-evidence)). The scripts' export (`stop-demo.ps1 -SaveHistory`, `deploy.ps1`'s snapshot, `configure-fabric.ps1 -RunLiveActivity`) uses your Contributor's managed Run Command, and stages its file in the demo lakehouse through OneLake with the Fabric workspace role deploy gave you (Admin, Member, or Contributor write OneLake: [secure data in OneLake](https://learn.microsoft.com/fabric/onelake/security/best-practices-secure-data-in-onelake)), with an Azure CLI token in the Storage audience ([OneLake access with APIs](https://learn.microsoft.com/fabric/onelake/onelake-access-api)).
- **No DevTestLab action:** a session ends before the VMs' auto-shutdown instead of moving it ([why](adr/0026-one-run-all-session.md#the-permissions-one-time-by-an-owner)).
- **Shared by the subscription:** custom roles belong to the whole subscription, so environments in one subscription share these two, and a `deploy.ps1` on newer code updates them for all; `control.roleNameSuffix` gives an environment its own, "DbHub Demo Activity Operator (*suffix*)" and "DbHub Demo Session Writer (*suffix*)", beside a demo on other code.
- **Why not one assignment at the subscription:** the subscription is shared, and there the identity could start, deallocate, and run commands on every VM. A1 and A2 limit it to the demo's VMs, T4 and its replica, T5's container, and its own control account.
- **After a redeploy,** A1 is deleted with the demo resource group: the next grant assigns it again (`deploy.ps1` when you may, otherwise `./scripts/grant-safety-stop.ps1`), and until then `validate.ps1` reports a **Warning** (`CONTROL.ROLE.A1`) and the runbook can't read the demo group. **Without the roles,** Run all can't act on the demo's resources, and says so; `./scripts/start-demo.ps1` runs a session from a PC with Contributor, and `./scripts/demo-control.ps1` sets the same activity profiles.

## The nightly safety stop

Part of every deployment ([ADR 0024](adr/0024-nightly-safety-stop.md); [what it does](cost-management.md#what-stops-or-pauses-on-its-own)). Contributor sets up everything except its role:

- **Contributor's part, on every `deploy.ps1`:** the identity `id-<prefix>-<environment>-safetystop` and the Automation account `aa-<prefix>-<environment>-safetystop` in the demo resource group (`infra/safetystop/safetystop.bicep`), the runbook `DbHub-Stop`, and its schedules.
- **The role:** the custom role **DbHub Demo Safety Stop**, assignable only in this subscription, with exactly 9 actions: read the resource group, the VMs, their instance view, T3's database, and T4; deallocate a VM; stop T4; and read and delete T5's container ([the list](adr/0024-nightly-safety-stop.md#the-role-dbhub-demo-safety-stop)). It can't start, create, or change anything, deletes nothing but T5's session-only container, has no Run Command, and has no Automation, Key Vault, Fabric, or role permission. Its one assignment is to the safety stop's identity at `rg-<prefix>-<environment>`, with the principal type set.
- **T5's container actions** (`Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/read` and `/delete`, approved by the owner on 2026-11-19: [ADR 0024](adr/0024-nightly-safety-stop.md#amendment-t5s-session-only-container-2026-11-19)) let it delete T5's container when a session's stop didn't, so its throughput doesn't bill all night. They could read or delete any Azure Cosmos DB container in the demo resource group, where T5's account is the only account; the runbook deletes `contosocare/patient-events` only, only while the `DbHubT5Container` tag is `Session` and `sqlvm01` doesn't run, and never the account, its keys, its network, or its data plane.
- **One definition for the subscription:** an environment's `deploy.ps1` on older code writes back the older 7 actions. `SAFETYSTOP.ROLE` is then a **Warning** that names what's missing when your run can't write it, and `STATUS.SAFETYSTOP` warns when its last run couldn't delete the container.
- **Who creates it:** `deploy.ps1`, when the person who runs it may create or update the role (`Microsoft.Authorization/roleDefinitions/write` in the subscription: an Owner or a User Access Administrator) and assign it (`Microsoft.Authorization/roleAssignments/write` on the demo resource group; a Role Based Access Control Administrator too, once the role exists), whatever `assignRoles` says: an owner-approved exception to [ADR 0008](adr/0008-identity-rbac-abac.md).
- **Otherwise:** `SAFETYSTOP.ROLE` is a **Warning**, never a **Fail**, and **DONE** says that nothing stops T4 after its 7-day restart until an Owner runs `./scripts/grant-safety-stop.ps1` once; the VMs' nightly auto-shutdown and T3's auto-pause still apply. The script runs the subscription guard, creates or updates the three custom roles and their assignments (P15, P16), and records T5's container lifecycle (`GRANT.T5.LIFECYCLE`). A destroy deletes the assignment with the group, and the role definition once no other environment's assignment holds it (`DESTROY.SAFETYSTOP.ROLE`); the next Owner's `deploy.ps1` or grant creates it again. With no Owner at all, the schedules still exist, and each job ends with `NotGranted` in its job history and in `status.ps1` (`STATUS.SAFETYSTOP`).

## Presenter access

Contributors already have everything Database Hub needs, so list only presenters who aren't Contributors in `presenterObjectIds`. `configure-fabric.ps1` handles them with `Set-DemoPresenterAccess`:

- **`assignRoles` false (the default):** nothing is called. `HUB.PRESENTER.READER` and `HUB.PRESENTER.ARCTELEMETRY` report **Manual action required**, with one `az role assignment create` command per presenter, filled in with your values. The commands leave out `--assignee-principal-type`, so they also work for a group.
- **`assignRoles` true:** the script checks that you can create role assignments at each scope, resolves each role **by name** at run time (`az role definition list --name`; no role ID is pinned), skips presenters who already hold it at that scope or above, and assigns the rest with `--assignee-object-id`, which needs no Microsoft Graph lookup. Without the rights, it's a **Fail** with the commands; `-WhatIf` assigns nothing.
- **Why two roles:** Hub discovery and performance data need Reader on the subscription ([monitor SQL](https://learn.microsoft.com/fabric/database/hub/monitor-sql)). Arc SQL performance data also needs `Microsoft.AzureArcData/sqlServerInstances/getTelemetry/action`, which the built-in **Azure Hybrid Database Administrator - Read Only Service Role** includes ([add SQL](https://learn.microsoft.com/fabric/database/hub/add-sql)); the Azure RBAC built-in role catalog doesn't list it, so it's resolved by name, and any role with that action works. With `t2SqlInstallMode = Developer`, T2 sends no performance data, so the Arc role is **Not supported** and isn't assigned.
- **The demo workspace:** after `deploy.ps1` imports the Real-Time Dashboard, each presenter in `presenterObjectIds` without a role on the demo workspace gets **Viewer** through the documented Add Workspace Role Assignment, which shares `RTD_DatabaseHub_LiveView`, the history report, and the Insights app (`FABRIC.PRESENTER.VIEWER`; Fabric's REST API can't share one item). It doesn't depend on `assignRoles`, since it's a role on the demo's own workspace, not an Azure role; a presenter who has a role keeps it, and you need Admin or Member on the workspace ([workspace roles](https://learn.microsoft.com/fabric/fundamentals/roles-workspaces)). A failure is a **Warning** with the steps in the Fabric portal.
- **Database Agents:** saving T3 in **Database agent settings** needs Azure write access on T3's database (`Microsoft.Sql/servers/databases/write`), which Contributor has; a Reader-only presenter sees the agent's issues but can't save the selection ([enable Database Agents](https://learn.microsoft.com/fabric/database/hub/enable-database-agents)). `T3.AGENT` checks the signed-in account's access, and the account that deployed the demo makes the one-time selection, which the Database Agent beat requires (`HUB.AGENT.T3`, [step by step](database-agents.md)). A **Save** checks your write access on every selected database, and the selection is saved for the tenant, so where others in your tenant use Database Agents, a database of theirs that you can't write to fails your **Save**: then whoever manages Database Agents in the tenant adds T3, rather than you unchecking theirs ([troubleshooting](troubleshooting.md#database-agent-settings)).

## Presentation surfaces and viewer licensing

Who can see what on each [presentation surface](presentation.md):

- **Database Hub and the Real-Time Dashboard** use the viewer's own Azure access, as for presenters above. The dashboard's data source is the documented telemetry proxy with pass-through identity, so sharing the dashboard doesn't share the data; a viewer without Reader sees empty tiles ([Real-Time Dashboard permissions](https://learn.microsoft.com/fabric/real-time-intelligence/dashboard-permissions)). Neither is Power BI content, so a Fabric Free license is enough.
- **The history report** is Power BI content: "On F SKUs smaller than F64, each user viewing Power BI content must have Pro, PPU, or an individual trial; on F64 or larger, users with only a Free license and a viewer role can view" ([Fabric licenses](https://learn.microsoft.com/fabric/enterprise/licenses)). So on a capacity smaller than F64, its viewers need Pro, PPU, or a trial (optional prerequisite P11); a presenter who shares their screen needs nothing more. The viewers' licenses are assumed: `PREFLIGHT.FABRIC.VIEWERLICENSE` is **Not selected** and reads nothing, and no script assigns licenses, which are assigned outside Azure.
- **The Insights app** isn't in Learn's list of Power BI items, but it reads the semantic model as the viewer, so plan for the same rule as the report; that's not yet verified. Its viewers need access to the app item and Read and Build on `SM_DatabaseHub_History`, and no Azure access ([the app's guide](../fabric/app/README.md#open-the-app)): its live-estate pages and Ask show them the owner's Database Hub view of the demo resource group.
- **Ask** needs each viewer's own GitHub account and Copilot plan, which their questions use ([role matrix](#role-matrix)).

## GitHub (optional)

The GitHub side needs no Azure permission beyond the one Contributor assignment for the GitHub identity (P7), and the scripts act on GitHub only when you ask ([ADR 0022](adr/0022-public-repository-and-github-actions-hardening.md)):

- **`setup-github-oidc.ps1 -ConfigureGitHub`** and **`setup-github-repo.ps1`** use the GitHub CLI as the account you signed in with (`gh auth login`; the scripts never sign in), and need that account to be an **administrator of the repository**: only administrators create environments and change security settings. Each environment gets you as its required reviewer.
- **On a private repository,** such as a private fork, on GitHub Free, Pro, or Team, what GitHub refuses (rulesets, required reviewers, private vulnerability reporting) is **Manual action required**, to run again once the repository is public.
- **The workflows' own token** has `contents: read`, and `id-token: write` only on the job that signs in to Azure; no workflow writes to the repository.

## T3 administration options

| Option | When | How |
|---|---|---|
| Default (P6) | You can own an Entra security group | The group is the T3 admin; T1's identity is added to it; T1 configures T3 |

## T4 and T5 access

- **T4,** the PostgreSQL flexible server, needs nothing beyond P1 and P6 ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md)): the template makes the P6 group T4's Microsoft Entra administrator (`flexibleServers/administrators`, which Contributor can write), T1's managed identity signs in through the group to create the runner's role, and no Azure role assignment is made; Database Hub monitors T4 with subscription Reader, which Contributor covers. To see T4's queries or sessions yourself, sign in to `contosocare` as a P6 member from a demo VM (T4 has no public endpoint).
- **T5,** the Azure Cosmos DB account, needs nothing beyond P1 to deploy and to show in Database Hub ([ADR 0027](adr/0027-t5-cosmos-db.md)): no group and no Azure role assignment. Its container exists only during a session once the session control's role has the container actions ([above](#the-on-demand-activity-control)).
  - **T1's data-plane role:** the template gives T1's managed identity **Cosmos DB Built-in Data Contributor** (`00000000-0000-0000-0000-000000000002`) at the account: a `Microsoft.DocumentDB/databaseAccounts/sqlRoleAssignments` resource, the account's own role-based access control, which Contributor creates (`sqlRoleAssignments/write`), not an Azure role assignment, so ADR 0008's Contributor-only model holds ([grant data-plane access](https://learn.microsoft.com/azure/cosmos-db/nosql/how-to-grant-data-plane-access)). The runner reads and writes documents only in `contosocare`/`patient-events`. Local (key) authentication is off, so no account key works for data, and nothing stores one.
  - **You and your presenters:** Database Hub reads T5 from Azure Resource Graph and Azure Monitor, so Reader on the subscription is enough to see it in Estate and Performance ([monitor Azure Cosmos DB](https://learn.microsoft.com/fabric/database/hub/monitor-cosmos-db)). Reading T5's documents yourself (the portal's Data Explorer) needs a data-plane role of your own, which the demo doesn't grant, from a demo VM: the account has no public network access.
