# Cleanup

`./scripts/destroy.ps1` deletes everything `deploy.ps1` created for the environment in your configuration, each part only when it can tell it's this environment's ([ADR 0002](adr/0002-resource-group-topology.md)), then checks that nothing is left. It's the only cleanup the demo needs: between demos, `stop-demo.ps1` stops what bills by the hour, and destroy deletes every billable resource but the T2 golden snapshots, which it keeps unless `-IncludeGolden` ([cost after destroy](#cost-after-destroy)). The **destroy** workflow in GitHub Actions does the same; it's optional, for maintainers, and you never need it.

Your environment is yours to destroy. Before it deletes anything, it lists what it deletes and what it keeps, and asks you to confirm (`-Force` doesn't ask). Each part reports its own `DESTROY.*` result. The Fabric, session control, and security group parts run first, and one that fails doesn't stop the others. An Arc or resource group **Fail** stops what comes after it; run `destroy.ps1` again to finish. It takes about 20 minutes, most of it the resource group's delete.

## What `destroy.ps1` does

1. **Records a manifest**, `out/destroy-manifest-<environment>.json`, before anything goes: the resource group's ID, its `deploymentId` tag, the Microsoft Entra principal IDs of its managed identities (the VMs', the Arc machine's, the T3 server's, and any user-assigned one), and the names the residual check needs; no secret. Once the group is gone, only the manifest knows the identities, so a run after an interruption keeps it ([when something fails partway](#when-something-fails-partway)). Every prefix and subscription with that environment name shares the default path ([check again later](#check-again-later-read-only)).
2. **Deletes what else `deploy.ps1` created**, each part only when it can tell it's this environment's:
   - **Fabric** (`DESTROY.FABRIC.CONTROL`, then `DESTROY.FABRIC.WORKSPACE`): the control's workspace (`control.fabricWorkspaceName`, "&lt;workspace&gt; Control" by default) with its managed private endpoint, when it holds only the control notebook `NB_DatabaseHub_Control` and that notebook's `RESOURCE_GROUP` is this environment's group, or it's empty and the control serves this environment. Then the demo's workspace (`fabric.workspaceName`), when it holds only what the demo creates: the lakehouse `LH_DatabaseHub` with its SQL analytics endpoint, the notebooks from `fabric/notebooks`, `NB_DatabaseHub_Control` (in the folder "DBHub Control" when the control's vault is public), the Real-Time Dashboard `RTD_DatabaseHub_LiveView`, the model `SM_DatabaseHub_History`, the report `RPT_DatabaseHub_History`, and the Insights app's three items: `APP_DatabaseHub_Insights` (an `AppBackend`) and the user data functions its backend makes beside it, `APP_DatabaseHub_Insights_connector` (its connector) and `APP_DatabaseHub_Insights` (the live estate and Manage), as `config/versions.json` lists them (`fabricApp.backendItems`). A workspace with anything else stays whole, and its result names what isn't the demo's (**Not selected**). `-KeepFabric` keeps both, with the history in the lakehouse (**Not selected**). A Fabric administrator can restore a deleted workspace during the tenant's retention period, 7 days by default ([retention and recovery](https://learn.microsoft.com/fabric/admin/portal-workspaces#retention-and-recovery)).
   - **Not while another demo environment uses the workspace, or might:** each `deploy.ps1` records its environment's workspaces on its resource group (the tags `DbHubFabricWorkspaceId` and `DbHubControlWorkspaceId`), and one Azure Resource Graph query across every subscription you can read finds the other demo environments ([query scope](https://learn.microsoft.com/azure/governance/resource-graph/concepts/query-language#query-scope), [ADR 0002](adr/0002-resource-group-topology.md#amendment-2026-11-17-a-workspace-another-environment-might-use-stays)). A workspace another environment records stays, and so does every workspace while an environment without those tags exists (one deployed before then, or one still being deployed that hasn't recorded them yet; the result says which, since 2026-11-19) or Resource Graph can't be read: a **Warning** that names the other environment, with the fix. A paused capacity, a missing workspace Admin role, or another Fabric error is a **Warning** with the fix too.
   - **The session control** in `rg-<prefix>-control` (`DESTROY.CONTROL`, with `DESTROY.CONTROL.ROLES` and `DESTROY.CONTROL.RESOURCES`), when the settings its runbooks were published with name this environment's resource group: its Azure part, as `setup-activity-control.ps1 -Remove` deletes it ([below](#the-on-demand-activity-control)): the role assignments, the custom roles once no role assignment holds them, the identity `id-<prefix>-automation`, the Key Vault (purged), and last the Automation account with its runbooks, schedules, and webhook; then the group, once nothing else is in it, as is an empty one an earlier run left. Deleting role assignments needs Owner or User Access Administrator: for anyone else, `DESTROY.CONTROL.ROLES` is **Manual action required**, `DESTROY.CONTROL` is a **Warning**, and the rest still goes. A control that serves another environment stays (**Not selected**, with the command that removes it).
   - **The T3 and T4 administrators' group** (`DESTROY.ENTRA.GROUP`), the security group `t3AdminGroupObjectId` names, when `init.ps1` created it for this environment: its name is `<prefix>-<environment>-sql-admins`, and its description ends "Created by init.ps1.". A group you supplied stays (**Not selected**).
3. **Deletes the Arc resources** that onboarding creates outside the template (`DESTROY.ARC.SQLINSTANCES`, then `DESTROY.ARC.MACHINES`): every `Microsoft.AzureArcData/sqlServerInstances` resource in the group, T2's and T1's unified-inventory instances, with their Arc SQL databases; then every `Microsoft.HybridCompute/machines` resource, with its extensions, license profiles, and Run Commands. No cascade from a machine to its SQL Server instances is documented, so the order is explicit, and each delete waits until a read returns Not Found ([Disconnect SQL Server instances from Azure Arc](https://learn.microsoft.com/sql/sql-server/azure-arc/delete-from-azure-arc), [machines](https://learn.microsoft.com/rest/api/hybridcompute/machines/delete), [SQL Server instances](https://learn.microsoft.com/rest/api/azurearcdata/sql-server-instances/delete)).
4. **Deletes the resource group** with everything in it (`az group delete`, `DESTROY.RESOURCEGROUP`), after T4's read replica `pgreplica01-<deploymentId>` when a session left one (`DESTROY.T4.REPLICA`), because Azure deletes a server's read replicas before the server ([read replicas](https://learn.microsoft.com/azure/postgresql/read-replica/concepts-read-replicas)). In it: the VMs with their disks, network interfaces, Run Commands, and the extensions a policy added (preflight lists them: `PREFLIGHT.POLICY.EXTENSIONS`); the virtual network with its NSGs, private endpoints, and private DNS zones with their virtual network links; T3's server and database; T4's flexible server `pgflex01-<deploymentId>`, stopped or not, with its database, PostgreSQL roles, and backups; T5's Azure Cosmos DB account `cosmos01-<deploymentId>` with its database, its container when there is one, its data-plane role assignment, private endpoint, and backups ([ADR 0027](adr/0027-t5-cosmos-db.md)); Ask's chat relay, the Container Apps environment `cae-<prefix>-<environment>-ask` and the app `ca-<prefix>-<environment>-ask` ([ADR 0028](adr/0028-ask-copilot-in-the-insights-app.md)); the auto-shutdown schedules; the nightly safety stop's identity `id-<prefix>-<environment>-safetystop`, its Automation account with its runbook and schedules, and its role assignment ([ADR 0024](adr/0024-nightly-safety-stop.md)); Bastion and its public IP if they exist; and, with the Key Vault opt-in, the vault, which goes into soft delete (`DESTROY.KEYVAULT`). It waits until the group is gone (`-WaitMinutes`, 60 by default). The system-assigned identities go with their resources, and with them T1's membership in the P6 group.
5. **Deletes the subscription deployment record** `<prefix>-<environment>-main` (`dbhub-demo-main` with the defaults), which holds the template's parameters and outputs (`DESTROY.DEPLOYMENT`; [`az deployment sub delete`](https://learn.microsoft.com/cli/azure/deployment/sub#az-deployment-sub-delete)), and **the budget** at the group's scope (`DESTROY.BUDGET`; [Budgets - Delete](https://learn.microsoft.com/rest/api/consumption/budgets/delete)): both outlive the group.
6. **Deletes the nightly safety stop's custom role** "DbHub Demo Safety Stop", a role definition in the subscription, once no role assignment holds it (`DESTROY.SAFETYSTOP.ROLE` **Pass**). Its assignment here went with the group; while another environment's nightly safety stop holds it, it stays (**Not selected**, with how many assignments hold it). The next deployment creates it again ([delete a custom role](https://learn.microsoft.com/azure/role-based-access-control/custom-roles-cli#delete-a-custom-role)).
7. **Keeps the golden group** `rg-<prefix>-golden` with its T2 golden snapshots (`DESTROY.GOLDEN` **Not selected**), so the next `deploy.ps1` restores T2 from it. `-IncludeGolden` deletes it too (**Pass**); the next deploy then makes T2 again, with no person. A golden group that doesn't exist is never listed as kept: the list before the confirmation and `DESTROY.GOLDEN` (**Pass**) say it doesn't exist, with or without `-IncludeGolden` (since 2026-11-19).
8. **Runs the residual check** (`TEARDOWN.RESIDUAL.*`, [below](#the-residual-check)) and sums it up in `DESTROY.RESIDUAL`: **Pass** only when every check is clean; **Fail** when something is left, so `destroy.ps1` exits with 1; **Warning** when nothing was found but something couldn't be verified.

With `fabric.manageCapacity` true, destroy also pauses a Fabric capacity that `start-demo.ps1` resumed (`DESTROY.FABRIC.CAPACITY`), after the workspaces' deletes, which need it running, and before the group's; otherwise it never calls the capacity. Nothing needs stopping first: the workloads run on T1 and the T2 host, which destroy deletes; T4's runner role lives in the server, and T5's data-plane role assignment is a child of its account. A T4 that Azure refused to create leaves only its private DNS zone `<prefix>-<environment>.private.postgres.database.azure.com` and that zone's virtual network link, which go with the group.

## What stays, and how to remove it

- **The Fabric capacity and your licenses:** you manage them ([presentation surfaces](presentation.md#cost)).
- **T3's selection in Database Agents,** if you made it (`HUB.AGENT.T3`): Database Hub keeps a database in **Database agent settings** after it's deleted, and a **Save** there checks every selected database, so the deleted T3 makes every later **Save** fail, the next deployment's T3 included, until it's removed (live, 2026-11-20; [enable Database Agents](https://learn.microsoft.com/fabric/database/hub/enable-database-agents)). No API removes it, so `destroy.ps1` lists it among what it keeps, says before it asks to remove it, and ends with `DESTROY.HUB.AGENT.T3` (**Manual action required**, with the link; the exit code doesn't count it). In Database Hub, **Manage agents** > **Database agent settings**, uncheck `azuresql01-<deploymentId>/ContosoCare` and **Save**, before or after `destroy.ps1`. The list shows no server, so other environments' T3s are rows named `ContosoCare` too: after `destroy.ps1`, clear the selection, check one at a time and **Save**, and uncheck any whose **Save** fails, as the deleted T3's does ([troubleshooting](troubleshooting.md#t3)).
- **What another environment uses, or what isn't the demo's:** a session control, Fabric workspace, or custom role that another environment uses or might; a workspace with items the demo didn't create; and a security group you supplied. Each result names it and says why it stayed.
- **`rg-<prefix>-golden`**, the T2 golden snapshots ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)), unless `-IncludeGolden`. It belongs to the prefix, not to one environment, and bills every month ([cost management](cost-management.md)).
- **The GitHub identity `id-<prefix>-github`**, which `setup-github-oidc.ps1` creates in `rg-<prefix>-control`; that group stays while it's there. Remove the identity yourself if you no longer use the GitHub path.
- **Role assignments your tenant made** for the demo's identities outside the demo, such as a policy's on a shared storage account: they stay, orphaned, and don't bill; removing one needs Owner, User Access Administrator, or Role Based Access Control Administrator ([below](#role-assignments-a-tenant-policy-made)).
- **Subscription settings:** resource provider registrations, such as `Microsoft.App`, which Ask's relay setup registers, are free, and destroy never unregisters them, because other workloads may use them. Microsoft Defender for Cloud plans, which your tenant may enforce with Azure Policy, bill per protected resource, so they stop billing for the demo once its resources are gone ([ADR 0016](adr/0016-cost-profiles.md)).
- **Shared resources that Azure, Defender for Cloud, or a policy creates once per subscription or region**, outside the demo's group, such as Network Watcher (`NetworkWatcherRG`, [enabled automatically](https://learn.microsoft.com/azure/network-watcher/network-watcher-create) when a virtual network is created in a region) and a default Log Analytics workspace in `DefaultResourceGroup-<region>`. Other workloads use them; `TEARDOWN.RESIDUAL.REFERENCES` reports any that still names the deleted group, so you can decide.
- **Records about deleted resources:** Defender for Cloud assessments, Azure Policy compliance states, and guest configuration assignments list them for a while; they aren't resources, can't be deleted, don't bill, and the services remove them (`TEARDOWN.RESIDUAL.RECORDS` reports them as evidence). The demo creates no diagnostic settings, which would outlive their resource and attach to a new one with the same name ([diagnostic settings](https://learn.microsoft.com/azure/azure-monitor/platform/diagnostic-settings)).
- **On your PC:** your clone keeps `config/demo.config.json` and `out/`: the logs, the destroy manifest, and the Insights app's Git-ignored deploy stage `out/fabric-app`, whose record of the deleted app the next `deploy.ps1` drops before `rayfin up`. The Azure CLI's and the Rayfin CLI's sign-ins stay until `az logout` and, from the repository root, `./out/fabric-app/node_modules/.bin/rayfin logout` ([your sign-in and tokens](security-model.md#your-sign-in-and-tokens)). Delete the clone when you're done. The app's deployment creates nothing else outside the workspace and the resource group: no Microsoft Entra app, service principal, or Fabric connection.
- **Ask's GitHub sign-ins:** each viewer's authorization of the OAuth App **Database Hub Insights Ask** stays on their GitHub account until they revoke it at <https://github.com/settings/applications> (**Authorized OAuth Apps**, then **Revoke**; [GitHub's steps](https://docs.github.com/apps/oauth-apps/using-oauth-apps/reviewing-your-authorized-oauth-apps)). A browser keeps its sign-in until **Sign out of GitHub** in the chat's account menu clears it, so use that before you destroy: afterward the app, and its menu, are gone. An organization owner who approved the app can deny it again in the organization's settings ([denying a previously approved OAuth app](https://docs.github.com/organizations/managing-oauth-access-to-your-organizations-data/denying-access-to-a-previously-approved-oauth-app-for-your-organization)). None of it bills ([Ask](security-model.md#ask-the-copilot-chat-in-the-insights-app-2026-11-18)).
- **An Arc-enabled machine you keep:** destroy deletes T2's guest with its host, the Connected Machine agent and the SQL Server extension inside it included. For a machine you keep elsewhere, follow Learn's order instead: tag it `ArcSQLServerExtensionDeployment` `Disabled`, uninstall the extension, delete the instance resource, then disconnect the agent ([azcmagent disconnect](https://learn.microsoft.com/azure/azure-arc/servers/azcmagent-disconnect)).

## Commands

| Command | What it does |
|---|---|
| `./scripts/destroy.ps1` | Asks, then runs the steps above for the configured environment (`-ConfigPath`, default `config/demo.config.json`) |
| `./scripts/destroy.ps1 -Force` | The same without asking (the **destroy** workflow passes it after you type the environment's name again) |
| `./scripts/destroy.ps1 -KeepFabric` | Keeps the demo's and the control's Fabric workspaces, with their items and the history in the lakehouse |
| `./scripts/destroy.ps1 -WhatIf` | Reads only: nothing is deleted, and no manifest is written (`DESTROY.RESOURCEGROUP` is **Not selected**) |
| `./scripts/destroy.ps1 -IfExpired` | Deletes only after the day of the group's `expiresOn` tag (the **expiry** workflow) |
| `./scripts/destroy.ps1 -IncludeGolden` | Also deletes `rg-<prefix>-golden` and its T2 golden snapshots; the next deploy makes T2 again, with no person |
| `./scripts/destroy.ps1 -WithoutGolden` | Changes nothing now: it overrides `DESTROY.GOLDEN.GUARD`, which no longer refuses anything, because a configuration's `PaygWizard` runs as `JumpstartImage` |
| `-SkipResidueCheck`, `-ResidueWaitMinutes <n>` | Skip the residual check (`DESTROY.RESIDUAL` **Not selected**), or wait longer than 10 minutes for Azure Resource Graph and Microsoft Entra to catch up |
| `-ManifestPath <path>`, `-WaitMinutes <n>`, `-OutputPath <path>` | Where the manifest goes; how long to wait for the group's delete; where the results go (`out/destroy.jsonl`) |
| `./scripts/destroy.ps1 -ResidueOnly [-ManifestPath <path>]` | Deletes nothing and asks nothing: runs only the residual check again with the manifest an earlier destroy wrote, into `out/destroy-residue-<environment>.jsonl` ([below](#check-again-later-read-only)) |
| `./tests/teardown/Invoke-TeardownTest.ps1 -ConfigPath <path>` | Runs the residual check again later, read-only, as Pester tests ([tests/teardown](../tests/teardown/README.md)) |
| `./scripts/setup-activity-control.ps1 -Remove` | Deletes only the session control and keeps the environment ([below](#the-on-demand-activity-control)) |

`./scripts/validate.ps1 -Area Teardown` adds a single read-only `TEARDOWN.RESIDUAL` check that also works while the environment is deployed. It matches the environment's `deploymentId` only, so after destroy, pass `-DeploymentId <id>`: the resource group that recorded it is gone. Without it, the check is a **Warning**; `destroy.ps1 -ResidueOnly` reads the `deploymentId` from the manifest instead.

`destroy.ps1` never signs in or changes your default subscription. If its subscription guard fails, nothing was read or deleted: sign in to the configured tenant yourself (`az login --tenant <tenantId>`) and run it again ([your sign-in and tokens](security-model.md#your-sign-in-and-tokens)). On a shared machine, a separate `AZURE_CONFIG_DIR` keeps your sign-in and default subscription apart from others' ([Azure CLI configuration](https://learn.microsoft.com/cli/azure/azure-cli-configuration), [prerequisites](prerequisites.md#optional-a-separate-azure-cli-profile)).

## When something fails partway

- **Interrupted destroy** (Ctrl+C, a sleeping laptop, an Actions timeout): run `destroy.ps1` again. It finishes what's left, the Fabric, session control, and security group parts included, also once the group is gone, and waits for a group that's still being deleted (`ResourceGroupBeingDeleted`). It keeps the manifest an earlier run recorded for the same resource group and subscription: once the group is gone, that manifest replaces the new one, which can't know the identities; while the group still exists, the identities it recorded for the same `deploymentId` are added, because some of their resources may already be gone. Without any manifest, the `deploymentId` comes from the deployment record's output, and the identity check is a **Warning**.
- **`DESTROY.FABRIC.*` Warning:** a workspace wasn't deleted. A paused capacity: resume it, or ask its administrator, then run `destroy.ps1` again. A missing Admin role on the workspace: ask one of its admins, or delete it in Fabric (**Workspace settings** > **Remove this workspace**). Another environment uses it, or might (the result names it): run `destroy.ps1` again after that environment's next `deploy.ps1`, which records the workspaces it uses, or after its destroy; or delete the workspace in Fabric once nothing uses it. Resource Graph couldn't be read: run `destroy.ps1` again later. Anything else: run it again in a few minutes.
- **`DESTROY.FABRIC.WORKSPACE` Not selected:** the demo's workspace holds something the demo didn't create, which the result names, so it stays whole. If it's yours to delete, delete that item and run `destroy.ps1` again, or delete the workspace in Fabric (**Workspace settings** > **Remove this workspace**). When the item is `UserDataFunction APP_DatabaseHub_Insights`, the Insights app's functions, the destroy ran on code from before 2026-11-19, which didn't know that item: update your copy (`destroy.ps1` doesn't update itself; `git pull` on `main`) and run `destroy.ps1` again.
- **`DESTROY.CONTROL` Warning:** part of the session control is left; `DESTROY.CONTROL.ROLES` and `DESTROY.CONTROL.RESOURCES` say what. For its resources, run `destroy.ps1` again. `DESTROY.CONTROL.ROLES` is **Manual action required** when you can't delete role assignments: an Owner or User Access Administrator removes what's left ([Remove Azure role assignments](https://learn.microsoft.com/azure/role-based-access-control/role-assignments-remove)).
- **`DESTROY.ENTRA.GROUP` Warning:** the security group couldn't be deleted. One of its owners, or a Groups Administrator, deletes it in the Microsoft Entra admin center (**Groups** > the group > **Delete**).
- **`DESTROY.ARC.*` Fail:** an Arc resource couldn't be deleted, so the resource group and everything after it weren't deleted (the Fabric, session control, and security group parts ran before). Delete it in the portal (**Azure Arc**, then **SQL Server instances**, then **Machines**), then run `destroy.ps1` again. Learn notes that a deleted Arc SQL Server resource can stay visible in the portal for a while because of caching; Resource Graph is the reference, and it doesn't bill.
- **`DESTROY.RESOURCEGROUP` Fail:** a lock or a policy blocked the delete, so nothing after it ran: the deployment record, the budget, the custom role, and the residual check. Locks are off by default (`enableLocks`), and removing one needs more than Contributor ([ADR 0001](adr/0001-iac-bicep-avm-compiled-arm.md)). Then run `destroy.ps1` again.
- **`DESTROY.RESOURCEGROUP` Warning:** the group was still being deleted after `-WaitMinutes`. Run `destroy.ps1` again later; it finishes the cleanup and checks again.
- **`DESTROY.DEPLOYMENT` Warning:** delete the record yourself: `az deployment sub delete --name <prefix>-<environment>-main --subscription <subscriptionId>`.
- **`DESTROY.BUDGET` Warning:** delete the budget `budget-<prefix>-<environment>` in Cost Management under **Budgets**, with the resource group as the scope; it stays listed after the group is gone.
- **`DESTROY.RESIDUAL` Fail:** the failing `TEARDOWN.RESIDUAL.*` results list what's left in their evidence (`remaining`): only what Azure Resource Manager still returned, or a role assignment the demo made. Run `destroy.ps1` again for anything in the group; delete anything outside it by name in the portal, or with `az resource delete --resource-group <group> --name <name> --resource-type <type> --subscription <subscriptionId>`. A role assignment left behind (`Identity not found` in **Access control (IAM)**) needs Owner, User Access Administrator, or Role Based Access Control Administrator.
- **`DESTROY.RESIDUAL` Warning:** nothing was found, but a check couldn't be verified or needs someone else: Resource Graph didn't list the configured subscription, Microsoft Graph answered for another tenant, a read failed, rows stayed unconfirmed after the check's 25 reads ([Resource Graph lags](#resource-graph-lags-behind-deletes)), a tenant policy's role assignment for a deleted identity is left ([below](#role-assignments-a-tenant-policy-made)), or the check couldn't run after the deletes. Run `./scripts/destroy.ps1 -ResidueOnly` later ([read-only](#check-again-later-read-only)); it checks again with the manifest, without deleting anything.
- **A deployment that failed halfway:** `destroy.ps1` handles a partial environment the same way; whatever wasn't created is skipped.

## Cost after destroy

With the resource group gone, nothing of the demo bills: no VMs or disks, public IPs, Bastion, T3, T4 or its read replica, T5's Azure Cosmos DB account with its container, private endpoint, and DNS zone, Ask's chat relay, or the nightly safety stop's Automation account ([ADR 0016](adr/0016-cost-profiles.md)); with the guest and its Arc resources gone, T2's pay-as-you-go SQL Server stops billing too ([manage licensing and billing](https://learn.microsoft.com/sql/sql-server/azure-arc/manage-license-billing)). The session control's Automation account and Key Vault go too, when it serves this environment, and so does the budget, which never billed. Only the golden group bills on, for its snapshot's used size, until `-IncludeGolden` deletes it. A custom role or a Fabric workspace that stays costs nothing; the capacity bills, which you manage. As in every estimate, the Fabric capacity, Fabric and Power BI licenses, and each viewer's GitHub Copilot plan aren't counted ([cost management](cost-management.md#at-a-glance)). Cost Management keeps showing charges up to the delete for a day or two, because usage arrives late. A soft-deleted opt-in Key Vault allows no operation but recover or purge, so it doesn't bill ([soft delete](https://learn.microsoft.com/azure/key-vault/general/soft-delete-overview)).

## The residual check

`Test-DemoTeardownResidue` reads Azure Resource Graph, Azure Resource Manager, the subscription's deployments, the budget, and Microsoft Entra, and changes nothing. Resource Graph and Microsoft Entra lag behind a delete, so it polls for up to `-ResidueWaitMinutes` while something still shows up. A check it can't read is a **Warning**, never a **Pass** ([ADR 0012](adr/0012-validation-model.md)). Every query is scoped to the configured subscription, and the checks never pass `--ids`, `--resource-id`, or a `{subscriptionId}` placeholder to the Azure CLI.

| Check | Clean when | Otherwise |
|---|---|---|
| `TEARDOWN.RESIDUAL.RESOURCEGROUP` | The resource group is gone | Fail |
| `TEARDOWN.RESIDUAL.TAGGED` | No resource or resource group in the subscription carries the environment's `deploymentId` tag, from the manifest, and the group `rg-<prefix>-<environment>` isn't listed by its exact name. `rg-<prefix>-control` isn't counted. The `solution` and `environment` tags alone never count ([only this environment](#only-this-environment)). | Fail when Azure Resource Manager still returns one; Warning for a row it didn't confirm ([Resource Graph lags](#resource-graph-lags-behind-deletes)), or without a manifest |
| `TEARDOWN.RESIDUAL.GROUPRESOURCES` | Resource Graph lists nothing in the group that Azure Resource Manager still returns | Fail; Warning for a row Resource Manager didn't confirm |
| `TEARDOWN.RESIDUAL.ARC` | No Arc machine, machine extension, license profile, Run Command, SQL Server instance, or Arc SQL database in the group, carrying the environment's `deploymentId`, or hosted by one of the group's machines or VMs | Fail; Warning for a row Resource Manager didn't confirm |
| `TEARDOWN.RESIDUAL.ROLEASSIGNMENTS` | No role assignment at or under the group, and none for the manifest's identities in the demo's other groups (`rg-<prefix>-control`, `rg-<prefix>-golden`) | Fail (removing one needs more than Contributor); Warning for one that something else, such as a tenant policy, gave a deleted identity elsewhere ([below](#role-assignments-a-tenant-policy-made)) |
| `TEARDOWN.RESIDUAL.IDENTITIES` | The manifest's identities are gone from Microsoft Entra ([getByIds](https://learn.microsoft.com/graph/api/directoryobject-getbyids), one request), and none is still a member of the P6 group ([checkMemberGroups](https://learn.microsoft.com/graph/api/directoryobject-checkmembergroups)) | Fail; Warning without a manifest, when the manifest didn't record the identities (it was taken after the group was gone), or when Microsoft Graph answers for another tenant |
| `TEARDOWN.RESIDUAL.DEPLOYMENTS` | No subscription deployment `<prefix>-<environment>-*` | Fail |
| `TEARDOWN.RESIDUAL.BUDGET` | The budget at the group's scope is gone | Fail |
| `TEARDOWN.RESIDUAL.REFERENCES` | No resource outside the group names it (a resource ID under it, or the group's own ID); `rg-<prefix>-golden` isn't counted, because a golden snapshot names its source group by design | Warning: such a resource may be shared, so it's reported, not deleted |
| `TEARDOWN.RESIDUAL.RECORDS` | Evidence only: what Defender for Cloud (assessments), Azure Policy (compliance states), guest configuration, and Resource Graph's own index (rows Resource Manager says are gone) still list for the deleted resources | Pass either way; Warning only when unreadable |
| `TEARDOWN.RESIDUAL.KEYVAULT` | With the Key Vault opt-in, the vault is neither active nor soft-deleted | Warning while it's soft-deleted ([ADR 0009](adr/0009-secrets-handling.md)); Not selected without the opt-in |

### Only this environment

Two environments can share a subscription and an environment name under different prefixes, such as `rg-dbhub-demo` and `rg-dbhubalt-demo`, with the same tags (`solution` `fabric-database-hub-demo`, `environment` `demo`) and resource names (`sqlvm01`, `archost01`, `arcsql01`). So the check matches the group only by its exact name, `rg-<prefix>-<environment>`; resources by the manifest's `deploymentId` tag, which the template derives from the subscription, the prefix, and the environment (`uniqueString`), on every template resource and the Arc machine; and Arc resources also by the group in their ID, or by the machine or VM that hosts them (`containerResourceId`). Never by those tags or a name alone. Without the manifest, `TAGGED` looks for the group by name only and is a **Warning**; `validate.ps1 -Area Teardown` matches the `deploymentId` only, too.

### Resource Graph lags behind deletes

Resource Graph's index can list a resource for a while after Azure Resource Manager deleted it: an Arc SQL Server instance's databases, for more than 30 minutes. So once the group is gone, each row it still lists for `TAGGED`, `GROUPRESOURCES`, and `ARC` is confirmed with a GET of its ID ([Resources - Get By Id](https://learn.microsoft.com/rest/api/resources/resources/get-by-id)), at most 25 reads in all (`Test-DemoTeardownResidue -MaxResourceReads`), with the API version `config/versions.json` pins, or the provider's newest stable one ([Providers - Get](https://learn.microsoft.com/rest/api/resources/providers/get), one read per provider, within the 25). HTTP 404 with `ResourceNotFound`, `ResourceGroupNotFound`, or `ParentResourceNotFound` ([not-found errors](https://learn.microsoft.com/azure/azure-resource-manager/troubleshooting/error-not-found)) is a stale index record: the check passes ("Only index records remain") and lists it under `TEARDOWN.RESIDUAL.RECORDS`. HTTP 200 is residue, a **Fail**. Anything else, or no read left, is unconfirmed, a **Warning**, never a Fail: run the check again later. While the group still exists, what Resource Graph lists counts as it is. The evidence has `indexRecords`, `unconfirmed`, `resourceManagerReads`, and `maxResourceReads`.

### Role assignments a tenant policy made

The demo gives the managed identities in its group role assignments only at or under the group (the nightly safety stop's stop-only role, [ADR 0024](adr/0024-nightly-safety-stop.md), and, only with `assignRoles`, Arc onboarding's Azure Connected Machine Onboarding, [ADR 0008](adr/0008-identity-rbac-abac.md)); its other assignments are for principals outside the group. So an assignment at or under the group, or for a manifest identity in `rg-<prefix>-control` or `rg-<prefix>-golden`, is the demo's own: a **Fail** while it's left. One for a manifest identity anywhere else was made by something else, such as a tenant policy with a `DeployIfNotExists` effect that grants new managed identities a role on a shared storage account: a **Warning** that names its scope (evidence `orphaned`: ID, scope, principal, role). Once the identity is deleted, it applies to no one, and the portal lists it as **Identity not found** ([troubleshooting](https://learn.microsoft.com/azure/role-based-access-control/troubleshooting#symptom---role-assignments-with-identity-not-found)). `destroy.ps1` never deletes it: it isn't the demo's, and Contributor lacks `Microsoft.Authorization/roleAssignments/delete`. An Owner, User Access Administrator, or Role Based Access Control Administrator of the scope removes it under **Access control (IAM)** > **Role assignments** ([Remove Azure role assignments](https://learn.microsoft.com/azure/role-based-access-control/role-assignments-remove)).

### Check again later, read-only

`destroy.ps1 -ResidueOnly` runs only the residual check, with the manifest an earlier destroy wrote. It deletes nothing, asks nothing, and leaves the manifest and `out/destroy.jsonl` as they were:

```powershell
./scripts/destroy.ps1 -ConfigPath ./out/demo.config.test.json -ResidueOnly -ManifestPath ./out/destroy-manifest-test.json
```

First `DESTROY.MANIFEST`: **Pass** with the manifest's time, `deploymentId`, and number of identities; **Fail**, and nothing is checked, when the file can't be read, or belongs to another resource group or another subscription (its `SubscriptionId`, compared without regard to case); **Warning** when there's no manifest at the path, and the check runs without it (the group by name only). Then the `TEARDOWN.RESIDUAL.*` checks and `DESTROY.RESIDUAL`, polling for up to `-ResidueWaitMinutes` (10 by default), into `out/destroy-residue-<environment>.jsonl` (or `-OutputPath`); the exit code is 1 only on a Fail.

**The default manifest path is shared** by every prefix and subscription with that environment name, so a destroy of another environment from the same clone, such as `rg-dbhubalt-demo`, or `rg-dbhub-demo` in another subscription, replaces it. A manifest of another resource group or subscription is never used: `-ResidueOnly` reports `DESTROY.MANIFEST` **Fail**, and a destroy replaces it, with a **Warning** in its log. To keep two environments' manifests, give each its own path, on the destroy and on the check, such as `-ManifestPath ./out/destroy-manifest-dbhubalt-demo.json`.

**Verified tokens, after canaries:** `az rest` and `az ad` can use the Azure CLI's default account, which can be in another tenant ([`az rest`](https://learn.microsoft.com/cli/azure/reference-index#az-rest)), so the check reads Resource Graph and Microsoft Graph with tokens verified for the configured tenant and caller, each after a canary: Resource Graph trims its answer to what the caller can read, so it must list the configured subscription, and Microsoft Graph must answer for the configured tenant ([get organization](https://learn.microsoft.com/graph/api/organization-get), [ADR 0011](adr/0011-control-surface-priority.md)). When a canary fails, the checks that depend on it are **Warnings** that say so, without waiting, and the manifest records `IdentitiesRecorded` `false`: sign in to the configured tenant and run `-ResidueOnly` again.

## The on-demand activity control

`destroy.ps1` deletes the session control (formerly the on-demand activity control) with the rest of the environment when its runbooks serve this environment ([above](#what-destroyps1-does)). To remove only the control and keep the environment:

```powershell
./scripts/setup-activity-control.ps1 -ConfigPath ./config/demo.config.json -Remove -WhatIf   # what it would delete
./scripts/setup-activity-control.ps1 -ConfigPath ./config/demo.config.json -Remove          # asks before each step
```

In order, it deletes (`CONTROL.REMOVE.*`):

1. **Fabric:** `NB_DatabaseHub_Control` from the existing workspace, its folder "DBHub Control" when it's empty, and the control's workspace with its managed private endpoint, through the documented Fabric REST Delete calls. `-SkipFabric` leaves Fabric alone (for example while the capacity is paused); then delete those items in Fabric yourself.
2. **The role assignments and the roles:** A1, A2, every Key Vault Secrets User assignment on the control's secrets, and the session writer's assignments; then the custom roles "DbHub Demo Activity Operator" and "DbHub Demo Session Writer", once no role assignment holds them. This needs an Owner, as granting did; without one, it reports **Manual action required** and goes on with the rest.
3. **The Azure resources, one by one:** the identity `id-<prefix>-automation`; the vault, which it then purges (purge protection is off for that reason, so the name is free at once); the Automation account last, with its runbooks, schedules, and webhook; and the template deployment records.
4. **The group** `rg-<prefix>-control`, only when nothing else is left in it: it may also hold the GitHub OIDC identity ([ADR 0002](adr/0002-resource-group-topology.md)), which `-Remove` never deletes.

`-Force` skips the questions. The control is part of every deployment ([ADR 0026](adr/0026-one-run-all-session.md)), so the next `./scripts/deploy.ps1` sets it up again; `"enabled": false` under `control` doesn't turn it off.
