# Cost management

The demo's own resources stay below a hard **$415 a month** for idle plus light use (the default for a new configuration since 2026-11-19; $375 from 2026-11-04, $250 before, and a configuration keeps its own value), and a demo-day session should stay below **$20** (`sessionCeilingUsd` was 15 before 2026-11-18). Every default is the cheapest option that works, except T4's size: since 2026-11-04 it's General Purpose `Standard_D4ds_v5`, for autonomous tuning, at the owner's direction ([below](#dated-example-the-4-vcore-t4-default-and-the-375-ceiling-2026-11-04)). No price in this repo is hard-coded: estimates come from the Azure Retail Prices API at run time, and every figure in the docs is a dated example ([ADR 0016](adr/0016-cost-profiles.md)). The current figures are the [default deployment's dated example](#dated-example-the-default-deployment-2026-11-05), with [T4's read replica](#dated-example-t4s-read-replica-2026-11-13) added for each session since 2026-11-13, [T3 at 2 vCores](#dated-example-t3-at-2-vcores-and-the-20-session-ceiling-2026-11-18) since 2026-11-18, and [T5](#t5-azure-cosmos-db-2026-11-18), whose container exists only during a session since 2026-11-19; [what stops or pauses on its own](#what-stops-or-pauses-on-its-own) lists every schedule, with its time.

## At a glance

- **Ceilings:** a hard **$415 a month** for idle plus light use (preflight fails above it; the default for a new configuration since 2026-11-19, which was 375 before; a configuration keeps its own value) and **$20 per demo-day session** (a Warning; $15 before 2026-11-18, and a configuration that still says 15 gets 20). The deployment adds a budget at `monthlyCeilingUsd`, with alerts at 50%, 80%, and 100%. Every default is the cheapest working option except T4's size: since 2026-11-04 it's General Purpose `Standard_D4ds_v5` (4 vCores), with autonomous tuning, at the owner's direction ([ADR 0016](adr/0016-cost-profiles.md), [ADR 0019](adr/0019-t4-postgresql-flexible-server.md)).
- **T3 at 2 vCores (2026-11-18, the owner's decision):** Database Agents doesn't support one-vCore serverless databases, so `lowest-cost`'s T3 goes from 0.5–1 to 0.5–2 vCores, and the next `./scripts/deploy.ps1` scales an existing T3 online. Serverless bills the vCore-seconds it uses, and the estimate prices T3 at its maximum for every running hour, so T3 adds $1.04 a running hour instead of $0.52. Dated example (list prices in USD for West US 3, 2026-11-18; the example configuration as below, with T4's read replica): `lowest-cost` is $15.03 a session (was $12.42) and $64.75 a light-use month (was $59.53), within the session ceiling, now $20, and $375 ([the dated example](#dated-example-t3-at-2-vcores-and-the-20-session-ceiling-2026-11-18)).
- **T2's migration assessment (2026-11-18) adds no cost:** Microsoft documents it as free for every edition of SQL Server enabled by Azure Arc ([migration assessment](https://learn.microsoft.com/sql/sql-server/azure-arc/migration-assessment)). The Azure extension for SQL Server, already on T2, runs it inside the guest once a week and uploads the result to the SQL Server instance's existing Azure resource, so it adds no resource and no meter, and every estimate stays as it was. The Database Agent loop on T3 adds nothing to the Azure estimates beyond T3's second vCore above; its Copilot analysis uses the Fabric capacity's Copilot, outside the ceiling.
- **Why $375 (since 2026-11-04; $250 before):** the worst case after T4 restarts itself. Azure starts a stopped flexible server again after 7 days, and the 4-vCore T4 then bills about $0.356 an hour (a dated example: West US 3, list prices, 2026-11-05, the same as on 2026-11-03). When a safety stop is fully in place, each restart counts as about a day, about $34 a month; otherwise the rest of the month, up to about $256 ([cost management](#dated-example-the-4-vcore-t4-default-and-the-375-ceiling-2026-11-04)). Since 2026-11-05 every deployment sets up that safety stop, the [nightly safety stop](#what-stops-or-pauses-on-its-own); it's fully in place when its schedule is enabled, its role is assigned on `rg-<prefix>-<env>` (P16), and its last run didn't fail. The on-demand control's daily T4 safety stop, when it's fully in place, counts too. An existing environment gets the new budget at its next `./scripts/deploy.ps1 -FromStage Infrastructure`; a configuration that sets `monthlyCeilingUsd` keeps its value.
- **Why $415 for a new configuration (2026-11-19, the owner's decision):** a first deployment's preflight runs before the nightly safety stop exists. Since 2026-11-19 it counts the safety stop the run sets up when you can assign its role (an Owner), so an Owner's first deployment of the example configuration comes to $149.34 in the worst case ($149.02 on the free tier), and so does the owner's own update. A Contributor's still counts T4's restart for the rest of the month, and T5's container all month, because nothing automatic deletes it until an Owner's grant (only `stop-demo.ps1` does): $398.23 at list price, and $374.62 on the free tier, where only Defender for Azure Cosmos DB bills for it. That's $16.77 under $415 ($40.38 on the free tier); it would have been over $375. The owner chose $415 from $398.42, with the Bastion hour the estimate counted until the same day ([ADR 0016](adr/0016-cost-profiles.md#2026-11-19-a-first-deployments-worst-case-and-a-415-default-for-a-new-configuration); dated examples: list prices in USD for West US 3, 2026-11-19, the subscription's Defender plans, private mode, 10 running hours, with Ask's chat relay). `init.ps1` writes 415; a value already in a configuration never changes. A Contributor's environment that keeps 375 or 390 goes over it only because of T5's container, so `PREFLIGHT.COST.MONTHLY` is a **Warning** there, not a **Fail**, and the update and `start-demo.ps1` go on ([T5](#t5-azure-cosmos-db-2026-11-18)).
- **What the monthly check says (2026-11-19):** preflight, `start-demo.ps1`, and `estimate-cost.ps1` give the month's worst case, the total they compare with `monthlyCeilingUsd` (the light-use month plus T4's automatic restart), the ceiling, the margin under or over it, and what it counted: T4's restart hours and T5's container, for the running hours (`Session`) or all month (`AlwaysOn`). `estimate-cost.ps1` prints it as a table too, "The monthly check". It counts no Bastion hour unless you pass `-BastionHours`: a default deployment and session have no Bastion, and `start-demo.ps1 -Interactive` counts the Bastion it deploys. Signed in, `estimate-cost.ps1` prices an environment that doesn't exist yet as `deploy.ps1`'s preflight will price its first run for you, from the same read-only reads of your permissions, and says what it assumed: T4's restart about a day each when you can assign the nightly safety stop's role, the rest of the month otherwise, and T5's container for the running hours only when the session control will hold its role. Dated examples (list prices in USD for West US 3, 2026-11-19; the example configuration, `lowest-cost`, private mode): not signed in, so without Defender for Cloud, $15.53 a session and $73.76 a light-use month ($15.73 and $73.95 with the Bastion hour), with a worst case of $330.08; signed in to an internal subscription with its Defender plans, as an Owner with no environment yet, $16.27 a session (of which Defender $0.73), $115.16 a light-use month (of which Defender $41.40), and a worst case of $149.34, the one preflight then checks ([ADR 0016](adr/0016-cost-profiles.md#2026-11-19-the-monthly-check-says-its-total-and-no-bastion-hour-by-default)).
- **To stay cheap:** stop the demo between sessions (`./scripts/stop-demo.ps1`). `t4SkuName` can set a smaller T4, such as `Standard_B1ms` (autonomous tuning then turns off); when Azure refuses it, the fallback moves on to the next size it accepts, cheapest first, and says what that costs (2026-11-09). To clear a monthly-ceiling **Fail**, raise `monthlyCeilingUsd` to the amount it names. T4 is part of every deployment since 2026-11-09, so `t4Enabled: false` no longer leaves it out.
- **Dated example, the default deployment** (2026-11-05; list prices in USD for West US 3 from the Azure Retail Prices API, which `./scripts/estimate-cost.ps1` reads without sign-in; the example configuration: `lowest-cost`, T2 in `JumpstartImage` mode, T4 on `Standard_D4ds_v5`, private mode assumed, Defender for Cloud not read, T3 as regular serverless, no golden snapshot; the Fabric capacity left out): $2.08 an hour while it runs; $10.61 for a 5-hour session, or $10.42 without the one hour of optional Bastion that the estimate counts per session (a default deployment needs no Bastion); $55.89 for a light-use month of 10 running hours. With T4's 7-day restart worst case, the month is $90.07 with the nightly safety stop in place (96 hours, $34.18) and $312.21 without it (the rest of the month, 720 hours, $256.32). `demo-day` comes to $117.55 and $339.69, and `enhanced-performance` to $172.39 and $394.53: over $375 without the safety stop, so it fails a first deployment's preflight, which runs before the safety stop exists ([cost management](#dated-example-the-default-deployment-2026-11-05)).
- **The default `business-day` profile adds nothing to the estimate (2026-11-03):** its two T3 incidents an hour (`resource-governance` at :15 and `log-rate-pressure` at :45, 5 minutes each) drive the serverless database to its maximum vCores, and the estimate already prices T3 at its maximum for every hour a profile keeps it awake (`t3ActiveShareOfMaxVcores` 1.0 in `config/profiles.json`), so the session and month estimates and both ceilings stay as they were. The incidents use the free offer's monthly vCore-second allowance faster, which the estimate counts at the same maximum. The VMs and a provisioned T4 cost the same whatever the load. What no estimate counts, T3 between its minimum and maximum vCores and the extra disk operations, came to at most $0.51 a session and $1.01 a light-use month in a dated estimate (2026-11-03, West US 3, list prices from the Azure Retail Prices API), $0.94 and $1.88 with the 2-vCore T3 of 2026-11-18 at the same prices, well within both ceilings ([cost management](#activity-profiles-business-day-phase-28-follow-up)).
- **Measured (2026-10-21 and 2026-10-22):** Phase 16's two-day test cycle, from a fresh build through stop and destroy in a disposable environment, came to about $4.50: its measured hours at the Retail Prices API's list prices, not a billed amount.
- **The T2 golden snapshot** is optional: it only speeds up a redeploy. It bills every month it exists, also after destroy, until `destroy.ps1 -IncludeGolden` deletes it. Dated example (2026-10-22, $0.05 per GB-month for Standard HDD snapshots, the same list price on 2026-11-05): at most about $6.40 a month in the estimate, which prices the 128 GiB provisioned size, and about $1.85 billed for the 37 GiB a `PaygWizard` host used. A `JumpstartImage` host's disk also holds the 34 GiB image, so its snapshot would bill more: an estimated 50 to 60 GiB used, about $2.50 to $3 a month (not measured). The estimate and the cost guardrails include it ([cost management](#the-t2-golden-snapshot-phase-20)).
- **T2 in `JumpstartImage` mode (the default since 2026-11-05) adds no Azure resource and no new cost:** the guest's disk is a file on the T2 host's existing OS disk, there's no storage account, and SQL Server is billed as before, Arc pay-as-you-go Standard per core-hour. The image's 34 GiB download into Azure is free ("Standard Data Transfer In" is $0.00 per GB), and writing it costs about $0.03 of disk operations on the host's Standard SSD. A first deployment no longer needs Bastion: Bastion Basic with its public IP is about $0.20 an hour, which a `PaygWizard` guest build used for about an hour at the guided stop. `estimate-cost.ps1` counted one Bastion hour per session (`bastionHoursPerSession`) for optional interactive access, such as T2's missing-index fix, until 2026-11-19; since then it counts none unless you pass `-BastionHours`, and `start-demo.ps1 -Interactive` counts the Bastion it deploys ([cost management](#t2s-jumpstartimage-mode-2026-11-05)).
- **Outside the ceiling:** the Fabric capacity bills while it runs (an F16 is about $2.88 an hour at list price, 2026-10-21). The notebooks, the Real-Time Dashboard, the report, and the Fabric App need it running; the app has no database or storage, and its functions run only when they're called: the read-only live estate for Ask and the pages (since 2026-11-18), and Manage's, when an operator opens Manage or sends an action (ADR 0029). So it uses capacity units only when a deployment deploys and checks it (every `deploy.ps1` does, since 2026-11-05) and while someone loads it and its queries and functions run. No estimate includes the capacity, which you manage. Database Hub doesn't need it. Its administrator pauses it when no workspace needs it. Viewer licenses (P11) are outside the ceiling as well.
- **No price is hard-coded:** `./scripts/estimate-cost.ps1` uses the Azure Retail Prices API at run time (cost management).
- **T4** bills compute only while it runs. While it exists, stopped or not, its storage, private DNS zone, and the two Defender plans that a tenant policy enforces (open-source relational databases and CSPM) come to about $24.30 a month (dated example, 2026-10-23 and 2026-10-26, list prices). A stopped T4 starts on its own after seven days, so the estimate counts its compute after a restart against the ceiling, and `stop-demo.ps1` and `status.ps1` say the date it starts again and whether the nightly safety stop stops it at the next auto-shutdown time. The estimate reads whether a safety stop is in place (since 2026-11-04): when the nightly safety stop's schedule is enabled, its role is assigned, and its last run didn't fail, or the on-demand control's daily T4 safety stop is fully in place, each restart counts as about a day (at most 4 a month, 96 hours); otherwise the rest of the month, with a **Warning** that names the missing piece and its fix (`./scripts/deploy.ps1`, or an Owner's `./scripts/grant-safety-stop.ps1`). A read that fails counts as missing. A first deployment's preflight runs before the safety stop exists: since 2026-11-19 it counts the one that run sets up when you can assign its role (an Owner), and the rest of the month otherwise, as before, and `estimate-cost.ps1`, signed in, prices an environment that doesn't exist yet the same way; when that setup then doesn't put it in place, the run says so, with the worst case without it (`DEPLOY.COST.T4RESTART`, [ADR 0016](adr/0016-cost-profiles.md#2026-11-19-a-first-deployments-worst-case-and-a-415-default-for-a-new-configuration); [cost management](#azure-database-for-postgresql-t4-phase-24)).
- **T4's read replica (2026-11-13)** exists only during a session: `start-demo.ps1` or Run all creates it, and `stop-demo.ps1` or the session's auto-stop deletes it, so it bills nothing between sessions and no 7-day restart applies to it. `deploy.ps1` creates it for its checks and deletes it at its end (since 2026-11-16), under $0.50 a run at these prices, so a deployment or an upgrade leaves nothing new billing. The estimate counts it in the running hours: its compute at T4's size, its storage by the hour, and its Defender plans where they're on. Dated example (list prices, West US 3, 2026-11-13, `Standard_D4ds_v5`): $0.361 an hour without Defender, $0.389 with this tenant's plans, so a 5-hour session gains $1.80 to $1.94 and a light-use month of 10 hours $3.61 to $3.89. The default first deployment's month with T4's restart and no safety stop goes from $312.21 to $315.82, within $375 either way, and the ceilings are unchanged. `demo-day`'s session goes from $14.75 to $16.56, over the $15 session ceiling of the time: a **Warning** that names the replica's share, never a **Fail** (within the $20 ceiling since 2026-11-18). `./scripts/start-demo.ps1 -SkipT4Replica` starts a session without it. T4's size decisions (its fallback and its move to the default) leave the replica's share out, so they're the same as before ([cost management](#dated-example-t4s-read-replica-2026-11-13), [ADR 0025](adr/0025-t4-read-replica.md)).
- **T4's fallback (2026-11-04; Phase 28 follow-up before):** when `t4SkuName` isn't set and Azure refuses `Standard_D4ds_v5` with `SkuNotAvailable`, `deploy.ps1` tries another zone, then `Standard_D4ads_v5` (4 vCores, tuning stays on), and creates T4 as `Standard_D2ds_v5`, with autonomous tuning off, after pricing it from the Azure Retail Prices API right then: the demo's month with T4's restart worst case (about a day per restart with the safety stop in place, the rest of the month otherwise), its storage, and its Defender plans against `monthlyCeilingUsd`, and a session against `sessionCeilingUsd`. Over a ceiling it's a **Warning** that names the ceiling to raise, and T4 is created anyway (2026-11-09). Since 2026-11-09 (user-directed), a size `t4SkuName` sets that Azure refuses falls back too: once more in another zone, then the next size Azure accepts, cheapest first. Every automatic size change says what was tried and refused, with the zones, what was created, and T4's monthly estimate at both, light use and worst case, with the difference (`DEPLOY.T4.FALLBACK`): on the console, the status page, **DONE**, and `status.ps1` afterwards. Until the server exists, **DONE** and **NOT DONE** say it was chosen but isn't created yet ([the cost check](#the-general-purpose-fallbacks-cost-check-phase-28-follow-up), [ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-11-09-user-directed-a-size-t4skuname-sets-falls-back-too-and-every-automatic-size-change-says-what-it-cost)).
- **The session control** (every deployment since 2026-11-14) adds its vault's operations and its Automation job minutes, of which the first 500 a month are included; the estimate prices them ([cost management](#the-on-demand-activity-control)). Its identity, Automation account, and vault cost nothing while no session runs, and the Fabric workspace it may add runs on your existing capacity.
- **T5, the Azure Cosmos DB account (2026-11-18),** has no stop, so its private endpoint and private DNS zone bill all month: $7.80 at list price. Since 2026-11-19 its container, the only part with throughput, exists only during a session: `start-demo.ps1` and Run all create it, and `stop-demo.ps1`, the session's end, and the nightly safety stop delete it. So its 400 RU/s bill only while the demo runs, $0.032 an hour at list price, and nothing on the subscription's free tier, which `deploy.ps1` takes when it's free. Dated example (list prices, West US 3, 2026-11-19; a light-use month of 10 running hours): **T5 comes to $8.12 a month at list price, $31.41 before; $7.80 on the free tier, as before**, plus about $0.05 (was $3.50) when a tenant policy turns Defender for Azure Cosmos DB on. When the session control holds a role that can't create the container yet (an update by someone who isn't an Owner, until `./scripts/deploy.ps1` runs as an Owner, or an Owner runs `./scripts/grant-safety-stop.ps1` once), it stays between sessions and bills all month, as before. A Contributor's new deployment, whose session control has no role, keeps the container for each session: `start-demo.ps1` creates it with your own rights, and Run all can start a session once an Owner runs the grant. Until then only `stop-demo.ps1` deletes it, unless the nightly safety stop's role has the container's actions, so the estimate counts it all month and the status page says to run `stop-demo.ps1` after each session (since the review of ab91ee5). The estimate counts the container in the running hours, with the free tier when it read it, and says which, and what the other lifecycle adds ([T5](#t5-azure-cosmos-db-2026-11-18)). The default first deployment's month with T4's restart and no safety stop is $329.19 at list price ($352.48 with the container all month), within $375.
- **The nightly safety stop** runs two short Automation jobs a night in `aa-<prefix>-<env>-safetystop`. The estimate counts up to 120 job minutes a month at the meter's price from the Retail Prices API: $0 within the 500 job minutes a month that Azure Automation includes (2026-11-05; rate plans with a flat discount or a fixed monthly credit don't include them). Its identity, Automation account, and role cost nothing ([ADR 0024](adr/0024-nightly-safety-stop.md)).
- **Ask's chat relay (2026-11-18)** bills only while someone uses the Copilot chat in the Insights app: an Azure Container App on the Consumption plan (1 vCPU, 2 GiB) that scales to zero about 10 minutes after the last question, with no fixed charge, no registry, and no log workspace. The estimate counts it for every running hour, an upper bound: $0.108 an hour at the 2026-11-19 list prices, so the default deployment's 5-hour session goes from $15.03 to $15.57 and its light-use month from $64.75 to $65.83, and no ceiling's result changes ([dated example](#dated-example-asks-chat-relay-2026-11-18)). `ask.enabled: false` leaves it out ([ADR 0028](adr/0028-ask-copilot-in-the-insights-app.md)).

## What stops or pauses on its own

Everything below runs with no person and no command. Times are the defaults: `autoShutdownTime` 19:00 in `autoShutdownTimeZone`, Pacific Standard Time.

| What | When | What it does | Set up by |
|---|---|---|---|
| The VMs' auto-shutdown (DevTest Labs schedules `shutdown-computevm-<vm>`) | Daily at `autoShutdownTime`: 19:00 | Shuts down and deallocates `sqlvm01` (T1) and `archost01` (T2's host); the T2 guest stops with its host | The template (`deploy.ps1`); `validate.ps1` checks it (`COST.AUTOSHUTDOWN`) |
| The nightly safety stop (schedule `dbhub-safety-stop`, `DbHub-Stop -Scope Nightly`) | Daily at the same time: 19:00 | Backs up the auto-shutdown: deallocates each VM that isn't deallocated or deallocating, a VM someone kept running or stopped only from inside included, and stops T4 when it's running, after Azure's 7-day restart too; it waits up to 10 minutes for a T4 that's starting. A read replica that a session left behind (no `stop-demo.ps1`) is stopped once T4 is stopped, the order Azure requires, and the job says so with the fix: `stop-demo.ps1` deletes it. Since 2026-11-19 it also deletes T5's container when a session's stop didn't and its lifecycle is Session, so its throughput doesn't bill overnight. It never starts anything, deletes nothing else, never connects to a database, and never uses Run Command | `deploy.ps1`, on every run ([ADR 0024](adr/0024-nightly-safety-stop.md)); it acts once its role is assigned (P16) |
| Its T3 check (schedule `dbhub-safety-t3check`, `-Scope T3Check`) | Daily 30 minutes later, 19:30; or T3's auto-pause delay plus 15 minutes when that's longer, for example 20:15 with a 60-minute delay | Reads T3's status through Azure Resource Manager only, which doesn't wake it, and reports in `status.ps1` when it isn't paused. Azure has no "pause now" for serverless, so it can't pause T3. Then it stops T4 when it runs, as the stop does, and a left-over read replica after it, so a T4 that Azure's 7-day restart started just after the stop doesn't run until the next evening | The same |
| A run's deferred stop (schedule `dbhub-safety-deferred`, `-Scope Nightly`), only on a night the stop waited for a `deploy.ps1` | Hourly from 65 minutes after the run ended until the next morning | Stops the demo as the nightly stop does, once no run keeps it busy; the VMs' auto-shutdown is set to its first time for that night | `deploy.ps1` (since 2026-11-14) |
| T3's auto-pause | `t3AutoPauseMinutes` after its last session: 15 minutes by default | Azure pauses the serverless database, which then bills only its storage; the first connection resumes it | The template |
| The activity profiles and incidents | Each profile ends 2 minutes before the next auto-shutdown; each incident at its hard maximum | The workload stops, so T3 can pause | `deploy.ps1`, `start-demo.ps1`, `demo-control.ps1` |
| A notebook run's auto-stop (schedule `dbhub-autostop`; the session control) | The run's end plus 10 minutes; for a Run all session, a second one (`dbhub-autostop-backup`) 30 minutes later, which runs only when the first one's job failed | Saves a session's metrics, deallocates the VMs, deletes T4's read replica and, when its lifecycle is Session, T5's container (since 2026-11-19), and stops T4, as **Stop now** does | The control's runbook, for each run |
| The control's daily T4 safety stop (schedule `dbhub-t4-safety-stop`) | Daily 15 minutes after `autoShutdownTime`, 19:15, or at `control.t4SafetyStopTime` | Stops T4 when it's running, then a left-over read replica; while `sqlvm01` doesn't run, it also deletes T5's container when its lifecycle is Session, a fallback for a night the nightly safety stop couldn't (since 2026-11-19) | `deploy.ps1`, with the session control, on every run |
| On-demand Bastion | Removed by every `stop-demo.ps1`, and by `deploy.ps1` when an earlier guided stop left it; otherwise `bastionMaxHours` (4) after it was created, but only with the `bastion-cleanup` workflow below | Deletes Bastion and its public IP, and rotates the T2 host's password | `deploy.ps1`, `stop-demo.ps1` |
| Optional GitHub schedules, off unless the repository variable `DBHUB_SCHEDULES_ENABLED` is `true` (cron in UTC; edit it for your time zone) | `schedule-stop` daily at 01:00 UTC; `bastion-cleanup` hourly at :10; `expiry` daily at 06:30 UTC | `schedule-stop` runs `stop-demo.ps1` (Bastion, the profiles, the guest, both VMs, and T4); `bastion-cleanup` removes an expired Bastion; `expiry` runs `destroy.ps1` once the resource group's `expiresOn` has passed | The workflows in `.github/workflows` |

- **Nothing in this list starts anything.** Only Azure starts a stopped T4 again after 7 days, and the nightly safety stop stops it again within a day: its T3 check that evening when it starts between the stop and the check, otherwise the next evening's stop; the optional `schedule-start` workflow starts a session (weekdays at 15:15 UTC, when enabled).
- **A `deploy.ps1` that's still running isn't cut off** (since 2026-11-14): while it runs, it marks the demo resource group busy (`DbHubBusyUntilUtc`, at most 3 hours ahead, moved on every 10 minutes), so the stop, its T3 check, and the control's T4 stop change nothing, and the VMs' auto-shutdown moves past the run. When the run ends after the stop's time, the demo stops 60 minutes later, and DONE and the status page say when; `./scripts/start-demo.ps1` keeps it running that night instead, and `./scripts/stop-demo.ps1` stops it at once. A run that was abandoned stops being marked within an hour, and the demo is stopped that night ([ADR 0024](adr/0024-nightly-safety-stop.md#amendment-the-busy-marker-so-the-nightly-stop-doesnt-cut-off-a-run-2026-11-14)). A `start-demo.ps1` session isn't marked: one still going at the stop's time is stopped, as before.
- **To skip one night:** turn off the `dbhub-safety-stop` and `dbhub-safety-t3check` schedules in `aa-<prefix>-<env>-safetystop` (Shared Resources > Schedules), since the T3 check stops T4 too, `dbhub-safety-deferred` when a run left one, and the VM's auto-shutdown in the Azure portal. The next `./scripts/deploy.ps1` turns the safety stop on again.
- **Where to see it:** `./scripts/status.ps1` (`STATUS.SAFETYSTOP`: its times, its role, what its last run stopped, and what its last T3 check found; `STATUS.NIGHTLYSTOP`: a run it waits for, the deferred stop, and a moved auto-shutdown), and the job history in `aa-<prefix>-<env>-safetystop` > Process Automation > Jobs.
- The Fabric capacity isn't in this list: its administrator pauses it.

So the practical minimum is `Standard_D4ds_v5`: $0.356 an hour against $0.178 for `Standard_D2ds_v5`, **+$31.33 a month**. `Standard_B4ms` is $0.272 an hour, but it's Burstable, so it isn't recommended.
- **SQL Server Enterprise (T1 and T2):** automatic tuning, which includes plan correction, is Enterprise-only in SQL Server 2022 ([editions](https://learn.microsoft.com/sql/sql-server/editions-and-components-of-sql-server-2022), updated 2026-10-19).
  - T1: the "SQL Server Enterprise / 1-4 vCPU VM License" meter is $1.50 an hour, against $0.40 for Standard.
  - T2: Arc's "Ent edition - PAYG" is $0.375 a core-hour, against $0.100, times the 4-core minimum: $1.50 an hour against $0.40.
  - Together, **+$387.20 a month**. It would also need T1's Enterprise Marketplace image and Enterprise in T2's guest setup; the demo installs Standard on both.
- **Both upgrades:** about **$855.51 a month**.

**Above the hard ceiling, even without the upgrades.** The **$250** monthly ceiling assumes idle plus light use, 10 running hours a month (`config/profiles.json`). A business-hours schedule needs `monthlyCeilingUsd` raised to about **$450**, or about **$875** with both upgrades, and the budget with it (`deploy.ps1 -FromStage Infrastructure`). Otherwise:

- the monthly check fails when it counts those hours (`estimate-cost.ps1 -LightUseHoursPerMonth 176` reports `PREFLIGHT.COST.MONTHLY` as a **Fail**); preflight's own run counts the 10-hour light-use month;
- the budget's alerts fire at 50%, 80%, and 100% of the ceiling;
- once the month's actual cost reaches the ceiling, `start-demo.ps1` stops starting the demo (`START.COST.ACTUAL` **Fail**) until the next month, unless you raise the ceiling or pass `-SkipCostCheck`.

**Neither upgrade adds a Database Hub visual:** PostgreSQL's tuning recommendations show in the Azure portal, and SQL Server's plan correction in its DMVs (`sys.dm_db_tuning_recommendations`) and SSMS.

## The T2 golden snapshot (Phase 20)

## Azure SQL (T3): free offer and lifecycle

- **Free offer:** by default (`t3FreeOffer: auto`), T3 uses the [Azure SQL Database free offer](https://learn.microsoft.com/azure/azure-sql/database/free-offer) with "continue using database for additional charges", so it never pauses for the limit. ## Activity profiles: business-day (Phase 28 follow-up)

`business-day` is the default activity profile since 2026-11-03 ([ADR 0010](adr/0010-workload-generator-technology.md#activity-profiles-business-day-by-default-2026-11-03)). What that changes in the estimate:

- **T3 is the resource whose bill follows the load.** Its two incidents an hour, `resource-governance` at :15 and `log-rate-pressure` at :45, 5 minutes each, drive the serverless database to its maximum vCores. Serverless bills each second for the larger of the CPU and the memory used, never above the maximum vCores ([serverless compute tier](https://learn.microsoft.com/azure/azure-sql/database/serverless-tier-overview)). The VMs, their SQL Server licenses, Arc's per-core billing, Defender for Cloud, and a provisioned T4 bill by the running hour, whatever the load. Two small amounts follow the load too and are in no estimate, for any profile: Standard SSD disk operations and T3's backup storage (below).
- **How the estimate counts it:** T3's running hour is priced at its maximum vCores times `t3ActiveShareOfMaxVcores` (`config/profiles.json`). With `business-day`, the estimate adds the incidents' minutes, 10 of every 60 from `scenarios/activity-profiles.json`, at the maximum for the part of the hour that share leaves out: maximum × (1 - share) × 10/60 vCore-hours per running hour, at the serverless vCore meter that the Retail Prices API gives at run time. The shipped share is 1.0, so the estimate already prices T3 at its maximum for every running hour: the increment is 0, and the session and month estimates and both ceiling checks are unchanged. `PREFLIGHT.COST.SESSION` and `PREFLIGHT.COST.MONTHLY` say so ("they add nothing"), with `activityProfile`, its source, and the increment in their evidence. With a lower share, a component "T3 compute, business-day incidents" adds the increment to both checks.
- **The free offer's allowance:** the incidents use the 100,000 vCore-seconds a month faster ([free offer](https://learn.microsoft.com/azure/azure-sql/database/free-offer)); the estimate already counts T3 at its maximum against it. A light-use month, 10 running hours at the `lowest-cost` maximum of 2 vCores (1 before 2026-11-18), uses 72,000 vCore-seconds.
- **Where it's checked:** preflight (`PREFLIGHT.COST.*`, which `deploy.ps1` runs), `start-demo.ps1`'s guardrail (`START.COST.*`, unless `-SkipCostCheck`) with its `-ActivityProfile`, and `estimate-cost.ps1`, each with the configured profile, or `business-day` for a configuration without `activityProfile`, which the run says once (`*.ACTIVITYPROFILE`) without changing the configuration.

## Disks switched to Standard HDD by the subscription's automation

The estimate prices each profile's disk tiers (E10 Standard SSD OS disks for `lowest-cost`). On 2026-10-24 an application identity that isn't the demo's switched both demo VMs' OS disks to Standard HDD while the VMs were deallocated.
