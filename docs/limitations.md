# Known limitations

What the demo can't do, what depends on a preview, and what isn't proven yet. Each item links to the decision or risk behind it, and fixes are in [troubleshooting](troubleshooting.md) by check ID; the acceptance status of every criterion is in the [final report](implementation-report.md#final-report).

## Preview disclosures

- **Generally available since 2026-11-17:** Database Hub itself (Overview, Estate, Performance, security posture, investigation, and Optimization insights), its real-time dashboards for Microsoft SQL, Azure Database for PostgreSQL, and Azure Cosmos DB, bulk monitoring enablement, the SSMS and VS Code entry points, and the Database Hub CLI skill in skills-for-fabric ([overview](https://learn.microsoft.com/fabric/database/hub/overview), [announcement](https://techcommunity.microsoft.com/blog/azuresqlblog/database-hub-in-microsoft-fabric-is-generally-available-your-entire-database-est/4574212)). It needs only a Fabric Free license.
- **Still in preview:** Copilot in Database Hub, Database Agents, alerts, and SQL Server on Azure VM performance monitoring; and, as Learn still labels them (checked 2026-11-18), unified inventory, the Arc SQL monitoring setting (API version `2023-09-01-preview`), the SQL telemetry endpoint, and Fabric Apps. Their behavior, prerequisites, labels, schemas, and APIs can change without notice. Database Hub's own tenant setting is still named **Users can access the Database hub (preview)** on Learn ([monitor SQL](https://learn.microsoft.com/fabric/database/hub/monitor-sql)).
- **Capacity:** Database Hub's own views need no Fabric capacity. Copilot, custom alerts, and shared dashboards do, and so do the demo's own items: the notebooks, the Real-Time Dashboard, the report, and the Insights app. The capacity, Fabric and Power BI licenses, and their cost are yours to manage, outside the demo's estimates, and so is each viewer's GitHub Copilot plan, which Ask uses ([cost management](cost-management.md#at-a-glance)).
- **What the repo does about it:** it uses only documented interfaces, never calls Database Hub's private routes except in one narrow, read-only exception (the Insights app's live-estate function, for Ask and the app's pages, [ADR 0013's amendment](adr/0013-agent-experience.md#amendment-2026-11-18-the-ga-skill-and-one-narrow-exception)), validates prerequisites and signals instead of promising outcomes, and gives every preview-dependent step a fallback ([ADR 0013](adr/0013-agent-experience.md), [fallbacks](troubleshooting.md#fallbacks-at-a-glance)).
- **No Hub API:** saved views, the **Enable Performance Monitoring** button, monitor templates, Copilot, and Database Agents' settings (**Manage agents**) are UI-only. The demo validates through Azure Resource Graph and the documented telemetry endpoint, and the Hub UI check stays **Manual action required**. Selecting T3 for Database Agents is required once for the Database Agent beat, and everything else works without it: `deploy.ps1` lists it under **Please confirm** with the link and the database to select (`HUB.AGENT.T3`), and [Database Agents for T3](database-agents.md) has every step. The selection is saved for the tenant, every database starts selected ("All databases are included by default"), and its list shows no server, so every environment's T3 is a row named `ContosoCare`. So the steps clear the selection only where nobody else in your tenant uses Database Agents: unchecking a database stops the agent watching it for whoever selected it, and a **Save** checks your write access on every selected database, so where others use it, a database of theirs you can't write to needs whoever manages Database Agents in your tenant. Deleted databases can stay in the list, selected, for a while (observed 2026-11-20), and while one is, every **Save** fails: `destroy.ps1` says to uncheck only T3 (`DESTROY.HUB.AGENT.T3`), and [troubleshooting](troubleshooting.md#database-agent-settings) has the fix for each case.
- **Database Agents and Copilot coverage:** Database Agents (preview) covers Azure SQL Database in Database Hub, so T3 only here: not SQL Server on Azure VMs or enabled by Azure Arc (T1, T2), not one-vCore serverless databases (why the lowest-cost T3 scales up to 2 vCores), and PostgreSQL (T4) only as a limited preview in Visual Studio Code. It raises an issue about 15 minutes after a condition starts and applies no change: every scenario needs a person's response, which the showcase's Database Agent beat makes itself ([Database Agents](https://learn.microsoft.com/fabric/database/hub/database-agents), [walkthrough](demo-walkthrough.md#the-database-agent-loop-on-t3)). It also needs T3 in the region associated with the Fabric tenant's home region, which no API reads. Copilot's target coverage and latency aren't documented, so every incident runs on T1, T2, and T3, and the walkthrough has fallbacks ([ADR 0013](adr/0013-agent-experience.md)).
- **Never promised:** the demo describes the signals to look for, never the AI's answers, and nothing an agent proposes runs without a person's decision.

## Database Hub's visuals in one session (the showcase)

**Run all** starts the showcase, which fills what can fill within one session. [Database Hub's visuals](database-hub-visuals.md#what-fills-each-database-hub-visual-and-when) says, visual by visual and target by target, what fills each one, when, and why some stay empty:

- **Some need history:** **CPU spikes** compares with a 48-hour baseline, so run the [baseline](database-hub-visuals.md#the-baseline-run-why-it-matters-and-when-it-doesnt) the day before; Azure SQL Database's index recommendations need "at least a day" of monitoring, and PostgreSQL's Azure Advisor up to seven days on one configuration.
- **Some can't fill here:** T1 and T2 have no automatic tuning (SQL Server 2022 Standard) and no license-model opportunity (they already use pay-as-you-go); Activator alerts don't support PostgreSQL; and utilization suggestions look for quiet targets. **Read replica lag** fills only while T4's read replica exists: not between sessions, not in a Run all session before an Owner's grant gives the session control its PostgreSQL actions, and not on a Burstable T4. T2's migration assessment is ready once its first upload is done (`T2.ARC.MIGRATIONASSESSMENT`), but it isn't an issue, so it isn't counted under **Optimization** in **What needs attention**.
- **T4's autonomous tuning is outside Database Hub:** on the default `Standard_D4ds_v5` (4 vCores) it recommends indexes for the `missing-index` lookups in the Azure portal and through `az postgres flexible-server autonomous-tuning`, after a tuning session (every 60 minutes while T4 runs), so at least about an hour after the activity starts; a size below 4 vCores, or Burstable, turns it off ([deployment](deployment.md#t4s-size-the-4-vcore-default-and-its-fallback-2026-11-04)).
- **Undocumented thresholds:** High CPU's 80%, CPU spikes' 48 hours, and "limited by service tier" are seen in Database Hub's UI and aren't on Learn, so they can change.
- **T1 and T2 may not appear in High CPU:** their telemetry's `AvgCPUPercent` is intermittently 0 ([SQL Server CPU in the telemetry](#deployment-and-operations)), and what Database Hub's Performance page reads for them isn't documented.
- **One Run all at a time:** a second Run all while a run is active is refused ("Stop now first, or wait for the run to end"); to change what runs, press **Stop now**, then Run all.

## Targets and licensing

- **Editions:** Developer, Express, and Evaluation editions can't drive Hub Performance. `t2SqlInstallMode = Developer` gives T2 Estate only ([ADR 0006](adr/0006-sql-editions-and-licensing.md)).
- **T2's default guest is Arc Jumpstart's image** (`JumpstartImage`): ArcBox's prebuilt SQL Server 2022 Standard guest disk ([ArcBox ITPro docs](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/azure_jumpstart_arcbox/ITPro/_index.md)). Jumpstart's environments "are all intended for evaluation, training, and demo purposes only and are not supported for production use cases" ([Jumpstart FAQ](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/FAQ/_index.md)), which is this demo's use, and the program is in maintenance mode ([release notes](https://jumpstart.azure.com/release_notes), checked 2026-11-05). Jumpstart publishes no separate license for its disk images; the software in them is Microsoft's, and SQL Server is billed through Arc pay-as-you-go.
- **Jumpstart can change the image:** a newer image at the same URL is used only after the guest passes the image checks (SQL Server 2022 Standard on the default instance, the guest's Administrator a sysadmin), with a **Warning** that names it (`STATUS.T2.IMAGE`). An image that fails them, or a changed published password, ends T2 **NOT DONE** with the fix ([troubleshooting](troubleshooting.md)), and nothing switches to another mode by itself.
- **A new T2 guest depends on Jumpstart at deploy time:** the host downloads the 34 GiB image from Jumpstart's public storage and reads its published credential from Jumpstart's pinned script on GitHub ([outbound access](prerequisites.md#outbound-access)). When either can't be reached, T2 ends **NOT DONE**; `deploy.ps1` again retries, and resumes a partial download.
- **`EvaluationOnlyAzureVm` can't use it:** the image is a Hyper-V guest disk, so it needs the nested host. With `t2Mode` `EvaluationOnlyAzureVm`, `PREFLIGHT.T2.MODE` is a **Fail** for `JumpstartImage`, and for an older configuration's `PaygWizard`, which runs as `JumpstartImage`: use `t2Mode` `Nested` with a nested-virtualization size, or `t2SqlInstallMode` `ProductKey` or `Developer`.
- **No mode installs pay-as-you-go SQL Server from Microsoft's media:** Learn documents that only in the setup wizard, which needs a person. `JumpstartImage` uses Jumpstart's prebuilt guest, and Arc sets pay-as-you-go; `ProductKey` (P10) and `Developer` are unattended too. An older configuration's `PaygWizard` runs as `JumpstartImage`, with no setup wizard, and a guest it finished is kept as it is.
- **Without `assignRoles`, Arc onboarding uses your token:** a Contributor-only caller can't create the host identity's role assignment, so `configure-arc.ps1` passes your Azure Resource Manager token, valid for about an hour, which endpoint protection can record off the VM ([the token handoff](security-model.md#the-token-handoff)).
- **The guest's Windows:** the default `JumpstartImage` guest runs Windows Server 2022 Standard, not an evaluation, so it has no 180-day expiry; the demo doesn't activate it, and records its license state in the host's health. A build mode's guest (`ProductKey`, `Developer`, or a kept `PaygWizard` guest) runs the Windows Server 2022 Evaluation, which expires 180 days after it's built: the host rearms it (`slmgr.vbs /rearm`) when 30 or fewer days are left, at most once every 24 hours, while the host runs and no activity profile does, and warns to rebuild T2 when no rearm is left ([slmgr.vbs options](https://learn.microsoft.com/windows-server/get-started/activation-slmgr-vbs-options)). `reset-demo.ps1 -RebuildGuest` reports **Not supported**, so a rebuild is `destroy.ps1` followed by `deploy.ps1`. Licensing of Windows guests in nested Hyper-V on Azure isn't documented, whatever the guest's source.
- **Arc pay-as-you-go lapse:** a T2 host left deallocated for more than 30 days breaks Arc pay-as-you-go authorization. `status.ps1` warns at 21 and 28 days.
- **Arc on a nested guest** isn't explicitly documented. It works here (onboarding, the Azure extension for SQL Server, monitoring, Estate, and telemetry), and the opt-in **evaluation-only** fallback stays for hosts without nested virtualization.
- **Extension delivery is slow in the guest:** downloads of the Azure extension for SQL Server from `<region>.his.arc.azure.com` fail intermittently with "certificate verify failed", so it takes from about 2 to about 45 minutes to arrive, after a golden restore too.
- **The golden snapshot** ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)): restoring pay-as-you-go SQL Server from it isn't documented, so after every restore the T2 checks verify Standard edition, license type PAYG, and monitoring before T2 counts as ready. A build mode's guest keeps counting its Windows evaluation inside it: `status.ps1` and preflight warn at 30 and 7 days, and after that the redeploy makes T2 from Jumpstart's image ([cleanup](cleanup.md)); a `JumpstartImage` guest's snapshot doesn't expire. Under Contributor, its access can't be narrowed: any Contributor on the subscription can create a disk from it, and `DenyAll` blocks export for everyone ([ADR 0008](adr/0008-identity-rbac-abac.md), [security model](security-model.md#residual-risks-accepted)).
- **T1's associated services:** the Marketplace image installs Analysis Services and Integration Services; T1's `AssociatedServices` step uninstalls them and restarts the SQL IaaS Agent, so unified inventory lists only the engine, and `deploy.ps1`'s validation fails while they're still listed after 10 minutes.
- **T4 in Database Hub is metrics only:** Hub's PostgreSQL monitoring "uses existing Azure Monitor metrics and doesn't provide query-level diagnostics", and Estate lists the flexible server, not its databases ([monitor PostgreSQL](https://learn.microsoft.com/fabric/database/hub/monitor-postgresql)). T4's sessions, waits, and blockers come from the runner (`status.ps1 -Detail`, `ContosoCare.Workload status --target T4`); Database Agents covers PostgreSQL only as a limited preview in Visual Studio Code ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md)).
- **A stopped T4 starts on its own after seven days** and bills compute until it's stopped again ([stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server)); while stopped, it rejects every management operation except start, so `deploy.ps1` starts it before the template. Once its role is assigned, the nightly safety stop stops it within a day, and the cost estimate counts about a day per restart; without a safety stop fully in place, the rest of the month, with a **Warning** that names the missing piece ([what stops on its own](../README.md#what-stops-or-pauses-on-its-own)).
- **The nightly safety stop's limits** ([ADR 0024](adr/0024-nightly-safety-stop.md)): it needs an Owner once per environment for its role (P16), and again after a destroy and redeploy; until then its jobs end `NotGranted`, and nothing stops a restarted T4. Its T3 check can't pause T3: Azure has no "pause now" for serverless, so a T3 that something keeps awake stays online until that stops. A schedule can start its job a few minutes late. Whichever run stops T4 sets its next restart just after that run a week later, so an idle T4 bills between about half an hour and about a day a week. The T3 check stops T4 whenever it runs, an evening session's too.
- **T4's read replica** ([ADR 0025](adr/0025-t4-read-replica.md)) is a same-region read replica only: no high-availability standby, no promotion or switchover, no geo-replica, and no geo-redundant backup (West US 3 has none). Database Hub's Read replica lag is "not HA standby or logical replication lag", and Database Hub has no HA or DR assessment for PostgreSQL ([monitor PostgreSQL](https://learn.microsoft.com/fabric/database/hub/monitor-postgresql)). Also:
  - **It exists only for a session:** `start-demo.ps1` waits for it at its end, about 9 minutes after T4 is Ready, and Azure can refuse its size at a session's start; the session then goes on without it, with a **Warning**. Its Azure Monitor history ends when the session's stop deletes it (Azure answers `ResourceNotFound` for its metrics then), so only what was saved first stays in the lakehouse: a Run all session's history, or what `stop-demo.ps1 -SaveHistory` captured. Until an Owner's grant gives the session control its PostgreSQL actions, a Run all session has no replica, and `start-demo.ps1` creates one.
  - **Azure's power order:** Azure starts T4 only after a stopped replica is Ready, and stops a replica only after T4 is stopped (`SourceReplicasStartStopOrder`); the scripts and runbooks follow it. Whether Azure's own 7-day start brings up a stopped replica before T4 isn't documented, so a replica that a session left behind is a **Warning** in `status.ps1` until `stop-demo.ps1` deletes it. The safety stops stop such a replica after T4; they never delete it.
  - **Estate:** Database Hub shows the replica as a server of its own; `HUB.ESTATE.T4.REPLICA` checks Azure Resource Graph only, so seeing it in the UI stays a manual check.
- **Query Store on T4 at every size but Burstable** (2026-11-23): Learn says not to enable it on the Burstable tier ([Query Store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)), so a Burstable `t4SkuName` has it off, and it records nothing on the read replica. Its query history is in T4's `azure_sys` database and the Azure portal, not in Database Hub. Enhanced metrics (free) are on for every size.
- **The notebooks can't read T4 live:** `notebookutils` has no Azure Resource Manager or PostgreSQL token, and T4 has no public endpoint, so the live-activity notebook links to Database Hub's PostgreSQL dashboard, and the demo's Real-Time Dashboard, which reads only the SQL telemetry endpoint, points to Database Hub's own dashboards for T4 and T5. T4's and its replica's metrics reach the history only through `POSTGRES_METRICS`, which Run all, `stop-demo.ps1 -SaveHistory`, and `deploy.ps1`'s history snapshot pass ([ADR 0025](adr/0025-t4-read-replica.md#the-history)); the live-activity notebook run by hand adds none.
- **Azure can refuse a T4 size** (`SkuNotAvailable`), even one the region's capability list includes (West US 3 refused `Standard_B1ms` and `Standard_B2s` on 2026-10-26); Learn's remedy is another size ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors)). The run then falls back by itself, for the default and for a size `t4SkuName` sets, and says what it created and what that costs; only a refusal of every size is a **Fail** (`DEPLOY.T4.SKU`), and the run ends **NOT DONE** with the fix ([the fallback](deployment.md#t4s-size-the-4-vcore-default-and-its-fallback-2026-11-04)).
- **An older T4 needs `deploy.ps1` for the showcase:** an existing T4 database gets `missing-index` in its catalog (`demo.fn_scenario_catalog`) only when `deploy.ps1` sets T4 up again, and an older runner on T1 refuses `--vcores` and the showcase until `deploy.ps1` updates it ([update an existing environment](deployment.md#update-an-existing-environment)).
- **`connection-surge` past the limit:** `max_connections` is 50 on every T4 size, and the surge fills its headroom for 5 seconds at most, so a few attempts are refused (at most 5 in any minute and 30 in a run; [ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-11-03-max_connections-at-50-on-every-size-and-connection-surge-past-the-limit-the-showcase)). A T4 whose new value waits for a restart keeps its old limit (`T4.MAXCONNECTIONS`, a **Warning**).
- **T5, Azure Cosmos DB** ([ADR 0027](adr/0027-t5-cosmos-db.md)):
  - **No stop:** an account can't be stopped or paused, and a container's throughput can only be deleted with the container. So T5's container exists only during a session: the starts create it (about a minute; with no session control role at all, `start-demo.ps1` creates it with your own rights), the stops delete it, and between sessions T5 bills only its private endpoint and DNS zone. It stays between sessions, billing its throughput unless the free tier covers it, only while the control holds an older role without the container's actions, until an Owner's `./scripts/deploy.ps1` or an Owner's `./scripts/grant-safety-stop.ps1` once, and in an environment deployed before 2026-11-19, until its next `./scripts/deploy.ps1`. `DEPLOY.T5.LIFECYCLE` and the status page say which applies ([cost management](cost-management.md#t5-azure-cosmos-db-2026-11-18)). Each session starts with an empty container.
  - **The free tier is one account per subscription, set only at creation, and not offered to internal subscriptions:** where another account has it, T5 is created without it and bills its throughput, and the run names that account (`DEPLOY.T5.FREETIER`). An account created without it never gets it; deleting T5 and running `deploy.ps1` again gets it only when the slot is free by then.
  - **Database Hub reads it from Azure Monitor metrics only,** at an hourly grain ([monitor Azure Cosmos DB](https://learn.microsoft.com/fabric/database/hub/monitor-cosmos-db)): a 10-minute storm shows in **Normalized RU Consumption** and **Throttled Requests** within its hour; **Avg Latency** stays empty, because it charts direct-mode latency and the runner uses the gateway (HTTPS 443 through the private endpoint); **Availability** is an hourly average. Whether the Database Agent covers Cosmos DB isn't part of the prompt pack yet.
  - **`ru-storm` throttles on purpose:** it drives one partition to 100% normalized RU, and its 429s are the scenario's signal. Its bounded documents are deleted at its end, and `reset-demo.ps1 -Target T5` removes any a stopped VM left behind.
  - **A new data-plane role can take minutes:** T1's access is checked for up to 10 minutes (`WORKLOAD.T5.WARMUP`); a run that ends before it takes effect is **NOT DONE**, and the next `deploy.ps1` checks again.

## Network and access

- **Egress:** NSGs can't restrict HTTPS by FQDN; a strict allow-list needs Azure Firewall, which isn't part of v1 ([ADR 0007](adr/0007-networking-modes-and-egress.md)).
- **No SQL endpoint from outside:** nothing outside the demo's virtual network reaches T1, T2, or a private T3, so Hub's **Open in SSMS** or VS Code links and the T-SQL agent skills need a Bastion session on a demo VM.
- **Default outbound access:** the VM subnets explicitly keep default outbound access, a path Microsoft is phasing out in favor of explicit methods. `outboundMode = NatGateway` is the ready alternative, at extra cost ([ADR 0017](adr/0017-outbound-access.md)).
- **Trusted Launch** is reported as incompatible with nested virtualization (Microsoft Q&A; the Trusted Launch page doesn't say either way), so the T2 host defaults to the Standard security type ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **Tenant policies:** preflight's policy inventory reads assignments and definitions without changing them. It doesn't read exemptions or assignments scoped to resource groups, and it treats conditions it can't evaluate conservatively; the what-if check remains the backstop for denials. Large policy sets take a few minutes to read ([ADR 0012](adr/0012-validation-model.md)).
- **The Azure CLI sign-in is the operator's:** the scripts never sign in, and never change the CLI's default subscription; on a machine where other tools share the Azure CLI configuration, [isolate the demo's sign-in](troubleshooting.md#optional-isolate-the-demos-azure-cli-sign-in-on-a-shared-machine).

## Deployment and operations

- **No artifact cache:** every new T2 guest downloads its source again (retries resume a dropped download): Jumpstart's 34 GiB image in the default mode, and about 6.2 GB of media from Microsoft in the build modes, where a changed file at a pinned URL fails closed until `config/versions.json` is updated.
- **Redeploy time:** the 30-minute target isn't met. T2's track is the critical path: its host build with the image's download, which the host's disk bounds, or its golden restore, then the SQL Server extension's download in the guest. Measured times are in [deployment](deployment.md#how-long-each-step-takes), and `DEPLOY.TIMING` records each run.
- **Bootstrap bundle in Run Command chunks:** Learn documents no size limit for an inline Run Command script. Chunks are 512 KiB of data by default, the largest size proven live, and each takes one Run Command round trip ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **Run Commands need a running VM, and policy extensions can hold them:** a deallocated VM answers `OperationNotAllowed`, and a policy-driven `MDE.Windows` update can hold a VM's Run Commands for about 10 minutes. The tracks wait for a new VM's extensions to settle and restart a stuck VM once, but a policy's extension that never finishes still ends a run **NOT DONE**, naming it.
- **Keeping the machine awake works on Windows only:** `deploy.ps1` keeps a Windows PC and its display awake, but not through a closed lid or a shutdown. A GitHub codespace stops after its idle timeout (30 minutes by default, reset by terminal output) and always after 12 hours ([GitHub Docs](https://docs.github.com/codespaces/setting-your-user-preferences/setting-your-timeout-period-for-github-codespaces)); `./scripts/deploy.ps1` then continues where it stopped.
- **The subscription's automation can switch a deallocated VM's OS disks to Standard HDD:** boots and IO are then slower, and IO-heavy scenarios (`io-pressure`, the T2 guest's VHDX) look worse than the profile intends. `deploy.ps1` keeps each drifted disk's type (`DEPLOY.DISKS.DRIFT`, a **Warning**), `status.ps1` reports it (`STATUS.DISKS`), and changing them back is the subscription owner's call ([change a disk's type](https://learn.microsoft.com/azure/virtual-machines/disks-convert-types)).
- **Validation while the demo is stopped:** a deallocated VM can't run a Run Command and shows empty instance views, so `validate.ps1` reports every check that needs it as a Warning to start the VM, the secret scan of Run Command instance views included. Validation's T3 checks that run through T1 resume a paused T3, which then bills until it auto-pauses again ([ADR 0012](adr/0012-validation-model.md)).
- **Telemetry:** 3–15 minutes of latency and retention of 7 days or less. T3 can keep sending telemetry while its serverless database reports `Paused`, so a fresh T3 sample doesn't prove the database is awake.
- **SQL Server CPU in the telemetry:** `AvgCPUPercent`, which the telemetry article calls the primary CPU signal, is intermittently 0 for T1 and T2 while `SQLProcessCPUPercent` shows the SQL process busy (in one T2 incident, 81 for 10 minutes, then 0 for the next 10, with the process at 84 to 88 throughout), while T3's reached 99.9. So the live-activity notebook and the Real-Time Dashboard read `SQLProcessCPUPercent` for T1 and T2 and `AvgCPUPercent` for T3; history saved before they did keeps 0 for T1's and T2's CPU.
- **T1's monitoring after a start:** after `sqlvm01` is deallocated and started, the SQL IaaS Agent's monitoring plugin (`DatabaseMonitorArcPlugin`) can stay NotRunning for hours, so T1 sends no telemetry. `start-demo.ps1`, `deploy.ps1`, and the control's runbooks wait up to 8 minutes for a status reported after the start (`MainServiceLastReportedTime`), restart the agent's service (`SQLIaaSExtension`) once when the plugin isn't Running, and wait up to 5 minutes more, so a start can take up to about 13 minutes longer. After a start by other means (the portal, `az vm start`, another schedule), run `start-demo.ps1`, which leaves running VMs as they are and does the same check (`START.T1.MONITORING`; [troubleshooting](troubleshooting.md#t1)).
- **Scenario bounds:** a database runs one Running run per scenario and four in all (`demo.usp_run_begin`'s errors 50108 and 50109), so a foreground `run` of a scenario that an activity profile is already running is refused; the profile host waits for a run of the same scenario that's still ending, ends runs an earlier host left Running without sessions, and tries a refused activity again every 30 seconds, at most 40 times, within its window. T3's `GP_S_Gen5_1` allows 75 concurrent workers and 75 concurrent logins ([resource limits](https://learn.microsoft.com/azure/azure-sql/database/resource-limits-vcore-single-databases)), and the catalog has no T3-specific cap, so keep overlapping T3 runs to about 60 sessions in all. `locking-blocking`'s longest single wait is about 20 seconds; `blocking-chain` gives waits of up to 60 seconds and deeper chains ([ADR 0010](adr/0010-workload-generator-technology.md#phase-25b-the-profile-hosts-lanes-and-supervisor-and-the-bounds-phase-25a-met-2026-10-26)).
- **Scenarios differ by target:** `parallel-scans` shows CPU waits, not Parallelism waits, where it runs serially, and its parallel plan is confirmed on T1 and T2 only; `blocking-chain` doesn't escalate on T3, which always uses [optimized locking](https://learn.microsoft.com/sql/relational-databases/performance/optimized-locking); the telemetry has no chain depth or blocker tree, so the skills prompts read them from the database; and on T3 `log-flush-waits` shows only as waits ([scenarios](../scenarios/README.md)).
- **The profile host restarts its own lanes, not itself:** a lane that stops finishing its polls is replaced after 5 minutes, so a stall can delay a profile change by about 5 minutes; a hung host process isn't restarted by anything but the next boot or a task restart, and `WORKLOAD.<target>.HOST` and `status.ps1` report it as a **Fail** while a profile is active.
- **Notebooks:** need a running F or Trial capacity, can't call Azure Resource Manager, and use a `kusto` token path to the telemetry endpoint that isn't documented; the printed-KQL fallback stays ([ADR 0014](adr/0014-notebook-role-and-capacity.md)).
- **Deploy to Azure button:** it provisions infrastructure only; the VM bootstraps start on `deploy.ps1 -Resume`, so `./scripts/deploy.ps1` stays the one path to a whole demo ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **License terms:** in the build modes, the unattended guest build and SQL Server setup accept the Windows Server evaluation and SQL Server license terms on the operator's behalf; the `JumpstartImage` guest comes with both already installed.
- **Mirroring:** not part of v1 ([ADR 0015](adr/0015-mirroring-deferral.md)).

## The session control

The session control (formerly the on-demand activity control) is part of every deployment: one Run all in `NB_DatabaseHub_Control` runs a whole session ([ADR 0026](adr/0026-one-run-all-session.md); [ADR 0020](adr/0020-on-demand-activity-control.md) before).

- **Its roles need an Owner once per environment,** and again after a destroy and redeploy: two custom roles and four assignments (A1 to A4). `deploy.ps1` grants them when you're an Owner or User Access Administrator; otherwise an Owner runs `./scripts/grant-safety-stop.ps1` once. Until then, Run all can't start a session, and `./scripts/start-demo.ps1` runs one from your PC with Contributor ([permissions](permissions.md#the-on-demand-activity-control)).
- **Where a policy makes new vaults private, its notebook starts slowly:** it lives in its own workspace (`control.fabricWorkspaceName`), whose managed private endpoint turns off starter pools, so each Spark session takes 3 to 5 minutes to start ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)).
- **The folder uses a preview API:** Folders - Create Folder is documented as a preview; when it fails, the notebook goes in the workspace's root with a Warning.
- **The activity starts minutes after the request:** the runbook starts the VMs when they're stopped (about 2 to 5 minutes), and Run Command under load can take up to about 11 minutes; telemetry then shows the activity 3 to 15 minutes later. The notebook's live view says when nothing has arrived yet.
- **The webhook expires** after 90 days by default; `setup-activity-control.ps1 -RotateWebhook` replaces it, and `status.ps1` warns 14 days before.
- **The webhook URL is a bearer secret:** whoever has it can start a bounded run or session, one at a time, within the allow-lists and caps, and the vault has no data-plane logs ([security model](security-model.md#the-session-control)).
- **A new scenario reaches the runbook only after the next `./scripts/deploy.ps1`,** which republishes the runbooks (`CONTROL.RUNBOOKS`) with the scenario catalog's allow-lists.
- **`start-demo.ps1` replaces a pending auto-stop with its own** (since 2026-11-19): the session stops by itself `-Hours` after its start (4 by default), and `START.CONTROL.AUTOSTOP` gives that time. A stop job that's already running is waited for, up to 10 minutes, and never stopped (`START.CONTROL.STOPJOB`); when the auto-stop can't be replaced, or the job still runs after the wait, the start carries on with a **Warning** that says when the VMs may deallocate and what to do. Without the session control's role (A1) none is scheduled, and the nightly stop is the limit.
- **A Run all whose notebook still follows its session sends its own stop at its session's end:** the notebook can't read Azure Resource Manager, so when a later `start-demo.ps1` replaced that session's auto-stop, the notebook still stops the demo at the end it planned. Run `./scripts/start-demo.ps1` again after that end, or start the local session after the notebook's.
- **The stop at the end of an update can still cut off a session that starts while the VMs deallocate:** it checks for a session before its wait, after it, before its first change, and before T2's guest and the VMs, but neither Run all nor `start-demo.ps1` waits for it. A session that starts in those last seconds gets a **Warning** in `DEPLOY.ENDSTOP` with how to start it again. Ctrl+C during the stop leaves running what it hadn't stopped, and the row says so.
- **An update's stop at its end waits at most 15 minutes** for work that still needs the hosts (a bootstrap pass, T2's first migration assessment); what doesn't finish goes on at the next start, or at the next `deploy.ps1` or `configure-arc.ps1`.

## Cost

- **Defender for Cloud:** plans that tenant policies enforce add cost that the demo can't turn off. Billing for a disconnected Arc SQL instance isn't documented, and the Defender Workload Unit meters may change how the invoice shows Defender ([cost management](cost-management.md#microsoft-defender-for-cloud)).
- **Outside the ceiling:** the Fabric capacity, which the notebooks need running and which bills by the hour until you or its administrator pause it ([cost management](cost-management.md#microsoft-fabric-capacity)); Fabric and Power BI licenses; and each viewer's GitHub Copilot plan, which Ask's questions use.
- **Premium SSD v2** needs a zonal VM, so `demo-day` and `enhanced-performance` use it only when `zone` is set; otherwise their data disks use Standard SSD (E10), and Premium SSD (P10) only as a `dataDiskSku` opt-in ([ADR 0016](adr/0016-cost-profiles.md)).
- **`lowest-cost` has no data disks:** SQL Server data on T1, and the guest's VHDX on the T2 host, share the 128 GiB OS disks. The host fails the build early when `C:` has too little free space (about 64 GiB in `JumpstartImage` mode, about 80 GB in the build modes), and because the Jumpstart guest's dynamic disk can grow to 100 GiB, `status.ps1` warns when less than 20 GiB is free (`STATUS.T2.DISKSPACE`). `dataDiskSku` `E10` adds data disks; switching back to `None` detaches them without deleting them, so they keep billing until you delete them ([ADR 0016](adr/0016-cost-profiles.md)).

## Presentation layer

- **Viewer licensing:** on a capacity smaller than F64, every viewer of Power BI content, such as the history report, needs Pro, PPU, or an individual trial, and the Insights app reads the same model as the viewer, so plan the same for it (not yet verified). Database Hub and the Real-Time Dashboard aren't Power BI content, and a presenter sharing their screen needs nothing more. The demo assumes its viewers have these licenses, so `PREFLIGHT.FABRIC.VIEWERLICENSE` is **Not selected** ([viewer licensing](permissions.md#presentation-surfaces-and-viewer-licensing), [presentation](presentation.md)).
- **Real-Time Dashboard:** its viewers need Reader on the subscription (and the Arc telemetry role when they're only Readers), because it queries the telemetry endpoint as each viewer. The dashboard schema has no theme property, so a dark theme can't be set, and Database Hub's template wizard that makes a similar dashboard is UI-only ([Real-Time Dashboard](../fabric/realtime/README.md#limitations)).
- **The Insights app:** Fabric Apps is a preview ([overview](https://learn.microsoft.com/fabric/apps/overview)), available only in [supported regions](https://learn.microsoft.com/fabric/apps/region-availability). Open it from its workspace item: its hosted URL opened directly stops at "Page not accessible directly" ([the app's guide](../fabric/app/README.md#known-limitation-the-hosted-url)). There's no CI deploy by default, because the Rayfin CLI's service principal sign-in isn't supported yet. Your `az login` deploys it while Fabric accepts that token, and the CLI's own browser sign-in (P14) is needed only after Fabric refuses it. Without either, the app isn't created, but the run still ends **DONE**, with the app's step **Failed** on the status page. It uses the workspace capacity's units, outside the demo's ceiling. The CLI can't call the deployed connector (it needs an app session), so the in-app path is checked in the browser, by a person.
- **Ask, the Copilot chat in the Insights app:** each viewer uses their own GitHub Copilot plan, so a viewer without one gets no answers, and the model and its limits are their plan's. The sign-in is GitHub's device flow, once per browser and per context: the app in the Fabric portal's frame and the app at its own address keep separate sign-ins. GitHub's device page shows the relay's Azure region as the request's location, and enables **Authorize** only while its window has the focus. The live estate isn't available today: Database Hub refuses the app's own sign-in (HTTP 401; R924, `FABRIC.APP.ESTATE` **Not supported**), so the pages show no live parts and **Live views** says so in one line, the dock says so in one plain sentence, history keeps working, and Database Hub itself has the live view; the same happens if its undocumented routes change ([above](#preview-disclosures)). A policy that denies a public endpoint leaves the relay out (`ASK.RELAY`, a **Warning**), and with the Fabric tenant setting "Enforce a strict content security policy for static-hosted Fabric Apps (preview)" on, the page can't reach it (`ASK.CSP`, a **Warning**). Copilot's answers aren't promised: every answer shows its query or source, and every tool is read-only ([ADR 0028](adr/0028-ask-copilot-in-the-insights-app.md)).
- **Manage in the Insights app** ([ADR 0029](adr/0029-insights-app-dba-console.md)): it sends a request only for an operator, the deployer or a member of the demo's admin group (refreshed at each `deploy.ps1`, `FABRIC.APP.OPERATORS`), one request at a time, after a confirmation; any other viewer sees it read-only. When the function can't send, Manage falls back to copy mode: it copies the request for Run all in `NB_DatabaseHub_Control`. Its sending mode waits for the identity proof ([below](#not-proven-live-yet)).
- **The Insights app labels four incident families:** IO, CPU, blocking, and log rate. Windows the live-activity notebook finds for the other wait families (`latch`, `memory`, `parallelism`, `tran_log`, `network`, and `deadlock`) show their raw family name on the Incidents page, and the replay plots their total wait time rather than their own signal.
