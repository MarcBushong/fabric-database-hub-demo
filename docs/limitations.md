# Known limitations

What the demo can't do, what depends on a preview, and what isn't proven yet. Each item links to the decision or risk behind it. The acceptance status of every criterion is in the [final report](implementation-report.md#final-report).

## Preview disclosures

- **Generally available since 2026-11-17:** Database Hub itself (Overview, Estate, Performance, security posture, investigation, and Optimization insights), its real-time dashboards for Microsoft SQL, Azure Database for PostgreSQL, and Azure Cosmos DB, bulk monitoring enablement, the SSMS and VS Code entry points, and the Database Hub CLI skill in skills-for-fabric ([overview](https://learn.microsoft.com/fabric/database/hub/overview), [announcement](https://techcommunity.microsoft.com/blog/azuresqlblog/database-hub-in-microsoft-fabric-is-generally-available-your-entire-database-est/4574212)). It needs only a Fabric Free license.
- **Still in preview:** Copilot in Database Hub, Database Agents, alerts, and SQL Server on Azure VM performance monitoring; and, as Learn still labels them (2026-11-18), unified inventory, the Arc SQL monitoring setting (API version `2023-09-01-preview`), the SQL telemetry endpoint, its tenant setting's name (**Users can access the Database hub (preview)**), and Fabric Apps. Their behavior, prerequisites, labels, schemas, and APIs can change without notice.
- **Capacity:** Database Hub's own views need no Fabric capacity. Copilot, custom alerts, and shared dashboards do, and so do the demo's own items: the notebooks, the Real-Time Dashboard, the report, and the Insights app. The capacity, Fabric and Power BI licenses, and their cost are yours to manage, outside the demo's estimates, and so is each viewer's GitHub Copilot plan, which Ask uses ([cost management](cost-management.md#at-a-glance)).
- **What the repo does about it:** it uses only documented interfaces, never calls Database Hub's private routes except in one narrow, read-only exception (the Insights app's live-estate function, for Ask and the app's pages, [ADR 0013's amendment](adr/0013-agent-experience.md#amendment-2026-11-18-the-ga-skill-and-one-narrow-exception)), validates prerequisites and signals instead of promising outcomes, and gives every preview-dependent step a fallback ([ADR 0013](adr/0013-agent-experience.md), [troubleshooting](troubleshooting.md#fallbacks-at-a-glance)).
- **No Hub API:** saved views, the **Enable Performance Monitoring** button, monitor templates, Copilot, and Database Agents' settings (**Manage agents**) are UI-only. The demo validates through Azure Resource Graph and the documented telemetry endpoint, and the Hub UI check stays **Manual action required**. Selecting T3 for Database Agents is optional, once per deployment, about 30 seconds, and needed only for the Database Agent loop on T3: `deploy.ps1` lists it under **Please confirm** with the link and the database to select (`HUB.AGENT.T3`).
- **Database Agents and Copilot coverage:** Database Agents (preview) covers Azure SQL Database in Database Hub, so T3 only here: not SQL Server on Azure VMs or enabled by Azure Arc (T1, T2), not one-vCore serverless databases (why the lowest-cost T3 has two vCores at most since 2026-11-18), and PostgreSQL (T4) only as a limited preview in Visual Studio Code. It raises an issue about 15 minutes after a condition starts and applies no change: every scenario needs a manual response, which the showcase's Database Agent beat makes itself ([Database Agents](https://learn.microsoft.com/fabric/database/hub/database-agents), [walkthrough](demo-walkthrough.md#the-database-agent-loop-on-t3)). It also needs T3 in the region associated with the Fabric tenant's home region, which no API reads. Copilot's target coverage and latency aren't documented, so every incident still runs on T1, T2, and T3, the walkthrough has fallbacks, and the live coverage record waits for the owner's rehearsal ([ADR 0013](adr/0013-agent-experience.md)).
- **Never promised:** the demo describes the signals to look for, never the AI's answers, and every action an agent proposes needs human approval.

## Database Hub's visuals in one session (the showcase)

**Run all** starts the showcase, which fills the visuals that can fill within one session; the [README](database-hub-visuals.md#what-fills-each-database-hub-visual-and-when) says, visual by visual and target by target, what fills each one, when, and when it stays empty.

- **Some need history, not activity:** **CPU spikes** compares with a 48-hour baseline (seen in the UI on 2026-11-03, not on Learn), so a target that sent no telemetry in the previous 48 hours likely has nothing to spike against; run the [baseline](database-hub-visuals.md#the-baseline-run-why-it-matters-and-when-it-doesnt) the day before. Azure SQL Database's index recommendations need "at least a day" of monitoring, and PostgreSQL's Azure Advisor up to seven days on one configuration.
- **Some can't fill here at all:** T1 and T2 have no automatic tuning (SQL Server 2022 Standard); Activator alerts don't support PostgreSQL; and Database Hub's utilization suggestions look for quiet targets, which a showcase isn't. The Optimization insights of general availability don't depend on the activity: Database Hub has T2's migration assessment ready once its first assessment has uploaded (`deploy.ps1` turns the assessment on and starts it, `T2.ARC.MIGRATIONASSESSMENT`); a ready assessment isn't an issue, so it doesn't add to the **Optimization** count in **What needs attention**. T1 and T2 show no license-model opportunity because they already use pay-as-you-go (checked in Database Hub's data on 2026-11-18). **Read replica lag** fills only while T4's read replica exists, during a session that Run all or `start-demo.ps1` started, or a `deploy.ps1` run (since 2026-11-13): between sessions, in a Run all session before an Owner's grant gives the session control its PostgreSQL actions, and on a Burstable T4 it stays empty.
- **T4's autonomous tuning is on by default, outside Database Hub (since 2026-11-04):** it was never possible here on the Burstable default; now the default size is `Standard_D4ds_v5`, with 4 vCores and Query Store, so autonomous tuning can recommend indexes for the showcase's T4 `missing-index` lookups, in the Azure portal and through `az postgres flexible-server autonomous-tuning`, not in Database Hub, whose PostgreSQL view is metrics-only. The first recommendation comes after a tuning session, every 60 minutes while T4 runs, so at least about an hour after the activity starts. A size you set below 4 vCores, or on Burstable, turns it off ([deployment](deployment.md#t4s-size-the-4-vcore-default-and-its-fallback-2026-11-04)). Unproven live: [below](#targets-and-licensing).
- **Undocumented thresholds:** High CPU's 80%, CPU spikes' 48 hours, and "limited by service tier" were seen in Database Hub's UI on 2026-11-03 and aren't on Learn, so they can change.
- **T1 and T2 may not appear in High CPU; observed intermittent:** their telemetry's `AvgCPUPercent` is intermittently 0 while the SQL process is busy (2026-10-23; and 2026-11-04, when `arcsql01` read 81 for 10 minutes, then 0 for the next 10, with `SQLProcessCPUPercent` at 84-88 throughout); see [SQL Server CPU in the telemetry](#deployment-and-operations). What Database Hub's Performance page reads for them isn't documented, and the Hub itself hasn't been checked yet.
- **One Run all at a time:** a second Run all while a run is active is refused, with "Stop now first, or wait for the run to end"; to change what runs, press **Stop now**, then Run all.

## Targets and licensing

- **Editions:** Developer, Express, and Evaluation editions can't drive Hub Performance. `t2SqlInstallMode = Developer` gives T2 Estate only ([ADR 0006](adr/0006-sql-editions-and-licensing.md)).
- **T2's default guest is Arc Jumpstart's image (since 2026-11-05):** in `JumpstartImage` mode the T2 host downloads Arc Jumpstart ArcBox's prebuilt SQL Server 2022 Standard guest disk ([ArcBox ITPro docs](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/azure_jumpstart_arcbox/ITPro/_index.md)). Jumpstart's FAQ says its environments, ArcBox included, "are all intended for evaluation, training, and demo purposes only and are not supported for production use cases" ([Jumpstart FAQ](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/FAQ/_index.md)), which is this demo's use, and the program is in maintenance mode ([release notes](https://jumpstart.azure.com/release_notes), checked 2026-11-05). Jumpstart publishes no separate license for its disk images; the software in them is Microsoft's, and SQL Server is billed through Arc pay-as-you-go.
- **Jumpstart can change the image:** a newer image at the same URL is used only after the guest passes the image checks (SQL Server 2022 Standard on the default instance, the guest's Administrator a sysadmin), with a **Warning** that names it (`STATUS.T2.IMAGE`); an image that fails them ends T2 **NOT DONE**, and nothing switches to another mode by itself. If Jumpstart changes the image's published password, the guest doesn't accept the credential from the pinned script within 15 minutes, and T2 ends **NOT DONE** with the fix: point `media.jumpstartArcBoxSqlStd.credentialSource` in `config/versions.json` at the Jumpstart commit that matches the image ([troubleshooting](troubleshooting.md)).
- **A new T2 guest depends on Jumpstart at deploy time:** the host downloads the image (34 GiB) from Jumpstart's public storage, `jumpstartprodsg.blob.core.windows.net`, and reads the image's published credential from Jumpstart's pinned script on GitHub, `raw.githubusercontent.com`, over HTTPS ([outbound access](prerequisites.md#outbound-access)). When either can't be reached, T2 ends **NOT DONE**; running `deploy.ps1` again retries, and resumes a partial download.
- **`EvaluationOnlyAzureVm` can't use it:** the image is a Hyper-V guest disk, so it needs the nested host. With `t2Mode` `EvaluationOnlyAzureVm`, `PREFLIGHT.T2.MODE` is a **Fail** for `JumpstartImage`: use `t2Mode` `Nested` with a nested-virtualization size, or `t2SqlInstallMode` `ProductKey` or `Developer`. An older configuration's `PaygWizard`, which runs as `JumpstartImage`, stops there too.
- **Pay-as-you-go SQL Server without a product key is documented only in the setup wizard,** so no mode installs it that way: the default `JumpstartImage` mode uses Arc Jumpstart's prebuilt SQL Server 2022 Standard guest, and Arc sets pay-as-you-go. `PaygWizard`, the default until 2026-11-05, whose setup wizard needed a person once per guest build, is retired from the one-click deployment (2026-11-09): a configuration that says it runs as `JumpstartImage`. `ProductKey` mode (P10) and `Developer` mode are unattended too.
- **Setup's interactive sign-in could leave sign-in data on the VM** in the retired `PaygWizard` mode: the scripts removed it right after the wizard and verified that none remained, and the build failed if any remained (R74; [risk register](implementation-report.md#risk-register)). Since 2026-11-09 no deployment signs in to setup; the same cleanup still runs after every Arc onboarding.
- **Without `assignRoles`, Arc onboarding uses your token:** a Contributor-only caller can't create the host identity's role assignment, so `configure-arc.ps1` passes your Azure Resource Manager token, valid for about an hour. Run Command hands it to the host's PowerShell as an argument; the scripts remove what's left of it on the VMs, but endpoint protection can record that command line off the VM, where they can't (ADR 0009).
- **The guest's Windows and its licensing:** the default `JumpstartImage` guest runs Windows Server 2022 Standard, not an evaluation, so it has no 180-day expiry; the demo doesn't activate it, and records its license state in the host's health. The build modes' guest runs the Windows Server 2022 Evaluation, which expires 180 days after it's built (the owner's `PaygWizard` guest, built on 2026-10-20, about 2027-04-18 without a rearm). Since 2026-11-05 the host rearms such a guest with `slmgr.vbs /rearm` when 30 or fewer days are left and a rearm is left, at most once every 24 hours, only while the host runs and no activity profile does, and warns to rebuild T2 when no rearm is left ([slmgr.vbs options](https://learn.microsoft.com/windows-server/get-started/activation-slmgr-vbs-options)). `reset-demo.ps1 -RebuildGuest` reports **Not supported** (R196), so a rebuild is `destroy.ps1` followed by `deploy.ps1`. Licensing of Windows guests in nested Hyper-V on Azure isn't documented, whatever the guest's source (R21).
- **Arc pay-as-you-go lapse:** a T2 host left deallocated for more than 30 days breaks Arc pay-as-you-go authorization. `status.ps1` warns at 21 and 28 days.
- **Arc on a nested guest** isn't explicitly documented. It worked live: onboarding, the Azure extension for SQL Server, monitoring, Estate, and telemetry from the nested guest (2026-10-20 and 2026-10-21). The opt-in **evaluation-only** fallback stays for hosts without nested virtualization.
- **Extension delivery is slow in the guest:** the Azure extension for SQL Server was slow to arrive in the live run, because downloads from `<region>.his.arc.azure.com` failed intermittently with "certificate verify failed" (R72). A golden restore reinstalls the extensions, so this sits on T2's path: in the quarantine test on 2026-10-22, the fresh onboarding took 45 minutes, most of it the extension's download retries.
- **Restoring a pay-as-you-go install is validated only empirically:** pay-as-you-go SQL Server copied with the T2 host's disk (the golden snapshot, [ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)) isn't explicitly documented. After every restore the T2 checks verify Standard edition, license type PAYG, and monitoring before T2 counts as ready; the quarantine test (2026-10-22) and the redeploy showed all three for a guest built in the retired `PaygWizard` mode. A `JumpstartImage` guest's capture and restore isn't proven live yet ([below](#not-proven-live-yet)).
- **The golden snapshot ages:** the guest's Windows evaluation keeps counting inside it (the owner's guest: about 2027-04-19). `status.ps1` and preflight warn at 30 and 7 days; after that, the redeploy makes T2 again from Arc Jumpstart's image, with no person ([cleanup](cleanup.md), [deployment](deployment.md)). A `JumpstartImage` guest's snapshot has no evaluation expiry, and it's only a speed-up: without one, the next deploy downloads and prepares the image again, with no person.
- **The golden snapshot's access can't be narrowed under Contributor:** the guardrail asked to keep it to the deploying identity, but without role assignments ([ADR 0008](adr/0008-identity-rbac-abac.md)) any Contributor on the subscription can create a disk from it. `DenyAll` still blocks export for everyone ([security model](security-model.md)).
- **T1's associated services:** the Marketplace image installs Analysis Services and Integration Services. T1's `AssociatedServices` step uninstalls them, so unified inventory lists only the engine (live, 2026-10-21). Inventory drops them only after the SQL IaaS Agent discovers the instances again: about 6 minutes after a restart, but 46 to 72 minutes without one (the parallel redeploy, 2026-10-22), so the step now restarts the agent, and `deploy.ps1`'s validation fails while they're still listed after 10 minutes.
- **T1's monitoring after a deallocation:** after `sqlvm01` was deallocated and started, the SQL IaaS Agent reported its monitoring plugin (`DatabaseMonitorArcPlugin`) NotRunning for more than 90 minutes, so T1 sent no Database Hub telemetry; restarting the agent's service (`SQLIaaSExtension`) fixed it within a minute (live, 2026-10-22). `start-demo.ps1` checks the plugin and restarts the service only when it isn't running (`START.T1.MONITORING`). After a start by other means (the portal, `az vm start`, or the auto-start of a schedule that doesn't use `start-demo.ps1`), run `start-demo.ps1`, which leaves running VMs as they are and does the same check.
  - **A restart right after boot can come too early (live, 2026-10-26):** `start-demo.ps1` restarted the service about a minute after the guest booted, before the plugin had reported any status; the plugin then stayed NotRunning for almost three hours (`START.T1.MONITORING` **Warning**), and `TELEMETRY.T1` failed in two deploys. The same restart run again later, with the VM up, had the plugin Running with uploads OK in 144 seconds and T1's telemetry back within a minute. Since Phase 25b, `start-demo.ps1` first waits up to 5 minutes for the agent to report the plugin's status, restarts the service only when the plugin isn't Running or still has no status, and then waits up to 5 minutes for Running and uploads OK, so a start can take up to about 10 minutes longer when the plugin doesn't come back by itself. If `START.T1.MONITORING` is still a **Warning**, run `start-demo.ps1` again a few minutes later; it repeats the check and the restart (R442).

- **T4 in Database Hub is metrics only:** Hub's PostgreSQL monitoring "uses existing Azure Monitor metrics and doesn't provide query-level diagnostics", and Estate lists the flexible server, not its databases ([monitor PostgreSQL](https://learn.microsoft.com/fabric/database/hub/monitor-postgresql)). T4's sessions, waits, and blockers come from the runner (`status.ps1 -Detail`, `ContosoCare.Workload status --target T4`); Database Agents covers PostgreSQL only as a limited preview in Visual Studio Code, not in Database Hub ([Database Agents](https://learn.microsoft.com/fabric/database/hub/database-agents), [ADR 0019](adr/0019-t4-postgresql-flexible-server.md)).
- **A stopped T4 starts on its own after seven days** and then bills compute until it's stopped again ([stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server)). Since 2026-11-05 the nightly safety stop in every deployment stops it again within a day, once its role is assigned: since 2026-11-09 its T3 check that evening when the restart comes between the stop and the check, otherwise the next evening's stop ([ADR 0024](adr/0024-nightly-safety-stop.md)). `stop-demo.ps1` and `status.ps1` give the date and name the run that stops it, and the cost estimate counts the worst case against the monthly ceiling: about a day per restart when a safety stop is fully in place (the nightly one, or the control's daily T4 safety stop), and the rest of the month otherwise, with a **Warning** that names the missing piece. While stopped, it rejects every management operation except start, so `deploy.ps1` starts it before the template.
- **The nightly safety stop's limits** ([ADR 0024](adr/0024-nightly-safety-stop.md)): it needs an Owner once per environment for its role (P16), and again after a destroy and redeploy; until then its jobs end `NotGranted` and nothing stops a restarted T4. Its T3 check can't pause T3: Azure has no "pause now" for serverless, so a T3 that something keeps awake stays online until that stops. A schedule can start its job a few minutes late. A restarted T4 bills up to about a day: whichever run stops it sets its next restart just after that run a week later, so after a stop by the T3 check, the next restart waits for the following evening's stop, and an idle T4 alternates between about half an hour and about a day a week. The T3 check stops T4 whenever it runs, an evening session's too. Its first evenings ran live from 2026-11-06; the 2026-11-09 changes aren't proven live yet.
- **T4's read replica (since 2026-11-13, [ADR 0025](adr/0025-t4-read-replica.md)):**
  - **A same-region read replica only:** no high-availability standby, no promotion or switchover, no geo-replica, and no geo-redundant backup (West US 3 has none). Database Hub's Read replica lag is "not HA standby or logical replication lag", and Database Hub has no HA or DR assessment for PostgreSQL ([monitor PostgreSQL](https://learn.microsoft.com/fabric/database/hub/monitor-postgresql)).
  - **For each session:** `start-demo.ps1` waits for it at its end, about 9 minutes after T4 is Ready (525 and 460 seconds in the live probe of 2026-11-13), and Azure can refuse its size at a session's start; the session then goes on without it, with a Warning. Its Azure Monitor history ends when the session's stop deletes it (Azure answers `ResourceNotFound` for a deleted replica's metrics), so only what was saved first stays in the lakehouse: a Run all session's history, or what `stop-demo.ps1 -SaveHistory` captured.
  - **Azure's power order:** Azure starts T4 only after a stopped replica is Ready, and stops a replica only after T4 is stopped (`SourceReplicasStartStopOrder`, live 2026-11-13). The scripts and runbooks follow it. Whether Azure's own 7-day start brings up a stopped replica before T4 isn't documented: a replica that a session left behind is a **Warning** in `status.ps1` until `stop-demo.ps1` deletes it.
  - **The safety stops don't delete it:** a Run all session or `start-demo.ps1` creates it, as `deploy.ps1` does for its checks, and the session's stop (Stop now or its auto-stop), `stop-demo.ps1`, or the end of `deploy.ps1` deletes it. The nightly safety stop and the control's daily T4 safety stop stop a left-over replica after T4, and never delete it. Until an Owner's grant gives the session control its PostgreSQL actions, a Run all session has no replica, says its replica beat isn't available, and leaves the replica to `start-demo.ps1`.
  - **Estate:** Database Hub shows the replica as a server of its own: the owner saw it on 2026-11-17, under **Performance**, then **PostgreSQL**, with its Read replica lag climbing. `HUB.ESTATE.T4.REPLICA` checks Azure Resource Graph only, so seeing it in the UI stays a manual check.
  - **Proven live** (2026-11-13 and 14): a new deployment and an older environment's upgrade create it; `start-demo.ps1` starts a stopped one before T4; `replica-lag` climbs to about 220 seconds in Azure Monitor's Read Replica Lag, which Database Hub's PostgreSQL dashboard charts (seen by the owner on 2026-11-17); `stop-demo.ps1 -SaveHistory` keeps it in the history; and the safety stop stops T4, then the replica. **Not proven live yet:** the replica's size fallback. The live probe of 2026-11-13 proved creation, inheritance, the power order, deletion, and the metrics on a pair of `Standard_D2ds_v5` servers.
- **Query Store on T4 only with autonomous tuning (since 2026-11-04):** Learn says not to enable it on the Burstable tier ([Query Store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)), so a Burstable T4 keeps it off (`pg_qs.query_capture_mode` `NONE`), and `Standard_D2ds_v5` keeps the server's default (off). The default 4-vCore size turns it on (`TOP`, with `capture_first_sample`) for autonomous tuning; its query history is in the Azure portal, not in Database Hub. Enhanced metrics (free) are on for every size.
- **The notebook can't read T4 live:** `notebookutils` has no Azure Resource Manager or Azure Database for PostgreSQL token, and T4 has no public endpoint, so the live-activity notebook links to Hub's PostgreSQL dashboard for T4 live. Since 2026-11-13, T4's and its read replica's Azure Monitor metrics reach the lakehouse history, the history model, and the Insights app's PostgreSQL page only through `POSTGRES_METRICS`, which `stop-demo.ps1 -SaveHistory` and `deploy.ps1`'s history snapshot pass ([ADR 0025](adr/0025-t4-read-replica.md#the-history)); a notebook run started in Fabric adds none. T4 isn't in the demo's Real-Time Dashboard, which reads only the SQL telemetry endpoint: since 2026-11-18 the dashboard, the control notebook's guide, and the walkthrough point to Database Hub's own real-time dashboards for PostgreSQL and Azure Cosmos DB, generally available since 2026-11-17, instead (ADR 0019's follow-up).
- **T4's smallest sizes can be unavailable:** on 2026-10-26 West US 3 refused `Standard_B1ms` (with no zone preference, then in zone 1) and `Standard_B2s` with `SkuNotAvailable` ("Specified SKU is not supported in this region") although the region's capability list included them; Learn's remedy is another size ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors)). `t4SkuName` takes `Standard_D4ds_v5` (the default since 2026-11-04, 4 vCores, about 21 times B1ms's hourly price), `Standard_D4ads_v5`, `Standard_D2ds_v5` (the documented General Purpose option the owner chose on 2026-10-26, about ten times), `Standard_B1ms` (the default before), or `Standard_B2s`, and until 2026-11-09 a size you set never changed: `deploy.ps1` (`DEPLOY.T4.SKU`) and preflight (`PREFLIGHT.T4.SKU`) reported a **Fail** that named the next option, and `t4AvailabilityZone` allowed one more try in another zone (R441). Since Phase 28, without `t4SkuName`, the run moves from B1ms to B2s by itself, and since its follow-up (2026-11-02) to General Purpose `Standard_D2ds_v5` when both are refused, after a cost check against both ceilings, saying so in its **DONE** banner; since 2026-11-09 the check only reports, and T4 is created anyway. `Standard_D2ds_v5` was created on the first try the same day (Azure placed it in zone 1). Since 2026-11-04, without `t4SkuName`, the run starts at `Standard_D4ds_v5` and, when Azure refuses it, tries another zone, then `Standard_D4ads_v5`, then `Standard_D2ds_v5` with autonomous tuning off after the cost check ([deployment](deployment.md#t4s-size-the-4-vcore-default-and-its-fallback-2026-11-04)). Since 2026-11-09 (user-directed) a size you set falls back too, to the next size Azure accepts, cheapest first, with a **Warning** that names what was tried and created and both monthly estimates; only a refusal of every size is a **Fail**. **Not proven live:** a refused `t4SkuName` and its retry in another zone.
- **T4's 4-vCore default and its autonomous tuning are unproven live (2026-11-04):** the scale of an existing T4 to `Standard_D4ds_v5` (a restart) and the move's cost check, its refusal (detected only as `SkuNotAvailable`), the zone retry and the `Standard_D4ads_v5` step, the tuning parameters, Query Store capturing the runner's `missing-index` lookups, the first recommendation's timing, and `cpu-pressure` scaled to 4 vCores are unit-tested only. An existing T4 database gets `missing-index` in its catalog (`demo.fn_scenario_catalog`) only when `deploy.ps1` sets T4 up again, and an older runner on T1 refuses `--vcores` and the showcase until `deploy.ps1` updates it ([update an existing environment](deployment.md#update-an-existing-environment)).
- **`connection-surge` past the limit is unproven live (2026-11-03):** the template now sets `max_connections` to 50 on every T4 size, and the surge fills its headroom for 5 seconds at most so a few attempts are past the limit (at most 5 refused attempts in any minute and 30 in a run; [ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-11-03-max_connections-at-50-on-every-size-and-connection-surge-past-the-limit-the-showcase)). Before that, the larger sizes' default limits (429 on B2s and 859 on D2ds_v5) were above the scenario's cap of 60 connections a wave, and on every size the overshoot only took the headroom, so `connections_failed` stayed 0. The restart that applies the new value, the refused attempts, and Database Hub's **Failed connections** on each size are unit-tested only until the owner's live check. A T4 whose new value still waits for a restart keeps its old limit (`T4.MAXCONNECTIONS` **Warning**).
- **T5, Azure Cosmos DB (since 2026-11-18, [ADR 0027](adr/0027-t5-cosmos-db.md)):**
  - **No stop:** an Azure Cosmos DB account can't be stopped or paused, and a container's throughput can't be taken away, only deleted with the container. So since 2026-11-19 T5's container exists only during a session: the stops delete it, and the starts create it again (about a minute), so between sessions T5 bills only its private endpoint and DNS zone, about $7.80 a month (dated example, 2026-11-18). That needs the session control's role to create the container again, which an Owner's `deploy.ps1` or `grant-safety-stop.ps1` gives; until then the container stays, and T5 bills its throughput every hour, $31.41 a month at list price, and the status page says so. Each session starts with an empty container, so T5's data doesn't carry over between sessions.
  - **The free tier is one account per subscription, set only at creation, and not offered to internal subscriptions:** in a subscription where another account has it, T5 is created without it and bills its throughput, and the run names that account (`DEPLOY.T5.FREETIER`); in an internal subscription ("Free tier is not supported for Internal subscriptions", live 2026-11-18), T5 is always created without it. An account created without it never gets it; deleting T5 and running `deploy.ps1` again creates it again, with the free tier only when the slot is free by then.
  - **Database Hub reads it from Azure Monitor metrics only,** at an hourly grain in its charts ([monitor Azure Cosmos DB](https://learn.microsoft.com/fabric/database/hub/monitor-cosmos-db)): a 10-minute storm shows in **Normalized RU Consumption** and **Throttled Requests** within the hour it falls in. **Avg Latency** stays empty: it charts direct-mode latency, and the runner uses the gateway (HTTPS 443 through the private endpoint). **Availability** is an hourly average. Whether the Database Agent covers Cosmos DB isn't part of the prompt pack yet.
  - **Throttling is the point:** `ru-storm` drives one partition to 100% normalized RU, so requests get 429s on purpose, and the runner counts them as the scenario's signal. Its bounded documents are deleted at its end; `reset-demo.ps1 -Target T5` removes any a stopped VM left behind.
  - **A new data-plane role can take minutes:** T1's access is checked with retries for up to 10 minutes (`WORKLOAD.T5.WARMUP`); a run that ends before it takes effect is **NOT DONE**, and the next `deploy.ps1` checks again.
  - **Not proven live yet:** a free-tier refusal at creation and its retry without it, and Defender for Azure Cosmos DB's charge in a tenant whose policy turns it on.

## Network and access

- **Egress:** NSGs can't restrict HTTPS by FQDN; a strict allow-list needs Azure Firewall, which isn't part of v1 ([ADR 0007](adr/0007-networking-modes-and-egress.md)).
- **No SQL endpoint from outside:** nothing outside the demo's virtual network reaches T1, T2, or a private T3, so Hub's **Open in SSMS** or VS Code links and the T-SQL agent skills need a Bastion session on a demo VM.
- **Default outbound access:** the VM subnets explicitly keep default outbound access, a path Microsoft is phasing out in favor of explicit methods. `outboundMode = NatGateway` is the ready alternative, at extra cost ([ADR 0017](adr/0017-outbound-access.md)).
- **Trusted Launch** is reported as incompatible with nested virtualization (Microsoft Q&A; the Trusted Launch page doesn't say either way), so the T2 host defaults to the Standard security type; one live test of a Trusted Launch host is still open ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **Tenant policies:** preflight's policy inventory reads assignments and definitions without changing them. It doesn't read exemptions or assignments scoped to resource groups, and it treats conditions it can't evaluate conservatively; the what-if check remains the backstop for denials. Large policy sets take a few minutes to read ([ADR 0012](adr/0012-validation-model.md)).
- **The Azure CLI sign-in is the operator's:** the scripts never sign in, and never change the CLI's default subscription. On a machine where other tools share the same Azure CLI configuration, isolate the demo's sign-in ([troubleshooting](troubleshooting.md#optional-isolate-the-demos-azure-cli-sign-in-on-a-shared-machine)).

## Deployment and operations

- **No artifact cache:** since 2026-10-20 every new T2 guest downloads its source again (retries resume a dropped download): in the default `JumpstartImage` mode Arc Jumpstart's 34 GiB image, from Jumpstart's public storage, and in the build modes about 6.2 GB of media from Microsoft, where a changed file at a pinned URL fails closed until `config/versions.json` is updated. A newer Jumpstart image is handled as in [targets and licensing](#targets-and-licensing).
- **Redeploy time:** measured at 38.8 minutes end to end with the parallel tracks and the golden snapshot (2026-10-22), and at 63.7 minutes with Phase 22's overlaps (2026-10-23), where T1 and T3 were ready at +26.8 minutes but T2 waited about 29.5 minutes for the SQL Server extension's download in its guest; the 30-minute target isn't met. T2's track is the critical path ([deployment](deployment.md#faster-redeploy-phase-22)). That download (R72) varies from about 2 minutes to about 40. Both runs predate `JumpstartImage`: they restored a `PaygWizard` guest from its golden snapshot.
- **`JumpstartImage` is measured once:** a clean first deployment ended **DONE** in 91 minutes on 2026-11-06 (West US 3, `lowest-cost`), of which T2's host build, with the image's download and first boot, took about 27 minutes and its Arc onboarding about 33. One run is one sample: the download is bound by the T2 host's disk (about 11 minutes for 34.1 GiB, about 51 MiB/s, on `Standard_E2s_v5` with an E10 Standard SSD), and a resumed download isn't seen live yet. `DEPLOY.TIMING` records each run.
- **Bootstrap bundle in Run Command chunks:** Learn documents no size limit for an inline Run Command script. Chunks are 512 KiB of data by default, the largest size proven live, and each chunk takes one Run Command round trip ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **Run Commands need a running VM, and policy extensions can hold them:** a deallocated VM answers `OperationNotAllowed`, and a policy-driven `MDE.Windows` update held one VM's Run Commands for about 10 minutes (R49). Since Phase 28 the tracks wait for a new VM's extensions to settle and restart a stuck VM once, but a policy's extension that never finishes still ends a run **NOT DONE**, naming it.
- **No deployment needs a person at T2 since 2026-11-09:** the guided stop of a first `PaygWizard` run (Phase 28), about 10 minutes for the Bastion sign-in, the pay-as-you-go and Standard choices, and setup's Azure sign-in, is retired with that mode. While the guest's one automatic sign-in that an earlier guided stop armed is left, a security scan of the guest would flag it; the T2 host turns it off at its next pass ([ADR 0009](adr/0009-secrets-handling.md#phase-28-amendment-the-guests-one-automatic-sign-in-and-the-portal-password-reset-2026-10-29)).
- **Keeping the machine awake works on Windows only:** `deploy.ps1` keeps a Windows PC and its display awake, but not through a closed lid or a shutdown; on macOS and Linux it changes nothing. A GitHub codespace stops after its idle timeout (30 minutes by default, reset by terminal output) and always after 12 hours ([GitHub Docs](https://docs.github.com/codespaces/setting-your-user-preferences/setting-your-timeout-period-for-github-codespaces)); `./scripts/deploy.ps1` then continues where it stopped.
- **The subscription's automation can switch a deallocated VM's disks to Standard HDD:** on 2026-10-24 an application identity that isn't the demo's changed both OS disks from Standard SSD (E10) to Standard HDD while the VMs were deallocated. Boots and IO are then slower, and IO-heavy scenarios (`io-pressure`, the T2 guest's VHDX) look worse than the profile intends. Azure doesn't change an OS disk's type through its VM, so `deploy.ps1` keeps each drifted disk's current type and carries on with the `DEPLOY.DISKS.DRIFT` **Warning**, and `status.ps1` reports it (`STATUS.DISKS`). The demo doesn't change the disks back: that's the subscription owner's call, and the automation can switch them again ([change a disk's type](https://learn.microsoft.com/azure/virtual-machines/disks-convert-types), R440).
- **Validation while the demo is stopped:** a deallocated VM can't run a Run Command and shows empty instance views, so `validate.ps1` reports every check that needs it as a Warning to start the VM, including the secret scan of Run Command instance views. Validation's T3 checks that run through T1 resume a paused T3, which then bills until it auto-pauses again ([ADR 0012](adr/0012-validation-model.md)).
- **Telemetry:** 3–15 minutes of latency and retention of 7 days or less. T3 kept sending telemetry while its serverless database reported `Paused` (2026-10-21), so a fresh T3 sample doesn't prove the database is awake.
- **SQL Server CPU in the telemetry:** `AvgCPUPercent`, which the telemetry article calls the primary CPU signal, was 0 in every T1 and T2 sample on 2026-10-23, while `SQLProcessCPUPercent` reached 99 and 97. It's intermittent (*observed 2026-11-04*): during a T2 `cpu-pressure` incident at intensity 8, `arcsql01`'s `SqlServerCPUUtilization` had `AvgCPUPercent` at most 81 from 14:36 to 14:46 UTC (`SQLProcessCPUPercent` at most 86, 84 on average), then at most 0 from 14:46 to 14:56 (`SQLProcessCPUPercent` at most 88); T3's `AvgCPUPercent` reached 99.9 in the same run, and T1's `Processes blocked` 6.
- **T1's monitoring plugin right after a cold start:** the SQL IaaS Agent extension's instance view can still hold the status from before the stop (live, 2026-11-04: Running and OK a minute after the start, NotRunning 12 minutes later, and no T1 telemetry). Since that day the control's runbooks, `start-demo.ps1`, and `deploy.ps1` count only a status whose `MainServiceLastReportedTime` is later than the VM's start, wait up to 8 minutes for one, and restart the agent once when none comes. Unproven live: how often the agent reports that time; an agent that doesn't report it gets one restart after 8 minutes on a cold start. Since Phase 25b, the live-activity notebook and the Real-Time Dashboard read `SQLProcessCPUPercent` for T1 and T2 and `AvgCPUPercent` for T3; history saved before that keeps 0 for T1's and T2's CPU, and what Database Hub's own Performance page shows for them isn't documented.
- **Scenario bounds:** a database runs one Running run per scenario and four in all (`demo.usp_run_begin`'s errors 50108 and 50109), so a foreground `run` of a scenario that an activity profile is already running is refused; the profile host waits for a run of the same scenario that's still ending, ends the runs an earlier host on the machine left Running without sessions (after a task restart), and tries a refused activity again every 30 seconds, at most 40 times, within its window. T3's `GP_S_Gen5_1` allows 75 concurrent workers and 75 concurrent logins ([resource limits](https://learn.microsoft.com/azure/azure-sql/database/resource-limits-vcore-single-databases)), and the catalog has no T3-specific concurrency cap, so keep overlapping T3 runs to about 60 sessions in all (Phase 25a ran 33). `locking-blocking`'s contenders wait at most 20 seconds per attempt, so its longest single wait is about 20 seconds; `blocking-chain` gives waits of up to 60 seconds and deeper chains ([ADR 0010](adr/0010-workload-generator-technology.md#phase-25b-the-profile-hosts-lanes-and-supervisor-and-the-bounds-phase-25a-met-2026-10-26)).
- **The Phase 25b scenarios by target:** `parallel-scans` runs serially on SQL Server Express, so it shows CPU waits there, not Parallelism waits. It ran serially on T3 too, at 1 vCore; T3's 2-vCore maximum since 2026-11-18 allows DOP 2, not yet seen live, so the parallel plan is confirmed on T1 and T2 only. `blocking-chain` doesn't escalate on T3, which always uses [optimized locking](https://learn.microsoft.com/sql/relational-databases/performance/optimized-locking): its links wait on transaction-ID locks there. The telemetry has no chain depth or blocker tree (`Processes blocked` counts blocked sessions), so the skills prompts read them from the database. `Log Flushes/sec` is a SQL Server counter, so on T3 `log-flush-waits` shows only as waits ([scenarios](../scenarios/README.md)).
- **The profile host restarts its own lanes, not itself:** a lane that stops finishing its polls is replaced after 5 minutes, so a stall can delay a profile change by about 5 minutes; a hung host process isn't restarted by anything but the next boot or a task restart, and `WORKLOAD.<target>.HOST` and `status.ps1` report it as a **Fail** while a profile is active.
- **Notebooks:** need a running F or Trial capacity, can't call Azure Resource Manager, and use a `kusto` token path to the telemetry endpoint that isn't documented. It worked on 2026-10-21, and the printed-KQL fallback stays ([ADR 0014](adr/0014-notebook-role-and-capacity.md)).
- **Deploy to Azure button:** it provisions infrastructure only; the VM bootstraps start on `deploy.ps1 -Resume`, so `./scripts/deploy.ps1` stays the one path to a whole demo ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **License terms:** in the build modes, the unattended guest build and SQL Server setup accept the Windows Server evaluation and SQL Server license terms on the operator's behalf. The default `JumpstartImage` guest comes with both already installed in Jumpstart's image ([targets and licensing](#targets-and-licensing)).
- **Mirroring:** not part of v1 ([ADR 0015](adr/0015-mirroring-deferral.md)).

## The on-demand activity control

The session control (formerly the on-demand activity control) is part of every deployment since 2026-11-14: one Run all in `NB_DatabaseHub_Control` runs a whole session ([ADR 0026](adr/0026-one-run-all-session.md); [ADR 0020](adr/0020-on-demand-activity-control.md) before).

- **Its roles need an Owner once per environment,** and again after a destroy and redeploy: two custom roles and four assignments (A1 to A4). `deploy.ps1` grants them when you're an Owner or User Access Administrator; otherwise an Owner runs `./scripts/grant-safety-stop.ps1` once. Until then, Run all can't start a session, T5's container stays between sessions, and `./scripts/start-demo.ps1` runs a session from your PC with Contributor ([permissions](permissions.md#the-on-demand-activity-control)).
- **Where a policy makes new vaults private, its notebook starts slowly:** it lives in its own workspace, for example "Database Hub Demo Control" (`control.fabricWorkspaceName`), whose managed private endpoint turns off starter pools, so each Spark session takes 3 to 5 minutes to start ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)).
- **The folder uses a preview API:** Folders - Create Folder is documented as a preview; when it fails, the notebook goes in the workspace's root with a Warning.
- **The activity starts minutes after the request:** the runbook starts the VMs when they're stopped (about 2 to 5 minutes), and Run Command under load waited up to 654 seconds in Phase 25a; telemetry then shows the activity 3 to 15 minutes later. The notebook's live view says when nothing has arrived yet.
- **The webhook expires** after 90 days by default; `setup-activity-control.ps1 -RotateWebhook` replaces it, and `status.ps1` warns 14 days before.
- **The webhook URL is a bearer secret:** whoever has it can start a bounded run or session, one at a time, within the allow-lists and caps. The vault has no data-plane logs ([security model](security-model.md#the-on-demand-activity-control-phase-25c)).
- **A new scenario reaches the runbook only after the next `./scripts/deploy.ps1`,** which republishes the runbooks (`CONTROL.RUNBOOKS`): their allow-lists are the scenario catalog at the time they were published.
- **`start-demo.ps1` replaces a pending auto-stop with its own** (since 2026-11-19; before, it cancelled a notebook run's, and the VMs then ran until `stop-demo.ps1` or the nightly auto-shutdown): the session stops by itself `-Hours` after the start (4 by default), and `START.CONTROL.AUTOSTOP` gives that time. A run's stop job that's already queued or running is waited for, up to 10 minutes, and never stopped (`START.CONTROL.STOPJOB`). When the auto-stop can't be replaced, or the stop job is still running after the wait or can't be read, the start carries on, and the Warning says when the VMs may deallocate and what to do. Without the session control's role (A1) nothing is scheduled, and the nightly stop is the limit.
- **A Run all whose notebook still follows its session sends its own stop at its session's end,** as before 2026-11-19: the notebook can't read Azure Resource Manager, and its end and its **Stop now** send the runbook the same request, so when a later `start-demo.ps1` replaced that session's auto-stop with its own, the notebook still stops the demo at the end it planned. Its auto-stop schedule, which `start-demo.ps1` replaced, no longer does. Run `./scripts/start-demo.ps1` again after that end, or start the local session after the notebook's.
- **The stop at the end of an update can still cut off a session that starts while the VMs deallocate** (since 2026-11-19): it reads whether a session uses the demo before its wait, after it, before its first change, and before T2's guest and the VMs, but neither Run all nor `start-demo.ps1` waits for it. A session that starts in those last seconds gets a **Warning** in `DEPLOY.ENDSTOP` with how to start it again, never silence. Ctrl+C during the stop leaves running what it hadn't stopped, and the row says so.
- **An update's stop at its end waits at most 15 minutes** for work that still needs the hosts (a bootstrap pass, T2's first migration assessment); what doesn't finish goes on at the next start, or at the next `deploy.ps1` or `configure-arc.ps1`.

## Cost

- **Defender for Cloud cost:** Defender plans that tenant policies enforce add cost that the demo can't turn off. Billing for a disconnected Arc SQL instance isn't documented (up to $14.52 a month more, dated example 2026-10-21), and the new Defender Workload Unit meters may change how the invoice shows Defender ([cost management](cost-management.md)).
- **Outside the ceiling:** the Fabric capacity, which the notebooks need running and which bills by the hour until you or its administrator pause it ([cost management](cost-management.md#microsoft-fabric-capacity)); Fabric and Power BI licenses; and each viewer's GitHub Copilot plan, which Ask's questions use.
- **Premium SSD v2** needs a zonal VM, so `demo-day` and `enhanced-performance` use it only when `zone` is set; otherwise their data disks use Standard SSD (E10), and Premium SSD (P10) only as a `dataDiskSku` opt-in ([ADR 0016](adr/0016-cost-profiles.md)).
- **`lowest-cost` has no data disks:** SQL Server data on T1 and the guest's VHDX (and, in the build modes, its media) on the T2 host share the 128 GiB OS disks. The host fails the build early with a clear message if `C:` has too little free space: about 80 GB in the build modes, and about 64 GiB in `JumpstartImage` mode (the 34 GiB image, 20 GiB for it to grow, and a 10 GiB margin). The Jumpstart guest's disk is dynamic, with a 100 GiB maximum that the 128 GiB OS disk can't hold fully grown, so `status.ps1` warns early, when less than 20 GiB is free (`STATUS.T2.DISKSPACE` **Warning**, with the fix). Set `dataDiskSku` to `E10` to add data disks ([ADR 0016](adr/0016-cost-profiles.md)). Switching an existing deployment to `None` detaches its data disks but doesn't delete them, so they keep billing until you delete them.
