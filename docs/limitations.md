# Known limitations

What the demo can't do, what depends on a preview, and what isn't proven yet. Each item links to the decision or risk behind it. The acceptance status of every criterion is in the [final report](implementation-report.md#final-report).

## Preview disclosures

- **What's in preview:** Microsoft Fabric Database Hub, its Database Agent and Copilot experience, SQL Server on Azure VM performance monitoring, unified inventory, the Arc SQL monitoring setting (API version `2023-09-01-preview`), and the SQL telemetry endpoint. Their behavior, prerequisites, labels, schemas, and APIs can change without notice.
- **What the repo does about it:** it uses only documented interfaces, never calls Database Hub's private routes, validates prerequisites and signals instead of promising outcomes, and gives every preview-dependent step a fallback ([ADR 0013](adr/0013-agent-experience.md), [troubleshooting](troubleshooting.md#fallbacks-at-a-glance)).
- **No Hub API:** saved views, the **Enable Performance Monitoring** button, monitor templates, and the Database Agent are UI-only. The demo validates through Azure Resource Graph and the documented telemetry endpoint, and the Hub UI check stays **Manual action required**.
- **Database Agent coverage:** its supported targets, prerequisites, permissions, entry point, and latency aren't documented. Every incident can run on any target, the [walkthrough](demo-walkthrough.md) has fallbacks, and the live coverage record waits for the owner's rehearsal ([ADR 0013](adr/0013-agent-experience.md)).
- **Never promised:** the demo describes the signals to look for, never the AI's answers, and every action an agent proposes needs human approval.

## Targets and licensing

- **Editions:** Developer, Express, and Evaluation editions can't drive Hub Performance. `t2SqlInstallMode = Developer` gives T2 Estate only ([ADR 0006](adr/0006-sql-editions-and-licensing.md)).
- **One manual step per T2 guest build** in the default `PaygWizard` mode: pay-as-you-go without a product key is documented only in the setup wizard. The wizard needs **Use Azure Login** (never a service principal secret), an Internet Explorer-based sign-in window, so the host turns IE Enhanced Security Configuration off for administrators in the guest while the step is open and back on after, and installs the WebView2 runtime first (`GuestWebView2`). `ProductKey` mode (P10) avoids the step.
- **Setup's interactive sign-in can leave sign-in data on the VM:** in `PaygWizard` mode, the scripts remove it right after the wizard and verify that none remains, and the build fails if any remains (R74; [risk register](implementation-report.md#risk-register)). `Developer` mode or a product key avoids that sign-in.
- **Without `assignRoles`, Arc onboarding uses your token:** a Contributor-only caller can't create the host identity's role assignment, so `configure-arc.ps1` passes your Azure Resource Manager token, valid for about an hour. Run Command hands it to the host's PowerShell as an argument; the scripts remove what's left of it on the VMs, but endpoint protection can record that command line off the VM, where they can't (ADR 0009).
- **Evaluation guest OS:** the Windows Server 2022 Evaluation guest expires 180 days after it's built; the owner's guest, built on 2026-10-20, expires about 2027-04-18. `reset-demo.ps1 -RebuildGuest` reports **Not supported** (R196), so a rebuild is `destroy.ps1` followed by `deploy.ps1`, which repeats the wizard step. Licensing of Windows guests in nested Hyper-V on Azure isn't documented (R21).
- **Arc pay-as-you-go lapse:** a T2 host left deallocated for more than 30 days breaks Arc pay-as-you-go authorization. `status.ps1` warns at 21 and 28 days.
- **Arc on a nested guest** isn't explicitly documented. It worked live: onboarding, the Azure extension for SQL Server, monitoring, Estate, and telemetry from the nested guest (2026-10-20 and 2026-10-21). The opt-in **evaluation-only** fallback stays for hosts without nested virtualization.
- **Extension delivery is slow in the guest:** the Azure extension for SQL Server was slow to arrive in the live run, because downloads from `<region>.his.arc.azure.com` failed intermittently with "certificate verify failed" (R72). A golden restore reinstalls the extensions, so this sits on T2's path: in the quarantine test on 2026-10-22, the fresh onboarding took 45 minutes, most of it the extension's download retries.
- **Restoring a pay-as-you-go install is validated only empirically:** pay-as-you-go SQL Server activated in the setup wizard, then copied with the T2 host's disk (the golden snapshot, [ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)), isn't explicitly documented. After every restore the T2 checks verify Standard edition, license type PAYG, and monitoring before T2 counts as ready; the quarantine test (2026-10-22) and the redeploy showed all three.
- **The golden snapshot ages:** the guest's Windows evaluation keeps counting inside it (the owner's guest: about 2027-04-19). `status.ps1` and preflight warn at 30 and 7 days; after that, the redeploy builds T2 again, which needs the setup-wizard step and a new capture ([cleanup](cleanup.md), [deployment](deployment.md)).
- **The golden snapshot's access can't be narrowed under Contributor:** the guardrail asked to keep it to the deploying identity, but without role assignments ([ADR 0008](adr/0008-identity-rbac-abac.md)) any Contributor on the subscription can create a disk from it. `DenyAll` still blocks export for everyone ([security model](security-model.md)).
- **T1's associated services:** the Marketplace image installs Analysis Services and Integration Services. T1's `AssociatedServices` step uninstalls them, so unified inventory lists only the engine (live, 2026-10-21). Inventory drops them only after the SQL IaaS Agent discovers the instances again: about 6 minutes after a restart, but 46 to 72 minutes without one (the parallel redeploy, 2026-10-22), so the step now restarts the agent, and `deploy.ps1`'s validation fails while they're still listed after 10 minutes.
- **T1's monitoring after a deallocation:** after `sqlvm01` was deallocated and started, the SQL IaaS Agent reported its monitoring plugin (`DatabaseMonitorArcPlugin`) NotRunning for more than 90 minutes, so T1 sent no Database Hub telemetry; restarting the agent's service (`SQLIaaSExtension`) fixed it within a minute (live, 2026-10-22). `start-demo.ps1` checks the plugin and restarts the service only when it isn't running (`START.T1.MONITORING`). After a start by other means (the portal, `az vm start`, or the auto-start of a schedule that doesn't use `start-demo.ps1`), run `start-demo.ps1`, which leaves running VMs as they are and does the same check.
  - **A restart right after boot can come too early (live, 2026-10-26):** `start-demo.ps1` restarted the service about a minute after the guest booted, before the plugin had reported any status; the plugin then stayed NotRunning for almost three hours (`START.T1.MONITORING` **Warning**), and `TELEMETRY.T1` failed in two deploys. The same restart run again later, with the VM up, had the plugin Running with uploads OK in 144 seconds and T1's telemetry back within a minute. Since Phase 25b, `start-demo.ps1` first waits up to 5 minutes for the agent to report the plugin's status, restarts the service only when the plugin isn't Running or still has no status, and then waits up to 5 minutes for Running and uploads OK, so a start can take up to about 10 minutes longer when the plugin doesn't come back by itself. If `START.T1.MONITORING` is still a **Warning**, run `start-demo.ps1` again a few minutes later; it repeats the check and the restart (R442).

- **T4 in Database Hub is metrics only:** Hub's PostgreSQL monitoring "uses existing Azure Monitor metrics and doesn't provide query-level diagnostics", and Estate lists the flexible server, not its databases ([monitor PostgreSQL](https://learn.microsoft.com/fabric/database/hub/monitor-postgresql)). T4's sessions, waits, and blockers come from the runner (`status.ps1 -Detail`, `ContosoCare.Workload status --target T4`); whether the Database Agent covers PostgreSQL isn't documented ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md)).
- **A stopped T4 starts on its own after seven days** and then bills compute until it's stopped again ([stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server)). `status.ps1` says when, and the cost estimate counts the worst case, until Phase 25c's scheduled daily safety stop covers it. While stopped, it rejects every management operation except start, so `deploy.ps1` starts it before the template.
- **No Query Store on T4:** Learn says not to enable it on the Burstable tier ([Query Store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)), so T4 has no query history; enhanced metrics (free) are on instead. It stays off on the General Purpose option too, so every size has the same configuration.
- **The notebook can't read T4:** `notebookutils` has no Azure Resource Manager or Azure Database for PostgreSQL token, and T4 has no public endpoint, so the live-activity notebook links to Hub's PostgreSQL dashboard instead. T4 isn't in the lakehouse history, the report, the Insights app, or the Real-Time Dashboard (follow-ups in ADR 0019).
- **T4's smallest sizes can be unavailable:** on 2026-10-26 West US 3 refused `Standard_B1ms` (with no zone preference, then in zone 1) and `Standard_B2s` with `SkuNotAvailable` ("Specified SKU is not supported in this region") although the region's capability list included them; Learn's remedy is another size ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors)). `t4SkuName` takes `Standard_B1ms` (default), `Standard_B2s` (the documented fallback), or `Standard_D2ds_v5` (the documented General Purpose option the owner then chose, about ten times B1ms's hourly price), and a size you set never changes: `deploy.ps1` (`DEPLOY.T4.SKU`) and preflight (`PREFLIGHT.T4.SKU`) report a **Fail** that names the next option, and `t4AvailabilityZone` allows one more try in another zone (R441). Since Phase 28, without `t4SkuName`, the run moves from B1ms to B2s by itself and finishes without T4 when both are refused, saying so in its **DONE** banner; it never picks a General Purpose size. `Standard_D2ds_v5` was created on the first try the same day (Azure placed it in zone 1).
- **`connection-surge` doesn't reach the limit on the larger sizes:** each wave holds at most the scenario's `maxConnections` (60 by default, 400 at most), and the default `max_connections` is 50 on B1ms but 429 on B2s and 859 on D2ds_v5 ([limits](https://learn.microsoft.com/azure/postgresql/configure-maintain/concepts-limits)). On those sizes the surge shows as many idle connections, without refused ones (`connections_failed` stays 0).

## Network and access

- **Egress:** NSGs can't restrict HTTPS by FQDN; a strict allow-list needs Azure Firewall, which isn't part of v1 ([ADR 0007](adr/0007-networking-modes-and-egress.md)).
- **No SQL endpoint from outside:** nothing outside the demo's virtual network reaches T1, T2, or a private T3, so Hub's **Open in SSMS** or VS Code links and the T-SQL agent skills need a Bastion session on a demo VM.
- **Default outbound access:** the VM subnets explicitly keep default outbound access, a path Microsoft is phasing out in favor of explicit methods. `outboundMode = NatGateway` is the ready alternative, at extra cost ([ADR 0017](adr/0017-outbound-access.md)).
- **Trusted Launch** is reported as incompatible with nested virtualization (Microsoft Q&A; the Trusted Launch page doesn't say either way), so the T2 host defaults to the Standard security type; one live test of a Trusted Launch host is still open ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **Tenant policies:** preflight's policy inventory reads assignments and definitions without changing them. It doesn't read exemptions or assignments scoped to resource groups, and it treats conditions it can't evaluate conservatively; the what-if check remains the backstop for denials. Large policy sets take a few minutes to read ([ADR 0012](adr/0012-validation-model.md)).
- **The Azure CLI sign-in is the operator's:** the scripts never sign in, and never change the CLI's default subscription. On a machine where other tools share the same Azure CLI configuration, isolate the demo's sign-in ([troubleshooting](troubleshooting.md#optional-isolate-the-demos-azure-cli-sign-in-on-a-shared-machine)).

## Deployment and operations

- **No artifact cache:** since 2026-10-20 every guest build downloads about 6.2 GB of media from Microsoft again (retries resume a dropped download), and a changed file at a pinned URL fails closed until `config/versions.json` is updated.
- **Redeploy time:** measured at 38.8 minutes end to end with the parallel tracks and the golden snapshot (2026-10-22), and at 63.7 minutes with Phase 22's overlaps (2026-10-23), where T1 and T3 were ready at +26.8 minutes but T2 waited about 29.5 minutes for the SQL Server extension's download in its guest; the 30-minute target isn't met. T2's track is the critical path ([deployment](deployment.md#faster-redeploy-phase-22)). That download (R72) varies from about 2 minutes to about 40.
- **Bootstrap bundle in Run Command chunks:** Learn documents no size limit for an inline Run Command script. Chunks are 512 KiB of data by default, the largest size proven live, and each chunk takes one Run Command round trip ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md)).
- **Run Commands need a running VM, and policy extensions can hold them:** a deallocated VM answers `OperationNotAllowed`, and a policy-driven `MDE.Windows` update held one VM's Run Commands for about 10 minutes (R49). Since Phase 28 the tracks wait for a new VM's extensions to settle and restart a stuck VM once, but a policy's extension that never finishes still ends a run **NOT DONE**, naming it.
- **A first `PaygWizard` run needs a person once** (Phase 28): about 10 minutes, about 60 to 90 minutes after the start (an estimate), for the Bastion sign-in, the pay-as-you-go and Standard choices, and setup's Azure sign-in. No assistant can do those sign-ins; `ProductKey` mode is fully unattended. While the step is armed, the guest signs itself in once, so a security scan of the guest at that moment would flag automatic sign-in ([ADR 0009](adr/0009-secrets-handling.md#phase-28-amendment-the-guests-one-automatic-sign-in-and-the-portal-password-reset-2026-10-29)).
- **Keeping the machine awake works on Windows only:** `deploy.ps1` keeps a Windows PC and its display awake, but not through a closed lid or a shutdown; on macOS and Linux it changes nothing. A GitHub codespace stops after its idle timeout (30 minutes by default, reset by terminal output) and always after 12 hours ([GitHub Docs](https://docs.github.com/codespaces/setting-your-user-preferences/setting-your-timeout-period-for-github-codespaces)); `./scripts/deploy.ps1` then continues where it stopped.
- **The subscription's automation can switch a deallocated VM's disks to Standard HDD:** on 2026-10-24 an application identity that isn't the demo's changed both OS disks from Standard SSD (E10) to Standard HDD while the VMs were deallocated. Boots and IO are then slower, and IO-heavy scenarios (`io-pressure`, the T2 guest's VHDX) look worse than the profile intends. Azure doesn't change an OS disk's type through its VM, so `deploy.ps1` keeps each drifted disk's current type and carries on with the `DEPLOY.DISKS.DRIFT` **Warning**, and `status.ps1` reports it (`STATUS.DISKS`). The demo doesn't change the disks back: that's the subscription owner's call, and the automation can switch them again ([change a disk's type](https://learn.microsoft.com/azure/virtual-machines/disks-convert-types), R440).
- **Validation while the demo is stopped:** a deallocated VM can't run a Run Command and shows empty instance views, so `validate.ps1` reports every check that needs it as a Warning to start the VM, including the secret scan of Run Command instance views. Validation's T3 checks that run through T1 resume a paused T3, which then bills until it auto-pauses again ([ADR 0012](adr/0012-validation-model.md)).
- **Telemetry:** 3–15 minutes of latency and retention of 7 days or less. T3 kept sending telemetry while its serverless database reported `Paused` (2026-10-21), so a fresh T3 sample doesn't prove the database is awake.
- **SQL Server CPU in the telemetry:** `AvgCPUPercent`, which the telemetry article calls the primary CPU signal, was 0 in every T1 and T2 sample on 2026-10-23, while `SQLProcessCPUPercent` reached 99 and 97. Since Phase 25b, the live-activity notebook and the Real-Time Dashboard read `SQLProcessCPUPercent` for T1 and T2 and `AvgCPUPercent` for T3; history saved before that keeps 0 for T1's and T2's CPU, and what Database Hub's own Performance page shows for them isn't documented.
- **Scenario bounds:** a database runs one Running run per scenario and four in all (`demo.usp_run_begin`'s errors 50108 and 50109), so a foreground `run` of a scenario that an activity profile is already running is refused; the profile host waits for a run of the same scenario that's still ending, ends the runs an earlier host on the machine left Running without sessions (after a task restart), and tries a refused activity again every 30 seconds, at most 40 times, within its window. T3's `GP_S_Gen5_1` allows 75 concurrent workers and 75 concurrent logins ([resource limits](https://learn.microsoft.com/azure/azure-sql/database/resource-limits-vcore-single-databases)), and the catalog has no T3-specific concurrency cap, so keep overlapping T3 runs to about 60 sessions in all (Phase 25a ran 33). `locking-blocking`'s contenders wait at most 20 seconds per attempt, so its longest single wait is about 20 seconds; `blocking-chain` gives waits of up to 60 seconds and deeper chains ([ADR 0010](adr/0010-workload-generator-technology.md#phase-25b-the-profile-hosts-lanes-and-supervisor-and-the-bounds-phase-25a-met-2026-10-26)).
- **The Phase 25b scenarios by target:** `parallel-scans` runs serially on T3 (1 vCore or less) and on SQL Server Express, so it shows CPU waits there, not Parallelism waits; the parallel plan (DOP 2) is expected on T1 and T2 only. `blocking-chain` doesn't escalate on T3, which always uses [optimized locking](https://learn.microsoft.com/sql/relational-databases/performance/optimized-locking): its links wait on transaction-ID locks there. The telemetry has no chain depth or blocker tree (`Processes blocked` counts blocked sessions), so the skills prompts read them from the database. `Log Flushes/sec` is a SQL Server counter, so on T3 `log-flush-waits` shows only as waits ([scenarios](../scenarios/README.md)).
- **The profile host restarts its own lanes, not itself:** a lane that stops finishing its polls is replaced after 5 minutes, so a stall can delay a profile change by about 5 minutes; a hung host process isn't restarted by anything but the next boot or a task restart, and `WORKLOAD.<target>.HOST` and `status.ps1` report it as a **Fail** while a profile is active.
- **Notebooks:** need a running F or Trial capacity, can't call Azure Resource Manager, and use a `kusto` token path to the telemetry endpoint that isn't documented. It worked on 2026-10-21, and the printed-KQL fallback stays ([ADR 0014](adr/0014-notebook-role-and-capacity.md)).
- **Deploy to Azure button:** works only once the repo is public. Until then, use `deploy.ps1` or GitHub Actions. It provisions infrastructure only; the VM bootstraps start on `deploy.ps1 -Resume`.
- **License terms:** the unattended guest build and SQL Server setup accept the Windows Server evaluation and SQL Server license terms on the operator's behalf.
- **Mirroring:** not part of v1 ([ADR 0015](adr/0015-mirroring-deferral.md)).

## The on-demand activity control

Optional, off by default ([ADR 0020](adr/0020-on-demand-activity-control.md)).

- **It needs an Owner once,** for its one custom role and three assignments, and again for A1 after each redeploy unless `assignRoles` is true. Contributor-only deployers use `demo-control.ps1` instead ([permissions](permissions.md#the-on-demand-activity-control)).
- **Where a policy makes new vaults private, its notebook starts slowly:** it lives in its own "DBHub Control" workspace, whose managed private endpoint turns off starter pools, so each Spark session takes 3 to 5 minutes to start ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)).
- **The folder uses a preview API:** Folders - Create Folder is documented as a preview; when it fails, the notebook goes in the workspace's root with a Warning.
- **The activity starts minutes after the request:** the runbook starts the VMs when they're stopped (about 2 to 5 minutes), and Run Command under load waited up to 654 seconds in Phase 25a; telemetry then shows the activity 3 to 15 minutes later. The notebook's live view says when nothing has arrived yet.
- **The webhook expires** after 90 days by default; `setup-activity-control.ps1 -RotateWebhook` replaces it, and `status.ps1` warns 14 days before.
- **The webhook URL is a bearer secret:** whoever has it can start a bounded run, one at a time, within the allow-lists and caps. The vault has no data-plane logs ([security model](security-model.md#the-on-demand-activity-control-phase-25c)).
- **A new scenario reaches the runbook only after setup runs again:** the runbook's allow-lists are the scenario catalog at the time `setup-activity-control.ps1` published it.
- **`start-demo.ps1` cancels a notebook run's pending auto-stop,** because a local session takes over, so the VMs then run until `stop-demo.ps1` or the nightly auto-shutdown; a Warning (`START.CONTROL.AUTOSTOP`) gives that time. A run's stop job that's already queued or running is waited for, up to 10 minutes, and never stopped (`START.CONTROL.STOPJOB`). When the auto-stop can't be cancelled, or the stop job is still running after the wait or can't be read, the start carries on, and the Warning says when the VMs may deallocate and what to do.
- **T4 comes with Phase 24:** the runbook and the safety stop handle `pgflex01-<deploymentId>`, and the catalog lists T4 for the notebook once Phase 24's scenarios do.

## Cost

- **Defender for Cloud cost:** Defender plans that tenant policies enforce add cost that the demo can't turn off. Billing for a disconnected Arc SQL instance isn't documented (up to $14.52 a month more, dated example 2026-10-21), and the new Defender Workload Unit meters may change how the invoice shows Defender ([cost management](cost-management.md)).
- **The Fabric capacity is outside the ceiling:** the notebooks need it running, and it bills by the hour until its administrator pauses it ([cost management](cost-management.md#microsoft-fabric-capacity)).
- **Premium SSD v2** needs a zonal VM, so `demo-day` and `enhanced-performance` use it only when `zone` is set; otherwise their data disks use Standard SSD (E10), and Premium SSD (P10) only as a `dataDiskSku` opt-in ([ADR 0016](adr/0016-cost-profiles.md)).
- **`lowest-cost` has no data disks:** SQL Server data on T1 and the guest's VHDX and media on the T2 host share the 128 GiB OS disks. The host fails the build early with a clear message if `C:` has less than about 80 GB free; set `dataDiskSku` to `E10` to add data disks ([ADR 0016](adr/0016-cost-profiles.md)). Switching an existing deployment to `None` detaches its data disks but doesn't delete them, so they keep billing until you delete them.

## Presentation layer

The Real-Time Dashboard and the template-wizard beat are Phase 18; the Power BI report is Phase 19, and the Fabric app (the Insights app) is Phase 19b ([presentation](presentation.md)).

- **Viewer licensing:** on Fabric capacities smaller than F64, everyone who views Power BI content, such as the history report (Phase 19), needs Pro, PPU, or an individual trial, and the Fabric app (Phase 19b) reads the same model as the viewer, so plan the same for it (TODO(verify)); the demo workspace's capacity is an F16 (P11, [presentation](presentation.md#licensing-and-permissions)). Database Hub and the Real-Time Dashboard aren't Power BI content, and a presenter sharing their screen needs nothing more. `PREFLIGHT.FABRIC.VIEWERLICENSE` warns about it.
- **Real-Time Dashboard:** its viewers need Reader on the subscription (and the Arc telemetry role when they're only Readers), because it queries the telemetry endpoint as each viewer. Its definition uses schema version 52 from Learn's example; the dashboard schema has no theme property, so a dark theme can't be set; and Database Hub's template wizard that makes a similar dashboard is UI-only ([Real-Time Dashboard](../fabric/realtime/README.md#limitations)).
- **The Insights app (Phase 19b):** Fabric Apps is a preview ([overview](https://learn.microsoft.com/fabric/apps/overview)), available only in [supported regions](https://learn.microsoft.com/fabric/apps/region-availability) (the demo's West US 3 capacity is one). Open it from its workspace item: opening its hosted URL directly stops at "Page not accessible directly" ([the app's guide](../fabric/app/README.md#known-limitation-the-hosted-url)). There's no CI deploy by default, because the Rayfin CLI's service principal sign-in isn't supported yet; an operator signs in once (P14). It uses the workspace capacity's units, outside the demo's ceiling. The CLI can't call the deployed connector (it needs an app session), so the in-app path is checked in the browser, by a person.
- **The Insights app labels four incident families:** IO, CPU, blocking, and log rate. Incident windows that the live-activity notebook finds for the Phase 25b wait families (`latch`, `memory`, `parallelism`, `tran_log`, `network`, and `deadlock`) show their raw family name on the Incidents page, and the replay plots their total wait time rather than their own signal. Their labels and signals are a follow-up.

Phase 22 destroyed and redeployed it twice more on 2026-10-23, with full validation and a second `deploy.ps1` ([implementation report](implementation-report.md#phase-22-faster-redeploy-the-follow-up-overlaps-and-one-timed-destroy-and-redeploy)); on a new `sqlvm01`, that redeploy also ran the `AssociatedServices` step's SQL IaaS Agent restart right after a fresh uninstall (`bfa6b2d`), and unified inventory listed only the database engine at the validation, about 41 minutes later. Still not proven live:

- Phase 22's overlaps on their failure paths (a failed template handed over to the waiting tracks, and the early T3 setup run again, `DEPLOY.T3.EARLYSETUP`): unit-tested with mocks; the measured run took the success path;
- the Fabric app's browser check of its Database Agent prompts (`FABRIC.APP.BROWSER`), which the owner does;
- the Database Hub UI and the Database Agent, which the owner rehearses;
- an end-to-end run with an identity that holds only Contributor (R210);
- T4 (Phase 24): proven live on 2026-10-26 on the General Purpose option (`Standard_D2ds_v5`): the template's server and its redeploy, T1's sign-in as the P6 group's role with its managed identity (R401), the runner's role and grants, each T4 scenario once with `reset`, Estate in Resource Graph, the metrics Hub's PostgreSQL dashboard charts, and the stop and start. Not proven live: `capacity-max` reaching T2's disk (its 4 GB scratch set stayed in memory, and 2 of its 12 sessions couldn't connect, which the runner now retries, R483), and the bounds check's reading of the runner's status (`WORKLOAD.<target>.BOUNDS` is a **Warning**, R346).
- the on-demand activity control (Phase 25c): proven live on 2026-10-27 (Phase 25d): setup on the private path, the owner's `-GrantRole`, runs from the notebook through the Fabric job API, a second request refused while one was active, Stop now, the auto-stop, and `start-demo.ps1`'s takeover of a pending auto-stop, with T4's start and stop through the runbooks after a fix (R480). Not proven live: the daily T4 safety stop's scheduled run (it's scheduled and linked, and its runbook's T4 stop ran through Stop now), the public-vault path, `-RotateWebhook`, and `-Remove`.
