# Automation support matrix

What the demo automates, what a person does and who, and what isn't supported, with the checks that report each. How the parts fit is in the [architecture](architecture.md), every command in [deployment](deployment.md#quick-reference-every-command), and each check's fix in [troubleshooting](troubleshooting.md).

## Automated vs manual

The scripts automate every step that has a documented interface. What's left is manual for a stated reason ([what stays manual, and why](#what-stays-manual-and-why)), and the scripts report it as **Manual action required** with its exact steps, so nothing is hidden. "You" is the person who deploys, with Contributor on the subscription, and ≈ marks an estimate. ## What stays manual, and why

Every manual step reports **Manual action required** with its exact steps. The first group exists only because no supported automation was found; the others are deliberate.

**No supported automation** (checked against Microsoft Learn):

| Step | Why it's manual |
|---|---|
| The Database Hub tenant setting (P4) | A tenant-wide Fabric administrator setting whose internal name isn't documented: [List Tenant Settings](https://learn.microsoft.com/rest/api/fabric/admin/tenants/list-tenant-settings) matches it only by title, and only for a Fabric administrator; for anyone else it's a reminder under **Please confirm** |
| Database Hub's UI: Estate, Performance, saved views, and monitor templates, with the template wizard | No public API, ARM, or Bicep resource; Learn documents them only as portal experiences ([overview](https://learn.microsoft.com/fabric/database/hub/overview), [monitor](https://learn.microsoft.com/fabric/database/hub/monitor)). The checks validate the signals behind them, and `HUB.ESTATE.VISUAL` stays **Manual action required** |
| Copilot in Database Hub and Database Agents, and the record of Copilot's coverage | No API. Database Agents covers Azure SQL Database only, so T3 ([Database Agents](https://learn.microsoft.com/fabric/database/hub/database-agents)); Copilot's target coverage isn't documented ([FAQ](https://learn.microsoft.com/fabric/database/hub/faq)), so the presenter records it ([agent guide](../fabric/agent/README.md#live-coverage-record)) |
| Selecting T3 for Database Agents (`HUB.AGENT.T3`) | Database Hub's settings have no API ([enable Database Agents](https://learn.microsoft.com/fabric/database/hub/enable-database-agents)); only [the Database Agent loop](demo-walkthrough.md#the-database-agent-loop-on-t3) needs it |
| The Insights app's browser check, only when **Please confirm** lists it | Its sign-in and connector run only in a browser session, and the CLI can't create the session the deployed connector needs ([CLI reference](https://learn.microsoft.com/fabric/apps/cli-reference)); the hosted URL, opened directly, fails in the preview ([the app's guide](../fabric/app/README.md#open-the-app)). When every query the app runs returned its data, it's a note instead |

**By design, a person approves or responds:** every action Copilot in Database Hub proposes; the response to Database Agents' issue on T3, which Run all's Database Agent loop makes itself; and the missing-index remediation.

**By design, you sign in,** so no script holds or requests your credentials:

- **The Azure CLI** (`az login`): no script signs in, signs out, or changes its default subscription; every call names the configured subscription, which the subscription guard checks ([prerequisites](prerequisites.md#target-subscription-configuration-the-subscription-guard)), and a separate CLI profile on a shared machine is yours to set ([prerequisites](prerequisites.md#optional-a-separate-azure-cli-profile)).
- **The Rayfin CLI** (P14), only when Fabric refuses the Azure CLI's token: `deploy.ps1` starts its sign-in at the next run's beginning, in a session that takes keyboard input, and without `-SignIn`, `configure-fabric-app.ps1` only reads it (`rayfin login status --json`). Its service principal sign-in isn't supported yet ([CLI reference](https://learn.microsoft.com/fabric/apps/cli-reference)).
- **GitHub, for Ask:** each viewer's own, with GitHub's device flow ([ADR 0028](adr/0028-ask-copilot-in-the-insights-app.md)). An organization that restricts OAuth apps approves the app once ([OAuth app access restrictions](https://docs.github.com/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions)), and each viewer can revoke it ([reviewing your authorized OAuth apps](https://docs.github.com/apps/oauth-apps/using-oauth-apps/reviewing-your-authorized-oauth-apps)).

**Needs more than Contributor** (the scripts print the exact commands, and run them when the caller may):

- **The nightly safety stop's and the session control's roles** (P16, P15): owner-approved exceptions that `deploy.ps1` makes when you may, whatever `assignRoles` says; otherwise an Owner runs `./scripts/grant-safety-stop.ps1` once ([the session control](permissions.md#the-on-demand-activity-control), [the nightly safety stop](permissions.md#the-nightly-safety-stop)). Until then the run still ends **DONE**, with a **Warning** (`SAFETYSTOP.ROLE`): nothing stops T4 after its 7-day restart (the VMs' auto-shutdown and T3's auto-pause still apply), Run all can't start a session, and T5's container stays, billing its 400 RU/s between sessions (`DEPLOY.T5.LIFECYCLE`).
- **Other roles:** Contributor for the GitHub identity (P7), Reader for presenters who aren't Contributors (P8), and the opt-in Key Vault's roles, with `assignRoles` ([permissions](permissions.md)).
- **Fabric:** the tenant settings (P4, P12, P13, and the strict content security policy setting) are a Fabric administrator's; resuming and pausing the capacity (P5) is its administrator's decision, outside the demo's resource group ([cost management](cost-management.md#microsoft-fabric-capacity)), unless `fabric.manageCapacity` opts in for an F capacity in the same subscription that's yours alone.

**Manual by choice:** sharing the history report outside the workspace, with its Direct Lake data access ([sharing the report](../fabric/powerbi/README.md#sharing-the-report)), and the maintainers' GitHub environments, which only `setup-github-oidc.ps1 -ConfigureGitHub` writes; otherwise the scripts print the `gh` commands.

## Capabilities by area

One line per capability: its status, then how, with the checks that report it. **(preview)** marks a dependency on a preview feature.

### Deploy and upgrade

- **One command:** Automated. `deploy.ps1` after `az login`: the first run's configuration (`INIT.*`), preflight, the template, four parallel tracks (`-Sequential` runs them in turn; `DEPLOY.TIMING`), validation, and **DONE** or **NOT DONE**, with a nonzero exit code unless it's **DONE**. It keeps a Windows PC awake, shows a live status page (`status.ps1 -Watch`), waits for T2 up to `-T2WaitMinutes` (180; `-NoWaitForT2` returns early, `DEPLOY.T2.BACKGROUND`), and continues where it stopped when run again ([one command](deployment.md#one-command-deployps1)).
- **Updates and upgrades:** Automated. A clean checkout of `main` fast-forwards first (`DEPLOY.SELFUPDATE`, a **Warning** with the command when it can't; `-NoSelfUpdate`). A first run where your environment exists writes the configuration from it, or makes a new environment when it isn't yours (`INIT.EXISTING`). An older demo is upgraded in place: `DEPLOY.T2.REBUILD`, `DEPLOY.T2.MODE`, `DEPLOY.T4.MISSING`, `DEPLOY.T5.MISSING`, `DEPLOY.CONTROL.ON`, `CONTROL.RUNBOOKS`, and `DEPLOY.T3.SCALE` ([update an existing environment](deployment.md#update-an-existing-environment)).
- **Recovery:** Automated. A T2 host whose VM agent stays down, or that's gone, is created again, and its guest restarted or a step run again when PowerShell Direct breaks (`DEPLOY.T2.HOSTREBUILD`, `.HOSTMISSING`, `.GUESTRESTART`, `.GUESTRETRY`); a stuck VM restarts once (`DEPLOY.WATCHDOG_<VM>`, `DEPLOY.EXTENSIONS_<VM>`, `DEPLOY.ARTIFACTS.CLEANUP_<VM>`); a changed bundle or runner reaches each VM (`DEPLOY.ARTIFACTS.CHANGED_<VM>`).
- **Preflight:** Automated. The subscription guard (`PREFLIGHT.GUARD.CONTEXT`), P1 to P6, the resource providers (which Contributor can register), the region, nested-capable sizes and quota, the tenant's policies with `networkMode` `auto` resolved from them (`PREFLIGHT.POLICY.*`, reused for `-PolicyCacheHours`), a what-if, and the cost against both ceilings.
- **Infrastructure:** Automated. Subscription-scope Bicep, checked by PSRule in CI: the network, NSGs, required tags, the budget, and the VMs' auto-shutdown; explicit `defaultOutboundAccess` or an opt-in NAT gateway; KMS activation; Trusted Launch for T1 when its image supports it (`securityType.t1` `Auto`); Premium SSD v2 only with a `zone`, and no data disks in `lowest-cost`; opt-in Spot (`hostPriority`, `t1Priority`) and Azure Hybrid Benefit, after an entitlement attestation. Bootstraps arrive in SHA-256-checked Run Command chunks.
- **Guards during a run:** Automated. The nightly safety stop waits for a running `deploy.ps1`, then stops the demo 60 minutes after it (`DEPLOY.NIGHTLYSTOP`: `./scripts/start-demo.ps1` keeps it running tonight, `./scripts/stop-demo.ps1` stops it now); a workspace another environment uses is named (`DEPLOY.FABRIC.SHARED`); T5 is left out, with Azure's reason, when Azure doesn't create it (`DEPLOY.T5`); a raised worst case is said (`DEPLOY.COST.T4RESTART`).
- **Tools:** Automated. The dev container, locally or in GitHub Codespaces on 4 cores, with every tool at its pinned version (`az login --use-device-code`); `collect-diagnostics.ps1`, a redacted, secret-scanned bundle for a **Deployment problem** issue (`DIAG.BUNDLE`).

### T1: SQL Server on an Azure VM

- **The VM:** Automated. SQL Server 2022 Standard PAYG with the SQL IaaS Agent extension; the image's Analysis Services and Integration Services uninstalled, so unified inventory lists only the engine (`T1.SQLVM.ASSOCIATEDSERVICES`).
- **Database Hub's Performance (preview):** Automated. The documented CLI settings merge, every other setting kept (`T1.SQLVM.MONITORING`, with the restart command when the plugin stops).
- **Not supported:** that monitoring on Developer edition (connection data only), and Entra authentication for SQL Server on T1, which needs Graph permissions and can't be turned off once on.

### T2: Arc-enabled SQL Server in a nested guest

- **The host:** Automated. `archost01` with Hyper-V, a NAT, a DNS forwarder, and no public IP, as a resumable state machine; the guest cut off from IMDS and the wire server (`T2.GUEST.ISOLATION`); egress limited to TCP 443 and KMS, with the FQDN gap documented.
- **`JumpstartImage`, the default:** Automated, with no person, product key, or Bastion. The host downloads [Arc Jumpstart](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/azure_jumpstart_arcbox/ITPro/_index.md)'s prebuilt SQL Server 2022 Standard guest, verified against its Content-MD5, makes it `arcsql01` at a first boot with no network (its published credential replaced, renamed, the SQL logins disabled, the extras removed), and checks it, or ends T2 **NOT DONE** with the fix. That meets Database Hub's [prerequisites for SQL Server enabled by Azure Arc](https://learn.microsoft.com/fabric/database/hub/add-sql#prerequisites-for-sql-server-enabled-by-azure-arc). It needs `t2Mode` `Nested` (`PREFLIGHT.T2.MODE`); `STATUS.T2.IMAGE` and `STATUS.T2.DISKSPACE` watch the image and the disk.
- **The build modes:** Automated after a prerequisite. `ProductKey` (P10; the key reaches the host only as a protected parameter) and `Developer` (Estate only), from evaluation media pinned by SHA-256; an evaluation guest is rearmed before it expires.
- **Arc:** Automated. Onboarding with your token (`T2.ARC.ONBOARDING`), PAYG (`T2.ARC.SQLEXTENSION`), monitoring (preview; `T2.ARC.MONITORING`, **Not supported** in `Developer` mode), no duplicate machines (`T2.ARC.NODUPLICATES`), and a cut-off guest or a long disconnection flagged (`T2.GUEST.STATE`, `T2.ARC.CONNECTED`). Hub's Performance for a nested guest isn't documented either way, so it's validated live.
- **Migration assessment:** Automated. On, with a first run, so Optimization shows T2's migration readiness; free and weekly (`T2.ARC.MIGRATIONASSESSMENT`; [assess migration readiness](https://learn.microsoft.com/sql/sql-server/azure-arc/migration-assessment)).
- **Golden snapshot (optional):** Automated. Capture (`GOLDEN.CAPTURE.*`, `GOLDEN.CAPTURE.SOURCE`), a proof in quarantine (`test-t2-golden.ps1 -Onboard`, `GOLDEN.TEST.*`), the restore on a redeploy (`t2Source`, `PREFLIGHT.T2.SOURCE`, `DEPLOY.T2.RESTORE`), its lifetime (`STATUS.T2.GOLDEN`), and a source host's guest released (`T2.GOLDEN.SOURCE`).
- **Sign-in data:** Automated. What setup leaves is removed and verified gone, and no operator token stays on the VMs, their logs, or a golden snapshot (`check-sign-in-data.ps1`, `SECURITY.SIGNIN.<VM>`, `GOLDEN.CAPTURE.SIGNIN`, `GOLDEN.TEST.SIGNIN`); clearing the Security log stays manual.
- **Optional:** onboarding with a host identity (`assignRoles`; `-UseHostIdentity`, `-UseCallerToken`), whose live proof is pending; the evaluation-only fallback (`t2Mode` `EvaluationOnlyAzureVm`).
- **Retired:** `PaygWizard` and its guided stop. A configuration's `PaygWizard` runs as `JumpstartImage`, and only the cleanup still runs (`DEPLOY.T2.GUIDEDLEFTOVER`, `STATUS.T2.AUTOSIGNIN`; [ADR 0006](adr/0006-sql-editions-and-licensing.md), [ADR 0009](adr/0009-secrets-handling.md)).

### T3: Azure SQL Database

- **Server and database:** Automated. Entra only with the P6 group as administrator, TLS 1.2, and the network mode; the schema, seed, and users from T1, through its membership in the P6 group (`T3.ADMINGROUP`), with interactive T-SQL as the fallback ([T3 as built](architecture.md#t3-as-built-phase-8)).
- **Database Hub's Performance (preview):** Automated. The extended property, from T1 (`T3.PROPERTY`); Hub's button is the manual alternative.
- **Free offer, warm-up, removal:** Automated. The free offer, with a check and a fallback (`PREFLIGHT.T3.FREEOFFER`, `T3.FREEOFFER`); a readiness gate (`T3.READINESS.*`); `stop-demo.ps1 -RemoveT3`; an older T3 scaled online (`DEPLOY.T3.SCALE`).
- **The Database Agent loop (preview):** Automated after one person's step. In Run all's second showcase cycle: `plan-regression` with automatic tuning held off, Database Agents' issue, and the run's own response. It needs T3 above one vCore and selected once in **Manage agents** (`HUB.AGENT.T3`); `T3.AGENT` is a **Pass** or a **Warning**, never a **Fail**; `T3.AUTOTUNING`, `STATUS.T3.AUTOTUNING`, and `STOP.T3.AUTOTUNING` watch the hold ([walkthrough](demo-walkthrough.md#the-database-agent-loop-on-t3)).

### T4: PostgreSQL and its read replica

- **The server:** Automated. `Standard_D4ds_v5` with autonomous tuning, in every deployment (`T4.SERVER`, `T4.CONFIG`), with virtual network integration (`T4.NETWORK`), Entra only, and the runner's role made by T1 through the P6 group (`WORKLOAD.T4.ENABLE`, `T4.ENTRAONLY`, `T4.ADMIN`). When Azure refuses the size: another zone, then the next size (`DEPLOY.T4.FALLBACK`), or **NOT DONE** ([T4 as built](architecture.md#t4-as-built)).
- **In the deployment and the sessions:** Automated. A stopped T4 starts before the template (`DEPLOY.T4.START`); the starts and stops start and stop it (`START.T4.START`, `-SkipT4`, `STOP.T4.STOP`), and so do both safety stops; `status.ps1` gives the date of Azure's 7-day restart, and the estimate counts its worst case (`PREFLIGHT.T4.CAPABILITY` checks the size and version).
- **Database Hub and the live view:** Automated. Estate and the **PostgreSQL** dashboard (`HUB.ESTATE.T4`, `METRICS.T4`); enhanced metrics (`T4.ENHANCEDMETRICS`, `STATUS.T4`, `STATUS.T4.LIVE`). Seeing it on the Estate page stays a manual check.
- **The read replica:** Automated. Created at each start, in about 9 minutes, and deleted at each stop (`START.T4.REPLICA`, `-SkipT4Replica`, `STOP.T4.REPLICA`), and marked as the session's, so a `deploy.ps1` meanwhile keeps it (`START.T4.REPLICA.HOLD`, a **Warning** when it can't be). `deploy.ps1` creates it for its checks and deletes it at its end (`DEPLOY.T4.REPLICA`, `DEPLOY.T4.REPLICA.END`); a refused size falls back (`DEPLOY.T4.REPLICA.FALLBACK`, `START.T4.REPLICA.FALLBACK`). It fills Hub's **Read replica lag** (`HUB.ESTATE.T4.REPLICA`, `METRICS.T4.REPLICA`) and the `replica-lag` scenario. A Burstable T4 has none: **Not supported**, with the fix.
- **History:** Automated: the lakehouse, the model, and the Insights app. Deferred: T4 pages in the history report and the Real-Time Dashboard ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md)).

### T5: Azure Cosmos DB

- **The account:** Automated. `patient-events` at 400 RU/s, in every deployment and on an upgrade (`DEPLOY.T5.MISSING`; `t5Enabled: false` is `DEPLOY.T5.OFF`), on the free tier when the subscription's one slot is free (`DEPLOY.T5.FREETIER`, `t5UseFreeTier`), Entra only, behind a private endpoint or, in public mode since 2026-11-21 when no policy needs one, reached from T1's subnet alone (`DEPLOY.T5.NETWORK`), with T1's data-plane role (`T5.ENTRAONLY`, `T5.NETWORK`, `T5.ACCESS`, `WORKLOAD.T5.WARMUP`).
- **The container, only during a session:** Automated once the session control's role can create it again. The starts create it (`START.T5.CONTAINER`, `CONTROL.T5.CONTAINER`, `DEPLOY.T5.CONTAINER`), every stop deletes it (`STOP.T5`), and `DbHubT5Container`, `DEPLOY.T5.LIFECYCLE`, `GRANT.T5.LIFECYCLE`, `T5.LIFECYCLE`, and `STATUS.T5` say which ([T5's cost](cost-management.md#t5-azure-cosmos-db-2026-11-18)).
- **Scenarios and Database Hub:** Automated. `ru-storm` (`reset-demo.ps1 -Target T5` cleans up after a cut-off storm); Estate and the Cosmos DB views (`HUB.ESTATE.T5`, `METRICS.T5`). Learn's [monitor a Cosmos DB account](https://learn.microsoft.com/fabric/database/hub/monitor-cosmos-db) still says Preview (checked 2026-11-19), while the general availability announcement includes Cosmos DB's dashboards.

### Workload and scenarios

- **Activity profiles:** Automated. `baseline`, `business-day` (the default), `showcase` (Run all's), `incident:<scenario>`, and `off`, on T1 to T5, run by the SYSTEM task `DbHubDemo-Workload` until the next auto-shutdown; set by `deploy.ps1` and `start-demo.ps1`, off at every stop, at boot only with `activityProfileOnBoot`.
- **Bounded scenarios:** Automated. One per incident and wait family, each with a hard time limit, only in `ContosoCare` and on sessions tagged `ContosoCare.Demo/` ([scenarios](../scenarios/README.md)); every run recorded (`demo.scenario_runs`, `demo.scenario_run_events`; T5's in `t5-runs.json` on T1); `demo-control.ps1` runs one on T1 to T5.
- **Stop and reset:** Automated after a prerequisite: killing sessions needs `ALTER ANY CONNECTION` and `VIEW SERVER PERFORMANCE STATE` (SQL Server) or `KILL DATABASE CONNECTION` and `VIEW DATABASE STATE` (Azure SQL), or it's **Manual action required**.
- **The runner:** Automated. A deterministic `win-x64` build in Run Command chunks with the pinned .NET runtime (SHA-512), and the demo objects and the runner's role on each target (`--grant-windows-login` on T1 and T2). Optional: the runner in a container against SQL Server on Linux (`workload-generator/compose.yaml`), for local tests.

### Database Hub and agents

- **Prerequisites:** the tenant setting (P4) is Manual, read on every run by a Fabric administrator (`PREFLIGHT.P4.HUBSETTING`, `FABRIC.P4.HUBSETTING`); a Fabric Free license is enough; presenters get Reader and the Arc telemetry role with `assignRoles` (P8; `HUB.PRESENTER.READER`, `HUB.PRESENTER.ARCTELEMETRY`).
- **Estate and telemetry:** Automated. Estate through Resource Graph (`HUB.ESTATE.T1` to `HUB.ESTATE.T5`, and `HUB.ESTATE.T4.REPLICA` during a session); SQL telemetry rows, the newest sample, and the lag (preview; `TELEMETRY.T1`–`T3`), with the notebook's `kusto` token checked at run time, since it isn't documented for this endpoint (`HUB.TELEMETRY.TOKEN`).
- **The UI:** Presenter-driven. Overview, Estate, Performance, Issue Details, saved views, and the template wizard have no API (`HUB.ESTATE.VISUAL`, **Manual action required**).

### Sessions and stops

- **The session control:** Automated after a prerequisite (P15). `deploy.ps1` sets it up and republishes its runbooks on every run (`DEPLOY.CONTROL`, `CONTROL.*`, `CONTROL.RUNBOOKS`), with its roles when you may (`CONTROL.ROLE.*`) and its notebook (`CONTROL.FABRIC.*`, `CONTROL.FABRIC.LAKEHOUSE`); `setup-activity-control.ps1` does the same alone (`-WhatIf`, `-RotateWebhook`, `-Remove`).
- **A Run all session:** Automated. Allow-listed scenarios, capped durations, one run at a time, and its auto-stop first; then the VMs and T4 start, T4's replica and T5's container are created, every target is brought back every 30 minutes, and old Run Commands are cleaned up (`START.CONTROL.RUNCOMMANDS`, `STATUS.RUNCOMMANDS`). Stop now and the auto-stop (and its backup, only if it fails) end it through Azure Resource Manager only. `stop-demo.ps1` removes a pending auto-stop (`STOP.CONTROL.AUTOSTOP`); `start-demo.ps1` replaces one with its session's own, `-Hours` (4) after the start (`START.CONTROL.AUTOSTOP`), and waits for a stop job in flight (`START.CONTROL.STOPJOB`); `status.ps1` reports it (`STATUS.CONTROL`).
- **From your PC:** Automated. `start-demo.ps1`: the cost check, both VMs and T4 at once, T3's warm-up in the background unless `-WaitForWarmUp` (`START.WARMUP`), T5's container, T4's replica, the relay, the profiles, and its own auto-stop, 4 hours later (`-Hours`). `stop-demo.ps1`: the guest shut down, the VMs deallocated, T4 stopped, the replica and T5's container deleted, Bastion removed, and the history with `-SaveHistory` (`-ParkT2` stops only T2). `reset-demo.ps1` restores the seed state, and its `-RebuildGuest` makes T2's guest again from Arc Jumpstart's image (since 2026-11-21); `status.ps1` shows each target and the month-to-date spend.
- **The nightly safety stop:** Automated after a prerequisite (P16; until then its jobs end `NotGranted`). At `autoShutdownTime` it deallocates the VMs, stops T4, then a replica a session left, and deletes T5's container; then it checks T3 without waking it and stops T4 again (`SAFETYSTOP.ROLE`, `STATUS.SAFETYSTOP`, `COST.SAFETYSTOP`; [ADR 0024](adr/0024-nightly-safety-stop.md)).
- **Bastion and the host password:** Optional. Bastion on demand (`start-demo.ps1 -Interactive`), removed with its public IP, in order, and after `bastionMaxHours`; the T2 host's one-time password by clipboard, an opt-in Key Vault (`keyVault.enabled`, with `assignRoles`), or the portal's **Reset password** ([reset-rdp](https://learn.microsoft.com/troubleshoot/azure/virtual-machines/windows/reset-rdp)), rotated afterward (`-ResetAdminPassword`).

### Cost, security, and validation

- **Cost:** Automated. `estimate-cost.ps1` and preflight price everything at run time from the Azure Retail Prices API, with your Defender for Cloud plans, against both ceilings; `start-demo.ps1` checks the estimate and the month-to-date cost first; the budget, the auto-shutdown, the safety stop, and a forgotten Bastion are audited (`COST.BUDGET`, `COST.AUTOSHUTDOWN`, `COST.SAFETYSTOP`, `COST.BASTION`). The Fabric capacity, Fabric and Power BI licenses, and each viewer's GitHub Copilot plan are outside every estimate ([cost management](cost-management.md#at-a-glance)).
- **Security:** Automated. A secret scan of script output, Run Command views, and deployment history (`SECURITY.SECRETSCAN.*`, and gitleaks on the repository), and an audit of role assignments, Key Vaults, public IPs, and inbound rules (`SECURITY.RBAC.ROLEASSIGNMENTS`, `SECURITY.SECRETS.KEYVAULT`, `SECURITY.NETWORK.NOPUBLICIP`, `SECURITY.NETWORK.INBOUND`).
- **Validation:** Automated. `validate.ps1` runs the live catalog by area (Preflight, Infrastructure, T1 to T5, Hub, Telemetry, Workload, Cost, Security, and Teardown), with stopped VMs as **Warnings** and `-TreatManualAsError`; static validation includes Windows PowerShell 5.1 compatibility for the VM-side scripts (`STATIC.PSSCRIPTANALYZER`).

### Destroy

- **Destroy:** Automated. `destroy.ps1` deletes what it can tell is this environment's: the Fabric workspaces (the demo's, with the Insights app and its functions item, and the control's; `-KeepFabric` keeps them), the session control, the group `init.ps1` created, the Arc resources, T4's read replica, the resource group (with T5 and the chat relay), the deployment record and the budget, and the custom roles no assignment holds; then a residual check (`TEARDOWN.RESIDUAL.*`, `DESTROY.RESIDUAL`; read-only with `-ResidueOnly`). It keeps `rg-<prefix>-golden` unless `-IncludeGolden` (`DESTROY.GOLDEN`). An account that can't delete role assignments gets `DESTROY.CONTROL.ROLES` as **Manual action required**, and the summary, `DESTROY.CONTROL`, is a **Warning** ([delete everything](../README.md#delete-everything)).

### Maintainers only

- **GitHub Actions (optional; users never need them):** OpenID Connect with `setup-github-oidc.ps1 -ConfigureGitHub` (`OIDC.GITHUB.*`; without it, `OIDC.GITHUB` is **Manual action required** with the `gh secret set` commands), required reviewers, and `setup-github-repo.ps1` for the repository's settings (`REPO.*`). The scheduled workflows (start, stop, Bastion cleanup, and `destroy.ps1 -IfExpired`) stay off unless `DBHUB_SCHEDULES_ENABLED` is `true` ([GitHub Actions](deployment.md#one-click-github-actions)).
- **The relay's image:** Automated. `.github/workflows/ask-relay-image.yml` builds, tests, and publishes `ghcr.io/marcbushong/fabric-database-hub-demo/ask-relay` on a push to the branches it names that changes `ask-relay/**` or the workflow, or by hand, never on a pull request or in a fork. The package is public, so Container Apps pulls it without credentials, and `config/versions.json` pins its digest.
- **Deploy to Azure button:** Automated after a prerequisite, a public repository: the infrastructure only, then `deploy.ps1 -Resume`.

## Not supported or deferred

- **Not supported:** monitoring Developer edition on T1; Entra authentication for SQL Server on T1; the `microsoft-sql` diagnostics skills on T1 and T2; rebuilding T2's guest in place in `ProductKey` or `Developer` mode (`reset-demo.ps1 -RebuildGuest` makes only an image guest again: run `destroy.ps1 -KeepFabric`, then `deploy.ps1`); a read replica for a Burstable T4; a dark theme for the Real-Time Dashboard; `INFO.MEASURES()` through Execute Queries; the Rayfin CLI's service principal sign-in; and `fabric.manageCapacity` for a Trial capacity or one in another subscription.
- **Deferred:** Fabric mirroring ([ADR 0015](adr/0015-mirroring-deferral.md)); T4 pages in the history report and the Real-Time Dashboard ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md)); and the Fabric data agent, which works over OneLake data, not Database Hub's signals.
- **Dropped or retired:** the artifact cache (tenant policies turn off shared-key and public access on storage accounts, and Defender for Storage bills each account), and `PaygWizard`'s guided stop.
