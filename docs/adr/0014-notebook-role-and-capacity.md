# ADR 0014: Notebooks, their roles, and the Fabric capacity dependency

- **Status:** Accepted
- **Date:** 2026-10-19 (revised the same day for plan §9, Revision 2)
- **Decision source:** User-directed (Q0: evolve the supplied notebook; Q7: reuse the demo workspace, whose ID is in the notebook metadata, with `LH_DatabaseHub`) and the user's Revision 2 request for a second, live-activity notebook (plan §9.3)
- **Related:** [ADR 0011](0011-control-surface-priority.md), [ADR 0012](0012-validation-model.md), [ADR 0013](0013-agent-experience.md), `fabric/README.md`

## Context

- The supplied notebook `NB_DatabaseHub_Deployment.ipynb` is Fabric's blank template: one `1+1` cell, the PySpark kernel (`synapse_pyspark`), and default lakehouse `LH_DatabaseHub` in the demo workspace (both IDs are in the notebook metadata). Its saved output contains Livy session IDs.
- Fabric notebooks need an F SKU or Trial capacity; Hub itself is free.
- `notebookutils.credentials.getToken` supports only the `storage`, `pbi`, `keyvault`, and `kusto` audiences. There's no Azure Resource Manager audience, so a notebook can't start VMs or run Run Command. The notebooks also can't reach the private SQL Servers.
- Using a `kusto` token against the telemetry REST endpoint isn't documented, so it has to be validated.
- Telemetry retention is 7 days or less.
- Fabric REST can create a notebook and update its definition. Changing the workspace needs the owner's go-ahead.

## Decision

### `fabric/notebooks/NB_DatabaseHub_Deployment.ipynb` (evolved, not replaced)

- **Keeps** its name, the PySpark kernel, the `LH_DatabaseHub` binding, the session timeout, and the compute setting. It replaces the template cell with real content and keeps nothing fabricated.
- **Roles:** deployment companion, validator, presenter script, troubleshooting and cleanup guide, and architecture explainer.
- **Sections** follow the brief: overview, value, architecture, prerequisites, security and permissions, cost, deployment, SQL Server and Arc, Azure SQL, Hub discovery, performance monitoring, agent skills, optional mirroring (deferred), data generation, scenarios, Hub and agent prompts, expected findings, remediation, reset, start and stop, validation, troubleshooting, cleanup, limitations and preview disclosures, and official references.
- It links to the live-activity notebook.

### `fabric/notebooks/NB_DatabaseHub_LiveActivity.ipynb` (new)

- **Purpose:** simulate live server activity and analyze locks, blocking, and overall consumption in Database Hub.
- **Same kernel and lakehouse binding** as the first notebook.
- **Sections** (plan §9.3):
  1. Parameters. Resource-changing cells need `CONFIRM = True`.
  2. Simulation control: start, stop, or switch activity profiles through `workflow_dispatch` with the P9 token. Without P9, the cell prints the Actions link and CLI command. Runs are recorded in `scenario_runs`.
  3. Live analysis through the telemetry REST endpoint with a `kusto` token, or a printed KQL fallback with an ADX link. Covers estate pulse, locks and blocking, overall consumption, and correlation of scenario windows with telemetry. Queries filter on time first, take deltas of cumulative counters, and branch on counter type.
  4. "See it in the Hub": deep links and Database Agent prompts. It describes signals, never expected AI output.
  5. Persist snapshots to `telemetry_snapshots` and `analysis_findings`, extending history past the retention window.
  6. Optional Real-Time Dashboard over the telemetry endpoint.
  7. Stop and clean up.

### Rules for both notebooks

- Markdown narration; parameterized environment values; no credentials; tokens never printed and token-like values redacted before display.
- Idempotent cells; ~~dry-run by default where meaningful;~~ resource-changing cells flagged and gated by `CONFIRM`. *Superseded in part on 2026-11-03: no dry-run defaults, `CONFIRM = True` by default; see [the amendment](#amendment-2026-11-03-no-dry-run-defaults).*
- They never claim that a cell provisioned something a supported API didn't. Where automation isn't supported, a validation cell is paired with a short manual instruction.
- Results go to Delta tables in `LH_DatabaseHub`: `validation_results`, `scenario_runs`, `telemetry_snapshots`, and `analysis_findings`.
- Outputs are stripped before commit. CI fails if any cell has outputs or execution counts, and a pre-commit hook strips them locally.

### Import

- `configure-fabric.ps1` creates or updates both notebooks in the demo workspace (its ID is in the notebook metadata) through Fabric REST, using the user's Fabric token. It runs only on the local path by default; in Actions only when the service-principal tenant setting and a workspace role allow it.
- **Changing the workspace is pending the owner's go-ahead.**

## Consequences

- **Positive:** presenters get a guided script, a validator, and a live analysis surface in Fabric, with history beyond telemetry retention.
- **Negative:** the notebooks need capacity (P5) and can only control the demo through GitHub (P9). The notebook `kusto` token path is undocumented; it worked on 2026-10-21 (R29 closed), and the fallbacks stay in case it changes: printed KQL, a Real-Time Dashboard, or `validate.ps1`.

## Phase 12 implementation notes (2026-10-20)

- **Import:** `scripts/configure-fabric.ps1`, built on the module functions `Get-DemoFabricToken`, `Get-DemoFabricNotebookDefinition`, and `Import-DemoFabricNotebook`. It finds each notebook by display name and calls Items - Create Item (type `Notebook`) or Items - Update Item Definition with format `ipynb` and one part, `notebook-content.ipynb`, as in the Create Notebook ipynb example (the definition article's generic example names the part `artifact.content.ipynb`; on 2026-10-21 Fabric accepted `notebook-content.ipynb` for both create and update). HTTP 202 is polled with Get Operation State after `Retry-After`. The token is a SecureString sent only to `https://api.fabric.microsoft.com/v1`; `-WhatIf` sends nothing and needs no token. When the configured lakehouse differs from the notebooks' binding, only the uploaded copy is rebound.
- **Parameters cell:** cell metadata `tags: ["parameters"]`, the convention that Fabric's **Toggle parameter cell** writes to `.ipynb` (as in Synapse and papermill). It was confirmed live: a job's `executionData.parameters` replaced the cell's defaults. Booleans that arrive from a pipeline as strings count as true only for `true`, `1`, or `yes`.
- **Language:** the metadata also carries `"language_info": {"name": "python"}`. The supplied file lacked it; Fabric's own export has it, and Run On Demand Item Job rejects a notebook without it.
- **Two switches for cells that undo work:** dropping the Delta tables needs `PURGE_DEMO_TABLES` and `CONFIRM`; stopping all activity needs `STOP_ACTIVITY` and `CONFIRM`. **Run all** with `CONFIRM = True` therefore starts a scenario without stopping it at the end. An identical simulation request within 2 minutes is skipped.
- **`demo-control.yml` input contract** (Phase 13 declares it): `environment`, `target` (`all`, `T1`, `T2`, `T3`), `scenario` (`baseline`, `business-day`, `off`, or `incident:<scenario>`), `duration` (minutes), `concurrency` and `intensity` (omitted when 0, so the scenario's defaults apply), `reset-before`, and `auto-cleanup`, all as strings. A Pester test checks the names against the workflow once it declares inputs.
- **Telemetry:** the notebook `kusto` token is checked once (`HUB.TELEMETRY.TOKEN`); afterward each query either runs or prints its KQL with the Azure Data Explorer web UI steps. Per-bin timelines of cumulative counters keep the first and last sample of each series in each bin and sum the increases between adjacent samples, skipping resets: the article's pattern for queries that must scale, applied per bin.
- **Delta tables:** `validation_results`, `scenario_runs`, `telemetry_snapshots`, and `analysis_findings`, appended with `mergeSchema`; rows from the same run are replaced on re-run. Correlation thresholds (for example, CPU in a window at least 1.5 times and 10 points above the same target outside incident windows) are presenter heuristics, not product behavior.
- **Form in Git:** sequential cell IDs and no outputs, which is what the pre-commit `nbstripout` hook writes, so the hook leaves the files unchanged.

## Amendment (2026-11-06): one analyze-only run at the end of each deployment

- **Decision source:** the owner, verbatim: "Can we add a step that calls the acitivty notebook one time after deployment so it starts to populate data? WOuld there be any concern for executing that?" The owner then agreed the design below with the coordinator and asked for it in its own pull request.
- **Why:** the history report was blank after a deployment. `configure-fabric.ps1` runs `NB_DatabaseHub_LiveActivity` once when it first imports it, so a new lakehouse gets the history tables, but `deploy.ps1`'s Fabric track runs in parallel with T1 and T2, before any target sends telemetry, so that run saves almost nothing (live, 2026-11-06: `FABRIC.SEMANTICMODEL.MEASURES`, "The history report is empty until NB_DatabaseHub_LiveActivity saves its first snapshots", and `'Analysis Findings'[Blocking Incidents]` blank over the whole history).
- **The step** (`Invoke-DemoHistorySnapshotStep`, `DEPLOY.FABRIC.HISTORY`): at the end of every `deploy.ps1` run that reaches its validation, in the parallel tracks and in `-Sequential`, after **DONE**'s checks and the switch to the run's activity profile ([ADR 0010](0010-workload-generator-technology.md#activity-profiles-business-day-by-default-2026-11-03)), the notebook runs once on demand (`Invoke-DemoFabricNotebookRun`), then the history model is refreshed once (`Invoke-DemoSemanticModelRefresh`), which for its Direct Lake tables is framing, so the report shows the new rows at once ([how Direct Lake works](https://learn.microsoft.com/fabric/fundamentals/direct-lake-how-it-works)). The notebook never touches the VMs, so the switch doesn't wait for Spark.
- **Analyze-only:** `CONFIRM` false, `STOP_ACTIVITY` false, `SAVE_RESULTS` true, `WINDOW_MINUTES` 1440, `KEY_VAULT_URL` empty, and the demo's `RESOURCE_GROUP`, as `stop-demo.ps1 -SaveHistory` sends them. `CONFIRM` must be false: with this ADR's defaults since 2026-11-03, **Run all** also sends a 240-minute `business-day` request through GitHub (P9), which would duplicate the activity the deployment started.

- **Bounded:** Spark's start and the analysis take about 2 to 5 minutes (an estimate); the step waits at most 10 minutes for the job and 5 for the refresh. A job still running then is a **Warning**; it keeps running in Fabric and saves its snapshots when it finishes.
- **Never blocking:** its record is **Pass**, a **Warning**, or **Not selected**, never a **Fail** or **Manual action required**, and `Test-DemoNonBlockingResult` names it too, so it never changes **DONE**, `DEPLOY.SUMMARY`'s status, or an exit code. A notebook that fails, or a step that stops with an error, is a **Warning** with Fabric's reason and evidence `reportedStatus` `Fail`. The status page shows it as its own row, **History report's snapshot**, marked "(doesn't block DONE)", and what didn't work is in its **Needs attention** box and in **DONE** and **NOT DONE** (`Get-DemoHistorySnapshotItem`).
- **The capacity stays the user's:** a paused capacity makes the notebook fail to start, which is a **Warning** with the capacity's state (read through `Test-DemoFabricWorkspace` first, or from Fabric's `CapacityNotActive` at the submit). Nothing resumes, pauses, or scales it ([pause and resume](https://learn.microsoft.com/fabric/enterprise/pause-resume)).
- **Not selected:** with `-WhatIf` or `-SkipFabric`; when **DONE**'s checks didn't run (a track didn't finish, or a check failed) or their telemetry checks didn't pass, since the notebook would have nothing to save; when the Fabric track didn't create the lakehouse or import the notebook; and in GitHub Actions. [Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job) supports service principals and managed identities (checked 2026-11-06), but the demo has no supported setup for the workflow's identity in Fabric: `deploy.yml` skips Fabric by default ("it needs Fabric access for the identity"), `setup-github-oidc.ps1` grants no workspace role, and the notebook's telemetry read with the run identity's `kusto` token is proven for a user only (R29). The [Import](#import) rule for Actions stays as it is.
- **A resumed run with nothing left to do runs it again:** harmless, since each run saves its own rows and the notebook replaces a run's rows only when that same run saves again, and it adds what happened since, such as incidents.
- **Partial data, said plainly:** the VMs start the profile's incidents only at the end of the run, so the first snapshot has the steady mix but no incident, and incident measures such as **Blocking Incidents** stay blank until incidents have run and the notebook runs again: `stop-demo.ps1 -SaveHistory`, `configure-fabric.ps1 -SkipHubChecks -SkipNotebookImport -RunLiveActivity`, or the next `deploy.ps1`. The Pass message, the README, and the deployment guide say so.
- **Consequences:** a run takes about 2 to 5 minutes longer, at most about 15, after its **DONE** checks, so `DEPLOY.TIMING`'s clock, which stops at **DONE**'s requirements, doesn't count it. The Spark session uses the capacity's units while it runs; the capacity's own billing doesn't change. Each run adds one snapshot's rows to the lakehouse.
- **Tests:** `tests/unit/DbHubDemo.HistorySnapshot.Tests.ps1` (the parameters against the notebook's parameters cell, every outcome, the status page's row, the Not selected cases, and that none of it blocks **DONE**), and the deployment paths' order in `DbHubDemo.Tracks.Tests.ps1` and `DbHubDemo.Lifecycle.Tests.ps1`. ## Amendment (2026-11-22): overlapping saves resolved at query time, rejected (F35)

- **Decision source:** the coordinator, on the final tests' timing of the model with a month and two months of history: the query-time version "is withdrawn", and F35's shared rule for the app (part 1) stays.
- **The problem:** the notebook saves every run's rows at its own interval: a session's own save every minute, `./scripts/stop-demo.ps1 -SaveHistory`'s every 5, and `./scripts/deploy.ps1`'s day-long snapshot every 15, while T4's and T5's Azure Monitor saves step from 1 to 1,440 minutes. The model's `Snapshot Value` takes each bin from its newest capture, so where a coarser save covers a finer one's minutes, both count. In a live test's history (2026-11-21), T5's first storm read 52,450 requests where its minutes give 24,820. Part 1 made the Insights app's T4 and T5 reads, and the incident RCA, take each interval from its finest save (`fabric/app/src/data/finest-per-interval.ts`).
- **What was tried (part 2):** `Snapshot Value` took each interval from its finest save at query time, by the rows each save holds, in the shared rule's order, with a remainder at its own bin's start. On the live test's model it was right: 6,933 of 6,933 bins equal its TypeScript reference, and the window's 32 totals and peaks equal `finestPerInterval`'s.
- **Why it's rejected: its query time, which grows with the window.**
  - **One day of history:** the Insights app's Estate query took 2.1 to 2.7 times the release's measure's time end to end, and T5's 1.7 to 2.2 times, against a bar of about 2. Two faster forms gave the same answers and were slower still: Estate 2.75 and 2.79 times, T5 3.30 and 3.42.
  - **A month and two months of history** (that day's rows copied for each earlier day): the app's 7-day Performance query took 19.0 and 20.3 s with the faster form, against the release's 2.8 and 2.6 s, 6.84 and 7.68 times. The other form ran out of an F4 capacity's 1 GB of memory per query ([semantic model SKU limitation](https://learn.microsoft.com/fabric/enterprise/powerbi/service-premium-what-is#semantic-model-sku-limitation)) after 27 to 30 s. Estate took 3.0 to 4.2 times the release's time, and T5 2.3 to 2.5 times. Each day of window added about 2 to 2.6 s with the faster form, while a second month of history changed little.
  - **The capacity:** a few 7-day queries within minutes put the F4 capacity into Fabric's 20-second interactive delay, twice ([throttling](https://learn.microsoft.com/fabric/enterprise/throttling)).
- **Decision:** the model keeps the release's `Snapshot Value`, the newest capture per bin, and the double count stays a known issue ([limitations](../limitations.md#the-history-models-overlapping-saves-f35)). A fix that resolves the overlaps when a save is written, so that the model's measures stay a sum, is the owner's decision. The owner chose design (i) on 2026-11-23 ([below](#amendment-2026-11-23-overlapping-saves-resolved-when-history-is-saved-f35-design-i)).
- **Kept:** the rule's TypeScript reference and its tests (`fabric/app/src/data/snapshot-value.ts`), and the check that names every DAX variable as Learn allows ([VAR](https://learn.microsoft.com/dax/var-dax)), with `tests/unit/data/dax-reserved-words.txt`: the live engine refused a variable named `Under` that every text check had passed. `./scripts/stop-demo.ps1 -SaveHistory` still saves up to the moment it runs.

## Amendment (2026-11-23): overlapping saves resolved when history is saved (F35, design (i))

- **Decision source:** the owner approved the coordinator's recommendations (2026-11-23, decision 3: "your recommendations for everything else"): design (i), a kept value beside each row, resolved when history is saved and delivered to an existing demo with no decision from its owner, after the release.
- **Three columns in `telemetry_snapshots`,** and `value` stays the raw value:
  - `grain_minutes` (integer): the save's interval, which the notebook writes with each save. A save from before has none, and its step is read as before: a SQL save's from its window, by the notebook's rule, and an Azure Monitor save's from its window and bins.
  - `kept_value` (double): the row's share of its interval under the shared rule, each interval from its finest save, by the rows each save holds (`finestPerInterval`, `fabric/app/src/data/finest-per-interval.ts`). A total keeps what's left after the finer saves' rows in its interval, never below 0, split across its rows by their values. A maximum or an average keeps a row's value only where it's higher than the finer saves', else null, so a chart's bin stays blank. Off the bin grid, the newest capture's rows keep their values.
  - `resolved_at_utc` (timestamp): the time just before the step that worked the row out read it. Null means not yet, which a null `kept_value` can't say.
- **The step** (`kept_value_step`, `fabric/history/kept_value.py`; the same code is in `NB_DatabaseHub_LiveActivity`): it reads the table's columns (`DESCRIBE TABLE`) and adds those it lacks (`ALTER TABLE ... ADD COLUMNS`). Then, for each target and analysis with rows to resolve, it reads the days around them, a day on either side, since no interval is longer than 1,440 minutes, applies the rule, and MERGEs `kept_value` and `resolved_at_utc`. When Delta reports a conflicting commit, it reads that batch's rows again and MERGEs again, up to 5 times. The MERGE updates a row only when its `resolved_at_utc` is null or not later than the step's read, so a step never overwrites a later step's kept values. Fabric's Delta tables all use Serializable isolation, the only level Fabric supports, where even a blind append can conflict with a MERGE, and `telemetry_snapshots` has no partitions, so the conflict checker counts a step's MERGE as reading the whole table ([concurrency control for Delta tables](https://learn.microsoft.com/fabric/data-engineering/delta-lake-concurrency-control)). A save appended while a step's MERGE runs therefore makes the MERGE fail with `ConcurrentAppendException`, and run again, with the save's rows when they fall in the batch's days; the append, which reads nothing, isn't the one that fails. Another step's MERGE, a save that replaces its own run's rows, and a change to the table's columns make it run again too. A save's rows that a step didn't read stay unresolved, and their bins read by the release's rule, until their own run's step, or the next one, works them and the rows around them out. The notebook's save runs its delete and its append again together after the same conflicts, at most 5 tries, 1 to 8 seconds apart, since a failed Delta transaction writes nothing, so a step at the same moment doesn't fail the save. It's a pure function of the raw rows, so a rerun changes nothing and a whole history can always be resolved again. It never raises: a row it couldn't work out stays unresolved.
- **Where it runs:**
  - **The notebook,** on its own save, where `deploy.ps1` has brought it up to date (follow-ups decision 2a), so a Run all session's save is resolved at once.
  - **The PC scripts,** which send the repository's `kept_value.py` to the lakehouse's Spark through Fabric's Livy API, so a workspace's old notebook doesn't matter ([Livy API](https://learn.microsoft.com/fabric/data-engineering/api-livy-overview), [session jobs](https://learn.microsoft.com/fabric/data-engineering/get-started-api-livy-session)): `deploy.ps1`'s Fabric track, which adds the columns, before `configure-powerbi.ps1`; `deploy.ps1`'s end, after its history snapshot, the main source of overlap; and `stop-demo.ps1 -SaveHistory` and `configure-fabric.ps1 -RunLiveActivity`, after their saves. A session runs on the workspace's starter pool, and is deleted when the step ends.
  - **Their token:** Learn documents the Livy API for a Microsoft Entra app or a service principal, with the `Lakehouse.Execute.All`, `Lakehouse.Read.All`, `Code.AccessFabric.All`, and `Code.AccessStorage.All` scopes, and with the tenant setting for the Livy API turned on ([authentication](https://learn.microsoft.com/fabric/data-engineering/get-started-api-livy)). The Azure CLI's token, which the repository's notebook runs use, isn't listed there. A read-only probe passed with it on 2026-11-23, on a test environment's lakehouse: a session, a SQL statement, a read of `telemetry_snapshots`, and the session's delete. So the steps use it, and there's no maintenance notebook. Should Fabric refuse it, the steps' **Warning** says so, and the history reads as it did before.
  - **Their results** (`Invoke-DemoHistoryKeptValue`): `DEPLOY.FABRIC.KEPTVALUE` in the Fabric track (the status page's **History's kept values** row), `DEPLOY.FABRIC.KEPTVALUE.END` at the end (beside the history snapshot's row), `STOP.FABRIC.KEPTVALUE`, and `FABRIC.KEPTVALUE`. Each is a **Pass** when no row is left, **Not selected** when there's nothing to work out, and otherwise a **Warning** that says why (a paused capacity, a refused session or statement, no token, a session or a step that didn't finish, or an HTTP error past the retries) and gives its fix; never a **Fail**, so none keeps a run from **DONE**, and **DONE** lists the last one's **Warning** under what needs attention. At `deploy.ps1`'s end, when its Fabric track's step didn't allow the kept form, for any reason (a first deployment's history without rows yet, or a busy capacity that refused the session), the end's step works out every row and then deploys the history model in the kept form itself, a **Pass** (`Switched`; design A, approved 2026-11-23), and the track's **Warning** and the model's record of the release's form become a **Pass** that keeps what they said; a switch that doesn't work is one **Warning** (`SwitchFailed`), and the end's other **Warnings** say that the model reads the release's form, with `./scripts/deploy.ps1 -FromStage Fabric`. When the end has nothing to work out (its history snapshot saved nothing, or there's still no table), it's **Not selected** and says that the next `./scripts/deploy.ps1` deploys the kept form by itself, and so are the track's **Warning** and the model's record of the release's form when a later run fixes the track's answer by itself (`NoTable`, `SessionFailed`, `TimedOut`, `Failed`, or `NoColumns`); a refused statement, a paused capacity, no token, or a bug keeps its own fix. Each step has one deadline, the session's start and the module's load included: 30 minutes in `deploy.ps1`'s Fabric stage or track and 15 elsewhere, of which the session may take 10 (5 in `stop-demo.ps1`); the session is always deleted, and one left behind ends after 20 minutes idle.
- **The model:** `Snapshot Value`, under every telemetry measure, has two forms, which `configure-powerbi.ps1 -SnapshotValueForm` deploys: `Kept` only from `deploy.ps1`'s Fabric track when `DEPLOY.FABRIC.KEPTVALUE` found the three columns there, and otherwise `Release`, its default. `FABRIC.SEMANTICMODEL.FORM` says which: a **Pass** for `Kept`, and a **Warning**, with `./scripts/deploy.ps1` as its fix, for `Release`.
  - **Kept,** where the three columns exist: per bin and series, when every row there is resolved, the sum of the kept values for a total, and for a maximum or an average the highest of each save's sum; otherwise the release's rule, the newest capture's sum. So a bin that isn't resolved yet reads as it did before, and none reads worse. While a query filters a column that tells a bin's saves apart (`Run ID`, `Source Notebook`, `Captured At UTC`, `Window Start UTC`, `Window End UTC`, `Value`, `Kept Value`, or `Resolved At UTC`), as Ask's question about the latest run does, every bin reads by the release's rule, so a run's own rows read as it saved them: a row's kept value is its share against every save, which such a filter hides.
  - **Release,** the measure as it was, where the columns don't exist yet or the step couldn't tell: a model that reads a column its table lacks can't be framed ([Direct Lake](https://learn.microsoft.com/fabric/fundamentals/direct-lake-how-it-works)). The model step that runs again after a first deployment's first history run waited past its 45 minutes (#68) deploys it too, until the next Fabric track.
- **The groundwork's two known differences from `finestPerInterval`** are aligned in both rules: each save's step is its declared grain, and a row that straddles a coarse point's window cut splits what's left of it across its uncovered stretches by length, as `finestPerInterval` does. Over whole-hour windows, when no save in them is coarser than an hour, the model's totals and peaks then agree with the Insights app's T4 and T5 views. A window's edge inside a coarser bin can still differ, by design: a per-bin model shows a remainder at its own bin's start.
- **Evidence so far** (2026-11-23, on a copy of a test environment's real `telemetry_snapshots`, 33,115 rows, dropped afterward):
  - **The step** added the three columns and resolved 32,402 rows in 21.5 seconds with one MERGE, and a rerun found nothing left in 2.1 seconds. The other 713 rows, off the bin grid, keep null by design.
  - **The proof** (`fabric/app/scripts/f35-proof.ts`, on the resolved copy, exported) found no difference: the kept values give each of 20,779 bins what `snapshotValues` gives it from the raw rows, and none is unresolved; each of 1,551 series-hours equals `finestPerInterval`; and both rules give each of the 151 saves the same step (none declares a grain: they're from before F35).
  - **What the release counted:** against the kept values, its rule, each bin's newest capture, read the totals of T1's `wait_deltas` 2.40 times, `counter_deltas` 2.50, and `storage_io` 2.51; T2's 2.44, 2.34, and 2.31; T3's 2.12, 1.68, and 1.02; and T5's `cosmosdb` 2.33.
- **Not proven live yet:** a net-new deployment, whose saves declare their grain; an update of a demo whose workspace keeps its old notebook; the deployed model's kept form against the same reference; and the app's 7-day Performance query on a month of history against the release's time.
