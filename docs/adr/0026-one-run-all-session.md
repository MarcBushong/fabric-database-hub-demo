# ADR 0026: One Run all for a whole demo session

- **Status:** Accepted for the user by the project's coordinator (2026-11-14), who reviews it with the user before anything merges; the user can reverse the grant, since without it Run all still runs a session without T4's read replica and says so. Live validation: [below](#validation).
- **Date:** 2026-11-14
- **Decision source:** User-directed (2026-11-14: "I just want to go to one notebook and execute one thing. It may execute many things though and that is okay"; the experience "as easy as possible for users to execute and show. One click, one deploy"; a demo session needs no GitHub Actions), with the control notebook in its own workspace "because of the network controls". The design, the grant, and this ADR's permissions were approved by the coordinator for the user.
- **Related:** [ADR 0012](0012-validation-model.md) (statuses), [ADR 0020](0020-on-demand-activity-control.md) (the control, its role, and its vault), [ADR 0024](0024-nightly-safety-stop.md) (the nightly stop and the busy marker), [ADR 0025](0025-t4-read-replica.md) (T4's read replica), [ADR 0010](0010-workload-generator-technology.md) (the showcase's replica slot), [permissions](../permissions.md)

## Context

- **Before:** a session took 4 or 5 actions across a PC and two notebooks: `start-demo.ps1` (or the control notebook's run, or the activity notebook with a GitHub token), `demo-control.ps1` for the replica beat, the activity notebook's Run all with its `CONFIRM` switch, finding Database Hub's pages and the Database Agent prompts, and `stop-demo.ps1 -SaveHistory`. The control (ADR 0020) was optional, and it never created T4's read replica, so a control run had no Read replica lag.
- **Fabric notebooks get no Azure Resource Manager token** (`notebookutils.credentials.getToken` offers storage, pbi, keyvault, and kusto), so whatever acts on Azure goes through the control's Azure Automation runbook, which the notebook starts through its webhook, read from the control vault.
- **The control notebook can't read a job's output, and the runbook can't reach a private vault's data plane** (the vault's managed private endpoint serves Fabric only). Azure Resource Manager's Secrets - Create Or Update isn't subject to a vault's network rules, and the webhook's own secret is written that way already (`infra/control/webhook.bicep`).
- **A deleted server's Azure Monitor metrics can't be read** (`ResourceNotFound`, live 2026-11-13), so the history needs the replica's metrics before the replica is deleted.

## Decision

### The session

The control notebook NB_DatabaseHub_Control, in its own workspace (with a private vault; a folder of the demo's workspace with a public one, [ADR 0020](0020-on-demand-activity-control.md)), is the one place a person runs a session: open it and select **Run all**. Nothing is edited first.

1. **The session request:** Run all sends `{"action":"session","sessionId":"<32 hex>"}` to the runbook DbHub-Control, which:
   - refuses while another run is active, with the reason;
   - plans the showcase on every target for the session's minutes (90 by default), ending before the VMs' next auto-shutdown, as a run always has: the VMs' profile hosts end their activity there. A shorter session ends after its last whole 30-minute showcase cycle, so no beat is cut off, and says when it ends and why; one with less than 30 minutes left is refused;
   - marks the demo busy (`DbHubBusyUntilUtc` and `DbHubBusyBy` `session`, [ADR 0024](0024-nightly-safety-stop.md#amendment-the-busy-marker-so-the-nightly-stop-doesnt-cut-off-a-run-2026-11-14)) until 15 minutes after its auto-stop, with the session's ID and start (`DbHubSessionId`, `DbHubSessionStartUtc`), so the nightly stop's passes leave the session to its own auto-stop;
   - creates the auto-stop and, 30 minutes later, a second one that runs only if the first one's job fails;
   - starts the VMs, T3 (with its first session), and T4, and dispatches each target's showcase as soon as it runs;
   - asks for T4's read replica as soon as T4 is Ready, at T4's size or the next documented size Azure accepts (never fewer vCores), asking again while T4 restarts or updates (`ReadReplicaServerInUnexpectedState`, live 2026-11-13), and waits for it; then sets its `max_standby_streaming_delay` and records its size;
   - writes its progress, each step in plain words with its fix, to the control vault's secret `dbhub-session-status`.
2. **The replica-lag beat:** the showcase runs `replica-lag` in T4's even cycles, from minute 20 (50 minutes after T4's profile is set), on T1's profile host when it has the replica configured ([ADR 0010](0010-workload-generator-technology.md)). The status gives the beat's windows, or why it won't run.
3. **The notebook** says before it sends anything when the session will end and why (the runbook's plan, which it computes the same way from `CATALOG_JSON`'s session rules: a session the auto-shutdown cuts short ends after its last whole 30-minute showcase cycle, so no beat stops midway, and none starts with less than 30 minutes left), and checks the control vault. It never checks, starts, or pauses the Fabric capacity, which runs it, and never checks licenses (below). Then it follows the status, prints the presenter's guide (Database Hub's pages, the history report, the Insights app, each beat in the demo's clock from each target's dispatch time in the status, moved to when its runner set the target's activity once the start's host check reads it (2026-11-19, [below](#2026-11-19-amendment-each-targets-showcase-counts-from-when-its-runner-set-it)), with when it shows, and the Database Agent prompts with this session's names and windows), and keeps a live view until the session's end. A Run all while a session runs follows that session instead of starting another.
4. **The end:** the notebook sends Stop now with the session's ID at the session's end (`WAIT_FOR_END`, the default). The runbook removes the auto-stops, saves T4's and the replica's Azure Monitor metrics to the secret `dbhub-session-metrics` first (`{"action":"capture"}` does the same on its own), deallocates the VMs, deletes the replica, then stops T4 and confirms its stop (Azure can refuse it for a minute after the replica's delete, so the runbook asks again), and clears the busy marker. About 15 minutes later, with everything stopped, once the SQL telemetry has arrived, the notebook runs `NB_DatabaseHub_LiveActivity` from the demo workspace in its own Spark session ([below](#the-historys-spark-session-2026-11-14)) with `SESSION_ID`, `SESSION_PLAN` (the beats), the session's window, `POSTGRES_METRICS`, the demo's workspace and lakehouse, and the environment's names (`RESOURCE_GROUP` and the targets', which the activity notebook's own defaults give as the owner's environment). That notebook records the session and its beats in `scenario_runs` last, so a session already there isn't saved twice. When Run all stopped early, the session's auto-stop does the Azure part 10 minutes after its end, and the next Run all saves the earlier session's history right after its own start is sent. Run all keeps its Spark session for the whole session, about two hours for 90 minutes, the history included; `WAIT_FOR_END = False` ends it after the guide.
5. **No GitHub Actions in a session:** the activity notebook's simulation control through `demo-control.yml` (and its P9 token) is removed, with no default and no fallback; the notebook analyzes and saves only. Actions stay for CI and the repository's own deploy workflows. The scripts that run it still pass `CONFIRM` and `STOP_ACTIVITY` as false, which only a copy imported before 2026-11-14 reads.

### The history's Spark session (2026-11-14)

**The requirement** (the coordinator, for the user): Run all works on F2, F4, and Trial capacities, and the history is never refused or lost because the control notebook's own Spark session still runs (R844, R847).

- **What Learn says** ([concurrency limits and queueing](https://learn.microsoft.com/fabric/data-engineering/spark-job-concurrency-and-queueing), updated 2026-10-02):
  - Admission is by a job's minimum Spark VCores. F2 has 20 with bursting, F4 24, Trial 128 (no queue), and the small FTL4 trial 16. A starter pool on F2 or F4 is one Medium node of 8 VCores.
  - A notebook job submitted while the capacity is fully used gets `[TooManyRequestsForCapacity] HTTP Response code 430`. "Queueing doesn't apply to interactive notebook jobs or notebook jobs submitted through the notebook public API." Jobs from pipelines, the scheduler, and Spark job definitions queue, for up to 24 hours, and "If a Fabric capacity is in a throttled state, new Spark jobs are rejected instead of queued."
  - So the earlier design, the activity notebook's job submitted through the API while Run all's own session still ran, could be refused on a small capacity whose other Spark sessions hold the rest of its cores.
- **The choice: a reference run.** The history runs in the control notebook's own Spark session: `notebookutils.notebook.run("NB_DatabaseHub_LiveActivity", 1800, <parameters>, <the demo workspace's ID>)`. "The notebook being referenced runs on the Spark pool of the notebook that calls this function," across workspaces by ID on runtime 1.2 and later ([NotebookUtils notebook run](https://learn.microsoft.com/fabric/data-engineering/notebookutils/notebookutils-notebook-run)). No second Spark job is submitted, so no capacity has anything to admit, queue, or refuse: one 8-VCore session fits F2, F4, FTL4, and Trial.
- **What it needs: the demo's lakehouse.** "Reference run allows child notebooks to run only if they use the same lakehouse as the parent ... The execution is blocked if the child specifies a different lakehouse than the parent notebook." So `deploy.ps1` resolves the demo's lakehouse by name (read-only), attaches it as the control notebook's default lakehouse in the uploaded copy (the repository's copy names none, [ADR 0021](0021-fabric-resources-by-name.md)), fills `DEMO_LAKEHOUSE_ID`, and reports it (`CONTROL.FABRIC.LAKEHOUSE`: Pass, or a Warning with its consequence when the lakehouse isn't resolved). The notebook passes the demo's workspace and lakehouse IDs to the activity notebook too. The control workspace reaches the demo workspace's lakehouse because "If the target workspace allows inbound public access, connections from other workspaces are permitted without additional configuration" ([cross-workspace communication](https://learn.microsoft.com/fabric/security/security-cross-workspace-communication)), and its outbound access protection stays off.
- **The fallback, with its reason on screen:** when the notebook's default lakehouse isn't the demo's (a copy imported before, or a lakehouse that wasn't resolved) or the reference run fails, the notebook says why and starts the activity notebook as a job in the demo workspace (Job Scheduler, as the presenter, with the `pbi` token, the earlier path). A 430 there is asked again twice, a minute apart, then printed as a **Warning** with the fix: the next Run all saves the history first, from the session's metrics in the control vault, or the activity notebook run by hand with the session's ID once another Spark session has ended, without T4's metrics.
- **An earlier session's history** is saved right after the start request is sent, so it overlaps the VMs' start instead of delaying it. Its metrics are read before the request, because the session that starts writes its own over them when it ends.
- **Rejected:**
  - *A one-time Fabric schedule for the history or the end:* a schedule carries no notebook parameters, so the session's ID, beats, and metrics would need another hand-off; its failures show only in the Monitoring hub; queued jobs expire after 24 hours; and a throttled capacity rejects them anyway. Its one gain, Run all ending before the session does, is what `WAIT_FOR_END = False` already gives.
  - *A smaller pool for the control's workspace:* not needed for admission once the history submits no job, and a public vault's control notebook shares the demo workspace's pool with the demo's own notebooks. It stays a follow-up if the capacity's units matter more than the session's speed.
  - *Checking the capacity's Spark load first:* the control never reads or changes the capacity (the user's decision), and a check before a job would race with other sessions anyway.
- **R844 stays accepted:** Run all holds its one session for about two hours, and that's now the whole session's Spark use, history included.
- **Unproven until the capacity is resumed:** the reference run from the control workspace into the demo workspace, and the default lakehouse across workspaces. The first live Run all on the user's F4 proves both, or its fallback line says why.

### 2026-11-16 amendment: the history's reference run and its job

**Live, the new user's first Run all on an F4** (session 1ce548a4). The reference run started across workspaces with the demo's lakehouse, as designed, and stopped 32 seconds in, at the activity notebook's first chart (section 6). Fabric runs its secret redaction on each cell's result and then parses it; that parse failed: "Unrecognized token 'REDACTED' ... column: 299381". The Estate pulse table before it passed. The control notebook had read the session's two secrets, which hold `{}` until a first session ends, and Fabric replaces "the secret values that are displayed in cell output with [REDACTED]" ([secret redaction](https://learn.microsoft.com/fabric/data-engineering/author-execute-notebook#secret-redaction)): the likely cause, which the run's snapshot confirms or not in the next window. The fallback job was then **queued** (NotStarted) until Run all's own session ended, although the page above says queueing doesn't apply to jobs submitted through the public API. Run all waited 30 minutes for it, holding the F4's one Spark session, and it started 5.5 minutes after the session ended.

- **A reference run prints, it doesn't display:** with `isReferenceRun` ([NotebookUtils runtime](https://learn.microsoft.com/fabric/data-engineering/notebookutils/notebookutils-runtime)), the activity notebook prints one line for each table (its rows and columns) and each chart (its panels), with no table value, no NaN or infinity, and nothing taken from a secret. A job or a run by hand shows them as before. `POSTGRES_METRICS` uses JSON's default separators, so its text is never the runbook's compact text of the same secret.
- **Run all never waits for the job:** one look at it. Completed is a **Pass**; Failed or Cancelled a **Warning** with the fix; queued says that Fabric starts it once this notebook's Spark session ends, and where its result shows.
- **Run all's last step ends its own Spark session** when a history job it started after a session's end still reads NotStarted, and the run is interactive (`isForInteractive`): `notebookutils.session.stop()`, after which no code runs, so it's the last statement of the last code cell ([session management](https://learn.microsoft.com/fabric/data-engineering/notebookutils/notebookutils-session-management)). A scheduled or pipeline run's session ends by itself. `WAIT_FOR_END = False` keeps its session.
- **A refused job** (HTTP 430: the capacity is full, a Trial, throttled, or its queue is full, 4 jobs on F2 and F4) stays a **Warning**, and the next Run all saves the history first, as before.

### 2026-11-16 amendment: a host that stops during a session

**Live, the same session:** archost01's start ended `VMStartTimedOut` at 16:41:48, 53 minutes in, and T2's Run Command failed two seconds later. Its power state had said running, so T2's activity had gone out, and the session's status said so until its end. Nothing said otherwise: the session's job had ended, and `DbHub-Monitor` looked only at T1's plugin. The coordinator's decision: surface it as soon as the runbook knows it, with Azure Resource Manager reads only, no new Spark time, and no new polling loop.

- **The session's start checks its hosts** before its last write: each VM its activity went out to (one instance-view read) and each dispatch Run Command (one read, `$expand=instanceView`). A VM that's deallocated or stopped, a provisioning failure since the session's start (an older one, an extension's, say, isn't blamed on it), or a Run Command that ended Failed, TimedOut, or Canceled is a **Warning** step, `Host`, with the fix. The status records the dispatch Run Commands (`runCommands`: VM, name, targets).
- **A VM agent that isn't Ready** (2026-11-17; live, the T2 host's agent never got its goal state after the session's start, and the status said T2's activity went out for the whole 30-minute session): a VM that runs, with its agent not **Ready** 15 minutes or more after its targets' activity went out (`dispatchUtc`), is a `Host` **Warning** too. The instance view read above carries the agent's status, so it costs no read. The session's own check comes right after the dispatch, so it's the re-checks that find it, 30 minutes into a session of 40 minutes or more.
- **`DbHub-Monitor`'s 30-minute re-checks look again** while the session runs, and add a new problem to the status once. The control identity can't read the vault's value through Azure Resource Manager, only write it, so the runbooks keep a copy of each status they write in the Automation account's variable `DbHubSessionStatus`, which `infra/control/control.bicep` creates. They use the sandbox's internal `Set-AutomationVariable` and `Get-AutomationVariable`, which need no role ([variables](https://learn.microsoft.com/azure/automation/shared-resources/variables)). A missing variable, or a sandbox without the cmdlets, is skipped with one log line.
- **Never over a newer status:** the monitor reads the copy again right before its write, and writes only when it's the same one, untouched since its first read (`updatedUtc`), of a session that still runs; otherwise it says so in one log line and writes nothing.
- **Run all's live cell** reads the session's status again at most every 5 minutes, in its existing loop, and prints each new step with its fix. The notebook's read and identity are the same as before: the vault's status secret.
- **Mixed versions:** a notebook from before reads no status in its live view, so it runs as before and doesn't show the host live; a notebook beside runbooks from before finds nothing new.

### 2026-11-19 amendment: each target's showcase counts from when its runner set it

**Live, 2026-11-19:** the guide and the live view anchor each target's beats on `dispatchUtc`, which the runbook stamps when Azure accepts the target's dispatch Run Command. The runner counts each target's showcase cycles from when `profile set` ran on the VM (`ActivityProfiles`, `state.SetAt`). On a VM that had just started, sqlvm01's Run Command set T3's profile 2 minutes 41 seconds after Azure accepted it. So every planned time of T3's showcase came that much early: "Now: T3 Respond" printed while T3's CPU was still at 99%, and the `database_agent` finding's window after the response held 1.6 minutes of the regression (CPU 99% to 37%, where it fell to about 5%). A slower start could have made it a false **Warning**. The coordinator's decision: fix it in the runbook only.

- **The dispatch script** (`Get-DbHubWorkloadScript`) records, for each target that got its activity, the VM's UTC time right after its set returned, seconds after the runner's own, and writes them in one `DBHUB-SET` line at the end of its output, before `DBHUB-DISPATCH`, within what the instance view keeps.
- **The session's host check** (`Get-DbHubSessionHealth`), which already reads each dispatch Run Command's instance view, moves each of the command's targets' `dispatchUtc` to that time (`Get-DbHubDispatchSetTime`): only later, by more than 5 seconds and at most an hour, so it's idempotent. The session's start runs that check right before it writes `running`, which is when the notebook computes the guide's beats, the live view's, and `SESSION_PLAN`, so all three count from it, with no notebook change. No new read: it's the instance view the check already reads.
- **Not covered then:** a Run Command that hasn't ended by the start's check (T2's, whose guest a cold start can keep waiting for minutes) kept the accepted time. `DbHub-Monitor`'s re-checks moved it too, but wrote it only with a new `Host` step, and the notebook didn't recompute its beats after the guide, so T2's planned times stayed as early as before. T3's Database Agent beat runs on sqlvm01, which the start's check covers. Covered since 2026-11-20 ([below](#2026-11-20-amendment-a-target-whose-activity-is-set-after-the-sessions-start)).
- **Mixed versions:** runbooks from before write no `DBHUB-SET` line, and nothing moves; `deploy.ps1` republishes the runbooks when they differ (`CONTROL.RUNBOOKS`).

### 2026-11-19 amendment: a session's stop keeps its plan

The Insights app's **Stop now** cancels the control's run in progress, which may be saving a session's history ([ADR 0029](0029-insights-app-dba-console.md)), and then runs the control's own Stop now, which saves that session's history again, as the next Run all's pre-check does for an earlier session. Those saves passed no plan, because the session's stop replaced its status with one that said only what was done. So a save that the cancel cut off before its `scenario_runs` rows was never completed with the session's row or its beats' rows (nor, cut off before its findings, their correlation and its `database_agent` finding), and since nothing said the session was saved, every later Run all and Stop now analyzed it again, for 7 days.

- **The stop keeps the plan:** `Write-DbHubStopStatus` copies the session's window, its targets' dispatch times, T4's tier, the replica-lag beat, and T5's end (`acceptedUtc`, `runEndUtc`, `dispatchUtc`, `t4`, `replicaLag`, `t5`) from the status it replaces, read from the `DbHubSessionStatus` copy above, when that copy is the same session's, and `planKept` says whether it did. `phase` still says `stopped`, so nothing reads it as a session that runs.
- **The re-saves pass the plan:** Stop now's save (`stopped_history`) and the pre-check's (`LEFTOVER`) rebuild the session's beats from that status as its end does (`status_beats`), so the activity notebook completes the save table by table ([R907](../implementation-report.md#a-sessions-history-saved-once-r907-2026-11-19)) and writes the session's row, which says it's saved, last. With the plan in the status, Stop now saves a session whose metrics the vault doesn't have too, without T4's and T5's metrics. A session stopped during its start, before it had an end, has no beats, as at its end, and its window ends at its stop.
- **When the status has no plan** (a stop by runbooks from before this amendment, which write no `planKept`; a stop that didn't find the session's status in the copy; or a later session's status that replaced it), the plan is the session's window from its metrics, with no beats: its history is saved without its beats, as before, and its row still says it's saved, so it's analyzed at most once more. A **Warning** says so once: after a reference run that saved it, not when the activity notebook answers that the session was already saved, or, for a history job, whose answer the notebook doesn't read, as the job starts, "unless it's saved already". For older runbooks its fix is `./scripts/deploy.ps1`, which republishes them. A session's end now passes the plan whenever its window is known, with no beats too, so such a session is recorded as saved.

### 2026-11-20 amendment: a session that start-demo.ps1 took over ends without stopping the demo

`start-demo.ps1` replaces a running session's auto-stop with its own, marked `[start-demo.ps1]` ([ADR 0020](0020-on-demand-activity-control.md#amendment-2026-11-19-start-demops1-schedules-its-own-auto-stop)). But a Run all that still followed its session sent its stop at the session's planned end, and that stop stopped the demo under the `start-demo.ps1` session, hours before that session's auto-stop. The owner's follow-up (2026-11-20): the newer session's own stop wins.

- **The end stops nothing:** a stop with the session's ID that comes at its planned end, while the pending `dbhub-autostop` is a `start-demo.ps1` one later than now, stops nothing (`Get-DbHubSessionTakeover`, `Complete-DbHubTakenOverSession`). "At its planned end" runs from 2 minutes before the status's `runEndUtc`, for the clocks, to 30 minutes after it, for a job that starts late.
- **The session still ends:** T4's and T5's metrics are saved for its history. Its busy marker is cleared while it's still this session's, so the nightly stop goes on as usual. Its status says it stopped, with `takenOver` (who, and when that auto-stop comes) and its plan, so the notebook saves its history with its beats. The VMs, T4, its read replica, T5's container, and the auto-stop stay as they are, and the notebook says "Taken over: ...", with that time and how to stop sooner.
- **No new request field:** the notebook's end and its Stop now send the same request, and the runbook refuses unknown fields, so a new field would make a newer notebook's end fail on runbooks not yet republished. The window needs no change to the request.
- **An explicit Stop now always stops everything** (the owner's intent; the re-review of 2026-11-20): one before a taken-over session's planned end, or more than 30 minutes after it, from the notebook or the Insights app, stops everything as before. One inside the window, while the status still says the session runs, sends the session's ID, so the runbook takes it for that end; its status comes back with `takenOver`, and the notebook's Stop now then sends a stop with no session ID, which the runbook never takes for a session's end, so it stops the `start-demo.ps1` session too. Stop now again after a taken-over end sends no session ID either: the status says it stopped. The Insights app runs the notebook's Stop now, so its **Stop now** stops the demo too.
- **Rollout:** the runbooks, which `./scripts/deploy.ps1` republishes (`CONTROL.RUNBOOKS`), and the control notebook, which it imports. Either one alone works: runbooks from before stop the demo at the end as before, and a notebook from before prints the taken-over end's `done` list after "Stopped:".
- **Validation:** unit-tested (`tests/unit/Automation.Runbooks.Tests.ps1`: the end, an explicit Stop now before it, and one 45 minutes after an end that sent no stop; `tests/unit/Fabric.ControlNotebook.Tests.ps1`: the notebook's messages and the history's save). Not run live.

### 2026-11-20 amendment: a target whose activity is set after the session's start

The owner's follow-up after the release: T2's session times after a cold start ran a few minutes early. T2's dispatch Run Command waits for the guest (up to 12 minutes for its heartbeat, then for its SQL Server), so it often hadn't ended by the start's check, which then kept T2's accepted time ([above](#2026-11-19-amendment-each-targets-showcase-counts-from-when-its-runner-set-it)). The runbook now follows such a Run Command, and the notebook counts the target's beats from when it set the activity.

- **The start says which targets are pending:** the start's check (`Get-DbHubSessionHealth -Unfinished`) lists each dispatch Run Command whose instance view is Pending, Running, or Unknown. Their targets go into the status's `dispatchPending`, with a `Times` step (Info) for each: "T2: its activity isn't set on archost01 yet ...". A Run Command that can't be read keeps today's behavior: its targets aren't pending.
- **The start follows them:** after the start writes `running`, its job reads each such Run Command's instance view every 20 seconds (`Wait-DbHubSessionDispatch`). It stops at 51 minutes (the longest dispatch timeout, 50, and a minute), at the session's end, or once the session is stopped (`Test-DbHubSessionOpen`). When one ends, `Update-DbHubSessionHealth` moves its targets' `dispatchUtc` to the `DBHUB-SET` time, takes them out of `dispatchPending`, and adds a `Times` step ("T2: its activity was set on archost01 12 minutes after ..."), or a `Host` **Warning** when the Run Command failed. It writes the status with the same guard as before, never over a newer one, and tries again up to 3 times when another job wrote the status meanwhile. These are reads only, one instance view per Run Command per poll, so a warm start, whose Run Commands have all ended by the start's check, costs nothing more.
- **DbHub-Monitor writes a move too:** its re-check now writes the status when a time moved, or `dispatchPending` changed, with no new `Host` step (outcome `Moved`), so a Run Command that ends after the start stopped following it is covered too.
- **The notebook holds and recounts:** the guide marks a pending target ("its times above come later by as much"). The live view announces none of a pending target's beats (nor the Database Agent view while T3 is pending), and reads the status at every refresh while one is pending instead of every 5 minutes. When a target's anchor moves, it recomputes the beats (`moved_targets`, `status_beats`), prints that target's beats still to come, and announces them at their times. The session's end saves the history with those beats, and Stop now and the pre-check rebuild them from the status, as before.
- **Mixed versions:** runbooks from before write no `dispatchPending`, so a newer notebook runs as before. A notebook from before ignores `dispatchPending` and prints the `Times` steps as any other step. `./scripts/deploy.ps1` republishes the runbooks and imports the notebook.
- **Validation:** unit-tested (`tests/unit/Automation.Runbooks.Tests.ps1`: the start's pending targets and its follow-up's move; DbHub-Monitor's `Moved` after the start stopped following; a warm start unchanged. `tests/unit/Fabric.ControlNotebook.Tests.ps1`: T2's beats held, then announced and saved from the moved time). Not run live.

### 2026-11-21 amendment: an auto-shutdown that deploy.ps1 moved

F25 (live, `dbhubfr` at bf010ed): a Run all during the hour after a `deploy.ps1` that the nightly stop waited for lost its VMs at that run's deferred stop's time. `deploy.ps1` had moved the VMs' DevTest Labs auto-shutdown there, and the session planned from `autoShutdownTime` alone. The session can't move it back (no DevTest Labs action, [below](#the-permissions-one-time-by-an-owner)), so it ends before it: the demo resource group's `DbHubAutoShutdownMoved` tag says where it is, and the **Plan** step says so, with the fix (Run all once it has passed, or `./scripts/stop-demo.ps1` first). The deferred pass already waits for the session's busy marker. ### 2026-11-21 amendment: "Run all is ready" only when Run all can start a session (F28)

### Nothing beyond Azure and Fabric

A demo session needs nothing beyond Azure and Fabric (the user, 2026-11-14: "We really just care about the deployment of the assets, and running the notebooks and activity"):

- **No GitHub Actions** (item 5) and no script on a PC.
- **No license handling:** viewers' Power BI licenses are assumed (Pro, the user's decision), so nothing detects, assigns, or works around them, and `PREFLIGHT.FABRIC.VIEWERLICENSE` is **Not selected** ([ADR 0012](0012-validation-model.md)).
- **The capacity stays the user's:** the control never checks, starts, or pauses it. The capacity runs the notebook, so a session that runs proves it's active; `deploy.ps1` only reports a paused capacity, with a clear message, and changes nothing in Fabric until it's active.

### In every deployment

`deploy.ps1` sets the control up on every run, for a new environment and an existing one, with nothing to turn on:

- **No switch:** `control.enabled` is ignored. An older configuration's `"enabled": false`, which `init.ps1` wrote by default, gets one line (`DEPLOY.CONTROL.ON`). A control set up before 2026-11-14 is adopted as it is: the same names, so the same resources, updated in place.
- **Azure part:** the setup without Fabric (the vault's mode, the group, the template, the runbooks with this code, the T4 safety stop, the webhook, the session's secrets, and the roles) runs beside the nightly safety stop while the tracks run.
- **Fabric part:** the notebook goes into Fabric after the Fabric track, where the vault actually is (`publicNetworkAccess`), with the demo's lakehouse as its default lakehouse ([above](#the-historys-spark-session-2026-11-14)). While the capacity isn't Active, nothing in Fabric changes: a Warning, and the next `deploy.ps1` does it. The capacity is never resumed or paused.
- **Never a Fail:** what doesn't work is a Warning with its fix ([ADR 0012](0012-validation-model.md)), never in DONE's way, as the nightly safety stop's problems are. The status page's **Session control** row and DONE's line say where Run all is, or what it still needs and who does it.
- **Preflight:** P2 also registers `Microsoft.Automation`, `Microsoft.KeyVault`, and `Microsoft.ManagedIdentity`. `Microsoft.Network` was already required; a private vault's managed private endpoint needs it, on any Fabric capacity, Trial included ([prerequisites](https://learn.microsoft.com/fabric/security/security-managed-private-endpoints-create#prerequisites)).
- **The control workspace's name:** the demo workspace's name followed by " Control", so two environments in one tenant never share a workspace. "DBHub Control", the earlier default, stays for a control set up before 2026-11-14.
- **Shared roles:** custom roles belong to the whole subscription, so environments in one subscription share them, and a `deploy.ps1` on newer code updates them for every environment there. `control.roleNameSuffix` gives an environment its own two roles, "DbHub Demo Activity Operator (*suffix*)" and "DbHub Demo Session Writer (*suffix*)", for an environment beside a demo on other code (the test environments use it). A role that already has exactly its approved actions isn't written again, so a Contributor's `deploy.ps1` has nothing to report about it.

### The permissions (one-time, by an Owner)

`deploy.ps1` grants them when the person running it may (Owner or User Access Administrator). Otherwise each missing one is a **Warning** with `./scripts/grant-safety-stop.ps1`, which an Owner runs once for the safety stop and the control together, as for the safety stop ([ADR 0024](0024-nightly-safety-stop.md)). Until then, Run all runs a session without what's missing and says so. Contributor stays the minimum for everything else ([ADR 0008](0008-identity-rbac-abac.md)).

**"DbHub Demo Activity Operator"** (A1 at the demo resource group, A2 at the control's Automation account) gains five actions:

| Action | What the session uses it for | What it could also touch, at the demo resource group |
|---|---|---|
| `Microsoft.DBforPostgreSQL/flexibleServers/write` | Creates T4's read replica | Could change T4; the runbook never does |
| `Microsoft.DBforPostgreSQL/flexibleServers/delete` | Deletes the replica after a session | Could delete T4; the runbook deletes only a server whose `replicationRole` says it's a read replica |
| `Microsoft.DBforPostgreSQL/flexibleServers/configurations/write` | Sets the replica's `max_standby_streaming_delay`, which the replica-lag beat needs | Could change any server parameter of T4 or the replica |
| `Microsoft.Insights/metrics/read` | Reads T4's and the replica's Azure Monitor metrics for the history | Read-only |
| `Microsoft.Resources/tags/write` | Marks the demo busy and records the session | Could change any tag in the demo resource group, `deploymentId` included |

No network join action: the replica's create names T4's delegated subnet and private DNS zone, and Azure created it for a role without `Microsoft.Network/virtualNetworks/subnets/join/action` and `Microsoft.Network/privateDnsZones/join/action` (live, 2026-11-14, 70 minutes after they were removed), so neither is granted. As first approved, the role had seven actions here, with those two.

Azure has no narrower action and no name condition for these: attribute-based conditions cover storage data actions only. A delete lock on T4 would block the identity's delete of T4, but `destroy.ps1` as a Contributor couldn't remove it, so there's none.

**Since 2026-11-19** ([ADR 0027](0027-t5-cosmos-db.md), approved for the user by the coordinator, who reviews it with the owner before any merge), three more, at the demo resource group only (A1), because T5's container exists only during a session: its provisioned throughput bills every hour it exists, and an Azure Cosmos DB account has no stop ([Azure Cosmos DB's permissions](https://learn.microsoft.com/azure/role-based-access-control/permissions/databases#microsoftdocumentdb)):

| Action | What the session uses it for | What it could also touch, at the demo resource group |
|---|---|---|
| `Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/read` | Reads whether T5's container is there, before T5's activity and after a delete | Any Azure Cosmos DB container's settings there, where T5's account is the only account; never its documents |
| `Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/write` | Creates T5's container at a session's start | Could change any container there; the runbook creates `contosocare/patient-events` only |
| `Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/delete` | Deletes T5's container at a session's stop | Could delete any container there; the runbook deletes `contosocare/patient-events` only, and only while the demo resource group's `DbHubT5Container` tag is `Session` |

Nothing of the account itself, its keys, its network, or its data plane: T1's own data-plane role reads and writes the documents.

**"DbHub Demo Session Writer"** (A4, new), for the same identity at the control vault's two session secrets only, never at the demo resource group, whose optional vault it never reaches:

| Action | What the session uses it for | What it could also touch |
|---|---|---|
| `Microsoft.KeyVault/vaults/secrets/read` | Reads the session secrets' properties (Azure Resource Manager never returns a value) | Nothing else: those two secrets only |
| `Microsoft.KeyVault/vaults/secrets/write` | Writes the session's status and metrics | Could overwrite those two secrets' values, which the notebook reads as status and metrics, never as credentials |

**A3** (Key Vault Secrets User) extends from the webhook's secret to the two session secrets, for the signed-in owner and `control.notebookUserObjectIds`, so the notebook can read them.

**A3 for the environment's deployer** (2026-11-19, the coordinator's fix from the docs audit): a Contributor's `deploy.ps1` can't give its deployer the three secrets, and the Owner's `grant-safety-stop.ps1` gave them only to the Owner and `control.notebookUserObjectIds`, so the person who deployed still couldn't Run all. The Owner's one run now gives them to the deployer too, with nothing to edit: the person whose `deploy.ps1` last set up the control vault, as Azure Resource Manager records it on the vault (`systemData.lastModifiedBy`, a user's sign-in name; every `deploy.ps1` run deploys `control.bicep`, and the grant changes nothing on the vault), resolved to an object ID through Microsoft Graph (`CONTROL.ROLE.DEPLOYER`). Nobody else: a change by an application or a managed identity (a GitHub workflow's deployment) names no person, and a name that doesn't resolve to exactly one user gives nobody, with a **Warning** and the fix, because the webhook URL is a bearer secret. `deploy.ps1`'s own grant is unchanged: its caller is the deployer.

**No DevTestLab action** (the coordinator's decision for the user, 2026-11-14: grant only what the runbook uses): the two that were pre-approved to move the VMs' auto-shutdown for a session aren't in the role. A session ends before the auto-shutdown instead, as a run always has, because the profile hosts on T1 and in T2's guest end their activity there (`--not-after`, set when they start); moving the auto-shutdown alone wouldn't keep a session's activity going. Running past it would need those hosts to take a later end too, a change on the VMs that the [implementation report](../implementation-report.md) lists as a follow-up.

## Consequences

- **Easier:** a session is one action, Run all, with nothing to edit, no script, and no GitHub; the replica beat and the history's PostgreSQL metrics come with it, and a session can't be cut off by the nightly stop.
- **Harder:**
  - The control identity can change or delete T4 and change tags in the demo resource group (above).
  - The runbook ports the replica's size order and its creation from the module, so two copies follow the same rules: tests run the same cases against both.
  - A session started late in the day is shorter (it ends before the VMs' auto-shutdown), and says so. Follow-up: let the VM-side profile hosts take a session's end, then move the auto-shutdown during a session as `deploy.ps1` does.
  - Run all takes longer to start in the control workspace (3 to 5 minutes for its managed network), and the replica's creation (about 9 minutes) runs while the VMs start.
