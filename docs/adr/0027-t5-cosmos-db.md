# ADR 0027: T5, an Azure Cosmos DB for NoSQL account

- **Status:** Accepted. Live validation: [below](#validation).
- **Date:** 2026-11-18; updated 2026-11-19 (the container only during a session)
- **Decision source:** User-directed (2026-11-18: review item 2 of the Ignite 2026 announcements, "Azure Cosmos DB as T5", in "Create a new branch and do them all"; 2026-11-18: "Make sure to account for users signing in and demoing this themselves and repeatable. Simple and one click as possible"), with the coordinator's decisions (a private endpoint in both network modes rather than a service endpoint; the free tier when the subscription's one slot is free) and the implementer's engineering detail
- **Related:** [ADR 0008](0008-identity-rbac-abac.md) (Contributor only), [ADR 0010](0010-workload-generator-technology.md) (the runner and bounded workloads), [ADR 0012](0012-validation-model.md) (statuses), [ADR 0016](0016-cost-profiles.md) (cost), [ADR 0018](0018-fast-redeploy-parallel-tracks-golden-snapshot.md) (tracks and DONE), [ADR 0019](0019-t4-postgresql-flexible-server.md) (T4, the pattern T5 follows), [ADR 0026](0026-one-run-all-session.md) (Run all)

## Context

- **Database Hub in Microsoft Fabric is generally available (Ignite, 2026-11-17)**, and it covers Azure Cosmos DB: the account in Overview and Estate, its own Performance view, and its security posture ([monitor Azure Cosmos DB in Database Hub](https://learn.microsoft.com/fabric/database/hub/monitor-cosmos-db), checked 2026-11-18). The demo had SQL Server on a VM (T1), Arc-enabled SQL Server (T2), Azure SQL Database (T3), and PostgreSQL (T4), and no Cosmos DB.
- **Database Hub reads Cosmos DB from Azure Monitor platform metrics, with no setup** (the same page): Normalized RU Consumption (Maximum), Total Request Units (Total), Throttled Requests (`TotalRequests` with `StatusCode` 429, Count), Provisioned Throughput (Maximum, at a 5-minute grain or coarser), Avg Latency (`ServerSideLatencyDirect`, Average; direct-mode connections only), and Availability (`ServiceAvailability`, Average, hourly). Its charts use an hourly grain. The Security page evaluates Microsoft Entra-only access (local authentication off), public network access (an Issue when it's on), and customer-managed keys (a Suggestion).
- **Normalized RU Consumption** is the highest share of the provisioned RU/s that one partition key range used in a minute; 100% means requests beyond it are rate-limited with 429 ([normalized RU](https://learn.microsoft.com/azure/cosmos-db/monitor-normalized-request-units), [429s](https://learn.microsoft.com/azure/cosmos-db/nosql/troubleshoot-request-rate-too-large), checked 2026-11-18). That's the DBA moment the review asked for: a hot partition drives it to 100%, the 429s show, and both recover when the load stops.
- **Prices** (Azure Retail Prices API, 2026-11-18, West US 3, list, USD; dated examples, ADR 0016): provisioned throughput `Azure Cosmos DB / RUs / 100 RU/s` $0.008 an hour, so 400 RU/s is $0.032 an hour, $23.36 a month; storage $0.25 a GB-month; the Free Tier meters $0. Defender for Azure Cosmos DB `Standard 100 RU/s` $0.0012 an hour (about $3.50 a month at 400 RU/s). A private endpoint `Standard Private Endpoint` $0.01 an hour ($7.30 a month), its private DNS zone $0.50 a month. **The free tier** covers the first 1000 RU/s and 25 GB of one account per subscription, and Azure sets it only when an account is created ([free tier](https://learn.microsoft.com/azure/cosmos-db/free-tier), checked 2026-11-18).
- **An account can't be stopped or paused**: provisioned throughput bills every hour it exists.
- **A container's throughput can't be taken away** (2026-11-19): manual throughput goes down to its minimum, 400 RU/s, and no lower; dedicated throughput can't become a shared database's or the reverse, which is set only when the database and the container are created ([provision throughput](https://learn.microsoft.com/azure/cosmos-db/set-throughput), checked 2026-11-19). So the only way to stop a container's throughput from billing is to delete the container. A database without throughput of its own bills nothing.
- **Permissions:** the data plane's role-based access control is the account's own `sqlRoleAssignments`, not an Azure role assignment, and `Microsoft.DocumentDB/databaseAccounts/sqlRoleAssignments/write` is within Contributor ([grant data-plane access](https://learn.microsoft.com/azure/cosmos-db/nosql/how-to-grant-data-plane-access), checked 2026-11-18). With local authentication off (`disableLocalAuth`), no key works for data ([connect with role-based access control](https://learn.microsoft.com/azure/cosmos-db/how-to-connect-role-based-access-control)).

## Decision drivers

1. **One click, every time:** after `az login`, `./scripts/deploy.ps1` deploys T5 on a first deployment and adds it to an older demo, with nothing for a person to do, and anyone who deploys the demo can demo T5 themselves.
2. **No secrets** and **Contributor as the minimum** (ADR 0008, ADR 0009).
3. **Secure by default:** no public network access, so Database Hub's Security page shows no Issue for T5.
4. **The DBA moment, repeatable:** normalized RU to 100% with 429s, then recovery, in every Run all, with the data, the RU, and the 429s back at their baseline before the next session.
5. **Lowest cost**, priced at run time, and failures and fallbacks on the status page.

## Considered options

| Area | Option | Outcome |
|---|---|---|
| Capacity | Provisioned throughput, 400 RU/s manual, on the container | **Chosen**: the minimum, a fixed ceiling that a hot partition reaches, and the normalized RU and Provisioned Throughput charts Database Hub draws |
| | Autoscale (1000 RU/s maximum, 100 RU/s floor) | Rejected: a storm scales instead of throttling until it reaches the maximum, and it costs more at the peak |
| | Serverless | Rejected: no provisioned throughput, so Database Hub's normalized RU view has nothing to normalize against |
| Network | A private endpoint in both network modes, public network access off | **Chosen** (the coordinator's decision): the same in both modes, no Issue on the Security page, and no policy that blocks public data services can stop it. $7.80 a month with its DNS zone |
| | A service endpoint on T1's subnet in public mode | Rejected: the account would keep public network access on (an Issue), and two network shapes for one target |
| Authentication | Microsoft Entra only: T1's managed identity with Cosmos DB Built-in Data Contributor, scoped to the account | **Chosen**: no key exists anywhere, and the assignment is a child resource that Contributor creates |
| | Account keys in a Key Vault | Rejected: a secret, and a Key Vault, which the default path doesn't create (ADR 0009) |
| Client | The documented REST API from the existing .NET runner, with an Entra token, over HTTPS 443 (gateway) | **Chosen**: no new package, and only port 443 through the private endpoint. Database Hub's Avg Latency stays empty (it charts direct-mode latency only) |
| | The Azure Cosmos DB .NET SDK in direct mode | Rejected for now: a new dependency and ports 10250 to 10255 through the private endpoint, for one chart |
| Where it's deployed | In the main template, with T3 and T4, and T5's checks as a step of T1's track | **Chosen**: one template deployment, and the runner's checks go through T1, which runs one Run Command at a time |
| | A track of its own | Rejected: its only work that doesn't need T1 is a read |
| Idle cost (2026-11-19) | The container only during a session: created at a session's start and deleted at its end through Azure Resource Manager; the account, its database, private endpoint, DNS zone, and T1's data-plane role stay | **Chosen** (the coordinator's follow-up, 2026-11-18): T5's throughput bills only while the demo runs, like the VMs' compute, and Database Hub keeps T5 in its estate. It needs the session control's role to create the container again (below) |
| | Keep 400 RU/s around the clock | Rejected: $23.36 a month at list price (2026-11-18), which most users of the demo pay, because internal subscriptions can't have the free tier, for a target that works only during sessions |
| | Autoscale | Rejected: its floor (a tenth of its maximum, at least 100 RU/s) still bills every hour, at autoscale's rate, and with a 1000 RU/s maximum a storm needs more than twice ru-storm's load before it throttles |
| | Shared throughput on the database | Rejected: the database then holds at least 400 RU/s all the time, the same cost, and a container's dedicated throughput can't move there anyway |
| | Delete the whole account between sessions | Rejected: Database Hub's estate would lose T5 between sessions, each session would wait for the account, its private endpoint, and T1's role again, and an account created again loses the free tier's slot to any other account that took it |

## Decision

### The account

- **`cosmos01-<deploymentId>`** in `rg-<prefix>-<environment>` (`infra/modules/cosmos01.bicep`, `config/versions.json` `cosmosdb`): Azure Cosmos DB for NoSQL, one region without zone redundancy or automatic failover, Session consistency, `disableLocalAuth` and `disableKeyBasedMetadataWriteAccess` true, `publicNetworkAccess` Disabled, TLS 1.2. The database **`contosocare`** and the container **`patient-events`**, partitioned by **`/patientId`** (hash, version 2), at **400 RU/s** of manual throughput on the container. Every path is indexed except the documents' `payload` filler, which nothing queries, so a write costs its size and not its index.
- **No availability zones or continuous backup:** zones multiply standard provisioned throughput by 1.25 ([pricing](https://azure.microsoft.com/pricing/details/cosmos-db/standard-provisioned/)), and point-in-time restore isn't part of the demo, whose runner writes its data again, so the default periodic backup applies. `ps-rule.yaml` suppresses PSRule's `Azure.Cosmos.AvailabilityZone` and `Azure.Cosmos.ContinuousBackup` for `cosmos01` with that reason.
- **The private endpoint `pe-<prefix>-<environment>-cosmos01`** in `snet-pe`, group `Sql`, with the `privatelink.documents.azure.com` zone linked to the virtual network and a zone group, in both network modes. `snet-pe`'s network security group lets T1's subnet reach it on TCP 443 (`Allow-Cosmos-From-T1`).
- **T1's data-plane role** (`infra/modules/cosmos01-access.bicep`): a `sqlRoleAssignment` of Cosmos DB Built-in Data Contributor (`00000000-0000-0000-0000-000000000002`) to sqlvm01's system-assigned identity, scoped to the account, with a deterministic name, so a redeploy changes nothing. No Azure role assignment.
- **The free tier:** `deploy.ps1` decides it before the template (`Resolve-DemoT5FreeTier`, `DEPLOY.T5.FREETIER`): an existing account keeps what it has; a new one gets it when the subscription isn't internal and Azure Resource Graph lists no other account in the subscription with it, and not when Resource Graph can't be read. Azure refuses the free tier in internal subscriptions ("Free tier is not supported for Internal subscriptions", live 2026-11-18, `subscriptionPolicies.quotaId` `Internal_2014-09-01`), so the run reads the subscription's offer first ([Subscriptions - Get](https://learn.microsoft.com/rest/api/resources/subscriptions/get)) rather than lose a failed template's 7 minutes. A refusal deploys the template again without it, once, with a Warning that gives Azure's reason. The refusal is checked before T3's free offer, and only an error detail that's Azure Cosmos DB's counts (`Test-DemoT5FreeTierRefusal`: the detail names Cosmos DB, its resource provider, or T5's `cosmos01` deployment); T3's own check ignores Cosmos DB's details and no longer takes "free tier" for its offer (review, 2026-11-19). So a refused T5 never moves T3 off the Azure SQL free offer, which a database can't get back, and an Azure SQL error never costs T5 a free tier that Azure sets only at creation. `t5UseFreeTier` false never asks for it.
- **Turning it off:** `t5Enabled` false in the configuration leaves T5 out of the template, the checks, the activity, and DONE (`DEPLOY.T5.OFF`, Not selected); an account an earlier run created stays and keeps billing until `destroy.ps1`. Preflight's policy check then leaves T5's Azure Cosmos DB types out too, so a policy that denies them no longer stops the run; with T5 on, a policy that denies only T5's types is a **Fail** whose fix is `t5Enabled` false (`PREFLIGHT.POLICY.RESOURCETYPES`; review, 2026-11-19).
- **When Azure doesn't create T5** (review, 2026-11-19): a run that creates T5's account and whose template failed in T5's resources alone (a region without capacity for new Azure Cosmos DB accounts, or a policy that denies them that preflight couldn't evaluate) deploys the template again once without T5, so the rest of an update finishes and can end **DONE**. `DEPLOY.T5`, a **Warning**, gives Azure's reason and the fix when it lasts (`t5Enabled` false, or another region), on the console, the status page's Infrastructure and T5 rows, and at the end. The resource group records it (`DbHubT5Refused`), so a resume leaves T5 out too rather than start from preflight (`DEPLOY.T5.MISSING`) and fail the same way; the next run that deploys the template tries T5 again and clears the record when it's created. An account that existed before the run is never left out: its failure stays a **Fail**, whose fix says how to deploy without T5.

### Deployment, upgrade, and DONE

- **T1's track** has a **T5** step in stage T4, after T4's: `Test-DemoT5` (`T5.ACCOUNT`, `T5.ENTRAONLY`, `T5.NETWORK`, `T5.CONTAINER`, `T5.FREETIER`, `T5.ACCESS`), then the runner's warmup through T1 (`WORKLOAD.T5.WARMUP`: a token, a read of the container, an upsert and a point read of one document), tried again every 45 seconds for up to 10 minutes while the new data-plane role and the private DNS record come into effect. A T5 failure doesn't stop T1's track. The Activity step sets T5's profile with T1's.
- **The run's validation** checks T5 in Database Hub's estate (`HUB.ESTATE.T5`, Azure Resource Graph) and its Azure Monitor metrics (`METRICS.T5`: requests and normalized RU in the last 15 minutes). **DONE requires both**, when T5 is on.
- **An older demo:** `DEPLOY.T5.MISSING` makes a resumed run start from preflight when the account doesn't exist, so the template creates it; a plain `deploy.ps1` on a finished demo runs the template anyway. No step for a person.
- **The status page** has a T5 group (Account checks and T1's access; Metrics in Azure Monitor).

### The workload

- **The runner** (`workload-generator`, `--target T5 --server <account>.documents.azure.com`) talks to the documented REST API over HTTPS with an Entra token for T1's managed identity, acts only in `contosocare`/`patient-events`, and keeps a run store of its own (`C:\ProgramData\DbHubDemo\t5-runs.json`).
- **healthy-baseline** includes T5 (bounded upserts and point reads over a fixed set of ids, so the data stays flat). **ru-storm** (T5 only) drives normalized RU to 100% with 429s by writing to one hot partition key, then a calm phase lets it recover; its maximum duration bounds it (ADR 0010). It writes a bounded, deterministic set of documents and deletes them at its end, also when it's stopped or cancelled, and `reset-demo.ps1 -Target T5` removes any left over, so every session starts from the same data.
- **Run all's showcase timeline** (ADR 0026) runs ru-storm on T5 twice, and the session control's allow-lists include T5 and ru-storm. Each T5 storm slot has `recoveryMinutes` 2 (2026-11-19, R896): the runner skips a storm that couldn't end at least 2 minutes before its profile's end, rather than clip it, and one whose window began before the profile was set, so T5's profile runs the whole session, its baseline keeps going after its last storm, and no storm is running when the session ends.

### The container only during a session (2026-11-19)

The coordinator's follow-up of 2026-11-18 asked to remove T5's provisioned throughput while the demo is idle, if that's reliable; the owner's condition (2026-11-19, provisionally approved by the coordinator for the owner, who decides in the morning): **a session must never run without T5's container.**

- **The lifecycle:** the demo resource group's `DbHubT5Container` tag. **Session** once the session control's custom role ("DbHub Demo Activity Operator", or this environment's name for it) has the container's actions and its identity holds that role at the demo resource group, so Run all can create the container again after a stop deletes it. Also **Session** when its identity holds no role there at all (the coordinator's fix 1, [below](#2026-11-19-session-when-the-session-control-has-no-role-and-what-preflight-prices)). **AlwaysOn** while it holds a role that can't (an update by someone who isn't an Owner, until an Owner runs `./scripts/grant-safety-stop.ps1` once), and no tag in an environment deployed before 2026-11-19: then nothing deletes the container, as before, and a Warning says what it bills and how to fix it (`T5.LIFECYCLE`, `STATUS.T5`, `STOP.T5`), or a Pass on the free tier, where it costs nothing.
- **Who sets it:** `deploy.ps1`, right after the session control's setup, which updates the role for an Owner and publishes the runbooks that create the container (`DEPLOY.T5.LIFECYCLE` and the status page's **T5.Lifecycle** row); `grant-safety-stop.ps1` after an Owner's grants (`GRANT.T5.LIFECYCLE`: AlwaysOn becomes Session); and `stop-demo.ps1`, which checks the role again before it deletes anything and turns Session back into AlwaysOn when the role can't any more (a shared role that another deployment changed back, for example). Only `deploy.ps1` and the grant turn the lifecycle on, because they're the runs that know the runbooks can create the container. `Update-DemoT5ContainerLifecycle`, `Resolve-DemoT5ContainerLifecycle`.
- **Created at each start**, through Azure Resource Manager ([Create Update Sql Container](https://learn.microsoft.com/rest/api/cosmos-db-resource-provider/sql-resources/create-update-sql-container)), with the definition in one place, `config/versions.json` `cosmosdb` (partition key, its version, indexing policy, throughput), which `infra/modules/cosmos01.bicep` deploys too, and the demo resource group's own tags: `start-demo.ps1` while the VMs boot (`START.T5.CONTAINER`, `New-DemoT5Container`), Run all's session start before T5's activity (`New-DbHubT5Container`, a session step on the status), `demo-control.ps1` and the control's run action before an activity on T5 (`CONTROL.T5.CONTAINER`), and `deploy.ps1`'s T5 step (`DEPLOY.T5.CONTAINER`), because a resumed run skips the template. A create that Azure refuses while it still deletes the last container with that name is tried again for up to 5 minutes. A container that can't be created keeps T5's activity from starting, and the result says why, with the fix.
- **Deleted at each stop**, only with the lifecycle Session ([Delete Sql Container](https://learn.microsoft.com/rest/api/cosmos-db-resource-provider/sql-resources/delete-sql-container)): `stop-demo.ps1` at its end, once T5's metrics were read for the history (`STOP.T5`, `Invoke-DemoT5ContainerStop`); Stop now and the auto-stop after the VMs' deallocation (`Remove-DbHubT5Container`); the nightly safety stop and its deferred pass; and the control's daily T4 pass, while sqlvm01 is deallocated, for a night the safety stop couldn't. `deploy.ps1` leaves it, because the demo runs business-day until the nightly stop.
- **The roles** (provisionally approved, 2026-11-19; the owner decides before anything reaches `main`): the session control's "DbHub Demo Activity Operator" gains `Microsoft.DocumentDB/databaseAccounts/sqlDatabases/containers/read`, `/write`, and `/delete`; the nightly safety stop's "DbHub Demo Safety Stop" gains `containers/read` and `containers/delete` ([ADR 0024](0024-nightly-safety-stop.md), [permissions](../permissions.md)). Both are assigned at the demo resource group only, where T5's account is the only Cosmos DB account, and neither reaches the account, its keys, its network, or its data. `deploy.ps1` updates both definitions for an Owner before any session relies on them (`CONTROL.ROLE.DEFINITION` and `SAFETYSTOP.ROLE` say what was added); otherwise `grant-safety-stop.ps1` does, once.
- **What stays:** the account, the database `contosocare` (no throughput of its own, so it bills nothing), the private endpoint and DNS zone ($7.80 a month at list price, 2026-11-18), and T1's data-plane role, which is scoped to the account, so a container created again needs nothing else. Database Hub keeps T5 in its estate, and its metrics show the sessions with gaps between them, as the stopped VMs' do.
- **The data:** each session starts with an empty container. healthy-baseline writes its documents as it runs (its first reads miss until it has, which counts as requests, not errors), and ru-storm's hot partition doesn't need any, so no seed runs.
- **The runner** refuses an activity on T5 while the container doesn't exist, with the reason, and its profile host tries again every 30 seconds; a reset with no container has nothing to clean (Pass).

### 2026-11-19: Session when the session control has no role, and what preflight prices

The coordinator's decisions of 2026-11-19, provisional until the owner's review, after a Contributor's first deployment of the example configuration came to $397.34 in the worst case, over the $390 default ([ADR 0016](0016-cost-profiles.md#2026-11-19-a-first-deployments-worst-case-and-a-390-default-for-a-new-configuration)):

- **Fix 1: no role at all is Session.** When the session control's identity holds no role at the demo resource group (a Contributor's deployment, which can't assign it, or an identity that doesn't exist yet), Run all can't start a session, and the sessions that can run, `start-demo.ps1` and `demo-control.ps1`, create the container with the person's own rights. So a stop may delete it: the condition that a session never runs without the container holds. `Get-DemoT5ControlRoleState` reads the role definition and the identity's role assignments once (Mode `Control`, `NoRole`, `Lacking`, or `Unknown`, with why), and `Resolve-DemoT5ContainerLifecycle` records Session for `Control` and `NoRole`.
- **A control that holds a role without the container's actions stays AlwaysOn,** as before: an environment from `main` that someone who isn't an Owner updates (its control keeps its role from before 2026-11-19), or an identity that holds another role at or above the group. Run all could start a session there that couldn't create the container. `Unknown` keeps what's recorded (fail safe).
- **The status page says which mode applies and why:** `DEPLOY.T5.LIFECYCLE` and the **T5.Lifecycle** row (evidence `mode`). With no role: a **Pass** that says `start-demo.ps1` creates the container with your own rights and `stop-demo.ps1` deletes it, that Run all can't start a session yet, and the grant command that lets it. With a role that lacks the actions: the **Warning** with the grant command, as before.
- **What preflight prices** (the coordinator's gap fix): T5's throughput as this run's lifecycle step will record it (`Get-DemoT5CostLifecycle -ThisRunDeploys`): Session when the control will be able to create the container (its role has the actions, or the deployer can write them, and it holds the role, or the deployer can assign it) or will have no role at all; AlwaysOn when it will hold a role without the actions, or when that can't be read. `start-demo.ps1` and `estimate-cost.ps1` price what's recorded. When the run records AlwaysOn after all (a role update that fails, for example), `DEPLOY.T5.LIFECYCLE` gives the month's worst case again, with what AlwaysOn adds, against `monthlyCeilingUsd`, and the ceiling to raise when it's over.
- **Who gets which:** an Owner's first deployment and update: Session (the run writes and assigns the role). A Contributor's first deployment: Session (no role). A Contributor's or a Role Based Access Control Administrator's update of an environment from `main`: AlwaysOn until an Owner runs the grant, which turns it into Session (`GRANT.T5.LIFECYCLE`).
- **Validation:** unit tests (`tests/unit/DbHubDemo.T5.Tests.ps1`: each mode for a deployment, a grant, and a stop, the texts and evidence on the status page, and the price for a new environment, an update from `main`, an Owner, a Contributor, and a deployer who can assign roles but not write them, and the worst case again when the run records what preflight didn't price; `DbHubDemo.Preflight.Tests.ps1`: an Owner's and a Contributor's first deployment). Live: see the implementation report.
### Stop, start, cost, and teardown

- **No stop:** an account has no stop, so `stop-demo.ps1` turns T5's activity off and deletes its container (above): only the private endpoint and its DNS zone bill between sessions (`STOP.T5`). With the lifecycle AlwaysOn it keeps the container and says what bills on, with the fix (a Warning, or a Pass on the free tier). `start-demo.ps1` has no account to start (`START.T5`); it creates the container (`START.T5.CONTAINER`) and sets T5's profile.
- **Cost:** `estimate-cost.ps1`, preflight, and the Cost area price T5's throughput, its storage, and Defender for Azure Cosmos DB (`CosmosDbs`, when its plan is on Standard) for the hours the demo runs, as the VMs' compute, and the private endpoint and DNS zone all month (2026-11-19; `docs/cost-management.md` has the before and after). Throughput uses the Free Tier meters when the account has or gets the free tier, list price otherwise or when it wasn't checked. Defender CSPM doesn't bill Cosmos DB accounts. Dated example (2026-11-18 prices, West US 3, list): **$7.80 a month idle plus $0.032 an hour while the demo runs** (plus $0.0048 an hour with Defender for Azure Cosmos DB), down from $31.41 a month all month; **$7.80 on the free tier**, as before. An environment whose lifecycle stays AlwaysOn pays the old figure.
- **Teardown:** `destroy.ps1` deletes the account with the resource group; the residual check is by tag and resource group, so it covers T5 with no change.

### Monitoring, status, and history

- `status.ps1` reads T5's state and its metrics (`STATUS.T5`), `validate.ps1 -Area T5` runs `Test-DemoT5 -IncludeMetrics`, and its Workload area reads the runner's T5 status.
- **History:** the session's T5 metrics are captured from the operator side, as T4's are (`COSMOS_METRICS`), and the live-activity notebook writes them to the history tables, so the history model has T5's peak normalized RU, requests, 429s, and RU consumed.

## Consequences

- Database Hub shows five targets, and T5's Performance view has a moment worth presenting: normalized RU at 100%, throttled requests, and the recovery.
- T5's account bills $7.80 a month whatever the demo does (its private endpoint and DNS zone, dated example), and its container's throughput only while the demo runs (2026-11-19). Until the session control's role can create the container, it stays between sessions and bills as before, $31.41 a month at list price, and the status page says so, with the fix.
- Each session starts T5 with an empty container, so its data never carries over; its first minute of reads miss while healthy-baseline writes them.
- Two custom roles gain container actions at the demo resource group (2026-11-19); the owner reviews them before anything reaches `main`.
- The 429s are intended: the runner counts them as the scenario's signal, not as failures.
- Avg Latency stays empty (the runner uses the gateway), and Availability is hourly, so a 10-minute storm shows in normalized RU and throttled requests first.
- A subscription whose free-tier slot is taken pays list price; the run says which account has it.

## Validation

- **Unit tests:** `tests/unit/DbHubDemo.T5.Tests.ps1` (names, the free tier, the upgrade's resume, `Test-DemoT5`, `METRICS.T5`, `STOP.T5`, the warmup's retry), the cost estimate's T5 components (`DbHubDemo.Cost.Tests.ps1`), the tracks and the status page (`DbHubDemo.Tracks.Tests.ps1`, `DbHubDemo.Progress.Tests.ps1`), and the runner's own tests.
- **Unit tests only: Azure refusing T5's free tier next to T3's free offer** (review, 2026-11-19). No live test can reach it: every subscription the live tests use is internal, where T5 never asks for the free tier (its `quotaId`), and no test environment's T3 has the free offer.
