# ADR 0022: A public repository, and GitHub Actions hardened for it

- **Status:** Accepted. Built and checked statically on 2026-10-27; `setup-github-repo.ps1 -WhatIf` checked read-only against the private repository the same day; the GitHub settings and a live Actions run are pending until the public repository exists
- **Date:** 2026-10-27
- **Decision source:** User-directed (2026-10-26: "We want to make this public and then parameterize the fabric IDs, do not store them" and "automate as much as possible for other folks using the repo"; 2026-10-27: "I want them to test the seamless experience"), with the coordinator's decisions of 2026-10-26 and 2026-10-27 (environment secrets for the identifiers, masked logs, an opt-in schedule environment, and a new public repository created from `main` as one fresh commit)
- **Related:** [ADR 0008](0008-identity-rbac-abac.md), [ADR 0009](0009-secrets-handling.md), [ADR 0011](0011-control-surface-priority.md), [ADR 0012](0012-validation-model.md), [security model](../security-model.md), [permissions](../permissions.md), [deployment](../deployment.md#one-click-github-actions), [SECURITY.md](../../SECURITY.md)

## Context

- **The route to public.** The public repository is `MarcBushong/fabric-database-hub-demo`, created from this repository's `main` as one fresh commit, with no history; this repository stays private as the archive. So everything on `main` must be fit to publish, and the old history, branches, and pull requests stay private.
- **Public Actions logs and artifacts.** Anyone can read a public repository's workflow logs, and anyone signed in to GitHub with read access, which in a public repository is everyone, can download its artifacts ([downloading workflow artifacts](https://docs.github.com/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)). GitHub masks a secret's value in logs, but only in the exact form it was stored, and it advises against structured data such as JSON as a secret's value, because it can't mask its parts; `::add-mask::` masks any other value from then on ([secure use reference](https://docs.github.com/actions/reference/security/secure-use), [workflow commands](https://docs.github.com/actions/reference/workflows-and-actions/workflow-commands#masking-a-value-in-a-log)). Masking covers the log, not the job summary's file or the artifacts the workflow uploads.
- **Forks and pull requests.** A workflow that a pull request from a fork triggers gets no secrets and a read-only `GITHUB_TOKEN`; `pull_request_target` runs in the base repository's context, with its secrets, so checking out a pull request's code there is dangerous ([events that trigger workflows](https://docs.github.com/actions/reference/workflows-and-actions/events-that-trigger-workflows), [secure use reference](https://docs.github.com/actions/reference/security/secure-use)).
- **OpenID Connect.** The demo's GitHub identity trusts the subject `repo:<owner>/<repo>:environment:<name>`, so a token is issued only to a job of that repository that runs in that environment; a fork has another owner or name in its subject ([OpenID Connect in Azure](https://docs.github.com/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-azure), [connect from Azure](https://learn.microsoft.com/azure/developer/github/connect-from-azure-openid-connect)).
- **Environments.** Required reviewers are available for public repositories on every plan; an environment's secrets reach a job only after a required reviewer approves it, and a scheduled job waits for that approval like any other. "Protected branches only" counts branches with **branch protection rules**, and when no branch has one, every branch can deploy; "Selected branches and tags" matches the names you give ([deployments and environments](https://docs.github.com/actions/reference/workflows-and-actions/deployments-and-environments)). The REST API creates an environment with its reviewers and branch policy, and `gh secret set --env` sets its secrets ([environments API](https://docs.github.com/rest/deployments/environments#create-or-update-an-environment), [branch policies API](https://docs.github.com/rest/deployments/branch-policies#create-a-deployment-branch-policy), [gh secret set](https://cli.github.com/manual/gh_secret_set)).
- **Repository rules.** Rulesets protect branches with rules such as `pull_request`, `non_fast_forward`, and `deletion`, and `~DEFAULT_BRANCH` targets the default branch ([rulesets API](https://docs.github.com/rest/repos/rules#create-a-repository-ruleset)). A pull request's author can't approve it ([approving a pull request with required reviews](https://docs.github.com/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews)), so a required approval would lock out a solo owner. A personal repository's administrator has no documented bypass actor ID. On this plan, rulesets and branch protection return HTTP 403 while the repository is private (checked 2026-10-26 and again with `setup-github-repo.ps1 -WhatIf` on 2026-10-27).
- **The demo's workflows before this ADR** read `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, and `DBHUB_CONFIG_JSON` from environment **variables**, which GitHub never masks, and the subscription guard's message names the subscription, the tenant, and the account. No live workflow had run yet (the coordinator's scan of 322 runs, 2026-10-26).

## Decision

1. **Fork safety.** No workflow runs on `pull_request_target` or `workflow_run`. The workflows that a pull request triggers (`validate.yml`'s static checks and `codeql.yml`) need no secret and have `contents: read` (CodeQL adds `security-events: write` on its job). Every workflow that reaches Azure (deploy, destroy, demo-control, warm-up, `validate.yml`'s live job, and the four scheduled ones) runs only by hand (`workflow_dispatch`) or on a schedule, through `reusable-demo-run.yml` in a GitHub environment; only that job gets `id-token: write`, and it passes the environment's secrets with `secrets: inherit`. The schedules stay off until the repository variable `DBHUB_SCHEDULES_ENABLED` is `true`. `Repo.LifecycleScripts.Tests.ps1` checks each of these.
2. **The identifiers are environment secrets, and every ID is masked before anything prints.**
   - `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, and `DBHUB_CONFIG_JSON` are environment **secrets**, never variables. They're identifiers, not credentials: the sign-in stays OpenID Connect with no secret ([ADR 0009](0009-secrets-handling.md) stands). They're secrets only so that GitHub masks them.
   - `demo-setup`'s first step, before `azure/login`, masks each of the three IDs in its given, lowercase, and uppercase forms, and every GUID and email address in `DBHUB_CONFIG_JSON`, with `::add-mask::` (`Register-DemoLogMask`).
   - In GitHub Actions only, the module masks what it learns at run time: the configuration's IDs (`Get-DemoConfig`), the subscription, the tenant, and the account before the guard's first log line, then the caller's object and client IDs and any other ID that a failed check names, and the deployment's random suffix (the resource group's tag reader and T3's names).
   - The module's three ways out, `Write-DemoLog`, `Write-DemoResultReport`, and `Export-DemoResult`, write every registered value, any other GUID, and the T3 and T4 servers' suffix as `***` in GitHub Actions, so the job summary and the uploaded `out/*.jsonl`, which `::add-mask::` doesn't cover, show no ID either. The results in memory keep their values, so nothing that reads a result changes, and nothing changes outside GitHub Actions. A test shows that the guard's message comes out masked in the log, the job summary, and the results.
3. **The reviewed environment, set up by `setup-github-oidc.ps1 -ConfigureGitHub` (opt-in).** With the GitHub CLI as the signed-in user (the script never signs in), each environment gets the caller as its required reviewer, `prevent_self_review` off (a solo owner approves their own runs), deployments from the **default branch only**, and its four secrets, each sent on standard input. Without the switch, the script writes nothing to GitHub and prints the `gh secret set --env` commands.
   - **"Selected branches" with the default branch, not "Protected branches only":** GitHub counts only branch protection rules there, and with none, every branch can deploy; `setup-github-repo.ps1` protects `main` with a ruleset, which isn't one. This deviates from the brief's "protected branches only" on purpose, for the same intent.
4. **The schedule environment, opt-in (`-ScheduleEnvironment`).** `<environment>-schedule` (or `-ScheduleEnvironmentName`) has its own federated credential, the default branch only, and **no** reviewers, so a scheduled run doesn't wait for an approval; the repository variable `DBHUB_SCHEDULE_ENVIRONMENT` points the schedules at it. Only a schedule uses it: a run of the same workflows by hand uses the reviewed environment, and `reusable-demo-run.yml` refuses the schedule environment for any run that a schedule didn't start, before it signs in. The script never sets `DBHUB_SCHEDULES_ENABLED`.
   - **The trade-off:** a scheduled start, stop, Bastion cleanup, or expiry runs without a reviewer. What limits it: the workflows on `main` change only through a pull request (the ruleset), only the default branch can deploy to the environment, the schedules are off until you turn them on, and those four workflows only start, stop, remove Bastion, or destroy an environment whose `expiresOn` has passed. Without the schedule environment, each scheduled run waits for a reviewer in the reviewed environment.
5. **The repository's settings, set by `setup-github-repo.ps1` (opt-in, after the repository is public; `-WhatIf` first).** As an administrator, with the GitHub CLI:
   - a ruleset, "Protect the default branch", on `~DEFAULT_BRANCH`: changes through a pull request with 0 required approvals, no force-push, no deletion, and no bypass actors;
   - secret scanning, and push protection, which refuses a push that contains a known secret format;
   - private vulnerability reporting, which `SECURITY.md` points to;
   - Dependabot alerts (version updates are already in `.github/dependabot.yml`);
   - with `-Template`, the template flag, so others start from **Use this template**, a copy with one fresh commit.

   Each setting is read first and applied only when it's off. A setting that GitHub refuses while the repository is private (HTTP 403, 404, or 422) is **Manual action required**: run the script again once it's public. It never changes the visibility. The repository defaults to `github.repository` in the configuration.
6. **Content and community files.** Internal policy, initiative, and resource-group names and resource-name suffixes became the technical facts they stood for in the code, the tests, and the docs, and an earlier pull request's text lost T3's server suffix. `SECURITY.md` (private vulnerability reporting, and what a public repository means for logs), `CONTRIBUTING.md` (the repository's rules and its validation), `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1), a **Deployment problem** issue form that asks for `status.ps1`'s output with every ID replaced, and the README's "Getting help".

## Consequences

- **Easier:** a public repository's Actions logs, job summaries, and artifacts show no ID; one command sets up the GitHub side; every run that reaches Azure needs a reviewer's approval, unless you choose the schedule environment for the schedules.
- **Harder:** GitHub never shows a secret's value again, so after a configuration change you set `DBHUB_CONFIG_JSON` again (run `setup-github-oidc.ps1 -ConfigureGitHub` again). In GitHub Actions, every GUID in the module's output reads `***`, harmless operation IDs included: debug with the same script locally.
- **Accepted risks:** a value that a third-party action or the Azure CLI prints in a form nobody registered (for example URL-encoded) could still show; administrators can bypass an environment's protection rules by default, which a solo owner accepts; the schedule environment's trade-off above.

## Validation

- **Static (2026-10-27):** `DbHubDemo.ActionsMask.Tests.ps1` (the masking), `DbHubDemo.Guard.Tests.ps1` (the guard's message masked in GitHub Actions, and the add-mask commands before its first line), `DbHubDemo.GitHubSetup.Tests.ps1` (both scripts, with a mocked GitHub CLI), and `Repo.LifecycleScripts.Tests.ps1` (fork safety, environment secrets, the masking step's order, and the schedule environment), plus actionlint and gitleaks.
- **Read-only (2026-10-27):** `setup-github-repo.ps1 -Template -WhatIf` against the private archive: the ruleset (HTTP 403) and private vulnerability reporting (HTTP 404) were **Manual action required**, and nothing was written.
- **Pending, once the public repository exists:** `setup-github-repo.ps1 -WhatIf`, then without it; `setup-github-oidc.ps1 -ConfigureGitHub`; then one run of `validate.yml` with `live` (or `deploy.yml`), whose log, job summary, and artifact must show `***` for every ID. Until then, these GitHub settings are **Manual action required**.
