# ADR 0009: Secrets handling

- **Status:** Accepted
- **Date:** 2026-10-19 (revised the same day for plan §9, Revision 2; revised 2026-10-21 for Phase 13: break-glass access through Run Command, and the Key Vault opt-in the owner decided; and for Phase 14 the same day: secret scanning as built, Phase 7's type-name guard, and the sign-in data that setup leaves on the VM; amended 2026-10-27 for Phase 26d: no operator token left anywhere; amended 2026-10-29 for Phase 28: the guest's one automatic sign-in, and the portal password reset without a clipboard; and 2026-10-30: IE Enhanced Security Configuration off for setup's Azure sign-in, and back on after)
- **Decision source:** Engineering (approved plan §4.5, §9.1, §9.4 C1); brief rule 6 (no credentials in source control, notebook output, ARM outputs, Actions logs, VM or guest script output, or docs); owner decision 2026-10-21 (user-directed) for the Key Vault opt-in
- **Related:** [ADR 0005](0005-arc-onboarding-authentication.md), [ADR 0008](0008-identity-rbac-abac.md), [security model](../security-model.md)

## Context

- Azure requires an administrator password when it creates a Windows VM. `osProfile.adminPassword` can't be changed on an existing VM through a template; it's either ignored or rejected.
- Plan §9.1 removes Key Vault from the default deployment (C1). Contributor can't grant itself the data-plane roles a vault in RBAC mode needs, and a vault adds soft-delete name collisions.
- *(Phase 13, 2026-10-21.)* The owner decided to add Key Vault back as an **opt-in** for operator sign-in, so a Bastion session needs no clipboard on the machine that runs the scripts. The default path doesn't change.
- Contributor can reset a VM's local administrator password with the VMAccess extension (`az vm user update`), or set it with a managed Run Command that runs `Set-LocalUser` in the VM (Phase 13 uses the Run Command; it needs the VM running).
- *(Dropped 2026-10-20.)* The artifact cache, a storage account that VMs read with account-key SAS, was dropped: the tenant's policies turn off shared-key access on storage accounts, and nothing in the demo needs a SAS any more (ADR 0016, C9).
- Values that are secret or sensitive during a run: VM administrator passwords, the T2 guest administrator password, Arc onboarding tokens, an optional SQL Server product key (P10), an optional GitHub token (P9), and Fabric and Kusto tokens in the notebooks.

## Decision drivers

1. Nothing secret is ever written to Git, outputs, logs, notebooks, or docs.
2. Works with Contributor alone.
3. Prefer no secret at all: identities and short-lived tokens.

## Decision

| Secret | Handling |
|---|---|
| VM administrator passwords (T1, T2 host) | Generated by `deploy.ps1` with a cryptographic RNG for **creation only**, passed as `@secure()` parameters, and then discarded. Never stored. On re-runs, the template omits `osProfile` for VMs that exist (ADR 0001). Deploy to Azure users type their own. Its symbols are limited to `#*+-.?_~`: on Windows the Azure CLI is the batch file `az.cmd`, where `%` would expand (`Invoke-DemoAz` refuses it), and `!`, `^`, `&`, redirection, and parentheses are cmd.exe metacharacters (Phase 6). |
| Break-glass access | *(Revised in Phase 13.)* `scripts/start-demo.ps1 -Interactive -ResetAdminPassword` creates Bastion on demand and sets a one-time password for the T2 host's administrator with a managed Run Command (`Set-LocalUser`; the value travels Base64-encoded in one protected parameter, because Run Command allows only `A-Za-z0-9._:/@=,+?&%~-` in parameter values, and Base64 of a printable password starts with a letter). It copies the password to the operator's clipboard and never displays, logs, or stores it; without a working clipboard nothing is set, and since Phase 28 the operator sets a password of their own with the portal's **Reset password**, which the scripts rotate afterward ([amendment](#no-clipboard-the-portals-reset-password)). A value that's shorter than 12 characters or reads like a type name (what a `SecureString` becomes when it's bound to a `[string]` parameter: the literal `System.Security.SecureString`) is refused before the Run Command. `stop-demo.ps1` rotates it to a value nobody keeps; on a deallocated host that's **Manual action required**, and the next start rotates it. |
| One-time host password, Key Vault opt-in (`keyVault.enabled`) | *(Phase 13, owner decision 2026-10-21.)* Off by default. With it on, which requires `assignRoles: true`, `deploy.ps1` deploys a vault in RBAC mode with soft delete and no access policies (`infra/modules/keyvault.bicep`; purge protection and a firewall are settings, for tenant policy), and grants the signed-in caller and `keyVault.operatorObjectIds` **Key Vault Secrets Officer** and `keyVault.readerObjectIds` **Key Vault Secrets User**, on the vault only, resolving the roles by name ([ADR 0008](0008-identity-rbac-abac.md)). `start-demo.ps1 -Interactive -ResetAdminPassword` stores the password as a secret **before** it sets it on the VM, so a password nobody can read is never set: the value reaches the Azure CLI in a private temporary file (`az keyvault secret set --file`), never on a command line, and the CLI returns only the secret's ID. Its expiry is Bastion's. Older versions are disabled; if the VM refuses the password, the new one is disabled too. No clipboard is used. `stop-demo.ps1` rotates the host password and disables every enabled version (nothing is deleted). Bastion's RDP form has no Key Vault option, so the operator copies the value in the vault's portal page into the **Username and password** form. `destroy.ps1` leaves the vault soft-deleted, and a later `deploy.ps1` recovers it under the same name. |
| T2 guest administrator password | Generated on the host, stored only on the host with DPAPI (LocalMachine scope, readable by host administrators). It never leaves the host. The operator copies it to the clipboard inside the Bastion session with a helper script for the `PaygWizard` step. *(Phase 28.)* At the guided stop the guest signs itself in once instead, with a temporary password kept only as an LSA secret and rotated right after ([amendment](#phase-28-amendment-the-guests-one-automatic-sign-in-and-the-portal-password-reset-2026-10-29)). |
| Arc onboarding token | The caller's short-lived token, passed only through protected Run Command parameters and PowerShell Direct arguments, kept in memory, never persisted. The Run Command is deleted afterward (ADR 0005). |
| Bootstrap bundle and media (not secret) | No SAS and no storage key since 2026-10-20. The bundle travels in Run Command chunks that hold no secrets: `New-DemoBootstrapChunk` refuses any content that contains a registered secret or matches the redaction patterns, the chunk scripts take no parameters, and each chunk Run Command is deleted as soon as it succeeds. The loader checks every chunk and the whole bundle against their SHA-256 values and fails closed; its own parameters (hash, chunk count, role, settings) aren't secret either. Media comes from pinned Microsoft URLs, checked against pinned SHA-256 values. |
| SQL Server product key (P10) | Secure input (`-ProductKey` as a `SecureString`, or an Actions secret), passed only in protected parameters, used once by setup, never written to disk in the guest outside setup's own handling. |
| GitHub token for the notebook (P9) | Lives in a Key Vault **the user provides**, read with `notebookutils.credentials.getSecret`. It's fine-grained and scoped to `actions: write` on this repo. The repo never deploys or reads that vault. |
| SQL authentication | None. T1 and T2 use Windows authentication with `sa` disabled; T3 is Microsoft Entra-only. |
| GitHub to Azure | OIDC only; no Azure credential is stored. `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, and `DBHUB_CONFIG_JSON` are identifiers, kept as environment secrets only so that GitHub masks them in a public repository's logs ([ADR 0022](0022-public-repository-and-github-actions-hardening.md), 2026-10-27; they were environment variables before). |
| Fabric, Kusto, and Graph tokens | Acquired at run time and never printed. Notebook cells redact token-like values before display. The telemetry endpoint accepts the notebook's own `kusto` token (live, 2026-10-21: `HUB.TELEMETRY.TOKEN` **Pass**, closing plan risk R29), so the notebooks need no stored credential to read telemetry. |

### Enforcement

- **Shared redacting logger:** every script logs through `Write-DemoLog` in `scripts/modules/DbHubDemo`. It masks JWT-shaped strings, `sig=` and `se=` SAS parameters, `AccountKey=`, `Password=`, GitHub token prefixes, and every value registered at run time with `Register-DemoSecret`. In Actions it also issues `::add-mask::`.
- **Run Command output** is scrubbed by the same logger before it's printed. The instance view keeps only the last 4 KB of a script's output and error.
- **What leaves in clear text:** content sent to VMs in Run Command scripts (the bootstrap bundle) is checked against the registered secrets and the redaction patterns first, and refused on a match (Phase 6).
- **Type names refused (Phase 7, 2026-10-21):** a SecureString or a credential converted with `[string]` becomes its .NET type name, text anyone can guess. `Invoke-DemoVmRunCommand` refuses `System.Security.SecureString` and `System.Management.Automation.PSCredential` as the value of any public or protected Run Command parameter, and a SecureString that holds one, before any Azure call, so such a value never reaches a VM. Phase 13 added the same check, and a 12-character minimum, for the one-time host password.
- **Tests and scanning:** Pester tests cover the redaction patterns. CI runs gitleaks on every pull request and fails when notebooks contain outputs.
- **Bicep:** secure parameters and the secret-related linter rules are errors (ADR 0001). Outputs never contain secrets.

## Consequences

- **Positive:** there are no long-lived secrets in the default deployment, no vault to manage, and no soft-delete collisions.
- **Opt-in (Phase 13):** with `keyVault.enabled`, a vault holds at most the current one-time password, readable only by the principals the deployment named and only until `stop-demo.ps1` disables it. The trade-offs are the role assignments (so `assignRoles` and a permission above Contributor), a few minutes of RBAC propagation the first time, and a vault name that soft delete keeps for its retention after `destroy.ps1` (handled by recovering it).
- **Future option:** Microsoft Entra ID sign-in through Bastion (preview for RDP) would need no password at all, but it joins the host to Microsoft Entra ID (`AADLoginForWindows`) and needs the Virtual Machine Administrator Login role; it isn't implemented.
- **Negative:**
  - Break-glass access needs a password reset each time.
  - *(Resolved 2026-10-20.)* The artifact cache depended on shared-key access, which the tenant's policies turn off; the cache was dropped.
- **Risks accepted:** without the host identity, the caller's onboarding token is on the host's PowerShell command line while the onboarding runs, where endpoint protection can record it (ADR 0005; Phase 26d amendment below). Since Phase 26d, the agent in the guest takes it from a protected file, not its command line.

## Phase 14: secret scanning as built (2026-10-21)

`Find-DemoSecretLeak` scans files, folders, or text with the same rules `Protect-DemoText` redacts with (JWTs, bearer tokens, SAS signatures, account keys, connection-string passwords, secret-named JSON properties, GitHub tokens, product keys), plus every value registered with `Register-DemoSecret` in the session and any `-KnownValue` given as a SecureString. It returns where each match is (source, line, rule) and an excerpt with the match replaced by `[REDACTED:<rule>]`; it never returns a matched value. Values that are already redaction markers, empty, asterisk masks, or `<placeholders>` aren't leaks, and the bearer and password rules, which also match prose, need a value of at least 8 characters with a digit or a symbol. Files are decoded as UTF-8, or as UTF-16 or UTF-32 when a byte order mark says so, or as UTF-16 without one when NUL bytes fall on every other byte: Windows PowerShell 5.1's `Out-File` and redirection write UTF-16, and a scanner that skipped those as binary would miss a token in them. Other binary and unreadable files are listed as skipped; a log another process is still writing is read with shared access.

| Where secrets could appear | How it's scanned | Automated by |
|---|---|---|
| Script output: console transcripts, `out/*.jsonl`, logs | Save the run to `out/` (`Start-Transcript -Path ./out/<name>.log`, or `*>&1 \| Tee-Object ./out/<name>.log`); `Find-DemoSecretLeak -Path ./out` | `validate.ps1 -Area Security` (`SECURITY.SECRETSCAN.OUTPUT`) scans `out/` and `-ScanPath` |
| Run Command instance views (the last 4 KB of output and error Azure keeps, plus the script and public parameters) | `az rest --method get --url .../runCommands/<name>?api-version=<pinned>&$expand=instanceView` through `Invoke-DemoAz`, then `Find-DemoSecretLeak -Text` | `SECURITY.SECRETSCAN.RUNCOMMANDS`, on running VMs only: a deallocated VM's instance views are empty |
| ARM deployment history: parameters, outputs, errors, and operations | `az deployment group list`, `az deployment operation group list`, and the subscription-scope equivalents, through `Invoke-DemoAz` | `SECURITY.SECRETSCAN.DEPLOYMENTS`, for the 25 newest deployments in the resource group and the environment's subscription deployments |
| GitHub Actions logs | `gh run view <run-id> --log > ./out/actions-<run-id>.log` after the run finishes, then `validate.ps1 -Area Security` or `Find-DemoSecretLeak -Path ./out/actions-<run-id>.log`. Actions masks registered values as `***`, which the scanner ignores | Manual download; the scan is automated |
| Notebook outputs | The repository's notebooks keep no outputs (static check). For a notebook run in Fabric, export it as a standard `.ipynb` file ([export a notebook](https://learn.microsoft.com/fabric/data-engineering/how-to-use-notebook)) into `out/` and scan it | Manual export; the scan is automated |
| Host and guest logs (`C:\ProgramData\DbHubDemo\logs`) | Copy them through Bastion into `out/`, then scan | Manual copy; the scan is automated |
| The VMs and the T2 guest after an interactive sign-in or an Arc onboarding: setup's log folders, temp folders, PowerShell history and transcripts, the Run Command handlers' and the Azure and Arc agents' folders, the demo's files, the PowerShell, Application, and Security event logs, and the sign-in caches | `./scripts/check-sign-in-data.ps1` runs `vm/bootstrap/Invoke-DemoSignInResidue.ps1` on the VM, and over PowerShell Direct in the guest, and reports counts and locations only (Phase 26d, below); `-Clean` removes what it finds | The host's `GuestSignInCleanup` step after the wizard, the sweep after Arc onboarding, and the golden capture gate and copy scan |
| The repository and its history | gitleaks on every pull request (`.github/workflows/reusable-static-checks.yml`, job **Secret scan**) and as a pre-commit hook, with every default rule plus `.gitleaks.toml`'s `jwt-any-delimiter`: the default `jwt` rule needs a quote, a backtick, a space, a semicolon, or the line's end after the token, so with gitleaks 8.30.1 it missed a token inside an XML element or followed by `&` in a URL (checked 2026-10-21 with a token built at run time); `tests/unit/Repo.Gitleaks.Tests.ps1` keeps that rule matching. The file's one allowlist exempts the public commit SHA pins in `config/versions.json`, and nothing else, from the default `sourcegraph-access-token` rule, which flagged them in a scan of the whole file. gitleaks reads raw bytes, so it can't see a token in a UTF-16 file (Git stores one as binary); copied logs go to the Git-ignored `out/`, where `Find-DemoSecretLeak` reads them | CI |

Live results on 2026-10-21 (`sqlvm01` deallocated): `SECURITY.SECRETSCAN.OUTPUT` **Pass** and `SECURITY.SECRETSCAN.DEPLOYMENTS` **Pass** (25 deployments with their operations); `SECURITY.SECRETSCAN.RUNCOMMANDS` is a **Warning** until the VMs run. GitHub secret scanning and code scanning aren't enabled on this private repository (checked with the GitHub REST API, 2026-10-21), so gitleaks is the repository's secret scan.

## Phase 26d amendment: no operator token left anywhere (2026-10-27)

The owner's requirement: no token from the operator's sign-in is left anywhere, on the VMs, in the guest, in their logs, in Run Command resources, or in snapshots, and everything is wiped for redeployments. Two sign-ins put a token on the VMs: setup's interactive Azure Login in the guest (`PaygWizard`), and the Arc onboarding token. Setup's interactive sign-in can't be told not to leave sign-in data, so the scripts remove it and prove that none remains (R74); the onboarding token is avoided where it can be, and removed where it can't.

### The sweep

`vm/bootstrap/Invoke-DemoSignInResidue.ps1` (Windows PowerShell 5.1, self-contained) runs on a VM and, with `-ResidueScope Guest` or `Both`, in the T2 guest over PowerShell Direct:

- **Where it looks:** setup's log folders (every `Setup Bootstrap\Log`), the Windows and profile temp folders, PowerShell history and transcripts, the Run Command handlers' folders, the Azure and Arc agents' logs and configuration, the demo's own files, the Windows PowerShell, PowerShell, Application, and Security (event 4688) logs, and, in the guest and on the evaluation VM, the sign-in caches the wizard's browser used.
- **What it finds:** JWT-shaped values and secret-named JSON properties. It decodes a token's claims in memory only, to tell a person's token from an application's or a managed identity's, and reports counts and locations only, never a value.
- **Archives in setup's log folders** are checked inside: a `.cab` is expanded with Windows' [`expand.exe`](https://learn.microsoft.com/windows-server/administration/windows-commands/expand), a `.zip` or `.gz` with .NET, into a temporary folder that's deleted right after. An archive whose files hold no token-shaped value passes; one that holds one, or can't be expanded, is deleted by `Clean`. (The read-only audit of 2026-10-27, before this, counted the T1 image's own setup archives as left.)
- **What `Clean` does:** redacts files in place in their own encoding, deletes such archives and the sign-in caches, clears a PowerShell or Application log only when it holds a token-shaped value (once more if a process that was still running wrote another one right after, such as the onboarding Run Command's PowerShell stopping), and never clears the Security log unless an operator asks (`-ClearSecurityLog`). Then it scans again.
- **The result** (ADR 0012), `SECURITY.SIGNIN.<VM>` and the checks below:
  - **Fail** (fail closed) when a person's token, or one it can't classify, is left in a file or a PowerShell or Application log, a sign-in cache is left, a file in setup's or the Run Command handlers' folders can't be read, or a machine can't be reached;
  - **Manual action required** when the Security log holds a token-shaped value: clearing it erases the audit trail, so the result gives the exact command (`./scripts/check-sign-in-data.ps1 -VmName <vm> -Clean -ClearSecurityLog`, or `wevtutil clear-log Security` on the VM);
  - **Warning** when the cleanup cleared an event log, because endpoint protection may report a cleared log, or when only an application's or a managed identity's token was found;
  - **Pass** otherwise.

### Where it runs

| When | How | Fails closed |
|---|---|---|
| Right after setup, every guest build and every install mode | The host's `GuestSignInCleanup` step (and `SignInCleanup` on the evaluation-only VM) waits while setup or the Installation Center runs, then cleans the guest and the host | The build stops |
| Right after every Arc onboarding | `Invoke-DemoArcOnboarding` runs the Run Command `DbHubDemo-SignInData` (no secret) with `Clean` on the host and in the guest | `T2.ARC.ONBOARDING` **Fail** |
| Before a golden capture | `New-DemoT2GoldenSnapshot` cleans the host and the guest and scans again (`GOLDEN.CAPTURE.SIGNIN`) | Nothing is captured on Fail or Manual action required |
| On every golden copy | `Test-DemoT2GoldenSnapshot` scans the quarantined copy without changing it (`GOLDEN.TEST.SIGNIN`) | The snapshot isn't tagged boot-verified |
| Any time | `./scripts/check-sign-in-data.ps1` (scan; `-Clean` asks first unless `-Force`) | `SECURITY.SIGNIN.<VM>` **Fail** |

### The onboarding token

- **The host identity whenever it's attached** (owner decision, 2026-10-27): `deploy.ps1` creates `id-<prefix>-<env>-arc-onboard` with the built-in **Azure Connected Machine Onboarding** role on `rg-<prefix>-<env>`, attaches it to `archost01`, deletes it with the group, and creates it again on each redeploy, when `assignRoles` is true. `Invoke-DemoArcOnboarding` uses it whenever it's attached (`az vm show`, read-only): `configure-arc.ps1`, the golden restore's reconnect, and `test-t2-golden.ps1 -Onboard`, whose test group gets its own. The host requests its token from IMDS, so none of the operator's leaves their machine. A connect that Azure refuses for authorization is retried after 30, 60, 120, 120, and 120 seconds while the new role assignment propagates; that adds nothing to a redeploy once it has propagated, and at most 7.5 minutes otherwise. `-UseHostIdentity` requires it; `-UseCallerToken` skips it.
- **Prevention in the guest:** the agent gets the token from a JSON file in a folder that only SYSTEM, Administrators, and the account running the onboarding can read (the agent's common flag `--config`), which is overwritten with zeros and deleted right after, so the token is never on the agent's command line. Only if the agent rejects the file or waits for a sign-in does it get the token on its command line, once; onboarding then reports a Warning.
- **Other protected values (Phase 26f, R528):** the Run Commands that receive the one-time host password or the SQL Server product key turn off their own session's further PowerShell engine and provider events and, after use, search the Windows PowerShell log for the exact value in memory and clear that log only when it's there (a **Warning**, or **Manual action required** with `wevtutil clear-log "Windows PowerShell"` when it can't be cleared), while the sweep finds product-key-shaped values so that `-Clean` removes older entries, and neither ever clears the Security log.
- **Contributor-only callers** can't create the role assignment, so they keep the caller's token: valid for about an hour, carrying the caller's rights. Managed Run Command passes protected parameters to a Windows script as arguments, so the host's PowerShell command line carries it while the onboarding runs. The Windows PowerShell log records that command line by default, and process-creation auditing (Security event 4688), script block logging, transcription, and endpoint protection can when they're on. The sweep right after onboarding removes it from the VMs; a copy that endpoint protection sent off the VM stays there.

### The golden snapshot

The snapshot captured on 2026-10-22 passed the capture's checks of that time: no token-shaped value in setup's log files and no sign-in cache in the guest. Those checks didn't cover the guest's temp folders, history, event logs, and agent logs, the host's Run Command handlers' folders and event logs, or free space; the guest had been cleaned by hand the day before. The tokens from that build expired within about an hour. A file scan can't prove that deleted data is gone from free space, so a recapture after the sweep and a zero fill of the free space, with the old snapshot kept until the new one is proven, closes it (R523).

### Not covered

- Copies made off the VMs: endpoint protection's telemetry, and anything an operator copied.
- The operator's own PC: the Azure CLI's and the Fabric Apps CLI's sign-ins stay until `az logout` and `rayfin logout`, which the scripts never run.

## Phase 28 amendment: the guest's one automatic sign-in, and the portal password reset (2026-10-29)

Two changes for the `PaygWizard` guided stop ([deployment](../deployment.md#the-guided-stop-paygwizard), [ADR 0006](0006-sql-editions-and-licensing.md#amendment-one-command-one-guided-stop-phase-28-2026-10-29)). Neither adds a role assignment or a Key Vault to the default path (ADR 0008).

### The guest signs itself in once, for the setup step only

**Why (owner-approved, 2026-10-29):** a colleague's assistant drove a deployment to the guest's console, but nobody could sign in to Windows in `arcsql01` for them, so the run sat waiting.

- **The mechanism:** Windows automatic sign-in for the guest's built-in Administrator, with `AutoAdminLogon` 1, `DefaultUserName`, and `AutoLogonCount` 1, so it signs in once at the next start. The password is a temporary random one, set through the existing guest password rotation (generated on the host, stored there with DPAPI), and the guest keeps it only as the LSA `DefaultPassword` secret, written with the documented `LsaStorePrivateData` API in the guest over PowerShell Direct ([protecting the automatic logon password](https://learn.microsoft.com/windows/win32/secauthn/protecting-the-automatic-logon-password), [LsaStorePrivateData](https://learn.microsoft.com/windows/win32/api/ntsecapi/nf-ntsecapi-lsastoreprivatedata)). It's never the plaintext Winlogon `DefaultPassword` registry value, which [turn on automatic logon](https://learn.microsoft.com/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon) says is stored in plain text; the arm deletes that value and fails when it's there afterward. The [Sysinternals Autologon](https://learn.microsoft.com/sysinternals/downloads/autologon) tool, which uses the same LSA secret, isn't used, so nothing is downloaded or pinned.
- **When:** only while `deploy.ps1`'s request on the host is valid (it waits for a person, with an expiry), and at most 3 times per request. The host records the arm before it makes it, so a run that stops midway still cleans up.
- **The cleanup always runs** (in a `finally`, after setup succeeded, failed, or timed out): the guest's logon task clears the settings and the secret as its first action, before it opens setup; then the host signs out every console session in the guest ([logoff](https://learn.microsoft.com/windows-server/administration/windows-commands/logoff)), because Windows records the last console user in `DefaultUserName` at a sign-in; sets `AutoAdminLogon` 0; deletes `AutoLogonCount`, the LSA secret, and the Winlogon `DefaultUserName` and `DefaultPassword` values; rotates the guest Administrator's password with the existing rotation; and reads everything back. `GuestSignInCleanup` then runs as before. The host's guard repeats the cleanup on every pass of its state machine (at startup and every 5 minutes) whenever automatic sign-in is armed and the request has expired or gone, and before any new arm. A cleanup that didn't finish keeps its record and runs again (fail closed). The brief's order put the sign-out after the rotation; the sign-out comes first so that no session can write `DefaultUserName` again after it's deleted.
- **Fail closed:** the sign-in data sweep (`vm/bootstrap/Invoke-DemoSignInResidue.ps1`) reports automatic sign-in that's on (or `AutoLogonCount`), the LSA `DefaultPassword` secret, the Winlogon `DefaultPassword` value, and, in the guest, the Winlogon `DefaultUserName` value. Any of them is a **Fail** in `check-sign-in-data.ps1` (`SECURITY.SIGNIN.<VM>`), in the golden capture's gate (`GOLDEN.CAPTURE.SIGNIN`, so nothing is captured), and in the golden test's scan (`GOLDEN.TEST.SIGNIN`); `-Clean` turns it off and deletes them. Leftovers after a run are removed by the host's next pass, which a resumed `deploy.ps1` or a `start-demo.ps1` triggers by starting the host, and `status.ps1`, which only reads, reports them as a **Warning** (`STATUS.T2.AUTOSIGNIN`).
- **The consequence, plainly:** while the window is open (from the arm until the guest's logon task clears it, about 2 minutes after the guest restarts, and at the latest until the host's cleanup), anyone with administrator rights on the T2 host, or with the guest's disk, could read the temporary password from the LSA secret. They could already take over the guest (the host holds the guest's password with DPAPI, reaches it over PowerShell Direct, and holds its disk), and the password is rotated right after, so the exposure is short-lived and low. A security scan of the guest during the window would flag automatic sign-in.

### No clipboard: the portal's Reset password

**Why:** the host's one-time password reached the operator only through the clipboard, or through the Key Vault opt-in, which needs `assignRoles`. In GitHub Codespaces, Cloud Shell, or any session without a working clipboard, a Contributor-only user had no way to sign in through Bastion.

- **When no clipboard works and the Key Vault opt-in is off, no password is set or shown.** The guided stop's prompt, the status page, and the `HUMAN ACTION REQUIRED` line give the documented portal path instead: open `archost01`, then **Help**, then **Reset password**, keep the user name, set a password of your own choosing, then sign in through Bastion with it ([reset Remote Desktop or the administrator password](https://learn.microsoft.com/troubleshoot/azure/virtual-machines/windows/reset-rdp), which runs the VMAccess extension). `start-demo.ps1 -Interactive -ResetAdminPassword` gives the same path.
- **What counts as a working clipboard** (review fix, 2026-10-29): PowerShell 7's `Set-Clipboard` doesn't fail where there's none. On Linux it needs `xclip`, and on macOS `pbcopy` ([Set-Clipboard](https://learn.microsoft.com/powershell/module/microsoft.powershell.management/set-clipboard)); without the tool, or when `xclip` has no X display, it keeps the text inside its own process, so a password would be set and copied nowhere. So a clipboard counts only on Windows when `Set-Clipboard` takes text, on macOS with `pbcopy`, and on Linux with an X display (`DISPLAY`, which XWayland sets too) and `xclip`; never in GitHub Codespaces (`CODESPACES`), an SSH session (`SSH_CLIENT` or `SSH_TTY`, as the same page detects one: the clipboard there isn't the person's), or Azure Cloud Shell. `start-demo.ps1 -Interactive -ResetAdminPassword` uses the same check.
- **It's rotated afterward:** the resource group's state records that a password was handed over (`DbHubHostPasswordUtc`), so the guided stop's cleanup rotates it to a value nobody keeps, and `stop-demo.ps1` does when that couldn't. A rotation that fails on a running host is now a **Warning** with the portal path (set a random value you don't keep), not a **Fail**, and the record stays, so the next stop or start tries again; on a deallocated host it stays **Manual action required**, and the next start rotates it.
- **Never DONE with it** (review of the live-proof fixes, 2026-10-29): a Ctrl+C at the guided stop skips the cleanup, so it doesn't hold the stop, and setup can still finish in the guest; the next run's guided stop then isn't needed, and before this fix nothing removed Bastion or rotated the password, and the run ended **DONE**. Now the T2 step cleans up whatever the state records (`DbHubGuidedStopUtc`, which stays while the guided stop's Bastion couldn't be removed, and `DbHubHostPasswordUtc`), in the parallel tracks and in `-Sequential`, and `deploy.ps1` is **NOT DONE**, naming `./scripts/stop-demo.ps1 -RemoveBastionOnly`, while either is still recorded. A password that `start-demo.ps1 -Interactive` handed over counts too: a `deploy.ps1` run whose T2 step runs during such a session ends that session's Bastion and password, and one whose T2 step doesn't run is **NOT DONE** until `stop-demo.ps1` runs.
- **Unchanged:** the demo never displays, logs, or stores a password; the clipboard path and the Key Vault opt-in work as before.

**Tests:** `tests/unit/Vm.GuidedSetup.Tests.ps1` (the arm keeps only the LSA secret with `AutoLogonCount` 1; the cleanup after success, failure, and time-out; fail closed; never while `deploy.ps1` waits), `tests/unit/Vm.SignInResidue.Tests.ps1` (the sweep fails on each leftover and `Clean` removes them), `tests/unit/DbHubDemo.OneCommand.Tests.ps1` (no clipboard: no password set or shown, the handover recorded, the portal path, the rotation's **Warning**; what counts as a clipboard on each platform, in Codespaces, SSH, and Cloud Shell; `STATUS.T2.AUTOSIGNIN`; never **DONE** with a guided stop's Bastion or a handover left open, and the guided stop's cleanup of them when it isn't needed), `tests/unit/DbHubDemo.Tracks.Tests.ps1` and `tests/unit/DbHubDemo.Lifecycle.Tests.ps1` (the T2 step's and the `-Sequential` T2 stage's cleanup of them), and `tests/unit/Repo.LifecycleScripts.Tests.ps1` (`start-demo.ps1` records the handover, and sets no password where `Set-Clipboard` only pretends). ### Setup's Azure sign-in: IE Enhanced Security Configuration (live finding, 2026-10-30)

**Why:** in the live proof, setup's **Use Azure Login** opened in an Internet Explorer-based control, and IE Enhanced Security Configuration (on for administrators, the Windows Server default) blocked `https://login.microsoftonline.com`, though the WebView2 runtime was installed. MSAL.NET documents that it uses its legacy, IE-based web view for Microsoft Entra ID authorities whatever is installed ([using WebView2 with MSAL.NET](https://learn.microsoft.com/entra/msal/dotnet/advanced/webview2)); which library setup uses isn't documented. Turning IE ESC off while setup was open didn't reach setup.

- **What changes, and when:** before the person is asked, before the guest's automatic sign-in, and before setup opens, the host turns IE ESC off for administrators in the guest (`IsInstalled` 0, as [Azure File Sync's deployment guide](https://learn.microsoft.com/azure/storage/file-sync/file-sync-deployment-guide#prepare-windows-server-to-use-with-azure-file-sync) documents for an interactive Azure sign-in, and re-enabled after), and adds the Azure portal's documented authentication hosts to the Trusted sites zone for the guest's Administrator (per-user `ZoneMap\Domains` and `ZoneMap\EscDomains` entries, [IE security zones registry entries](https://learn.microsoft.com/previous-versions/troubleshoot/browsers/security-privacy/ie-security-zones-registry-entries)). Nobody is asked before both IE ESC is off and WebView2 is installed, for about 15 minutes or 3 passes at most: then the host logs a **Warning**, says `guidedSignIn` fallback, and asks anyway, leading with the dialog's **Add...**, which worked live (fail open, Phase 28 review); its record still drives the cleanup.
- **The cleanup** is part of the automatic sign-in's, in the same `finally` paths (setup done, failed, or timed out, and the host's guard when the request has expired or gone), except between two tries of the automatic sign-in: IE ESC goes back on for administrators and users, and the Administrator's Trusted sites entries go back to a snapshot taken before the change (names and zones only), so sites added with the dialog's **Add...** meanwhile go too; the snapshot never holds the sign-in hosts' own Trusted sites entries, so they go even when an earlier pass's changes were already there when it was taken (Phase 28 review). The record is written before the change, so a run that stops midway still restores; a restore that can't be checked keeps its record and runs again (fail closed), and the setup step isn't done before. `GuestSignInCleanup` and the golden capture still require IE ESC on, as before.
- **The consequence, plainly:** while the guided stop is open (from the preparation until the cleanup, usually 15 to 60 minutes), IE ESC is off for administrators in the guest, and Microsoft's sign-in hosts are Trusted sites for its Administrator. Only the guest's administrators browse there, nothing in the guest is reachable from outside (no inbound path), and setup's own sign-in is the only browsing the demo does, so the exposure is short-lived and low. No secret is involved: the snapshot and the record hold site names and zone numbers only.
