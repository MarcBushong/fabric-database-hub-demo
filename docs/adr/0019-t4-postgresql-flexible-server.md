# ADR 0019: T4, an Azure Database for PostgreSQL flexible server

- **Status:** Accepted. Built and checked statically and against a local PostgreSQL 18.6 on 2026-10-23; validated live on 2026-10-26 on the General Purpose option (see the amendment); amended 2026-10-29 for Phase 28's Burstable fallback, 2026-11-02 for its General Purpose fallback, and 2026-11-03 for `max_connections` on every size and `connection-surge` past the limit
- **Date:** 2026-10-23
- **Decision source:** User-directed (2026-10-23: "add PostgreSQL as T4: the smallest burstable flexible server, stopped and started with the demo, with its own bounded activity and incidents", then "I want to see live query data and metrics. History not as important"), with the networking, access, live-view, history, and metrics choices decided by the coordinator for the owner the same day
- **Related:** [ADR 0007](0007-networking-modes-and-egress.md), [ADR 0008](0008-identity-rbac-abac.md), [ADR 0009](0009-secrets-handling.md), [ADR 0010](0010-workload-generator-technology.md), [ADR 0012](0012-validation-model.md), [ADR 0016](0016-cost-profiles.md), [ADR 0018](0018-fast-redeploy-parallel-tracks-golden-snapshot.md), [architecture](../architecture.md), [limitations](../limitations.md)

## Context

- **Database Hub supports Azure Database for PostgreSQL flexible server (preview).** Estate lists flexible servers, not their databases. Its PostgreSQL monitoring "uses existing Azure Monitor metrics" and has no query-level diagnostics; discovery needs Reader and nothing else (no extended property, Arc, or extra resource provider). Performance has a **PostgreSQL** dashboard over `cpu_percent`, `memory_percent`, `storage_percent`, `iops`, `active_connections`, and `connections_failed` ([monitor PostgreSQL](https://learn.microsoft.com/fabric/database/hub/monitor-postgresql), checked 2026-10-23).
- **The tenant (read-only checks, 2026-10-23):** 64 enforcing policy rules, none for `Microsoft.DBforPostgreSQL`; Defender for open-source relational databases and Defender CSPM are on Standard through a tenant policy, so they bill T4; the resource provider is registered; West US 3 offers `Standard_B1ms` (1 vCore, 2 GiB, 640 IOPS) and PostgreSQL 11 to 18 ([Location Based Capabilities](https://learn.microsoft.com/rest/api/postgresql/flexibleserver/location-based-capabilities/execute)).
- **A stopped flexible server starts on its own after seven days,** and rejects every other management operation while stopped ([stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server)).
- **Fabric notebooks can't reach T4:** `notebookutils` tokens cover storage, Power BI, Key Vault, and Kusto only, so there's no Azure Resource Manager or `ossrdbms` audience ([notebookutils](https://learn.microsoft.com/fabric/data-engineering/notebook-utilities)).
- **Query Store** mustn't be enabled on the Burstable tier ([Query Store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)).

## Decision

1. **The server.** `pgflex01-<deploymentId>` in `rg-<prefix>-<environment>` (`infra/modules/pgflex01.bicep`), Burstable `Standard_B1ms` by default (`t4SkuName`; `Standard_B2s` is the documented fallback and General Purpose `Standard_D2ds_v5` the documented option the owner chose, see the 2026-10-26 amendment; the tier follows the size), in an optional availability zone at creation (`t4AvailabilityZone`), 32 GiB (P4) without auto-grow, 7-day backups without geo-redundancy, no high availability, PostgreSQL **18** pinned in `config/versions.json` (`postgresql.majorVersion`), and the database `contosocare`. `t4Enabled` (default true) turns it off.
2. **Networking: virtual network integration in both network modes.** A delegated `/28` (`snet-pg`, 10.42.0.96/28), a private DNS zone `<prefix>-<environment>.private.postgres.database.azure.com` linked to the network, and no public access. Its network security group allows port 5432 only from T1's subnet. No private endpoint, so no endpoint charge ([private access](https://learn.microsoft.com/azure/postgresql/network/concepts-networking-private)).
3. **Access: Microsoft Entra only, no secret anywhere.** Password authentication is off; the P6 group (T3's administrator) is T4's Entra administrator. T1's managed identity, a member of P6, signs in as the group's role and creates the runner's role `contosocare_runner` for its own object ID with `pgaadauth_create_principal_with_oid`, then the schema, seed, and grants (`Enable-DemoT4Workload`, action Run Command `EnableT4`). No operator token travels and no password exists ([Entra users](https://learn.microsoft.com/azure/postgresql/security/security-manage-entra-users), [managed identity](https://learn.microsoft.com/azure/postgresql/security/security-connect-with-managed-identity)). The runner's role gets the demo's tables and functions in `contosocare` and, if allowed, `pg_read_all_stats`, and nothing else.
4. **Workload: the same runner interface and scenario names as T1 to T3.** `run`, `stop`, `reset`, `status`, `profile`, and `setup` take `--target T4` (Npgsql, TLS `VerifyFull`, no pooling, the managed identity's token as each connection's password). T4 runs `healthy-baseline`, `cpu-pressure`, `locking-blocking`, `io-pressure`, and two PostgreSQL-only scenarios, `connection-surge` and `idle-in-transaction`, each with a hard maximum duration; only `ContosoCare.Demo/` sessions in `contosocare` are touched (`pg_terminate_backend` in `demo.usp_kill_demo_sessions`), and `reset` restores the seed. T4's activity profile is a file on T1 (`activity-t4.json`), so setting it never connects to T4.
5. **Live view: Hub's PostgreSQL dashboard and the runner's `status`.** The free enhanced metrics are on (`metrics.collector_database_activity`: sessions by state and by wait event type, the oldest transaction and query, deadlocks). `status.ps1` shows them (`STATUS.T4`), and with `-Detail` the runner's live view of sessions, waits, blockers, and connections against `max_connections` (`STATUS.T4.LIVE`). The notebook says it can't read T4 and links to Hub.
6. **Lifecycle.** `deploy.ps1` starts a stopped T4 before the template; a T4 track checks the server (`Test-DemoT4`) and its metrics (`METRICS.T4`), and T1's track sets it up (a T4 failure doesn't stop T1). `start-demo.ps1` starts it, `stop-demo.ps1` stops it, `destroy.ps1` removes it with the resource group.
7. **Cost.** Compute is billed only while it runs; storage, its DNS zone, and the two Defender plans are billed all month, stopped or not. The estimate counts the 7-day restart's worst case against the monthly ceiling until a scheduled daily safety stop covers it (Phase 25c).

## Alternatives considered

- **A private endpoint** in private mode: $7.30 a month more, and a public server underneath. Rejected.
- **Public access with firewall rules** in public mode: T1 has no public IP, and a single mode is simpler to validate. Rejected.
- **The operator creates the runner's role** with an `ossrdbms` token: a token would travel through Run Command. Rejected (decision 2 of the coordinator).
- **A Real-Time Dashboard page over a Log Analytics workspace** (diagnostic settings): a new resource, $0 to $2.30 a month after the 5 GB free allowance, and a 2 to 10 minute delay. Deferred as a follow-up; Hub's dashboard is the live view.
- **T4 in the lakehouse history, the report, and the app:** needs an export path the notebook can't provide (no ARM token). Deferred as a follow-up (an operator-side export to OneLake).

## Consequences

- T4 adds about $24 to $27 a month while stopped (dated example, list prices 2026-10-23: storage $3.68, DNS zone $0.50, Defender for open-source relational databases $15, CSPM about $5.11) plus $0.017 an hour while running; the restart worst case adds up to about $12 a month. On the General Purpose option (`Standard_D2ds_v5`, 2026-10-26 list prices) compute is about $0.178 an hour and the restart worst case about $128 a month until Phase 25c's daily safety stop caps it. `estimate-cost.ps1` prices the configured size at run time.
- Hub shows T4's metrics, not its queries; the runner's `status` is the only query-level view.
- The Entra group sign-in by T1's managed identity is documented for groups and was proven live for a managed identity member on 2026-10-26 (R401).

## Validation

- Static: Bicep build and lint, PSRule, Pester (`DbHubDemo.T4.Tests.ps1`, the tracks, lifecycle, cost, estate, and VM tests), and the .NET tests (`PostgresTests`).
- Local: every T4 scenario, `status`, and `reset` against PostgreSQL 18.6 (`CONTOSOCARE_TEST_PG_SERVER`).
- Live (after the go): `deploy.ps1` creates T4, `HUB.ESTATE.T4` and `METRICS.T4` pass, each scenario runs once and resets, the convergence deploy changes nothing, and stop and start work.

## Amendments

### 2026-10-26: T4's size is a setting, and Azure refused every documented size in West US 3 (live)

- **What happened:** the first live deployments couldn't create `pgflex01-<deploymentId>`. Azure answered `SkuNotAvailable` ("Specified SKU is not supported in this region. Please choose a different SKU.") about three minutes into each creation, although the Location Based Capabilities API (2025-08-01) listed every Burstable size in zones 1 to 3 with `OfferRestricted` off, and `PREFLIGHT.T4.CAPABILITY` passed. Learn says the size is either not supported in the region or temporarily unavailable, and the remedy is another size ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors)). Azure dropped each refused server itself; only the private DNS zone and its virtual network link, which the template creates first, remained.

  | Attempt (UTC) | Size | Zone | Result |
  |---|---|---|---|
  | 14:11 | `Standard_B1ms` | no preference | `SkuNotAvailable` |
  | 15:21 | `Standard_B1ms` | 1 | `SkuNotAvailable` |
  | 15:35 | `Standard_B2s` | no preference | `SkuNotAvailable` |
  | 16:53 | `Standard_D2ds_v5` (General Purpose) | no preference (Azure placed it in zone 1) | Created: the server in 6 minutes 11 seconds, the module in about 8 minutes |

- **Decision (coordinator, for the owner):** the size and zone are settings. `t4SkuName` is `Standard_B1ms` by default, with `Standard_B2s` (2 vCores, 4 GiB) as the documented fallback; `t4AvailabilityZone` applies only when T4 is created, because a server keeps its zone. A refused size is a **Fail** in `deploy.ps1` (`DEPLOY.T4.SKU`, read from the deployment operations, where the code is) and in preflight (`PREFLIGHT.T4.SKU`; one more try in another zone is a **Warning**), and its remediation names the fallback, or, when the fallback was refused, a Region access request, a zone, or `t4Enabled: false`. Nothing raises the size on its own. `Test-DemoT4` and the cost estimate use the configured size, with its 7-day restart worst case (R441).
- **The owner's choice (11:44 ET):** after West US 3 refused both Burstable sizes, try General Purpose `Standard_D2ds_v5` (2 vCores, 8 GiB) once, at about $0.18 an hour, with a monthly worst case of about $128 for T4's 7-day restart until Phase 25c's daily safety stop is live. It's a documented option, never the default and never set automatically; the tier follows the size (`Burstable` for `Standard_B*`, otherwise `GeneralPurpose`), and General Purpose is priced per vCore-hour. Had it been refused too, no other size, zone, or region would have been tried. Query Store stays off on every size, so the server's configuration is the same.
- **Today's outcome:** `Standard_D2ds_v5` was created on the first try (16:53 UTC; the template took 8 minutes 45 seconds instead of about 2, R419). T1's managed identity signed in as the P6 group's role and set T4 up (`WORKLOAD.T4.ENABLE` **Pass**, so the R401 fallback wasn't needed); the server checks, `METRICS.T4` (after a fix: its query string couldn't pass through az.cmd), `HUB.ESTATE.T4`, `STATUS.T4`, and `STATUS.T4.LIVE` (859 connections on this size) passed; each scenario ran once and reset, the convergence redeploy changed nothing (R400), and T4 stopped, started, and stopped with the demo. It stopped at 19:06 UTC, so it starts on its own at 2026-11-02 19:06 UTC and then bills about $0.18 an hour until it's stopped, unless Phase 25c's daily safety stop is live by then. The B1ms default and the B2s fallback stay as they are; a Region access request for them is the owner's manual step ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors), "Other provisioning issues"). While T4 is off, its private DNS zone and virtual network link stay in the group (about $0.50 a month); `destroy.ps1` removes them with the group.

### 2026-10-29: the Burstable fallback (Phase 28)

- **Why:** a refused default size ended a colleague's first run in a **Fail** that needed a configuration edit (brief item 6). For the Burstable fallback only, this replaces the 2026-10-26 amendment's "nothing raises the size on its own".
- **Decision:** when the configuration doesn't set `t4SkuName` (it has no schema default any more, so an unset size is told apart from `Standard_B1ms` set on purpose), `deploy.ps1` tries `Standard_B1ms`, then `Standard_B2s`, the same Burstable class, by itself. Preflight reads the region's sizes with [`az postgres flexible-server list-skus`](https://learn.microsoft.com/cli/azure/postgres/flexible-server#az-postgres-flexible-server-list-skus) (the Location Based Capabilities API at the pinned version when the CLI's answer isn't in that shape) and starts with B2s when B1ms isn't listed or a refusal of B1ms in the same zone is on record (`PREFLIGHT.T4.CAPABILITY` or `PREFLIGHT.T4.SKU`, a **Warning**); the template's own `SkuNotAvailable` is the fallback for a refusal the list doesn't predict (`DEPLOY.T4.SKU` **Warning**). What was used is recorded in the resource group's tag `DbHubT4Sku` (`Standard_B2s`, or `None`), which later runs reuse (`Resolve-DemoEffectiveConfig`). A `t4SkuName` the configuration sets always wins over the record, and a deployment with T4 in it clears a recorded `None` (and any record once `t4SkuName` is set), so a T4 that's deployed is always judged by **DONE** (review fix, 2026-10-29).
- **When both are refused:** the run finishes without T4 (`DEPLOY.T4.SKU` **Warning**: `t4Enabled` stays as configured, but the server isn't created). **DONE** says T4 isn't deployed and why, and the result names the exact option, `"t4SkuName": "Standard_D2ds_v5"`, with its hourly price from the Azure Retail Prices API at run time, or a dated example when the API doesn't answer (ADR 0016). `HUB.ESTATE.T4` and `METRICS.T4` aren't required for **DONE** then (ADR 0018, section 1).
- **Unchanged:** a General Purpose size is never chosen on its own; a `t4SkuName` the configuration sets is never changed, and its refusal is still a **Fail**; the fallback applies only when T4 is created, so an existing server is deployed with the configured size, as before. *(The first and last points were replaced on 2026-11-02, below: the fallback can now choose General Purpose, and an existing server keeps its own size.)*
- **Validation:** unit-tested (`tests/unit/DbHubDemo.Lifecycle.Tests.ps1`, `DbHubDemo.Preflight.Tests.ps1`, `DbHubDemo.T4.Tests.ps1`, `DbHubDemo.Tracks.Tests.ps1`); not yet run live.

### 2026-11-02: the General Purpose fallback (Phase 28 follow-up)

- **Why:** one subscription in West US 3 refused both Burstable sizes on every run from 2026-10-29 to 2026-11-02, so a default configuration never got T4, while a configuration that set `t4SkuName` to `Standard_D2ds_v5` ran fine on the General Purpose tier. **The owner's decision (2026-11-02):** when both Burstable sizes are refused, fall back automatically to General Purpose `Standard_D2ds_v5`. This replaces the 2026-10-29 amendment's "a General Purpose size is never chosen on its own", for the fallback only.
- **When:** only Azure's `SkuNotAvailable` for the size the attempt sent, read from the T4 deployment's operations (`Get-DemoT4CreateFailure`), moves the fallback on: `Standard_B1ms`, then `Standard_B2s`, then `Standard_D2ds_v5`. A quota limit, a policy denial, or a transient error fails the template as before. A `t4SkuName` the configuration sets always wins, with no fallback and no size change, and `t4Enabled: false` turns T4 off with no fallback.
- **Priced first:** right before the fallback would create `Standard_D2ds_v5`, `deploy.ps1` prices it from the [Azure Retail Prices API](https://learn.microsoft.com/rest/api/cost-management/retail-prices/azure-retail-prices) through the demo's estimate (`Get-DemoT4GeneralPurposeCost`, `Get-DemoCostEstimate`; ADR 0016). The worst case is T4 running every hour of the month, because a stopped server starts again on its own after seven days ([overview](https://learn.microsoft.com/azure/postgresql/overview): "The server remains stopped for seven days unless you restart it sooner"; [stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server): "Server will be automatically started after 7 days"), plus its storage, its private DNS zone, and the Defender for open-source relational databases and Defender CSPM plans where the subscription's plans are on Standard (what a tenant policy enforces, `PREFLIGHT.POLICY.DEFENDER`); what has no price is named and left out. With the rest of the demo's light-use month it must be within `monthlyCeilingUsd`, and a session within `sessionCeilingUsd`. Otherwise, or without a compute price, T4 is left out (`DEPLOY.T4.SKU` **Warning**, record `None`) with a note naming the ceiling and the value to raise it to; the next run that deploys the template checks again. `deploy.ps1`'s preflight prices the same step ahead (`PREFLIGHT.T4.FALLBACK`) with the run's own estimate's prices, starting from the record; a standalone `preflight.ps1` doesn't read the record, so it prices the configuration, or an existing server's own size, with the General Purpose step ahead. When the fallback's own estimate fails, `PREFLIGHT.T4.FALLBACK` is a **Warning** and the run's own cost checks stand, a monthly-ceiling **Fail** included; after Azure rejects the T3 free offer, the check runs again without its allowance (review of 20e855c), unless the rejected attempt has already created the server, which then exists and bills and isn't priced again (review of 64c28b2).
- **Said loudly:** a console line, the status page's Infrastructure step, and the **DONE** or **NOT DONE** banner: `T4 created as General Purpose Standard_D2ds_v5 because Burstable sizes were refused here; about <price> USD an hour while running`, with the price the check read, never a number in the code. The banner says "created" only with evidence that the server exists (this run's template, T4's own checks, the T4 track's record, or a [Servers - Get](https://learn.microsoft.com/rest/api/postgresql/servers/get)); otherwise it says the fallback chose `Standard_D2ds_v5` but T4 isn't created yet, and why (review of 20e855c). A failed template or a `T4.SERVER` **Fail** isn't proof that the server is missing, because it depends only on the network and a failed read fails `T4.SERVER` too: the Servers - Get decides then (review of 64c28b2). `stop-demo.ps1` (`STOP.T4.STOP`) and `status.ps1` (`STATUS.T4`) give the date Azure starts a stopped T4 again, the stop time plus seven days, what it then bills, and whether the on-demand control's daily safety stop (ADR 0020) stops it again, read from its schedule as `CONTROL.SAFETYSTOP` reads it.
- **Kept:** the record `DbHubT4Sku` is `Standard_D2ds_v5` (or `Refused` when Azure refuses it too; nothing is tried again on its own then), in the resource group's tags and the run record, so a redeploy keeps the size and never tries `Standard_B1ms` again. An existing server keeps its own size, whatever the record says and whether the fallback or a configuration created it, unless the configuration sets `t4SkuName`. A record that doesn't match the server is cleared, never set to the server's size, so a record always means the fallback chose it (review of 20e855c). A server that a failed attempt of the same run created counts as existing: T4 is read again after each failed attempt while the fallback is choosing, and a server it finds keeps its size and record, is never recorded `None` or `Refused`, and is never moved to another size; `status.ps1` and `validate.ps1` report one that exists although the record says T4 is off as a **Warning** (review of 64c28b2). A `None` record from Phase 28 gets the General Purpose fallback, with its cost check, on the next run that deploys the template.
- **The template, on both tiers:** the tier follows the size (`Burstable` for `Standard_B*`, otherwise `GeneralPurpose`). The rest is valid on both and unchanged: 32 GiB of Premium SSD at P4 without auto-grow, 7-day backups without geo-redundancy, high availability off (Burstable doesn't support it), no IOPS setting (Premium SSD's IOPS come from its tier), and Query Store off ([compute options](https://learn.microsoft.com/azure/postgresql/configure-maintain/concepts-compute)).
- **Validation:** unit-tested (`tests/unit/DbHubDemo.T4Fallback.Tests.ps1`, one Describe per guardrail, and the preflight, cost, lifecycle, T4, tracks, activity control, and one-command tests). Live, only the free preflight check (2026-11-02): `PREFLIGHT.T4.FALLBACK` **Pass** in West US 3, with prices read live that day, within both ceilings. The owner chose to merge without a live proof, so the create path (B1ms, then B2s refused, then `Standard_D2ds_v5` created) and keeping the size on a redeploy haven't run live; the first real fallback run is to be watched (R600, R601). The follow-up for a server that a failed attempt created (review of 64c28b2) is unit-tested only (R602).

### 2026-11-03: `max_connections` at 50 on every size, and `connection-surge` past the limit (the showcase)

- **Why:** the owner asked to "fill all the visuals" (2026-11-03). Database Hub's PostgreSQL **Failed connections** chart (`connections_failed`) stayed empty on `Standard_B2s` and `Standard_D2ds_v5`, whose default `max_connections` (429 and 859) is above `connection-surge`'s cap of 60 connections a wave. And on every size, the surge's `overshoot` attempts only took the `headroom` slots its ramp had left free, so the server refused nothing; no refusal was ever seen live.
- **Decision (the coordinator for the owner, stage 2 decision D3):** the template sets `max_connections` to **50 on every size** (`config/versions.json` `postgresql.maxConnections`, `infra/modules/pgflex01.bicep`), `Standard_B1ms`'s own default.
  - **The parameter:** an integer, allowed values 25-5000, **static**; its default follows the memory: 50 at 2 GiB, 429 at 4 GiB, 859 at 8 GiB ([connection settings](https://learn.microsoft.com/azure/postgresql/server-parameters/param-connections-authentication-connection-settings), updated 2026-07-13). "After you change this setting, you need to restart your server for the new limit to start working" ([limits](https://learn.microsoft.com/azure/postgresql/configure-maintain/concepts-limits), updated 2026-07-10). 15 slots stay reserved (`reserved_connections` 5 and `superuser_reserved_connections` 10, both read-only), which leaves 35 for the runner.
  - **Why it's safe:** it lowers the limit within the documented range, and Learn's caution is only against raising it above the default. 50 is the default size's own limit, which the scenarios are sized for: apart from the surge, a T4 scenario's concurrency is 16 at most, plus a few helper sessions, the baseline, and a control session per run. Database Hub's PostgreSQL monitoring reads Azure Monitor metrics and opens no connection.
  - **The restart:** a static parameter's new value waits until the server restarts (`isConfigPendingRestart`, [Configurations - Get](https://learn.microsoft.com/rest/api/postgresql/configurations/get)). Right before T1 sets T4 up (T1's T4 step, or the sequential T4 stage), `deploy.ps1` restarts a Ready T4 whose `max_connections` waits, with [Servers - Restart](https://learn.microsoft.com/rest/api/postgresql/servers/restart), which restarts the PostgreSQL engine, not the compute ([restart a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-restart-server)). It waits until the value is in effect (`DEPLOY.T4.RESTART`). Nothing pending means no restart, and no other step restarts T4, so no setup runs into one. `Test-DemoT4` reports the value (`T4.MAXCONNECTIONS`: **Pass** in effect; **Warning** while it waits for a restart, or when it's another value).
  - **Existing servers:** `./scripts/deploy.ps1 -FromStage Infrastructure`, or a plain `./scripts/deploy.ps1` after a run that ended **DONE** (it starts over), applies the template, which sets the value, and T1's T4 step then restarts T4 and sets it up. `deploy.ps1 -Resume` doesn't: after a finished deployment it only runs the validation again.
- **`connection-surge` past the limit (the owner's bounds, 2026-11-03):** after a wave's ramp, the runner fills the headroom one connection at a time for **5 seconds at most**, so its next attempts are past the limit and the server refuses them (SQLSTATE 53300), then closes the connections it filled before the hold.
  - At most **5 refused attempts in any minute and 30 in a run**, fixed in the runner (`SurgeBounds`), whatever `overshoot` is; a refusal during a ramp counts too, so a wave starts only while one more is allowed.
  - Refusals come only from the connection limit: every attempt signs in with T1's managed identity like any other runner session, and a sign-in failure ends the surge, so it never repeats a failed sign-in, which Microsoft Defender could read as a brute-force attempt.
  - Only `ContosoCare.Demo/connection-surge/<run>` sessions to `contosocare` are opened, all within the run's duration (15 minutes at most). The other T4 lanes' connection opens retry a 53300 refusal for up to 90 seconds, so they record no failure.
- **Validation:** unit-tested (`tests/unit/DbHubDemo.T4.Tests.ps1`; the runner's `ConnectionSurgeTests`). **Not proven live:** the restart, the value on each size, and refused attempts in Database Hub's Failed connections wait for the owner's live check ([limitations](../limitations.md)).
