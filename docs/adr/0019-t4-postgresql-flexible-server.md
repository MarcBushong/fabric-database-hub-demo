# ADR 0019: T4, an Azure Database for PostgreSQL flexible server

- **Status:** Accepted. Built and checked statically and against a local PostgreSQL 18.6 on 2026-10-23; validated live on 2026-10-26 on the General Purpose option (see the amendment)
- **Date:** 2026-10-23
- **Decision source:** User-directed (2026-10-23: "add PostgreSQL as T4: the smallest burstable flexible server, stopped and started with the demo, with its own bounded activity and incidents", then "I want to see live query data and metrics. History not as important"), with the networking, access, live-view, history, and metrics choices decided by the coordinator for the owner the same day
- **Related:** [ADR 0007](0007-networking-modes-and-egress.md), [ADR 0008](0008-identity-rbac-abac.md), [ADR 0009](0009-secrets-handling.md), [ADR 0010](0010-workload-generator-technology.md), [ADR 0012](0012-validation-model.md), [ADR 0016](0016-cost-profiles.md), [ADR 0018](0018-fast-redeploy-parallel-tracks-golden-snapshot.md), [architecture](../architecture.md), [limitations](../limitations.md)

## Context

- **Database Hub supports Azure Database for PostgreSQL flexible server (preview).** Estate lists flexible servers, not their databases. Its PostgreSQL monitoring "uses existing Azure Monitor metrics" and has no query-level diagnostics; discovery needs Reader and nothing else (no extended property, Arc, or extra resource provider). Performance has a **PostgreSQL** dashboard over `cpu_percent`, `memory_percent`, `storage_percent`, `iops`, `active_connections`, and `connections_failed` ([monitor PostgreSQL](https://learn.microsoft.com/fabric/database/hub/monitor-postgresql), checked 2026-10-23).
- **The tenant (read-only checks, 2026-10-23):** 64 enforcing policy rules, none for `Microsoft.DBforPostgreSQL`; Defender for open-source relational databases and Defender CSPM are on Standard through a tenant policy, so they bill T4; the resource provider is registered; West US 3 offers `Standard_B1ms` (1 vCore, 2 GiB, 640 IOPS) and PostgreSQL 11 to 18 ([Location Based Capabilities](https://learn.microsoft.com/rest/api/postgresql/flexibleserver/location-based-capabilities/execute)).
- **A stopped flexible server starts on its own after seven days,** and rejects every other management operation while stopped ([stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server)).
- **Fabric notebooks can't reach T4:** `notebookutils` tokens cover storage, Power BI, Key Vault, and Kusto only, so there's no Azure Resource Manager or `ossrdbms` audience ([notebookutils](https://learn.microsoft.com/fabric/data-engineering/notebook-utilities)).
- **Query Store** mustn't be enabled on the Burstable tier ([Query Store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)).

## Decision

1. **The server.** `pgflex01-<deploymentId>` in `rg-<prefix>-<environment>` (`infra/modules/pgflex01.bicep`), Burstable `Standard_B1ms` by default (`t4SkuName`; `Standard_B2s` is the documented fallback and General Purpose `Standard_D2ds_v5` the documented option the owner chose, see the 2026-10-26 amendment; the tier follows the size), in an optional availability zone at creation (`t4AvailabilityZone`), 32 GiB (P4) without auto-grow, 7-day backups without geo-redundancy, no high availability, PostgreSQL **18** pinned in `config/versions.json` (`postgresql.majorVersion`), and the database `contosocare`. `t4Enabled` (default true) turns it off.
2. **Networking: virtual network integration in both network modes.** A delegated `/28` (`snet-pg`, 10.42.0.96/28), a private DNS zone `<prefix>-<environment>.private.postgres.database.azure.com` linked to the network, and no public access. Its network security group allows port 5432 only from T1's subnet. No private endpoint, so no endpoint charge ([private access](https://learn.microsoft.com/azure/postgresql/network/concepts-networking-private)).
3. **Access: Microsoft Entra only, no secret anywhere.** Password authentication is off; the P6 group (T3's administrator) is T4's Entra administrator. T1's managed identity, a member of P6, signs in as the group's role and creates the runner's role `contosocare_runner` for its own object ID with `pgaadauth_create_principal_with_oid`, then the schema, seed, and grants (`Enable-DemoT4Workload`, action Run Command `EnableT4`). No operator token travels and no password exists ([Entra users](https://learn.microsoft.com/azure/postgresql/security/security-manage-entra-users), [managed identity](https://learn.microsoft.com/azure/postgresql/security/security-connect-with-managed-identity)). The runner's role gets the demo's tables and functions in `contosocare` and, if allowed, `pg_read_all_stats`, and nothing else.
4. **Workload: the same runner interface and scenario names as T1 to T3.** `run`, `stop`, `reset`, `status`, `profile`, and `setup` take `--target T4` (Npgsql, TLS `VerifyFull`, no pooling, the managed identity's token as each connection's password). T4 runs `healthy-baseline`, `cpu-pressure`, `locking-blocking`, `io-pressure`, and two PostgreSQL-only scenarios, `connection-surge` and `idle-in-transaction`, each with a hard maximum duration; only `ContosoCare.Demo/` sessions in `contosocare` are touched (`pg_terminate_backend` in `demo.usp_kill_demo_sessions`), and `reset` restores the seed. T4's activity profile is a file on T1 (`activity-t4.json`), so setting it never connects to T4.
5. **Live view: Hub's PostgreSQL dashboard and the runner's `status`.** The free enhanced metrics are on (`metrics.collector_database_activity`: sessions by state and by wait event type, the oldest transaction and query, deadlocks). `status.ps1` shows them (`STATUS.T4`), and with `-Detail` the runner's live view of sessions, waits, blockers, and connections against `max_connections` (`STATUS.T4.LIVE`). The notebook says it can't read T4 and links to Hub.
6. **Lifecycle.** `deploy.ps1` starts a stopped T4 before the template; a T4 track checks the server (`Test-DemoT4`) and its metrics (`METRICS.T4`), and T1's track sets it up (a T4 failure doesn't stop T1). `start-demo.ps1` starts it, `stop-demo.ps1` stops it, `destroy.ps1` removes it with the resource group.
7. **Cost.** Compute is billed only while it runs; storage, its DNS zone, and the two Defender plans are billed all month, stopped or not. The estimate counts the 7-day restart's worst case against the monthly ceiling until a scheduled daily safety stop covers it (Phase 25c).

## Alternatives considered

- **A private endpoint** in private mode: $7.30 a month more, and a public server underneath. Rejected.
- **Public access with firewall rules** in public mode: T1 has no public IP, and a single mode is simpler to validate. Rejected.
- **The operator creates the runner's role** with an `ossrdbms` token: a token would travel through Run Command. Rejected (decision 2 of the coordinator).
- **A Real-Time Dashboard page over a Log Analytics workspace** (diagnostic settings): a new resource, $0 to $2.30 a month after the 5 GB free allowance, and a 2 to 10 minute delay. Deferred as a follow-up; Hub's dashboard is the live view.
- **T4 in the lakehouse history, the report, and the app:** needs an export path the notebook can't provide (no ARM token). Deferred as a follow-up (an operator-side export to OneLake).

## Consequences

- T4 adds about $24 to $27 a month while stopped (dated example, list prices 2026-10-23: storage $3.68, DNS zone $0.50, Defender for open-source relational databases $15, CSPM about $5.11) plus $0.017 an hour while running; the restart worst case adds up to about $12 a month. On the General Purpose option (`Standard_D2ds_v5`, 2026-10-26 list prices) compute is about $0.178 an hour and the restart worst case about $128 a month until Phase 25c's daily safety stop caps it. `estimate-cost.ps1` prices the configured size at run time.
- Hub shows T4's metrics, not its queries; the runner's `status` is the only query-level view.
- The Entra group sign-in by T1's managed identity is documented for groups and was proven live for a managed identity member on 2026-10-26 (R401).

## Validation

- Static: Bicep build and lint, PSRule, Pester (`DbHubDemo.T4.Tests.ps1`, the tracks, lifecycle, cost, estate, and VM tests), and the .NET tests (`PostgresTests`).
- Local: every T4 scenario, `status`, and `reset` against PostgreSQL 18.6 (`CONTOSOCARE_TEST_PG_SERVER`).
- Live (after the go): `deploy.ps1` creates T4, `HUB.ESTATE.T4` and `METRICS.T4` pass, each scenario runs once and resets, the convergence deploy changes nothing, and stop and start work.

## Amendments

### 2026-10-26: T4's size is a setting, and Azure refused every documented size in West US 3 (live)

- **What happened:** the first live deployments couldn't create `pgflex01-<deploymentId>`. Azure answered `SkuNotAvailable` ("Specified SKU is not supported in this region. Please choose a different SKU.") about three minutes into each creation, although the Location Based Capabilities API (2025-08-01) listed every Burstable size in zones 1 to 3 with `OfferRestricted` off, and `PREFLIGHT.T4.CAPABILITY` passed. Learn says the size is either not supported in the region or temporarily unavailable, and the remedy is another size ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors)). Azure dropped each refused server itself; only the private DNS zone and its virtual network link, which the template creates first, remained.

  | Attempt (UTC) | Size | Zone | Result |
  |---|---|---|---|
  | 14:11 | `Standard_B1ms` | no preference | `SkuNotAvailable` |
  | 15:21 | `Standard_B1ms` | 1 | `SkuNotAvailable` |
  | 15:35 | `Standard_B2s` | no preference | `SkuNotAvailable` |
  | 16:53 | `Standard_D2ds_v5` (General Purpose) | no preference (Azure placed it in zone 1) | Created: the server in 6 minutes 11 seconds, the module in about 8 minutes |

- **Decision (coordinator, for the owner):** the size and zone are settings. `t4SkuName` is `Standard_B1ms` by default, with `Standard_B2s` (2 vCores, 4 GiB) as the documented fallback; `t4AvailabilityZone` applies only when T4 is created, because a server keeps its zone. A refused size is a **Fail** in `deploy.ps1` (`DEPLOY.T4.SKU`, read from the deployment operations, where the code is) and in preflight (`PREFLIGHT.T4.SKU`; one more try in another zone is a **Warning**), and its remediation names the fallback, or, when the fallback was refused, a Region access request, a zone, or `t4Enabled: false`. Nothing raises the size on its own. `Test-DemoT4` and the cost estimate use the configured size, with its 7-day restart worst case (R441).
- **The owner's choice (11:44 ET):** after West US 3 refused both Burstable sizes, try General Purpose `Standard_D2ds_v5` (2 vCores, 8 GiB) once, at about $0.18 an hour, with a monthly worst case of about $128 for T4's 7-day restart until Phase 25c's daily safety stop is live. It's a documented option, never the default and never set automatically; the tier follows the size (`Burstable` for `Standard_B*`, otherwise `GeneralPurpose`), and General Purpose is priced per vCore-hour. Had it been refused too, no other size, zone, or region would have been tried. Query Store stays off on every size, so the server's configuration is the same.
- **Today's outcome:** `Standard_D2ds_v5` was created on the first try (16:53 UTC; the template took 8 minutes 45 seconds instead of about 2, R419). T1's managed identity signed in as the P6 group's role and set T4 up (`WORKLOAD.T4.ENABLE` **Pass**, so the R401 fallback wasn't needed); the server checks, `METRICS.T4` (after a fix: its query string couldn't pass through az.cmd), `HUB.ESTATE.T4`, `STATUS.T4`, and `STATUS.T4.LIVE` (859 connections on this size) passed; each scenario ran once and reset, the convergence redeploy changed nothing (R400), and T4 stopped, started, and stopped with the demo. It stopped at 19:06 UTC, so it starts on its own at 2026-11-02 19:06 UTC and then bills about $0.18 an hour until it's stopped, unless Phase 25c's daily safety stop is live by then. The B1ms default and the B2s fallback stay as they are; a Region access request for them is the owner's manual step ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors), "Other provisioning issues"). While T4 is off, its private DNS zone and virtual network link stay in the group (about $0.50 a month); `destroy.ps1` removes them with the group.
