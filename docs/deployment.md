# Deployment

How to deploy the demo and run it day to day. The building blocks below ran live in West US 3 on 2026-10-20 and 2026-10-21. The scripts that chain them (`deploy.ps1`, `start-demo.ps1`, `stop-demo.ps1`, and `reset-demo.ps1`) ran end to end in Phase 20's live test on 2026-10-22: the measured times are [below](#parallel-tracks-phase-20), and the [implementation report](implementation-report.md#phase-20-fast-redeploy-parallel-tracks-and-a-t2-golden-snapshot) has the full results. Those runs predate T2's default install mode since 2026-11-05, `JumpstartImage` ([below](#t2-from-arc-jumpstarts-image-jumpstartimage)), whose first clean deployment ended **DONE** in 91 minutes on 2026-11-06 ([what a clean first deployment shows](#what-a-clean-first-deployment-shows-2026-11-06)). When something isn't **Pass**, see [troubleshooting](troubleshooting.md).

## Before you start

1. Meet the prerequisites in [prerequisites.md](prerequisites.md): P1–P6 are required, and P12–P14 are for the Insights app, which every deployment adds but which never keeps the run from **DONE**. Contributor on the subscription is enough for the default path. One more is recommended, once per environment: an Owner for the nightly safety stop's role (P16); without one, the run still ends **DONE** and prints the Owner's command ([the nightly safety stop](#the-nightly-safety-stop)). Every tool is in the repository's [dev container](../.devcontainer/devcontainer.json), locally or in GitHub Codespaces.
2. Sign in yourself, once, as the account that runs the demo: `az login`, or `az login --use-device-code` in a codespace or a container without a browser ([sign in interactively](https://learn.microsoft.com/cli/azure/authenticate-azure-cli-interactively)). The scripts never sign in, sign out, or change the Azure CLI context, and **you don't need to change your default subscription**: every Azure call carries the configured subscription, and the subscription guard checks the account and tenant that subscription's sign-in uses before anything is written ([prerequisites](prerequisites.md#target-subscription-configuration-the-subscription-guard)). On a machine whose Azure CLI profile is shared with other work, you can sign in under a separate `AZURE_CONFIG_DIR` instead ([optional isolation](prerequisites.md#optional-a-separate-azure-cli-profile)); in Cloud Shell, skip this step.
3. Write `config/demo.config.json` (Git ignores it) with `./scripts/init.ps1` ([below](#first-run-initps1)), or copy `config/demo.config.example.json` and fill it in by hand. `Get-DemoConfig` checks it against `config/environment.schema.json`. Since Phase 28 this step is optional: `./scripts/deploy.ps1` writes the file itself when it's missing, with the same prompts ([one command, one guided stop](#one-command-one-guided-stop-phase-28)).

```powershell
az login                               # once; leave the default subscription as it is
./scripts/init.ps1 -CreateAdminGroup   # optional: config/demo.config.json from your sign-in (deploy.ps1 runs it when the file is missing)
./scripts/preflight.ps1                # optional, read-only: guard, P1-P6, region, sizes, quota, policy, and the cost estimate
./scripts/estimate-cost.ps1            # optional: the live estimate against both ceilings
./scripts/deploy.ps1                   # everything else, with one guided stop in PaygWizard mode
```

If a script stops at `PREFLIGHT.GUARD.CONTEXT`, its message names the failed check:

| Check | What it means | Fix |
|---|---|---|
| `account` | The Azure CLI has no sign-in for the configured subscription, has it in another tenant, or reaches it as another account than `azureAccount` | `az login --tenant <tenantId>` as the right account, or correct `azureAccount` |
| `canary.arm`, `canary.armRest` | Azure Resource Manager refused the configured subscription for that account | Check the account's role on the subscription (P1) |
| `canary.armToken`, `canary.fabricToken`, `canary.kustoToken`, `canary.graphToken` | No token without interaction (an expired sign-in or a new MFA prompt), or a token for another tenant or identity | `az login --tenant <tenantId>` again |
| `canary.graphOrganization` | Microsoft Graph answered for another tenant | The same; the sign-in is mixed up with another tenant's |

A **Warning** on the guard means `azureAccount` isn't set: the evidence names the account the guard found, so you can set it.

### First run: `init.ps1`

`init.ps1` (Phase 26b, [ADR 0023](adr/0023-first-run-automation.md)) writes your configuration from your sign-in, so a first run needs no IDs looked up by hand. It took 44 seconds in a read-only run on 2026-10-27.

1. **Your subscriptions, before the guard:** `az account list --output json` reads the subscriptions the Azure CLI's own sign-in cached in its profile ([az account list](https://learn.microsoft.com/cli/azure/account#az-account-list)). It's read-only and local, and it's the one Azure CLI call the scripts make before the subscription guard, because the guard needs a subscription to check. With more than one, `init.ps1` asks (or takes `-SubscriptionId`); it never runs `az account set`. Not signed in: **Manual action required** with the `az login` command.
2. **The guard** runs for the chosen subscription, its tenant, and its account, and everything after it goes through it.
3. **You:** Microsoft Graph's [`/me`](https://learn.microsoft.com/graph/api/user-get), with the guard's verified token, gives the budget alerts' address (`ownerEmail`) and the owner tag. `az ad signed-in-user show` isn't used: it answers for the Azure CLI's default account, which can be in another tenant.
4. **P1** (`INIT.P1.CONTRIBUTOR`): your permissions on the subscription, as preflight reads them; without Contributor, **Manual action required** with the Owner's exact `az role assignment create` command.
5. **Fabric** (`INIT.FABRIC.CAPACITY`, `INIT.FABRIC.WORKSPACE`): the F, Trial, and P capacities you can assign ([List Capacities](https://learn.microsoft.com/rest/api/fabric/core/capacities/list-capacities); Premium Per User isn't offered), and it asks when there's more than one; then whether the workspace `fabric.workspaceName` ("Database Hub Demo" by default) exists ([List Workspaces](https://learn.microsoft.com/rest/api/fabric/core/workspaces/list-workspaces)). A workspace that doesn't exist yet gets `fabric.importNotebooks` true, and `deploy.ps1` creates it, its lakehouse, and the notebooks. Nothing is created in Fabric here. A paused capacity is a **Warning**: the Fabric track needs it running.
6. **P6** (`INIT.P6.GROUP`): the security group `-AdminGroupObjectId`, or the one named `-AdminGroupName` (by default `<prefix>-<environment>-sql-admins`), and whether you own it. With `-CreateAdminGroup`, a missing group is created with you as its owner, through Microsoft Graph's [Create group](https://learn.microsoft.com/graph/api/group-post-groups) with `owners@odata.bind`, then [Add owners](https://learn.microsoft.com/graph/api/group-post-owners) if the owners don't list you: an administrator who creates a security group isn't made its owner automatically. These are the calls behind `az ad group create` and `az ad group owner add`. Where the tenant lets only administrators create groups ([self-service group management](https://learn.microsoft.com/entra/identity/users/groups-self-service-management)), it's **Manual action required** with the steps for an administrator, and the configuration gets the all-zero placeholder until you run `init.ps1 -Force -AdminGroupObjectId <id>`.
7. **T2's mode, without a question** (since 2026-11-09, user-directed: "It should be one click everytime and especially the first time"): `-T2SqlInstallMode` when you give it, otherwise `JumpstartImage` (the default since 2026-11-05: Arc Jumpstart's prebuilt SQL Server 2022 Standard guest, with Hub Performance on T2 and no stop; [below](#t2-from-arc-jumpstarts-image-jumpstartimage)), and one line says which and how to choose another on purpose: `Developer` (no stop; T2 in Hub's Estate only). `PaygWizard`, whose setup wizard needs a person in Bastion, is retired from the one-click deployment (2026-11-09): a configuration that says it runs as `JumpstartImage`. `ProductKey` (P10) is set in the configuration file instead.
8. **The file** (`INIT.CONFIG`): the example configuration with these values, validated against the schema. A path Git would commit is refused (**Fail**). An existing file is replaced only with `-Force`, after a copy to `out/config-backup` (Git-ignored). `fabric.manageCapacity` stays false unless `-ManageCapacity`. The VMs' auto-shutdown time zone is this machine's (a codespace is usually in UTC; pass `-TimeZone 'Eastern Standard Time'` or your own).
9. **Next steps:** the exact commands, with `-ConfigPath` when you wrote another file.

`-WhatIf` reads everything and writes nothing: no file and no group. `-NonInteractive` never asks; an ambiguous choice is **Manual action required** with the parameter to pass.

**From `deploy.ps1` (Phase 28):** when the configuration file doesn't exist, `deploy.ps1` runs these same steps first (`Initialize-DemoFirstRun`, with `-CreateAdminGroup`, and with `-NonInteractive` when the session can't take keyboard input), then deploys with the file it wrote. When a step needs a person (no sign-in, a group that only an administrator may create, or a choice it can't ask about), it stops before anything is created and ends **NOT DONE** with that step's fix and the command to run next.

## One command: `deploy.ps1`

```powershell
./scripts/deploy.ps1
```

`deploy.ps1` runs Preflight, then Infrastructure while the tracks start, each in its own process (T1 with T3, T2, T4, and Fabric) with its own guard, then the validation ([parallel tracks](#parallel-tracks-phase-20), [ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)), and last, once **DONE**'s telemetry checks pass, the history report's snapshot ([below](#the-history-reports-snapshot-at-the-end-2026-11-06)). The tracks do the same work as the stages below, which `-Sequential` runs one after another (`Invoke-DemoDeployment`). Each stage is idempotent, so a rerun converges. Since Phase 28 it's the whole deployment after `az login`, with one guided stop in `PaygWizard` mode and one ending, **DONE** or **NOT DONE** ([below](#one-command-one-guided-stop-phase-28)).

| Stage | What it does | A Fail here |
|---|---|---|
| Preflight | The subscription guard, P1–P6, region, sizes, quota, policy, and the cost estimate against both ceilings. It resolves the network mode, the T3 free offer, and the P6 group's name. | Stops before anything is deployed |
| Infrastructure | Deploys `azuredeploy.json` at subscription scope. If Azure rejects the T3 free offer, it deploys again with regular serverless and reports a **Warning** (`T3.FREEOFFER`). With the Key Vault opt-in, it then deploys the vault and your access to it ([below](#opt-in-the-password-in-key-vault-instead-of-the-clipboard)). With the on-demand activity control, it then grants A1 again ([below](#the-on-demand-activity-control-a1-after-a-redeploy)). Then it sets up the [nightly safety stop](#the-nightly-safety-stop), Warnings only. | Stops (a vault **Fail** doesn't, nor does A1 or the safety stop) |
| Artifacts | Builds the bootstrap bundle and the workload runner, then sends both to each VM in Run Command chunks. A VM that already has exactly these chunks is skipped. | Stops |
| Bootstraps | Deploys the template again with both SHA-256 hashes and chunk counts, which runs the loaders; waits for them, then for T1 to be Ready. | Stops |
| T3 | Adds T1 to the T3 administrators group (P6), runs the T3 setup from T1, enables the runner on T3, and checks T3, in the order that worked live. | Stops |
| Activity | Sets the configured `activityProfile` on T1, T3, and T4 until the next auto-shutdown; `business-day`, the default, starts as `baseline` and is switched after **DONE**'s checks (`DEPLOY.INCIDENTS_*`). | Never: a Warning |
| Monitoring | Turns on T1's performance monitoring, as `configure-monitoring.ps1 -Target T1` does. A template deployment keeps the SQL IaaS extension `Updating` for about 10 minutes; that's a wait, not a failure. | Stops |
| T2 | Arc onboarding and configuration (`configure-arc.ps1`), then T2's activity profile. | Stops |
| Fabric | The Database Hub checklist and, on request, the notebook import (`configure-fabric.ps1`), then the Insights app (`configure-fabric-app.ps1`, [part of every deployment](#the-insights-app-part-of-every-deployment-2026-11-05)). | Stops; the Insights app's step never does |
| Validation | Telemetry for each ready target, the runner's status, and a summary; then **DONE**'s checks, the switch to the activity profile, and the history report's snapshot (`NB_DatabaseHub_LiveActivity` once, analyze-only; [below](#the-history-reports-snapshot-at-the-end-2026-11-06)). | Reported; the snapshot is never a **Fail** |

- **Manual steps are never hidden.** **Manual action required** doesn't stop the run: the stage stays open, the later stages still run, and `DEPLOY.SUMMARY` lists every manual item with its exact steps. Fix it, then run `./scripts/deploy.ps1` again, which continues by itself since Phase 28 (`-Resume` does the same).
- **State lives in the resource group's tags** (`DbHub*`: the last stage that finished, the bundle and runner hashes, the VMs that have them, the network mode, the free-offer decision, the P6 group name, T4's size when its fallback chose it, the guided stop's time limit, and when the T2 host's loader started a bootstrap generation that nobody has seen finish), so a rerun or `-Resume` works from any machine and from GitHub Actions. The recorded stage never moves past an open stage.
- **Results** go to the console, to `out/deploy.jsonl` (one [ADR 0012](adr/0012-validation-model.md) result per line), and to the job summary in GitHub Actions, and the console's transcript goes to `out/logs/deploy-<time>.log` (not in GitHub Actions). Deployment success alone is never **Pass**. Exit codes (Phase 28): 0 when the run ends **DONE**, 1 when it ends **NOT DONE** with a **Fail**, and 2 when it ends **NOT DONE** otherwise; a `-WhatIf` run returns 0 unless a check failed. GitHub Actions keeps the earlier codes: 0 when nothing failed, 1 for any **Fail**, 2 for **Manual action required** with `-TreatManualAsError`.

| Option | Use |
|---|---|
| `-Resume` | Continue after the last stage that finished, each track after the last step it finished in this deployment. Since Phase 28 a run without `-Resume` or `-FromStage` does this by itself when the last deployment didn't finish (not in GitHub Actions); a run that starts over clears the tracks' records first, so a later resume never skips a step that failed after an earlier run finished it. A VM's track that a resume would continue past its Artifacts step goes back to that step when the VM doesn't have the bootstrap bundle or the workload runner that this checkout builds, so a fix pulled since the last run reaches it ([below](#one-command-one-guided-stop-phase-28); 2026-11-06). |
| `-FromStage <stage>` / `-StopAfter <stage>` | Run a range of stages. `-StopAfter Infrastructure` gives what the Deploy to Azure button gives. |
| `-WhatIf` | Run the read-only preflight (without registering providers) and the template's what-if, then stop. Nothing is recorded. |
| `-SkipRunner` | Deploy without the workload runner (no .NET SDK needed); the activity profiles are **Not selected**. |
| `-SkipFabric`, `-ImportNotebooks` | Skip the Fabric stage, and the history report's snapshot at the end (**Not selected**), or also update both notebooks when they're already in the workspace (also `fabric.importNotebooks`). Without it, the stage imports only the notebooks that are missing, so a new workspace or lakehouse gets them without asking ([configuration](configuration.md#fabric)). |
| `-T1WaitMinutes`, `-T2WaitMinutes`, `-MonitoringWaitMinutes`, `-TelemetryWaitMinutes` | How long each wait lasts (45, 180, 20, and 15 by default). The T2 guest build takes about 60–90 minutes in the build modes, `PaygWizard`, `ProductKey`, and `Developer` (in `JumpstartImage` mode, the host's build with the image's download and first boot took about 27, measured on 2026-11-06), and in `PaygWizard` mode the guided stop then waits at least 45 minutes for a person once it asks, so `-T2WaitMinutes` covers both (Phase 28; it was 120). `-MonitoringWaitMinutes` is elapsed time, the reads included, and a T1 monitoring plugin that reports `NotRunning` gets only a short grace of it (3 minutes, or 5 when this run merged the monitoring flag) before the SQL IaaS Agent service is restarted (Phase 28 live finding, 2026-10-30: the wait ran 25 minutes on a plugin that a restart brought back in 17 seconds). |
| `-Sequential` | Run the stages one after another, as before Phase 20, instead of the parallel tracks. It has no guided stop. It's judged by the same DONE requirements: after its validation, with no stage open, it checks what DONE needs read-only, and it's **DONE** once the recorded stage is `Validation` and they pass; otherwise **NOT DONE** with `./scripts/deploy.ps1`, which continues after the last stage that finished. Its Fabric stage imports the Real-Time Dashboard and the history model and report, as the parallel Fabric track does, then the Insights app (2026-11-05; before, it was `./scripts/configure-fabric-app.ps1`'s alone): the app's sign-in starts at the beginning of the run, as in the parallel path, and the Fabric stage waits for it, at most until its deadline, right before the app's step. It ends with the history report's snapshot too, after its **DONE** checks and the switch ([below](#the-history-reports-snapshot-at-the-end-2026-11-06)). |
| `-NoWaitForT2` | Don't wait for T2's guest build (Phase 28): T1, T3, T4, and Fabric finish now, T2 keeps building in the background (`DEPLOY.T2.BACKGROUND`, **Manual action required**), and a later `./scripts/deploy.ps1` finishes it, with the guided stop in `PaygWizard` mode. |
| `-WaitForT2` | Wait for T2 in GitHub Actions or another CI system too. Elsewhere it's the default since Phase 28, so the switch is accepted but redundant. |
| `-NoStatusPage`, `-NoBrowser` | Write no progress model and no status page (the guided stop's prompt, reminders, and `HUMAN ACTION REQUIRED` line still come in the console, from the T2 track's process); or write them but open nothing in a browser (the page's path and the portal link are printed). |
| `-PolicyCacheHours` | Reuse preflight's last complete policy inventory while the policy assignments that apply are unchanged and it's at most this old (168 by default; the reused results say so). `0` reads every policy definition again (7–13 minutes measured). |

**The machine that runs `deploy.ps1` must stay awake.** Its tracks poll Azure from your machine; if it sleeps (Modern Standby included), every process freezes until it wakes, and the run takes that much longer (live, 2026-10-23: 35 minutes). Since Phase 28, `deploy.ps1` keeps a Windows PC and its display awake until it ends, and releases that in a `finally` ([SetThreadExecutionState](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate), with `ES_SYSTEM_REQUIRED`, `ES_DISPLAY_REQUIRED`, and `ES_CONTINUOUS`; Phase 25a found the display flag necessary). It can't stop a lid close or a shutdown, so plug a laptop in and leave it open. On macOS and Linux it changes nothing: keep the machine awake with its own settings.

### One command, one guided stop (Phase 28)

Two colleagues' first runs took more than 2 hours and never finished: preflight's first policy inventory and stuck Run Command deletes held the bootstraps back, `deploy.ps1` returned with T2 still building and a second command to remember, and a PC that went to sleep froze a run. Since Phase 28, `./scripts/deploy.ps1` is the one command after `az login`, in every install mode ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md#amendments-2026-10-29-phase-28-one-command-one-guided-stop)):

1. **No configuration yet:** it writes one first, as `init.ps1` does ([first run](#first-run-initps1)).
2. **At the start** it prints what to expect for this run, keeps the PC awake ([above](#one-command-deployps1)), writes the live status page and opens it ([below](#the-live-status-page-and-statusps1--watch)), and says when a person is needed. In a session that can take keyboard input, when the Rayfin CLI isn't signed in to the demo's tenant, it also starts the Insights app's browser sign-in, which the run never waits for ([below](#the-insights-app-part-of-every-deployment-2026-11-05)). A session that can't take keyboard input (redirected input, CI, an automation shell, or an assistant) gets a notice before anything is spent: in `PaygWizard` mode, that the guided stop needs a person at a browser for about 10 minutes, with `JumpstartImage` (the default), `-NoWaitForT2`, `ProductKey`, or `Developer` as the alternatives and what each gives; and that the Insights app's sign-in doesn't start there, so `./scripts/configure-fabric-app.ps1 -SignIn`, run yourself in a terminal, adds the app. The run then goes on. In GitHub Codespaces it warns that a codespace stops after 30 minutes without activity by default (terminal output counts as activity, and `deploy.ps1` prints progress at least every 5 minutes), and how to raise that: **Settings** > **Codespaces** > **Default idle timeout**, up to 240 minutes, for codespaces you create afterward, or `gh codespace create --idle-timeout 240m` ([GitHub Docs: idle timeout](https://docs.github.com/codespaces/setting-your-user-preferences/setting-your-timeout-period-for-github-codespaces)). An organization's policy can set a lower maximum.
3. **It waits for T2 without a golden snapshot**, in every install mode, up to `-T2WaitMinutes` (180), printing the host's build phase and the elapsed time every few minutes, with an estimate of when the guided stop comes in `PaygWizard` mode, or Arc onboarding in the other modes. On a time-out it ends **NOT DONE** with the exact command; `./scripts/deploy.ps1` waits again where it stopped. A golden restore doesn't build or stop, so it stays as fast as before.
4. **The guided stop (`PaygWizard`)** prepares everything a person needs, prompts once, and continues by itself afterward ([below](#the-guided-stop-paygwizard)).
5. **Run it again with no parameters**, and it continues an unfinished deployment from the resource group's state tags, as `-Resume` does. The start banner and every **NOT DONE** banner say so: "If this window closes or the PC restarts, run ./scripts/deploy.ps1 again; it continues where it stopped." It starts VMs that were stopped, for example by the nightly auto-shutdown or `./scripts/stop-demo.ps1` (Phase 28 live finding: a rerun after the auto-shutdown found the VMs deallocated, and its first Run Command failed). On an existing environment, `deploy.ps1` reads each VM's power state; a deallocated or stopped `sqlvm01` or `archost01` gets `az vm start --no-wait` ([az vm start](https://learn.microsoft.com/cli/azure/vm#az-vm-start)) before preflight, so it boots while preflight runs, and runs before the template or any track needs it (`DEPLOY.VMSTART`; one that doesn't start ends **NOT DONE** with the next action). A deployed T4 that's stopped starts too ([Servers - Start](https://learn.microsoft.com/rest/api/postgresql/flexibleserver/servers/start)); T3 resumes on its own at its first connection. The T2 guest starts with its host, and a golden snapshot's source host gets its guest back, as `start-demo.ps1` does. Running VMs are only read. A VM it starts gets the interim `baseline` as soon as it runs when the profile has incidents, and the run's first Run Command there waits for it (`DEPLOY.INTERIM_*`, see [activity profiles](#activity-profiles-and-boot-behavior)); otherwise activity profiles stay as the run's own steps set them. The status page shows it as **Start the VMs that were stopped**: "Starting sqlvm01 and archost01, which were stopped (deallocated); no action needed from you."
   - **T1's monitoring plugin on every run** (Phase 28 live finding, 2026-10-30: `start-demo.ps1` found `DatabaseMonitorArcPlugin` running at 07:47, and by 09:12 it was `{"State":"NotRunning"}`; the resumed run, whose T1 track had finished earlier, ended **NOT DONE** on `TELEMETRY.T1`). Once the VMs run, a run that ends with the validation and has no T1 Monitoring step of its own checks the plugin, whether or not it started `sqlvm01`, and restarts the SQL IaaS Agent service when the plugin isn't running (`DEPLOY.T1.MONITORING`; live, the restart brought it back in 161 seconds). It restarts it at once, as `start-demo.ps1` does; only the T1 Monitoring step gives a `NotRunning` plugin a grace first. It runs in its own process beside the tracks, so the guided stop's prompt never waits for it; `-Sequential` checks it before its first stage that needs the VMs. T2 has no such check: its monitoring is a setting of the Arc SQL Server instance, which a restart doesn't turn off, and DONE's `T2.ARC.MONITORING` reads it.
   - **Telemetry gets a second look before NOT DONE:** when `TELEMETRY.T1`, `T2`, or `T3` finds no rows, or only old ones, the check looks at that target's monitoring once (T1's plugin, restarted if it stopped; T2's Arc connection and monitoring, read-only; T3 woken by the warm-up, with its extended property), then, when it's on, waits up to `-TelemetryWaitMinutes` and checks again; the new result replaces the first. An access error, an unknown resource ID, or telemetry under another resource ID isn't retried. The status page says "Restarting T1's monitoring plugin, which stopped after a restart; no action needed." In DONE's checks it comes last, and only when everything else DONE needs passed. `validate.ps1` only reports `TELEMETRY.*`; `./scripts/start-demo.ps1` checks T1's plugin too, even when the VMs already run.
   - **A resume trusts only this deployment's records** (Phase 28 live finding, 2026-10-30: a fresh run's Fabric step failed while `DbHubTrackFabric` still held the finished step of the **DONE** run before it, and the next plain `deploy.ps1` resumed past the step and ended **DONE** without running it). Each track records its last finished step (`DbHubTrackT1`, `DbHubTrackT2`, `DbHubTrackT4`, `DbHubTrackFabric`) only when a step succeeds. So once preflight passes, and before any track or the template starts, a run that starts over (the last deployment ended **DONE**, or `-FromStage Preflight`) clears every track's record; a run over a range (`-FromStage`) lowers the records of the tracks it runs again; `-Sequential` does the same; a resume keeps them. The status page shows the step each resumed track picks up at as "Didn't finish in the previous run; running it again."
   - **A fix you pulled reaches the VMs** (live finding, 2026-11-06: a fix to the T2 host's bootstrap was pulled while `archost01` built its guest, and the plain `./scripts/deploy.ps1` that **NOT DONE** named resumed T2 after its Bootstraps step, so the host kept running the old bundle). Before the tracks start, a resumed run (a plain run after a deployment that didn't finish, or `-Resume`) builds the bootstrap bundle as the Artifacts step does, which gives the same SHA-256 for the same content, and the workload runner too, unless `-SkipRunner` or the deployment records none (a zip built from the same inputs is reused). It compares them with the state tags: a VM has one only when its hash tag (`DbHubBundleSha256`, `DbHubRunnerSha256`) is that SHA-256 and its sent-to tag lists the VM. A VM track that the resume would continue past its Artifacts step, and whose VM lacks either, goes back to that step and runs Bootstraps and the steps after them again; T2's Restore and T1's T3Setup don't run again. The console says why ("T2: the bootstrap bundle changed since the last run (archost01 has ...; this checkout builds ...), so this run sends it to archost01 again and runs T2's Artifacts and Bootstraps steps again, with the steps after them."), `DEPLOY.ARTIFACTS.CHANGED_<VM>` records it, and the status page's Artifacts row says "The bootstrap bundle changed since the last run (...), so it's sent again, and the loader runs again." The VM's loader then stops the old bundle's bootstrap run if it's still going, with what it started, and starts the new one ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md#amendment-a-changed-bundle-takes-over-from-a-run-thats-still-going-2026-11-06)). With nothing changed, the resume is exactly as before, and the console says so; a build that fails is a **Warning**, `DEPLOY.ARTIFACTS.CHANGED`, and the resume goes on as recorded. `-FromStage` doesn't check, because its Artifacts step sends what a VM lacks anyway; `-Sequential -Resume` doesn't either: run `-Sequential -FromStage Artifacts` there.
   - **A network error is retried, and a failure says so at once** (Phase 28 live finding, 2026-10-30: a TLS handshake that failed once, "The SSL connection could not be established", stopped the history report step, and the run ended **NOT DONE**). The calls to Fabric, Power BI, Azure Resource Manager, and Microsoft Graph get up to 4 attempts after a network error (a failed TLS handshake, a reset connection, a DNS failure, a timeout) or HTTP 408, 429, 502, 503, or 504, 5, 15, and 30 seconds apart, or after what Retry-After says, with one line each: "A network error reached api.powerbi.com; retrying in 5 s (attempt 2 of 4); no action needed." ([transient fault handling](https://learn.microsoft.com/azure/architecture/best-practices/transient-faults), [Fabric throttling](https://learn.microsoft.com/rest/api/fabric/articles/throttling)). A request that starts or adds something (a notebook run, a refresh, a Microsoft Graph group change) goes again only when it never reached the service, or on HTTP 429, and a create sent again that finds its name taken uses the item, lakehouse, or workspace of that name. When a track's step fails anyway, the console says so at once: `The history report step failed: <why, with the innermost cause>. The other tracks continue; the run ends NOT DONE, and ./scripts/deploy.ps1 resumes it.` When the cause was a network error, **NOT DONE**'s next step is to run `./scripts/deploy.ps1` again: "A network error stopped it (requests that are safe to repeat were retried)." The policy inventory stops reading definitions at the first one a network error stopped, instead of paying the retries again for each, and a wait counts its reads' time: the wait for a new workspace's capacity reads on through a short outage, and gives up after its 5 minutes and one read's attempts.
6. **Ctrl+C stops it within seconds**, at any point, with its track processes (Phase 28 live finding: a Ctrl+C at the guided stop had seemed to do nothing, because the stop waited for the T2 track's own cleanup, minutes of Azure calls). The run notes the Ctrl+C ([Console.CancelKeyPress](https://learn.microsoft.com/dotnet/api/system.console.cancelkeypress)) and leaves a cancel marker for the track processes, so their slow Azure cleanups (a Run Command's delete, the chunks' cleanup, the guided stop's Bastion removal and password rotation) are left to the next run or `./scripts/stop-demo.ps1`; a track that doesn't end within about 3 seconds has its process ended, with everything it started ([Process.Kill](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.kill)), and only the process with the start time the track reported ([Process.StartTime](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.starttime)), so a reused process ID ends nothing else. Their private files go with the run's handoff directory. Then the PC may sleep again, and the console and the status page end at **NOT DONE**, **Stopped, not done**, with the command that continues; the steps that were running go back to **Pending**. PowerShell usually ends the script itself after Ctrl+C, so the exit code is PowerShell's own. Stopped at the guided stop, Bastion stays up and `archost01`'s password from the guided stop stays valid until the next run cleans them up when it gets to T2, whether or not setup finished meanwhile (Phase 28 review: before, a guided stop that setup had finished in the meantime wasn't needed, so nothing removed them, and the run ended **DONE**), or until `./scripts/stop-demo.ps1` does; the host's request expires on its own, which turns the guest's one-time sign-in off. If you're stopping for the day, run `./scripts/stop-demo.ps1`, which removes Bastion and rotates the password.
7. **It ends with one banner:** **DONE**, with what Database Hub shows and where to look, and, under **Please confirm**, each thing that only a person can confirm, once; or **NOT DONE**, with why (only what keeps the run from DONE), the single next action, and the exact command (usually `./scripts/deploy.ps1` again, after the fix it names), plus `./scripts/collect-diagnostics.ps1` for a **Deployment problem** issue. The command is the run's own, so it keeps the `-ConfigPath` you ran with, and when the next action needs other parameters, such as `-FromStage Artifacts`, the action and the command name the same one: `./scripts/deploy.ps1 -ConfigPath "./config/livetest.local.json" -FromStage Artifacts`, for example. Every other `./scripts/` command it names gets the same `-ConfigPath`, so a copied command never acts on `config/demo.config.json`'s environment instead (live finding, 2026-11-06: the action said `-FromStage Artifacts` while the command line gave the plain command, and both dropped `-ConfigPath`). A `-Resume` that an older remediation names is left out: the plain command resumes by itself whenever the deployment is unfinished, and after a run whose recorded stage reached the validation (a rerun after **DONE** whose template failed, for example), it starts over, template included, where `-Resume` would run only the validation. The console's **Fail** and **Warning** lines and `DEPLOY.SUMMARY`'s manual steps get the same treatment. A run stopped with Ctrl+C says to run the command again, which continues and first sends what a pulled fix changed. The exit code is nonzero unless it's **DONE**. When this run started VMs that were stopped, or created them, a **NOT DONE** or stopped run adds one line naming what now runs and bills, and how it stops: `./scripts/stop-demo.ps1` now, or the nightly auto-shutdown at its configured time (Phase 28). `DEPLOY.SUMMARY` stays, for the details. **DONE** never comes while the deployment state records a guided stop whose cleanup didn't finish (its Bastion may be up) or a handed-over host password that isn't rotated: the T2 step cleans them up first (`DEPLOY.T2.GUIDEDLEFTOVER`), in the parallel tracks and in `-Sequential`, and what's still open after that is **NOT DONE** with `./scripts/stop-demo.ps1 -RemoveBastionOnly` as the command (Phase 28 review).
8. **At the end** it prints the run's time, and, after a build, "capture a golden snapshot with capture-t2-golden.ps1 to make future redeploys skip the build and the guided stop". In `JumpstartImage` mode a snapshot is only an optional speed-up: it saves the image's download and first boot ([the golden snapshot](#the-t2-golden-snapshot-capture-t2-goldenps1-and-test-t2-goldenps1)).

That's read in the pinned package's code; the reference doesn't document it. Without one, the app isn't created in that run, and the run still ends **DONE**. #### The history report's snapshot at the end (2026-11-06)

The owner, 2026-11-06: "Can we add a step that calls the acitivty notebook one time after deployment so it starts to populate data?" Before, the history report was blank after a deployment: the Fabric track runs `NB_DatabaseHub_LiveActivity` once when it first imports it, to create the lakehouse's history tables, but in parallel with T1 and T2, before any target sends telemetry, so that run saves almost nothing (live, 2026-11-06: `FABRIC.SEMANTICMODEL.MEASURES` "The history report is empty until NB_DatabaseHub_LiveActivity saves its first snapshots", and the report's **Blocking Incidents** blank over the whole history). - **When:** after **DONE**'s checks and the switch to the run's activity profile (`DEPLOY.INCIDENTS_*`). A resumed run that has nothing left to do takes another snapshot: that's harmless, because each run saves its own rows (the notebook replaces a run's rows only when that same run saves again), and it adds what happened since, such as incidents.
- **What runs:** `NB_DatabaseHub_LiveActivity` on demand ([Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job), `Invoke-DemoFabricNotebookRun`), analyze-only: `CONFIRM` false, so its **Run all** sends no 240-minute activity request through GitHub (P9) on top of the one the deployment started; `STOP_ACTIVITY` false; `SAVE_RESULTS` true over the last 1,440 minutes (`WINDOW_MINUTES`); no Key Vault (`KEY_VAULT_URL` empty); and the demo's resource group (`RESOURCE_GROUP`), as `stop-demo.ps1 -SaveHistory` sends it. - **As whom:** whoever ran `deploy.ps1`, with the Azure CLI's Fabric and Power BI tokens after the subscription guard. The workspace, the lakehouse, the notebook, and the model are read by name, read-only; nothing is created.
- **How long:** about 2 to 5 minutes (an estimate: Spark's start and the analysis); it waits at most 10 minutes for the job and 5 for the refresh. A job still running then is a **Warning**: it keeps running in Fabric and saves its snapshots when it finishes, and the report shows them after the model's automatic update or `./scripts/configure-powerbi.ps1`.
- **Never blocking:** `DEPLOY.FABRIC.HISTORY` is **Pass**, a **Warning**, or **Not selected**, never a **Fail** or **Manual action required**, so it never changes **DONE**, `DEPLOY.SUMMARY`'s status, or an exit code. `deploy.ps1` and every track process write one progress model, `out/deploy-progress.json`, at each step's start and end, under a lock, through a temporary file and a rename, so a reader never sees half a file. From it, `deploy.ps1` writes `out/deploy-status.html` at least every 15 seconds while it runs (both Git-ignored):

- **One banner, in exactly one of four states:** **Deploying, no action needed** (you can step away; keep the PC on; with the estimate and what's running), **Waiting for you** (the guided stop: what to do now, the portal link, the steps, and a countdown to its time limit), **Done** (where to look in Database Hub, and what didn't work without blocking DONE, the Insights app or the history report's snapshot), or **Stopped, not done** (why, and the exact command, usually `./scripts/deploy.ps1` again). When `deploy.ps1` stops updating the model for more than 3 minutes (its window closed, or the PC slept or restarted), the page says **Stopped, not done** with when that happened.
- **The steps, per track, in order:** Preflight (with the Insights app's sign-in); Infrastructure; T1 (artifacts, bootstrap, monitoring, telemetry); T3; T4; Fabric; T2 (the host's build phases, which in `JumpstartImage` mode are the image's download and first boot; in `PaygWizard` mode the guided stop and the setup check; then the sign-in cleanup, Arc onboarding, monitoring, and telemetry); Validation, then the history report's snapshot (not with `-SkipFabric`). Each shows **Pending**, **Running**, **Done**, **Action needed**, **Failed**, or **Skipped** (mapped from the [ADR 0012](adr/0012-validation-model.md) statuses underneath), its elapsed time, and a one-line message. A wait that's Azure's, such as an extension that a policy installs, says "Azure-side, no action needed". The steps that never block DONE, the Insights app's and the history report's snapshot, say "(doesn't block DONE)"; when one **Failed**, its line is also in the **Needs attention** box under the banner, and once the run ends, so is a snapshot that needs action, such as a paused capacity ([above](#the-insights-app-part-of-every-deployment-2026-11-05), [the snapshot](#the-history-reports-snapshot-at-the-end-2026-11-06)).
- **Freshness:** the last update's time, and a warning when no step changed for 20 minutes while nobody was asked for anything.
- **Safe by design:** the page refreshes itself with `<meta http-equiv="refresh">` and has no JavaScript and no external resources, so it works offline. Every message is HTML-encoded (`System.Net.WebUtility.HtmlEncode`) and passes through the module's redaction (`Protect-DemoText`) first; the model holds no secret, and portal links are the only links.
- **Opening it:** `deploy.ps1` opens it at the start with `Start-Process` on Windows, `open` on macOS, and `xdg-open` where it exists. In GitHub Codespaces it prints the path and how to preview it: `python3 -m http.server 8000 --directory out` in a second terminal, then the forwarded port 8000 in the **Ports** tab and `deploy-status.html`; a forwarded port is private to you unless you change its visibility ([GitHub Docs: forwarding ports](https://docs.github.com/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace)). Or use `./scripts/status.ps1 -Watch`.
- **In a second terminal, anywhere:** `./scripts/status.ps1 -Watch` shows the same banner and steps in the console every few seconds (`-IntervalSeconds`), until the run ends. Without a local model (another machine, or after a restart without a rerun), it shows what `status.ps1` reads from Azure.

#### T2 from Arc Jumpstart's image (`JumpstartImage`)

Since 2026-11-05, `t2SqlInstallMode` is `JumpstartImage` by default: in your own subscription, T2 needs nobody, with no setup wizard, no product key, no Bastion, and no sign-in beyond your own `az login`. There's no guided stop and no `DEPLOY.T2.GUIDEDSTOP` ([ADR 0006](adr/0006-sql-editions-and-licensing.md)). T2's guest is [Arc Jumpstart](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/azure_jumpstart_arcbox/ITPro/_index.md)'s work: ArcBox's prebuilt SQL Server 2022 Standard guest disk, which ArcBox's own [logon script](https://github.com/microsoft/azure_arc/blob/e2c114eed98d18105dcf3a718bef965d5112781b/azure_jumpstart_arcbox/artifacts/ArcServersLogonScript.ps1) runs as a Generation 2 Hyper-V guest and reaches over PowerShell Direct with its published default credential. The demo reuses that process (both links are at pinned commits, checked on 2026-11-05). `PaygWizard`, `ProductKey`, and `Developer` stay available as opt-in modes. Measured live on 2026-11-06 (West US 3, `lowest-cost`): a clean first deployment ended **DONE** in 91 minutes; T2's host build, its steps through `JumpstartImageCheck` below, took about 27 minutes, and its Arc onboarding with the SQL Server extension, PAYG, and monitoring about 33 more. In an earlier run, the image's download and verification took about 11 minutes, about 51 MiB/s, bound by the host's disk (`Standard_E2s_v5` with an E10 Standard SSD).

The T2 host's steps, as `health.json`'s `currentStep` and the status page name them, after `NestedVirtualization`, `HyperVRole`, `DnsServerRole`, `NatNetwork`, and `DnsForwarder`:

1. **`GuestSource`** records where the guest came from in `guest-source.json`: the Jumpstart image, or the build. An existing guest never changes its source, so a mode that needs the other source fails here: "The guest arcsql01 was ..., but t2SqlInstallMode is now ..., and an existing guest never changes its source. Set t2SqlInstallMode back in config/demo.config.json, then run ./scripts/deploy.ps1 -FromStage Infrastructure, which brings the setting to the host; or rebuild T2 for the new mode: ./scripts/destroy.ps1, then ./scripts/deploy.ps1 (ADR 0006)." Preflight doesn't check this; the host does. Two exceptions in this mode since 2026-11-09: a guest built in `PaygWizard` mode whose SQL Server setup was never finished is deleted and made again from the image, and one with SQL Server set up is kept as it is, in `PaygWizard` mode ([an older demo](#an-older-demo-a-plain-deployps1-upgrades-it-2026-11-09)).
2. **`DataDisk`**: in `lowest-cost`, which has no data disk, the guest's disk goes on the host's 128 GiB OS disk, which needs about 64 GiB free in this mode: the image's 34.13 GiB download, 20 GiB for it to grow, and the usual 10 GiB margin, not the disk's 100 GiB maximum. A new host has that; rather than reserve the maximum, `status.ps1` warns early (`STATUS.T2.DISKSPACE`, a **Warning** below 20 GiB free). `demo-day` and `enhanced-performance` have a data disk.
3. **`GuestImage`** downloads `https://jumpstartprodsg.blob.core.windows.net/arcbox/prod/ArcBox-SQL-STD.vhdx`, public for anonymous reads: 36,645,634,048 bytes, a dynamic VHDX with a 100 GiB maximum, pinned in `config/versions.json` as `media.jumpstartArcBoxSqlStd` (its ETag, Content-MD5, size, and Last-Modified, 2025-08-02). It hashes the file as it streams and checks it against the blob's own Content-MD5 and length, failing closed: a mismatch deletes the download, and the next pass downloads it again. A download that stops resumes at the next pass while the ETag is the same. The pinned ETag is the tested image; a newer image at the same URL (another ETag) is used only once the guest passes the image checks (step 7), with a **Warning** that names its ETag and date, which `status.ps1` repeats (`STATUS.T2.IMAGE`). The host records the download in `jumpstart-image.json`.
4. **`GuestVm`** creates a Generation 2 VM with the profile's vCPUs and memory (`lowest-cost`: 2 vCPUs and 8 GiB, at or above ArcBox's 2 vCPUs and 6 GB) and its network adapter **not connected**.
5. **`GuestFirstBoot`** works over [PowerShell Direct](https://learn.microsoft.com/virtualization/hyper-v-on-windows/user-guide/powershell-direct) while the guest has no network:
   - **The published default credential** is read at run time from Jumpstart's logon script at the pinned commit, on `raw.githubusercontent.com`, once the file's SHA-256 matches `media.jumpstartArcBoxSqlStd.credentialSource` (fail closed). No password is stored in this repository: the value stays in memory, is never logged, and is used once, to replace the guest Administrator's password with a random one, which the host stores with DPAPI, as it stores the guest's password in every mode ([ADR 0009](adr/0009-secrets-handling.md)), and proves before it keeps it. A guest that doesn't accept the published credential within 15 minutes fails the step ([troubleshooting](troubleshooting.md#t2-arc-jumpstarts-image-jumpstartimage)).
   - **The guest becomes `arcsql01`:** the computer is renamed, set to UTC, and restarted; SQL Server is renamed with the documented procedure (`sp_dropserver`, `sp_addserver ... 'local'`, then a service restart: [rename a computer that hosts SQL Server](https://learn.microsoft.com/sql/database-engine/install-windows/rename-a-computer-that-hosts-a-stand-alone-instance-of-sql-server)); `BUILTIN\Administrators` becomes a sysadmin, as in the build; every enabled SQL login is disabled, `sa` with a random password nobody keeps; and the sample database `AdventureWorksLT2022` is dropped.
   - **Only the engine stays:** Integration Services and the Launchpad service are stopped and disabled, and Integration Services is uninstalled with SQL Server setup, as on T1, so Arc's inventory lists only the engine ([uninstall](https://learn.microsoft.com/sql/sql-server/install/uninstall-an-existing-instance-of-sql-server-setup); a failed uninstall is only a **Warning**). `C:\Jumpstart`, with its SQL Server media and sample files, is deleted, and an Arc agent identity left in the image is reset locally.
   - **Then the network adapter is connected.** The host records the first boot in `jumpstart-firstboot.json`.
6. **`GuestOnline`** and **`GuestHardening`**, as in every mode: a static address, IMDS and the WireServer blocked, and the host's port rules ([ADR 0004](adr/0004-guest-imds-isolation.md)).
7. **`JumpstartImageCheck`** stops T2 unless the guest has a default instance of SQL Server Standard, version 16.x (SQL Server 2022), and its Administrator is a sysadmin: "T2 can't use this Jumpstart image: ...", and the run ends **NOT DONE**. First-boot work that didn't finish (the computer or server name, an enabled SQL login, the sample database, `C:\Jumpstart`) runs again instead, and a SQL Server that isn't running is started.
8. **`ArcOnboarding`** and the rest, as in the other unattended modes: onboarding ([ADR 0005](adr/0005-arc-onboarding-authentication.md)), `GuestSignInCleanup`, `configure-arc.ps1`'s PAYG and monitoring, then `ConfigureSql`, `SeedDatabase`, and `WorkloadRunner`.

- **What Database Hub gets:** SQL Server 2022 Standard with license type PAYG (pay-as-you-go through Azure Arc) and monitoring on, as in `PaygWizard` mode, so T2 shows in Estate and Performance and feeds the Database Agent; it meets Database Hub's [prerequisites for SQL Server enabled by Azure Arc](https://learn.microsoft.com/fabric/database/hub/add-sql#prerequisites-for-sql-server-enabled-by-azure-arc). ArcBox itself sets license type Paid; the demo sets PAYG, with its resource-group tag `ArcSQLServerExtensionDeployment=PAYG` and `configure-arc.ps1`, which needs no Software Assurance ([license types](https://learn.microsoft.com/sql/sql-server/azure-arc/manage-license-billing)). The image's Windows Server 2022 Standard isn't an evaluation, so it has no 180-day expiry ([licensing](limitations.md#targets-and-licensing)).
- **Outbound HTTPS:** besides its other downloads, the host reaches `jumpstartprodsg.blob.core.windows.net` (the image) and `raw.githubusercontent.com` (Jumpstart's pinned script). Its network security group already allows outbound 443; a tenant firewall or proxy that restricts egress must allow both ([ADR 0017](adr/0017-outbound-access.md)).
- **No automatic fallback:** when the image can't be downloaded, prepared, or checked, the run ends **NOT DONE** with the cause, and nothing switches to another mode by itself (the user's decision of 2026-11-05). Each case's fix is in [troubleshooting](troubleshooting.md#t2-arc-jumpstarts-image-jumpstartimage): first run `./scripts/deploy.ps1` again; then, only if the image stays unusable, an unattended mode, `ProductKey` (your own SQL Server Standard or Enterprise license) or `Developer` (T2 in Hub's Estate only), set in `t2SqlInstallMode`, then `./scripts/destroy.ps1` and `./scripts/deploy.ps1`. `PaygWizard` isn't an option any more: it's retired from the one-click deployment.
- **Nested only:** `t2Mode` `EvaluationOnlyAzureVm` can't use the image, which is a Hyper-V guest disk: `PREFLIGHT.T2.MODE` is a **Fail** with the fix, `t2Mode` `Nested` with a nested-virtualization size, or another install mode.
- **The golden snapshot is optional here:** a redeploy from one skips T2's host build, which took about 27 minutes on 2026-11-06, and nothing is lost without one ([the golden snapshot](#the-t2-golden-snapshot-capture-t2-goldenps1-and-test-t2-goldenps1)).
- **Jumpstart's terms:** "Jumpstart Scenarios, ArcBox, LocalBox, and Agora are all intended for evaluation, training, and demo purposes only and are not supported for production use cases" ([Jumpstart FAQ](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/FAQ/_index.md)). This repository is a demo.
- **The build modes' evaluation guard:** `PaygWizard`, `ProductKey`, and `Developer` build the guest from the Windows Server evaluation ISO. After a pass that finds the host Ready, at most every 24 hours, the host reads the guest's Windows license; for an evaluation with 30 or fewer days left, a rearm left, and no activity profile running, it runs `slmgr.vbs /rearm`, restarts the guest, then runs `slmgr.vbs /ato` ([Slmgr.vbs options](https://learn.microsoft.com/windows-server/get-started/activation-slmgr-vbs-options)), and records it in `guest-evaluation.json`. With no rearm left, it logs a warning to rebuild T2, which `health.json` repeats. It runs only while the host runs and never during a golden capture; the Jumpstart guest isn't an evaluation, so there it only records the license.

#### The guided stop (`PaygWizard`)

Since 2026-11-09 no deployment reaches it: `PaygWizard` is retired from the one-click deployment, and a configuration's `PaygWizard`, the default before 2026-11-05, runs as `JumpstartImage` ([an older demo](#an-older-demo-a-plain-deployps1-upgrades-it-2026-11-09)). What follows describes the mode as it was, for an environment that an earlier guided stop left open; the default `JumpstartImage` mode needs nobody ([above](#t2-from-arc-jumpstarts-image-jumpstartimage)). Installing pay-as-you-go SQL Server without a product key is documented only in SQL Server setup's wizard ([install from the command prompt](https://learn.microsoft.com/sql/database-engine/install-windows/install-sql-server-from-the-command-prompt): `/PID` is optional and installs Evaluation without it, and no parameter selects pay-as-you-go), so a person makes that choice, once per guest build. Everything around it is automated with documented mechanisms ([ADR 0006](adr/0006-sql-editions-and-licensing.md#amendment-one-command-one-guided-stop-phase-28-2026-10-29)):

1. **Before the prompt** (about 10 to 15 minutes, nothing to do yet): when the host reaches the setup step, `deploy.ps1` writes the host's request, with its time limit, creates on-demand Bastion in the background, and onboards Arc when the host waits for it. The host prepares the guest: SQL Server setup pre-filled from a [configuration file](https://learn.microsoft.com/sql/database-engine/install-windows/install-sql-server-using-a-configuration-file) (`/ConfigurationFile`, `UIMODE="Normal"`) with the features, the default instance, the service accounts, the sysadmins, and the Azure extension's subscription, resource group, region, and tenant (the file holds no secret); a logon task in the guest that opens it; a logon task on the host that opens [Virtual Machine Connection](https://learn.microsoft.com/windows-server/virtualization/hyper-v/virtual-machine-connection) to `arcsql01` when you sign in; [setup's Azure sign-in](#setups-azure-sign-in-ie-enhanced-security-configuration) (the WebView2 runtime, IE Enhanced Security Configuration off for administrators, and Microsoft's sign-in sites as Trusted sites); and one automatic sign-in of the guest ([below](#the-guests-one-automatic-sign-in)). Nobody is asked before the host reports the sign-in ready, or, when that preparation doesn't finish within about 15 minutes or 3 passes, before the host gives up waiting for it (`guidedSignIn` **fallback**); until then the status page shows the host's preparation as Azure-side, no action needed.
2. **The prompt:** a large banner, a beep, and on Windows the console window flashes ([FlashWindowEx](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-flashwindowex)). The browser opens `archost01`'s page in the Azure portal, and the link is printed too. The prompt says what to do, about how long it takes, and how long the run waits for it: at least 45 minutes after it asks, until a printed local time. A short reminder repeats every 5 minutes until it's done. The status page's banner turns **Waiting for you**, with the same steps and a countdown, and one plain line is printed for an assistant to relay: `HUMAN ACTION REQUIRED: DEPLOY.T2.GUIDEDSTOP - ...` with the status page's path.
3. **What the person does** (about 10 minutes, then 10 to 15 while setup installs):
   1. In the portal, on `archost01`'s page, select **Connect**, then **Bastion**, and sign in as the VM's administrator ([Bastion RDP](https://learn.microsoft.com/azure/bastion/bastion-connect-vm-rdp-windows)). The password: with a working clipboard, a one-time password is already on it (never shown, logged, or stored); with the [Key Vault opt-in](#opt-in-the-password-in-key-vault-instead-of-the-clipboard), it's in the vault; with neither (GitHub Codespaces, Cloud Shell, or any session without a clipboard), nothing is set or shown, and the prompt gives the portal's own path instead: open `archost01`, then **Help**, then **Reset password**, keep the user name, and type a password of your own choosing ([reset a password in the portal](https://learn.microsoft.com/troubleshoot/azure/virtual-machines/windows/reset-rdp)). The demo never sees it, and it's rotated afterward.
   2. Virtual Machine Connection to `arcsql01` opens by itself. The guest is already signed in, and SQL Server setup is open and pre-filled.
   3. On the **Edition** page, select **Use pay-as-you-go billing through Microsoft Azure**, then **Standard**, and **Next**; accept the license terms.
   4. On the **Azure Extension for SQL Server** page, select **Use Azure Login** and sign in with your own Azure account. Never enter a service principal secret. If the **Use Azure Login** window stays blank, or Internet Explorer says content from `https://login.microsoftonline.com` is blocked, follow the dialog's directions: select **Add...**, then **Add**, to put the Microsoft sign-in page in Trusted sites, and **Close**. Then select **Use Azure Login** again. Repeat for any other sign-in site it names. Confirmed live on 2026-10-30; turning the setting off while setup is open doesn't help ([troubleshooting](troubleshooting.md#t2-the-setup-wizard-step)).
   5. Select **Next** on the pre-filled pages, then **Install**. When setup says it's complete, select **Close**, and close the Bastion tab.
4. **The check, and recovery:** the host checks what was installed: SQL Server Standard, the default instance `MSSQLSERVER`, and the Azure extension that setup installed, before anything is onboarded. A wrong install (Evaluation or Developer, a named instance, or no Azure extension) isn't onboarded: the console, the status page, and `health.json` say exactly how to fix it with setup's documented steps ([edition upgrade](https://learn.microsoft.com/sql/database-engine/install-windows/upgrade-downgrade-sql-server-edition-setup) to pay-as-you-go Standard, or [uninstall a named instance](https://learn.microsoft.com/sql/sql-server/install/uninstall-an-existing-instance-of-sql-server-setup) and install again), and the run keeps waiting and checks again.
5. **After it, on its own:** the guest's automatic sign-in is turned off and cleaned up, IE Enhanced Security Configuration goes back on and the Trusted sites entries back to what they were, `GuestSignInCleanup` removes the sign-in data that setup leaves on the VM and verifies that none remains (unchanged), the database is seeded, Arc's license type is set to PAYG and monitoring turned on, and T2's telemetry is awaited. Bastion is removed, and the host password is rotated to a value nobody keeps (a **Warning** when it can't be yet: `stop-demo.ps1` rotates it, and so does the portal's **Reset password** with a random value).
6. **A time-out** ends **NOT DONE** with `./scripts/deploy.ps1`, which waits for the step again; the host's request expires on its own, and the host then cleans up the guest's automatic sign-in and its browser settings.

#### Setup's Azure sign-in: IE Enhanced Security Configuration

Live, on 2026-10-30, **Use Azure Login** opened a white window, then Internet Explorer's dialog: "Content within this application coming from the website listed below is being blocked by Internet Explorer Enhanced Security Configuration", for `https://login.microsoftonline.com`, though the host's `GuestWebView2` step had succeeded. Setup's sign-in is an Internet Explorer-based control: MSAL.NET, a .NET Framework app's sign-in library, documents that it uses its legacy, IE-based web view for Microsoft Entra ID authorities whatever WebView2 runtime is installed ([using WebView2 with MSAL.NET](https://learn.microsoft.com/entra/msal/dotnet/advanced/webview2)). Microsoft doesn't document which library setup uses, so that part is an inference. Turning IE ESC off while setup was open didn't help either: the setting reaches programs that start afterward. Since then, the host prepares it before anyone is asked, before the guest signs itself in, and before setup opens:

- **WebView2:** checked in the guest (`Test-DemoGuestWebView2`), and installed when it's missing (`Install-DemoHostGuestWebView2`, the signed standalone installer), as before.
- **IE Enhanced Security Configuration off for administrators**, with the registry value [Azure File Sync's deployment guide](https://learn.microsoft.com/azure/storage/file-sync/file-sync-deployment-guide#prepare-windows-server-to-use-with-azure-file-sync) documents for an interactive Azure sign-in on Windows Server (`IsInstalled` 0 under the administrators' component), which Server Manager's **Local Server** > **IE Enhanced Security Configuration** sets too.
- **Microsoft's sign-in sites as Trusted sites** for the guest's Administrator, the fallback while IE ESC is on: each of the Azure portal's documented [authentication hosts](https://learn.microsoft.com/azure/azure-portal/azure-portal-safelist-urls#azure-portal-urls-for-proxy-bypass), as an exact host, gets the zone 2 under both `ZoneMap\Domains` and `ZoneMap\EscDomains`, the per-user entries Microsoft documents ([IE security zones registry entries](https://learn.microsoft.com/previous-versions/troubleshoot/browsers/security-privacy/ie-security-zones-registry-entries)). Not the **Site to Zone Assignment List** policy, which would lock the user's own zone settings and so the dialog's **Add...** ([seamless SSO quickstart](https://learn.microsoft.com/entra/identity/hybrid/connect/how-to-connect-sso-quick-start)). The host first saves what was there, names and zones only.
- **Nobody is asked before it's ready, for a bounded time:** the host's health says `guidedSignIn` **ready** only once WebView2 is there and IE ESC is off; until then the setup step is **InProgress**, and the status page shows the host's message, "Preparing setup's Azure sign-in in arcsql01 (Azure-side, no action needed): ...", and tries again about every 5 minutes. It fails open (Phase 28 review): when the preparation isn't ready about 15 minutes, or 3 passes, after it began for this request, the host logs a **Warning**, says `guidedSignIn` **fallback**, and opens setup anyway, so `deploy.ps1` asks for the person; the console, the status page, and the host's own steps lead with the dialog's **Add...**, which worked live, and `DEPLOY.T2.GUIDEDSTOP` says the automatic preparation didn't finish. Its record still drives the cleanup below.
- **Undone in the cleanup,** with the automatic sign-in's, after success, failure, or a time-out, but not between two of its tries: IE ESC goes back on for administrators and users (the Windows Server default), and the Trusted sites entries go back to what was saved, so sites added with **Add...** meanwhile go too. What's saved never includes the sign-in hosts' Trusted sites entries, so the cleanup removes them even when an earlier pass's changes were already there when it saved (Phase 28 review). A restore that can't be checked fails closed: the record stays, the host tries again at its next pass, and the setup step isn't done before; `GuestSignInCleanup` and the golden capture still require IE ESC on.

#### The guest's one automatic sign-in

A colleague's assistant reached the guest's console with nobody there to sign in to Windows, so the run sat waiting. Since Phase 28 (owner-approved, 2026-10-29), the guest signs itself in once, for the setup step only ([ADR 0009](adr/0009-secrets-handling.md#phase-28-amendment-the-guests-one-automatic-sign-in-and-the-portal-password-reset-2026-10-29)):

- **Armed only while the guided stop waits for a person:** the guest's Administrator gets a new random password through the existing rotation; Windows automatic sign-in is turned on with `AutoLogonCount` 1; and the password is kept only as the LSA `DefaultPassword` secret, through the documented `LsaStorePrivateData` API ([protecting the automatic logon password](https://learn.microsoft.com/windows/win32/secauthn/protecting-the-automatic-logon-password), [LsaStorePrivateData](https://learn.microsoft.com/windows/win32/api/ntsecapi/nf-ntsecapi-lsastoreprivatedata)), never as the plaintext Winlogon `DefaultPassword` value ([turn on automatic logon](https://learn.microsoft.com/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon)). Nothing is downloaded. The guest restarts, signs in, and its logon task opens the pre-filled setup.
- **Always cleaned up**, in a `finally` after success, failure, or a time-out, and again by the host's next pass whenever the request has expired or gone: the console session is signed out first (Windows records the last console user at a sign-in), then `AutoAdminLogon` is set to 0, the LSA secret and the Winlogon `DefaultUserName` and `DefaultPassword` values are deleted, the guest password is rotated again, and a final read checks that nothing is left. `GuestSignInCleanup` then runs as before.
- **Fail closed:** the sign-in data scan (`check-sign-in-data.ps1`, the golden capture's gate, and the golden test's sign-in check) fails on automatic sign-in that's on, the LSA secret, or the Winlogon values, so no golden snapshot is captured with any of them; `-Clean` removes them. `status.ps1` reports a leftover as a **Warning** (`STATUS.T2.AUTOSIGNIN`), which the host's next pass removes.

#### Off the critical path: the policy inventory

Preflight's first policy inventory took 7 to 13 minutes, on the critical path. With `networkMode` `private`, it resolves nothing the template needs, so the parallel run's preflight leaves it out (its checks are **Not selected** for the moment) and runs it in a background job beside the template and the tracks. Its results replace the placeholders at the end, and one that hasn't finished after the tracks is a **Warning**. The template's what-if still runs before anything is created, so a policy that denies part of the deployment still stops the run before it starts. With `networkMode` `auto` (the default), nothing changes: the inventory decides whether T3 goes private, so it runs first, and its cache (`-PolicyCacheHours`) keeps later runs fast. With `public` it runs first too: a policy that turns SQL public access off modifies instead of denying, so the what-if doesn't see it, and `PREFLIGHT.POLICY.SQLPUBLIC` must stop the run before T3 is created public and then cut off from T1. `-SkipPolicyInventory` still skips it.

#### T4's size: the 4-vCore default and its fallback (2026-11-04)

T4's default is General Purpose `Standard_D4ds_v5` (4 vCores, 16 GiB) with autonomous tuning (`t4AutonomousTuning`), the owner's decision of 2026-11-04 ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-11-04-user-directed-general-purpose-standard_d4ds_v5-by-default-with-autonomous-tuning)): autonomous tuning runs "on any currently supported compute SKU with at least 4 vCores" ([autonomous tuning](https://learn.microsoft.com/azure/postgresql/monitor/concepts-autonomous-tuning), updated 2026-07-16), on Query Store, which shouldn't run on Burstable ([Query Store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)); both checked 2026-11-04.

- **The tuning parameters:** with tuning on, the template sets `pg_qs.query_capture_mode` `TOP`, `pg_qs.parameters_capture_mode` `capture_first_sample`, then `index_tuning.analysis_interval` 60 before `index_tuning.mode` `REPORT`, as Learn asks. All four are dynamic, so none waits for a restart ([Query Store parameters](https://learn.microsoft.com/azure/postgresql/parameters/parameters-query-store), [autonomous tuning parameters](https://learn.microsoft.com/azure/postgresql/parameters/parameters-autonomous-tuning)). With tuning off, it leaves them alone, except that a Burstable T4 gets Query Store's capture mode `NONE`.
- **The switch:** `t4AutonomousTuning` unset means on where the size allows it. An explicit Burstable size, or fewer than 4 vCores, with the switch unset turns tuning off, with a **Warning** that says why (`PREFLIGHT.T4.TUNING`); the switch set to `true` with such a size is a preflight **Fail** with the exact fix. A `t4SkuName` you set never changes.
- **When Azure refuses it** with `SkuNotAvailable` (only without `t4SkuName`): `deploy.ps1` tries once more in another zone that the region's capability list gives for the size, then `Standard_D4ads_v5` (4 vCores; tuning stays on) in the configured zone, then `Standard_D2ds_v5` with tuning off, after [its cost check](#t4s-general-purpose-fallback-phase-28-follow-up), or finishes without T4. **DONE** names the size that was created and whether tuning is on. The resource group's tag `DbHubT4Size` records a fallback size, so later runs keep it.
- **An existing T4** whose size the configuration doesn't set, and no record keeps, moves to `Standard_D4ds_v5` at the next `deploy.ps1`: preflight says so first (`PREFLIGHT.T4.SIZE`), with the cost check against the ceilings, and the template prices the move again, then scales it (`DEPLOY.T4.SIZE`, a **Warning**, because "When you change the number of vCores or the compute tier, the server restarts", typically in a minute or less: [scaling](https://learn.microsoft.com/azure/postgresql/scale/concepts-scaling-resources)). Over either ceiling, or without a price, it keeps its size, and `DEPLOY.T4.SIZE` names the ceiling to raise. A T4 that isn't Ready keeps its size for that run, and a scale Azure refuses keeps the size and records it. `start-demo.ps1` never scales T4.

#### T4's size: the Burstable fallback (Phase 28)

Before 2026-11-04, when `t4SkuName` wasn't set the default was `Standard_B1ms`, and this fallback applied. When `t4SkuName` isn't set in your configuration and Azure refuses `Standard_B1ms` in the region (`SkuNotAvailable`, seen in West US 3), `deploy.ps1` tries `Standard_B2s`, the same Burstable class, by itself. Preflight already looks for both in the region's capability list ([az postgres flexible-server list-skus](https://learn.microsoft.com/cli/azure/postgres/flexible-server#az-postgres-flexible-server-list-skus)) and starts with B2s when B1ms is missing, and a refusal the list didn't predict is retried at deployment. What was used is recorded in the resource group's tag `DbHubT4Sku`, so later runs reuse it. When both are refused, the run goes on to [the General Purpose fallback](#t4s-general-purpose-fallback-phase-28-follow-up). Only `SkuNotAvailable` moves the fallback on: a quota limit, a policy denial, or a transient error fails the template as before. A `t4SkuName` you set is never changed: a refusal of it is still a **Fail** ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-10-29-the-burstable-fallback-phase-28)).

#### T4's General Purpose fallback (Phase 28 follow-up)

When Azure refuses both Burstable sizes with `SkuNotAvailable`, `deploy.ps1` creates T4 as General Purpose `Standard_D2ds_v5` (2 vCores, 8 GiB) by itself, the owner's decision of 2026-11-02 ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-11-02-the-general-purpose-fallback-phase-28-follow-up)):

- **Priced first:** right before it would create the server, it prices `Standard_D2ds_v5` from the Azure Retail Prices API and checks the worst case, T4 running every hour of the month (a stopped server starts again on its own after seven days) with its storage and the Defender plans a tenant policy enforces, against `monthlyCeilingUsd`, and a session against `sessionCeilingUsd` ([the cost check](cost-management.md#the-general-purpose-fallbacks-cost-check-phase-28-follow-up)). Over either, or without a price, T4 is left out (`DEPLOY.T4.SKU` **Warning**, recorded as `None`), and **DONE** says which ceiling to raise; the next run that deploys the template checks again. After Azure rejects the T3 free offer, the check runs again without the free offer's allowance, unless the rejected attempt has already created the server, which is then kept as it is. `deploy.ps1`'s preflight prices the same step ahead (`PREFLIGHT.T4.FALLBACK`), and starts there when the region lists neither Burstable size or a record says so; a standalone `./scripts/preflight.ps1` doesn't read the record. When the fallback's own estimate can't be read, `PREFLIGHT.T4.FALLBACK` is a **Warning** and preflight's own cost checks stand, a monthly-ceiling **Fail** included.
- **Said loudly:** the console logs `T4 created as General Purpose Standard_D2ds_v5 (2 vCores) because Azure refused the 4-vCore sizes here, so autonomous tuning is off (it needs 4 vCores); about <price> USD an hour while running ...`, with the price the check read; the status page's Infrastructure step and the **DONE** or **NOT DONE** banner say the same, and the banner adds when a stopped T4 starts again. The banner says "created" only with evidence that the server exists; when the fallback chose `Standard_D2ds_v5` and its creation failed for another reason (a quota, a policy denial, a transient error), it says T4 isn't created yet and why, and the next `deploy.ps1` creates it after checking its price again. A template that failed for another resource doesn't count as proof either way, because T4's server depends only on the network: the ending then reads the server.
- **Kept:** `DbHubT4Size` (`DbHubT4Sku` before 2026-11-04) records `Standard_D2ds_v5` (or `Refused` when Azure refuses it too, and then nothing is tried again on its own), so a redeploy keeps the size and never tries the larger sizes again. An existing server always keeps its own size, whatever the record says, unless you set `t4SkuName`; a record that doesn't match it is cleared, so a `Standard_D2ds_v5` server you created with `t4SkuName` isn't said to come from a refusal once you remove the setting. A server that a failed attempt created counts as existing too: it keeps its size and record, and is never recorded `None` or `Refused`. `status.ps1` and `validate.ps1` report a server that exists although the record says T4 is off as a **Warning**. The template is the same on both tiers: the tier follows the size, and storage, backups, and high availability (off) are valid on both.
- **Never off (2026-11-09):** T4 is part of every deployment, so `t4Enabled: false` is ignored, with a note, and no cost check, autonomous tuning, or record leaves it out ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-11-09-user-directed-t4-is-part-of-every-deployment)).

#### Run Commands that don't stall a run (Phase 28)

A colleague's run waited on seven chunk Run Commands stuck in `Deleting` on `sqlvm01`, and its bootstrap never started. Policy-installed extensions (`MDE.Windows`, Guest Configuration, Defender for SQL, the Azure Monitor agent) can keep a new VM's agent from processing Run Command changes for a while (R49, R336). Now ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md#phase-28-amendment-chunk-hygiene-that-doesnt-stall-2026-10-29)):

- **Chunk deletes aren't waited for:** each chunk's delete is sent and the next chunk goes; one bounded cleanup at the end, and another at the next run, reports what Azure is still deleting as a **Warning** (`DEPLOY.ARTIFACTS.CLEANUP_<VM>`). Leftovers don't block the loader: a VM allows 25 managed Run Commands ([managed Run Command](https://learn.microsoft.com/azure/virtual-machines/windows/run-command-managed)).
- **Extensions settle first:** before a VM's artifacts and before its loader, the track waits up to 20 minutes until the VM's instance view ([az vm get-instance-view](https://learn.microsoft.com/cli/azure/vm#az-vm-get-instance-view)) shows no extension creating, updating, or deleting, and names each one in the log and on the status page: "Azure is finishing `<extension>` on `<VM>` (installed by a policy in your tenant); no action needed".
- **A watchdog:** when that wait, the chunks, or the loader stay stuck for about 15 to 20 minutes, it saves the VM's instance view (agent and extension statuses, redacted) to `out/diagnostics` for the diagnostics bundle, restarts that VM once ([az vm restart](https://learn.microsoft.com/cli/azure/vm#az-vm-restart), which Contributor may do; T1 before its bootstrap; the T2 host never during the guided stop, the golden Release, or its guest build, which the deployment state shows without asking the host's agent (`DbHubT2BuildUtc`), and while the Release runs, `archost01`'s artifacts go without the wait or the watchdog), says so on the status page with the cause and the restart's time (`DEPLOY.WATCHDOG_<VM>` **Warning**), and goes on. Still stuck: the run ends **NOT DONE** with `DEPLOY.EXTENSIONS_<VM>` **Fail**, naming the extension and the next step.
- **Sequential after a stall:** when no chunk finishes for 5 minutes while several run, the rest go one at a time (`DEPLOY.ARTIFACTS.STALL_<VM>` **Warning**), and a retry after the watchdog sends them one at a time too.

#### Diagnostics: `collect-diagnostics.ps1`

When a run ends **NOT DONE** and the next step doesn't help, `./scripts/collect-diagnostics.ps1` zips what a **Deployment problem** issue needs into `out/diagnostics-<time>.zip`: the results (`out/*.jsonl`), the progress model, the console transcripts (`out/logs`), and the saved instance views (`out/diagnostics`). It redacts every line again (`Protect-DemoText`), replaces GUIDs, e-mail addresses, the servers' random suffix, your home folder, and your configuration's owner and account with placeholders, scans the result with the module's secret scanner, and writes nothing when the scan finds anything (`DIAG.BUNDLE` **Fail**). Read the zip before you attach it: the repository is public.

### T4 in the deployment (Phase 24)

T4, the PostgreSQL flexible server `pgflex01-<deploymentId>` ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md)), comes with the template, in every deployment (since 2026-11-09, `t4Enabled: false` is ignored, with a note):

- **Its size and zone:** `t4SkuName` is `Standard_D4ds_v5` (General Purpose, 4 vCores, with autonomous tuning) by default since 2026-11-04, with `Standard_D4ads_v5` and then `Standard_D2ds_v5` (tuning off) as the fallbacks when Azure refuses it ([the 4-vCore default](#t4s-size-the-4-vcore-default-and-its-fallback-2026-11-04)); `Standard_B1ms` and `Standard_B2s` (Burstable, tuning off) are the cheaper sizes you can set. The tier follows the size. `t4AvailabilityZone` (empty, `1`, `2`, or `3`) applies only when T4 is created, because a server keeps its zone. When `t4SkuName` isn't set, `deploy.ps1` moves from B1ms to B2s by itself (Phase 28), then to `Standard_D2ds_v5` once its cost check passes, or finishes without T4 (Phase 28 follow-up; [the Burstable fallback](#t4s-size-the-burstable-fallback-phase-28), [the General Purpose fallback](#t4s-general-purpose-fallback-phase-28-follow-up)). A size you set is never changed: when Azure refuses it with `SkuNotAvailable`, the template fails and `DEPLOY.T4.SKU` is a **Fail** that names the next option, and the next preflight reports it again (`PREFLIGHT.T4.SKU`, a **Warning** instead for one more try in another zone) ([capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors)).
- **Before the template:** a stopped T4 is started first (`DEPLOY.T4.START`), because a stopped flexible server rejects every other management operation, the template's update included.
- **The T4 track** (its own process, like T1, T2, and Fabric): `Server` runs `Test-DemoT4` (`T4.SERVER`, `T4.CONFIG`, `T4.ENTRAONLY`, `T4.NETWORK`, `T4.ADMIN`, `T4.DATABASE`, `T4.ENHANCEDMETRICS`); `Telemetry` waits for its Azure Monitor metrics (`METRICS.T4`). The validation adds `HUB.ESTATE.T4`.
- **T1's track** gets a `T4` step after `T3`: `Enable-DemoT4Workload` (`WORKLOAD.T4.ENABLE`) has T1's managed identity, a member of the P6 group, sign in as the group's role, create the runner's role, apply and seed the schema, and add T4 to the activity host. A T4 failure is reported (and in `DEPLOY.SUMMARY`) but doesn't stop T1's track; `deploy.ps1 -FromStage T4` runs the T4 work again. The Activity step sets T4's profile with T1's and T3's.
- **The stage** `T4` sits between `T3` and `Activity` for `-FromStage`, `-StopAfter`, and `-Sequential`; `-Resume` continues the T4 track after `DbHubTrackT4`.
- **`max_connections` is 50 on every size** (2026-11-03, [ADR 0019](adr/0019-t4-postgresql-flexible-server.md#2026-11-03-max_connections-at-50-on-every-size-and-connection-surge-past-the-limit-the-showcase)), so `connection-surge` can fill Database Hub's **Failed connections**. It's a static parameter: a template that changes it leaves it waiting for a restart ([server parameters](https://learn.microsoft.com/azure/postgresql/server-parameters/param-connections-authentication-connection-settings)). T1's `T4` step, and the `T4` stage of `-Sequential`, restart T4 when one waits ([Servers - Restart](https://learn.microsoft.com/rest/api/postgresql/servers/restart), which restarts the engine, not the compute), wait up to 10 minutes for it to be Ready, and report `DEPLOY.T4.RESTART`; the restart ends T4's open sessions, and the runner's connections retry. A deployment that changes nothing never restarts T4. The T4 track's `Server` step only reports: `T4.MAXCONNECTIONS` is a **Warning** while the value waits.

### Update an existing environment

A change to the template, the workload runner, or its T-SQL reaches an environment that's already deployed only through a run that deploys them again. `./scripts/deploy.ps1 -Resume` after a run that ended **DONE** continues after the last stage that finished, the validation: it never deploys the template, and it validates again, except that since 2026-11-06 it first sends a changed bootstrap bundle or workload runner to the VMs that lack it and runs their tracks again from the Artifacts step.

| Command | What it applies |
|---|---|
| `./scripts/deploy.ps1 -FromStage Infrastructure` | Everything after preflight, which it skips: **the template**, with T4's `max_connections` (waiting for a restart when it changed), T4's size (an existing server that the configuration doesn't size moves to `Standard_D4ds_v5`, with a restart, since 2026-11-04, once the move's cost check passes) and its autonomous tuning parameters, and the budget at `monthlyCeilingUsd` ($375 by default since 2026-11-04; a configuration that sets it keeps its value); **the artifacts**, a new bootstrap bundle and workload runner when their hashes changed (the runner carries `scenarios/`, with the activity profiles and the scenario catalog, and the T-SQL in `database/common`); **the loaders**, where T1's runner step installs the new runner and runs its `setup` on T1, T3, and T4, and T2's on T2, which applies `110-demo-control.sql` and `120-scenario-procedures.sql`; T1's `T3` step, which sets T3 up again; **T1's `T4` step**, which restarts T4 when `max_connections` waits for it, then sets T4 up again; then the activity profiles, T1's monitoring, T2's Arc configuration, Fabric, and the validation, with `T4.MAXCONNECTIONS` |
| `./scripts/deploy.ps1` after a run that ended **DONE** | The same, after preflight: a run after **DONE** starts over, with preflight's cost checks against both ceilings |
| `./scripts/deploy.ps1 -FromStage Artifacts` | The runner and its T-SQL, without the template: T4's limit and the budget stay as they are |
| `./scripts/deploy.ps1 -Resume` | After **DONE**, the validation only, unless the bootstrap bundle or the workload runner changed since: then the tracks of the VMs that lack them run again from their Artifacts step, without the template. After a run that didn't finish, it continues where that run stopped, with the same check, as a plain `./scripts/deploy.ps1` does (2026-11-06) |

Raising `monthlyCeilingUsd` needs the template too, because the budget's amount comes from it ([cost management](cost-management.md#dated-example-the-4-vcore-t4-default-and-the-375-ceiling-2026-11-04)). So an existing environment gets the $375 default budget at its next `deploy.ps1 -FromStage Infrastructure` (or a plain `deploy.ps1` after a run that ended **DONE**). Either way, a move of T4 to a larger size is priced first: a plain run's preflight prices the new size against both ceilings (`PREFLIGHT.COST.*`) and says the move ahead (`PREFLIGHT.T4.SIZE`), and, because `-FromStage Infrastructure` skips preflight, the template step itself prices a move to the default, or to a larger `t4SkuName` you set, with the same estimate as the 2-vCore fallback, the safety stop's restart rule included. Over either ceiling, or without a price, T4 keeps its size, and `DEPLOY.T4.SIZE` names the ceiling to raise; nothing is recorded, so the next run checks again (the review of PR 20).

**The on-demand activity control** isn't part of `deploy.ps1`: after the deployment, `./scripts/setup-activity-control.ps1 -SkipFabric` publishes the runbooks (`DbHub-Control`, `DbHub-Stop`, `DbHub-Monitor`) with the settings they need, such as the showcase profile and T1's monitoring checks, and `./scripts/setup-activity-control.ps1` without `-SkipFabric` also imports the control notebook again, with its new defaults (Run all runs the showcase on T1 to T4).

#### An older demo: a plain `deploy.ps1` upgrades it (2026-11-09)

User-directed: "a true one click deployment" that works for any user, an older demo included, and (2026-11-09) "They should not need to manually do a wizard. They should sign into Az login and then have everything deployed." In a subscription that already has the demo, run `./scripts/deploy.ps1`, as for a new one; don't start VMs or repair parts of it by hand first ([AGENTS.md](../AGENTS.md) says the same to an AI agent). Besides continuing where an earlier run stopped, sending changed bootstraps, and starting what's stopped, it upgrades what an older demo lacks, and no default, upgrade, redeploy, or failure path leads to the setup wizard:

- **A configuration that says `PaygWizard`** (`init.ps1` wrote it as its default before 2026-11-05, and the configuration file, Git-ignored, survives `git pull`, `destroy.ps1`, and redeploys): the run uses `JumpstartImage` and says so in one line at its start and on the status page. The file isn't changed; to drop the line, set `t2SqlInstallMode` to `JumpstartImage`. No configuration value, and no command line, leads to the setup wizard.
- **A T2 guest whose SQL Server setup wizard was never finished** (built in `PaygWizard` mode): in `JumpstartImage` mode, the T2 host deletes that guest, which has nothing to keep, and makes T2 again from Arc Jumpstart's image, with no step for a person. That takes about 27 minutes, as measured on 2026-11-06, including the 34 GiB download at about 51 MiB/s, then about 33 for Arc onboarding. The run says so on the console and on the status page (`DEPLOY.T2.REBUILD`, a **Warning**), deletes the old guest's Arc machine and its SQL Server instances in Azure, as `destroy.ps1` does, only when the host and Azure both show they're the old guest's (anything unclear deletes nothing), and cleans up what an interrupted guided stop left open (its request on the host, before the loader runs, on-demand Bastion, and a handed-over host password). T1, T3, T4, Fabric, and `archost01` itself are untouched. Only positive evidence counts: the guest was read over PowerShell Direct just then, has no SQL Server instance, runs no setup, never passed the host's setup check, and no guided stop waits for a person; anything unclear keeps the guest ([ADR 0006](adr/0006-sql-editions-and-licensing.md#amendment-older-demos-upgrade-in-one-click-2026-11-09)).
- **A finished T2 guest** (SQL Server set up) is never deleted on its own. One built in `PaygWizard` mode is kept as it is, in that mode, whatever the configuration says (`DEPLOY.T2.MODE`), and later runs and `status.ps1` remember it (the resource group's `DbHubT2InstallMode` tag); a golden snapshot of one still restores, though one of the image is preferred. A finished `ProductKey` or `Developer` guest is kept too, but only its own mode uses it: those were deliberate choices, and their license and checks differ, so when the configuration names another mode the run refuses with the fix (set the mode back, or `./scripts/destroy.ps1`, then `./scripts/deploy.ps1`).
- **No T4** (a demo from before Phase 24, or a deleted server): a plain run after **DONE** deploys the template, which creates T4. A plain run that would resume an unfinished one starts from preflight instead (`DEPLOY.T4.MISSING`), so preflight checks T4's cost, the template creates it, and T1 sets it up.
- **T4 that an earlier fallback left out, or `t4Enabled: false`:** T4 is part of every deployment (2026-11-09), so the configuration's `t4Enabled: false` is ignored, with a note, and a `None` or `Refused` record is tried again from the default size (`DEPLOY.T4.RETRY`); the cost check and autonomous tuning only report. Only when Azure refuses every size does the run end **NOT DONE**, with the fix, and the status page's T4 rows say why.

`-FromStage T2` doesn't send the bootstrap bundle, so a host that still runs an older one does neither of the T2 guest parts above: run `./scripts/deploy.ps1` (it sends a changed bundle) or `./scripts/deploy.ps1 -FromStage Artifacts`.

## Day to day

### Start: `start-demo.ps1`

```powershell
./scripts/start-demo.ps1 -WarmUpMinutes 30
```

1. **Cost guardrail:** the live estimate against `sessionCeilingUsd` and `monthlyCeilingUsd`, and this month's actual cost (Cost Management, which lags by up to a day) plus one session against `monthlyCeilingUsd`. A **Fail** stops the start before anything runs; `-SkipCostCheck` starts anyway. The estimate and the month-to-date figure include the golden snapshots in `rg-<prefix>-golden`.
2. Starts `sqlvm01` and the T2 VM at once (Phase 20). A VM that's still deallocating (for example during the nightly auto-shutdown) is waited for first. A VM that's already running, where an earlier session can have left `business-day`'s incidents running, gets `baseline` on its targets first, in one managed Run Command sent without waiting (2026-11-03), so an incident in progress ends early in this start. A VM this start boots gets the same as soon as it runs, before any of this start's Run Commands there: its profile host resumes the profile stored there about 2 minutes after the boot, and a stored `business-day` lasts 8 hours from its switch, or until 2 minutes before the next auto-shutdown, so it can outlive a stop (review of PR 16, 2026-11-04). There, T3's and T4's profiles, files on T1, are set at once, and T1's or T2's is tried again every 15 seconds while its SQL Server, or T2's guest, starts, for at most 10 minutes; this start's own Run Commands there wait for it, and one not set by then is a **Warning** (`START.INTERIM_*`) with the commands (re-review of PR 16). Each of those requests asks the VM side for no readiness wait of its own (`readySeconds` 0), and T2 isn't tried again once its relay holds the guest for a golden capture (a capture in progress, a capture marker that can't be read, or a restored copy whose Arc identity wasn't reset) or finds it not running: that's **Not selected** with the reason, because nothing runs there to quiet (review of PR 17, 2026-11-04). The switch (step 6) brings the profile back. A golden snapshot's source host gets its air-gapped guest back (`T2.GOLDEN.SOURCE`) as soon as it runs, before its interim `baseline`, so the interim never waits for a guest the capture left off; when the release leaves it off (a capture in progress there, or a release that failed), `START.INTERIM_T2` is **Not selected** and nothing is sent or waited for there. T1's monitoring plugin, which can stay NotRunning after a deallocation, gets the SQL IaaS Agent service restarted (`START.T1.MONITORING`), so T1 keeps sending Hub telemetry. Right after boot the agent reports no plugin status yet, and a restart then can leave the plugin NotRunning (live, 2026-10-26), so the step first waits up to 5 minutes for that status. It restarts the service only when the plugin isn't Running, or still has no status, and then waits up to 5 minutes for Running and uploads OK; a restart that doesn't help is a **Warning**. With the on-demand activity control, a notebook run's pending auto-stop is cancelled first, because this session takes over: a **Warning** (`START.CONTROL.AUTOSTOP`) says the VMs now run until `stop-demo.ps1` or the nightly auto-shutdown at its time. If it can't be cancelled, the start carries on and the Warning gives the pending stop's time and how to cancel it. A run's `DbHub-Stop` job that's already queued or running is waited for, up to 10 minutes, and never stopped (`START.CONTROL.STOPJOB`) ([ADR 0020](adr/0020-on-demand-activity-control.md#stop-layers)).
3. **T3** persists between demos by default and is resumed. After `stop-demo.ps1 -RemoveT3`, it's recreated under the same names from the recorded bundle and runner, configured from T1, and checked by the readiness gate, which reports a **Warning** with the measured lag until Resource Graph, the extended property, and fresh telemetry all agree. T1's monitoring is checked again after that template deployment.
4. **T4** (Phase 24): its start is requested with the VMs and confirmed before its profile is set (`START.T4.START`); `-SkipT4` leaves it stopped.
5. Sets the activity profile (`-ActivityProfile`, or the configured `activityProfile`, `business-day` by default since 2026-11-03) on T1, T3, T4, and T2 until the next auto-shutdown. T2's guest needs a few minutes after the host starts, and T1's SQL Server can still be starting because both VMs boot at once, so both profiles are retried, within one readiness budget of 4 minutes that the VM side waits in. A target that stayed down through the interim's 10-minute wait gets one attempt without another wait, so the waits never add up: when T1 or T2 never answers, a start that booted the VMs waits about 15 minutes in all for it (the interim's 10 minutes and 150 seconds, then one attempt each for the profile and the switch), and one that found them running about 5 minutes per such target, plus the switch's at most 3 (review of PR 17, 2026-11-04). A profile with incidents (`business-day` or `incident:<scenario>`) is set as `baseline` first (`START.PROFILE_*` says so), so no incident slows this start's own Run Commands. Then it deletes the finished `DbHubControl-*` Run Commands that the on-demand activity control left on the VMs that run, without waiting for the deletes (`START.CONTROL.RUNCOMMANDS`, Phase 28 follow-up): the control's stop path never uses Run Command, so a run's own stay until the next run, and a VM allows 25 managed Run Commands ([Run Command overview](https://learn.microsoft.com/azure/virtual-machines/run-command-overview)). Finished means a terminal execution state, or an empty or Unknown one more than an hour after the time in the Run Command's name, so a control run that overlaps the start keeps the one it has just created. A delete that fails, for example on a VM that was deallocated meanwhile, is a **Warning** the next start retries, never a **Fail**.
6. **The switch** (2026-11-03): this start's own Run Commands are done, so the targets on the interim `baseline` get `business-day`, one managed Run Command per VM (`DbHubDemo-Profile`), both VMs within 3 minutes (`START.INCIDENTS_*`: **Pass**, or a **Warning** with the command, never a **Fail**). With `-Interactive -ResetAdminPassword`, `archost01`'s switch comes after the host password. A start that ends before its switch (Ctrl+C, an error) sends it without waiting. The console's `Activity:` line says what runs and how to choose `baseline`, and a configuration without `activityProfile` gets one notice (`START.ACTIVITYPROFILE`), and its cost check (`START.COST.*`, unless `-SkipCostCheck`) includes the incidents ([activity profiles](#activity-profiles-and-boot-behavior)).
7. `-WarmUpMinutes` lets the activity run in the background (`START.WARMUP`), so the script returns once the profiles are set; `-WaitForWarmUp`, which the scheduled start and warm-up workflows pass, waits that long and then checks that telemetry arrives, so Hub charts have history when the presenter joins.
8. **The Fabric capacity, opt-in** (`fabric.manageCapacity`, Phase 26b): by default the capacity isn't called, and `START.FABRIC.CAPACITY` is **Not selected**. With `fabric.manageCapacity` true, for an F capacity that's yours alone, in the configured subscription, and named in `fabric.capacityName`, a **Paused** capacity is resumed ([Fabric Capacities - Resume](https://learn.microsoft.com/rest/api/microsoftfabric/fabric-capacities/resume), before the VMs start) and recorded in the resource group's tag `DbHubFabricCapacityResumed` (`<resource group>/<name>`, with `DbHubFabricCapacityResumedUtc`), so `stop-demo.ps1` pauses only what the demo resumed. An Active capacity is left as it is and not recorded. A Trial capacity or one in another subscription isn't an Azure resource the scripts can reach: **Not supported**. Contributor on the capacity is enough. It bills while it runs, outside the demo's cost ceilings.

### Stop: `stop-demo.ps1`

```powershell
./scripts/stop-demo.ps1               # Bastion, the password, profiles off, the guest, then both VMs
./scripts/stop-demo.ps1 -SaveHistory  # the same, then the session's history saved to the lakehouse (opt-in)
./scripts/stop-demo.ps1 -ParkT2       # only the T2 side; T1 and T3 keep running for agent-focused demos
./scripts/stop-demo.ps1 -RemoveT3     # also delete T3; start-demo.ps1 recreates it under the same names
```

In order, it removes on-demand Bastion and then its public IP, rotates the T2 host's one-time password, sets every activity profile to `off`, shuts the guest down cleanly, and deallocates the VMs. The profiles go off in one managed Run Command per VM, both VMs at once, waited for at most about 3 minutes (2026-11-03): an incident in progress can keep a VM's Run Commands waiting for minutes, so a profile that isn't off in time is a **Warning**, reported after the deallocation, that says the VM was deallocated anyway, which stops the incident with it. The guest's clean shutdown has the same bound; when it runs out (`STOP.GUEST` **Warning**), also when `archost01` answers 409 Conflict until then, the host's deallocation shuts the guest down through its automatic stop action. Once Bastion is gone, it also clears the record of a guided stop whose cleanup didn't finish, as after a Ctrl+C at the guided stop, so `deploy.ps1`'s **DONE** no longer waits for it (Phase 28 review). Before T2's SQL Server setup, the guest has no demo module or workload runner yet, so T2's profile is **Not selected** ("T2 isn't set up yet"), not a **Warning** (Phase 28 live finding; `status.ps1 -Detail` and `start-demo.ps1` say the same). T3 stays: with its profile off it auto-pauses `t3AutoPauseMinutes` after the last session. Turning the T3 profile off doesn't wake T3, because the T3 profile is a file on T1. T4's profile goes off and T4 stops (`STOP.T4.STOP`); Azure starts a stopped flexible server again on its own after seven days ([stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server)), so `STOP.T4.STOP` gives that date and time (the stop plus seven days; an earlier stop from the activity log), what it then bills at T4's own size from the Retail Prices API, and what stops it again: the nightly safety stop at the next auto-shutdown time when it's in place, otherwise the on-demand control's daily safety stop when it's scheduled; without either, nothing does, so it says what's missing and to run `stop-demo.ps1` again once T4 has started (Phase 28 follow-up; [the nightly safety stop](#the-nightly-safety-stop)). `status.ps1` reports the same. A T4 that was never created is left alone (both **Not selected**); one whose state couldn't be read is still stopped. With the on-demand activity control, it also removes a pending auto-stop of a notebook run (`STOP.CONTROL.AUTOSTOP`), so it can't deallocate the VMs of a later session.

Phase 26b adds two opt-in steps at the end, both skipped with `-ParkT2`:

- **The session's history** (`-SaveHistory`, or `fabric.saveHistoryOnStop` true; `STOP.FABRIC.SAVEHISTORY`): `NB_DatabaseHub_LiveActivity` runs on demand ([Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job)) over the last `-SaveHistoryWindowMinutes` (720 by default, in 5-minute bins), at most 15 minutes, with `SAVE_RESULTS` true and `CONFIRM` and `STOP_ACTIVITY` false, so it writes only the lakehouse's history tables. The workspace and lakehouse are found by name, never created here. A capacity that isn't running is **Manual action required**. Overlapping runs are fine: the report keeps the newest capture of each bin.
- **The capacity the demo resumed** (`fabric.manageCapacity` true; `STOP.FABRIC.CAPACITY`): only the capacity that the tag `DbHubFabricCapacityResumed` records is paused ([Fabric Capacities - Suspend](https://learn.microsoft.com/rest/api/microsoftfabric/fabric-capacities/suspend)), after the history run, never while it's still going, and then the record is cleared. A record of a capacity that's already paused is stale and is cleared without a call. A capacity the demo didn't resume stays running. With the default (false), the capacity isn't called, and a record left from earlier is a **Warning**.

### Disks the subscription's automation switched (Phase 24)

On 2026-10-24 an application identity that isn't the demo's switched both VMs' OS disks to Standard HDD while they were deallocated, and the next template deployment failed: Azure doesn't change an OS disk's type through its VM (`OperationNotAllowed`). The demo never changes a disk back ([limitations](limitations.md#deployment-and-operations), R440).

### Destroy: `destroy.ps1`

`./scripts/destroy.ps1` deletes the Arc SQL Server instances first, then the Arc machines, then the resource group with everything in it, and waits until it's gone. ## Activity profiles and boot behavior

- `deploy.ps1` (the Activity stage), `start-demo.ps1`, `demo-control.yml`, and the live-activity notebook set a profile: `off`, `baseline`, `business-day`, or `incident:<scenario>`. Every profile ends two minutes before the next auto-shutdown.
- **`business-day` is the default since 2026-11-03** (the owner's decision, [ADR 0010](adr/0010-workload-generator-technology.md#activity-profiles-business-day-by-default-2026-11-03)): the steady mix plus bounded incidents at fixed minutes past each UTC hour, so Database Hub's Performance page has problems to show within the hour ([the schedule](demo-walkthrough.md#the-hourly-incidents-business-day)). For the quieter demo, set `"activityProfile": "baseline"`, or pass `-ActivityProfile baseline` to `start-demo.ps1`. A configuration without `activityProfile` gets `business-day`, which `deploy.ps1`, `preflight.ps1`, and `start-demo.ps1` say once (`*.ACTIVITYPROFILE`), and their cost checks include it; no script writes the configuration. One that `init.ps1` wrote before this change names `baseline` and keeps it.
- **An incident never slows a run's own Run Commands:** `deploy.ps1` and `start-demo.ps1` set `baseline` first where they set the profile, so T3 stays awake and telemetry flows for their checks, and switch a VM's targets to `business-day` once their own Run Commands on that VM are done: `deploy.ps1` after **DONE**'s checks, whether the run is **DONE** or not (`DEPLOY.INCIDENTS_*`); `start-demo.ps1` at the warm-up's start (`START.INCIDENTS_*`). One managed Run Command per VM (`DbHubDemo-Profile`, which each change replaces and whose script does nothing after its expiry), both VMs within 3 minutes; a switch that doesn't finish in time is a **Warning** with the command, never a **Fail**. A run that's stopped (Ctrl+C) or fails sends the switch without waiting, so no VM stays on `baseline`; a VM is forgotten only once Azure accepts its switch request, so a Ctrl+C in the middle of the switch leaves the VMs it hadn't reached to that send, which says what it sent. A VM that's already running when the run starts gets `baseline` on its targets first, sent without waiting, with a script that does nothing after 10 minutes, so an incident an earlier session left running ends early in the run, and a VM the run starts gets the same as soon as it runs, tried again there every 15 seconds while its SQL Server, or T2's guest, starts, and the run's first Run Command there waits for it, at most about 12.5 minutes (`START.INTERIM_*`, `DEPLOY.INTERIM_*`: a **Warning** with the commands when it isn't set by then); the run's switch covers those VMs too. **DONE**'s requirements are unchanged.
- **The VMs don't set a profile at boot by default** (`activityProfileOnBoot: false`). A VM that starts some other way (a manual start in the portal, a restart) serves only the profile someone set, and `stop-demo.ps1` sets every profile to `off`. Live, the task restarted `baseline` on T1 and T3 at every boot, which kept T3's serverless database awake ([ADR 0016](adr/0016-cost-profiles.md), R183).
- Set `activityProfileOnBoot: true` to have every boot start the configured profile again, for example for an unattended scheduled start without `start-demo.ps1`. A profile with incidents starts as `baseline` at boot, and the next `start-demo.ps1` or `deploy.ps1` switches it.
- After a runner install (a deployment), the VMs apply the configured profile once, whatever this setting, with `baseline` in place of a profile with incidents until the run switches it.
- **Checks while incidents run:** **DONE**'s checks read Database Hub, Azure, and Fabric, never a target through its own load, and a run switches only after them. `validate.ps1` can run at any time. A check that reads a target through its load turns a **Fail** into a **Warning** that names the incident and when to run the area again only when an incident can explain it: the runner's status (`WORKLOAD.<target>.COMMAND`) and `T3.PROPERTY`'s T-SQL from T1 when they fail the way load makes reads fail (a time-out, a 409, a lock, or a resource limit) while one of `business-day`'s incidents is due on that target, from its start minute to 3 minutes after its end (or on T1, for the reads `sqlvm01` makes for T3 and T4); the host lane (`.HOST`) when the target's own status says it runs `business-day` and an incident is due, which the VM reads from the runner's whole status, so a status that lists several runs counts too. A fault no incident causes (settings.json missing, no runner, a refused login, a host whose process ended) stays a **Fail** at any time, and so does a property that's read and wrong; a **Fail** after the incident's time is a fault.
- **The notebooks:** since the same day, `CONFIRM = True` by default, so **Run all** of `NB_DatabaseHub_LiveActivity` sends `business-day` on every target for 240 minutes through `demo-control.yml` (P9), and never stops it ([the notebooks](../fabric/README.md#the-notebooks)).

## Bastion and the one-time host password

Bastion is on demand only, and the default `JumpstartImage` mode doesn't need it to deploy. The opt-in `PaygWizard` mode's setup-wizard step needs the host's desktop: since Phase 28, `deploy.ps1`'s [guided stop](#the-guided-stop-paygwizard) creates Bastion, hands over the password the same way, and removes it afterward. In every mode it stays available for interactive access, for example T2's missing-index fix, where a person runs [`remediation.sql`](../scenarios/missing-index/remediation.sql) in the guest, the SSMS fallbacks (SSMS is installed in the Jumpstart guest), or troubleshooting. By hand:

```powershell
./scripts/start-demo.ps1 -Interactive -ResetAdminPassword
```

- `-Interactive` deploys Azure Bastion Basic and its Standard public IP from `infra/modules/bastion.bicep` into the existing `AzureBastionSubnet` (about 8 minutes live). It's a template deployment, because the Azure CLI's `az network bastion` commands need an extension that prompts to install. It's tagged with an expiry of now plus `bastionMaxHours` (4 by default); a longer request is capped at it.
- `-ResetAdminPassword` sets a one-time password for the host's administrator with a Run Command (`Set-LocalUser`; the password travels only as a protected parameter) and copies it to your clipboard. It's never displayed, logged, or stored. Without a working clipboard (GitHub Codespaces, Cloud Shell, GitHub Actions) and without the Key Vault opt-in, nothing is set or shown: in the Azure portal, open `archost01`, then **Help**, then **Reset password**, keep the user name, and set a password of your own choosing, then sign in through Bastion with it ([reset a password in the portal](https://learn.microsoft.com/troubleshoot/azure/virtual-machines/windows/reset-rdp), which uses the VMAccess extension). The resource group records that a password was handed over (Phase 28), so `stop-demo.ps1` rotates yours afterward too.
- `stop-demo.ps1` deletes the Bastion host, then its public IP, and rotates the password to a value nobody keeps. The hourly `bastion-cleanup.yml` does the same after the expiry, and deletes at once a public IP that an interrupted Bastion delete left behind (a public IP bills by the hour on its own); `status.ps1` reports either as a **Warning** with its current hourly list price.
- A rotation needs the host running. When it's deallocated, the result is **Manual action required** with the steps; the next `start-demo.ps1` rotates a leftover one-time password for you. A rotation that fails on a running host is a **Warning** since Phase 28 (it was a **Fail**): the record stays, so the next stop or start tries again, and the portal's **Reset password** with a random value you don't keep does the same.

### Opt-in: the password in Key Vault instead of the clipboard

With `keyVault.enabled: true` (owner decision, 2026-10-21), the one-time password goes to an Azure Key Vault instead of your clipboard, so `start-demo.ps1 -Interactive -ResetAdminPassword` works from any session, including Cloud Shell. It's off by default: the default path stays Contributor-only, with no vault and no role assignment for it ([ADR 0008](adr/0008-identity-rbac-abac.md), [ADR 0009](adr/0009-secrets-handling.md)).

```json
"assignRoles": true,
"keyVault": { "enabled": true }
```

- **It requires `assignRoles: true`**, and the account that runs `deploy.ps1` needs `Microsoft.Authorization/roleAssignments/write` on the resource group (Owner, User Access Administrator, or Role Based Access Control Administrator). The schema refuses `keyVault.enabled` without `assignRoles`, and no vault is deployed when the permission is missing.
- **The vault:** `deploy.ps1`'s Infrastructure stage deploys `infra/modules/keyvault.bicep` as `kv-<prefix><environment>-<deploymentId>`: RBAC authorization, no access policies, soft delete (`keyVault.softDeleteRetentionDays`, 7 by default; Key Vault fixes it at creation), purge protection only with `keyVault.purgeProtection` (irreversible), and the firewall open to all networks unless `keyVault.allowedIpRanges` lists your public addresses. If a tenant policy requires purge protection or a firewall, set those; a denial names the policy. A vault **Fail** is reported but doesn't stop the deployment, because only `start-demo.ps1 -Interactive` needs it. Sources: [Key Vault RBAC](https://learn.microsoft.com/azure/key-vault/general/rbac-guide), [soft delete](https://learn.microsoft.com/azure/key-vault/general/soft-delete-overview).
- **Access, on the vault only, by role name:** you (the signed-in caller) and `keyVault.operatorObjectIds` get **Key Vault Secrets Officer**, to write and disable the password; `keyVault.readerObjectIds` get **Key Vault Secrets User**, to read it in the portal. Add the GitHub workflow identity to `keyVault.operatorObjectIds` so the scheduled stop can disable the secret. A new role assignment can take several minutes to reach Key Vault; the write retries for up to 10 minutes.
- **Start:** `start-demo.ps1 -Interactive -ResetAdminPassword` makes sure of the vault and your access, stores the password as the secret `<vm>-one-time-password` (content type `password`, the VM and user name as tags, the Bastion expiry as its expiry), and only then sets it on the VM. The value reaches the Azure CLI in a private temporary file, never on a command line, and the CLI returns only the secret's ID. Older versions are disabled. If the VM refuses the password, the new version is disabled at once.
- **Stop:** `stop-demo.ps1` (and the scheduled stop and `bastion-cleanup.yml`) rotates the host password and disables every enabled version of the secret (`STOP.KEYVAULT`), even when the host is deallocated and can't be rotated. Nothing is deleted. `status.ps1` reports a readable password past its expiry as a **Warning** (`STATUS.KEYVAULT`).
- **Destroy:** the vault goes into soft delete with the resource group (`DESTROY.KEYVAULT` says for how long). Its name stays taken until the retention ends, so a `deploy.ps1` within that time recovers it under the same name (`az keyvault recover`).

**Signing in with the stored password.** Bastion's RDP connection form offers **Microsoft Entra ID (Preview)**, **Username and password**, and **Kerberos**; it has no Key Vault option ([Connect to a Windows VM using RDP](https://learn.microsoft.com/azure/bastion/bastion-connect-vm-rdp-windows), checked 2026-10-21). Only Bastion's SSH forms still offer **Password from Azure Key Vault** ([SSH to a Windows VM](https://learn.microsoft.com/azure/bastion/bastion-connect-vm-ssh-windows)), and the setup wizard needs the desktop. So:

1. In the Azure portal, open the key vault named in `START.KEYVAULT`, then **Objects** > **Secrets** > `archost01-one-time-password`, and select the current version.
2. Copy the **Secret value** with the portal's copy button next to the field; you don't need to show it ([Key Vault quickstart, retrieve a secret](https://learn.microsoft.com/azure/key-vault/secrets/quick-create-portal) describes the page).
3. Open `archost01`, select **Connect** > **Bastion**, choose **Username and password**, enter the user name from `START.KEYVAULT`, paste the password, and select **Connect**.

The copy happens inside the portal, so the machine that ran `start-demo.ps1` needs no clipboard. **Future option:** Microsoft Entra ID sign-in through Bastion, which needs no password at all. It's in preview for RDP, works with Bastion Basic in the portal, and needs Windows Server 2022 or later, the `AADLoginForWindows` extension on the host, and the **Virtual Machine Administrator Login** role ([Bastion Microsoft Entra ID authentication](https://learn.microsoft.com/azure/bastion/bastion-entra-id-authentication)). It isn't implemented: it would join the host to Microsoft Entra ID and add a role assignment.

## The nightly safety stop

Every `deploy.ps1` sets it up (since 2026-11-05, [ADR 0024](adr/0024-nightly-safety-stop.md)): in the parallel path right after the tracks get the template's handoff, so no track waits for it, a resumed run included; with `-StopAfter Infrastructure`, before the run ends; and with `-Sequential`, after the Infrastructure stage. Each step is idempotent, and each problem is a **Warning**, never a **Fail**:

| Result | What it does |
|---|---|
| `SAFETYSTOP.RESOURCES` | Deploys `infra/safetystop/safetystop.bicep` to the demo resource group (deployment `dbhub-safetystop`): the identity `id-<prefix>-<environment>-safetystop` and the Automation account `aa-<prefix>-<environment>-safetystop` (Basic, local authentication off), with the demo's tags |
| `SAFETYSTOP.RUNBOOK` | Publishes `DbHub-Stop` (Windows PowerShell 5.1, `automation/runbooks/DbHub-Stop.ps1` with its shared code and its own settings baked in), only when the published content differs |
| `SAFETYSTOP.SCHEDULE` | Two daily schedules in `autoShutdownTimeZone`: `dbhub-safety-stop` at `autoShutdownTime` (Scope `Nightly`) and `dbhub-safety-t3check` 30 minutes later, or T3's auto-pause delay plus 15 minutes when that's longer (Scope `T3Check`, which also stops a running T4 since 2026-11-09). A schedule that's disabled, at another time, or not linked is created again, so a run turns a disabled one on again and follows a changed `autoShutdownTime`; one that's right is kept (each link's scope is read by its ID, since the list of job schedules returns no parameters) |
| `SAFETYSTOP.ROLE` | Creates or updates the custom role "DbHub Demo Safety Stop" and assigns it to the identity at the demo resource group when you may; otherwise a **Warning** with the one command for an Owner, `./scripts/grant-safety-stop.ps1` |

- **DONE with a missing piece:** the run still ends **DONE**, and its banner and the status page add one line: that nothing stops T4 after its 7-day restart until the piece is fixed, that the VMs' nightly auto-shutdown and T3's auto-pause still apply, and the fix.
- **What it does each night** is in the README's [what stops or pauses on its own](../README.md#what-stops-or-pauses-on-its-own). `status.ps1` (`STATUS.SAFETYSTOP`) and `validate.ps1 -Area Cost` (`COST.SAFETYSTOP`) show it, and each job is in the account's job history (Process Automation > Jobs).
- **An Owner's one command,** `./scripts/grant-safety-stop.ps1 [-ConfigPath <path>] [-WhatIf]`, runs the subscription guard and then creates the role and its assignment only, and writes `out/grant-safety-stop.jsonl`. A destroy deletes the assignment with the group, so after a redeploy by someone who can't assign roles it's needed again.

## How the VMs bootstrap

1. `deploy.ps1` builds the bootstrap bundle (`vm/` and `database/`) and sends it to each VM with `Send-DemoBootstrapBundle`: SHA-256-checked chunks of 512 KiB by default, one managed Run Command at a time, each deleted once it succeeds. Nothing secret travels in a chunk, and there's no storage account or SAS.
   - It also builds the workload runner with `Publish-DemoWorkloadRunner` (the .NET SDK pinned in `config/versions.json`), then sends it the same way with `Send-DemoWorkloadRunner`: about 3.2 MB, 7 chunks.
2. `deploy.ps1` deploys the template again with the bundle's SHA-256 and chunk count, and the runner's (`Get-DemoDeploymentParameter -BootstrapBundleSha256 -BootstrapChunkCount -WorkloadRunnerSha256 -WorkloadRunnerChunkCount`). That adds a managed Run Command on each VM that runs the loader. The loader checks every chunk and the whole bundle (a mismatch stops everything), unpacks it to `C:\ProgramData\DbHubDemo`, and registers the SYSTEM task `DbHubDemo-Bootstrap`. `Wait-DemoBootstrapLoader` then reports the loader's exit code.
3. The task runs at startup and every 5 minutes until the VM is ready. It survives reboots and records progress in `state.json` and `health.json` in `C:\ProgramData\DbHubDemo`; logs are in `logs\`.
4. T1 formats its data disk (or, in `lowest-cost`, uses SQL Server's default folders on its OS disk), configures SQL Server, and creates and seeds `ContosoCare`. The T2 host installs Hyper-V, then makes and hardens the guest `arcsql01` (on the OS disk in `lowest-cost`, after a free-space check) according to `t2SqlInstallMode`: in `JumpstartImage` mode, the default, from Arc Jumpstart's prebuilt SQL Server 2022 Standard disk, which it downloads and checks ([above](#t2-from-arc-jumpstarts-image-jumpstartimage)); in the build modes, it downloads the media from Microsoft (with retries that resume), builds the guest, and installs SQL Server. It then waits for Arc onboarding (`configure-arc.ps1`, below) and, in `PaygWizard` mode, for the manual step below.
5. **Workload runner** ([ADR 0010](adr/0010-workload-generator-technology.md#phase-13-delivery-and-hosting-as-built-2026-10-20)). The last step on each VM installs the runner and starts its activity host:
   - **On T1:** it assembles and verifies the runner and downloads the pinned .NET runtime (SHA-512 checked). It applies the demo objects (`110-*.sql`, `120-*.sql`) to `ContosoCare` on T1 and starts the SYSTEM task `DbHubDemo-Workload`.
   - **For T3:** after T1 joins the T3 administrators group, `deploy.ps1` runs `Enable-DemoT3Workload`, which applies the same objects to T3 and adds T3 to the task.
   - **On the T2 host:** the step waits (`WaitingForGuestSql`) until the guest's SQL Server is ready. Then it copies the runner and the runtime into the guest over PowerShell Direct and starts the same task there for T2.
   - **Activity profile:** after the install, the task runs the configured `activityProfile` until two minutes before the next auto-shutdown, with `baseline` in place of a profile with incidents (`business-day`, the default since 2026-11-03), which `deploy.ps1` switches to once its own Run Commands on the VM are done. At later boots it sets a profile only when `activityProfileOnBoot` is true ([Activity profiles and boot behavior](#activity-profiles-and-boot-behavior)). While a T3 profile runs, T3's serverless database stays awake, which bills compute ([ADR 0016](adr/0016-cost-profiles.md#phase-13-note-the-workload-runner-and-t3-serverless-compute-2026-10-20)). Set `off` to keep the targets idle.
   - **Check it:** `Invoke-DemoWorkloadCommand -Config $config -Target T1 -ArgumentList 'status', '--json'` runs any runner command on a target.

## Arc onboarding: `configure-arc.ps1`

```powershell
./scripts/configure-arc.ps1 -WaitForHostMinutes 120
```

1. It reads the T2 host's `health.json` through a read-only Run Command. With `-WaitForHostMinutes`, it reads it again every 5 minutes until the host waits for it, needs a manual step, is ready, or failed. Without it, it reads the state once and tells you to run it again later.
2. **`ProductKey` mode only (prerequisite P10):** when the host reports `WaitingForProductKey`, the script sends the key. Pass `-ProductKey` to type it at a hidden prompt; in GitHub Actions, the `DBHUB_SQL_PRODUCT_KEY` secret supplies it.
   - The key travels only as a protected Run Command parameter, and the script removes the environment variable as soon as it has read it.
   - The host stores the key with DPAPI and deletes it after setup.
   - A key is never sent to a host that isn't waiting for one.
3. When the host reports `WaitingForArcOnboarding`, the script onboards `arcsql01`: with the least-privilege host identity `id-<prefix>-<env>-arc-onboard` whenever it's attached to `archost01` (`assignRoles: true`), and otherwise with your short-lived Azure Resource Manager token, passed only as a protected parameter ([ADR 0005](adr/0005-arc-onboarding-authentication.md#phase-7-implementation-notes-2026-10-20)). Right after, a sweep removes what's left of the token on the host and in the guest and verifies that none is ([ADR 0009](adr/0009-secrets-handling.md)). Order of onboarding:
   - **`PaygWizard`:** onboarding comes right after the SQL Server media step, before the wizard.
   - **`ProductKey` and `Developer`:** onboarding comes after the unattended install.
   - **`JumpstartImage`:** onboarding comes after the image checks (`JumpstartImageCheck`).
   - If the guest is already connected, the script only confirms it. If an Arc machine from an earlier guest build exists, it deletes that machine's SQL Server instances, then the machine, and then onboards, so there are no duplicates.
4. It checks the Azure extension for SQL Server (1.1.2504.99 or later, license type PAYG), the SQL Server instance resource, and monitoring, and fixes what it can.
   - In `PaygWizard` mode, these checks report **Manual action required** until you finish the wizard step below. Run `configure-arc.ps1` again afterward.
5. It reports `T2.ARC.CONNECTED`, `T2.ARC.NODUPLICATES`, and `T2.ARC.DISCONNECTEDDAYS`, and writes every result to `out/configure-arc.jsonl`. `-WhatIf` runs only the guard.

Options:

- `-UseHostIdentity`: require the least-privilege host identity, and fail when it isn't attached (it needs `assignRoles: true`). It's used whenever it's attached anyway.
- `-UseCallerToken`: use your token even when the host identity is attached, for example while its role assignment is repaired.
- `-Force`: onboard again even when the host isn't waiting, to repair a broken connection.
- `-SkipConfiguration`: onboard only.

## Performance monitoring: `configure-monitoring.ps1`

Validated live: T1 on 2026-10-20 (`T1.SQLVM.MONITORING` **Pass**) and T2 on 2026-10-21 (`T2.ARC.MONITORING` **Pass**, with T2 telemetry about 7 minutes later).

```powershell
./scripts/configure-monitoring.ps1 -Target T1, T2 -WaitMinutes 15
```

- **T1:** merges the `DatabaseWatcheronAzureVM` feature flag into the SQL IaaS Agent extension's existing public settings and keeps every other setting. It then waits until the extension's status shows `DatabaseMonitorArcPlugin` with `"State":"Running"` and `"MetricsUploadStatus":"OK"`, which takes 3 to 15 minutes ([Microsoft Learn](https://learn.microsoft.com/azure/azure-sql/virtual-machines/windows/enable-performance-monitoring-sql-vm)).
  - After a template deployment, the extension shows `Updating` for about 10 minutes (Phase 13 live finding); with `-WaitMinutes` that's a wait, and without it a **Warning**, not a **Fail**. The monitoring flag survives the redeployment. `deploy.ps1` (the Monitoring stage) and `start-demo.ps1` (after recreating T3) run this check with a 20-minute wait.
  - A template run can also leave the plugin `NotRunning`, which waiting doesn't change (live, 2026-10-27). Since Phase 25d, when the Monitoring stage's wait ends with the extension Succeeded, the flag set, and the plugin not Running, `deploy.ps1` restarts the SQL IaaS Agent service, as `start-demo.ps1` does after a start, and reports `DEPLOY.T1.MONITORING` (live: Running with uploads OK 166 seconds after the restart). Since Phase 28, a `NotRunning` plugin ends that wait after a short grace (3 minutes, or 5 when the run merged the flag), not after `-MonitoringWaitMinutes`, the wait counts elapsed time with its reads, a console line every few minutes and the status page say what it waits for, and after a restart that worked `T1.SQLVM.MONITORING` is read again, so its Warning doesn't tell anyone to act (live, 2026-10-30: the wait had run 25 minutes, the restart then took 17 seconds, and the console still printed "Run configure-monitoring.ps1 -WaitMinutes 15").
  - It also reports `T1.SQLVM.ASSOCIATEDSERVICES`, read-only: **Pass** when unified inventory lists only the engine for T1, and a **Warning** while it still lists the image's Analysis Services or Integration Services as SQL Server instances. T1's `AssociatedServices` bootstrap step stops, disables, and uninstalls them (live, 2026-10-21); the demo uses the engine.
- **T2:** sets `monitoring.enabled` on the SQL Server instance resource. In `Developer` mode, it reports **Not supported**.
- **T3:** its monitoring setting is the database's extended property `MS_EnablePerformanceMonitoringPreview`, which the T3 stage of `deploy.ps1` sets from T1. `validate.ps1 -Area T3` checks it (`T3.PROPERTY`); this script reports **Not selected** for T3.

## The `PaygWizard` manual step (validated live 2026-10-21)

**Since Phase 28, `deploy.ps1` guides this step** ([the guided stop](#the-guided-stop-paygwizard)): it creates Bastion, hands over the host password, opens the portal page, and the guest signs itself in and opens setup pre-filled, so only the **Edition** page's two choices, **Use Azure Login**, and **Install** are left. The host's own message (in `health.json`, the console, and the status page) gives these steps. The steps below are the by-hand path, which still works: for example when the guest's automatic sign-in didn't open setup after 3 tries (the host then says to sign in as Administrator and run `C:\DbHubDemo\setup\Start-GuidedSetup.ps1`, which opens the same pre-filled setup), or on a host whose bundle predates Phase 28.

When T2 reports **Manual action required**, `health.json` on the host lists these steps, with the drive letter of the mounted SQL Server media:

1. Run `./scripts/start-demo.ps1 -Interactive -ResetAdminPassword` to create Bastion (about 8 minutes) and get a one-time host password on your clipboard (or, with the [Key Vault opt-in](#opt-in-the-password-in-key-vault-instead-of-the-clipboard), in the vault).
2. In the Azure portal, connect to `archost01` with Bastion.
3. On the host, in an elevated PowerShell window, run `C:\ProgramData\DbHubDemo\Copy-GuestCredential.ps1` to copy the guest password to the clipboard. It never displays the password; run it again with `-Clear` when you're done.
4. Open Hyper-V Manager and connect to `arcsql01`. At the sign-in screen, select **Clipboard** > **Type clipboard text** to enter the password for `Administrator`.
5. In the guest, run `setup.exe` from the SQL Server media drive. Select **Installation** > **New SQL Server standalone installation**.
6. On the **Edition** page, select **Use pay-as-you-go billing through Microsoft Azure**, then **Standard**.
7. On the **Azure Extension for SQL Server** page, select **Use Azure Login** and sign in with your own Azure account. Pay-as-you-go needs this page: the extension can't be cleared, and **Next** without a sign-in fails. The subscription, resource group, and region are filled in from the existing Arc connection and can't be changed. Never enter a service principal secret. If Windows asks you to add sites to the Trusted sites zone, follow your organization's rules ([installation wizard, Azure Extension for SQL Server](https://learn.microsoft.com/sql/database-engine/install-windows/install-sql-server-from-the-installation-wizard-setup)).
   - If the **Use Azure Login** window stays blank, or Internet Explorer says content from `https://login.microsoftonline.com` is blocked, follow the dialog's directions: select **Add...**, then **Add**, to put the Microsoft sign-in page in Trusted sites, and **Close**. Then select **Use Azure Login** again. Repeat for any other sign-in site it names ([setup's Azure sign-in](#setups-azure-sign-in-ie-enhanced-security-configuration); confirmed live on 2026-10-30).
   - Turning IE Enhanced Security Configuration off in **Server Manager** while setup is open doesn't help: setup keeps the setting it started with. Only when no dialog ever comes: close setup, open **Server Manager** > **Local Server** > **IE Enhanced Security Configuration**, set **Administrators** to **Off**, open setup again, and select **Use Azure Login** again. The host turns it back on afterward.
   - The WebView2 runtime: the host's `GuestWebView2` step installs it before this step, and the guided stop checks it again; Windows Server 2022 doesn't include it.
   - To install it by hand, for example on a host whose bundle predates that step, use the Evergreen **standalone** x64 installer from `https://go.microsoft.com/fwlink/?linkid=2124701` (HTTPS): check that `Get-AuthenticodeSignature` reports `Valid` with a Microsoft Corporation signer, then run it with `/silent /install`. The Evergreen bootstrapper hangs here, because it downloads over HTTP (port 80), which the T2 network security group blocks ([WebView2 distribution](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution)).
   - If sign-in says "There was an issue looking up your account", select **Next** to try again. It worked on the second try in the live run.
8. Select **Database Engine Services**, and leave **Azure Extension for SQL Server** selected. Keep the default instance (`MSSQLSERVER`).
9. Choose **Windows authentication mode**, select **Add Current User** as a SQL Server administrator, and install.
10. Close setup. The host detects the Standard instance within about 5 minutes and continues on its own:
    - Its `GuestSignInCleanup` step removes the sign-in data that setup leaves on the VM and verifies that none remains; the build stops if any remains. The step waits while setup or the Installation Center still runs, so close both.
    - It turns Internet Explorer Enhanced Security Configuration back on if it's off (since Phase 28, the guided stop's own cleanup does that first); leave it on afterward.
    - Then Query Store, file growth caps, and the `ContosoCare` seed.
11. Run `./scripts/configure-arc.ps1` to converge the SQL Server extension (license type, monitoring) once Azure finishes creating it, then `./scripts/configure-monitoring.ps1 -Target T2`. Or run `./scripts/deploy.ps1 -Resume`: its T2 stage does the same, then sets T2's activity profile.
12. Run `./scripts/stop-demo.ps1 -RemoveBastionOnly`: it deletes Bastion and its public IP and rotates the host password. The hourly `bastion-cleanup.yml` does the same after `bastionMaxHours`.

The setup wizard deploys the `WindowsAgent.SqlServer` extension to `arcsql01` through Azure; in the live run it stayed in **Creating** long after setup finished, because its downloads failed intermittently inside the guest (R72). Run `configure-arc.ps1` again once it's there.

## The T2 golden snapshot: `capture-t2-golden.ps1` and `test-t2-golden.ps1`

The setup-wizard step for pay-as-you-go SQL Server can't be scripted, so Phase 20 keeps a finished T2 host as an incremental snapshot of `archost01-osdisk` in `rg-<prefix>-golden` ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)):

```powershell
./scripts/capture-t2-golden.ps1          # preconditions, the guest air-gapped, the host stopped, then the snapshot (DenyAll) and a disk check
./scripts/test-t2-golden.ps1 -Onboard    # a quarantined copy: no outbound traffic, the Arc identity reset, SQL Server Standard, then a fresh onboarding with PAYG and monitoring
```

- **Which modes:** `capture-t2-golden.ps1` accepts `PaygWizard`, where the snapshot keeps the setup-wizard step, and `JumpstartImage` (since 2026-11-05), where it's only an optional speed-up: a redeploy skips T2's host build, about 27 minutes when measured on 2026-11-06, and nothing is lost without one, because the next deploy prepares the image again with no person. `ProductKey` and `Developer` are **Not supported** (`GOLDEN.CAPTURE.MODE`): they install unattended on every build. `t2Source` `auto` restores only a snapshot of the configured install mode, and `destroy.ps1`'s golden guard (`DESTROY.GOLDEN.GUARD`) stays `PaygWizard`-only.
- A snapshot is used only after `test-t2-golden.ps1` tags it boot-verified; older snapshots of the prefix are deleted only then.
- The guest's 180-day evaluation runs inside it: `status.ps1` (`STATUS.T2.GOLDEN`) and preflight (`PREFLIGHT.T2.SOURCE`) warn at 30 and at 7 days left. After that, capture again from a fresh build and the wizard step. A `JumpstartImage` guest isn't an evaluation: its snapshot's `dbhubEvalExpiresUtc` tag is `none`, and these warnings don't apply.
- It's priced from the Retail Prices API on the OS disk's provisioned size ([cost management](cost-management.md#the-t2-golden-snapshot-phase-20)); `destroy.ps1 -IncludeGolden` deletes it.
- Live (2026-10-22): captured from the finished host, proven in quarantine (4,492 seconds, the extension download included), and restored by the redeploy above.
- **Sign-in data (ADR 0009):** the capture removes the sign-in data left on the host and in the guest and captures nothing unless a fresh scan finds none (`GOLDEN.CAPTURE.SIGNIN`); the test scans each copy too (`GOLDEN.TEST.SIGNIN`). `capture-t2-golden.ps1 -WipeFreeSpace` also overwrites the guest's and the host's free space with zeros, compacts the guest's disk, and trims both volumes, so nothing deleted survives in free space and the snapshot keeps no zeroed block; it needs 45 GB free on the host's `C:` (`-MinHostFreeGB`) and adds about an hour. With `assignRoles: true`, `test-t2-golden.ps1 -Onboard` onboards with the test group's own host identity, not your token. Both scripts keep your PC and its display awake until they finish.

## Run Commands, policies, and deallocated VMs

Every VM-side action goes through Run Command, which has three limits that the scripts handle for you:

- **A policy-installed extension blocks it for a while.** Tenant policies install Guest Configuration and Defender for SQL after a deployment, and update `MDE.Windows` later; live, an `MDE.Windows` update blocked Run Commands on `archost01` for about 10 minutes (R49). A **Conflict** is retried with waits of 10, 20, 40, 80, and then 120 seconds, about 12.5 minutes in all, and the log names the likely cause.
- **It needs a running VM.** On a deallocated VM, Azure answers `OperationNotAllowed`, which isn't retried: the message says to start the VM first (`start-demo.ps1`). A password rotation then reports **Manual action required**, and a profile change on a VM that isn't running reports **Not selected**, because nothing runs there.
- **A Run Command created again right after it was deleted can report the previous run** instead of running its script (live, 2026-10-21). `Invoke-DemoVmRunCommand` ignores a result whose execution started before the request, tries once more after 60 seconds, and then reports it as stale, so it never counts as the new script's result (Phase 7).
- **Deletes that Azure doesn't finish don't hold a run up (Phase 28).** Chunk deletes aren't waited for, the VM's extensions settle before its artifacts and its loader, a watchdog restarts a stuck VM once, and a stall sends the rest one at a time ([Run Commands that don't stall a run](#run-commands-that-dont-stall-a-run-phase-28)).
