# Deployment

How `./scripts/deploy.ps1` deploys and updates the demo, how to run the demo day to day, and every command, switch, and step, with how long each takes. The [README](../README.md#quick-start) has the short path, and [troubleshooting](troubleshooting.md) the fix for each result that isn't **Pass**. You never need GitHub Actions or the Deploy to Azure button: `deploy.ps1`, the other scripts, and the control notebook do everything; both are optional, [for maintainers](#for-maintainers).

## Deploy it, step by step

**Where it goes:** your own Azure subscription and Fabric capacity, in one Microsoft Entra tenant: the resource groups `rg-dbhub-demo` (`rg-<prefix>-<environment>`, West US 3 by default; preflight checks that Database Hub supports your `location`) and `rg-dbhub-control` (the [session control](#the-session-control)), and the Fabric workspace **Database Hub Demo** (another prefix gets its own: [first run](#first-run-initps1)), which the scripts find by name and create when it's missing, so you never look up an ID ([ADR 0021](adr/0021-fabric-resources-by-name.md)). The [README](../README.md#whats-deployed-and-by-what) lists every part, and what creates and deletes it. Run the scripts on your computer, in the repository's [dev container](../.devcontainer/devcontainer.json), or in GitHub Codespaces.

### Before you start

Once; [prerequisites](prerequisites.md) has each item, who provides it, and how it's checked:

| You need | Who provides it |
|---|---|
| **Contributor** on the Azure subscription (P1), and quota for about **8 vCPUs** of nested-virtualization VM sizes, which preflight checks | The subscription's Owner |
| *Recommended, once per environment:* an **Owner** (or User Access Administrator) for the nightly safety stop's and the session control's roles (P16, P15). As one, `deploy.ps1` assigns them; otherwise **DONE**'s first note is `./scripts/grant-safety-stop.ps1`, for an Owner to run once, which also gives you, who deployed, the control vault's three secrets, so you can Run all with nothing to edit (`CONTROL.ROLE.DEPLOYER`, since 2026-11-19). Until then, Run all can't start a session (`./scripts/start-demo.ps1` can), nothing stops T4 when Azure starts it again 7 days after a stop, and T5's container can stay, and bill, between sessions | You, or the Owner |
| An **F or Trial Fabric capacity** you can assign, **running** while you deploy | You, or its administrator |
| The tenant settings **Users can access the Database hub (preview)** (P4) and, without a workspace, **Create workspaces**; for the Insights app, **Fabric Apps (preview)** and **Dataset Execute Queries REST API** (P12, P13); for Ask, **Enforce a strict content security policy for static-hosted Fabric Apps (preview)** left off, its default | Your Fabric administrator |
| For Ask, the Copilot chat in the Insights app: each viewer's own GitHub Copilot plan, and, where a GitHub organization restricts OAuth apps, its approval of **Database Hub Insights Ask**, once | Each viewer; the organization's owner |
| Outbound HTTPS from the VMs, in the default T2 mode to `jumpstartprodsg.blob.core.windows.net` and `raw.githubusercontent.com` too ([ADR 0017](adr/0017-outbound-access.md)); PowerShell 7.4, the Azure CLI with Bicep, Node.js 24, and Git, or the dev container ([tools](prerequisites.md#tools); `deploy.ps1` installs the .NET SDK on Windows) | You, or a restrictive firewall's administrator |

Without the Insights app's or Ask's settings, the rest works, and the run still ends **DONE**.

- **Your sign-in:** you run `az login` yourself, as the account that runs the demo ([sign in interactively](https://learn.microsoft.com/cli/azure/authenticate-azure-cli-interactively)). The scripts never sign in or out or change the Azure CLI's context, so your default subscription stays as it is: every call names the configured subscription, and the subscription guard (`PREFLIGHT.GUARD.CONTEXT`) checks its account and tenant before anything is written ([the guard](prerequisites.md#target-subscription-configuration-the-subscription-guard), [when it stops a script](troubleshooting.md#the-guard-stops-a-script)). A shared Azure CLI profile can be kept apart with `AZURE_CONFIG_DIR` ([a separate profile](prerequisites.md#optional-a-separate-azure-cli-profile)).
- **Cost:** preflight prices the deployment for your region at run time, from Azure's list prices, against two ceilings: $20 a session (`sessionCeilingUsd`, a **Warning** above it) and $415 a month for a new configuration (`monthlyCeilingUsd`, a hard ceiling: preflight fails above it, and nothing is deployed; a configuration keeps its own value). `./scripts/estimate-cost.ps1` shows the estimate first, with no sign-in. The Fabric capacity, Fabric and Power BI licenses, and each viewer's GitHub Copilot plan are outside every estimate ([cost management](cost-management.md#at-a-glance)).

### Steps

After `az login`, nobody is needed during the run; a first deployment took 91 minutes (on 2026-11-06, before T4's read replica, the session control, T5, and Ask; [expected duration](#expected-duration)).

1. **Get the code:** `git clone https://github.com/MarcBushong/fabric-database-hub-demo.git`, **Use this template** for your own copy, or [GitHub Codespaces](https://codespaces.new/MarcBushong/fabric-database-hub-demo?quickstart=1). No `git pull` is needed: `deploy.ps1` updates a clean checkout of `main` itself ([updates from GitHub](#updates-from-github-2026-11-09)).
2. **Sign in:** `az login` (`az login --use-device-code` in a codespace or a container).
3. **Deploy:** `./scripts/deploy.ps1`. Its first run writes `config/demo.config.json` from your sign-in, asking only when there's more than one subscription or capacity, and creates the group `dbhub-demo-sql-admins`, which administers T3 and T4 ([first run](#first-run-initps1)). Then it checks everything, deploys T1 (with T3 and T5), T2, T4, and Fabric in parallel, and waits for T2, whose host makes `arcsql01` from Arc Jumpstart's SQL Server 2022 Standard image (about 27 minutes) and onboards it to Azure Arc (about 33 more) ([T2's install modes](#options-t2s-install-modes)). Every run also sets up the [nightly safety stop](#the-nightly-safety-stop) and the [session control](#the-session-control), and ends with the [history report's snapshot](#the-history-reports-snapshot-at-the-end-2026-11-06). An older demo updates with the same command ([update](#update-an-existing-environment)).
4. **The ending:** **DONE** means Database Hub shows every target ([what DONE needs](#what-done-needs)); it names first what an Owner still has to grant, then where Run all is (`DEPLOY.CONTROL`), and lists under **Please confirm** what only a person can confirm, such as selecting T3 for Database Agents, required once for the Database Agent beat, a minute or two in Database Hub's **Manage agents** (`HUB.AGENT.T3`, [step by step](database-agents.md)). **NOT DONE** gives why, the next action, and the exact command, usually `./scripts/deploy.ps1` again, which continues where it stopped, also after the window closes or the PC restarts. When such a run started VMs, one line says which now bill, and how they stop: `./scripts/stop-demo.ps1` now, or the nightly auto-shutdown. After **DONE**, a new deployment keeps running, and **DONE** says what it bills an hour and until when; an update that found the demo stopped stops what it started at its end ([the stop at the end of an update](#the-stop-at-the-end-of-an-update-2026-11-19)).
5. **See it:** open **Database Hub** in the Fabric portal ([Database Hub](https://learn.microsoft.com/fabric/database/hub/overview)) at Estate and Performance ([Monitor a Microsoft SQL database](https://learn.microsoft.com/fabric/database/hub/monitor-sql)), whose problem panels the default `business-day` profile's hourly incidents fill ([the hourly incidents](demo-walkthrough.md#the-hourly-incidents-business-day)). For one now, `./scripts/demo-control.ps1 -Target T2 -Scenario incident:cpu-pressure -Duration 25`, then investigate it with Copilot in Database Hub. Database Agents (preview) covers Azure SQL Database only, T3 here: once you've selected T3, a Run all session shows its loop ([the Database Agent loop](demo-walkthrough.md#the-database-agent-loop-on-t3)).
6. **Keep the build** (optional): `./scripts/capture-t2-golden.ps1`, then `./scripts/test-t2-golden.ps1 -Onboard`, so a redeploy skips T2's build; it bills every month ([golden snapshot](#the-t2-golden-snapshot-capture-t2-goldenps1-and-test-t2-goldenps1)).
7. **The Insights app and Ask** come with every deployment and never block **DONE** ([the Insights app](#the-insights-app-part-of-every-deployment-2026-11-05)); open the app from its workspace item. Each viewer signs in to GitHub once per browser, on their own Copilot plan ([the Copilot chat](../README.md#the-copilot-chat-in-the-insights-app)).
8. **Run a session:** resume the capacity if it's paused, open `NB_DatabaseHub_Control` where **DONE** says, and select **Run all** ([Run all](#run-a-session-run-all)); from a PC, `./scripts/start-demo.ps1`, then `./scripts/stop-demo.ps1 -SaveHistory`; a `start-demo.ps1` session stops by itself 4 hours after its start (`-Hours` changes that). What you forget stops at `autoShutdownTime`, 19:00 by default in the time zone `init.ps1` wrote, this machine's ([what stops on its own](cost-management.md#what-stops-or-pauses-on-its-own)).
9. **Remove it:** `./scripts/destroy.ps1` ([destroy](#destroy-destroyps1)).

### While it runs

- **The status page,** `out/deploy-status.html`, opens at the start and refreshes itself, offline: **Deploying, no action needed** (you can step away), **Done**, or **Stopped, not done**, with every step of every track and a red **Needs attention** box ([the status page](#the-live-status-page-and-statusps1--watch)). `./scripts/status.ps1 -Watch` shows the same in a second terminal, anywhere.
- **Keep the machine on:** `deploy.ps1` keeps a Windows PC and its display awake until it ends; plug a laptop in and leave it open. On macOS and Linux, keep it awake yourself: a sleeping machine freezes the run.
- **If something goes wrong,** run `./scripts/deploy.ps1` again; when **NOT DONE** repeats, `./scripts/collect-diagnostics.ps1` writes a redacted zip for a **Deployment problem** issue ([diagnostics](#diagnostics-collect-diagnosticsps1), [getting help](../README.md#troubleshooting-and-help)).
- **To stop it,** Ctrl+C: the run and its background processes stop within seconds, and it ends **Stopped, not done**, with the command that continues.

### Running it with an AI assistant

An assistant such as GitHub Copilot can drive the whole deployment: in the default T2 mode, T2 needs no person. [AGENTS.md](../AGENTS.md) gives it the rules: run `./scripts/deploy.ps1`, which also upgrades an older demo; never assemble a partial setup by hand or leave out a target; and report **DONE** or **NOT DONE** with its reason, the exact next command, and what [the banner says](#what-the-banner-may-say). `deploy.ps1` notices a session that can't take keyboard input and never asks there: a choice it can't make is **NOT DONE** with the parameter to pass to `./scripts/init.ps1`. What stays yours: `az login`; the Rayfin CLI's browser sign-in for the Insights app, only when Fabric refuses your Azure CLI's token (`FABRIC.APP.TOKEN`, a **Warning**), which starts only in a session that can take keyboard input, so run `./scripts/configure-fabric-app.ps1 -SignIn` yourself in a terminal; an Owner's `./scripts/grant-safety-stop.ps1`; and the selection of T3 for Database Agents, required once for the Database Agent beat, which has no API ([step by step](database-agents.md)).

### In GitHub Codespaces

The dev container has every tool. A codespace stops after 30 minutes without activity by default; `deploy.ps1` prints progress at least every 5 minutes, which counts, and warns at the start, but raise the timeout before a first run: **Settings** > **Codespaces** > **Default idle timeout**, up to 240 minutes, for codespaces you create afterward, or `gh codespace create --idle-timeout 240m` ([GitHub Docs](https://docs.github.com/codespaces/setting-your-user-preferences/setting-your-timeout-period-for-github-codespaces)); an organization's policy can set a lower maximum. A codespace can't open a browser: preview the status page as `deploy.ps1` prints (`python3 -m http.server 8000 --directory out` in a second terminal, then port 8000 in the **Ports** tab, which stays private to you: [forwarding ports](https://docs.github.com/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace)), or use `./scripts/status.ps1 -Watch`. The Rayfin CLI's browser sign-in, needed only after Fabric refused your Azure CLI's token, may not complete there; `./scripts/configure-fabric-app.ps1 -SignIn` adds the app later from a machine with a browser. A codespace is usually in UTC, which `init.ps1` writes as the auto-shutdown time zone unless you pass `-TimeZone`.

### What DONE needs

**DONE** means Database Hub shows every target ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md#1-when-the-clock-stops)): every track finished, no **Fail**, no **Manual action required** except under **Please confirm**, and a **Pass**, checked again read-only when the run didn't see it, for:

- `HUB.ESTATE.T1` to `HUB.ESTATE.T5` (T5 only when Azure created its account; otherwise `DEPLOY.T5` says so);
- `TELEMETRY.T1`, `TELEMETRY.T2`, `TELEMETRY.T3`, `METRICS.T4`, and `METRICS.T5`;
- `HUB.ESTATE.T4.REPLICA` and `METRICS.T4.REPLICA`, T4's read replica and its lag (**Not supported** meets them on a Burstable T4);
- `T2.ARC.SQLINSTANCE` and `T2.ARC.MONITORING`: Standard, PAYG or Paid, monitoring on; in `Developer` mode these and `TELEMETRY.T2` aren't needed, and **DONE** says T2 has no performance data;
- `T1.SQLVM.ASSOCIATEDSERVICES`;
- `FABRIC.ITEMS.REQUIRED`: the workspace, lakehouse, notebooks, Real-Time Dashboard, and history model and report (not with `-SkipFabric`), missing only when a list answered without one. A paused capacity (HTTP 404 `CapacityNotActive`) is **NOT DONE**, naming the capacity first (`FABRIC.P5.CAPACITY`) for you or its administrator to resume, since `deploy.ps1` never resumes, pauses, or scales it; throttling (429) or a service error (5xx) is a **Warning**: run `./scripts/deploy.ps1` again in a few minutes.

T4 is in every run, whatever `t4Enabled` says: when Azure refuses every size, the run deploys the rest and ends **NOT DONE** (`DEPLOY.T4.SKU` and `DEPLOY.T4.OFF`, **Fail**).

**Please confirm** lists, once and never blocking **DONE**, what a rerun can't resolve (apart from what needs you in `DEPLOY.SUMMARY`):

- **"Users can access the Database hub (preview)" (P4), when it couldn't be read:** preflight (`PREFLIGHT.P4.HUBSETTING`) and the Fabric track (`FABRIC.P4.HUBSETTING`) read it through the admin API ([Tenants - List Tenant Settings](https://learn.microsoft.com/rest/api/fabric/admin/tenants/list-tenant-settings)), which needs a Fabric administrator. On: **Pass**; on for security groups only: a **Warning** (every presenter must be a member); off: **Manual action required**, which does block **DONE**.
- `FABRIC.P5.CAPACITY` for a capacity SKU the check doesn't know, such as a Trial.
- `HUB.PRESENTER.*` with `assignRoles` false, the default: an administrator runs the commands in the result ([ADR 0008](adr/0008-identity-rbac-abac.md)).
- `FABRIC.APP.BROWSER`, when the app's queries couldn't verify it: open the app once and see "Connector check passed" on **Live views**; when they did (`FABRIC.APP.QUERIES`), it's a note, **Not selected** ([ADR 0012](adr/0012-validation-model.md#2026-11-09-the-rayfin-cli-with-the-azure-clis-tokens)).
- `HUB.AGENT.T3`: required once for the Database Agent beat, and everything else works without it. Select T3 once in Database Hub's **Agent (preview)** > **Manage agents** > **Database agent settings**, with the link and database it gives; Database Agents has no API. It stays until T3 is recreated (`stop-demo.ps1 -RemoveT3`, or a new deployment) ([step by step](database-agents.md)).

**Never blocking DONE either:** the Insights app (`FABRIC.APP.*`, `DEPLOY.FABRIC.APP`), Ask (`ASK.RELAY`, `ASK.RELAY.HEALTH`, `ASK.CSP`, `ASK.SIGNIN`), the history model's DAX check while **Dataset Execute Queries REST API** is off (`FABRIC.SEMANTICMODEL.*`, **Manual action required**), and the history snapshot (`DEPLOY.FABRIC.HISTORY`). What didn't work is in the banner and on the status page, with the fix. **NOT DONE** is only for what can change the outcome, and its next step is that item's own fix.

### What a clean first deployment shows (2026-11-06)

Besides **Pass**, expect these **Warnings**; none blocks **DONE** or needs a rerun: `T4.MAXCONNECTIONS`, while `max_connections` waits for the restart T1's T4 step then does (`DEPLOY.T4.RESTART`); `DEPLOY.ARTIFACTS.CLEANUP_<VM>`, while Azure still deletes a chunk Run Command ([stuck in Deleting](troubleshooting.md#run-commands-stuck-in-deleting)); `PREFLIGHT.T3.FREEOFFER` and `T3.FREEOFFER`, when the subscription can't give T3 the free offer, so T3 is regular serverless ([T3's cost](cost-management.md#azure-sql-t3-free-offer-and-lifecycle)); `FABRIC.SEMANTICMODEL.MEASURES`, checked before the [snapshot at the end](#the-history-reports-snapshot-at-the-end-2026-11-06) fills them; `DEPLOY.T5.FREETIER`, in an internal subscription, where Azure doesn't offer the free tier, or when another Azure Cosmos DB account has it; `T2.ARC.MIGRATIONASSESSMENT`, while the extension picks up the setting (the run retries for 10 minutes, and the next `deploy.ps1` or `configure-arc.ps1` starts it); and, when you aren't an Owner, `SAFETYSTOP.ROLE` and `CONTROL.ROLE.*`, with `./scripts/grant-safety-stop.ps1` for an Owner. `HUB.AGENT.T3` is under **Please confirm**.

### The Insights app, part of every deployment (2026-11-05)

`configure-fabric-app.ps1`, the Fabric track's last step, deploys the Insights app `APP_DatabaseHub_Insights` ([ADR 0029](adr/0029-insights-app-dba-console.md), [its guide](../fabric/app/README.md)) and the two user data functions beside it: `APP_DatabaseHub_Insights_connector`, its read-only connector to the history model, and `APP_DatabaseHub_Insights`, with the live estate (eight read-only Database Hub routes from the generally available `databasehub-cli` skill, scoped to the demo's resource group: the repository's one exception to documented interfaces only, [ADR 0013](adr/0013-agent-experience.md#amendment-2026-11-18-the-ga-skill-and-one-narrow-exception); Database Hub refuses the app's own sign-in today, so `FABRIC.APP.ESTATE` is **Not supported**, R924) and Manage's `manageAccess`, `manageRequest`, and `manageJob`, which start or stop a session, which bills. `destroy.ps1` deletes them with the workspace.

- **With your `az login`:** each Rayfin CLI command gets an Azure CLI token for its audience, so no browser opens (`DEPLOY.FABRIC.APPSIGNIN`, **Not selected**; [the app's guide](../fabric/app/README.md#deploy), [ADR 0023](adr/0023-first-run-automation.md#amendment-the-azure-clis-tokens-for-the-rayfin-cli-2026-11-09-user-directed)). When Fabric refuses that token (`FABRIC.APP.TOKEN`, a **Warning**), the CLI's own cached sign-in (P14) deploys the app, or `./scripts/configure-fabric-app.ps1 -SignIn` adds it with a browser sign-in; the next `deploy.ps1` with keyboard input starts that sign-in at its beginning (recorded in `out/fabric-app-auth.json`, never a token), and only the app's step waits, at most 15 minutes; in CI it doesn't start (**Not supported**).
- **It never blocks DONE:** an error in the step is its record `DEPLOY.FABRIC.APP` (**Manual action required**, marked `nonBlocking` with the `reportedStatus`), never a **Fail**, so it never blocks **DONE**, `DEPLOY.SUMMARY`, or a GitHub Actions run. The status page shows the step **Failed**, in red, with the error and the fix, also in its **Needs attention** box, `status.ps1 -Watch`, and **DONE** (`Failed (doesn't block DONE): the Insights app. ...`). Fixes, in order: the record's own; the tenant settings **Fabric Apps (preview)** and **Dataset Execute Queries REST API**, which preflight checks (`PREFLIGHT.FABRIC.APPSETTINGS`, a **Warning** at worst); `./scripts/configure-fabric-app.ps1 -SignIn`.
- **Ask's chat relay** ([ADR 0028](adr/0028-ask-copilot-in-the-insights-app.md), [its guide](../ask-relay/README.md)): `ca-<prefix>-<environment>-ask` in the Container Apps environment `cae-<prefix>-<environment>-ask`, from a public image pinned by digest (`askRelay.image` in `config/versions.json`), so you never build it or run GitHub Actions. The step registers `Microsoft.App` when needed and checks the relay (`ASK.RELAY`, `ASK.RELAY.HEALTH`, `ASK.SIGNIN`) and the strict content security policy setting, which must stay off (`ASK.CSP`); a **Warning** names its fix ([troubleshooting](troubleshooting.md#ask-the-copilot-chat-in-the-insights-app-2026-11-18)). It scales to zero about 10 minutes after the last question; `"ask": { "enabled": false }` leaves it out (**Not selected**).

### The history report's snapshot at the end (2026-11-06)

After **DONE**'s checks and the switch to the run's activity profile, `deploy.ps1` runs `NB_DatabaseHub_LiveActivity` once, as you, analyze-only ([Run On Demand Item Job](https://learn.microsoft.com/rest/api/fabric/core/job-scheduler/run-on-demand-item-job)): `SAVE_RESULTS` over the last 1,440 minutes (`WINDOW_MINUTES`) for `RESOURCE_GROUP` (for a notebook imported before 2026-11-14, also `CONFIRM` and `STOP_ACTIVITY` false and `KEY_VAULT_URL` empty). Then it refreshes the Direct Lake model ([how Direct Lake works](https://learn.microsoft.com/fabric/fundamentals/direct-lake-how-it-works)), so the report has the run's data ([ADR 0014](adr/0014-notebook-role-and-capacity.md#amendment-2026-11-06-one-analyze-only-run-at-the-end-of-each-deployment)). About 2 to 5 minutes (an estimate); it waits at most 10 for the job and 5 for the refresh.

- `DEPLOY.FABRIC.HISTORY` is **Pass**, a **Warning**, or **Not selected**, never blocking. A paused capacity, a job that outlives its wait, or a failed notebook (`reportedStatus` `Fail`) is a **Warning** on the status page's last row, **History report's snapshot**; after resuming a capacity, `./scripts/configure-fabric.ps1 -SkipHubChecks -SkipNotebookImport -RunLiveActivity` takes the snapshot. It's **Not selected** with `-WhatIf` or `-SkipFabric`, in GitHub Actions, when **DONE**'s telemetry checks didn't pass, and without the lakehouse or the notebook.
- Incidents start only after **DONE**'s checks, so incident measures such as **Blocking Incidents** stay blank until the notebook runs again: `./scripts/stop-demo.ps1 -SaveHistory`, the command above, or the next `deploy.ps1`; `./scripts/configure-powerbi.ps1 -CheckModelData` checks every measure.
- **The Incident RCA's evidence** (2026-11-20, [ADR 0031](adr/0031-incident-rca.md)): before the run, the runners' export on the VMs, through managed Run Commands that only read (not a session's last: the activity goes on), with what an earlier save didn't take, staged as `RCA_EVIDENCE_FILE` ([the history](../fabric/README.md#the-incident-rcas-evidence-in-the-history-2026-11-20)). `DEPLOY.FABRIC.HISTORY` says what it did in a sentence and in its evidence `rca`; an export, or a save of it, that didn't work makes a **Pass** a **Warning**, with its fix, never in **DONE**'s way.
- A new lakehouse's history tables come from the notebook's first run, when the Fabric track imports it; a busy capacity can queue it, so the track waits up to 45 minutes, refreshes the model, and follows it up to 45 more; one that never completes is a **Warning** ([#68](https://github.com/MarcBushong/fabric-database-hub-demo/issues/68)). An update doesn't run it.

## Update an existing environment

Run `./scripts/deploy.ps1`, as for a new environment: no flag, no edit to your configuration, and nothing started or repaired by hand first ([AGENTS.md](../AGENTS.md) says the same to an assistant). Until you do, nothing changes: the environment never reads GitHub, and a newer copy of the scripts works with it, where `status.ps1`, `start-demo.ps1`, and `stop-demo.ps1` say what isn't deployed yet, with `./scripts/deploy.ps1` as the fix (a **Warning** or **Not selected**, never a **Fail**). The run updates a clean checkout of `main` first ([updates from GitHub](#updates-from-github-2026-11-09)), writes a missing configuration from what's deployed when the environment is yours (`INIT.EXISTING`, [first run](#first-run-initps1)), and continues an unfinished run, with any changed bundle or runner sent to the VMs ([how a run behaves](#one-command-one-guided-stop-phase-28)). After a run that ended **DONE**, it starts over, with preflight and the template, so every change reaches the environment, from T4's `max_connections` and size and the budget at your `monthlyCeilingUsd` to the runner's T-SQL (`database/common`), which its `setup` applies on every target. To apply only part of it ([options](#options)): `./scripts/deploy.ps1 -FromStage Infrastructure` applies the template and everything after it without preflight; `-FromStage Artifacts`, the runner and its T-SQL without the template; `-Resume` after **DONE**, only the validation and a changed bundle or runner.

### The stop at the end of an update (2026-11-19)

An update leaves the demo as it found it (`Invoke-DemoUpdateEndStop`; the coordinator's decision for the owner, who can reverse it). The run starts what's stopped so its steps can reach the hosts (`DEPLOY.VMSTART`, which records what ran and what was stopped when it began); before 2026-11-19, all of it then ran, and billed, until the nightly stop.

- **When it stops:** the run ends **DONE**, and `DEPLOY.VMSTART` says the demo was stopped when it began: no demo VM ran or was starting, and the run started something. Once **DONE**'s checks and the history snapshot are done, it stops again what it started through `stop-demo.ps1`'s own stop (`Stop-DemoEnvironment -SkipFabric`): the activity off, T3's Database Agent hold released, T2's guest shut down, both VMs deallocated, T4 stopped, T5's container deleted, and a pending auto-stop removed. It leaves the history and the Fabric capacity alone.
- **What it waits for first, at most 15 minutes in all:** a bootstrap pass that still runs on a demo VM it deallocates, and T2's first migration assessment, until it uploads. What isn't done by then goes on at the next start (a bootstrap pass), or at the next `./scripts/deploy.ps1` or `./scripts/configure-arc.ps1` (the assessment), and the row says so.
- **When it keeps running,** with **DONE**'s line about what it bills an hour (list prices, read at run time), until when, and that `./scripts/stop-demo.ps1` stops it now: a new deployment, so you can look at it right away; a demo that was running or starting when the run began; a session that uses the demo; and `./scripts/deploy.ps1 -KeepRunning`. A run that isn't **DONE** keeps what it started for the next run, with its billing note.
- **A session that uses the demo:** a pending auto-stop of Run all, the Insights app's **Start**, or `start-demo.ps1`; Run all's busy marker, or a request to the session control on its way; or a `start-demo.ps1` that began during the run, which records its start (`DbHubStartDemoUtc`). It's read before the wait, after it, and twice in the stop (`STOP.SESSION`): before its first change, and before T2's guest and the VMs, which then keep running (a **Warning**: the activity is off already, so stop and start the session again). A session that starts during the deallocation itself is a **Warning** with how to start it again; an auto-stop left from before the run, whose session the nightly stop ended, doesn't count. When it can't be read, the demo keeps running.
- **Where it shows:** the status page's **Stop at the end** row, **DONE**'s line, and `DEPLOY.ENDSTOP` in `out/deploy.jsonl`. A stop that fails is a **Warning** with `./scripts/stop-demo.ps1` as the fix, never **NOT DONE**, and tonight's nightly stop stays in place; a demo stopped this way needs no nightly stop that night, so **DONE** leaves out `DEPLOY.NIGHTLYSTOP`'s line. Ctrl+C during it leaves running what it hadn't stopped, and the row says so.

### Older code over a newer demo (2026-11-23)

`deploy.ps1` moves an environment forward: a clean checkout of `main` updates itself first ([updates from GitHub](#updates-from-github-2026-11-09)). An older checkout that can't update itself (`DEPLOY.SELFUPDATE`) runs the code it has, and that can put an older workload runner on the VMs. That isn't a supported path.

For the Incident RCA's Query Store evidence, which waits on the VMs in sidecars until a history save takes it, two losses are accepted limits:

- sidecars sealed more than 30 days before a newer runner comes back;
- the rows of a session whose runner was replaced mid-session.

[rca/README.md](../rca/README.md#versioning) says what an older runner keeps. Before you deploy older code, take every sidecar into the history with the VMs running: `./scripts/configure-fabric.ps1 -SkipHubChecks -SkipNotebookImport -RunLiveActivity`, and run it again while its line says sidecars still wait.

## Day to day

### Run a session: Run all

Resume the Fabric capacity if it's paused (Run all never resumes it; that's yours or its administrator's, and `fabric.manageCapacity` lets the start and stop scripts do it for a capacity that's yours alone), open `NB_DatabaseHub_Control` where **DONE** says (`DEPLOY.CONTROL`: the folder "DBHub Control" of the demo's workspace, or the control's own workspace), and select **Run all**, about 30 minutes before your audience. It starts the VMs, T4, T4's read replica, and T5's container, runs the 90-minute showcase on all five targets, prints a presenter's guide, then stops everything and saves the session's history. Its auto-stop (`dbhub-autostop`) runs 10 minutes after the session's end, with a backup (`dbhub-autostop-backup`) 30 minutes later only if the first failed.

Its first cell's switches need no edit: `DURATION_MINUTES` (90 by default, 30 to 120), `MODE = "check"` (the plan, sending nothing), `STOP_NOW = True` or `RESET_NOW = True` for **Stop now** and **Reset**, and `MODE = "activities"` with `ACTIVITIES` for chosen scenarios only, with no replica or history ([the notebook's guide](../fabric/control/README.md)). During a session, `./scripts/demo-control.ps1` on a target replaces its showcase (on T3, it ends the Database Agent loop). Until an Owner has run `./scripts/grant-safety-stop.ps1`, or from a PC, use `./scripts/start-demo.ps1`, then `./scripts/stop-demo.ps1 -SaveHistory`.

### Start: `start-demo.ps1`

`./scripts/start-demo.ps1 -WarmUpMinutes 30`, in order:

1. **The cost guardrail:** the estimate against both ceilings, and this month's actual cost plus one session (`START.COST.*`, `START.COST.ACTUAL`); a **Fail** stops it, unless `-SkipCostCheck`.
2. **The session's auto-stop** (since 2026-11-19, `START.CONTROL.AUTOSTOP`), before the VMs start: the same one-time auto-stop a Run all session uses (`dbhub-autostop`, with its backup 30 minutes later), `-Hours` after this start (4 by default, 0.5 to 24), or after the warm-up with `-WaitForWarmUp`; the result says when, on the VMs' clock, and when the nightly stop comes first. It replaces a pending auto-stop of an earlier session, after waiting up to 10 minutes for a `DbHub-Stop` job already running (`START.CONTROL.STOPJOB`), and running `start-demo.ps1` again starts the hours over. Marked `[start-demo.ps1]`, it gives way to a later Run all or the Insights app's **Start**, which replace it with their own plan, and it moves past a `deploy.ps1` that's still running. Without the session control's role at the demo resource group (A1, before an Owner's `./scripts/grant-safety-stop.ps1`), or until `./scripts/deploy.ps1` has republished the runbooks after an update of the scripts, none is scheduled, and a **Warning** says the nightly stop is the limit, with the fix; the start never fails for it ([ADR 0020](adr/0020-on-demand-activity-control.md#amendment-2026-11-19-start-demops1-schedules-its-own-auto-stop)).
3. **The VMs** start together. Each VM's targets get `baseline` first, so an incident an earlier session left ends early (`START.INTERIM_*`, a **Warning** with the commands when it can't be set within 10 minutes), and a golden snapshot's source host gets its guest back (`T2.GOLDEN.SOURCE`). T1's monitoring plugin gets the SQL IaaS Agent service restarted when it isn't running (`START.T1.MONITORING`).
4. **T3** resumes (`-SkipT3` leaves it alone); after `stop-demo.ps1 -RemoveT3`, it's recreated under the same names and set up from T1, a **Warning** until its readiness gate passes.
5. **T4** starts (`START.T4.START`; `-SkipT4` leaves it stopped), after a stopped replica (`START.T4.REPLICA.START`); then its read replica is created within the warm-up, about 9 minutes (`START.T4.REPLICA`, `START.T4.REPLICA.FALLBACK`; a **Warning** when it fails; `-SkipT4Replica` leaves it out).
6. **T5's container** is created again with your own rights (`START.T5`, `START.T5.CONTAINER`, about a minute), and Ask's relay is woken (`ASK.RELAY.HEALTH`).
7. **The profiles:** `-ActivityProfile`, or `activityProfile` (`business-day` by default), on every target until the next auto-shutdown, as `baseline` first when it has incidents (`START.PROFILE_*`), switched once the start's own Run Commands are done (`START.INCIDENTS_*`, within 3 minutes; with `-Interactive -ResetAdminPassword`, after the password). Finished `DbHubControl-*` Run Commands are deleted (`START.CONTROL.RUNCOMMANDS`), since a VM allows 25 ([Run Command overview](https://learn.microsoft.com/azure/virtual-machines/run-command-overview)). The console's `Activity:` line says what runs and how to choose `baseline`, and a configuration without `activityProfile` gets one notice (`START.ACTIVITYPROFILE`).
8. **The warm-up:** `-WarmUpMinutes` runs it in the background (`START.WARMUP`); `-WaitForWarmUp` waits, then checks telemetry.
9. **The capacity, opt-in** (`fabric.manageCapacity`; `START.FABRIC.CAPACITY`, **Not selected** by default): a **Paused** F capacity that's yours alone, in the subscription and named in `fabric.capacityName`, is resumed ([Fabric Capacities - Resume](https://learn.microsoft.com/rest/api/microsoftfabric/fabric-capacities/resume)) and recorded (`DbHubFabricCapacityResumed`, `DbHubFabricCapacityResumedUtc`), so the stop pauses only that; a Trial, or another subscription's, is **Not supported**. Contributor on it is enough; it bills outside the ceilings.

### Stop: `stop-demo.ps1`

```powershell
./scripts/stop-demo.ps1               # Bastion, the password, profiles off, T4's read replica, the guest, both VMs, T4, then T5's container
./scripts/stop-demo.ps1 -SaveHistory  # the same, with the session's history saved to the lakehouse before T5's container goes
./scripts/stop-demo.ps1 -ParkT2       # only the T2 side; T1, T3, T4, and T5 keep running for agent-focused demos
./scripts/stop-demo.ps1 -RemoveT3     # also delete T3; start-demo.ps1 recreates it under the same names
```

1. **Bastion** and its public IP go, and the T2 host's one-time password is rotated ([Bastion](#bastion-and-the-one-time-host-password)); `-RemoveBastionOnly` does only this, and with `-IfExpired` only after Bastion's expiry.
2. **Every profile goes off,** both VMs at once, within about 3 minutes (a **Warning** after that; the deallocation stops the incident). T3 stays, and auto-pauses `t3AutoPauseMinutes` after its last session.
3. **T4's read replica** is deleted while the VMs deallocate (about 100 seconds; `STOP.T4.REPLICA`); with `-SaveHistory`, its and T4's metrics are read first, since Azure Monitor has none for a deleted replica (`STOP.T4.HISTORY`).
4. **The Incident RCA's evidence** (`-SaveHistory` or `fabric.saveHistoryOnStop`, 2026-11-20): the runners' export on the VMs, through managed Run Commands that only read, at most 8 minutes, one at a time on the T2 host (`STOP.RCA.EXPORT`, and `STOP.RCA.CAPTURE.<target>` for what the observer captured, with its gaps); the history in step 7 takes it ([the history](../fabric/README.md#the-incident-rcas-evidence-in-the-history-2026-11-20)). Without a save, nothing is exported: it stays on the VMs for the next export.
5. **T2's guest shuts down** (`STOP.GUEST`, a **Warning** when it doesn't in time, and the host's deallocation shuts it down), and **both VMs are deallocated.**
6. **T4 stops** (`STOP.T4.STOP`), with the date Azure starts it again, seven days later ([stop a server](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server)), what it then bills, and what stops it again: the nightly safety stop, or else the control's `dbhub-t4-safety-stop`; with neither, run `stop-demo.ps1` again once it has started. A pending auto-stop goes too, a Run all session's or a `start-demo.ps1` session's (`STOP.CONTROL.AUTOSTOP` says whose).
7. **The history** (`-SaveHistory` or `fabric.saveHistoryOnStop`; `STOP.FABRIC.SAVEHISTORY`; not with `-ParkT2`): `NB_DatabaseHub_LiveActivity` over the last `-SaveHistoryWindowMinutes` (720), at most 15 minutes, with T4's metrics as `POSTGRES_METRICS`, so the lag curve reaches the report and the app, and the RCA evidence staged as `RCA_EVIDENCE_FILE`. After a Run all session's handoff (below), it's saved without that session's RCA evidence, which the control's stop keeps in the control vault, and `STOP.FABRIC.SAVEHISTORY` says so. A capacity that isn't running is **Manual action required**, and the metrics wait in `out/history-pending` (`STOP.T4.HISTORY.PENDING`) for `./scripts/configure-fabric.ps1 -SkipHubChecks -SkipNotebookImport -RunLiveActivity -PostgresMetricsPath <file>`; the RCA documents the run didn't take are listed there too, by ID, and the next history save fetches them again from the VMs (`STOP.RCA.PENDING`).
8. **The capacity the demo resumed** is paused (`STOP.FABRIC.CAPACITY`; [Suspend](https://learn.microsoft.com/rest/api/microsoftfabric/fabric-capacities/suspend)); with the default, a leftover record is a **Warning**.
9. **Last, T5's container** is deleted (`STOP.T5`), so its 400 RU/s stop billing; the account and its private endpoint stay. While the control can't create it again, it's kept, with the Owner's command.

**During a Run all session** (since 2026-11-22), the session's stop goes to the session control, as Stop now's does: after step 1, `stop-demo.ps1` starts the control's `DbHub-Stop` job and waits for it, at most 40 minutes, after up to 12 for the host password's Run Command and up to 10, twice, for a job of the control's that's already running (`STOP.CONTROL.SESSION`, and `STOP.CONTROL.HOSTPASSWORD` when the T2 host's delete of that Run Command outlasts its wait). Right before the job, the session's auto-stop and its backup go (`STOP.CONTROL.AUTOSTOP`), and the control's jobs are read again, so the auto-stop can't start a second stop beside it, and a Stop now that starts anyway waits for it and stops only what's left. That job marks the stop begun, so a re-check's export of the session's evidence is kept apart from the stop's (by runbooks that `./scripts/deploy.ps1` published on 2026-11-22 or later), exports it, saves the session's metrics, deletes T4's read replica, stops T4, deallocates the VMs, deletes T5's container, and records the session's stop, whose lines come after it (`STOP.RCA.*`). The profiles aren't set off and T2's guest isn't shut down first: the VMs' deallocation ends both, as with Stop now. Before it, the Database Agent beat's hold on T3 is released, and with `-SaveHistory` T4's and the replica's metrics are read; after it, steps 5 to 9 confirm what it stopped and do the rest, except that step 7 saves the history without the session's Incident RCA evidence: the control's stop kept it in the control vault, and the next Run all that starts a session within 7 days saves it, or Run all's own save at the session's planned end does, if the capacity stays on. After 7 days, it stays in the vault, and nothing saves it. To have it in the history at once, stop a Run all session with Stop now in `NB_DatabaseHub_Control` instead. When the control can't take it, the stop goes on as above, with a **Warning** that says why; while a stop job of the control's still runs, nothing is stopped under it ([troubleshooting](troubleshooting.md#the-on-demand-activity-control)).

### Status: `status.ps1`

`./scripts/status.ps1` is read-only: each VM (`STATUS.VM_<VM>`) and its disks against the profile (`STATUS.DISKS`); the demo's leftover Run Commands (`STATUS.RUNCOMMANDS`, a **Warning** that names each `DbHubControl-*` one, and each `DbHubDemo-*` one but `DbHubDemo-Bootstrap` and `DbHubDemo-Profile`, with its `az vm run-command delete` command); T1's unified inventory (`T1.SQLVM.ASSOCIATEDSERVICES`, a **Warning** while Analysis Services or Integration Services are listed) and its monitoring; T3 (`STATUS.T3`); T4 (`STATUS.T4`: its live metrics, or, when it's stopped, when Azure starts it again, what it then bills, and what stops it), its fallback size and hourly price (`STATUS.T4.SIZE`), and its replica's lag (`STATUS.T4.REPLICA`); T5, and whether its container is there and bills (`STATUS.T5`); each target's profile (`STATUS.PROFILE_*`); T2's Arc connection (`T2.ARC.CONNECTED`, `T2.ARC.DISCONNECTEDDAYS`), its free disk space (`STATUS.T2.DISKSPACE`, a **Warning** below 20 GiB), its Jumpstart image (`STATUS.T2.IMAGE`, a **Warning** for one newer than the tested one), a golden snapshot's days (`STATUS.T2.GOLDEN`), and an automatic sign-in left armed (`STATUS.T2.AUTOSIGNIN`); Bastion with its hourly price (`STATUS.BASTION`) and a stored host password past its expiry (`STATUS.KEYVAULT`); the month-to-date cost (`STATUS.COST`), the next auto-shutdown (`STATUS.SHUTDOWN`) or a moved one (`STATUS.NIGHTLYSTOP`), the nightly safety stop (`STATUS.SAFETYSTOP`), the session control (`STATUS.CONTROL`), and the expiry tag; and, with `fabric.manageCapacity` or a leftover `DbHubFabricCapacityResumed` record, the capacity (`STATUS.FABRIC.CAPACITY`). `-Detail` adds the full health, T2's profile, and T4's live view from T1 (`STATUS.T4.LIVE`: connections against `max_connections`, sessions, blockers, the oldest transaction), each a Run Command of 30 to 60 seconds. `-Watch` follows a running `deploy.ps1`.

### Reset: `reset-demo.ps1`

`./scripts/reset-demo.ps1 [-Target T1] [-Reseed] [-UndoRemediation]` runs the runner's `reset` on each target: it stops every scenario and profile, kills leftover `ContosoCare.Demo/` sessions, checks that no demo transaction is open, empties the scratch tables, and sets the profile to `off` (unless `-KeepProfile`). Resetting T3 resumes a paused database. `-RebuildGuest` is **Not supported** for now: run `./scripts/destroy.ps1 -KeepFabric`, then `./scripts/deploy.ps1`.

### Destroy: `destroy.ps1`

`./scripts/destroy.ps1` deletes everything `deploy.ps1` created for this environment, each part only when it can tell it's this environment's, after it lists what it deletes and keeps and you confirm (`-Force` doesn't ask); it takes about 20 minutes, and a rerun finishes what a stopped one left. [Delete everything](../README.md#delete-everything) has the order and what stays, and [cleanup](cleanup.md) the residual check and partial failures. Never destroy an environment someone else uses without their go-ahead.

- **Switches:** `-KeepFabric` keeps the Fabric workspaces with their history; `-IncludeGolden` also deletes `rg-<prefix>-golden`; `-IfExpired` (the optional expiry workflow) does nothing until the day after the group's `expiresOn` tag; `-ResidueOnly` repeats the residual check, read-only, from `out/destroy-manifest-<environment>.json`; `-SkipResidueCheck` and `-ResidueWaitMinutes` control that check (`TEARDOWN.RESIDUAL.*`, `DESTROY.RESIDUAL`; [teardown tests](../tests/teardown/README.md)).
- **Results:** a `DESTROY.*` result per part. Without Owner or User Access Administrator, `DESTROY.CONTROL.ROLES` is **Manual action required** (the summary `DESTROY.CONTROL` a **Warning**), and the rest still goes; with `fabric.manageCapacity`, the capacity the demo resumed is paused (`DESTROY.FABRIC.CAPACITY`, a **Warning** when it can't be).
- **What stays:** the Fabric capacity and licenses; `rg-<prefix>-golden` until `-IncludeGolden`; a group you supplied; your tenant's own role assignments; resource provider registrations; what another environment uses; and each viewer's GitHub authorization of **Database Hub Insights Ask**, until they revoke it at <https://github.com/settings/applications> (**Authorized OAuth Apps**), and a browser's sign-in, which **Sign out of GitHub** in the chat's account menu clears.

## One command: `deploy.ps1`

### The stages

`deploy.ps1` runs Preflight, then Infrastructure while four [parallel tracks](#parallel-tracks-phase-20) start (T1 with T3 and T5, T2, T4, and Fabric), then the validation, and last the history report's snapshot. The tracks do the stages' work, which `-Sequential` runs one stage after another. Each stage is idempotent, so a rerun converges.

| Stage | What it does | A Fail here |
|---|---|---|
| Preflight | The subscription guard, P1–P6 (`PREFLIGHT.P2.PROVIDERS` registers missing providers; `PREFLIGHT.P3.QUOTA`), the region, sizes, policy, and the cost against both ceilings (`PREFLIGHT.COST.*`); it resolves the network mode, T3's free offer, and the P6 group | Stops before anything is deployed |
| Infrastructure | `azuredeploy.json` at subscription scope, again with regular serverless when Azure rejects T3's free offer (`T3.FREEOFFER`, a **Warning**); the opt-in [Key Vault](#opt-in-the-password-in-key-vault-instead-of-the-clipboard); then, beside the tracks, the [nightly safety stop](#the-nightly-safety-stop) and the [session control](#the-session-control) | Stops (not for the vault, the safety stop, or the control) |
| Artifacts | The bootstrap bundle and the workload runner, sent to each VM in Run Command chunks unless it has them | Stops |
| Bootstraps | The template again with both hashes and chunk counts, which runs the loaders; then T1 Ready | Stops |
| T3 | T1 into the T3 administrators group (P6); T3's setup and runner from T1; its checks | Stops |
| T4 | T5's container when it's missing (`DEPLOY.T5.CONTAINER`), its checks (`T5.*`), and T1's access (`WORKLOAD.T5.WARMUP`); T4's checks (`T4.*`), its restart when `max_connections` waits (`DEPLOY.T4.RESTART`), its setup from T1 (`WORKLOAD.T4.ENABLE`), its metrics, and its read replica | Reported, and **DONE** waits for it |
| Activity | `activityProfile` on T1, T3, T4, and T5 until the next auto-shutdown, as `baseline` until after **DONE**'s checks (`DEPLOY.INCIDENTS_*`) | Never: a **Warning** |
| Monitoring | T1's performance monitoring, as `configure-monitoring.ps1 -Target T1` | Stops |
| T2 | `configure-arc.ps1`: Arc onboarding, PAYG, monitoring, and the migration assessment; then T2's profile | Stops |
| Fabric | `configure-fabric.ps1` (the workspace, lakehouse, missing notebooks, all of them with `-ImportNotebooks` or `fabric.importNotebooks`, the Real-Time Dashboard, and the presenters as Viewers), `configure-powerbi.ps1` (the history model and report), `configure-fabric-app.ps1` (the Insights app and Ask); then the control's notebook | Stops; the app's step never does |
| Validation | Telemetry, the runner, and the summary; **DONE**'s checks, the profile switch, the [history snapshot](#the-history-reports-snapshot-at-the-end-2026-11-06), and the replica's delete (`DEPLOY.T4.REPLICA.END`) | Reported; the snapshot is never a **Fail** |

### Options

| Option | Use |
|---|---|
| No option | Continues an unfinished deployment where it stopped; after **DONE**, starts over, template included |
| `-Resume` | Not needed. After **DONE**, the validation only, unless the bundle or the runner changed: then those VMs' tracks from their Artifacts step, without the template |
| `-FromStage <stage>`, `-StopAfter <stage>` | A range of stages: Preflight, Infrastructure, Artifacts, Bootstraps, T3, T4, Activity, Monitoring, T2, Fabric, or Validation. `-FromStage Infrastructure` skips preflight; `-FromStage Artifacts` sends the runner and its T-SQL without the template; `-FromStage T4` sets T4 and T5 up again. `-StopAfter Infrastructure` deploys the template, as the optional Deploy to Azure button does, plus the nightly safety stop and the session control |
| `-WhatIf` | The read-only preflight (no provider registration) and the template's what-if; nothing is recorded |
| `-SkipRunner` | No workload runner and no .NET SDK; the profiles are **Not selected** |
| `-SkipFabric`, `-ImportNotebooks` | No Fabric stage and no history snapshot (**Not selected**); or also update the notebooks already there, as `fabric.importNotebooks` does ([configuration](configuration.md#fabric)) |
| `-T1WaitMinutes`, `-T2WaitMinutes`, `-MonitoringWaitMinutes`, `-TelemetryWaitMinutes` | 45, 180, 20, and 15 by default. `-T2WaitMinutes` covers the build modes' guest build (60 to 90 minutes). `-MonitoringWaitMinutes` is elapsed time; a T1 plugin that reports `NotRunning` gets 3 minutes of it (5 when the run merged the flag) before the SQL IaaS Agent service is restarted |
| `-Sequential` | The stages one after another, judged by the same **DONE** requirements, with the Insights app and the history snapshot |
| `-NoWaitForT2`, `-WaitForT2` | Don't wait for T2's guest build (`DEPLOY.T2.BACKGROUND`, **Manual action required**: a later `./scripts/deploy.ps1` finishes it); or wait in GitHub Actions and other CI too, as elsewhere |
| `-NoStatusPage`, `-NoBrowser` | No progress model or status page; or the page without opening a browser |
| `-PolicyCacheHours`, `-SkipPolicyInventory` | Reuse preflight's last complete policy inventory while the assignments are unchanged and it's at most this old (168 by default; `0` reads every definition, 7 to 13 minutes); or skip it, and `networkMode` `auto` resolves to `private` |
| `-ConfigPath`, `-OutputPath` | Another configuration (`config/demo.config.json` by default, which the first run writes), and another results file (`out/deploy.jsonl`) |
| `-TreatManualAsError` | In GitHub Actions: exit code 2 for **Manual action required** |
| `-NoSelfUpdate` | No check or update from GitHub's `main` (`DBHUB_NO_SELF_UPDATE=1` does the same) |

### State, results, and exit codes

- **Manual steps are never hidden:** **Manual action required** doesn't stop the run; the stage stays open, later stages still run, and `DEPLOY.SUMMARY` lists each item with its steps. Fix it, then run `./scripts/deploy.ps1` again.
- **State lives in the resource group's tags** (`DbHub*`: the last stage, each track's last step, the bundle's and runner's hashes and the VMs that have them, the network mode, the free-offer decision, the P6 group, T4's fallback size, and more), so a rerun works from any machine and from GitHub Actions; the recorded stage never passes an open one.
- **Results** go to the console, `out/deploy.jsonl` (one [ADR 0012](adr/0012-validation-model.md) result per line), and GitHub Actions' job summary; the console's transcript to `out/logs/deploy-<time>.log`. `DEPLOY.TIMING` records each track's steps and each target's ready time. Deployment success alone is never **Pass**.
- **Exit codes:** 0 for **DONE**, 1 for **NOT DONE** with a **Fail**, 2 for **NOT DONE** otherwise; `-WhatIf` returns 0 unless a check failed. In GitHub Actions: 0 when nothing failed, 1 for any **Fail**, 2 for **Manual action required** with `-TreatManualAsError`.

### Updates from GitHub (2026-11-09)

Before anything else, `deploy.ps1` fetches origin's `main` (`git fetch`, at most 20 seconds, never a credential prompt), with the `git` on `PATH` or one where Git is usually installed. It updates only a git checkout on `main`, tracking `origin/main`, with no tracked file modified or staged (`config/` and `out/` are Git-ignored, so your configuration doesn't count), and behind `origin/main`: `git merge --ff-only` ([git merge](https://git-scm.com/docs/git-merge#Documentation/git-merge.txt---ff-only)), one line from which commit to which, then a fresh `pwsh` with the same parameters and that run's exit code (`DEPLOY.SELFUPDATE`, **Pass**; the restarted run carries `DBHUB_SELF_UPDATED`). A resumed run then sends what changed to the VMs, so one command updates both.

- **When it doesn't update,** `DEPLOY.SELFUPDATE` is a **Warning** with the reason and the exact command, and the run goes on with the code it has ([each case](troubleshooting.md#deployps1s-update-from-github-deployselfupdate-2026-11-09)). A checkout that has everything on GitHub's `main` already is a **Pass**, on any branch.
- **Opting out:** `-NoSelfUpdate`, or `DBHUB_NO_SELF_UPDATE=1` (`true` too; `0` doesn't opt out); CI (`GITHUB_ACTIONS`, `CI`, or `TF_BUILD`) skips the check. Both are **Not selected**.
- **Your own copy,** made with **Use this template** or a fork, fetches its own `main`, not this repository's fixes; bring those in with your own `git pull` from this repository.

### First run: `init.ps1`

`init.ps1` ([ADR 0023](adr/0023-first-run-automation.md)) writes `config/demo.config.json` from your sign-in, so a first run needs no IDs looked up by hand; `deploy.ps1` runs the same steps when there's no configuration, with `-CreateAdminGroup` (and `-NonInteractive` without keyboard input). You can also copy `config/demo.config.example.json` and fill it in; `Get-DemoConfig` checks it against `config/environment.schema.json`.

1. **Your subscription:** `az account list` ([az account list](https://learn.microsoft.com/cli/azure/account#az-account-list)), local and read-only, the one Azure CLI call before the subscription guard; it asks when there's more than one (or takes `-SubscriptionId`), never runs `az account set`, and without a sign-in is **Manual action required** with the `az login` command. Then the guard, and Microsoft Graph's [`/me`](https://learn.microsoft.com/graph/api/user-get) for the budget alerts' address (`ownerEmail`) and the owner tag.
2. **An environment that exists already** (`INIT.EXISTING`, [#60](https://github.com/MarcBushong/fabric-database-hub-demo/issues/60)): `rg-<prefix>-<environment>`, `rg-<prefix>-control`, `rg-<prefix>-golden`, or the record `<prefix>-<environment>-main` ([az deployment sub list](https://learn.microsoft.com/cli/azure/deployment/sub#az-deployment-sub-list)). When it's yours (its record's `ownerEmail` or an `owner` tag is your address, or you own the group that administers its T3 and T4: [List group owners](https://learn.microsoft.com/graph/api/group-list-owners)), the configuration comes from what's deployed, so the update changes nothing you didn't ask for (**Warning**): its last deployment's parameters ([az deployment sub show](https://learn.microsoft.com/cli/azure/deployment/sub#az-deployment-sub-show)), its group, the workspaces it records (`DbHubFabricWorkspaceId`, `DbHubControlWorkspaceId`; `fabric.importNotebooks` true for the demo's own), and its control's `control.roleNameSuffix`. What Azure doesn't record (`sessionCeilingUsd`, `activityProfile`, `t3FreeOffer`, `t2Source`, `bastionMaxHours`, `presenterObjectIds`, `keyVault`, and some control and `fabric` settings) keeps its default, which the message lists; what you pass, such as `-Location`, `-TimeZone`, `-OwnerEmail`, or `-WorkspaceName`, wins; and a recovered environment with another prefix that records no workspace is **Manual action required** with `-Prefix`, until `-WorkspaceName` names its workspace. When it isn't yours, or that can't be told, nothing is written for it: with `-Prefix`, **Manual action required** (`-OwnerEmail` with the budget address it records claims it), and without, a new environment (**Warning**), the first of `<prefix>2` to `<prefix>99` that's yours or free, with its own group and workspace. A read that fails is a **Fail**; with none of it, a new environment (**Pass**).
3. **P1** (`INIT.P1.CONTRIBUTOR`): without Contributor, **Manual action required** with the Owner's `az role assignment create` command.
4. **Fabric** (`INIT.FABRIC.CAPACITY`, `INIT.FABRIC.WORKSPACE`): the F, Trial, and P capacities you can assign ([List Capacities](https://learn.microsoft.com/rest/api/fabric/core/capacities/list-capacities); not Premium Per User), asking when there's more than one, and the workspace ([List Workspaces](https://learn.microsoft.com/rest/api/fabric/core/workspaces/list-workspaces)). **Each environment has its own workspace:** `fabric.workspaceName` is "Database Hub Demo" for the default prefix, and "Database Hub Demo `<prefix>`" for a new environment with any other prefix, whether `-Prefix` named it (`./scripts/init.ps1 -Prefix <prefix> -CreateAdminGroup`) or the run picked it, unless `-WorkspaceName` names another. A workspace that exists is checked against what the other demo environments record, in one Azure Resource Graph query across the subscriptions you can read ([query scope](https://learn.microsoft.com/azure/governance/resource-graph/concepts/query-language#query-scope)): a default name gives way to the environment's own (a **Warning**, and a line on `deploy.ps1`'s start banner and status page), a `-WorkspaceName` that names another environment's is **Manual action required**, and an environment's own workspace that another records too stays, as a **Warning**. `deploy.ps1`'s preflight then stops before it creates anything when the configuration names a workspace that another environment records and this one doesn't, a hand-edited file included (`DEPLOY.FABRIC.SHARED`, a **Fail** with the fix). A new workspace gets `fabric.importNotebooks` true; an existing one false, so only missing notebooks are added. Nothing is created in Fabric here; a paused capacity is a **Warning**.
5. **P6** (`INIT.P6.GROUP`): the group `-AdminGroupObjectId`, or the one named `-AdminGroupName` (`<prefix>-<environment>-sql-admins` by default); `-CreateAdminGroup` creates a missing one with you as its owner ([Create group](https://learn.microsoft.com/graph/api/group-post-groups), [Add owners](https://learn.microsoft.com/graph/api/group-post-owners)). Where only administrators may create groups ([self-service group management](https://learn.microsoft.com/entra/identity/users/groups-self-service-management)), **Manual action required** with their steps, and a placeholder until `init.ps1 -Force -AdminGroupObjectId <id>`.
6. **T2's mode,** without a question: `-T2SqlInstallMode` (`JumpstartImage` or `Developer`), else `JumpstartImage`; `ProductKey` is set in the file; a recovered environment keeps its own.
7. **The file** (`INIT.CONFIG`), validated against the schema: a path Git would commit is refused (**Fail**), and an existing file is replaced only with `-Force`, after a copy to `out/config-backup`; without `-Prefix`, the new one keeps the prefix and environment the old one holds, never the example's `dbhub`, and `INIT.CONFIG` says so (since 2026-11-19), while another `-Prefix` still wins. `fabric.manageCapacity` stays false unless `-ManageCapacity`, and the auto-shutdown time zone is this machine's unless `-TimeZone`. Then the exact next commands: they, and every fix, name this run's `-ConfigPath` when you wrote another file and its `-Prefix` when it isn't the default (since 2026-11-19), so following one never writes or deploys the default prefix's configuration.

`-WhatIf` reads everything and writes nothing; `-NonInteractive` never asks, and neither does a terminal that can't take input: an ambiguous choice is **Manual action required** with the parameter to pass, or a terminal that can take input. From `deploy.ps1`, a step that needs a person stops the run before anything is created, **NOT DONE** with its fix. `deploy.ps1` has no `-Prefix`: for another prefix, run `./scripts/init.ps1 -Prefix <prefix> -CreateAdminGroup` first.

### One command, one guided stop (Phase 28)

How a run behaves. No mode stops for a person any more ([the guided stop](#the-guided-stop-paygwizard) is retired).

- **At the start,** it writes a missing configuration, keeps a Windows PC and its display awake until it ends ([SetThreadExecutionState](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate); not on macOS or Linux, and not through a lid close), opens the status page, and starts what's stopped before preflight: a deallocated `sqlvm01` or `archost01` ([az vm start](https://learn.microsoft.com/cli/azure/vm#az-vm-start)) and a stopped T4 ([Servers - Start](https://learn.microsoft.com/rest/api/postgresql/flexibleserver/servers/start)) (`DEPLOY.VMSTART`; one that doesn't start is **NOT DONE**), with the interim `baseline` on a VM it starts (`DEPLOY.INTERIM_*`).
- **T1's monitoring plugin,** every run: beside the tracks, a run with no T1 Monitoring step restarts the SQL IaaS Agent service when the plugin isn't running (`DEPLOY.T1.MONITORING`); telemetry that hasn't come gets its target's monitoring checked once, then up to `-TelemetryWaitMinutes` more.
- **It waits for T2** without a golden snapshot, up to `-T2WaitMinutes` (180), printing the host's build phase; a time-out is **NOT DONE**, and the next run waits on.
- **A plain rerun continues** from the state tags, as `-Resume` does, trusting only this deployment's records (`DbHubTrackT1`, `DbHubTrackT2`, `DbHubTrackT4`, `DbHubTrackFabric`, cleared when a run starts over). A fix you pulled reaches the VMs: a VM whose bundle or runner differs from this checkout's (`DbHubBundleSha256`, `DbHubRunnerSha256`) goes back to its Artifacts step (`DEPLOY.ARTIFACTS.CHANGED_<VM>`; a failed build is the **Warning** `DEPLOY.ARTIFACTS.CHANGED`), and its loader stops the old run ([ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md#amendment-a-changed-bundle-takes-over-from-a-run-thats-still-going-2026-11-06)); with `-Sequential`, use `-FromStage Artifacts`.
- **A resume still lists what the earlier run found** (since 2026-11-19, the final tests' F10): a run whose T1 track an earlier run finished still lists `HUB.AGENT.T3`, and each run's ending saves what a resume skips in `out/deploy-carry-<resource group>.json` (Git-ignored, this PC only): the Insights app's and Ask's results, the Hub tenant setting's, the presenters', the Fabric capacity's, and the history report's data check. The next run of the same deployment shows those it didn't check again, under **Please confirm**, in what didn't work, and in **DONE**'s mention of the Insights app, with one line that says from which run ("From the earlier run at 10:12 (Pacific Standard Time), since this run didn't check them again: ..."). A result the run made itself always wins, an earlier one never changes whether the run is **DONE**, and `DEPLOY.CARRIED` lists what was shown. After `./scripts/configure-fabric-app.ps1` runs on its own, the app's earlier state isn't shown; deleting the file only loses those earlier results.
- **Network errors are retried:** calls to Fabric, Power BI, Azure Resource Manager, and Microsoft Graph get up to 4 attempts after a network error or HTTP 408, 429, 502, 503, or 504 ([transient faults](https://learn.microsoft.com/azure/architecture/best-practices/transient-faults), [Fabric throttling](https://learn.microsoft.com/rest/api/fabric/articles/throttling)), and one that creates something only when it never arrived, or on 429.
- **Ctrl+C stops it within seconds** ([Console.CancelKeyPress](https://learn.microsoft.com/dotnet/api/system.console.cancelkeypress)): its tracks' processes end after about 3 seconds ([Process.Kill](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.kill)), slow cleanups are left to the next run or `./scripts/stop-demo.ps1`, and it ends **Stopped, not done**, with PowerShell's exit code.
- **One banner ends it:** **DONE**, or **NOT DONE** with why, the next action, the exact command (every command it names keeps your `-ConfigPath`), and `./scripts/collect-diagnostics.ps1`. **DONE** never comes while an earlier guided stop's cleanup is open: the T2 step finishes it (`DEPLOY.T2.GUIDEDLEFTOVER`), or **NOT DONE** names `./scripts/stop-demo.ps1 -RemoveBastionOnly`. It doesn't suggest a golden snapshot, which bills every month, also after `destroy.ps1` ([the T2 golden snapshot](#the-t2-golden-snapshot-capture-t2-goldenps1-and-test-t2-goldenps1)).

### The live status page and `status.ps1 -Watch`

`deploy.ps1` and its tracks write `out/deploy-progress.json`, and `deploy.ps1` renders `out/deploy-status.html` from it at least every 15 seconds (both Git-ignored): the banner (**Deploying, no action needed**, **Done**, or **Stopped, not done**, also once the model stops changing for 3 minutes), then each track's steps, **Pending**, **Running**, **Done**, **Action needed**, **Failed**, or **Skipped** ([ADR 0012](adr/0012-validation-model.md)), with a time and a one-line message, and a red **Needs attention** box for what didn't work but doesn't block **DONE**. It warns when nothing changed for 20 minutes, refreshes itself, and has no JavaScript, external resources, or secrets. `./scripts/status.ps1 -Watch` shows the same in a console (`-IntervalSeconds`), or, without a local model, what `status.ps1` reads from Azure.

### Parallel tracks (Phase 20)

The tracks start right after Preflight, each in its own process with its own subscription guard, and wait for the template's result ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)); the bundle and the runner are built during Preflight.

| Track | Steps, in order | Ready when |
|---|---|---|
| T1 (with T3 and T5) | T3Setup (T1 joins the T3 group during the template and sets T3 up first), Artifacts (bundle and runner in one wave), Bootstraps (with T1's monitoring flag merged), T3, T4, T5, Activity, Monitoring, Telemetry | `TELEMETRY.T1` and `TELEMETRY.T3` |
| T2 | Restore (a golden host, once the template has deployed `archost01`, with its artifacts sent during the Release), Artifacts, Bootstraps, T2 (`configure-arc.ps1`, with `-Force` for a golden host, then the host's verdict, `DEPLOY.T2.READY`), Telemetry | `T2.ARC.SQLINSTANCE`, `T2.ARC.MONITORING`, then `TELEMETRY.T2` |
| T4 | Server (its checks), Replica (after T1's restart for `max_connections`), Telemetry | `METRICS.T4`, `HUB.ESTATE.T4.REPLICA`, and `METRICS.T4.REPLICA` |
| Fabric | `configure-fabric.ps1`, `configure-powerbi.ps1`, then `configure-fabric-app.ps1`, which never fails the track | The notebooks, the dashboard, the model, and the report |

- **Without a snapshot,** the T2 track builds the guest, and `deploy.ps1` waits for it; with `-NoWaitForT2`, or in CI without `-WaitForT2`, it returns once the rest is ready (`DEPLOY.T2.BACKGROUND`).
- **The validation** checks the Hub Estate, T1's unified inventory (a **Fail** while Analysis Services or Integration Services are still listed after 10 minutes), the runner, T3's readiness gate, and the dashboard's tiles.
- **The policy inventory:** with `networkMode` `private`, a background job runs it beside the tracks (its checks **Not selected** until then, a **Warning** if it doesn't finish), and the template's what-if still runs first. With `auto`, the default, it runs first, since it decides whether T3 goes private; with `public` too, so `PREFLIGHT.POLICY.SQLPUBLIC` can stop a run before T3 is created public and then cut off by a policy.

### Faster redeploy (Phase 22)

A redeploy that restores T2 from a [golden snapshot](#the-t2-golden-snapshot-capture-t2-goldenps1-and-test-t2-goldenps1) overlaps more ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md#amendments-2026-10-23-phase-22-the-follow-up-overlaps)): the tracks' guards run during the template, T2's Restore starts once `archost01` exists, with its artifacts sent during the Release, T1's bundle and runner go in one wave of 8 chunks, and T3 is set up first. T2 stays the critical path, because the SQL Server extension's download in its guest can take 30 minutes or more, with no documented fix; [how long each step takes](#how-long-each-step-takes) has the measured redeploys, and the [implementation report](implementation-report.md#phase-22-faster-redeploy-the-follow-up-overlaps-and-one-timed-destroy-and-redeploy) the rest.

`t2SqlInstallMode` is `JumpstartImage` by default, and nobody is asked. To choose another, set it in `config/demo.config.json` before the first deployment (`./scripts/init.ps1 -T2SqlInstallMode Developer` writes `Developer`); an existing guest keeps its mode.

| Mode | What you do | What T2 gives in Database Hub |
|---|---|---|
| `JumpstartImage` (default) | Nothing: no product key, no Bastion, no sign-in beyond `az login`; needs `t2Mode` `Nested`, the default (below) | Estate and Performance, pay-as-you-go through Azure |

#### T2 from Arc Jumpstart's image (`JumpstartImage`)

T2's guest is [Arc Jumpstart](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/azure_jumpstart_arcbox/ITPro/_index.md) ArcBox's prebuilt SQL Server 2022 Standard disk, used as ArcBox's [logon script](https://github.com/microsoft/azure_arc/blob/e2c114eed98d18105dcf3a718bef965d5112781b/azure_jumpstart_arcbox/artifacts/ArcServersLogonScript.ps1) does; there's no guided stop and no `DEPLOY.T2.GUIDEDSTOP`. Jumpstart's environments are "intended for evaluation, training, and demo purposes only and are not supported for production use cases" ([Jumpstart FAQ](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/FAQ/_index.md)), which is this demo's use.

### T4 in the deployment

T4, the PostgreSQL flexible server `pgflex01-<deploymentId>` ([ADR 0019](adr/0019-t4-postgresql-flexible-server.md)), is in every deployment. A stopped T4 is started before the template (`DEPLOY.T4.START`), after a replica a session left stopped (`DEPLOY.T4.REPLICA.START`), since Azure starts T4 only after its replicas. Its track reports `T4.SERVER`, `T4.CONFIG`, `T4.ENTRAONLY`, `T4.NETWORK`, `T4.ADMIN`, `T4.DATABASE`, `T4.ENHANCEDMETRICS`, and `T4.MAXCONNECTIONS`, then its replica and `METRICS.T4`; the validation adds `HUB.ESTATE.T4`. T1's `T4` step (`WORKLOAD.T4.ENABLE`) has T1's managed identity, a P6 member, create the runner's role and the schema and add T4 to the activity host; `./scripts/deploy.ps1 -FromStage T4` runs it again. `max_connections` is 50 on every size, so `connection-surge` fills **Failed connections**; it's static ([server parameters](https://learn.microsoft.com/azure/postgresql/server-parameters/param-connections-authentication-connection-settings)), so when it changes, T1's step restarts T4's engine ([Servers - Restart](https://learn.microsoft.com/rest/api/postgresql/servers/restart)) and waits up to 10 minutes (`DEPLOY.T4.RESTART`).

#### T4's size: the 4-vCore default and its fallback (2026-11-04)

T4's default is General Purpose `Standard_D4ds_v5` (4 vCores, 16 GiB) with autonomous tuning, which needs "at least 4 vCores" ([autonomous tuning](https://learn.microsoft.com/azure/postgresql/monitor/concepts-autonomous-tuning)) and Query Store, which shouldn't run on Burstable ([Query Store](https://learn.microsoft.com/azure/postgresql/monitor/concepts-query-store)). `t4SkuName` sets another, such as the cheaper Burstable `Standard_B1ms` or `Standard_B2s`; `t4AvailabilityZone` (empty, `1`, `2`, or `3`) applies at creation only.

- **Tuning:** on, the template sets `pg_qs.query_capture_mode` `TOP`, `pg_qs.parameters_capture_mode` `capture_first_sample`, `index_tuning.analysis_interval` 60, and `index_tuning.mode` `REPORT`, all dynamic ([parameters](https://learn.microsoft.com/azure/postgresql/parameters/parameters-autonomous-tuning)); a Burstable T4 gets capture mode `NONE`. `t4AutonomousTuning` unset means on where the size allows it; a smaller size turns it off with a **Warning** (`PREFLIGHT.T4.TUNING`), and `true` with one is a **Fail**, also without preflight (`DEPLOY.T4.TUNING`).
- **When Azure refuses the size** (`SkuNotAvailable`; [capacity errors](https://learn.microsoft.com/azure/postgresql/troubleshoot/how-to-resolve-capacity-errors)): another zone, then by default `Standard_D4ads_v5`, then `Standard_D2ds_v5` with tuning off; for a size `t4SkuName` sets, the next size Azure accepts, cheapest first. Each is priced against both ceilings first ([the cost check](cost-management.md#the-general-purpose-fallbacks-cost-check-phase-28-follow-up); `PREFLIGHT.T4.FALLBACK` ahead), and over one T4 is still created, with a `DEPLOY.T4.SKU` **Warning** naming the ceiling to raise. A refused server's `Dropping` shell is waited for up to 15 minutes, or the run ends **NOT DONE** (`DEPLOY.T4.REMOVING`). `DEPLOY.T4.FALLBACK`, a **Warning**, gives the sizes tried, the size created, and the monthly estimate at both (`STATUS.T4.SIZE` too); the tags `DbHubT4Size` and `DbHubT4Refused` keep that size.
- **An existing T4** keeps its size unless `t4SkuName` changes it, except one nothing sizes, which moves to `Standard_D4ds_v5` once, priced first (`PREFLIGHT.T4.SIZE`, `DEPLOY.T4.SIZE`; the server restarts, typically within a minute: [scaling](https://learn.microsoft.com/azure/postgresql/scale/concepts-scaling-resources)). Over a ceiling, unpriced, not Ready, or refused, it keeps its size, and `DEPLOY.T4.SIZE` names the ceiling to raise. `start-demo.ps1` never scales T4.

#### T4's read replica in the deployment (2026-11-13)

T4's same-region read replica, `pgreplica01-<deploymentId>` ([ADR 0025](adr/0025-t4-read-replica.md)), exists for each session: the starts create it, and the stops delete it. In `deploy.ps1`, T4's `Replica` step waits up to 90 minutes for T1's restart of T4, then deploys `infra/replica/pgreplica01.bicep` (deployment `dbhub-t4-replica`) at T4's size, in its subnet and DNS zone, Microsoft Entra only, about 9 minutes (T4 shows **Updating**, which blocks management operations, not connections), records `DbHubT4Replica` and `DbHubT4ReplicaSize`, and checks `T4.REPLICA`, `HUB.ESTATE.T4.REPLICA`, and `METRICS.T4.REPLICA` (`physical_replication_delay_in_seconds`).

- **Its size** is T4's or larger: on `SkuNotAvailable`, another zone, then `Standard_D4ads_v5` or `Standard_D4ds_v5`, then larger sizes, each a **Warning** with both hourly prices (`DEPLOY.T4.REPLICA.FALLBACK`); a refusal of every size is a **Fail** (`DEPLOY.T4.REPLICA`) with a Region access request as the fix. A Burstable T4 has none (`PREFLIGHT.T4.REPLICA`, `DEPLOY.T4.REPLICA`, `HUB.ESTATE.T4.REPLICA`, `METRICS.T4.REPLICA`: **Not supported**, with a General Purpose size as the fix). When T4 grows, the replica is deleted first (`DEPLOY.T4.REPLICA.REMOVE`) and created again.
- **At the run's end,** after **DONE**'s checks and the snapshot, it's deleted, **NOT DONE** included (about 2 minutes; `DEPLOY.T4.REPLICA.END`; [ADR 0025](adr/0025-t4-read-replica.md#amendment-deployps1-deletes-the-replica-at-its-end-2026-11-16)), unless a session uses it: a Run all session's until its auto-stop, a `start-demo.ps1` session's until its `DbHubSessionUntilUtc` tag. When the run can't tell, or the delete fails, a **Warning** names `./scripts/stop-demo.ps1` for when no session runs.

### T5 in the deployment (2026-11-18)

T5, the Azure Cosmos DB for NoSQL account `cosmos01-<deploymentId>` ([ADR 0027](adr/0027-t5-cosmos-db.md), [settings](configuration.md#t5-azure-cosmos-db)), comes with the template unless `t5Enabled` is `false`: Microsoft Entra only, no public network access, the database `contosocare` with the container `patient-events` at 400 RU/s, the private endpoint `pe-<prefix>-<environment>-cosmos01` with the zone `privatelink.documents.azure.com`, and T1's role, Cosmos DB Built-in Data Contributor.

- **The free tier** (`DEPLOY.T5.FREETIER`), set only at creation: a new T5 gets it when no other account in the subscription has it; otherwise a **Warning** naming that account, or saying the subscription is internal ("Free tier is not supported for Internal subscriptions"). When Azure refuses it anyway, the template goes again without it; `"t5UseFreeTier": false` never asks for it.
- **T1's `T5` step,** in stage `T4`: `T5.ACCOUNT`, `T5.ENTRAONLY`, `T5.NETWORK`, `T5.CONTAINER`, `T5.FREETIER`, `T5.ACCESS`, and the runner's warm-up through T1 (`WORKLOAD.T5.WARMUP`, retried for up to 10 minutes); the validation adds `HUB.ESTATE.T5` and `METRICS.T5`.
- **The container exists only during sessions** ([ADR 0027](adr/0027-t5-cosmos-db.md#the-container-only-during-a-session-2026-11-19)), since an account can't be stopped: the stops delete it (`STOP.T5`), and the starts create it (`START.T5.CONTAINER`). `DEPLOY.T5.LIFECYCLE` (the tag `DbHubT5Container`) is a **Pass** when the session control's role can create it again, which the run adds for an Owner, or when the control holds no role at all, so `start-demo.ps1` creates it with your rights; otherwise the container stays between sessions, a **Warning** with `./scripts/grant-safety-stop.ps1`, or a **Pass** on the free tier, where that costs nothing. The run creates a missing container (`DEPLOY.T5.CONTAINER`).
- **When Azure doesn't create the account** (`DEPLOY.T5`, a **Warning**), the template goes again without T5, so the rest finishes, and the next run tries again; when it lasts, set `"t5Enabled": false`, or use another region. With `false`, `DEPLOY.T5.OFF` is **Not selected**, and an account an earlier run created bills until `destroy.ps1`.

### The nightly safety stop

Every `deploy.ps1` sets it up beside the tracks ([ADR 0024](adr/0024-nightly-safety-stop.md)); each problem is a **Warning**, never a **Fail**:

| Result | What it does |
|---|---|
| `SAFETYSTOP.RESOURCES` | Deploys `infra/safetystop/safetystop.bicep` (deployment `dbhub-safetystop`): the identity `id-<prefix>-<environment>-safetystop` and the Automation account `aa-<prefix>-<environment>-safetystop` (Basic, local authentication off) |
| `SAFETYSTOP.RUNBOOK` | Publishes `DbHub-Stop` (`automation/runbooks/DbHub-Stop.ps1`) when it changed |
| `SAFETYSTOP.SCHEDULE` | `dbhub-safety-stop` at `autoShutdownTime`, and `dbhub-safety-t3check` 30 minutes later, or T3's auto-pause delay plus 15 when that's longer, which stops a running T4 too, in `autoShutdownTimeZone`; a schedule that's off, moved, or unlinked is created again |
| `SAFETYSTOP.ROLE` | "DbHub Demo Safety Stop", a stop-only role of 9 actions ([permissions](permissions.md#the-nightly-safety-stop)), at the demo resource group, when you may assign it; otherwise a **Warning** with `./scripts/grant-safety-stop.ps1` |

What it does each night is in [what stops or pauses on its own](cost-management.md#what-stops-or-pauses-on-its-own); `status.ps1` (`STATUS.SAFETYSTOP`), `validate.ps1 -Area Cost` (`COST.SAFETYSTOP`), and the account's job history show it. With a piece missing, the run still ends **DONE**, with one line on what then doesn't stop and the fix. An Owner's `./scripts/grant-safety-stop.ps1 [-ConfigPath <path>] [-WhatIf]` creates or updates the safety stop's and the session control's roles and assigns them, gives the environment's deployer the control vault's three secrets (`CONTROL.ROLE.DEPLOYER`: the person whose `deploy.ps1` last set up the vault, as Azure records it on the vault), then records T5's container lifecycle (`GRANT.T5.LIFECYCLE`; `out/grant-safety-stop.jsonl`); a destroy deletes the assignments with the group, so it's needed again after a redeploy by someone who can't assign roles.

#### A run the nightly stop waits for (2026-11-14)

`deploy.ps1` marks the demo resource group busy while it runs ([ADR 0024](adr/0024-nightly-safety-stop.md#amendment-the-busy-marker-so-the-nightly-stop-doesnt-cut-off-a-run-2026-11-14)): its own process sets `DbHubBusyUntilUtc` 60 minutes ahead every 10 minutes, and the stop, its T3 check, and the control's T4 stop change nothing while it's ahead (`Deferred`), by at most 3 hours. When the stop's time falls inside the run, the status page's **Nightly stop** row says so, `dbhub-safety-deferred` runs the stop hourly from the marker's end until morning, and the VMs' auto-shutdown moves past the run. A run that ends past the stop's time keeps the demo up 60 minutes more (`DEPLOY.NIGHTLYSTOP`, a **Warning** that says when): `./scripts/start-demo.ps1` keeps it running tonight, until its session's auto-stop (4 hours by default) or the next nightly stop, and `./scripts/stop-demo.ps1` stops it now. Since 2026-11-19, an update that found the demo stopped stops it at its end instead ([the stop at the end of an update](#the-stop-at-the-end-of-an-update-2026-11-19)), which puts the nightly stop back as usual. An abandoned run's marker expires within an hour, so the deferred pass and the moved auto-shutdown still stop the demo that night; `status.ps1` shows the move (`STATUS.NIGHTLYSTOP`) until the next start, stop, or deploy puts it back.

### The session control

The session control (formerly the on-demand activity control) runs a whole session from one Run all ([ADR 0026](adr/0026-one-run-all-session.md), [the notebook's guide](../fabric/control/README.md), [settings](configuration.md#the-session-control), [roles](permissions.md)). - **In Fabric,** after the Fabric track: `NB_DatabaseHub_Control`, in the folder "DBHub Control" of the demo's workspace with a public vault, or in its own workspace (the demo's name followed by " Control") with a managed private endpoint (`CONTROL.FABRIC.*`), with `LH_DatabaseHub` as its lakehouse (`CONTROL.FABRIC.LAKEHOUSE`); while the capacity isn't Active, the next run does it. ### Cost guardrails

Preflight, `start-demo.ps1`, and `estimate-cost.ps1` price the demo at live list prices, with the subscription's Defender for Cloud plans, against both ceilings, and `start-demo.ps1` adds a session to this month's actual cost (`START.COST.ACTUAL`, shown as `STATUS.COST`); the template adds a budget at `monthlyCeilingUsd`, with alerts, and the VMs' nightly auto-shutdown. ### Run Commands, policies, and deallocated VMs

Every VM-side action is a Run Command, at most 25 per VM ([managed Run Command](https://learn.microsoft.com/azure/virtual-machines/windows/run-command-managed)). A **Conflict** from a policy-installed extension (`MDE.Windows`, Guest Configuration, Defender for SQL, the Azure Monitor agent) is retried for about 12.5 minutes, and a VM's artifacts and loader wait up to 20 minutes for its extensions to settle ([az vm get-instance-view](https://learn.microsoft.com/cli/azure/vm#az-vm-get-instance-view)), with "Azure is finishing `<extension>` on `<VM>` (installed by a policy in your tenant); no action needed". A deallocated VM answers `OperationNotAllowed`, so a password rotation is then **Manual action required**, and a profile change **Not selected**. Chunk deletes aren't waited for (`DEPLOY.ARTIFACTS.CLEANUP_<VM>`), and a stall sends the rest one at a time (`DEPLOY.ARTIFACTS.STALL_<VM>`), both **Warnings**. A watchdog saves a stuck VM's instance view to `out/diagnostics`, restarts it once ([az vm restart](https://learn.microsoft.com/cli/azure/vm#az-vm-restart); never the T2 host during a golden Release or a guest build), then deallocates and starts it once (`DEPLOY.WATCHDOG_<VM>`, a **Warning**, or a **Fail** whose fix is to wait 30 minutes and run `./scripts/deploy.ps1` again: [ADR 0003](adr/0003-t2-host-size-security-type-bootstrap.md#2026-11-16-amendment-a-restart-azure-doesnt-finish)); extensions that stay stuck are `DEPLOY.EXTENSIONS_<VM>`, a **Fail** that names them.

### Disks the subscription's automation switched (Phase 24)

An identity outside the demo can switch the VMs' OS disks to Standard HDD while they're deallocated, and Azure doesn't change an OS disk's type through its VM (`OperationNotAllowed`). So `deploy.ps1` passes a drifted disk's type to the template as it is (`diskSkuOverrides`), with a **Warning** (`DEPLOY.DISKS.DRIFT`), and `status.ps1` reports it (`STATUS.DISKS`); the demo never changes a disk back ([limitations](limitations.md#deployment-and-operations)).

### Diagnostics: `collect-diagnostics.ps1`

When a run ends **NOT DONE** and its next step doesn't help, `./scripts/collect-diagnostics.ps1` zips the results (`out/*.jsonl`), the progress model, the transcripts (`out/logs`), and the saved instance views (`out/diagnostics`) into `out/diagnostics-<time>.zip` for a **Deployment problem** issue. It redacts every line again, replaces GUIDs, addresses, the servers' suffix, your home folder, and your owner and account with placeholders, and writes nothing when its secret scan finds anything (`DIAG.BUNDLE`, **Fail**). Read the zip before you attach it: the repository is public.

## Bastion, the golden snapshot, and the other scripts

### Bastion and the one-time host password

Bastion is on demand only, and no deployment needs it: it's for interactive access, such as T2's missing-index fix (a person runs [`remediation.sql`](../scenarios/missing-index/remediation.sql) in the guest), the SSMS fallbacks (SSMS is in the Jumpstart guest), or troubleshooting.

```powershell
./scripts/start-demo.ps1 -Interactive -ResetAdminPassword
```

- `-Interactive` deploys Azure Bastion Basic and a Standard public IP from `infra/modules/bastion.bicep` into `AzureBastionSubnet` (about 8 minutes), tagged to expire after `bastionMaxHours` (4 by default, also the cap).
- `-ResetAdminPassword` sets a one-time password for the T2 host's administrator through a Run Command (`Set-LocalUser`, a protected parameter) and copies it to your clipboard, never displayed, logged, or stored. Without a clipboard (Codespaces, Cloud Shell, GitHub Actions) and without the Key Vault opt-in, nothing is set: in the Azure portal, open `archost01`, **Help** > **Reset password**, set a password of your own, and sign in through Bastion ([reset a password](https://learn.microsoft.com/troubleshoot/azure/virtual-machines/windows/reset-rdp)); `stop-demo.ps1` rotates yours afterward too.
- `stop-demo.ps1` deletes Bastion and its public IP (also one an interrupted delete left, which bills by the hour on its own), and rotates the password to a value nobody keeps. Nothing else removes Bastion, except the optional GitHub schedules' hourly `bastion-cleanup.yml`; until then it bills, and `status.ps1` warns with its hourly price (`STATUS.BASTION`).
- A rotation needs the host running: deallocated, it's **Manual action required**, and the next `start-demo.ps1` rotates the leftover; one that fails on a running host is a **Warning**, retried at the next stop or start.

#### Opt-in: the password in Key Vault instead of the clipboard

With `keyVault.enabled: true` and `assignRoles: true`, the one-time password goes to an Azure Key Vault, so `start-demo.ps1 -Interactive -ResetAdminPassword` works from any session, Cloud Shell included. It's off by default, and separate from the session control's vault, which never holds a password ([ADR 0008](adr/0008-identity-rbac-abac.md), [ADR 0009](adr/0009-secrets-handling.md)).

```json
"assignRoles": true,
"keyVault": { "enabled": true }
```

- **It needs** `Microsoft.Authorization/roleAssignments/write` on the resource group (Owner, User Access Administrator, or Role Based Access Control Administrator); the schema refuses `keyVault.enabled` without `assignRoles`.
- **The vault** `kv-<prefix><environment>-<deploymentId>` (`infra/modules/keyvault.bicep`) has RBAC authorization ([Key Vault RBAC](https://learn.microsoft.com/azure/key-vault/general/rbac-guide)), soft delete ([soft delete](https://learn.microsoft.com/azure/key-vault/general/soft-delete-overview)), and purge protection only with `keyVault.purgeProtection`, which is irreversible; its other `keyVault.*` settings and its two roles, for you and the principals you list, are in [permissions](permissions.md#the-key-vault-opt-in). A vault **Fail** doesn't stop the deployment.
- **Start** stores the password as the secret `<vm>-one-time-password`, expiring with Bastion, before it sets it (`START.KEYVAULT`); **stop** rotates it and disables every version (`STOP.KEYVAULT`); `status.ps1` warns about one readable past its expiry (`STATUS.KEYVAULT`); **destroy** leaves the vault in soft delete (`DESTROY.KEYVAULT`), and a `deploy.ps1` within that time recovers it.
- **To sign in with it:** Bastion's RDP form has no Key Vault option ([Connect to a Windows VM using RDP](https://learn.microsoft.com/azure/bastion/bastion-connect-vm-rdp-windows)), so open the vault `START.KEYVAULT` names in the portal, **Objects** > **Secrets** > `archost01-one-time-password`, copy the current **Secret value** ([retrieve a secret](https://learn.microsoft.com/azure/key-vault/secrets/quick-create-portal)), then open `archost01`, **Connect** > **Bastion**, **Username and password**, and paste it. Microsoft Entra ID sign-in through Bastion, in preview for RDP, isn't implemented ([Bastion Microsoft Entra ID authentication](https://learn.microsoft.com/azure/bastion/bastion-entra-id-authentication)).

### The T2 golden snapshot: `capture-t2-golden.ps1` and `test-t2-golden.ps1`

Optional: an incremental snapshot of the finished `archost01-osdisk` in `rg-<prefix>-golden` lets a redeploy skip T2's host build, about 27 minutes in `JumpstartImage` mode ([ADR 0018](adr/0018-fast-redeploy-parallel-tracks-golden-snapshot.md)).

```powershell
./scripts/capture-t2-golden.ps1          # preconditions, the guest air-gapped, the host stopped, then the snapshot (DenyAll) and a disk check
./scripts/test-t2-golden.ps1 -Onboard    # a quarantined copy: no outbound traffic, the Arc identity reset, SQL Server Standard, then a fresh onboarding with PAYG and monitoring
```

- **Where T2 comes from** (`t2Source`): `auto`, the default, restores a new `archost01` from the newest boot-verified snapshot of the configured mode, and builds without one; `golden` requires one; `build` never uses one; an existing host keeps its disk (`PREFLIGHT.T2.SOURCE`). A snapshot is used, and older ones deleted, only after `test-t2-golden.ps1` verifies it.
- **Modes:** `JumpstartImage` and a kept `PaygWizard` guest; `ProductKey` and `Developer` are **Not supported** (`GOLDEN.CAPTURE.MODE`). `DESTROY.GOLDEN.GUARD` refuses nothing any more. An evaluation guest's days run on in a snapshot: `STATUS.T2.GOLDEN` and `PREFLIGHT.T2.SOURCE` warn at 30 and 7 left; then capture again from a fresh build. A `JumpstartImage` guest isn't an evaluation.
- **It bills every month** ([cost management](cost-management.md#the-t2-golden-snapshot-phase-20)) until `destroy.ps1 -IncludeGolden`.
- **Sign-in data ([ADR 0009](adr/0009-secrets-handling.md)):** the capture removes it and captures nothing unless a fresh scan is clean (`GOLDEN.CAPTURE.SIGNIN`); the test scans each copy (`GOLDEN.TEST.SIGNIN`). `-WipeFreeSpace` also zeroes free space (45 GB free on the host's `C:`, `-MinHostFreeGB`, and about an hour). With `assignRoles: true`, the test onboards with its own host identity. Both keep your PC awake.
- **The Incident RCA's capture ([ADR 0031](adr/0031-incident-rca.md)):** the capture stops T2's workload runner and deletes what its observer kept in the guest, and captures nothing while any is left, so a T2 restored from the snapshot never exports this environment's capture as its own. It captures nothing either while T2 documents that a history save didn't take are listed, which the deletion would lose (`GOLDEN.CAPTURE.RCA`, which names the list and how to save them): this PC's pending list (`out/history-pending`), which the scripts' next history save fetches, or the session control's status (its Automation variable `DbHubSessionStatus`, which [Variable - Get](https://learn.microsoft.com/rest/api/automation/variable/get) reads with the access the scripts already use), whose documents only a Run all session's start fetches, one session's per start on any VM, so the fix asks for a Run all session for each session it lists, at least, and the capture again after each. A status that a tenant's policy has encrypted can't be read that way, since Azure Resource Manager returns an encrypted variable with no value ([variables](https://learn.microsoft.com/azure/automation/shared-resources/variables)), so the capture captures nothing then. Its fix: Run all sessions, each to its planned end (Run all's own end or its auto-stop: a stop before it can leave capture that the stop's lines don't name), until one has no `RCA.EARLIER` line at its start about evidence still on the VMs or in the control vault, no `RCA.EXPORT` line that says "document(s) of another session go with that session's evidence" (the status then carries them for that session), and no `RCA.PENDING` line at its end; then, the same day, `./scripts/deploy.ps1`, which re-creates the variable unencrypted but empty, and the capture, before the tenant's policy encrypts it again. Both save them with the demo workspace's `NB_DatabaseHub_LiveActivity`: when its copy is from before the Incident RCA (with `fabric.importNotebooks` false, the update keeps it), no save takes them, so the fix updates it first, `./scripts/configure-fabric.ps1 -SkipHubChecks -Notebook NB_DatabaseHub_LiveActivity`, which leaves the workspace's other notebook as it is; the capture reads the notebook's definition only then ([Get Item Definition](https://learn.microsoft.com/rest/api/fabric/core/items/get-item-definition)). `GOLDEN.CAPTURE.PREPARE` says how much it deleted, and how much of it no export had taken, which isn't in the history; to keep that part, save the history before the capture (`./scripts/stop-demo.ps1 -SaveHistory` at a session's end). An export alone doesn't put evidence in the history. When the capture fails after stopping the runner, it starts the runner again if the guest still runs; otherwise the guest's next start does.

### Arc onboarding: `configure-arc.ps1`

`deploy.ps1`'s T2 stage runs it; run it yourself to resume or repair (`./scripts/configure-arc.ps1 -WaitForHostMinutes 120`). It reads the host's `health.json` through a read-only Run Command, every 5 minutes with `-WaitForHostMinutes`, then:

1. **`ProductKey` mode (P10), at `WaitingForProductKey`:** sends the key (`-ProductKey` prompts for it; in GitHub Actions, the `DBHUB_SQL_PRODUCT_KEY` secret) as a protected parameter, only to a host waiting for one, which keeps it with DPAPI and deletes it after setup.
2. **At `WaitingForArcOnboarding`:** onboards `arcsql01` with the host identity `id-<prefix>-<env>-arc-onboard` when it's attached (`assignRoles: true`), or else your short-lived token as a protected parameter, then sweeps what's left of it ([ADR 0005](adr/0005-arc-onboarding-authentication.md#phase-7-implementation-notes-2026-10-20)). An earlier build's Arc machine is deleted first, so there are no duplicates.
3. **Checks and fixes** the Azure extension for SQL Server (1.1.2504.99 or later, license type PAYG), the instance, and monitoring, and turns on T2's migration assessment with its first run (`T2.ARC.MIGRATIONASSESSMENT`, free, a **Warning** at worst); reports `T2.ARC.CONNECTED`, `T2.ARC.NODUPLICATES`, and `T2.ARC.DISCONNECTEDDAYS`, all in `out/configure-arc.jsonl`.

`-UseHostIdentity` requires the host identity; `-UseCallerToken` uses your token anyway; `-Force` onboards again, to repair a connection; `-SkipConfiguration` onboards only; `-WhatIf` runs only the guard.

### Performance monitoring: `configure-monitoring.ps1`

`./scripts/configure-monitoring.ps1 -Target T1, T2 -WaitMinutes 15`:

- **T1:** merges the `DatabaseWatcheronAzureVM` flag into the SQL IaaS Agent extension's settings, then waits for `DatabaseMonitorArcPlugin` with `"State":"Running"` and `"MetricsUploadStatus":"OK"`, 3 to 15 minutes ([enable performance monitoring](https://learn.microsoft.com/azure/azure-sql/virtual-machines/windows/enable-performance-monitoring-sql-vm)); for about 10 minutes after a template deployment the extension shows `Updating`, a wait with `-WaitMinutes`, else a **Warning**. It reports `T1.SQLVM.MONITORING` and, read-only, `T1.SQLVM.ASSOCIATEDSERVICES`.
- **T2:** sets `monitoring.enabled` on the SQL Server instance resource; **Not supported** in `Developer` mode.
- **T3:** its setting is the database's extended property `MS_EnablePerformanceMonitoringPreview`, which `deploy.ps1`'s T3 stage sets and `validate.ps1 -Area T3` checks (`T3.PROPERTY`); **Not selected** here.

### Activity profiles and boot behavior

- **Who sets a profile:** `deploy.ps1`, `start-demo.ps1`, Run all, and `./scripts/demo-control.ps1` (or the optional `demo-control.yml`): `off`, `baseline`, `business-day`, `incident:<scenario>`, or Run all's `showcase`, each until two minutes before the next auto-shutdown.
- **`business-day` is the default** ([the schedule](demo-walkthrough.md#the-hourly-incidents-business-day), [ADR 0010](adr/0010-workload-generator-technology.md#activity-profiles-business-day-by-default-2026-11-03)); for a quieter demo, `"activityProfile": "baseline"` or `-ActivityProfile baseline`. Without the setting, `business-day` is said once (`*.ACTIVITYPROFILE`) and priced. Runs set `baseline` first and switch afterward, also after Ctrl+C or a failure (`DEPLOY.INCIDENTS_*`, `START.INCIDENTS_*`, `DEPLOY.INTERIM_*`, `START.INTERIM_*`), so no incident slows their Run Commands.
- **At boot** the VMs set no profile (`activityProfileOnBoot: false`); `true` starts the configured one, as `baseline` when it has incidents.
- **Checks while incidents run:** **DONE**'s checks never read a target through its load; in `validate.ps1`, a failure an incident due on that target can explain (`WORKLOAD.<target>.COMMAND`, `T3.PROPERTY`, the host lane `.HOST`) is a **Warning** naming it, and any other fault stays a **Fail**.

### How the VMs bootstrap

[The bootstrap's README](../vm/bootstrap/README.md#flow) has the flow: the bundle (`vm/` and `database/`) and the workload runner reach each VM in SHA-256-checked chunk Run Commands (nothing secret, no storage account; the runner built with the .NET SDK pinned in `config/versions.json`, `DEPLOY.DOTNETSDK`); the loader unpacks them to `C:\ProgramData\DbHubDemo` and registers the SYSTEM task `DbHubDemo-Bootstrap`, which runs at startup and every 5 minutes until the VM is ready (`health.json`); and the runner ([ADR 0010](adr/0010-workload-generator-technology.md#phase-13-delivery-and-hosting-as-built-2026-10-20)) applies `110-*.sql` and `120-*.sql` and starts `DbHubDemo-Workload` on T1, for T3 through T1, and in T2's guest. `Invoke-DemoWorkloadCommand -Config $config -Target T1 -ArgumentList 'status', '--json'` runs a runner command. While T3's profile runs, T3 stays awake and bills compute ([ADR 0016](adr/0016-cost-profiles.md#phase-13-note-the-workload-runner-and-t3-serverless-compute-2026-10-20)).

### The guided stop (`PaygWizard`)

`PaygWizard`, T2's default until 2026-11-05, needed a person once per guest build, because pay-as-you-go SQL Server without a product key installs only through setup's wizard ([install from the command prompt](https://learn.microsoft.com/sql/database-engine/install-windows/install-sql-server-from-the-command-prompt)); `deploy.ps1` waited for that person, the guided stop (`DEPLOY.T2.GUIDEDSTOP`; [ADR 0006](adr/0006-sql-editions-and-licensing.md#amendment-one-command-one-guided-stop-phase-28-2026-10-29)). It's retired since 2026-11-09, and `PaygWizard` runs as `JumpstartImage`. What an earlier guided stop left open (the host's request, on-demand Bastion, a handed-over host password) is cleaned up when the run gets to T2 (`DEPLOY.T2.GUIDEDLEFTOVER`), and **DONE** never comes before; `./scripts/stop-demo.ps1 -RemoveBastionOnly` does it by hand. Its one automatic sign-in of the guest, with a temporary password kept only as the LSA `DefaultPassword` secret ([ADR 0009](adr/0009-secrets-handling.md#phase-28-amendment-the-guests-one-automatic-sign-in-and-the-portal-password-reset-2026-10-29)), is undone at the host's next pass, which also rotates the guest's password; the sign-in data scan (`check-sign-in-data.ps1`, the golden capture, and the golden test) still fails on any of it, `-Clean` removes it, and `status.ps1` reports a leftover (`STATUS.T2.AUTOSIGNIN`, a **Warning**).

### Setup's Azure sign-in: IE Enhanced Security Configuration

Only the guided stop opened setup's Azure sign-in, whose **Use Azure Login** window stayed blank on 2026-10-30: Internet Explorer Enhanced Security Configuration (IE ESC) blocked `https://login.microsoftonline.com` ([ADR 0009](adr/0009-secrets-handling.md#setups-azure-sign-in-ie-enhanced-security-configuration-live-finding-2026-10-30)). Until 2026-11-09, the host prepared the guest first (the WebView2 runtime, IE ESC off for administrators, and Microsoft's sign-in sites as Trusted sites), undoing each after setup. A guest an earlier guided stop left prepared gets IE ESC back on, and its Trusted sites back, at the host's next pass; `GuestSignInCleanup` and the golden capture still require IE ESC on.

### The `PaygWizard` manual step (validated live 2026-10-21)

No deployment asks for it, and you shouldn't do it by hand: run `./scripts/deploy.ps1`, which makes a guest whose setup was never finished again from the Jumpstart image, and keeps a finished one ([an older demo](#an-older-demo-a-plain-deployps1-upgrades-it-2026-11-09)).
