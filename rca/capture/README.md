# The capture queries

The exact statements the runner's observer lane runs ([ADR 0031](../../docs/adr/0031-incident-rca.md), [the contract](../README.md)). Each block in the two files is one statement, named `-- name: <ID>`, with its purpose, targets, and cadence in its comments. The runner embeds these files and runs exactly these blocks; the verifiers ran exactly these blocks too.

- [sqlserver.sql](sqlserver.sql): T1 and T2 (SQL Server 2022) and T3 (Azure SQL Database), 24 blocks.
- [postgresql.sql](postgresql.sql): T4 and its read replica (PostgreSQL 18), 12 blocks.
- T5 (Azure Cosmos DB) has no query: its evidence is Azure Monitor's metrics, which the history already saves (below).

**Blind.** Every block reads what a DBA's tools read, and nothing in it names a scenario or reads what the workload plans or reports about itself. The sentinel runs every 30 s for the whole session, and **When** says which signal starts each block ([capture triggers](../README.md#capture-triggers)). Phase 1 runs the blocks marked 1; Phase 2 adds the others.

The runner's own client-side counts are what the workload reports about itself, so detection doesn't use them.
