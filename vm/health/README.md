# Health reporting

`C:\ProgramData\DbHubDemo\health.json` on T1 and the T2 host summarizes the bootstrap after every run of the state machine. The validator reads it through Run Command ([ADR 0012](../../docs/adr/0012-validation-model.md)).

| File | Purpose |
|---|---|
| `health.schema.json` | JSON Schema (2020-12) for `health.json`. A Pester test validates the file the module writes against it. |
| `Get-DemoHealth.ps1` | Prints `health.json` in compact form, with steps reduced to a name-to-status map, so it fits in Run Command's 4 KB output. `-View Summary` (Phase 7) prints only what the orchestrator gates on: role, state, status, the first 500 characters of the message, the current step, the generation, the install mode, Arc onboarding, and the guest's state and SQL Server edition; since Phase 28 also the `PaygWizard` guided stop's state from `details.guidedSetup` (whether the guest's automatic sign-in is armed, `deploy.ps1`'s request, setup's sign-in preparation `guidedSignIn`, which had to be `ready`, or `fallback` once the host stopped waiting for it, before anyone was asked, and the last cleanup), which since the guided stop's retirement (2026-11-09) shows only what an earlier one left. |

- **`state`** is the machine state: `InProgress`, `RebootPending`, `WaitingForArcOnboarding`, `WaitingForProductKey`, `WaitingForGuestSql` (the host's runner step waits for the guest's SQL Server, Phase 13), `WaitingForInput` (for example, the runner's chunks haven't all arrived), `ManualActionRequired`, `Ready`, or `Failed`.
- **A new generation's pass** (since 2026-11-19, the follow-up to issue #65): the loader starts a new bootstrap generation, which checks every step again, but the state machine writes `health.json` only when a step converges or when its pass ends, so until then the file still says what the pass before found, often `Ready`. On the T2 host, both views of `Get-DemoHealth.ps1` therefore report a generation that the loader started in the last 30 minutes (`settings.json`) and `health.json` doesn't report yet as `InProgress`, with that generation, the pass's current step from `state.json` once it has started, `generationPending`, and the file's own `reportedGeneration` and `reportedState`. `deploy.ps1`'s waits for the host take it as in progress, so its PowerShell Direct steps into the guest (Arc onboarding, the activity profile) start only once that pass has reported, and Arc onboarding with `-Force` (a golden copy) waits until that pass ends, for up to 20 minutes.
- **`status`** maps it to the ADR 0012 model: `Ready` is **Pass** (**Warning** when warnings exist; notes don't count), `Failed` is **Fail**, `ManualActionRequired` is **Manual action required**, and in-flight states are **Warning**.
- **`instructions`** carries the exact operator steps when manual action is required, such as, until 2026-11-09, the `PaygWizard` setup-wizard steps.
- **`warnings`** lists non-blocking issues, such as media trusted on first use or the T1 sysadmin recovery. Since 2026-11-20 (F24), each starts with the step that gave it (`<Step>: ...`), and a one-off note (a restart that's pending, media trusted on first use, the T1 sysadmin recovery, or a sign-in cleanup) goes with the next bootstrap generation. Any other warning stays while its cause does: a step drops its own warnings only when its Set runs again to its end (Done or NotSelected), which says again what still holds; a Set that throws or stops early, as when the guest doesn't answer, leaves them. A lasting warning from an older bundle, which names no step, gets its step's name at the next generation. `-View Summary` prints the first two, each cut to 240 characters, with `warningCount`, so `validate.ps1` (`INFRA.HEALTH.<vm>`) and `status.ps1` (`STATUS.VM_<vm>`) say which step warned.
- **`notes`** (since 2026-11-23) lists what a new VM's bootstrap gives by design, as information, each starting with its step: a sign-in cleanup that cleared an event log after T2's Arc onboarding, the restart SQL Server setup asked for when it removed Analysis Services and Integration Services from a new T1, T1's sysadmin recovery, and Jumpstart's image checked by its pinned SHA-256. A step gives its note only when the VM's own setup caused it in that generation: the sign-in cleanup when Arc onboarding ran in it, or T2's guest disk was downloaded or built in it, and T1's restart and sysadmin recovery when their step is setting up for the first time; on a VM that was set up before, the same events are one-off warnings, since nothing by design causes them there (the review of cb4bc479). Unlike a warning, a note leaves a Ready VM a **Pass**, so `validate.ps1`, `status.ps1`, and the status page say **Pass** too, and name the notes. They're one-off, as a one-off warning is: the next bootstrap generation clears them, and so does their step when its Set runs again. A bundle since then writes `notes` even when it's empty, and `-View Summary` prints the first two, each cut to 240 characters, with `noteCount`, only when health.json has `notes`, so the validator can tell its warnings from an older bundle's (the re-check of ea1ea20f). A bundle from before then gave these as warnings, which its next generation clears.
- **`details`** holds role-specific facts. On the host: the install mode; size, zone, and Secure Boot from IMDS; Arc onboarding; and the guest's state, uptime, computer name, evaluation days left, and SQL Server edition and version, read over PowerShell Direct, plus the guest's workload runner (`details.guest.workload`), and since 2026-11-18 the last restart that cleared a broken PowerShell Direct channel into the guest (`details.guestRecovery`, from `guest-recovery.json`; both views of `Get-DemoHealth.ps1` read that file itself as `guestRecovery`, so `deploy.ps1` sees a restart a Run Command made before the bootstrap's next pass; issue #65). On T1: the SQL Server edition and version, whether `ContosoCare` exists, the data folder, and the workload runner (`details.workload`: the runner's SHA-256, the .NET version, the profile, setup results, whether T3 is enabled, and the task's state). A failure while collecting details is reported in `healthDetailError` and doesn't stop the run.

The file is written with the module's redaction and never holds secrets.
