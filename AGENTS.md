# Instructions for AI agents

These are for an agent asked to **set up, deploy, upgrade, or try** this demo for someone. To change the code, read [.github/copilot-instructions.md](.github/copilot-instructions.md) instead.

## Use the scripts, not a setup of your own

1. **Signed in?** Run `az account show`. If it fails, ask the person to run `az login` themselves (`az login --use-device-code` in a codespace). Never sign in for them, and never run `az account set`: the scripts use the subscription in the configuration.
2. **No `config/demo.config.json` yet?** Run `./scripts/init.ps1 -CreateAdminGroup`, or let `./scripts/deploy.ps1` write it on its first run. Neither asks how T2 gets SQL Server: the default, `JumpstartImage`, needs nobody.
3. **Deploy:** run `./scripts/deploy.ps1`. It's the one path for a new environment and for one that exists in the subscription already, an older demo included: it continues an unfinished run, starts stopped VMs, sends changed bootstraps, rebuilds a T2 guest whose SQL Server setup wizard was never finished from Arc Jumpstart's image (about 27 minutes), keeps a finished T2 guest as it is, creates T4 when it's missing, sets up T4's read replica (it creates it for its checks, about 9 minutes, and deletes it at its end unless a session uses it), creates T5 (Azure Cosmos DB) when it's missing, sets up the session control and republishes its runbooks, and sets up the nightly safety stop ([update an existing environment](docs/deployment.md#update-an-existing-environment), [upgrading an existing demo](README.md#upgrading-an-existing-demo)). An older configuration's `"t2SqlInstallMode": "PaygWizard"`, the default before 2026-11-05, runs as `JumpstartImage`, with no setup wizard; the run says so in one line.
4. **Interrupted, or NOT DONE?** Run `./scripts/deploy.ps1` again, or the exact command its banner prints. It continues where it stopped.

## Don't

- **Don't `git pull`, switch branches, stash, or reset yourself** before or between runs. `deploy.ps1` checks GitHub's `main` first: a clean checkout of `main` updates itself (fast-forward only) and starts again with the new code. When it can't (local changes, another branch, diverged, offline, no Git), it says so in a `DEPLOY.SELFUPDATE` **Warning** with the exact command, and runs the code it has; report that Warning to the person, and leave the command to them, because it touches their files ([updates from GitHub](docs/deployment.md#updates-from-github-2026-11-09)).
- **Don't assemble a partial setup by hand** in place of `deploy.ps1`: no starting VMs, repairing monitoring, onboarding Arc, or creating resources piece by piece with `az` or the portal. `deploy.ps1` does each of them in order and checks them, and a hand-made state can keep it from finishing.
- **Don't finish T2's SQL Server by hand,** and don't ask a person to: no Bastion sign-in to a VM and no setup wizard. `deploy.ps1` makes T2 from the Jumpstart image, and runs a configuration's `PaygWizard` as `JumpstartImage`. Don't change `t2SqlInstallMode` on your own.
- **Don't leave a target out on your own:** not T1, T2, T3, T4 (PostgreSQL) with its read replica, T5 (Azure Cosmos DB), or Fabric. When `deploy.ps1` leaves T4 or T5 out, it says why in `DEPLOY.T4.OFF` or `DEPLOY.T5.OFF`; report that. Don't pass `start-demo.ps1 -SkipT4Replica` unless the person asks for it, and don't set `t5Enabled` or `t5UseFreeTier` yourself.
- **Don't read, print, or store a password, key, or token.**

## Report what deploy.ps1 says

- **The ending banner:** **DONE**, or **NOT DONE** with its reason and the exact next command it prints. Without **DONE**, the setup isn't finished; say so.
- **What it changed in an existing environment,** when these lines appear: `DEPLOY.T2.REBUILD`, `DEPLOY.T2.MODE`, `DEPLOY.T2.HOSTREBUILD` (the T2 host deleted and created again because its VM agent stayed down, or a **Fail** with the fix), `DEPLOY.T2.HOSTMISSING` (a T2 host that was gone, created again), `DEPLOY.T2.GUESTRESTART` and `DEPLOY.T2.GUESTRETRY` (T2's guest restarted once, or a step run again, because PowerShell Direct into it broke; or a **Fail** with the fix), `DEPLOY.T3.SCALE` (a run that would have resumed starts from preflight, so the template scales T3 to the profile's vCores online; since 2026-11-18), `DEPLOY.T4.MISSING`, `DEPLOY.T4.RETRY`, `DEPLOY.T4.OFF`, `DEPLOY.T4.REPLICA` (T4's read replica it added, or why not), `DEPLOY.T4.REPLICA.END` (the replica deleted at the run's end, or kept for a session that uses it, or a **Warning** with the fix), `DEPLOY.T5.MISSING` (T5, the Azure Cosmos DB account, created in an environment that didn't have it), `DEPLOY.T5` (a **Warning**: Azure didn't create T5's account, with Azure's reason, so the run finished without T5, and the fix when it lasts), `DEPLOY.T5.FREETIER` (whether T5 uses the subscription's one Azure Cosmos DB free-tier account, or why not), `DEPLOY.T5.LIFECYCLE` (whether T5's container exists only during a session from now on, and why, or why it stays between sessions, with the fix, and the month's worst case again when preflight didn't price that), `DEPLOY.CONTROL.ON` (the session control set up although the configuration said `"enabled": false`), and `CONTROL.RUNBOOKS` (the control's runbooks, republished, or a **Warning** with the fix).
- **Where Run all is:** `DEPLOY.CONTROL` says where the control notebook `NB_DatabaseHub_Control` is (one Run all runs a whole session, since 2026-11-14), or what it still needs and who does it.
- **The Incident RCA, when its lines appear** (since 2026-11-20, [ADR 0031](docs/adr/0031-incident-rca.md)). It needs no setting, sign-in, or grant; with `fabric.importNotebooks` false, the person runs two commands once (below).
  - **In `deploy.ps1`:**
    - `FABRIC.SEMANTICMODEL.RCA`, a **Warning** when the history model left out the RCA tables because the lakehouse doesn't have them yet, or they couldn't be listed. It says what adds them, and until then the Insights app says no RCA capture is recorded. With `fabric.importNotebooks` false, the update brings an activity notebook that nobody edited up to date and runs it, so the tables come with it; one someone edited in Fabric is kept, and then the fix is `./scripts/configure-fabric.ps1 -SkipHubChecks -Notebook NB_DatabaseHub_LiveActivity -RunLiveActivity`, then `./scripts/configure-powerbi.ps1`: pass that on, and don't run it yourself, because it replaces the edited notebook, which that setting keeps as the person left it.
    - `DEPLOY.FABRIC.HISTORY`'s sentence about the RCA evidence, which makes it a **Warning** when the snapshot's export, or the save of what it exported, didn't work.
  - **In `./scripts/stop-demo.ps1 -SaveHistory`, and `./scripts/configure-fabric.ps1 -RunLiveActivity`:**
    - `STOP.RCA.EXPORT` and `FABRIC.RCA.EXPORT`: the export from the VMs;
    - `STOP.RCA.CAPTURE.<target>` and `FABRIC.RCA.CAPTURE.<target>`: what the observer captured on each target, or its gaps (`T4_REPLICA` is T4's read replica);
    - `STOP.RCA.PENDING` and `FABRIC.RCA.PENDING`: documents that aren't in the history yet, which the next history save adds. After `./scripts/stop-demo.ps1` handed a Run all session's stop to the control, `STOP.RCA.PENDING` is the control's stop's line: the next session's start fetches those documents, as it says;
    - `FABRIC.RCA.EVIDENCE`: evidence that wasn't sent with the notebook's run.
  - **In Run all's output:** `RCA.EXPORT`, `RCA.CAPTURE.<target>`, `RCA.PENDING` (Stop now's, since 2026-11-22: what the stop left on the VMs for this session's history, which start takes it, and until when), `RCA.EARLIER` (an earlier session's evidence still on the VMs, which a later start exports; a **Warning** when it can't go into that session's history any more), and `RCA.EVIDENCE` (whether the activity notebook wrote every document).

  None of them blocks **DONE**, a session, or a stop, and what an export didn't take stays on the VMs for the next one. Pass each **Warning** on with its fix, usually `./scripts/deploy.ps1` or the next history save ([what each says](docs/troubleshooting.md#the-incident-rcas-capture)). Don't fetch the evidence with Run Commands yourself.
- **When `./scripts/stop-demo.ps1` stops a Run all session,** `STOP.CONTROL.SESSION` (since 2026-11-22): the session's stop went to the session control, as Stop now's does, and the `STOP.RCA.*` lines after it are that stop's. With `-SaveHistory`, the history is then saved without that session's Incident RCA evidence, which the control keeps for the next Run all that starts a session within 7 days; after that, nothing saves it (`STOP.FABRIC.SAVEHISTORY` says so). A **Warning** says the control couldn't take it, so `stop-demo.ps1` stopped the demo itself, as before, and why; or that a stop job of the control's still runs, so it stopped nothing under it: then `./scripts/stop-demo.ps1` again, once that job has finished; or "It couldn't: ...": the control stopped the session, and `stop-demo.ps1` stopped what it missed; or that the job ended without a readable result, so `stop-demo.ps1` confirmed each stop itself. `STOP.CONTROL.HOSTPASSWORD`, a **Warning**, says the T2 host was still deleting the host password's Run Command when the stop's export started there. Pass each on; don't start or stop the control's jobs yourself.
- **A Fabric workspace that another environment uses too:** `DEPLOY.FABRIC.SHARED` is a **Warning** that names it, with the fix (each environment its own `fabric.workspaceName` and `control.fabricWorkspaceName`). For a workspace that another environment records and this one doesn't, it's a **Fail** in preflight, before anything is created, and the run ends **NOT DONE** with the fix (since 2026-11-19). Pass it on, and don't change the configuration yourself.
- **Every automatic size change:** `DEPLOY.T4.FALLBACK` and `DEPLOY.T4.REPLICA.FALLBACK` say what was asked for, what Azure refused, what was deployed, and the cost difference; pass them on.
- **When the month's worst case is over the ceiling, but only warns,** `PREFLIGHT.COST.MONTHLY` (a **Warning**, since 2026-11-19): T5's container is priced all month because nothing automatic deletes it after a session (the session control has no role), and the month would fit with it for the running hours only. The run goes on. Pass on the worst case, the ceiling, and the three fixes it names (an Owner's `./scripts/grant-safety-stop.ps1`, a higher `monthlyCeilingUsd`, or `t5Enabled` false), and that `./scripts/stop-demo.ps1` after each session deletes the container until then; don't change the configuration yourself.
- **When the month's worst case went up during the run,** `DEPLOY.COST.T4RESTART` (a **Warning**, since 2026-11-19): preflight counted the nightly safety stop that the run sets up, but it isn't fully in place, so T4's 7-day restart counts the rest of the month. Pass on the worst case, the ceiling, and the fix it names (an Owner's `./scripts/grant-safety-stop.ps1`, or the ceiling to raise); don't change `monthlyCeilingUsd` yourself.
- **When the demo stops tonight,** when `DEPLOY.NIGHTLYSTOP` is a **Warning**: the run was still going at the nightly stop's time, which waited for it, and the demo now stops 60 minutes after the run. Pass on its time and both choices: `./scripts/start-demo.ps1` keeps it running tonight, `./scripts/stop-demo.ps1` stops it now. Don't change the schedules yourself.
- **Whether the demo still runs and bills after the run,** `DEPLOY.ENDSTOP` and its line in **DONE** (since 2026-11-19): an update that found the demo stopped stops again what it started (or a **Warning** with `./scripts/stop-demo.ps1` as the fix); otherwise **DONE** says what the demo bills an hour, until when, and that `./scripts/stop-demo.ps1` stops it now. Pass it on. Don't pass `deploy.ps1 -KeepRunning` unless the person asks to demo right after the update.
- **Whether it updated itself from GitHub:** the first line, "Updated this copy from GitHub's main: ... to ...", or the `DEPLOY.SELFUPDATE` **Warning** with its command.
- **What its first run found, when it wrote the configuration:** `INIT.EXISTING` (since 2026-11-18). A **Warning** that the environment is the person's, so the configuration came from what's deployed, with the settings that kept their defaults and whether the run republishes its notebooks (`fabric.importNotebooks`, with why); or that it isn't theirs, so the run deploys a new environment with the prefix it names. Pass on which, and the settings it lists; don't change the configuration or the prefix yourself.
- **What it lists under Please confirm:** for example the Database Hub tenant setting, which only a Fabric administrator can read, and Database Hub's own pages, which have no API.

## Steps only a person can do

- `az login`.
- **The Insights app's browser sign-in, only if Fabric refuses the Azure CLI's token** (`FABRIC.APP.TOKEN`, a **Warning**, and the run says the app wasn't created). Since 2026-11-09 the app deploys with the person's `az login`, so usually there's nothing to do. `deploy.ps1` doesn't start that sign-in under an assistant, so ask the person to run `./scripts/configure-fabric-app.ps1 -SignIn` in their own terminal.
- **The Insights app's browser confirmation, only when it's listed under Please confirm.** When the app is deployed and every query it runs returned its data, `FABRIC.APP.BROWSER` is a note instead (since 2026-11-09).
- **Nothing for T2, T4, or T5:** no setup wizard, and no step for PostgreSQL, its read replica, or Azure Cosmos DB. T4 is part of every deployment; when Azure refuses every T4 size, or every size of its read replica, the run ends **NOT DONE** with the fix (a Region access request, or `t4SkuName`; or, when Azure refused them over the subscription's vCore quota for Azure Database for PostgreSQL, room in it, more quota, or another region), which only the person can act on. A Burstable `t4SkuName` has no replica: `DEPLOY.T4.REPLICA` is **Not supported**, with the fix. T5 needs no sign-in or key: T1's managed identity has its data-plane role, and Database Hub reads it with the person's Reader access.
- **When the person isn't an Owner:** an Owner runs `./scripts/grant-safety-stop.ps1` once, which **DONE** prints as its first note; it grants the nightly safety stop's role and the session control's roles together, and gives the person who deployed the control vault's secrets, so they can Run all with nothing to edit (`CONTROL.ROLE.DEPLOYER`, since 2026-11-19). Until then, Run all can't run a whole session, and T5's container stays between sessions and bills.
- **Once per deployment, required for the Database Agent beat: selecting T3 for Database Agents** (`HUB.AGENT.T3`, under **Please confirm**), a minute or two in Database Hub's **Manage agents**; everything else works without it. Database Agents has no API: pass on the link and the database the run prints, and [the steps](docs/database-agents.md), and never automate the portal.
- **Each viewer's GitHub sign-in for the Copilot chat in the Insights app,** once per browser, on their own GitHub Copilot plan. To remove it later, each viewer revokes **Database Hub Insights Ask** at github.com/settings/applications.
- **Running a session:** open `NB_DatabaseHub_Control` and select **Run all** (`DEPLOY.CONTROL` says where it is), after resuming the Fabric capacity, which no script resumes unless `fabric.manageCapacity` is on.

## Cost

- **Before you deploy, say what it costs:** `./scripts/estimate-cost.ps1` estimates it from Azure's list prices, with no sign-in. Preflight checks the same estimate against `monthlyCeilingUsd` and `sessionCeilingUsd` and stops at a hard ceiling.
- **A session from the PC stops by itself** (since 2026-11-19): `./scripts/start-demo.ps1` schedules an auto-stop 4 hours after its start (`-Hours` changes it; running it again starts the hours over), and `START.CONTROL.AUTOSTOP` says when. Pass that time on. When it's a **Warning** (the session control has no role yet), the nightly stop is the limit until an Owner runs `./scripts/grant-safety-stop.ps1` once.
- **When the person doesn't want new resources,** say what then won't work, rather than skipping parts quietly: for example, without `deploy.ps1` there's no T4, so no PostgreSQL in Database Hub, and no nightly safety stop, so T4 bills again after Azure starts it on its own 7 days after a stop. Without T4's read replica (`start-demo.ps1 -SkipT4Replica`), Database Hub's Read replica lag stays empty and the `replica-lag` beat isn't available; it bills only during a session, because `stop-demo.ps1` deletes it, and so does `deploy.ps1` at its end. T5 (Azure Cosmos DB) can't be stopped, so since 2026-11-19 its container, which holds its 400 RU/s, exists only during a session: the stops delete it and the starts create it, and only its private endpoint and DNS zone, when it has them, bill between sessions (since 2026-11-21, a new T5 in public mode has none unless a policy needs them: `DEPLOY.T5.NETWORK` says which). Until the session control's role can create the container again (`DEPLOY.T5.LIFECYCLE` is a **Warning**: an Owner runs `./scripts/grant-safety-stop.ps1` once), the container stays and its throughput bills between sessions too, unless the subscription's one free-tier account covers it; `estimate-cost.ps1` says which.
