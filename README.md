# Fabric Database Hub hybrid SQL demo

A low-cost, repeatable customer demo of **Microsoft Fabric Database Hub (preview)** and its in-Hub **Database Agent (preview)** across three SQL targets and one PostgreSQL target in one Azure resource group.

**The story:** fragmented visibility before; one hybrid estate in Database Hub after; then a live incident (locking, CPU, IO, a missing index, or an inefficient query) that the presenter investigates with the Database Agent. Every action the agent proposes needs human approval.

> **Preview disclosure:** Database Hub, the Database Agent, SQL VM performance monitoring, unified inventory, the Arc SQL monitoring setting, the telemetry endpoint, and Fabric Apps are previews and can change. This repo uses only documented interfaces and says plainly what's manual, unsupported, or not yet proven ([limitations](docs/limitations.md)).

## At a glance

`deploy.ps1` deploys everything below that has documented automation, with one command after `az login`, in parallel tracks: T1 with T3, T2, T4, and Fabric. In the default T2 mode, `JumpstartImage` (since 2026-11-05), T2 needs no person: the T2 host downloads [Arc Jumpstart](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/azure_jumpstart_arcbox/ITPro/_index.md)'s prebuilt SQL Server 2022 Standard guest disk and makes it `arcsql01`, and no Bastion is needed. After `az login`, a default deployment needs a person only for the Insights app's browser sign-in at the start of a run in a terminal you type in (about a minute, an estimate) and, when you aren't an Owner, for one command that an Owner runs once for the nightly safety stop's role (`./scripts/grant-safety-stop.ps1`); neither keeps the run from **DONE**. A clean first deployment took **91 minutes** to **DONE**, measured on 2026-11-06 from a fresh clone, in West US 3 with the default `lowest-cost` profile ([quick start](#quick-start)). The opt-in `PaygWizard` mode stops once instead, for about 10 minutes of a person's time, and finishes T2 in the same run (Phase 28). The redeploys measured below predate `JumpstartImage`; they restored T2 from a golden snapshot. With Phase 22's overlaps, a redeploy with the T2 golden snapshot took **63.7 minutes** end to end on 2026-10-23: T1 and T3 were ready at +26.8 minutes, 9.5 minutes sooner than in Phase 20, but T2 waited about 29.5 minutes for the SQL Server extension's download in its guest. Phase 20's redeploy, before those overlaps, took **38.8 minutes** on 2026-10-22. Neither run had a manual step, and the 30-minute target isn't met yet ([quick start](#quick-start)). [Deploy it, step by step](#deploy-it-step-by-step) comes next, then [automated vs manual](#automated-vs-manual), which lists every step, automated or not.

## Deploy it, step by step

**Where it goes:** into **your own Azure subscription** and **your own Fabric capacity**, in the same Microsoft Entra tenant. The demo is tested that way.

- **Azure:** the resource group `rg-dbhub-demo`, in West US 3 by default (`location` in your configuration; preflight checks that Database Hub supports the region). It holds T1 to T4, their network (no VM has a public IP), the workload runner, and the [nightly safety stop](#what-stops-or-pauses-on-its-own). Two more groups appear only if you use what they hold: `rg-dbhub-golden` keeps the optional T2 golden snapshot, and `rg-dbhub-control` holds the optional [on-demand activity control](#on-demand-activity-control-optional).
- **Fabric:** the workspace **Database Hub Demo**, with the lakehouse `LH_DatabaseHub`, on an F or Trial capacity. The scripts find both by name and create them when they're missing, so you never look up an ID.
- **Where you run the scripts:** your computer, the repository's [dev container](.devcontainer/devcontainer.json), or GitHub Codespaces. GitHub Actions is optional ([quick start](#quick-start)).

**Before you start** (once; people do these):

| You need | Who provides it |
|---|---|
| **Contributor** on the Azure subscription | The subscription's Owner |
| *Recommended, once per environment:* an **Owner** (or User Access Administrator) for the nightly safety stop's role. When you're one, `deploy.ps1` assigns it itself. Otherwise the run still ends **DONE** and prints one command for an Owner, `./scripts/grant-safety-stop.ps1`; until it's run, nothing stops T4 when Azure starts it again 7 days after a stop, while the VMs' nightly auto-shutdown and T3's auto-pause still apply | You, or the subscription's Owner |
| An **F or Trial Fabric capacity** you can assign, **running** while you deploy | You, or the capacity's administrator |
| The Fabric tenant setting **Users can access the Database hub (preview)**, and **Create workspaces** unless you already have a workspace | Your Fabric administrator |
| For the Insights app: the Fabric tenant settings **Fabric Apps (preview)** and **Dataset Execute Queries REST API**. Without them, the app isn't created, but the run still ends **DONE**, and the status page says why | Your Fabric administrator |
| Quota for about **8 vCPUs** of VM sizes with nested virtualization in the region | The subscription; preflight checks it |
| Outbound HTTPS from the VMs, as for their other downloads. In the default T2 mode, the T2 host also downloads its guest's disk from Arc Jumpstart's public storage (`jumpstartprodsg.blob.core.windows.net`) and Jumpstart's pinned script from GitHub (`raw.githubusercontent.com`) | The demo's network allows it; where your tenant's firewall or proxy restricts outbound traffic, its network administrator |
| PowerShell 7.4, the Azure CLI with Bicep, the .NET SDK, Node.js 24, and Git, or a codespace that has them | You |

**Steps** (91 minutes the first time, measured on 2026-11-06, most of it T2: its host build, about 27 minutes, then its Arc onboarding, about 33; after `az login`, you're needed only for the Insights app's browser sign-in at the start, about a minute, an estimate, and, when you aren't an Owner, an Owner runs one command once for the nightly safety stop's role):

1. **Get the code:** select **Use this template** on GitHub for your own copy, clone it with `git clone https://github.com/MarcBushong/fabric-database-hub-demo.git`, or open it in [GitHub Codespaces](https://codespaces.new/MarcBushong/fabric-database-hub-demo?quickstart=1).
2. **Sign in to Azure:** `az login` (in a codespace or a container, `az login --use-device-code`). The scripts never sign in for you, and never change your default subscription.
3. **Deploy, with one command:** `./scripts/deploy.ps1`. On the first run it writes your configuration from your sign-in, as `./scripts/init.ps1 -CreateAdminGroup` does: it picks your subscription and Fabric capacity, asking when there's more than one, creates the Microsoft Entra group `dbhub-demo-sql-admins`, which administers T3 and T4, with you as its owner, and asks for T2's mode (`JumpstartImage`, the default, needs no person; [options](#options-t2s-install-modes)). Then it checks everything (preflight), deploys T1, T3, T4, and the Fabric items in parallel while T2 builds, and waits for T2. In the default mode, the T2 host downloads Arc Jumpstart's SQL Server Standard guest disk (34 GiB), checks it, and makes it `arcsql01` while the guest has no network (T2's host build took about 27 minutes when measured on 2026-11-06); then it onboards the guest to Azure Arc with the SQL Server extension, pay-as-you-go, and monitoring, about 33 minutes more. In the opt-in `PaygWizard` mode, the run instead stops once for you, about 60 to 90 minutes in, for about 10 minutes through Bastion ([the guided stop](#the-guided-stop-about-10-minutes)). At the start, when the Rayfin CLI isn't signed in yet, a browser opens once for the Insights app's sign-in (on Windows, the CLI runs in a window of its own); the run doesn't wait for it, and only the app's step does, at most 15 minutes from the start. It starts only in a terminal you type in, not in CI or under an assistant ([Running it with an AI assistant](#running-it-with-an-ai-assistant)). Every run also sets up the [nightly safety stop](#what-stops-or-pauses-on-its-own), and ends by running the live-activity notebook once, analyze-only, so the [history report](docs/deployment.md#the-history-reports-snapshot-at-the-end-2026-11-06) has data. It keeps your PC awake, opens a [live status page](#while-it-runs), and prints what to expect.
4. **The ending:** the run ends with one banner. **DONE** means Database Hub shows every target, with where to look and which activity runs, and lists once, under **Please confirm**, what only you can confirm, such as a tenant setting the run couldn't read; none of it keeps the run from **DONE**. A clean first deployment also shows a few **Warnings** that need nothing, such as T4's `max_connections` waiting for a restart and the history report's blank measures, checked before the run's snapshot at the end fills the report ([the full list](docs/deployment.md#what-a-clean-first-deployment-shows-2026-11-06)). When the Insights app couldn't be created, **DONE** also says so, with its actual error and fix (step 7). When you can't assign roles, **DONE** also gives the one command an Owner runs for the nightly safety stop's role. **NOT DONE** says why (only what keeps it from **DONE**), the single next action, and the exact command, with the `-ConfigPath` you ran with: usually `./scripts/deploy.ps1` again, which continues where it stopped. When a fix you pulled meanwhile changed what runs on the VMs (their bootstrap or the workload runner), that run sends it to them again first, and the VM stops its earlier bootstrap run, if it's still going, and starts the new one. When the run started or created VMs and isn't **DONE**, one line says which now run and bill, and how they stop: `./scripts/stop-demo.ps1` now, or the nightly auto-shutdown. If the window closes or the PC restarts, run `./scripts/deploy.ps1` again; you never need a flag to continue. It starts VMs that were stopped, for example by the nightly auto-shutdown or `./scripts/stop-demo.ps1`, while preflight runs, and T4 too when it's stopped. It checks T1's monitoring plugin on every run, which can stop after a restart, and restarts it when it has.
5. **See it:** open **Database Hub** in the Fabric portal ([Database Hub](https://learn.microsoft.com/fabric/database/hub/overview)) and look at Estate and Performance ([Monitor a Microsoft SQL database](https://learn.microsoft.com/fabric/database/hub/monitor-sql)). Performance's problem panels, such as **High CPU resources over time**, **CPU spikes over time**, and **Databases limited by service tier** (as the preview names them, 2026-11-03), list only resources that have that problem, so they're expected to fill from the default `business-day` profile's bounded incidents at fixed minutes every hour, each a few minutes after it starts ([the hourly incidents](docs/demo-walkthrough.md#the-hourly-incidents-business-day)). For one right now, run `./scripts/demo-control.ps1 -Target T2 -Scenario incident:cpu-pressure -Duration 25`. Then investigate it with the Database Agent, approving or cancelling each action it proposes.
6. **Keep the finished build** (optional): `./scripts/capture-t2-golden.ps1`, then `./scripts/test-t2-golden.ps1 -Onboard`, so the next redeploy restores T2 in about 30 to 45 minutes (an estimate) instead of making it again. In the default `JumpstartImage` mode that's only a speed-up: it skips T2's host build (the image's download, its first boot, and the image check), which took about 27 minutes when measured on 2026-11-06, and the snapshot bills every month it exists ([cost](#cost)). In `PaygWizard` mode it also saves the next guided stop.
7. **The Insights app:** part of every deployment. `deploy.ps1`'s Fabric track creates it, after the browser sign-in it started at the beginning of the run. Open the app from its item in the workspace. When it can't be created, for example because a tenant setting is off or nobody finished the sign-in, the deployment goes on and still ends **DONE**: the status page shows the app's step as **Failed**, in red, with the actual error and the fix, and the **DONE** banner and the console say the same, as `Failed (doesn't block DONE): the Insights app. ...`. Once that's fixed, `./scripts/configure-fabric-app.ps1 -SignIn` adds the app, with one browser sign-in that only you can do; after a run that ended **DONE**, the next `./scripts/deploy.ps1` starts over and tries again too.
8. **Between sessions:** `./scripts/stop-demo.ps1`, which also stops T4 and says the date Azure starts it again on its own, seven days later, and `./scripts/start-demo.ps1` next time, which takes about 8 minutes. If you forget, every evening at `autoShutdownTime` (19:00 Pacific by default) the VMs shut down and the nightly safety stop deallocates any that still run and stops T4 ([what stops or pauses on its own](#what-stops-or-pauses-on-its-own)).
9. **Remove it:** `./scripts/destroy.ps1`.

### The guided stop (about 10 minutes)

**Only in the opt-in `PaygWizard` mode.** The default `JumpstartImage` mode has no guided stop and needs no Bastion to deploy ([options](#options-t2s-install-modes)). `PaygWizard` builds the guest from installation media, and installing pay-as-you-go SQL Server without a product key is documented only in setup's wizard, so a person makes that choice once per guest build ([ADR 0006](docs/adr/0006-sql-editions-and-licensing.md)). Everything around it is automated:

- **When:** about 60 to 90 minutes after the start (an estimate; it can be later, and the run waits). The start banner and the status page say so, and the run prints its progress with an estimate of when it comes. Keep the window open.
- **What you see:** a large **WAITING FOR YOU** banner, a beep, and the console window flashing; the browser opens `archost01`'s page in the Azure portal; the status page turns **Waiting for you**, with the steps, the link, and a countdown; a short reminder every 5 minutes; and one plain line for an assistant to relay, `HUMAN ACTION REQUIRED: DEPLOY.T2.GUIDEDSTOP ...`.
- **What you do:**
  1. In the portal, select **Connect**, then **Bastion**, and sign in to `archost01` as its administrator. The password: a one-time password is already on your clipboard (never shown or saved), or in the demo's key vault with the [Key Vault opt-in](docs/deployment.md#opt-in-the-password-in-key-vault-instead-of-the-clipboard). **Without a working clipboard** (GitHub Codespaces, Cloud Shell, an SSH session, or Linux without a desktop and `xclip`), nothing is set or shown: first open `archost01` in the portal, then **Help**, then **Reset password**, keep the user name, and type a password of your own choosing ([reset a password](https://learn.microsoft.com/troubleshoot/azure/virtual-machines/windows/reset-rdp)). Either way, it's rotated afterward.
  2. Virtual Machine Connection to the guest `arcsql01` opens by itself. The guest has signed itself in, once, for this step, and SQL Server setup is open and pre-filled.
  3. On the **Edition** page, choose **Use pay-as-you-go billing through Microsoft Azure**, then **Standard**; accept the license terms.
  4. On the **Azure Extension for SQL Server** page, select **Use Azure Login** and sign in with your own Azure account. The sign-in window is an Internet Explorer-based control, so before setup opens, the host turns IE Enhanced Security Configuration off for administrators in the guest and adds Microsoft's sign-in sites to Trusted sites, and it undoes both afterward. **If the Azure Login window stays blank, or Internet Explorer says content from `https://login.microsoftonline.com` is blocked,** follow the dialog's directions: select **Add...**, then **Add**, to put the Microsoft sign-in page in Trusted sites, and **Close**. Then select **Use Azure Login** again. Repeat for any other sign-in site it names. The dialog can open behind setup's window, so check with Alt+Tab. **If the window stays blank and no dialog comes at all,** IE Enhanced Security Configuration was still on when setup started, and turning it off while setup is open doesn't reach setup (confirmed live on 2026-10-30). Cancel setup. In the guest, open **Server Manager** > **Local Server** > **IE Enhanced Security Configuration** and set **Administrators** to **Off**. Then start setup again: `C:\DbHubDemo\setup\Start-GuidedSetup.ps1` opens it pre-filled, and the host also reopens it within about 5 minutes; on a guest that has neither, run `setup.exe` from the SQL Server media drive. Redo steps 3 and 4. The cleanup after setup turns the setting back on. Never type into the service principal fields: "Requires all input values for AZURESERVICEPRINCIPAL" only means you haven't signed in yet. ([Troubleshooting](docs/troubleshooting.md#t2-the-setup-wizard-step) has more.)
  5. Select **Next** on the pre-filled pages, then **Install**. When setup is complete, select **Close**, and close the Bastion tab.
- **Then, by itself:** the host checks what you installed (Standard, the default instance, the Azure extension). If something's wrong, such as Evaluation or a named instance, it shows the documented fix and keeps waiting. Otherwise it signs the guest out, turns its automatic sign-in off, turns IE Enhanced Security Configuration back on and takes the sign-in sites out of Trusted sites, and removes the sign-in data that setup leaves; Arc gets pay-as-you-go and monitoring; Bastion is removed; and the host password is rotated.
- **How long the run waits:** at least 45 minutes after it asks, until a time it prints. After that, it ends **NOT DONE**; run `./scripts/deploy.ps1` again when you have about 15 minutes, and it guides you again.

### While it runs

- **The status page,** `out/deploy-status.html`, opens at the start and updates itself every 10 to 15 seconds, offline. Its banner says **Deploying, no action needed** (you can step away), **Waiting for you**, **Done**, or **Stopped, not done**, with every step of every track below it: its status, its time, and a one-line message. An Azure-side wait, such as an extension that a policy in your tenant installs, says "no action needed". The steps that never block **DONE**, the Insights app's and, last, the history report's snapshot, say "(doesn't block DONE)". When one of them didn't work, it shows **Failed** in red, or **Action needed** (such as a paused capacity), with its actual error and fix, and the same text is in a red **Needs attention** box right under the banner, also once the run is **Done**. `./scripts/status.ps1 -Watch` shows the same in a second terminal, anywhere.
- **Keep the machine on:** `deploy.ps1` keeps a Windows PC and its display awake until it ends; plug a laptop in and leave it open. On macOS and Linux, keep it awake yourself.
- **If something goes wrong:** run `./scripts/deploy.ps1` again. When **NOT DONE** repeats, `./scripts/collect-diagnostics.ps1` writes a redacted zip for a **Deployment problem** issue ([getting help](#getting-help)).
- **To stop it:** Ctrl+C stops the run within seconds, its background processes too; the PC may sleep again, and the console and the status page say **NOT DONE**, **Stopped, not done**, with the command that continues where it stopped, and that also brings the VMs a fix you pull before you run it. Stopped at the guided stop, Bastion stays up and the host password stays valid until the next run cleans them up when it gets to T2, even when setup finished meanwhile (it isn't **DONE** before), or until `./scripts/stop-demo.ps1` does, which is what to run if you're done for the day ([details](docs/deployment.md#one-command-one-guided-stop-phase-28)).

### In GitHub Codespaces

The repository's dev container has every tool, in a codespace or on your machine. A codespace stops after 30 minutes without activity by default; terminal output counts as activity, and `deploy.ps1` prints progress at least every 5 minutes, but raise the timeout before a first run to be safe: **Settings** > **Codespaces** > **Default idle timeout**, up to 240 minutes, for codespaces you create afterward, or `gh codespace create --idle-timeout 240m` ([GitHub Docs](https://docs.github.com/codespaces/setting-your-user-preferences/setting-your-timeout-period-for-github-codespaces)). In the opt-in `PaygWizard` mode, a codespace has no clipboard for the script, so the guided stop uses the portal's **Reset password** (above). A codespace can't open a browser: preview the status page through a forwarded port, as `deploy.ps1` prints, or use `./scripts/status.ps1 -Watch`. The Insights app's sign-in runs in the codespace's terminal, where its browser sign-in may not complete; the run still ends **DONE**, and `./scripts/configure-fabric-app.ps1 -SignIn` adds the app later from a machine with a browser.

**Cost:** the default ceilings are $15 a session and $375 a month (`sessionCeilingUsd`, `monthlyCeilingUsd`; $250 before 2026-11-04). Preflight prices the deployment for your region at run time and warns when an estimate passes either ceiling ([cost](#cost)). **Stuck?** See [troubleshooting](docs/troubleshooting.md), or open an issue with the **Deployment problem** template ([getting help](#getting-help)).

## Running it with an AI assistant

An assistant such as GitHub Copilot can drive the whole deployment for you: in the default T2 mode, `JumpstartImage`, T2 needs no person. Your sign-ins stay yours, and no assistant should do them for you: `az login`, the Insights app's browser sign-in, and, only in the opt-in `PaygWizard` mode, the guided stop's, once, for about 10 minutes.

- **What the assistant can do:** run `./scripts/deploy.ps1`, `./scripts/status.ps1 -Watch`, and `./scripts/collect-diagnostics.ps1`; read the results and the status page; and run `./scripts/deploy.ps1` again after an interruption, since it continues where it stopped with no flag, and starts VMs that were stopped, for example by the nightly auto-shutdown. `deploy.ps1` notices a session that can't take keyboard input, says so at the start, and goes on; on a first run in such a session it never asks, and a choice it can't make is **NOT DONE** with the parameter to pass (`./scripts/init.ps1` takes them). A first run that can't ask writes `JumpstartImage`, the default.
- **What you must do, and when** (only in the opt-in `PaygWizard` mode, about 60 to 90 minutes after the start, for about 10 minutes): sign in to `archost01` through Bastion; choose **pay-as-you-go** and **Standard** in the pre-filled setup; and sign in to Azure on setup's **Azure Extension for SQL Server** page ([the guided stop](#the-guided-stop-about-10-minutes)). If the **Use Azure Login** window stays blank, or Internet Explorer says content from `https://login.microsoftonline.com` is blocked, follow the dialog's directions: **Add...**, then **Add**, to put the Microsoft sign-in page in Trusted sites, and **Close**; then select **Use Azure Login** again, and repeat for any other sign-in site it names. If it stays blank and no dialog comes, cancel setup, set **IE Enhanced Security Configuration** for **Administrators** to **Off** in the guest's **Server Manager** > **Local Server**, and start setup again ([the guided stop](#the-guided-stop-about-10-minutes), step 4). Without a clipboard, you first set the host's password yourself in the portal (**Help** > **Reset password**). Plan to be at a browser then; the start banner says when, as `PLAN FOR A PERSON: DEPLOY.T2.GUIDEDSTOP ...`.
- **The handoff:** in `PaygWizard` mode, at the guided stop, the run prints one plain line for the assistant to relay to you, `HUMAN ACTION REQUIRED: DEPLOY.T2.GUIDEDSTOP - ...`, with the time limit and the status page's path, and repeats it every 5 minutes.
- **It waits, then resumes:** the run waits at least 45 minutes once it asks, and continues by itself when setup is done. If nobody came in time, it ends **NOT DONE**; `./scripts/deploy.ps1` again guides you from that step.
- **Also yours:** `az login` itself, and the Insights app's browser sign-in. `deploy.ps1` starts that sign-in only in a session that can take keyboard input, so under an assistant, run `./scripts/configure-fabric-app.ps1 -SignIn` yourself in a terminal, before the deployment (its Fabric track then uses that sign-in) or after it. Without it, the run still ends **DONE**, and the status page shows the app as **Failed**, with that command. When you aren't an Owner, **DONE** also prints `./scripts/grant-safety-stop.ps1` for an Owner to run once, for the nightly safety stop's role; an assistant can't grant it for you.
- **Fully unattended:** the default `JumpstartImage` mode, or `ProductKey` mode with your own SQL Server Standard product key, set in the session as above ([options](#options-t2s-install-modes)); both give the same Database Hub views with no person needed for T2. `Developer` mode is unattended too, but T2 then shows in Estate only.

## Quick start

The shortest correct path from a clone to a running demo, in your own subscription and tenant, with no IDs to look up. [Deployment](docs/deployment.md) has every option, and [troubleshooting](docs/troubleshooting.md) helps with anything that isn't **Pass**.

[![Open in GitHub Codespaces](https://github.com/codespaces/badge.svg)](https://codespaces.new/MarcBushong/fabric-database-hub-demo?quickstart=1)

Every tool is in the repository's [dev container](.devcontainer/devcontainer.json), on your machine or in GitHub Codespaces (a 4-core machine). Without it, you need PowerShell 7.4, the Azure CLI with Bicep, the .NET SDK, Node.js 24, and Git ([tools](docs/prerequisites.md#tools)).

```powershell
# Once: clone (a codespace already has the clone) and sign in
git clone https://github.com/MarcBushong/fabric-database-hub-demo.git
cd fabric-database-hub-demo
az login                                     # you sign in; in a codespace or a container: az login --use-device-code

# Deploy: one command. The first run writes config/demo.config.json from your sign-in (as init.ps1 does), then
# preflight, the infrastructure, and T1 with T3, T2, T4, and Fabric as parallel tracks; it waits for T2 (nothing needs
# you in the default JumpstartImage mode; one guided stop in the opt-in PaygWizard mode), and ends DONE or NOT DONE.
# At the start, a browser opens once for the Insights app's sign-in, and the run goes on meanwhile. Run it again to
# continue where it stopped.
./scripts/deploy.ps1
./scripts/grant-safety-stop.ps1              # only when DONE asks for it: an Owner, once, for the nightly safety stop's role
./scripts/status.ps1 -Watch                  # optional, in a second terminal: the live status page's view
./scripts/configure-fabric-app.ps1 -SignIn   # only when the run says the Insights app wasn't created: it deploys with your az login, and opens a browser sign-in only if Fabric refuses that

# Optional, before the first deploy: write the configuration or check, on their own
./scripts/init.ps1 -CreateAdminGroup         # writes config/demo.config.json from your sign-in; asks only when there's a choice
./scripts/preflight.ps1                      # checks only (it registers missing providers), and the cost against both ceilings

# Optional, once per guest build: keep the finished T2 host for a faster redeploy (in PaygWizard mode, after the
# guided stop, so a redeploy needs no manual step)
./scripts/capture-t2-golden.ps1
./scripts/test-t2-golden.ps1 -Onboard

# Fabric: deploy.ps1's Fabric track runs these; run one yourself to repeat it
./scripts/configure-fabric.ps1 -ImportDashboard
./scripts/configure-powerbi.ps1
./scripts/configure-fabric-app.ps1
./scripts/configure-fabric.ps1 -SkipHubChecks -SkipNotebookImport -RunLiveActivity   # the history snapshot deploy.ps1 takes last

# Each session
./scripts/start-demo.ps1 -WarmUpMinutes 30    # business-day by default: bounded incidents at fixed minutes every hour
#   or, for the quieter demo with the steady mix only: ./scripts/start-demo.ps1 -ActivityProfile baseline -WarmUpMinutes 30
./scripts/status.ps1                          # read-only: health, profiles, Bastion, and the cost so far
./scripts/validate.ps1 -Area Hub, Telemetry   # Estate and fresh telemetry for each target
./scripts/demo-control.ps1 -Target T2 -Scenario incident:cpu-pressure -Duration 25   # one incident right now, in place of T2's profile
./scripts/reset-demo.ps1                      # back to a known state, without a redeploy
./scripts/stop-demo.ps1 -SaveHistory          # saves the session's history for the report and the app, then stops

# When a run doesn't finish: a redacted zip for a Deployment problem issue
./scripts/collect-diagnostics.ps1

# For good
./scripts/destroy.ps1
```

- **`init.ps1`** ([deployment](docs/deployment.md#first-run-initps1)), which `deploy.ps1` runs by itself when there's no configuration, reads the subscriptions your sign-in can see with `az account list`, the one Azure CLI call before the subscription guard, and asks which one when there's more than one; it never changes your default subscription. After the guard, it fills in your tenant, account, and budget-alert address, the Fabric capacity you can assign (it asks when there's more than one), and the workspace name, "Database Hub Demo" by default. With `-CreateAdminGroup`, it creates the P6 group `dbhub-demo-sql-admins` with you as its owner when no group has that name; where only administrators may create groups, it prints their steps instead. It asks for T2's mode: `JumpstartImage`, the default, needs no person and shows T2 in Database Hub's Performance; `PaygWizard` shows the same after one guided stop of about 10 minutes per guest build; and `Developer` needs no person but shows T2 in Estate only. It writes only the Git-ignored file, validated against the schema and never over an existing one without `-Force` (the old one goes to `out/config-backup` first), and prints the exact next steps. `-WhatIf` writes nothing and creates nothing.
- **The Fabric items, with no IDs:** `deploy.ps1`'s Fabric track finds the workspace and the lakehouse `LH_DatabaseHub` by name, and creates them on your capacity when they're missing ([ADR 0021](docs/adr/README.md)). It imports the notebooks that are missing, so a new workspace gets them without asking; `fabric.importNotebooks` true, which `init.ps1` writes for a new workspace, also updates them from the repository on every deploy. A new lakehouse gets its history tables from one run of `NB_DatabaseHub_LiveActivity`, and every `deploy.ps1` ends with another, analyze-only, once its telemetry checks pass, so the history report has the run's data ([deployment](docs/deployment.md#the-history-reports-snapshot-at-the-end-2026-11-06)). Creating a workspace needs the Fabric tenant setting "Create workspaces" for you, and an F or Trial capacity that you can assign and that's running.
- **Still manual, by design:** the sign-in; Contributor (P1, which an Owner assigns); the nightly safety stop's role when you can't assign it (P16, one command for an Owner); the Fabric tenant settings (P4, P12, and P13); the capacity itself; T2's guided stop, only in the opt-in `PaygWizard` mode; and the Rayfin CLI's browser sign-in for the Insights app (P14), which `deploy.ps1` starts for you at the beginning of the run. [Automated vs manual](#automated-vs-manual) gives each reason.
- **The activity profile (`activityProfile`):** `business-day` by default since 2026-11-03: the steady OLTP mix plus bounded incidents at fixed minutes past each UTC hour on every target, so Database Hub's Performance page, the report's incident views, and the Database Agent have something to show within the hour, with no extra command ([the schedule](docs/demo-walkthrough.md#the-hourly-incidents-business-day)). `deploy.ps1` and `start-demo.ps1` set `baseline` while their own Run Commands on a VM run and switch to `business-day` once those are done, so an incident never slows them, also when a run ends **NOT DONE**, fails, or is stopped with Ctrl+C. For the quieter demo, set `"activityProfile": "baseline"` in your configuration, or pass `-ActivityProfile baseline` to `start-demo.ps1`. A configuration that `init.ps1` wrote before this change names `baseline` and keeps it; one without the key gets `business-day`, which the run says once, and its cost check includes it ([ADR 0010](docs/adr/0010-workload-generator-technology.md#activity-profiles-business-day-by-default-2026-11-03)).

## On-demand activity control (optional)

Start the demo's activity from a Fabric notebook when you want it, watch it live in the same notebook, and know it stops by itself ([ADR 0020](docs/adr/0020-on-demand-activity-control.md); the [notebook's guide](fabric/control/README.md)).

- **How it works:** the notebook `NB_DatabaseHub_Control` sends one request (a scenario per target and a duration) to an Azure Automation webhook. Its runbook checks the request against the scenario catalog's allow-lists, refuses it while another run is active, creates the run's own **auto-stop** first, starts what's stopped, and sets each target's activity profile. **Stop now** in the notebook, the auto-stop, the VMs' nightly shutdown, the [nightly safety stop](#what-stops-or-pauses-on-its-own) that every deployment has, and the control's own daily T4 safety stop each stop it by themselves, through Azure Resource Manager only. There's no recurring schedule.
- **A local session takes over:** `stop-demo.ps1` removes a run's pending auto-stop, and so does `start-demo.ps1`, with a **Warning** that the VMs now run until `stop-demo.ps1` or the nightly auto-shutdown at its time (`START.CONTROL.AUTOSTOP`). If a run's stop job is already queued or running, `start-demo.ps1` first waits up to 10 minutes for it to finish (`START.CONTROL.STOPJOB`).
- **It's optional and needs an Owner once:** `./scripts/setup-activity-control.ps1` sets it up with Contributor, and an Owner runs `./scripts/setup-activity-control.ps1 -GrantRole` once, signed in with multifactor authentication, to create the one custom role and its three assignments. Without an Owner, use `./scripts/demo-control.ps1` from your machine, which needs only Contributor. Turn it on with `control.enabled` in your configuration. You don't need it to keep T4 stopped: since 2026-11-05 the nightly safety stop does that in every deployment ([ADR 0024](docs/adr/0024-nightly-safety-stop.md)).
- **The webhook URL is the credential.** It's kept only as a secret in a Key Vault in `rg-<prefix>-control`, which only the users you name can read; the notebook reads it for each request and never prints it.

### Why it may need a second workspace

The notebook reads the webhook URL from that vault, and a Fabric notebook reaches a vault without public access only through a **managed private endpoint**. Network isolation in Fabric is per workspace, not per folder: a managed private endpoint creates a **managed virtual network for the whole workspace**, which turns off starter pools, so **every** Spark notebook in that workspace then starts in 3 to 5 minutes instead of seconds ([managed virtual networks](https://learn.microsoft.com/fabric/security/security-managed-vnets-fabric-overview)); the control notebook's runs started in 107 to 166 seconds (2026-10-27). A folder can't have a network of its own. Putting the endpoint on the demo's workspace would slow its other notebooks too, so where one is needed, the control notebook gets its own workspace.

So `setup-activity-control.ps1` adapts to your tenant (`control.vaultNetworkMode`, default `auto`):

| Your tenant | The vault | The notebook |
|---|---|---|
| New Key Vaults can keep public access | Public, with access granted per user through Microsoft Entra roles | In a folder, "DBHub Control", of the demo's existing workspace: it starts fast |
| An Azure Policy makes new vaults private (for example a Modify that sets `publicNetworkAccess` to `Disabled`) | Private | In a separate workspace, "DBHub Control", on the same capacity, with a managed private endpoint to the vault that the script creates and approves. Its sessions take 3 to 5 minutes to start |

`public` and `private` force a path. `public` in a tenant whose policy would make the vault private is refused before anything is created: the script names the policy and never adds its exclusion tag, because opting out of a network control is your governance team's decision. `destroy.ps1` keeps the control; `setup-activity-control.ps1 -Remove` deletes it ([cleanup](docs/cleanup.md#the-on-demand-activity-control)).

## The baseline run: why it matters, and when it doesn't

**What it runs.** The `baseline` activity profile runs the `healthy-baseline` scenario as back-to-back 30-minute runs ([`activity-profiles.json`](scenarios/activity-profiles.json)): the steady Contoso Care mix of front-desk, billing, and scheduling lookups and small updates that stay within the seeded values.

| Target | Sessions | Intensity | What it does there |
|---|---|---|---|
| T1 `sqlvm01`, T2 `arcsql01` | 2 | 3 | Low, flat CPU; steady `Batch Requests/sec` and `Transactions/sec`; `Processes blocked` at 0 |
| T3 `ContosoCare` | 1 | 2 | The same, lighter. It also keeps the serverless database awake, which bills vCore-seconds, inside the free monthly allowance first when T3 has the free offer |
| T4 `contosocare` | 1 | 2 | The same lookups, a work-item update, and an audit row; low CPU and connections |

- **The quiet profile:** set `"activityProfile": "baseline"` for a demo without incidents; the default since 2026-11-03 is `business-day`, which runs the baseline under bounded incidents every hour.
- **Under the incidents:** `business-day` and the showcase run it beneath their incidents.
- **On its own:** in the control notebook, `"scenario": "baseline"` for a target runs it alone, for up to 120 minutes; `./scripts/start-demo.ps1 -ActivityProfile baseline` runs it until `./scripts/stop-demo.ps1` or the nightly auto-shutdown.

**Why it matters:**

- **CPU spikes stays empty without history.** A target that sent no telemetry in the previous 48 hours has nothing to spike against. Demo VMs are deallocated most of the time, so that's the usual state.
- **Recommendations need days, not minutes.** Azure SQL Database's advisor needs at least a day of the same pattern, and PostgreSQL's Advisor up to a week. A single session never produces them; T3's automatic plan correction is the one exception ([above](#recommendations-and-optimizations)).
- **Incidents stand out against normal load.** **Recent signal changes**, a before-and-after chart, and an agent's "is this sustained or a spike?" all compare the incident with what came before. Without a baseline, the first minutes of an incident are also the first minutes of data.
- **T3 stays awake.** Without activity, the serverless database pauses after its auto-pause delay (`t3AutoPauseMinutes`, 15 by default), and its charts show gaps. "No data" means neither healthy nor down ([FAQ](https://learn.microsoft.com/fabric/database/hub/faq)).

**Why it doesn't:**

- **Most visuals fill on absolute thresholds within one session:** High CPU (over 80%, *observed 2026-11-03*; on T1 and T2 intermittent, *observed 2026-11-04*), waits by category, blocking, deadlocks, log, databases limited by service tier, and T4's CPU, connections, failed connections, IOPS, and storage.
- **The showcase brings its own baseline:** it runs the baseline under its incidents, so Run all 30 minutes before the audience is enough for a full demo of those visuals.

**How long to run it** (costs are dated examples: West US 3 list prices from the Azure Retail Prices API, 2026-11-03):

Prefer `baseline` to `business-day` here: hourly incidents raise the baseline that the next day's spikes are compared with (an inference, since the computation isn't documented) | About 1.4 billed hours more: about **$1.71-$3.08** |

So with the safety stop, $375 covers about 118 running hours a month: about 59 showcases, or about 34 with a day-before baseline each; without it, about 18 hours. ## Cost

- **Ceilings:** a hard **$375 a month** for idle plus light use (preflight fails above it) and **$15 per demo-day session** (a Warning). The deployment adds a budget at `monthlyCeilingUsd`, with alerts at 50%, 80%, and 100%. Every default is the cheapest working option except T4's size: since 2026-11-04 it's General Purpose `Standard_D4ds_v5` (4 vCores), with autonomous tuning, at the owner's direction ([ADR 0016](docs/adr/0016-cost-profiles.md), [ADR 0019](docs/adr/0019-t4-postgresql-flexible-server.md)).
- **Why $375 (since 2026-11-04; $250 before):** the worst case after T4 restarts itself. Azure starts a stopped flexible server again after 7 days, and the 4-vCore T4 then bills about $0.356 an hour (a dated example: West US 3, list prices, 2026-11-05, the same as on 2026-11-03). When a safety stop is fully in place, each restart counts as about a day, about $34 a month; otherwise the rest of the month, up to about $256 ([cost management](docs/cost-management.md#dated-example-the-4-vcore-t4-default-and-the-375-ceiling-2026-11-04)). Since 2026-11-05 every deployment sets up that safety stop, the [nightly safety stop](#what-stops-or-pauses-on-its-own); it's fully in place when its schedule is enabled, its role is assigned on `rg-<prefix>-<env>` (P16), and its last run didn't fail. The on-demand control's daily T4 safety stop, when it's fully in place, counts too. An existing environment gets the new budget at its next `./scripts/deploy.ps1 -FromStage Infrastructure`; a configuration that sets `monthlyCeilingUsd` keeps its value.
- **To stay cheap:** set `t4SkuName` to `Standard_B1ms` (which turns autonomous tuning off), set `t4Enabled` to `false`, or lower `monthlyCeilingUsd`. Preflight's monthly check, and `start-demo.ps1`'s, give the same three options.

- **The default `business-day` profile adds nothing to the estimate (2026-11-03):** its two T3 incidents an hour (`resource-governance` at :15 and `log-rate-pressure` at :45, 5 minutes each) drive the serverless database to its maximum vCores, and the estimate already prices T3 at its maximum for every hour a profile keeps it awake (`t3ActiveShareOfMaxVcores` 1.0 in `config/profiles.json`), so the session and month estimates and both ceilings stay as they were. The incidents use the free offer's monthly vCore-second allowance faster, which the estimate counts at the same maximum. The VMs and a provisioned T4 cost the same whatever the load. What no estimate counts, T3 between its minimum and maximum vCores and the extra disk operations, came to at most $0.51 a session and $1.01 a light-use month in a dated estimate (2026-11-03, West US 3, list prices from the Azure Retail Prices API), well within both ceilings ([cost management](docs/cost-management.md#activity-profiles-business-day-phase-28-follow-up)).
- **Measured (2026-10-21 and 2026-10-22):** Phase 16's two-day test cycle, from a fresh build through stop and destroy in a disposable environment, came to about $4.50: its measured hours at the Retail Prices API's list prices, not a billed amount.

It bills every month it exists, also after destroy, until `destroy.ps1 -IncludeGolden` deletes it. Dated example (2026-10-22, $0.05 per GB-month for Standard HDD snapshots, the same list price on 2026-11-05): at most about $6.40 a month in the estimate, which prices the 128 GiB provisioned size, and about $1.85 billed for the 37 GiB a `PaygWizard` host used. ## Clean up

- **After every session:** `./scripts/stop-demo.ps1` turns every activity profile off, waiting at most about 3 minutes for both VMs at once, shuts the guest down, and deallocates both VMs, also when a VM is busy with an incident, which stops with it. `-ParkT2` stops only T2, and `-RemoveT3` also deletes T3 until the next start. Ask the capacity's administrator to pause it if nothing else needs it. If you forget, the VMs' auto-shutdown and the nightly safety stop stop the VMs and T4 that evening ([what stops or pauses on its own](#what-stops-or-pauses-on-its-own)).
- **For good:** `./scripts/destroy.ps1` deletes the Arc SQL Server instances, then the Arc machine, then the resource group, then the deployment record and the group's budget, which both outlive the group, and checks that nothing is left behind ([cleanup](docs/cleanup.md)). Verified live in a disposable environment (2026-10-22): the group, the Arc machine and its SQL instance, the deployment record, and the managed identities were gone, and a subscription snapshot compared with the one before deploy showed nothing left.
- **The golden snapshot stays, when you captured one:** destroy keeps `rg-<prefix>-golden`, so the next `deploy.ps1` restores T2 from it (in `PaygWizard` mode, without the setup wizard); `-IncludeGolden` deletes it too. Without one, the next deploy makes T2 again: in the default `JumpstartImage` mode with no person, so destroy doesn't ask for a snapshot there. It refuses only to destroy a `PaygWizard` environment that no boot-verified snapshot protects, unless `-WithoutGolden` accepts losing the wizard's work.
- **The nightly safety stop's role stays:** its identity, Automation account, schedules, and role assignment go with the resource group, but its custom role, "DbHub Demo Safety Stop", is a definition in the subscription. After destroy it has no assignment and costs nothing, and the next deployment uses it again; `DESTROY.SAFETYSTOP.ROLE` gives the `az role definition delete` command for an Owner who wants it gone.
- **Tenant governance:** your tenant's own automation may give the demo's identities role assignments outside the demo, as it did in the test environment. They stay behind, orphaned, after destroy; they don't bill, the residual check reports them as a **Warning** that names the scope, and removing one needs Owner or User Access Administrator.
- **Fabric items stay:** destroy doesn't touch the workspace, so delete the notebooks, the dashboard, the model, the report, and the app there when you no longer need them.
- **The on-demand activity control stays** (when you set it up): destroy keeps `rg-<prefix>-control`. `./scripts/setup-activity-control.ps1 -Remove -WhatIf` shows what it deletes; without `-WhatIf`, it deletes the control's Fabric items, its role assignments (an Owner), and its Azure resources, and the group only when nothing else is in it.

## Your sign-in and tokens

**Where you sign in:**

- `az login` on your PC.
- Only in the opt-in `PaygWizard` mode, at the guided stop, once per guest build: to the T2 host through Bastion, and to Azure on SQL Server setup's Azure page inside the T2 guest. The default `JumpstartImage` mode needs no sign-in for T2 beyond `az login`.
- The Rayfin CLI, once, for the Insights app: `deploy.ps1` starts its browser sign-in at the beginning of the run.

**What the scripts do with it:**

- Nothing from your sign-in is stored in the repository, the configuration, Key Vault, logs, or snapshots.
- Short-lived tokens travel only in memory or as protected Run Command parameters, and the Run Commands that carried them are deleted right after. A Run Command that receives the one-time host password or the SQL Server product key clears the VM's Windows PowerShell log afterward when that log recorded the value (a Warning, because endpoint protection may report it), and never the Security log.
- The host password for the guided stop goes to your clipboard, never shown, or to the Key Vault opt-in; without either, nothing is set, and you choose one yourself with the portal's **Reset password**. Either way it's rotated afterward ([ADR 0009](docs/adr/0009-secrets-handling.md)).
- The guest signs itself in once for the guided stop (Phase 28): its Administrator gets a temporary random password that Windows keeps only as an LSA secret, never in plain text, and right after setup (or a failure or time-out) automatic sign-in is turned off, the secret is deleted, the password is rotated, and the console is signed out. While that window is open, an administrator of the T2 host, or someone with the guest's disk, could read the temporary password; they could take over the guest anyway, so the exposure is short and low ([security model](docs/security-model.md#the-guests-one-automatic-sign-in-phase-28)).
- With `assignRoles: true`, Arc onboarding uses the host's own Onboarding-only identity, so your token isn't used at all. Without it, your token (valid for about an hour) is used, and endpoint protection on the host can record the command line that carried it.
- Right after setup, and after every Arc onboarding, the scripts remove the sign-in data left on the VMs and verify that none remains. The build fails if any remains, and so does an automatic sign-in that's still armed. `./scripts/check-sign-in-data.ps1` checks any time, and reports counts and locations only. It never clears the Security log on its own; it gives you the command.
- The golden snapshot is captured only after a clean scan. Nothing from your sign-in is kept or reused across redeploys, so in `PaygWizard` mode each new guest build asks you to sign in again.
- **The Jumpstart image's published password** (`JumpstartImage` mode): the T2 host reads it during the deploy from Arc Jumpstart's own script at a pinned commit, checked by its SHA-256, and keeps it only in memory; it's never in the repository, the configuration, or a log. The host uses it once, while the guest has no network, to replace it with a random password that it keeps protected like the other guest passwords, and it disables `sa` and every other SQL login ([ADR 0009](docs/adr/0009-secrets-handling.md)).

**What stays on your own PC:** your Azure CLI sign-in, and the Rayfin CLI's own sign-in if you made one. End them with `az logout` and, from the repository root, `./out/fabric-app/node_modules/.bin/rayfin logout` when you're done; the scripts never do that.

**Mode tip:** the default `JumpstartImage` mode, a product key (`ProductKey`), or `Developer` mode avoids the guided stop's sign-ins entirely.

## Getting help

- **A result that isn't Pass:** every **Fail**, **Warning**, and **Manual action required** comes with its remediation, and [troubleshooting](docs/troubleshooting.md) explains the common ones; the [FAQ](docs/faq.md) and [limitations](docs/limitations.md) cover what's out of scope. `./scripts/status.ps1` (read-only) shows where an environment stands.
- **A deployment that doesn't finish:** `deploy.ps1` ends **NOT DONE** with the next command; run it, and if the same thing happens again, run `./scripts/collect-diagnostics.ps1`. It writes a zip of the run's results, progress, and logs, redacted, with your IDs and account replaced, and refuses to write one that its secret scan doesn't pass. Open an issue with the **Deployment problem** template, which asks for the command, how the run ended, the results that aren't **Pass**, and the zip (read it before you attach it).
- **A bug in the code or the docs:** open an issue with the **Bug report** template. For an idea, use **Feature request**.
- **Replace your IDs first:** this repository is public. Before you paste output into an issue, replace subscription, tenant, object, client, and workspace IDs, the T3 and T4 server names' random suffix, and your account with placeholders such as `<subscriptionId>`, and never paste a token, a password, or a webhook URL.
- **A security problem:** report it privately, as [SECURITY.md](SECURITY.md) describes, never in an issue.
- **Questions about the products** (Database Hub, the Database Agent, Fabric, Azure Arc): see [Microsoft Learn](https://learn.microsoft.com/fabric/database/hub/overview) and the [official sources](docs/references.md); this repository is a demo, not a product support channel.
