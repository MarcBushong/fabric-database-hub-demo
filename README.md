# Fabric Database Hub hybrid SQL demo

A low-cost, repeatable customer demo of **Microsoft Fabric Database Hub**, generally available since Microsoft Ignite on 2026-11-17, with its **Copilot** and **Database Agents** (previews). It runs across five targets, three SQL Server, one PostgreSQL, and one Azure Cosmos DB, and deploys with one command into your own Azure subscription and Fabric capacity. Each session is one **Run all** in a Fabric notebook.

**The story:** fragmented visibility before; one hybrid estate in Database Hub after, with what needs attention, what changed, and which server is ready to migrate; then a live incident (locking, CPU, IO, a missing index, an inefficient query, a read replica that falls behind, or a throttled Cosmos DB container) that the presenter investigates with Copilot, and, on T3, the whole Database Agent loop: the agent raises the issue, Copilot explains it, a person responds, and the agent tracks it to its close. Every action an agent proposes needs a person's approval.

> **What's generally available, and what's a preview:** Database Hub is generally available (2026-11-17): its estate, performance, security, and optimization views, its real-time dashboards for SQL, PostgreSQL, and Cosmos DB, its SSMS and VS Code entry points, bulk monitoring enablement, and its CLI skill. Copilot, Database Agents, alerts, and SQL Server on Azure VM monitoring are still previews, as are unified inventory, the Arc SQL monitoring setting, the telemetry endpoint, and Fabric Apps, and they can change. Database Hub's own views need no Fabric capacity; Copilot, custom alerts, shared dashboards, and the demo's notebooks and app do. This repo uses only documented interfaces, with one narrow, read-only exception: the Insights app's live estate. It says plainly what's manual, unsupported, or not yet proven ([limitations](docs/limitations.md#preview-disclosures)).

## Quick start

1. **Sign in:** `az login` (in a codespace or a container, `az login --use-device-code`). You sign in; the scripts never do.
2. **Deploy:** `./scripts/deploy.ps1`. It does everything else and ends **DONE** or **NOT DONE**, with the exact next command. A first deployment takes about an hour and a half, and needs nobody while it runs.
3. **Do what DONE lists, once:** when you aren't an Owner of the subscription, an Owner runs `./scripts/grant-safety-stop.ps1`; and, optionally, select T3 for Database Agents ([demo it yourself](#demo-it-yourself)).
4. **Each session:** resume your Fabric capacity, open `NB_DatabaseHub_Control`, and select **Run all**, about 30 minutes before your audience. It starts everything, runs a 90-minute showcase on all five targets, and stops it all at the end.
5. **Stop now, if you need to:** `./scripts/stop-demo.ps1`. A new deployment keeps running until you do, or until the nightly safety stop at 19:00, which catches whatever you forget; a `start-demo.ps1` session stops by itself after 4 hours.
6. **Later:** update with `./scripts/deploy.ps1` again ([upgrading](#upgrading-an-existing-demo)); delete everything with `./scripts/destroy.ps1` ([delete everything](#delete-everything)).

**Already have a demo in this subscription?** A fresh clone's first `./scripts/deploy.ps1` finds the one that's yours and updates it. For a second, separate environment beside it, run `./scripts/init.ps1 -Prefix <prefix> -CreateAdminGroup` first, then `./scripts/deploy.ps1`. It gets its own Fabric workspace, "Database Hub Demo &lt;prefix&gt;", unless `-WorkspaceName` names another. If `init.ps1` asks for something, such as which capacity, run the command it prints: it keeps your `-Prefix`.

```powershell
git clone https://github.com/MarcBushong/fabric-database-hub-demo.git   # or "Use this template", or a codespace
cd fabric-database-hub-demo
az login                 # you sign in; in a codespace or a container: az login --use-device-code
./scripts/deploy.ps1     # everything else, in one command
```

**What it costs:** about $3 an hour while it runs, about $6 for a Run all session, and about $43 a month while it's stopped, at list prices, before your subscription's Defender for Cloud plans; the Fabric capacity, licenses, and each viewer's GitHub Copilot plan aren't included ([what it costs](#what-it-costs)).

- PowerShell 7.4, the Azure CLI with Bicep, Node.js 24, and Git. The repository's [dev container](.devcontainer/devcontainer.json) has them all, locally or in GitHub Codespaces. On Windows, `deploy.ps1` installs the .NET SDK for you.
- For the Copilot chat in the Insights app: each viewer's own GitHub account with a GitHub Copilot plan.

### What deploy.ps1 does, and how it ends

On its first run, `deploy.ps1` writes `config/demo.config.json` from your sign-in, asking only for your subscription and your capacity, and creates the Microsoft Entra group that administers T3 and T4 (`./scripts/init.ps1 -CreateAdminGroup` does the same on its own, if you'd rather choose settings first). Then it checks everything (preflight), deploys the targets and the Fabric items in parallel tracks, and waits for T2, which needs nobody: its host downloads [Arc Jumpstart](https://github.com/Azure/arc_jumpstart_docs/blob/71a945c619f78acb441c6470d76a9b58347169fe/docs/azure_jumpstart_arcbox/ITPro/_index.md)'s prebuilt SQL Server 2022 Standard guest. A live status page, `out/deploy-status.html`, follows the run (`./scripts/status.ps1 -Watch` in a terminal), and a Windows PC stays awake. Before each run, it updates a clean checkout of `main` from GitHub; `-NoSelfUpdate` runs the code you have.

- **DONE:** Database Hub shows every target. The banner names, first, what an Owner still has to grant, if anything; then where Run all is, where to look, and which activity runs; and it lists under **Please confirm** what only you can check, such as a tenant setting it couldn't read, or the optional Database Agents step. None of that keeps it from **DONE**. A new deployment keeps running, so you can look at it right away, and **DONE** says what it bills an hour, until when, and that `./scripts/stop-demo.ps1` stops it now; an update of a demo that was stopped stops it again at its end ([upgrading](#upgrading-an-existing-demo)).
- **NOT DONE:** why, the single next action, and the exact command: usually `./scripts/deploy.ps1` again, which continues where it stopped, also after the window closes or the PC restarts.
- **The Insights app and its chat** deploy with your `az login`. When either can't be, the run still ends **DONE**, and the status page says why, with the fix; a browser sign-in, `./scripts/configure-fabric-app.ps1 -SignIn`, is needed only if Fabric refuses your Azure CLI's token.

**See it:** open **Database Hub** in the Fabric portal and look at Estate and Performance. The default activity, `business-day`, runs bounded incidents at fixed minutes every hour, so Performance's problem panels fill within the hour; investigate what you see with Copilot in Database Hub.

**More:** [deployment](docs/deployment.md#deploy-it-step-by-step) has every step, option, and command, and [how long each takes](docs/deployment.md#how-long-each-step-takes). An AI assistant can run it for you, but `az login` stays yours ([running it with an AI assistant](docs/deployment.md#running-it-with-an-ai-assistant), [AGENTS.md](AGENTS.md)).

## Demo it yourself

Whoever deploys the demo can present it, as often as they like, with the same steps every time.

**Once per deployment:**

1. **Deploy:** `az login`, then `./scripts/deploy.ps1`, and wait for **DONE** ([quick start](#quick-start)). An upgrade is the same command. If **DONE**'s first note names `./scripts/grant-safety-stop.ps1`, an Owner runs it once: Run all needs the roles and the vault access it grants.
2. **Optional, for the Database Agent loop on T3: select T3 for Database Agents,** about 30 seconds, while T3 is awake (right after **DONE**, or during a session). Database Agents has no API, so **DONE** and the status page list it under **Please confirm** (`HUB.AGENT.T3`), with the link and the exact database. In [Database Hub](https://app.fabric.microsoft.com/workloads/fdh/databaseHub), select **Manage agents** > **Database agent settings** and turn **Enabled** on. Every database starts selected ("All databases are included by default"), and the selection is saved for your whole tenant, so:
   - **If only you use Database Agents in this tenant** (a demo or lab tenant): clear the selection, select `azuresql01-<deploymentId>/ContosoCare`, turn on **Flag long-running queries**, **Force last known good plans**, and **Flag high CPU**, then **Apply** and **Save**. If **Save** says "Database agent changes couldn't be saved", uncheck the databases that no longer exist, are paused, have one vCore, or are outside your Fabric home region, then **Save** again.
   - **If others use Database Agents in your tenant:** don't clear or uncheck their databases, which would stop the agent watching them. Select T3 with the same policies in addition, then **Apply** and **Save**. A **Save** checks your write access on every selected database, so if it fails on one of theirs, ask whoever manages Database Agents in your tenant to add T3, rather than removing theirs.

   The list shows no server, so every environment's T3 is a row named `ContosoCare`: when several are, check them one at a time and **Save**, and uncheck again any whose **Save** fails ([troubleshooting](docs/troubleshooting.md#t3)). It stays selected through sessions and upgrades, unless T3 is recreated (`stop-demo.ps1 -RemoveT3`); when you delete the demo, uncheck only your T3 (`destroy.ps1` says so). Database Agents covers Azure SQL Database, so T3 only; without it, every other moment still works ([the Database Agent loop](docs/demo-walkthrough.md#the-database-agent-loop-on-t3)).
3. **Each viewer, once per browser: sign in with GitHub in the Insights app's chat,** `APP_DatabaseHub_Insights` in the demo workspace. Its Copilot chat uses the viewer's own GitHub Copilot plan ([the Copilot chat](#the-copilot-chat-in-the-insights-app), [the Insights app](fabric/app/README.md)).

**Every session:**

1. **Run all:** resume the Fabric capacity if it's paused (Run all never resumes it), open `NB_DatabaseHub_Control`, and select **Run all**, about 30 minutes before your audience: the first data reaches Database Hub 10 to 35 minutes after it starts ([what fills each visual, and when](docs/database-hub-visuals.md)). There's nothing to edit, and the guide it prints gives each moment's time in your clock.
2. **Show the DBA moments** (the rehearsal steps are in [the walkthrough](docs/demo-walkthrough.md#the-dba-moments-in-a-run-all-session)):
   - **[Open at Overview](docs/demo-walkthrough.md#open-at-overview):** **What needs attention**, then **Recent signal changes**. Ask Copilot "What changed in my databases?", "Which resource should I investigate next?", and "Which security findings should I address first?".
   - **[T2 ready to migrate](docs/demo-walkthrough.md#optimization-t2-ready-to-migrate):** Overview's **Optimization** card or **Estate**, then T2 (`arcsql01`) and its migration assessment: its readiness for each Azure SQL target and the recommended size, at no charge. The Azure portal's **Assessments** page for `arcsql01` always has it. T1 and T2 show no license finding because they already use pay-as-you-go.
   - **[The Database Agent loop on T3](docs/demo-walkthrough.md#the-database-agent-loop-on-t3),** from about 30 to 60 minutes into the session, when you selected T3: T3's plan regresses, and about 15 minutes later the agent raises an issue. Open it, select **Explain why**, then **Analyze slow query**. When the notebook prints "Now: T3 Respond", Run all makes the manual response, forcing the last good plan; T3's CPU falls, and the issue closes, or you close it once you've checked.
   - **[T5's RU storm](docs/demo-walkthrough.md#t5-azure-cosmos-dbs-ru-storm),** at minutes 3 and 18 of each 30-minute cycle: in **Estate**, filter to Azure Cosmos DB and select `cosmos01-<deploymentId>`, then **Performance**: **Normalized RU Consumption** at 100% with **Throttled Requests (429s)**, while **Availability** stays at 100%; both recover when the storm ends. Nothing to sign in to or set up.
3. **The end:** Run all stops everything and saves the session's history. The report and the Insights app show it, with T3's CPU before and after the response.

**Reset, stop, and repeat:** every Run all repeats the moments. The agent raises a new issue each session (closed ones stay in its history), `FORCE_LAST_GOOD_PLAN` comes back on however a session ends (`./scripts/status.ps1` shows it), T2's assessment stays on through upgrades, and T5's storm deletes its documents when it ends, so every session's storm starts from the same data. To start clean: `RESET_NOW = True` in the notebook, or `./scripts/reset-demo.ps1`. To stop from a PC: `./scripts/stop-demo.ps1`. The [nightly stop](#what-stops-or-pauses-on-its-own) catches what you forget.

### The Copilot chat in the Insights app

Ask questions about the estate in the Insights app itself, on your own GitHub Copilot: Copilot runs read-only queries on the demo's history, answers with the app's own charts, and shows the query behind every answer. Its live estate tool can't read Database Hub today, which refuses the app's own sign-in (R924), so it says so, and Database Hub itself has the live view. Nothing to install, and nothing to register ([ADR 0028](docs/adr/0028-ask-copilot-in-the-insights-app.md)).

1. **Open the Insights app** from its workspace item, and select **Ask Copilot**: the chat docks on the right; drag its edge, or make it full screen. It wakes its relay as it opens, and so does `./scripts/start-demo.ps1`; after a quiet spell the first answer takes a few seconds more.
2. **Sign in with GitHub, once per browser:** select **Sign in with GitHub**. It copies a code and opens github.com/login/device in a new tab: paste the code, check that the app is **Database Hub Insights Ask**, and select **Authorize**. Use the GitHub account that has your Copilot plan; it can differ from your Fabric account. The chat continues by itself and keeps you signed in on this browser for up to six months. GitHub may show the request coming from the chat's relay in Azure, not from where you are.
3. **Ask:** pick a starter, such as **Which target worked hardest this week?**, or type a question; **Was Cosmos DB throttled?** charts T5's RU storm once its metrics are in the history. Select **Ask why** on a chart, and **Show the source** under an answer to see its DAX or the Database Hub API routes it read. **New chat** starts over for the next audience; **Export** saves the conversation with every query.

**When it says it can't:** the chat says what's wrong and what to do. Only two things need someone else, and only in some tenants: an organization that restricts OAuth apps, whose owner approves **Database Hub Insights Ask** once for the account that gives you Copilot; and the Fabric tenant setting "Enforce a strict content security policy for static-hosted Fabric Apps (preview)", which must stay off, as it is by default (`deploy.ps1` reports a **Warning** when it's on). **What goes to GitHub Copilot:** your questions, a guide to the history model (names, not data), and the results of the read-only queries it runs, never a password or an Azure or Fabric token ([security model](docs/security-model.md#ask-the-copilot-chat-in-the-insights-app-2026-11-18)). **Sign out of GitHub** is in the chat's account menu, with **Switch GitHub account**; to remove the app's access for good, revoke **Database Hub Insights Ask** in GitHub's settings ([delete everything](#delete-everything)).

## Day to day

- **Run a session:** Run all ([every session](#demo-it-yourself)). It starts the VMs, T4, T4's read replica, and T5's container, runs the 90-minute showcase of bounded incidents on all five targets, prints a presenter's guide with each moment's time and Copilot prompts, then stops everything and saves the session's history ([the notebook's guide](fabric/control/README.md)).
- **Or from your PC:** `./scripts/start-demo.ps1` (about 10 minutes, T4's read replica included), then `./scripts/stop-demo.ps1 -SaveHistory`, which saves the session's history. If you forget the stop, the session stops by itself 4 hours after its start (`-Hours` changes that; running `start-demo.ps1` again starts the hours over), and `START.CONTROL.AUTOSTOP` says when; a later Run all or the Insights app's **Start** replaces it with its own plan.
- **Stop now:** `./scripts/stop-demo.ps1`: it turns the activity off, shuts T2's guest down, deallocates both VMs, deletes T4's read replica, stops T4, and deletes T5's container, which the next session creates again (`STOP.T5`). Or the notebook's **Stop now** cell, with `STOP_NOW = True`. If you forget, the [nightly stop](#what-stops-or-pauses-on-its-own) stops the demo that evening.
- **See where it stands:** `./scripts/status.ps1`, read-only; `-Detail` adds more.
- **An incident right now:** `./scripts/demo-control.ps1 -Target T2 -Scenario incident:cpu-pressure -Duration 25`. `-Target T4 -Scenario incident:replica-lag -Duration 10` makes T4's read replica fall about 4 minutes behind, then catch up, and `-Target T5 -Scenario incident:ru-storm -Duration 10` drives T5's normalized RU to 100% with throttled (429) requests, then lets it recover; both need a session. During a Run all session, an incident on a target replaces that target's showcase until it ends (on T3, it ends the Database Agent loop). `./scripts/reset-demo.ps1` goes back to a known state without a redeploy.
- **`deploy.ps1` ended NOT DONE:** run the command its banner prints, usually `./scripts/deploy.ps1` again; it continues where it stopped. The banner and the status page, `out/deploy-status.html`, say why.
- **A sign-in error** (an expired token, "AADSTS", "TokenCreatedWithOutdatedPolicies", or Microsoft Graph refusing): run `az login --tenant <tenantId>` yourself (`az login --use-device-code` in a codespace), then the same command again. The scripts never sign in for you, and never change your default subscription ([your sign-in and tokens](docs/security-model.md#your-sign-in-and-tokens)).

**Where to show it:** **Database Hub** is the live product view, and the product you're demonstrating; its own views need no capacity. The **Insights app**, `APP_DatabaseHub_Insights`, opened from its workspace item, is the demo's own operations product: Mission Control, the "Did we catch it?" scoreboard, a replay, and a postmortem of each session, from the saved history, with Ask, its GitHub Copilot chat, and Manage ([the 3-minute WOW](docs/demo-walkthrough.md#the-3-minute-wow-what-only-the-app-shows)). Beside them, the Real-Time Dashboard `RTD_DatabaseHub_LiveView` is the live view as code, and the Power BI report `RPT_DatabaseHub_History` the saved history. [Presentation surfaces](docs/presentation.md) says what each viewer needs, and the [demo walkthrough](docs/demo-walkthrough.md) has 15- and 30-minute scripts.

## What you control

- **The configuration**, `config/demo.config.json`, which `init.ps1` or `deploy.ps1`'s first run writes. A change takes effect at the next `./scripts/deploy.ps1`; [configuration](docs/configuration.md) explains the settings you're most likely to change, and `config/environment.schema.json` describes every one:
  - where: `subscriptionId`, `tenantId`, `location`, `prefix`, and `environment`;
  - size and cost: `profile` (`lowest-cost` by default), `t4SkuName`, `monthlyCeilingUsd`, `sessionCeilingUsd`, `t5UseFreeTier` (`true` by default: T5 takes the subscription's free tier when it's free, set only when the account is created; Azure doesn't offer it to internal subscriptions), and `t5Enabled` (`true` by default; `false` leaves T5 out of the next deployments, and an existing account stays, billing, until `destroy.ps1`);
  - when the demo stops: `autoShutdownTime` and `autoShutdownTimeZone`, which the VMs' auto-shutdown and the nightly safety stop use, and `t3AutoPauseMinutes`;
  - the activity: `activityProfile` (`business-day` by default; `baseline` for a quiet demo);
  - who presents: `presenterObjectIds`, whom `deploy.ps1` adds to the demo workspace as Viewers (and, with `assignRoles`, gives the Azure roles Database Hub needs);
  - Fabric: `fabric.workspaceName`, `fabric.capacityName`, and `fabric.lakehouseName`; and the control's `control.fabricWorkspaceName` and `control.roleNameSuffix`. Each environment needs its own `fabric.workspaceName`, and its own `control.fabricWorkspaceName` when its configuration sets one. A new environment with any prefix but the default gets "Database Hub Demo `<prefix>`" (2026-11-19). Two environments in one workspace overwrite each other's notebooks: `deploy.ps1` stops before it creates anything in a workspace that another environment records and this one doesn't (`DEPLOY.FABRIC.SHARED`, a **Fail**), says so in a **Warning** for two that share one already, and `destroy.ps1` keeps that workspace;
  - the Copilot chat: `ask.enabled` (on by default), and, rarely, `ask.githubClientId` for your own GitHub OAuth App or `ask.image` for your own relay image, pinned by digest.
- **`deploy.ps1`'s switches**, rarely needed: `-FromStage <stage>` runs again from a stage, `-StopAfter <stage>` stops after one, `-SkipFabric` leaves Fabric alone, `-NoSelfUpdate` runs the code you have, `-KeepRunning` leaves the demo running after an update that found it stopped (to demo right away), and `-WhatIf` changes nothing.
- **Run all's parameters,** in the control notebook's first cell; none needs editing: `DURATION_MINUTES` (90 by default, 30 to 120), `MODE` (`"check"` shows the plan and sends nothing), and `STOP_NOW = True` or `RESET_NOW = True` for its **Stop now** and **Reset** cells ([the switches](fabric/control/README.md#the-switches)).
- **A session's switches:** `start-demo.ps1 -ActivityProfile <name>`, `-SkipT4Replica`, and `-Hours <n>` (when the session stops by itself: 4 by default, 0.5 to 24); `stop-demo.ps1 -SaveHistory`, `-ParkT2`, and `-RemoveT3`.
- **The nightly stop:** at `autoShutdownTime` every evening. To skip one night, turn its schedules off ([what stops or pauses on its own](#what-stops-or-pauses-on-its-own)); the next `./scripts/deploy.ps1` turns them on again.
- **What isn't yours to set here:** the Fabric capacity, which you or its administrator resume and pause, licenses, and Database Hub's tenant setting.

## What stops or pauses on its own

Nothing here needs you, and nothing here starts anything: only Azure starts a stopped T4 again, 7 days after its stop, and the nightly safety stop stops it again within a day. Times are the defaults: `autoShutdownTime` 19:00, in `autoShutdownTimeZone`.

| What | When | What it does |
|---|---|---|
| The VMs' auto-shutdown | Daily at `autoShutdownTime` | Deallocates `sqlvm01` and `archost01`; T2's guest stops with its host |
| The nightly safety stop | The same time, and its T3 check 30 minutes later | Deallocates a VM that still runs, stops T4, after Azure's 7-day restart too, stops a read replica that a session left behind, and deletes T5's container when a session or `deploy.ps1` left it (the next session creates it again). It never starts or creates anything. It waits for a `deploy.ps1` that's still running, then stops the demo 60 minutes after the run ends, and **DONE** says when |
| T3's auto-pause | `t3AutoPauseMinutes` (15) after its last session | Azure pauses the serverless database, which then bills only its storage |
| A Run all session's auto-stop | 10 minutes after the session's end, and a backup 30 minutes later that runs only when the first one failed | Deletes T4's read replica, stops T4, deallocates the VMs, and deletes T5's container |
| A `start-demo.ps1` session's auto-stop | 4 hours after `start-demo.ps1` (`-Hours`), or after the warm-up it waits for | The same as Run all's. A later Run all or the Insights app's **Start** replaces it, `start-demo.ps1` again starts the hours over, `stop-demo.ps1` removes it, and it waits for a `deploy.ps1` that's still running. Without the session control's role (before an Owner's `./scripts/grant-safety-stop.ps1`) there's none, and a **Warning** says the nightly stop is the limit |
| The end of a `deploy.ps1` update | Once **DONE**'s checks are done | Stops again what the update started when the demo was stopped as it began (`DEPLOY.ENDSTOP`). A new deployment, a demo that was running, a session that started meanwhile, and `-KeepRunning` keep it running, and **DONE** says what it bills an hour and until when |
| The control's daily T4 safety stop | 15 minutes after `autoShutdownTime` | Stops T4 when it runs, then a left-over read replica, and deletes T5's container while `sqlvm01` isn't running |
| Ask's chat relay | About 10 minutes after the last question | Scales to zero, so it bills nothing until the next question |

- **To skip one night:** turn off the schedules `dbhub-safety-stop` and `dbhub-safety-t3check` in `aa-<prefix>-<environment>-safetystop` (and `dbhub-safety-deferred` when a run left one), the session control's `dbhub-t4-safety-stop` in `aa-<prefix>-control`, which stops T4 too, and the VMs' auto-shutdown in the Azure portal. Turn them on again the next day; the next `./scripts/deploy.ps1` turns the nightly safety stop's on again.
- **Where to see it:** `./scripts/status.ps1` (`STATUS.SAFETYSTOP` and `STATUS.NIGHTLYSTOP`). [Cost management](docs/cost-management.md#what-stops-or-pauses-on-its-own) lists every schedule, with the hours each part runs.
- The Fabric capacity isn't on this list: you or its administrator pause it.

## Upgrading an existing demo

- **Nothing changes until you run `./scripts/deploy.ps1`.** The deployed environment never reads GitHub, and a newer copy of the scripts works with it: `status.ps1`, `start-demo.ps1`, and `stop-demo.ps1` say what isn't deployed yet, with `./scripts/deploy.ps1` as the fix, never as a **Fail**.
- **One command:** `./scripts/deploy.ps1`. A plain run updates the demo it finds: the environment your configuration file names, or, without one, the one in this subscription that's yours (below). It first updates a clean checkout of `main` from GitHub, then runs that code; `-NoSelfUpdate` runs the code you have. Your configuration file needs no edit, and the run continues where it stopped if it's interrupted.
- **Without your configuration file** (a fresh clone, another PC; [#60](https://github.com/MarcBushong/fabric-database-hub-demo/issues/60)): the same command's first run writes it from what's deployed when the environment is yours (its owner tag or budget address is your sign-in, or you own the group that administers its T3 and T4), so the update changes nothing you didn't ask for; `INIT.EXISTING` lists the settings that kept their defaults. When it isn't yours, or that can't be told, the run never updates it: it deploys a new environment with the next free prefix (`dbhub2`, ...). To update an environment with another prefix, run `./scripts/init.ps1 -Prefix <prefix>` first; to add a second environment beside yours instead, see the [quick start](#quick-start) ([deployment](docs/deployment.md#first-run-initps1)). Every command `init.ps1` then prints names that `-Prefix`, and `init.ps1 -Force` keeps the prefix of the file it replaces.
- **What that run adds and changes,** with nothing to do by hand: T4's read replica for each session; the session control behind Run all (a control you set up before is adopted as it is); **T5**, the Azure Cosmos DB account, with T1's access to it and its place in Run all, and its container only during a session; the redesigned Insights app with Ask, its Copilot chat (registering the `Microsoft.App` resource provider when the subscription hasn't); T3 at 2 vCores, scaled online (under 30 seconds of interruption; a free-offer database keeps its offer); T2's migration assessment, turned on with its first run; a configuration whose session ceiling is exactly 15 gets the new 20. It republishes the runbooks, the notebooks, the history model, the Insights app, and the workload runner, and keeps the lakehouse's history and T4's data. A T4 that `t4SkuName` doesn't size moves to the default, `Standard_D4ds_v5`, once, with a restart, when it's on another size. It brings back a T2 host whose VM agent no longer starts, rebuilding only that VM, once, when nothing else works (about 70 minutes more), and retries a step into T2's guest that PowerShell Direct broke, restarting the guest once when needed ([#65](https://github.com/MarcBushong/fabric-database-hub-demo/issues/65); `DEPLOY.T2.GUESTRETRY`, `DEPLOY.T2.GUESTRESTART`).
- **It leaves the demo as it found it:** when the demo was stopped as the run began, the run stops again what it started once **DONE**'s checks are done, through `stop-demo.ps1`'s own stop, so an update no longer bills until the nightly stop. It first waits, at most 15 minutes, for work that still needs the hosts, such as T2's first migration assessment. **DONE** and the status page's **Stop at the end** row say what it stopped (`DEPLOY.ENDSTOP`); a stop that fails is a **Warning** with `./scripts/stop-demo.ps1` as the fix, never **NOT DONE**. To demo right after the update, run `./scripts/deploy.ps1 -KeepRunning`, or `./scripts/start-demo.ps1` afterwards.
- **What you may do once afterward:** when you aren't an Owner, an Owner runs `./scripts/grant-safety-stop.ps1`, which **DONE** prints first: it grants the nightly safety stop's and the session control's roles, and gives you, who deployed, the control vault's secrets, so you can Run all with nothing to edit; until then T5's container stays between sessions; optionally, select T3 for Database Agents (`HUB.AGENT.T3`, under **Please confirm**; [demo it yourself](#demo-it-yourself)); and each viewer signs in to GitHub once per browser for the chat.
- **`destroy.ps1` deletes more than it used to** (2026-11-17): also the session control, the Fabric workspaces with the history in the lakehouse, and the administrators' group that `init.ps1` created, each only when it's this environment's ([delete everything](#delete-everything)).
- **Cost:** between sessions, nothing new bills but T5's private endpoint and DNS zone; the rest is in [what it costs](#what-it-costs). In a Contributor's environment, until an Owner's grant, only `stop-demo.ps1` deletes T5's container, so the estimate prices it all month; when only that puts the month over your `monthlyCeilingUsd`, preflight and `start-demo.ps1` warn instead of failing, with the fix, and the update goes on.

[Deployment](docs/deployment.md#update-an-existing-environment) has each change in detail, and the [changelog](CHANGELOG.md) lists them by release.

## Delete everything

`./scripts/destroy.ps1` deletes everything `deploy.ps1` created for the environment in your configuration. First it lists what it deletes and what it keeps, and asks you to confirm; `-Force` doesn't ask. Each part reports its own `DESTROY.*` result. The Fabric, session control, and group parts run first, and one that fails doesn't stop the others; a **Fail** in the Arc or resource group part stops what comes after it, so run `destroy.ps1` again to finish.

**What it deletes, in this order,** each part only when it can tell it's this environment's:

1. **Fabric:** the control's workspace with its managed private endpoint, when its control notebook serves this environment, and the demo's workspace, when every item in it is one the demo creates, the control notebook's folder and the Insights app's three items (the app and its two user data functions) included. A workspace that holds anything else stays whole, and its result names what isn't the demo's. Neither goes while another environment uses it, or might (below). `-KeepFabric` keeps both workspaces, with the history in the lakehouse. A Fabric administrator can restore a deleted workspace during your tenant's retention period, 7 days by default ([retention and recovery](https://learn.microsoft.com/fabric/admin/portal-workspaces#retention-and-recovery)).
2. **The session control** in `rg-<prefix>-control`, when its runbooks serve this environment's resource group: its role assignments, its custom roles once no other assignment holds them, the identity, the Key Vault (purged), and the Automation account with its runbooks, schedules, and webhook; then the group, once it's empty. Deleting role assignments needs Owner or User Access Administrator: for anyone else, `DESTROY.CONTROL.ROLES` is **Manual action required** with the fix, and the rest still goes.
3. **The T3 and T4 administrators' group,** when `init.ps1` created it for this environment.
4. **T2's Arc resources:** the SQL Server instances, then the machine.
5. **T4's read replica,** when a session left one (Azure deletes replicas before their primary).
6. **The resource group** and everything in it, T5 and the chat relay included, then the deployment record and the group's budget, which outlive the group.
7. **The custom role "DbHub Demo Safety Stop",** once no role assignment holds it.

Then it checks that nothing of the environment is left (`DESTROY.RESIDUAL`, [cleanup](docs/cleanup.md)).

**What it keeps, and how to remove it:**

- **The Fabric capacity and your licenses:** you manage them, and no script deletes them.
- **T3's selection in Database Agents,** if you made it: Database Hub keeps a deleted database selected, and a **Save** checks every selected one, so the deleted T3 fails every later **Save** there, by anyone in your tenant, a new deployment's included. No API removes it, so `destroy.ps1` says so before it asks and at its end (`DESTROY.HUB.AGENT.T3`, with the link): in Database Hub, **Manage agents** > **Database agent settings**, uncheck only `azuresql01-<deploymentId>/ContosoCare` and **Save**, before or after `destroy.ps1`, and leave every other database as it is ([cleanup](docs/cleanup.md#what-stays-and-how-to-remove-it)).
- **`rg-<prefix>-golden`, when you captured a golden snapshot:** the next `deploy.ps1` restores T2 from it. It bills every month until `./scripts/destroy.ps1 -IncludeGolden` deletes it.
- **What another environment uses:** a custom role that another environment's role assignments hold, a session control whose runbooks serve another resource group, or a workspace with items that aren't the demo's. Each result names it and says why it stayed.
- **A Fabric workspace another demo environment uses, or might:** each `deploy.ps1` records its environment's workspaces on its resource group, and `destroy.ps1` keeps any workspace another environment records, and every workspace while it can't tell, with a **Warning** (`DESTROY.FABRIC.WORKSPACE` or `DESTROY.FABRIC.CONTROL`) that names the other environment and the fix ([cleanup](docs/cleanup.md)). With one environment, the usual case, everything still goes in one command.
- **A security group you supplied** rather than `init.ps1 -CreateAdminGroup`: delete it in the Microsoft Entra admin center when nothing else uses it.
- **What's on your PC and in GitHub:** the Insights app's Git-ignored deploy stage `out/fabric-app` (delete it if you won't deploy again); your Azure CLI's and the Rayfin CLI's sign-ins (`./out/fabric-app/node_modules/.bin/rayfin logout`, then `az logout`; [your sign-in](docs/security-model.md#your-sign-in-and-tokens)); and **each viewer's GitHub authorization of Database Hub Insights Ask**, the chat's OAuth App: each viewer revokes it at [github.com/settings/applications](https://github.com/settings/applications) (**Authorized OAuth Apps**), and **Sign out of GitHub** in the chat clears a browser's sign-in. The app's deployment makes nothing else: no Microsoft Entra app, service principal, or Fabric connection.
- **Subscription settings:** resource provider registrations, such as `Microsoft.App` for the chat relay, which cost nothing and other resources may use, and the Defender for Cloud plans your tenant turns on.
- **Your tenant's own role assignments:** your tenant's automation may give the demo's identities role assignments outside the demo. They stay behind, orphaned; they don't bill, the residual check reports them as a **Warning** that names the scope, and removing one needs Owner or User Access Administrator.

**How long:** about 20 minutes. Measured on 2026-11-17 in two test environments: 16 minutes with the resource group, 10.5 of them for the group's delete; the Fabric, control, and group parts took 3 to 5 minutes more in a second run. If it's interrupted, run it again: it finishes what's left, also once the resource group is gone.

**Only the session control:** `./scripts/setup-activity-control.ps1 -Remove` deletes it alone (`-WhatIf` shows what), and the next `deploy.ps1` sets it up again.

## Troubleshooting and help

- **A result that isn't Pass:** every check reports one of six statuses: **Pass**, **Fail**, **Warning**, **Manual action required**, **Not supported**, or **Not selected**, and a successful deployment alone is never **Pass**. Every **Fail**, **Warning**, and **Manual action required** comes with its remediation, and [troubleshooting](docs/troubleshooting.md) explains the common ones; the [FAQ](docs/faq.md) and [limitations](docs/limitations.md) cover what's out of scope. `./scripts/status.ps1` (read-only) shows where an environment stands.
- **A deployment that doesn't finish:** `deploy.ps1` ends **NOT DONE** with the next command; run it, and if the same thing happens again, run `./scripts/collect-diagnostics.ps1`. It writes a zip of the run's results, progress, and logs, redacted, with your IDs and account replaced, and refuses to write one that its secret scan doesn't pass. Open an issue with the **Deployment problem** template, which asks for the command, how the run ended, the results that aren't **Pass**, and the zip (read it before you attach it).
- **A bug in the code or the docs:** open an issue with the **Bug report** template. For an idea, use **Feature request**.
- **Replace your IDs first:** this repository is public. Before you paste output into an issue, replace subscription, tenant, object, client, and workspace IDs, the T3 and T4 server names' random suffix, and your account with placeholders such as `<subscriptionId>`, and never paste a token, a password, or a webhook URL.
- **A security problem:** report it privately, as [SECURITY.md](SECURITY.md) describes, never in an issue.
- **Questions about the products** (Database Hub, its Copilot and Database Agents, Fabric, Azure Arc): see [Microsoft Learn](https://learn.microsoft.com/fabric/database/hub/overview) and the [official sources](docs/references.md); this repository is a demo, not a product support channel.
